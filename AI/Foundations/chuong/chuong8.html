1. Vì sao PyTorch

PyTorch chiếm ưu thế trong nghiên cứu và ngày càng phổ biến trong production. Ba lý do:

  • Đồ thị tính toán động. Đồ thị được dựng trong lúc code chạy, nên bạn có thể dùng if, for, và print ở giữa mô hình. Debug bằng cách in ra shape là chuyện bình thường.
  • API giống NumPy. Nếu đã quen chương 3, phần lớn cú pháp là quen thuộc.
  • Hệ sinh thái. Hugging Face transformers, và gần như mọi mô hình mã nguồn mở, đều dựng trên PyTorch.
🔗 Bạn có cần PyTorch để làm AI Engineer không?

Trả lời thẳng: không bắt buộc, nhưng nên biết ở mức đọc hiểu.

Nếu công việc của bạn là gọi API LLM và xây hệ thống quanh nó (phần lớn AI Engineer), bạn sẽ hiếm khi viết PyTorch. Nhưng bạn sẽ đọc code PyTorch khi tìm hiểu một mô hình, và bạn sẽ cần nó nếu đụng tới fine-tuning ở 10.5 chương 3. Chương này cho bạn đủ để không bị chặn ở hai tình huống đó.

2. Tensor

tensor giống ndarray của NumPy, cộng thêm hai thứ: thiết bị (CPU hay GPU) và khả năng theo dõi gradient.

python
import torch

x = torch.tensor([[1.0, 2.0], [3.0, 4.0]])

print(x.shape)     # torch.Size([2, 2])
print(x.dtype)     # torch.float32   ← mặc định là float32, KHÁC NumPy (float64)
print(x.device)    # cpu

# Phần lớn thao tác giống hệt NumPy
x + 1
x @ x
x.sum(dim=0)      # PyTorch dùng dim= thay cho axis=
x.reshape(4)
x[x > 2]

# Chuyển đổi với NumPy — CHIA SẺ bộ nhớ, không sao chép
import numpy as np
a = x.numpy()          # tensor → ndarray
y = torch.from_numpy(a) # ndarray → tensor
a[0, 0] = 99

⚠️ Ba khác biệt với NumPy hay gây bất ngờ
  1. dim= thay cho axis=. Ý nghĩa giống hệt (chiều biến mất), chỉ khác tên tham số.
  2. Mặc định là float32, không phải float64. Trộn tensor float32 với mảng NumPy float64 sẽ báo lỗi kiểu.
  3. .numpy() và from_numpy() chia sẻ bộ nhớ. Sửa một bên là sửa cả hai. Dùng .clone() nếu muốn bản sao độc lập.

3. Autograd

Đây là trái tim của PyTorch. Đặt requires_grad=True, và PyTorch sẽ ghi lại mọi phép toán áp lên tensor đó để có thể tính gradient ngược lại.

python
x = torch.tensor(2.0, requires_grad=True)

y = x ** 2 + 3 * x        # PyTorch ghi lại: bình phương, nhân, cộng
y.backward()               # tính gradient ngược về x

print(x.grad)              # tensor(7.)
# Kiểm chứng bằng tay: dy/dx = 2x + 3 = 2(2) + 3 = 7 ✓
# Đây đúng là hàm ở chương 2, mục 4.1

So sánh với chương 7: những gì bạn tính tay qua mười bước, .backward() làm trong một dòng — và làm đúng như vậy cho mạng có hàng tỉ tham số.

3.1. Gradient được tích luỹ, không ghi đè

Đây là hành vi gây bất ngờ nhất của PyTorch, và là nguồn gốc của lỗi phổ biến nhất với người mới:

python
x = torch.tensor(2.0, requires_grad=True)

for i in range(3):
    y = x ** 2
    y.backward()
    print(f"lần {i+1}: x.grad = {x.grad}")

# lần 1: x.grad = 4.0   ← đúng (dy/dx = 2x = 4)
# lần 2: x.grad = 8.0   ← CỘNG DỒN, không phải ghi đè
# lần 3: x.grad = 12.0

# Cách sửa: xoá gradient trước mỗi lần tính mới
x.grad = None          # hoặc optimizer.zero_grad() trong code thật
📌 Vì sao PyTorch thiết kế như vậy

Nghe như một lỗi thiết kế, nhưng nó có lý do: tích luỹ gradient cho phép mô phỏng batch lớn trên GPU nhỏ. Bạn chạy backward trên 4 batch nhỏ liên tiếp rồi mới gọi optimizer.step() một lần — hiệu quả tương đương một batch lớn gấp 4, nhưng chỉ cần bộ nhớ của batch nhỏ.

Kỹ thuật này gọi là gradient accumulation, và nó gần như bắt buộc khi fine-tune mô hình lớn trên GPU tiêu dùng — bạn sẽ gặp lại ở 10.5 chương 3.

3.2. torch.no_grad()

Khi chỉ suy luận, việc theo dõi gradient là lãng phí thuần tuý — tốn bộ nhớ để lưu đồ thị mà không bao giờ dùng tới.

4. nn.Module

Mọi mô hình PyTorch đều kế thừa nn.Module. Nó tự động theo dõi các tham số, xử lý việc chuyển thiết bị, và quản lý chế độ train/eval.

python
import torch.nn as nn

class MangPhanLoai(nn.Module):
    def __init__(self, so_dau_vao, so_an, so_lop):
        super().__init__()          # BẮT BUỘC, luôn gọi đầu tiên
        self.lop1 = nn.Linear(so_dau_vao, so_an)
        self.lop2 = nn.Linear(so_an, so_lop)
        self.dropout = nn.Dropout(0.3)

    def forward(self, x):
        x = torch.relu(self.lop1(x))
        x = self.dropout(x)
        return self.lop2(x)     # trả logits thô, KHÔNG softmax — xem lưu ý dưới


model = MangPhanLoai(784, 128, 10)

# nn.Module tự tìm ra mọi tham số
tong = sum(p.numel() for p in model.parameters())
print(f"Tổng tham số: {tong:,}")   # 101,770
# = (784×128 + 128) + (128×10 + 10)

# Gọi model(x), KHÔNG gọi model.forward(x) trực tiếp
out = model(x)
⚠️ Hai lỗi kinh điển với nn.Module

1. Quên super().__init__(). Không có nó, PyTorch không đăng ký được các lớp con, và model.parameters() trả về rỗng — optimizer sẽ không cập nhật gì cả, mô hình không bao giờ học. Triệu chứng: loss hoàn toàn không đổi qua mọi epoch.

2. Áp softmax trong forward rồi lại dùng CrossEntropyLoss. Hàm mất mát này đã bao gồm softmax bên trong (nó là LogSoftmax + NLLLoss). Áp softmax hai lần khiến gradient nhỏ đi và mô hình học rất chậm. Quy tắc: forward trả logits thô.

5. Dataset và DataLoader

python
from torch.utils.data import Dataset, DataLoader

class BoDuLieuVanBan(Dataset):
    """Dataset tuỳ chỉnh cần đúng ba phương thức."""

    def __init__(self, van_ban, nhan, tokenizer):
        self.van_ban = van_ban
        self.nhan = nhan
        self.tokenizer = tokenizer

    def __len__(self):
        return len(self.van_ban)

    def __getitem__(self, idx):
        """Trả về MỘT mẫu. DataLoader lo việc gộp thành batch."""
        ma = self.tokenizer(self.van_ban[idx], truncation=True, max_length=256)
        return {
            "input_ids": torch.tensor(ma["input_ids"]),
            "label": torch.tensor(self.nhan[idx]),
        }


loader = DataLoader(
    dataset,
    batch_size=32,
    shuffle=True,      # True cho train, False cho val/test
    num_workers=4,     # tiến trình nạp dữ liệu song song
    pin_memory=True,   # tăng tốc chuyển sang GPU
    drop_last=False,   # giữ batch cuối dù không đầy
)
💡 Ba tham số hay bị đặt sai
  • shuffle=True cho tập test. Vô hại về mặt kết quả nhưng làm khó việc so sánh và debug. Đặt False.
  • num_workers quá cao. Nhiều hơn số nhân CPU sẽ chậm đi vì tranh chấp. Bắt đầu bằng 4 và đo.
  • Quên collate_fn cho dữ liệu độ dài khác nhau. Văn bản có độ dài khác nhau không gộp thành tensor được nếu không đệm (padding) — cần viết hàm collate_fn riêng.

6. Vòng lặp huấn luyện sáu bước

Đây là đoạn code bạn sẽ viết đi viết lại tới khi thuộc. Sáu bước, đúng thứ tự:

python
model.train()                             # bật chế độ huấn luyện

for epoch in range(so_epoch):
    tong_loss = 0.0

    for x, y in train_loader:
        x, y = x.to(device), y.to(device)

        optimizer.zero_grad()             # 1. xoá gradient của bước trước
        out = model(x)                       # 2. lượt tiến
        loss = criterion(out, y)             # 3. tính mất mát
        loss.backward()                    # 4. lượt lùi — điền vào .grad
        optimizer.step()                    # 5. cập nhật trọng số

        tong_loss += loss.item()            # 6. ghi lại (.item() để tránh giữ đồ thị)

    print(f"Epoch {epoch}: loss = {tong_loss / len(train_loader):.4f}")
Thử: đi từng bước vòng lặp huấn luyện
Bấm “Bước tiếp” để đi qua từng bước và xem trạng thái bên trong thay đổi thế nào.
Chú ý bước 1 và bước 4. Nếu bỏ bước 1, giá trị .grad ở bước 4 sẽ cộng dồn với gradient của batch trước — mô hình cập nhật theo một hướng sai. Đây là lỗi khó phát hiện nhất vì mô hình vẫn chạy, chỉ là học kém đi một cách khó hiểu.
⚠️ Hậu quả khi bỏ sót từng bước
Bỏ sótHậu quả
optimizer.zero_grad() Gradient cộng dồn qua các batch → hướng cập nhật sai, mô hình học rất kém. Không báo lỗi.
loss.backward() .grad vẫn là None → step() không đổi gì → loss đứng yên hoàn toàn
optimizer.step() Gradient được tính nhưng trọng số không bao giờ đổi → loss đứng yên
model.train() Dropout và BatchNorm ở chế độ eval → regularization không hoạt động
.item() khi cộng loss Giữ tham chiếu tới cả đồ thị tính toán → rò rỉ bộ nhớ, hết VRAM sau vài epoch

7. Đánh giá và lưu mô hình

python
@torch.no_grad()
def danh_gia(model, loader, criterion, device):
    model.eval()                     # QUAN TRỌNG: tắt dropout, BatchNorm dùng thống kê chạy
    tong_loss, dung, tong = 0.0, 0, 0

    for x, y in loader:
        x, y = x.to(device), y.to(device)
        out = model(x)
        tong_loss += criterion(out, y).item() * y.size(0)
        dung += (out.argmax(dim=1) == y).sum().item()
        tong += y.size(0)

    model.train()                    # nhớ bật lại trước khi huấn luyện tiếp
    return tong_loss / tong, dung / tong
Chế độDropoutBatchNorm
model.train()Hoạt động — tắt ngẫu nhiên nơ-ronDùng thống kê của batch hiện tại và cập nhật thống kê chạy
model.eval()Tắt hoàn toàn — dùng mọi nơ-ronDùng thống kê chạy đã tích luỹ, không cập nhật
⚠️ Quên model.eval() — lỗi tinh vi nhất

Mô hình vẫn chạy, vẫn cho kết quả, chỉ là kết quả kém đi và không tất định: cùng một đầu vào cho hai kết quả khác nhau ở hai lần gọi, vì dropout vẫn ngẫu nhiên tắt nơ-ron.

Triệu chứng thường gặp: điểm validation thấp hơn thực tế một cách khó hiểu, hoặc kết quả suy luận dao động. Nếu thấy hiện tượng đó, đây là thứ đầu tiên nên kiểm tra.

8.1. Mixed precision

Dùng độ chính xác 16-bit cho phần lớn phép tính, giữ 32-bit ở những chỗ nhạy cảm. Tiết kiệm khoảng một nửa bộ nhớ và chạy nhanh hơn đáng kể trên GPU hiện đại.

python
from torch.amp import autocast, GradScaler

scaler = GradScaler()

for x, y in train_loader:
    x, y = x.to(device), y.to(device)
    optimizer.zero_grad()

    with autocast(device_type="cuda", dtype=torch.float16):
        out = model(x)
        loss = criterion(out, y)

    scaler.scale(loss).backward()    # nhân loss lên để gradient nhỏ không bị làm tròn về 0
    scaler.step(optimizer)
    scaler.update()
📌 Vì sao cần GradScaler với FP16 mà không cần với BF16

float16 có dải giá trị hẹp: gradient rất nhỏ sẽ bị làm tròn về 0 (hiện tượng underflow), khiến mô hình mất tín hiệu học. GradScaler nhân loss lên một hệ số lớn trước khi backward, rồi chia lại trước khi cập nhật — giữ gradient nằm trong dải biểu diễn được.

bfloat16 có dải giá trị rộng bằng float32 (chỉ kém về độ chính xác), nên không bị underflow và không cần scaler. Đó là lý do BF16 là lựa chọn mặc định khi huấn luyện mô hình lớn trên GPU hỗ trợ nó. Chi tiết về các kiểu số ở 10.5 chương 5.

10. Hugging Face — cầu nối sang LLM

Trong thực tế bạn hiếm khi huấn luyện mô hình từ đầu. Hugging Face transformers cho phép nạp mô hình đã huấn luyện bằng vài dòng.

python
from transformers import AutoTokenizer, AutoModel

ten_mo_hinh = "..."          # tên mô hình trên Hugging Face Hub

tokenizer = AutoTokenizer.from_pretrained(ten_mo_hinh)
model = AutoModel.from_pretrained(ten_mo_hinh)

van_ban = "Tiếng Việt có sáu thanh điệu."
dau_vao = tokenizer(van_ban, return_tensors="pt")

print(dau_vao["input_ids"].shape)   # [1, số_token]
print(tokenizer.convert_ids_to_tokens(dau_vao["input_ids"][0]))
# Xem tokenizer cắt câu tiếng Việt thành những mảnh nào —
# đây là chủ đề chính của 10.2 chương 1

with torch.no_grad():
    ket_qua = model(**dau_vao)

print(ket_qua.last_hidden_state.shape)   # [1, số_token, số_chiều]
# Mỗi token thành một vector — chính là embedding ở 10.3 chương 2
🔗 Ba dòng cuối là cầu nối sang phần còn lại của trụ cột
  • input_ids — tokenization, chủ đề chính của 10.2 chương 1. Ở đó bạn sẽ thấy vì sao tiếng Việt tốn nhiều token hơn tiếng Anh và điều đó ảnh hưởng chi phí ra sao.
  • last_hidden_state — mỗi token thành một vector. Gộp các vector này lại chính là embedding dùng trong RAG (10.3 chương 2).
  • Bên trong model(...) là các khối Transformer — nội dung của chương 10.

Bài tập

Huấn luyện MNIST từ đầu tới cuối

Viết một chương trình hoàn chỉnh: nạp MNIST bằng torchvision, định nghĩa MLP hai lớp ẩn, huấn luyện 10 epoch, đánh giá trên test, vẽ đường cong loss.

Yêu cầu: có đủ sáu bước, có model.train()/model.eval() đúng chỗ, có dừng sớm, và lưu checkpoint tốt nhất.

Gợi ý

Ảnh MNIST là 28×28, nên lớp đầu nhận 784 đầu vào — nhớ x.view(x.size(0), -1) để làm phẳng.

Dùng nn.CrossEntropyLoss(), và không áp softmax trong forward.

Với MLP đơn giản, độ chính xác quanh 97–98% là bình thường. Nếu dưới 90%, kiểm tra xem có chuẩn hoá ảnh về [0,1] chưa.

Cố tình bỏ zero_grad()

Lấy chương trình ở bài 1, xoá dòng optimizer.zero_grad(). Chạy lại và ghi lại: loss thay đổi thế nào, độ chính xác cuối cùng bao nhiêu.

Sau đó thêm code in ra p.grad.norm() của một tham số qua vài batch đầu, và giải thích con số bạn thấy.

Gợi ý

Norm của gradient sẽ tăng dần qua các batch thay vì dao động quanh một mức ổn định — vì gradient của các batch trước vẫn còn đó và cộng dồn lên.

Hiệu ứng thực tế: bước cập nhật ngày càng lớn, tương đương learning rate tăng dần một cách mất kiểm soát. Loss thường vẫn giảm ban đầu (nên dễ bị bỏ qua) rồi dao động mạnh hoặc phân kỳ.

Đây là lý do lỗi này nguy hiểm: nó không báo lỗi và không hỏng ngay.

Dataset cho văn bản tiếng Việt

Viết một Dataset tuỳ chỉnh nhận danh sách văn bản tiếng Việt và nhãn. Trong __getitem__, chuẩn hoá Unicode về NFC (chương 3, mục 6.1) trước khi tokenize.

Viết collate_fn đệm các chuỗi trong batch về cùng độ dài. Kiểm chứng bằng cách in shape của một batch.

Gợi ý

collate_fn nhận một list các mẫu và trả về một batch. Dùng torch.nn.utils.rnn.pad_sequence(batch, batch_first=True, padding_value=0).

Nhớ trả kèm attention_mask để mô hình biết đâu là token thật, đâu là phần đệm — nếu không, phần đệm sẽ tham gia vào tính toán và làm sai kết quả.

Dừng sớm và checkpoint

Thêm vào chương trình bài 1: theo dõi val loss mỗi epoch, lưu checkpoint mỗi khi val loss cải thiện, và dừng nếu không cải thiện sau 3 epoch liên tiếp (patience = 3).

Cuối cùng, nạp lại checkpoint tốt nhất và đánh giá trên test.

Gợi ý

Giữ hai biến: val_loss_tot_nhat = float("inf") và so_epoch_khong_cai_thien = 0.

Điểm quan trọng: checkpoint cuối cùng không phải checkpoint tốt nhất. Nếu bạn dừng ở epoch 15 với patience 3, mô hình tốt nhất ở epoch 12 — phải nạp lại nó chứ không dùng trạng thái hiện tại.

Nạp mô hình Hugging Face và khảo sát tokenizer

Nạp một mô hình đa ngôn ngữ từ Hugging Face. Với 10 câu tiếng Việt và bản dịch tiếng Anh tương ứng, đếm số token của mỗi bên.

Tính tỉ lệ trung bình token_tiếng_Việt / token_tiếng_Anh. Nếu API LLM tính tiền theo token, tỉ lệ này có ý nghĩa gì với chi phí?

Gợi ý

Dùng len(tokenizer.encode(text)). In cả tokenizer.convert_ids_to_tokens(...) để nhìn thấy tiếng Việt bị cắt thành những mảnh nào — thường là từng âm tiết hoặc nhỏ hơn.

Tỉ lệ cụ thể phụ thuộc mô hình, nhưng tiếng Việt hầu như luôn tốn nhiều token hơn tiếng Anh cho cùng nội dung. Hệ quả trực tiếp: cùng một ứng dụng, phiên bản tiếng Việt tốn nhiều tiền hơn và chạm giới hạn cửa sổ ngữ cảnh sớm hơn.

Đây là bài tập chuẩn bị trực tiếp cho 10.2 chương 1.

Quiz

Q1

optimizer.zero_grad() để làm gì? Bỏ nó thì sao?

Xem đáp án
✓ Đáp án

Xoá gradient tích luỹ từ bước trước. PyTorch cộng dồn gradient vào .grad thay vì ghi đè, nên không xoá thì gradient của các batch trước vẫn còn đó.

Bỏ nó: hướng cập nhật sai và bước cập nhật ngày càng lớn — tương đương learning rate tăng dần mất kiểm soát. Không có lỗi nào được báo, mô hình vẫn chạy, chỉ học kém đi một cách khó hiểu. Đây là lý do nó nguy hiểm.

Hành vi cộng dồn là cố ý: nó cho phép gradient accumulation — mô phỏng batch lớn trên GPU nhỏ.

Q2

torch.no_grad() dùng khi nào và nó tiết kiệm gì?

Xem đáp án
✓ Đáp án

Dùng khi chỉ suy luận — đánh giá, dự đoán, sinh văn bản. Nó tắt việc dựng đồ thị tính toán.

Tiết kiệm bộ nhớ (không lưu kết quả trung gian cho lượt lùi) và thời gian (không ghi lại phép toán). Với mô hình lớn, khác biệt bộ nhớ là rất đáng kể — quên nó là một trong những nguyên nhân phổ biến nhất của lỗi hết VRAM khi đánh giá.

Q3

model.eval() ảnh hưởng tới những lớp nào, và quên nó gây hậu quả gì?

Xem đáp án
✓ Đáp án

Ảnh hưởng tới hai loại lớp có hành vi khác nhau giữa train và inference:

  • Dropout — eval() tắt hoàn toàn, dùng mọi nơ-ron.
  • BatchNorm — eval() dùng thống kê chạy đã tích luỹ thay vì thống kê của batch hiện tại.

Quên nó: không có lỗi nào, nhưng kết quả kém đi và không tất định — cùng đầu vào cho hai kết quả khác nhau vì dropout vẫn ngẫu nhiên. Triệu chứng: điểm validation thấp bất thường, hoặc kết quả suy luận dao động.

Q4

state_dict() chứa gì? Vì sao nên lưu nó thay vì lưu cả model?

Xem đáp án
✓ Đáp án

state_dict() là một dictionary ánh xạ tên tham số → tensor giá trị. Nó chứa trọng số và buffer, không chứa kiến trúc.

Nên lưu nó vì hai lý do:

  • Tính di động. torch.save(model, ...) dùng pickle, gắn chặt với tên class và đường dẫn module lúc lưu — đổi cấu trúc thư mục là nạp hỏng.
  • Bảo mật. Nạp file pickle từ nguồn không tin cậy có thể thực thi mã tuỳ ý. Đây là lý do hệ sinh thái chuyển sang safetensors.

Với checkpoint để tiếp tục huấn luyện, nhớ lưu cả optimizer.state_dict() — Adam có trạng thái riêng (momentum, phương sai chạy) và mất nó sẽ làm gián đoạn quá trình huấn luyện.

Q5

Lỗi "khác thiết bị" xảy ra khi nào và phòng thế nào?

Xem đáp án
✓ Đáp án

Khi hai tensor tham gia cùng một phép toán nằm ở hai thiết bị khác nhau — thường là mô hình đã .to("cuda") nhưng một tensor nào đó còn ở CPU.

Chỗ hay quên nhất: tensor tạo bên trong forward hoặc bên trong vòng lặp huấn luyện. Cách phòng: luôn kèm device=x.device khi tạo tensor mới — ví dụ torch.zeros(n, device=x.device).

Q6

DataLoader có nên shuffle=True cho tập test không?

Xem đáp án
✓ Đáp án

Không. Xáo trộn tập test không làm sai kết quả tổng thể (accuracy và loss trung bình không đổi), nhưng gây hai bất tiện:

  • Khó đối chiếu dự đoán với mẫu gốc khi phân tích ca sai.
  • Khó tái lập chính xác giữa các lần chạy để so sánh.

Xáo trộn chỉ cần cho tập train, để mỗi epoch mô hình thấy các batch theo thứ tự khác nhau — tránh việc nó học theo thứ tự dữ liệu.

Q7

Mixed precision đánh đổi gì? Vì sao FP16 cần GradScaler mà BF16 thì không?

Xem đáp án
✓ Đáp án

Đánh đổi: giảm khoảng một nửa bộ nhớ và chạy nhanh hơn, đổi lấy độ chính xác số thấp hơn.

float16 có dải giá trị hẹp: gradient rất nhỏ bị làm tròn về 0 (underflow), khiến mô hình mất tín hiệu học. GradScaler nhân loss lên trước khi backward rồi chia lại trước khi cập nhật, giữ gradient trong dải biểu diễn được.

bfloat16 có dải giá trị rộng bằng float32 (đánh đổi ở số chữ số có nghĩa chứ không phải ở dải), nên không bị underflow và không cần scaler. Đó là lý do BF16 là mặc định khi huấn luyện mô hình lớn.

Q8

Loss hoàn toàn không đổi qua mọi epoch. Kiểm tra những gì, theo thứ tự?

Xem đáp án
✓ Đáp án
  1. Optimizer có nhận được tham số không? len(list(model.parameters())) — nếu bằng 0 thì gần như chắc chắn quên super().__init__().
  2. Có gọi loss.backward() và optimizer.step() không? Thiếu một trong hai là trọng số không bao giờ đổi.
  3. Gradient có chảy không? Sau backward(), duyệt model.named_parameters() và kiểm tra p.grad có None hay bằng 0 không.
  4. Learning rate có bằng 0 không? Nghe ngớ ngẩn nhưng xảy ra thường xuyên, nhất là khi dùng scheduler.
  5. Thử overfit một batch nhỏ. Nếu ngay cả 16 mẫu cũng không học được, lỗi nằm ở pipeline chứ không phải ở dữ liệu.

Trường hợp đặc biệt: nếu loss đứng yên ở 0,693 với bài toán nhị phân, đó là ln(2) — mô hình đang đoán 50/50, tức hoàn toàn không học được gì.

Tổng kết

Sau chương 8, bạn đã nắm:

  • tensor = ndarray + thiết bị + gradient; dim= thay axis=; mặc định float32.
  • Autograd dựng đồ thị lúc chạy; .backward() tự động làm những gì bạn tính tay ở chương 7.
  • Gradient tích luỹ, không ghi đè — đây là lý do zero_grad() tồn tại, và cũng là thứ cho phép gradient accumulation.
  • nn.Module — luôn gọi super().__init__(); forward trả logits thô, không softmax.
  • Vòng lặp sáu bước và hậu quả cụ thể khi bỏ sót từng bước.
  • model.eval() tắt dropout và đổi hành vi BatchNorm — quên là kết quả kém đi và không tất định.
  • Lưu state_dict(), không lưu cả model — vì tính di động và vì rủi ro bảo mật của pickle.
  • GPU — mọi tensor phải cùng thiết bị; mixed precision tiết kiệm một nửa bộ nhớ; FP16 cần scaler, BF16 thì không.
  • Debug — in shape, kiểm tra gradient, và luôn overfit một batch nhỏ trước.
  • Hugging Face — input_ids dẫn sang tokenization, last_hidden_state dẫn sang embedding.
