WebSocket nền tảng & Socket.IO

Giao thức WebSocket cho kết nối hai chiều thời gian thực — xương sống của Call realtime và Live Chat. So sánh với polling/SSE và làm chủ Socket.IO.

🎯 Học xong chương này bạn sẽ

• Giải thích handshake nâng cấp từ HTTP lên WebSocket (HTTP Upgrade), khái niệm frame và kênh full-duplex bền vững.

• So sánh rạch ròi WebSocket với request-response, short polling, long polling và SSE — biết chọn đúng công cụ.

• Hiểu vì sao Socket.IO không phải "WebSocket thuần": reconnect, fallback, rooms, namespaces, acknowledgement.

• Xây được phòng chat theo room và relay signaling cho cuộc gọi (trao đổi offer/answer/ICE).

• Trả lời tự tin các câu phỏng vấn kinh điển: WS vs HTTP, WS vs SSE, heartbeat, WS có dùng TCP không, scale WS khó ở đâu.

💡 Liên hệ hệ thống Contact Center

Một tổng đài hiện đại là realtime tới tận lõi: agent thấy cuộc gọi mới ngay khi đổ chuông, trạng thái hàng đợi (queue) nhảy số liên tục, tin nhắn live chat hiện tức thời, và việc thiết lập cuộc gọi WebRTC cần trao đổi tín hiệu (signaling) hai chiều với độ trễ thấp. Toàn bộ những luồng này đều khó làm tốt bằng HTTP request-response thuần — đây chính là sân nhà của WebSocket. Chương này là nền móng cho cả F2 (realtime patterns) và F5 (scaling realtime).

① Giao thức WebSocket

WebSocket (chuẩn RFC 6455) là một giao thức cho phép mở một kết nối hai chiều, bền vững giữa client và server trên cùng một kết nối TCP duy nhất. Khác với HTTP — nơi client phải hỏi thì server mới được trả lời — WebSocket cho phép cả hai phía chủ động gửi dữ liệu bất cứ lúc nào, không cần đợi yêu cầu trước đó.

Handshake: nâng cấp từ HTTP lên WebSocket

WebSocket không tự dựng kết nối từ con số 0. Nó mượn HTTP để bắt tay rồi "nâng cấp" (upgrade) kênh đó thành WebSocket. Client gửi một HTTP request đặc biệt với header Upgrade: websocket:

handshake.httpHTTP
# 1) Client gửi yêu cầu nâng cấp
GET /socket HTTP/1.1
Host: cc.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

# 2) Server đồng ý → đổi giao thức
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Mã 101 Switching Protocols là dấu hiệu then chốt: từ giây phút này kết nối TCP không còn nói tiếng HTTP nữa mà chuyển sang nói tiếng WebSocket. Header Sec-WebSocket-Accept được server tính bằng cách ghép Sec-WebSocket-Key của client với một chuỗi ma thuật (GUID cố định) rồi băm SHA-1 — bước này chứng minh server thực sự hiểu giao thức (chống lại proxy "vô tình" trả về 101).

Client mở TCP→ HTTP GET + Upgrade→ 101 Switching Protocols→ Kênh WebSocket full-duplex→ Trao frame hai chiều

Scheme: ws:// và wss://

WebSocket dùng scheme riêng: ws:// (không mã hóa, tương tự http) và wss:// (chạy trên TLS, tương tự https). Trong môi trường thật luôn dùng wss://: vừa bảo mật vừa giúp đi qua proxy/firewall tốt hơn vì traffic được mã hóa, proxy không "nghịch" được phần thân.

Frame: đơn vị dữ liệu của WebSocket

Sau handshake, dữ liệu không đi theo "request/response" nữa mà theo các frame. Mỗi frame có header rất gọn (chỉ 2–14 byte) gồm: bit FIN (đây có phải frame cuối của một message không), opcode (kiểu frame), bit MASK và độ dài payload. Các opcode quan trọng:

OpcodeLoại frameÝ nghĩa
0x1TextDữ liệu văn bản UTF-8 (thường là JSON)
0x2BinaryDữ liệu nhị phân (audio, ảnh, ArrayBuffer)
0x8CloseYêu cầu đóng kết nối (kèm mã lý do)
0x9PingKiểm tra "còn sống" — bên kia phải trả Pong
0xAPongPhản hồi cho Ping (heartbeat)
💡 Overhead cực thấp — điểm mạnh chí mạng

Một HTTP request kéo theo hàng trăm byte header (Cookie, User-Agent, Authorization…) mỗi lần. Một WebSocket frame chỉ tốn vài byte header. Với tổng đài bắn cập nhật queue mỗi giây cho hàng nghìn agent, khác biệt này quyết định băng thông và độ trễ.

Một chi tiết bảo mật: frame gửi từ client lên server BẮT BUỘC được masking (XOR với một khóa ngẫu nhiên 4 byte). Mục đích không phải để bảo mật nội dung mà để chống tấn công "cache poisoning" trên các proxy cũ. Frame từ server xuống client thì không mask.

Ping/Pong & kết nối bền (heartbeat)

Một kết nối WebSocket "mở mãi" nhưng có thể chết âm thầm: cáp mạng rớt, agent đóng laptop, NAT/proxy timeout sau vài phút im lặng. TCP không phải lúc nào cũng báo ngay. Vì vậy WebSocket có cơ chế heartbeat: một bên định kỳ gửi frame Ping, bên kia phải đáp Pong trong khoảng thời gian cho phép; nếu không thì coi như kết nối đã chết và đóng lại. Đây là cách hệ thống phát hiện rớt mạng nhanh để đánh dấu agent offline, đẩy cuộc gọi sang agent khác.

② WebSocket vs HTTP / polling / SSE

Để hiểu vì sao WebSocket ra đời, phải thấy các giải pháp "realtime giả" trước nó đã chật vật thế nào. Bài toán muôn thuở: server có dữ liệu mới, làm sao đẩy ngay cho client?

HTTP request-response thuần

Client hỏi → server trả → đóng. Server không thể chủ động gửi gì cho client. Hợp với CRUD, tải trang, gọi API — nhưng vô dụng nếu server cần "báo trước" một sự kiện (có cuộc gọi mới đổ về).

Short polling — hỏi đi hỏi lại

Client cứ vài giây lại gọi GET /new-events để hỏi "có gì mới không?". Đa số lần trả về rỗng → lãng phí. Độ trễ trung bình bằng nửa chu kỳ poll; muốn nhanh hơn thì poll dày hơn → server "ngộp" request.

short-polling.jsBrowser
// Mỗi 3s hỏi server: có cuộc gọi mới trong queue không?
setInterval(async () => {
  const res = await fetch('/api/queue/new-calls');
  const calls = await res.json();   // thường rỗng → phí băng thông
  render(calls);
}, 3000);

Long polling — giữ request lại

Khôn hơn: client gọi request, server không trả ngay mà "treo" request đó cho đến khi có sự kiện (hoặc hết timeout). Có sự kiện → trả về ngay lập tức → client gọi lại request mới. Độ trễ gần như tức thời, nhưng mỗi sự kiện vẫn tốn một vòng request/response đầy đủ header, và server phải giữ nhiều kết nối "treo".

SSE — Server-Sent Events (một chiều server→client)

SSE là một kênh một chiều: server giữ một kết nối HTTP mở và liên tục đẩy các event xuống client qua text/event-stream. Trình duyệt có sẵn EventSource, tự reconnect, hỗ trợ Last-Event-ID để gửi lại event bị lỡ. Nhưng SSE chỉ server→client: client muốn gửi lên vẫn phải dùng HTTP request riêng. SSE cũng chỉ truyền text (không nhị phân) và bị giới hạn số kết nối đồng thời trên HTTP/1.1.

⚠️ "Realtime" không đồng nghĩa với "phải WebSocket"

Một dashboard giám sát chỉ hiển thị số liệu queue (server đẩy xuống, client không gửi gì lên) thì SSE đơn giản hơn, đi qua hạ tầng HTTP có sẵn dễ hơn. Chỉ khi cần hai chiều thật sự (agent gửi tin nhắn, trao đổi tín hiệu cuộc gọi) thì WebSocket mới là lựa chọn xứng đáng.

③ Socket.IO

Socket.IO không phải là WebSocket. Đây là hiểu lầm phổ biến nhất. Socket.IO là một thư viện (client + server) xây trên WebSocket nhưng bọc thêm rất nhiều tính năng mà WebSocket thuần không có. Nó có giao thức riêng (gói trong Engine.IO ở tầng dưới và Socket.IO ở tầng trên), nên client Socket.IO chỉ nói chuyện được với server Socket.IO, không cắm thẳng vào một WebSocket server thuần được.

🔌 Engine.IO (tầng dưới)

Lo việc thiết lập kết nối: thử WebSocket, nếu môi trường chặn thì fallback sang HTTP long-polling; quản lý heartbeat, nâng cấp transport.

📡 Socket.IO (tầng trên)

Cung cấp khái niệm event có tên, rooms, namespaces, acknowledgement, gửi lại khi reconnect — API thân thiện cho developer.

Vì sao không dùng WebSocket thuần cho mọi việc?

WebSocket chuẩn cho bạn một ống dẫn byte hai chiều — đẹp nhưng "trần trụi". Mọi thứ phía trên bạn phải tự xây: tự reconnect khi rớt, tự định nghĩa định dạng message, tự làm cơ chế "gửi cho một nhóm người", tự xác nhận "server đã nhận chưa". Socket.IO đóng gói sẵn những thứ này. Cái giá phải trả: thêm một lớp overhead giao thức và bị khóa vào hệ sinh thái Socket.IO.

④ Tính năng cốt lõi của Socket.IO

Event có tên (named events)

Thay vì gửi một blob rồi tự parse message.type, Socket.IO cho bạn đặt tên event. Hai phía gọi emit và lắng nghe on theo tên — code đọc như tiếng người.

events.jsSocket.IO
// Server
io.on('connection', (socket) => {
  socket.emit('call:incoming', { callId: 'c-91', from: '+8490...' });
  socket.on('call:answer', (data) => routeCall(data.callId));
});

// Client
socket.on('call:incoming', (call) => showRingingUI(call));
socket.emit('call:answer', { callId: 'c-91' });

Rooms — kênh con để broadcast nhóm

Room là một "nhãn" gắn lên các socket. Bạn cho socket join('room') rồi io.to('room').emit(...) để gửi cho mọi socket trong room đó. Đây là công cụ chủ lực của Contact Center: mỗi cuộc gọi là một room (agent + supervisor đang giám sát), mỗi hàng đợi là một room (tất cả agent thuộc kỹ năng đó nghe trạng thái queue).

rooms.jsSocket.IO
io.on('connection', (socket) => {
  // Agent vào hàng đợi "sales" → nghe cập nhật của queue đó
  socket.join('queue:sales');

  // Khi có cuộc gọi mới đổ vào queue sales
  io.to('queue:sales').emit('queue:update', { waiting: 7 });

  // Supervisor giám sát một cuộc gọi cụ thể → join room của call
  socket.on('monitor:join', (callId) => socket.join(`call:${callId}`));
});

Namespaces — tách kênh theo nghiệp vụ

Namespace chia một kết nối thành nhiều "đường truyền logic" (vd /chat, /calls, /admin) dùng chung một kết nối WebSocket vật lý. Mỗi namespace có middleware, sự kiện, room riêng. Hữu ích để áp quyền khác nhau: namespace /admin chỉ supervisor được vào, có thể gắn middleware kiểm tra vai trò.

💡 Phân biệt room vs namespace

Namespace = tách theo chức năng/quyền (cố định, ít, do dev định nghĩa: /chat, /calls). Room = nhóm động trong một namespace (mỗi cuộc gọi, mỗi queue — sinh ra/biến mất liên tục). Đừng dùng namespace cho cái thay đổi liên tục.

Acknowledgement — "server đã nhận chưa?"

Khi gửi một tin nhắn quan trọng (vd lưu nội dung chat vào hệ thống), bạn muốn biết server đã xử lý chưa. Socket.IO cho phép truyền một callback kèm emit; bên nhận gọi callback để báo kết quả — giống một "RPC" nhẹ trên WebSocket.

ack.jsSocket.IO
// Client gửi tin nhắn và chờ server xác nhận đã lưu
socket.emit('chat:send', { text: 'Xin chào' }, (res) => {
  if (res.ok) markDelivered(res.messageId);
  else showRetry();
});

// Server xử lý rồi gọi callback (tham số cuối)
socket.on('chat:send', async (msg, ack) => {
  const saved = await saveMessage(msg);
  ack({ ok: true, messageId: saved.id });
});

Tự reconnect & gửi dữ liệu nhị phân

Khi mạng rớt, client Socket.IO tự kết nối lại với chiến lược backoff (giãn dần thời gian thử) để tránh "bão reconnect" đè server. Socket.IO cũng truyền được dữ liệu nhị phân (Buffer, ArrayBuffer) — hữu ích khi gửi đoạn ghi âm, ảnh đính kèm trong chat.

🐛 Reconnect KHÔNG đồng nghĩa "không mất message"

Khi rớt rồi nối lại, các message phát ra trong lúc đứt có thể mất nếu bạn không có cơ chế bù (server lưu lại, dùng acknowledgement, hoặc đồng bộ lại trạng thái sau reconnect). Với cuộc gọi/giao dịch, đừng tin "socket nối lại là xong" — phải thiết kế idempotency và đồng bộ lại trạng thái.

⑤ Ví dụ thực chiến: phòng chat & call signaling

5.1 — Phòng chat live (room-based)

Khách bấm "Chat với agent" → tạo một room chat:<ticketId>; khách và agent cùng join room này; tin nhắn của bên nào cũng broadcast cho cả room.

chat-server.jsNode.js · Socket.IO
const { Server } = require('socket.io');
const io = new Server(httpServer, { cors: { origin: '*' } });

// Middleware: xác thực token trước khi cho kết nối
io.use((socket, next) => {
  const user = verifyToken(socket.handshake.auth.token);
  if (!user) return next(new Error('unauthorized'));
  socket.data.user = user;
  next();
});

io.on('connection', (socket) => {
  // Tham gia phòng chat của một ticket
  socket.on('chat:join', (ticketId) => {
    socket.join(`chat:${ticketId}`);
    socket.to(`chat:${ticketId}`).emit('chat:peer-joined', socket.data.user.name);
  });

  // Nhận tin nhắn → lưu DB → phát cho cả room (kèm ack)
  socket.on('chat:message', async ({ ticketId, text }, ack) => {
    const saved = await saveMessage({ ticketId, text, by: socket.data.user.id });
    io.to(`chat:${ticketId}`).emit('chat:message', saved);
    ack({ ok: true, id: saved.id });
  });

  // Hiển thị "đang gõ..."
  socket.on('chat:typing', (ticketId) =>
    socket.to(`chat:${ticketId}`).emit('chat:typing', socket.data.user.name));
});
💡 Vì sao dùng socket.to() chứ không io.to() cho "đang gõ"

socket.to(room) gửi cho mọi người trong room trừ chính người gửi — đúng cho "đang gõ" và "peer-joined". Còn io.to(room) gửi cho tất cả, kể cả người gửi — đúng cho tin nhắn (để client hiển thị lại tin của mình từ một nguồn nhất quán đã lưu DB).

5.2 — Call signaling (relay offer/answer cho WebRTC)

Cuộc gọi audio/video thường dùng WebRTC để truyền media ngang hàng (peer-to-peer). Nhưng để hai bên "tìm thấy nhau" và thống nhất codec/đường mạng, chúng phải trao đổi vài gói tín hiệu: offer, answer (SDP) và các ICE candidate. WebRTC không định nghĩa cách truyền những gói này — đó là việc của signaling server, và WebSocket/Socket.IO là phương tiện hoàn hảo vì cần hai chiều, độ trễ thấp.

Agent tạo Offer (SDP)→ Server relay qua WS→ Khách tạo Answer→ Relay về→ Trao ICE candidate→ Media P2P (không qua server)
signaling.jsNode.js · Socket.IO
io.on('connection', (socket) => {
  // Hai bên cùng join room của cuộc gọi
  socket.on('call:join', (callId) => socket.join(`call:${callId}`));

  // Relay offer/answer/ICE — server CHỈ chuyển tiếp, không hiểu nội dung
  socket.on('webrtc:offer', ({ callId, sdp }) =>
    socket.to(`call:${callId}`).emit('webrtc:offer', { sdp }));

  socket.on('webrtc:answer', ({ callId, sdp }) =>
    socket.to(`call:${callId}`).emit('webrtc:answer', { sdp }));

  socket.on('webrtc:ice', ({ callId, candidate }) =>
    socket.to(`call:${callId}`).emit('webrtc:ice', { candidate }));
});
⚠️ Signaling server KHÔNG truyền media

Một hiểu lầm hay gặp: nghĩ rằng âm thanh cuộc gọi đi qua WebSocket. Không. WebSocket chỉ relay tín hiệu thiết lập (offer/answer/ICE). Sau khi bắt tay xong, media đi P2P qua WebRTC (hoặc qua TURN server nếu P2P bị NAT chặn). Hiểu sự tách biệt này là dấu hiệu của ứng viên đã làm realtime thật.

⑥ Khi nào dùng WebSocket vs SSE vs polling?

Đừng mặc định "realtime là WebSocket". Hãy hỏi: dữ liệu đi một chiều hay hai chiều? tần suất ra sao? cần nhị phân không? hạ tầng có hỗ trợ kết nối bền không?

🔁 Dùng WebSocket

Hai chiều, độ trễ thấp, tần suất cao: live chat, call signaling, collaboration, multiplayer, presence (online/offline).

📥 Dùng SSE

Một chiều server→client, chủ yếu text: dashboard queue chỉ-xem, feed thông báo, log streaming, progress của tác vụ nền.

🐢 Dùng polling

Cập nhật hiếm, không cần tức thời, hoặc hạ tầng cũ chặn kết nối bền: kiểm tra trạng thái mỗi vài phút.

🐛 Khi nào KHÔNG nên dùng WebSocket

• Dữ liệu thay đổi hiếm (vài phút/lần) → giữ kết nối mở là phí tài nguyên. • Chỉ cần server đẩy một chiều → SSE đơn giản hơn. • Cần được cache/CDN/REST-friendly → WebSocket bỏ qua hết hạ tầng HTTP caching. • API công khai cho bên thứ ba → REST dễ tích hợp hơn nhiều. • Tải file lớn không tương tác → HTTP/streaming phù hợp hơn.

⚠️ Lỗi thường gặp & Best practices

🚫 Tin "kết nối mở = còn sống"

Kết nối có thể chết âm thầm. Luôn bật heartbeat (ping/pong) để phát hiện rớt và dọn tài nguyên.

🚫 Không xác thực lúc handshake

Đừng để ai cũng connect rồi mới kiểm tra. Dùng middleware io.use() verify token trước khi cho vào.

🚫 Broadcast toàn cục cho việc cục bộ

Dùng rooms thay vì io.emit() cho cả nghìn client. Bắn nhầm dữ liệu nhạy cảm + tốn băng thông.

🚫 Bỏ qua backpressure

Gửi nhanh hơn client tiêu thụ → buffer phình, RAM tăng. Theo dõi buffer, throttle event "đang gõ".

🚫 Quên dọn listener khi disconnect

Listener/room không gỡ → rò rỉ bộ nhớ, gửi nhầm cho socket đã chết. Xử lý 'disconnect' tử tế.

🚫 Một node, không tính scale

Nhiều instance Node thì room/broadcast không tự đồng bộ. Cần Redis adapter (xem F5) để bắc cầu pub/sub.

🧪 Bài tập

🧪 Bài 1 — Giải thích handshake

Mô tả từng bước biến một kết nối HTTP thành WebSocket. Mã trạng thái nào báo hiệu thành công? Vai trò của Sec-WebSocket-Key và Sec-WebSocket-Accept là gì?

Gợi ý

Client gửi GET với Upgrade: websocket + Sec-WebSocket-Key (nonce ngẫu nhiên). Server tính Sec-WebSocket-Accept = base64(SHA-1(key + GUID cố định)) và trả 101 Switching Protocols. Mã 101 là dấu hiệu thành công; cặp key/accept chứng minh server đúng là server WebSocket (chống proxy trả 101 vô tình).

🧪 Bài 2 — Chọn công nghệ realtime

Với mỗi tình huống của tổng đài, chọn WebSocket / SSE / polling và giải thích: (a) dashboard hiển thị số khách đang chờ; (b) live chat khách–agent; (c) trao đổi tín hiệu cuộc gọi; (d) kiểm tra trạng thái một báo cáo xuất file chạy nền.

Gợi ý

(a) SSE — một chiều server→client, chỉ-xem. (b) WebSocket — hai chiều, độ trễ thấp. (c) WebSocket — hai chiều, relay offer/answer tức thời. (d) Polling (hoặc SSE) — sự kiện hiếm, có thể hỏi mỗi vài giây; không cần kết nối bền.

🧪 Bài 3 — Room cho cuộc gọi

Thiết kế sơ đồ room cho: một cuộc gọi có 1 agent + 1 khách + (tùy chọn) 1 supervisor giám sát. Khi supervisor "barge-in" (xen vào nói), những ai nên nhận event? Viết tên các room và event chính.

Gợi ý

Room call:<id> chứa agent + khách (relay media signaling). Supervisor join room đó ở chế độ "monitor" (chỉ nghe, không gửi tín hiệu của mình). Khi barge-in, server emit call:barge tới room → cả agent và khách biết có người thứ ba nói. Có thể tách thêm room call:<id>:whisper để supervisor nói riêng chỉ agent nghe.

Ngân hàng câu hỏi phỏng vấn

WebSocket & Socket.IO — chủ đề ruột khi phỏng vấn vị trí Fullstack realtime.

Q1WebSocket khác HTTP ở điểm nào?Junior›

Trả lời: HTTP theo mô hình request-response: client hỏi thì server mới trả, mỗi request là một vòng riêng kèm đầy đủ header, và server không chủ động gửi được. WebSocket mở một kết nối hai chiều bền vững trên một TCP: sau handshake, cả hai phía gửi dữ liệu (frame) bất cứ lúc nào với overhead rất thấp. WebSocket hợp cho realtime hai chiều (chat, call), HTTP hợp cho CRUD/API.

Q2"Full-duplex" nghĩa là gì?Junior›

Trả lời: Full-duplex là cả hai phía có thể gửi và nhận đồng thời, độc lập, trên cùng một kênh — như gọi điện thoại (cùng nói cùng nghe). Half-duplex là phải thay phiên (như bộ đàm). HTTP request-response giống half-duplex theo lượt; WebSocket là full-duplex thật sự.

Q3Mô tả handshake WebSocket. Mã trạng thái nào báo thành công?Middle›

Trả lời: Client gửi HTTP GET kèm Upgrade: websocket, Connection: Upgrade và Sec-WebSocket-Key (nonce ngẫu nhiên). Server đáp 101 Switching Protocols kèm Sec-WebSocket-Accept = base64(SHA-1(key + GUID chuẩn)). Sau đó kênh TCP đó chuyển sang nói WebSocket, trao đổi frame hai chiều.

⚠️ Bẫy: nói "WebSocket là một giao thức hoàn toàn tách rời HTTP" — thực ra nó mượn HTTP để bắt tay rồi mới nâng cấp.

Q4WebSocket có dùng TCP không? UDP thì sao?Middle›

Trả lời: Có, WebSocket chạy trên TCP (nên đảm bảo thứ tự và độ tin cậy của byte). Nó không dùng UDP. Vì là TCP nên WebSocket có thể bị head-of-line blocking: một gói trễ làm nghẽn cả luồng — đây là lý do media cuộc gọi (cần đúng thời gian thực, chấp nhận mất gói) lại dùng WebRTC/UDP chứ không phải WebSocket.

⚠️ Bẫy: nhầm WebSocket với WebRTC. WebSocket = TCP (signaling); WebRTC media = thường UDP (SRTP).

Q5WebSocket vs SSE — chọn cái nào khi nào?Middle›

Trả lời: SSE một chiều server→client, chỉ text, có sẵn reconnect và Last-Event-ID, chạy trên HTTP thường nên dễ qua hạ tầng/proxy — hợp dashboard chỉ-xem, feed, notification. WebSocket hai chiều, độ trễ thấp, truyền nhị phân — hợp chat, call signaling, collaboration. Nguyên tắc: chỉ cần đẩy một chiều thì SSE; cần hai chiều thật thì WebSocket.

Q6Socket.IO có phải là WebSocket không? Khác gì?Middle›

Trả lời: Không. Socket.IO là thư viện xây trên WebSocket (qua Engine.IO ở dưới). Nó thêm: tự reconnect có backoff, fallback sang HTTP long-polling khi WS bị chặn, event có tên, rooms, namespaces, acknowledgement, gửi nhị phân. Đổi lại có giao thức riêng nên cần client Socket.IO để kết nối, không cắm thẳng vào WS server thuần được.

⚠️ Bẫy: nói "dùng Socket.IO thì cứ là WebSocket" — nó có thể đang chạy long-polling fallback chứ chưa nâng cấp lên WS.

Q7Phân biệt rooms và namespaces trong Socket.IO.Middle›

Trả lời: Namespace tách theo chức năng/quyền (cố định, ít: /chat, /calls, /admin), mỗi namespace có middleware và sự kiện riêng nhưng dùng chung kết nối WS vật lý. Room là nhóm động bên trong một namespace (mỗi cuộc gọi, mỗi queue), dùng để broadcast tới một tập socket: io.to('call:91').emit(...). Quy tắc: namespace cho cái cố định, room cho cái sinh-diệt liên tục.

Q8Acknowledgement trong Socket.IO là gì? Khi nào cần?Middle›

Trả lời: Là cơ chế truyền một callback kèm emit; bên nhận gọi callback để báo kết quả — giống RPC nhẹ. Cần khi bạn muốn chắc chắn bên kia đã nhận và xử lý (vd: lưu tin nhắn vào DB rồi mới đánh dấu "đã gửi"). Lưu ý kết hợp timeout: nếu không có ack trong hạn thì xử lý như thất bại để thử lại.

Q9Heartbeat là gì và tại sao cần?Middle›

Trả lời: Heartbeat là việc định kỳ gửi Ping và chờ Pong để xác nhận kết nối còn sống. Cần vì một kết nối có thể chết âm thầm (rớt mạng, NAT/proxy timeout, máy ngủ) mà TCP không báo ngay. Phát hiện sớm giúp đóng socket, dọn room, và quan trọng với tổng đài: đánh dấu agent offline ngay để không định tuyến cuộc gọi vào một agent đã "biến mất".

Q10Khi nào KHÔNG nên dùng WebSocket?Senior›

Trả lời: Khi dữ liệu thay đổi hiếm (giữ kết nối mở là lãng phí), khi chỉ cần đẩy một chiều (SSE gọn hơn), khi cần tận dụng caching/CDN và hạ tầng REST, khi làm API công khai cho bên thứ ba (REST dễ tích hợp hơn), hoặc khi truyền file lớn không tương tác (HTTP streaming hợp hơn). WebSocket cũng đắt về tài nguyên (mỗi kết nối là một socket mở giữ trạng thái) nên đừng dùng nếu lợi ích realtime không đáng.

Q11Scale WebSocket khó ở đâu? Cách giải quyết?Senior›

Trả lời: Khó vì WebSocket là stateful: mỗi kết nối gắn với một instance cụ thể và giữ trạng thái lâu dài. Vấn đề: (1) sticky session — load balancer phải đưa client về đúng node giữ kết nối (hoặc hỗ trợ WS đúng cách); (2) broadcast xuyên node — agent trên node A và supervisor trên node B cùng một room thì một mình node không phát tới nhau được; (3) số kết nối mở giới hạn theo RAM/file descriptor. Giải pháp: dùng Redis pub/sub adapter để bắc cầu sự kiện giữa các node, scale ngang nhiều instance, dùng sticky session, và cân nhắc tách tầng gateway WebSocket riêng. Chi tiết ở F5 và F3.

⚠️ Bẫy: nói "cứ thêm node là scale được" mà quên broadcast xuyên node và sticky session.

Q12Vì sao frame từ client lên server phải masking?Senior›

Trả lời: Theo RFC 6455, mọi frame client→server phải XOR payload với một khóa ngẫu nhiên 4 byte (masking). Mục đích không phải bảo mật nội dung (TLS lo việc đó) mà để chống tấn công cache poisoning: nếu không mask, một script độc có thể tạo dữ liệu trông giống HTTP request hợp lệ, lừa các proxy/cache trung gian cũ diễn giải sai và đầu độc cache. Masking làm payload trở nên ngẫu nhiên với proxy. Frame server→client thì không mask.
