Kiến trúc & Scaling hệ thống Realtime

Khi số kết nối realtime tăng vượt một server, bài toán scale WebSocket, sticky session và đồng bộ broadcast giữa các node trở thành cốt lõi của thiết kế.

🎯 Học xong chương này bạn sẽ

• Hiểu vì sao kết nối WebSocket là stateful và gắn chặt với một node — gốc rễ của mọi khó khăn khi scale realtime ngang.

• Giải thích được sticky session: khi nào bắt buộc, khi nào không, và cách load balancer định tuyến client về đúng node.

• Dùng Redis adapter / pub-sub backplane để broadcast một sự kiện xuyên tất cả các instance.

• Cấu hình load balancing WebSocket (L4 vs L7, hỗ trợ Upgrade, connection draining) và thiết kế service stateless bằng cách externalize state ra Redis.

• Scale tầng database & cache (replica, sharding) và biết cách ước lượng dung lượng cho N cuộc gọi/chat đồng thời.

• Thiết lập observability (số kết nối, độ trễ, metrics) và graceful drain khi deploy để không rớt cuộc gọi.

💡 Liên hệ thực tế hệ thống Contact Center

Một tổng đài chăm sóc khách hàng vào giờ cao điểm có thể có hàng nghìn agent online, mỗi agent giữ một kết nối WebSocket để nhận trạng thái cuộc gọi, tin nhắn chat, cập nhật hàng đợi (queue) và ticket theo thời gian thực. Một server Node không thể ôm hết: ta phải chạy nhiều instance sau load balancer. Nhưng khi agent A (kết nối node 1) gửi tin cho agent B (kết nối node 2), làm sao node 1 "với tới" được B? Đó chính là toàn bộ câu chuyện của chương này — và là bộ câu hỏi phỏng vấn kinh điển cho vị trí fullstack realtime.

① Thách thức cốt lõi khi scale realtime

Với HTTP REST thông thường, mỗi request là stateless và độc lập: load balancer ném request về bất kỳ node nào cũng được, vì node nào cũng phục vụ được nhờ state nằm ở DB/cache chung. Scale ngang chỉ là "thêm node, thêm load balancer" — quá dễ.

WebSocket thì ngược lại hoàn toàn. Một kết nối WS là một kết nối TCP sống lâu (long-lived) được "nâng cấp" (Upgrade) từ HTTP. Sau khi bắt tay xong, socket đó gắn chặt vào tiến trình Node cụ thể đang giữ file descriptor của nó. Đây là điểm mấu chốt:

🔗 Kết nối là stateful

Object socket, danh sách rooms agent tham gia, dữ liệu phiên... sống trong RAM của đúng một process. Node khác không thấy.

📡 Broadcast xuyên node

Khi cần phát "cuộc gọi mới vào queue VIP" tới mọi agent VIP, các agent đó nằm rải rác trên nhiều node. Phát cục bộ chỉ tới được client cùng node.

Hình dung trực quan: ta có 3 instance Node sau một load balancer. Agent A nối vào node 1, agent B nối vào node 3. A gửi tin nhắn nội bộ cho B:

Agent A→ Node 1✗ Node 3 (giữ socket của B)→ Agent B

Node 1 không có socket của B trong RAM, nên io.to(B).emit(...) chạy cục bộ sẽ im lặng thất bại — không lỗi, không tới nơi. Đây là cú sốc kinh điển khi lần đầu chạy realtime trên 2 node: "code đúng mà tin nhắn lúc tới lúc không".

⚠️ Hai bài toán độc lập, đừng nhầm lẫn

(1) Định tuyến kết nối: client phải đến được node giữ session của nó (đặc biệt với transport polling của Socket.IO) → giải bằng sticky session.

(2) Phát tin xuyên node: một sự kiện cần lan tới client ở mọi node → giải bằng backplane / Redis adapter.

Nhiều người giải bài (2) bằng Redis adapter rồi tưởng hết sticky session — sai. Hai vấn đề khác nhau, thường phải giải cả hai.

Vì sao không "đẩy hết lên một server khổng lồ"?

Scale dọc (vertical: máy mạnh hơn) có trần cứng: một process Node bị giới hạn bởi Event Loop đơn luồng, số file descriptor, RAM cho mỗi socket (vài KB đến vài chục KB tùy buffer). Quan trọng hơn, một server đơn là SPOF (single point of failure) — nó chết là cả tổng đài tê liệt. Vì vậy production luôn chạy nhiều instance: vừa để chịu tải, vừa để có dự phòng (HA). Và ngay khi có node thứ hai, mọi vấn đề ở trên xuất hiện.

② Sticky session (session affinity)

Sticky session (hay session affinity) là cơ chế load balancer luôn định tuyến các request/kết nối từ cùng một client về cùng một node backend. Với realtime, lý do bắt buộc nhất đến từ cách Socket.IO bắt tay.

Vì sao Socket.IO cần sticky session

Socket.IO không phải WebSocket thuần. Nó thực hiện quá trình "kết nối" qua nhiều HTTP request trước khi nâng cấp:

HTTP handshake (polling)→ cấp sid phiên→ vài request polling kế tiếp→ Upgrade → WebSocket

Trong giai đoạn polling, mỗi request là một HTTP request riêng. Nếu load balancer phân tải vòng tròn (round-robin), request thứ hai có thể rơi vào node khác — node đó không biết sid này (vì session đang nằm trong RAM node đầu) → trả lỗi Session ID unknown, kết nối lặp đi lặp lại không bao giờ ổn định. Triệu chứng điển hình: client cứ disconnect/reconnect liên tục, lỗi 400 Bad Request trên endpoint /socket.io/.

💡 Nếu chỉ dùng WebSocket thuần (transport: ['websocket'])

Nếu ép Socket.IO bỏ qua polling, chỉ dùng websocket, thì sau handshake duy nhất là một kết nối TCP bền vững — về lý thuyết không cần sticky. Nhưng đa số production vẫn bật polling làm fallback (cho mạng/proxy chặn WS), nên vẫn nên bật sticky cho an toàn. Sticky không hại, chỉ làm phân tải kém đều một chút.

Các cách triển khai sticky session

nginx.confNginx
# Sticky theo IP hash cho cụm Node giữ kết nối agent
upstream cc_realtime {
    ip_hash;                 # cùng IP client → cùng node
    server 10.0.1.11:3000;
    server 10.0.1.12:3000;
    server 10.0.1.13:3000;
}

server {
    listen 443 ssl;
    location /socket.io/ {
        proxy_pass http://cc_realtime;

        # BẮT BUỘC để nâng cấp HTTP → WebSocket
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;

        # Cho kết nối realtime sống lâu (mặc định 60s là quá ngắn)
        proxy_read_timeout  3600s;
        proxy_send_timeout  3600s;
    }
}
🐛 Lỗi kinh điển: quên header Upgrade

Thiếu proxy_set_header Upgrade + Connection "upgrade" → handshake WebSocket bị từ chối, client tụt về polling vĩnh viễn (tốn tài nguyên, độ trễ cao). Còn quên tăng proxy_read_timeout → kết nối idle bị cắt sau 60s, agent "rớt mạng" định kỳ dù mạng vẫn tốt.

③ Redis adapter / Pub-Sub backplane

Sticky session giải quyết việc client đến đúng node, nhưng không giải quyết việc broadcast xuyên node. Đây là vai trò của adapter — một lớp "đường xương sống" (backplane) để các instance nói chuyện với nhau.

Ý tưởng cốt lõi rất gọn: dùng Redis Pub/Sub làm bảng tin trung gian. Khi một node muốn broadcast, nó publish sự kiện lên một channel Redis. Mọi node khác đã subscribe channel đó sẽ nhận được và tự phát lại tới các client mà chúng đang giữ. Kết quả: một lệnh emit ở node 1 lan tới client ở mọi node một cách trong suốt.

Node 1: io.to('queue:vip').emit()→ PUBLISH → Redis→ Node 2 (SUB) → client của nó + Node 3 (SUB) → client của nó
server.tsNode.js · Socket.IO
import { Server } from 'socket.io';
import { createAdapter } from '@socket.io/redis-adapter';
import { createClient } from 'redis';

const io = new Server(httpServer);

// Cần 2 client: 1 để PUBLISH, 1 để SUBSCRIBE (Redis SUB chặn connection)
const pubClient = createClient({ url: process.env.REDIS_URL });
const subClient = pubClient.duplicate();
await Promise.all([pubClient.connect(), subClient.connect()]);

io.adapter(createAdapter(pubClient, subClient));

// Từ giờ, lệnh dưới đây sẽ tới MỌI agent VIP dù họ ở node nào
io.to('queue:vip').emit('call:incoming', {
  callId: 'c_9182', customer: '+84...', priority: 'high',
});

Adapter làm gì "phía sau"?

Adapter chặn các lời gọi emit/join/leave mang tính "rộng" (broadcast, room) và đồng bộ chúng qua Redis. Cụ thể, room membership và việc phát tới room trở thành thông tin chia sẻ: node 1 không cần giữ socket của B, nó chỉ cần publish lệnh "phát tới room X", node giữ B sẽ thi hành. Một số tác vụ cần phản hồi từ node khác (như io.fetchSockets(), lấy tổng số client toàn cụm) cũng đi qua cơ chế request/response trên Redis.

⚠️ Redis adapter KHÔNG thay thế sticky session

Adapter chỉ lo broadcast xuyên node. Quá trình handshake polling của một client cụ thể vẫn cần về đúng node giữ phiên đó. Nếu bỏ sticky mà chỉ có adapter, handshake polling vẫn lỗi. Hai mảnh ghép phải đi cùng nhau.

💡 Liên hệ chương trước

Cơ chế Pub/Sub đã học ở F3 · Redis; còn việc xử lý nền (ghi âm cuộc gọi, gửi email) thì dùng queue ở F4 · Message Queue & BullMQ. Adapter ở đây là fan-out tức thời cho socket, khác mục đích với queue (xử lý job bền, có retry).

④ Load balancing cho WebSocket

Load balancer cho realtime có vài điểm khác biệt quan trọng so với LB cho API REST. Trước hết, phải phân biệt tầng hoạt động:

LớpHoạt động ởĐặc điểm với WebSocket
L4 (TCP)Tầng giao vận, chỉ thấy IP:portĐơn giản, độ trễ thấp; không đọc được HTTP nên affinity chỉ theo IP. WS đi xuyên trong suốt vì nó là TCP.
L7 (HTTP)Tầng ứng dụng, hiểu HTTP headerĐọc được path/cookie → routing & cookie affinity tinh vi; bắt buộc phải hỗ trợ HTTP Upgrade để nâng cấp WS.

Với một tổng đài thường dùng L7 (Nginx, HAProxy, hoặc ALB của cloud) vì cần định tuyến theo path (/socket.io/, /api/) và cookie affinity mịn hơn. Điều kiện tiên quyết: LB phải hiểu và chuyển tiếp header Upgrade/Connection, nếu không kết nối WS không thiết lập được.

Connection draining — chìa khóa để deploy không rớt cuộc gọi

Đây là phần dễ bị bỏ qua nhất. Với REST, deploy phiên bản mới rất nhẹ nhàng: request ngắn, node cũ xử lý nốt vài trăm ms rồi tắt. Với WebSocket, kết nối sống hàng giờ. Nếu bạn tắt node thẳng tay khi deploy, tất cả agent trên node đó bị ngắt đột ngột — cuộc gọi đang nói chuyện rớt trạng thái, tin nhắn đang gõ mất.

Connection draining (rút cạn kết nối) là quy trình: ngừng nhận kết nối mới vào node sắp tắt, nhưng giữ kết nối hiện tại sống thêm một khoảng, đồng thời chủ động báo client reconnect để chúng tự nối sang node khác một cách có trật tự.

LB: gỡ node khỏi pool (no new conn)→ Server: gửi 'server:draining' tới client→ Client reconnect → node khác→ Node cũ: chờ cạn → exit
graceful-drain.tsNode.js
let draining = false;

process.on('SIGTERM', async () => {
  draining = true;

  // 1) Ngừng nhận kết nối HTTP/WS mới (LB cũng đã gỡ node khỏi pool)
  httpServer.close();

  // 2) Báo mọi agent: hãy reconnect sang node khác trong vài giây tới
  io.emit('server:draining', { reconnectInMs: 2000 });

  // 3) Cho client thời gian tự reconnect rồi mới ngắt
  await sleep(10_000);

  // 4) Flush state còn dở ra Redis/DB, đóng adapter & DB
  await flushPendingState();
  await io.close();
  await closeDb();
  process.exit(0);
});

// Healthcheck trả 503 khi đang drain để LB ngừng gửi traffic
app.get('/healthz', (req, res) =>
  res.status(draining ? 503 : 200).end());
💡 Phía client phải "đồng lõa"

Draining chỉ trọn vẹn khi client biết tự reconnect. Socket.IO client đã có reconnect tự động với backoff; ta chỉ cần lắng nghe server:draining để chủ động đóng và nối lại sớm thay vì chờ timeout. Trên Kubernetes, đặt terminationGracePeriodSeconds dài hơn tổng thời gian drain để pod không bị kill giữa chừng.

⑤ Stateful vs Stateless: externalize state

Nguyên tắc vàng để scale dễ dàng: giữ service càng stateless càng tốt. Một service stateless là service mà bất kỳ instance nào cũng phục vụ được bất kỳ request nào, vì mọi state quan trọng nằm ở kho chung (Redis/DB), không nằm trong RAM riêng của process.

Nghe có vẻ mâu thuẫn với WebSocket (vốn stateful). Cách hòa giải: kết nối socket buộc phải gắn với một node (đó là bản chất TCP), nhưng mọi state có ý nghĩa nghiệp vụ thì đẩy ra ngoài. Khi đó, nếu node chết, client reconnect sang node khác và khôi phục được trạng thái từ kho chung.

StateĐể trong RAM node (xấu)Externalize ra Redis (tốt)
Trạng thái agent (online/busy/wrap-up)Mất khi node down; node khác không thấyHSET agent:123 status busy → ai cũng đọc được, tính được tổng quan đội ngũ
Map userId → socketIdChỉ đúng cho node hiện tạiLưu vào Redis để biết user ở node/room nào (adapter cũng dùng cơ chế tương tự)
Hàng đợi cuộc gọi đang chờKhông chia sẻ được tảiRedis list/sorted set → mọi node cùng nhìn 1 hàng đợi nhất quán

presence.tsNode.js · Redis
// Khi agent kết nối — ghi presence ra Redis (state ngoài RAM)
io.on('connection', async (socket) => {
  const agentId = socket.data.agentId;

  // presence có TTL: nếu node chết, key tự hết hạn (không kẹt "online giả")
  await redis.set(`presence:${agentId}`, nodeId, 'EX', 30);

  // heartbeat gia hạn TTL mỗi 10s khi còn sống
  const hb = setInterval(() =>
    redis.expire(`presence:${agentId}`, 30), 10_000);

  socket.on('disconnect', async () => {
    clearInterval(hb);
    await redis.del(`presence:${agentId}`);
    // broadcast cho dashboard giám sát — qua adapter nên tới mọi node
    io.to('supervisors').emit('agent:offline', { agentId });
  });
});
🐛 "Sticky-only" che giấu thiết kế xấu

Nếu bạn lưu giỏ hàng/trạng thái phiên chỉ trong RAM rồi dựa hoàn toàn vào sticky để "luôn về đúng node", thì khi node đó chết, client mất sạch state — và autoscale (thêm/bớt node) gây xáo trộn lớn. Sticky nên là tối ưu định tuyến, không phải nơi chứa state. State thật phải externalize.

⑥ Scale Database & tầng Cache

Scale tầng realtime mà quên tầng dữ liệu thì chỉ chuyển nút cổ chai xuống dưới. Khi 50 node Node cùng đập vào một database, DB trở thành SPOF mới.

Read replica — tách đọc khỏi ghi

Hầu hết tải của tổng đài là đọc: lấy lịch sử chat, thông tin khách hàng, danh sách ticket. Ta cho master DB lo ghi, và nhiều read replica lo đọc. Lưu ý độ trễ nhân bản (replication lag): replica có thể chậm vài chục–vài trăm ms so với master. Với dữ liệu cần đọc-sau-ghi tức thì (vừa tạo ticket xong phải thấy ngay), hãy đọc từ master hoặc dùng cache.

Cụm Node (nhiều instance)→ Ghi → Master DB + Đọc → Replica 1 / Replica 2

Sharding — chia ngang dữ liệu

Khi một bảng quá lớn (vd lịch sử cuộc gọi hàng trăm triệu bản ghi), ta shard: chia dữ liệu theo khóa (vd tenantId với hệ thống multi-tenant, hoặc theo vùng). Mỗi shard là một DB độc lập, gánh một phần dữ liệu. Đánh đổi: truy vấn xuyên shard (cross-shard) phức tạp; chọn shard key sai gây "hot shard" (lệch tải).

Tầng cache — chắn trước DB

Đặt Redis cache trước DB cho dữ liệu đọc nhiều, đổi ít: hồ sơ khách hàng, cấu hình hàng đợi, danh bạ agent. Pattern phổ biến là cache-aside:

cache-aside.tsNode.js
async function getCustomer(id) {
  const key = `customer:${id}`;

  // 1) Thử cache trước
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  // 2) Miss → đọc DB (ưu tiên replica cho read)
  const row = await db.query('SELECT * FROM customers WHERE id=$1', [id]);

  // 3) Ghi lại cache với TTL để tránh stale vô hạn
  await redis.set(key, JSON.stringify(row), 'EX', 300);
  return row;
}
⚠️ Cache stampede & invalidation

Khi một key nóng hết hạn cùng lúc, hàng nghìn request cùng miss và đập vào DB (cache stampede). Giảm thiểu bằng TTL có jitter, khóa làm mới (mutex), hoặc serve-stale-while-revalidate. Và nhớ: invalidation (xóa cache khi dữ liệu đổi) là một trong "hai bài toán khó nhất khoa học máy tính".

⑦ Observability & ước lượng dung lượng

Không đo thì không scale đúng. Với hệ thống realtime, có một bộ metrics đặc thù cần theo dõi liên tục:

🔌 Kết nối

Số WS đang mở / node, tốc độ connect-disconnect, tỉ lệ reconnect (reconnect cao = mạng/LB có vấn đề).

⏱️ Độ trễ

p50/p95/p99 từ lúc emit tới lúc client ack; độ trễ vòng qua Redis adapter.

🧠 Tài nguyên

RAM/CPU mỗi node, độ trễ Event Loop (event loop lag), số file descriptor đang dùng.

📨 Throughput

messages/giây phát ra & nhận vào, kích thước payload, tỉ lệ message rớt.

🟥 Redis

Ops/giây, độ trễ, bộ nhớ; Redis adapter là SPOF tiềm tàng nếu không HA.

📊 Nghiệp vụ

Số cuộc gọi đồng thời, độ dài hàng đợi, thời gian chờ trung bình của khách.

Công cụ thường dùng: Prometheus thu metrics + Grafana vẽ dashboard; trace phân tán (OpenTelemetry) để lần một sự kiện đi xuyên các node; log tập trung (ELK/Loki). Đặt cảnh báo trên event loop lag và số kết nối/node để autoscale kịp.

Ước lượng dung lượng (capacity planning)

Câu hỏi phỏng vấn rất hay gặp: "Hệ thống cần phục vụ X kết nối đồng thời, bạn cần bao nhiêu node?". Cách tư duy theo bước:

  1. Xác định mục tiêu: giả sử 50.000 agent online đồng thời, mỗi người 1 kết nối WS.
  2. Đo "ngân sách" mỗi node: một process Node tinh chỉnh tốt có thể giữ ~10.000–30.000 kết nối idle (tùy RAM mỗi socket và lượng message). Lấy con số thận trọng, ví dụ 10.000/node để có headroom.
  3. Tính số node tải: 50.000 / 10.000 = 5 node. Cộng dự phòng N+1 (chịu được 1 node chết) và headroom giờ cao điểm → làm tròn lên 7 node.
  4. Kiểm tra nút cổ chai khác: Redis (ops/s cho fan-out), băng thông mạng (msg/s × kích thước), DB writes. Đôi khi Redis hoặc DB mới là trần thật, không phải số socket.
  5. Tải bằng số liệu thật: chạy load test (k6, artillery) mô phỏng connect + traffic thực tế để hiệu chỉnh con số "10.000/node" cho đúng workload của mình.
💡 Một phép tính băng thông nhanh

50.000 agent, mỗi người nhận 2 cập nhật/giây, mỗi message ~500 byte → 50.000 × 2 × 500 ≈ 50 MB/s ≈ 400 Mbps chỉ riêng phát ra. Con số này cho thấy mạng và fan-out (Redis) thường là giới hạn trước cả CPU. Luôn tính cả hai chiều và nhân hệ số đỉnh.

🐛 SPOF ẩn: chính cái backplane bạn thêm vào

Bạn thêm Redis adapter để scale — nhưng nếu Redis đó là một instance đơn, nó vừa trở thành SPOF mới: Redis chết → broadcast toàn cụm tê liệt. Giải pháp: chạy Redis ở chế độ HA (Sentinel/Cluster), tách Redis pub/sub khỏi Redis cache/queue để cô lập sự cố, và có chiến lược degrade (vẫn phục vụ cục bộ khi backplane gián đoạn ngắn).

⚠️ Lỗi thường gặp & Best practices

🚫 Tưởng Redis adapter thay sticky

Adapter lo broadcast, sticky lo định tuyến phiên. Thiếu sticky → handshake polling lỗi liên miên. Cần cả hai.

🚫 Quên header Upgrade ở LB

WS không nâng cấp được, tụt về polling; hoặc thiếu timeout dài → kết nối idle bị cắt định kỳ.

🚫 Tắt node thẳng tay khi deploy

Không drain → rớt mọi cuộc gọi/chat trên node đó. Luôn drain + báo client reconnect.

🚫 Để state nghiệp vụ trong RAM

Node chết là mất sạch, autoscale gây xáo trộn. Externalize presence/queue/session ra Redis.

🚫 Redis/LB là SPOF

Một instance Redis hay một LB đơn → cả cụm phụ thuộc. Chạy HA (Sentinel/Cluster), LB dự phòng.

🚫 Không đo lường

Không có metrics kết nối/độ trễ/event-loop-lag thì scale theo cảm tính, autoscale sai nhịp.

✅ Presence có TTL + heartbeat

Tránh "online giả" khi node chết đột ngột; dashboard giám sát luôn phản ánh đúng.

✅ Load test trước khi tin con số

Mỗi workload khác nhau; đo thật bằng k6/artillery rồi mới chốt số node/ngân sách.

🧪 Bài tập

🧪 Bài 1 — Chẩn đoán tin nhắn "lúc tới lúc không"

Một hệ thống chat nội bộ agent chạy 3 instance Node sau Nginx round-robin. Khi 1 node, mọi thứ ổn; khi scale lên 3 node, agent báo tin nhắn thỉnh thoảng không tới và đôi khi bị "văng ra" rồi nối lại. Hãy chỉ ra hai nguyên nhân gốc và cách sửa từng cái.

Gợi ý

(1) Thiếu backplane: broadcast cục bộ không xuyên node → tin nhắn tới người cùng node thì được, khác node thì mất. Sửa: thêm Redis adapter. (2) Thiếu sticky session: handshake polling của Socket.IO rơi vào node khác giữa chừng → "Session ID unknown", reconnect liên tục. Sửa: bật ip_hash/cookie affinity và đảm bảo header Upgrade + timeout dài.

🧪 Bài 2 — Ước lượng dung lượng

Tổng đài cần phục vụ 80.000 agent online đồng thời. Đo được một node giữ an toàn ~12.000 kết nối với traffic thực tế. Mỗi agent nhận trung bình 3 message/giây, mỗi message ~400 byte. Hãy tính: (a) số node tải kèm dự phòng N+1, (b) băng thông phát ra ước lượng, (c) nút cổ chai nào cần kiểm tra thêm.

Gợi ý

(a) 80.000 / 12.000 ≈ 6,67 → 7 node tải; cộng N+1 và headroom đỉnh → ~8–9 node. (b) 80.000 × 3 × 400 byte ≈ 96 MB/s ≈ ~770 Mbps phát ra — cân nhắc NIC/băng thông và chi phí. (c) Redis fan-out (ops/s cho broadcast), độ trễ adapter, DB writes cho presence, và event loop lag mỗi node. Rất có thể Redis/mạng là trần thật trước số socket.

🧪 Bài 3 — Deploy không rớt cuộc gọi

Viết (mô tả hoặc code) quy trình graceful drain cho một node realtime khi nhận SIGTERM trên Kubernetes, sao cho không agent nào mất trạng thái cuộc gọi đang diễn ra. Liệt kê các bước và những cấu hình K8s/LB liên quan.

Gợi ý

Bước: (1) healthcheck trả 503 → LB gỡ node khỏi pool, (2) httpServer.close() ngừng conn mới, (3) emit server:draining để client reconnect sang node khác, (4) chờ một khoảng cho client chuyển, (5) flush state ra Redis, đóng adapter/DB, exit. K8s: preStop hook gọi/đợi drain, terminationGracePeriodSeconds > tổng thời gian drain để pod không bị kill sớm; readiness probe gắn với cờ draining.

Ngân hàng câu hỏi phỏng vấn

Scaling realtime — chủ đề "lọc" ứng viên fullstack thật sự hiểu hệ thống.

Q1Vì sao scale WebSocket khó hơn scale REST API?Junior›

Trả lời: REST stateless, mỗi request độc lập nên LB ném về node nào cũng được. WebSocket là kết nối TCP sống lâu, stateful, gắn chặt với một process — socket và room nằm trong RAM node đó. Vì vậy phát sinh hai bài toán riêng: client phải về đúng node (sticky session) và broadcast phải xuyên node (backplane).

Q2Sticky session là gì và vì sao Socket.IO cần nó?Junior›

Trả lời: Sticky session (session affinity) là việc LB luôn đưa cùng một client về cùng một node. Socket.IO khởi đầu bằng vài HTTP request polling và cấp một sid lưu trong RAM node đầu; nếu request polling kế tiếp rơi vào node khác sẽ báo "Session ID unknown" và reconnect liên tục. Sticky đảm bảo chuỗi handshake về cùng node.

⚠️ Bẫy: nói "có Redis adapter rồi thì không cần sticky" — sai, adapter chỉ lo broadcast, không lo handshake polling.

Q3Redis adapter (backplane) hoạt động thế nào?Middle›

Trả lời: Adapter dùng Redis Pub/Sub làm đường xương sống. Khi một node gọi broadcast/emit tới room, adapter publish sự kiện lên channel Redis; các node khác đã subscribe nhận được và emit lại tới các client mà chúng đang giữ. Cần hai client Redis (một publish, một subscribe vì SUB chiếm connection). Nhờ đó một emit ở node bất kỳ lan tới client ở mọi node một cách trong suốt.

Q4Làm sao broadcast một sự kiện tới mọi instance? Ngoài Redis còn cách nào?Middle›

Trả lời: Cách phổ biến là Redis Pub/Sub adapter. Ngoài ra: Redis Streams (có lưu trữ, đọc lại được), Kafka/NATS (bền, throughput cao, hợp event bus toàn hệ thống), hay Sharded Pub/Sub trên Redis Cluster để giảm tải khi cụm lớn. Lựa chọn tùy yêu cầu độ bền (Pub/Sub là fire-and-forget, mất message nếu node down lúc đó) và quy mô.

Q5Thiết kế một service realtime stateless nghĩa là gì?Middle›

Trả lời: Là thiết kế sao cho bất kỳ instance nào cũng phục vụ được bất kỳ client nào, vì state nghiệp vụ (presence agent, hàng đợi cuộc gọi, session) nằm ở Redis/DB chung chứ không trong RAM riêng. Kết nối TCP vẫn buộc gắn với một node, nhưng khi node chết, client reconnect sang node khác và khôi phục state từ kho chung. Điều này giúp scale ngang và autoscale mượt.

⚠️ Bẫy: dựa vào sticky để chứa state là phản pattern — sticky chỉ nên là tối ưu định tuyến.

Q6L4 và L7 load balancer khác nhau ra sao với WebSocket?Middle›

Trả lời: L4 cân bằng ở tầng TCP, chỉ thấy IP:port, đơn giản và độ trễ thấp, affinity chỉ theo IP. L7 hiểu HTTP nên định tuyến theo path/cookie, cookie affinity mịn hơn, nhưng bắt buộc phải hỗ trợ HTTP Upgrade để nâng cấp WS. Tổng đài thường dùng L7 để tách /socket.io/ với /api/ và làm affinity bằng cookie. Dù lớp nào cũng phải cho kết nối sống lâu (tăng timeout).

Q7SPOF trong kiến trúc realtime nằm ở đâu? Khắc phục ra sao?Senior›

Trả lời: SPOF tiềm tàng: load balancer đơn, một instance Redis (vừa là backplane vừa là cache), master DB, hoặc một node giữ quá nhiều kết nối. Khắc phục: LB dự phòng (active-active/failover), Redis HA bằng Sentinel/Cluster và tách pub/sub khỏi cache, DB có replica + failover tự động, chạy đủ node theo N+1 để chịu được một node chết, và có chiến lược degrade khi backplane gián đoạn.

⚠️ Bẫy: thêm Redis adapter để "scale" mà quên rằng Redis đơn vừa trở thành SPOF mới.

Q8Hệ thống cần 100.000 kết nối đồng thời — bạn ước lượng dung lượng thế nào?Senior›

Trả lời: Tư duy theo bước: (1) đo ngân sách mỗi node bằng load test thật, ví dụ giữ an toàn ~10–15k kết nối/node; (2) chia ra số node tải (100k/10k = 10 node); (3) cộng dự phòng N+1 và headroom đỉnh → ~12 node; (4) kiểm tra nút cổ chai khác: Redis fan-out ops/s, băng thông mạng (số msg/s × kích thước), DB writes, event loop lag; (5) hiệu chỉnh bằng số liệu đo thực tế. Thường mạng hoặc Redis là trần thật trước cả số socket.

Q9Graceful drain khi deploy là gì? Mô tả quy trình.Senior›

Trả lời: Là rút cạn kết nối có trật tự để không rớt cuộc gọi: (1) healthcheck trả 503 để LB gỡ node khỏi pool, ngừng nhận conn mới; (2) emit server:draining để client chủ động reconnect sang node khác; (3) chờ một khoảng cho client chuyển; (4) flush state còn dở ra Redis/DB, đóng adapter và DB; (5) exit. Trên K8s dùng preStop hook và terminationGracePeriodSeconds dài hơn tổng thời gian drain để pod không bị kill giữa chừng.

Q10Khi autoscale (thêm/bớt node) realtime, cần lưu ý gì?Senior›

Trả lời: Scale-in nguy hiểm hơn scale-out với WS vì gỡ node làm rớt nhiều kết nối — phải drain trước khi gỡ. Tín hiệu autoscale nên là số kết nối/node và event loop lag, không chỉ CPU (WS có thể "đầy kết nối" nhưng CPU thấp). State phải externalize để node mới phục vụ được ngay và node bị gỡ không làm mất dữ liệu. Cảnh báo: scale đột ngột gây "reconnect storm" — đặt backoff + jitter ở client. Cân nhắc consistent hashing để bớt xáo trộn khi đổi số node.

⚠️ Bẫy: dùng CPU làm metric autoscale duy nhất cho realtime — dễ scale sai nhịp.

Q11Presence (online/offline) của hàng chục nghìn agent — thiết kế thế nào để chính xác và scale?Middle›

Trả lời: Lưu presence ở Redis với TTL + heartbeat: khi connect set presence:agentId có hạn ~30s, mỗi ~10s gia hạn. Nếu node chết đột ngột, key tự hết hạn nên không kẹt "online giả". Khi trạng thái đổi, broadcast qua adapter tới room supervisors để dashboard cập nhật tức thời. Cách này không phụ thuộc RAM một node, mọi instance đọc được presence toàn cục.

Q12Sự kiện realtime cần đảm bảo độ tin cậy (không mất, đúng thứ tự) thì làm sao?Senior›

Trả lời: Redis Pub/Sub là fire-and-forget nên không đảm bảo độ bền. Khi cần độ tin cậy: (1) dùng backplane bền hơn (Redis Streams/Kafka) có thể đọc lại; (2) thêm ack + retry và idempotency key ở client để chống mất/trùng; (3) lưu sự kiện quan trọng (tin nhắn, trạng thái cuộc gọi) vào DB rồi mới phát, để client reconnect có thể đồng bộ lại từ DB; (4) gắn sequence number cho mỗi room để client phát hiện thiếu/đảo thứ tự và yêu cầu gửi lại. Realtime nên xem là kênh "nhanh", còn DB là nguồn chân lý.

⚠️ Bẫy: coi WebSocket là kênh đảm bảo giao nhận — nó không phải; luôn có nguồn chân lý ở DB để khôi phục.
