Bất đồng bộ & Event Loop

Chủ đề quan trọng nhất để hiểu Node.js. Một Contact Center xử lý hàng nghìn cuộc gọi, tin nhắn, truy vấn DB đồng thời chỉ trên một luồng JavaScript — bí mật nằm ở Event Loop và mô hình non-blocking I/O. Hiểu sai phần này = viết ra code chậm, treo, hoặc sai thứ tự.

🎯 Học xong chương này bạn sẽ

• Giải thích vì sao JS "đơn luồng" lại xử lý được hàng nghìn tác vụ I/O song song.

• Vẽ và giải thích được Event Loop: call stack, macrotask, microtask, thứ tự thực thi.

• Thành thạo Promise, async/await, và 4 combinator (all/allSettled/race/any).

• Biết khi nào chạy tuần tự vs song song, và cách giới hạn concurrency.

• Trả lời chuẩn các câu "đoán output" — dạng câu hỏi phỏng vấn ám ảnh nhất.

① Vì sao cần bất đồng bộ?

JavaScript chạy trên một luồng (single thread) — chỉ có một call stack, làm một việc tại một thời điểm. Nếu mọi thao tác đều blocking (chặn), thì khi đọc DB mất 200ms, toàn bộ server "đứng hình", không nhận được cuộc gọi hay tin nhắn nào khác.

❌ blocking
// Giả sử đọc file đồng bộ
const data = fs.readFileSync('calls.log');
// ⏳ server đứng yên ở đây tới khi đọc xong
handleNextCall(); // các cuộc gọi khác phải chờ
✅ non-blocking
fs.readFile('calls.log', (err, data) => {
  // chạy khi đọc xong
});
handleNextCall(); // ✅ chạy NGAY, không phải chờ I/O
💡 Ý tưởng cốt lõi

Node.js không tự đa luồng cho code của bạn. Thay vào đó, nó giao việc I/O (đọc file, query DB, gọi mạng) cho hệ điều hành / thread pool của libuv, rồi tiếp tục chạy code khác. Khi I/O xong, callback được đưa vào hàng đợi để Event Loop thực thi. Đây là lý do một server Node phục vụ được hàng chục nghìn kết nối đồng thời (lý tưởng cho realtime Contact Center).

② Callback & "callback hell"

Callback là hàm được truyền vào hàm khác để gọi lại khi tác vụ hoàn thành. Đây là cơ chế bất đồng bộ nguyên thủy. Vấn đề: lồng nhiều callback → kim tự tháp khó đọc, khó xử lý lỗi.

callback-hell.jsJavaScript
// Quy trình: tìm agent rảnh → gán cuộc gọi → ghi log → thông báo
findAvailableAgent(queueId, (err, agent) => {
  if (err) return handle(err);
  assignCall(agent, callId, (err, call) => {
    if (err) return handle(err);
    writeLog(call, (err) => {
      if (err) return handle(err);
      notify(agent, (err) => {        // 😵 kim tự tháp ngày càng sâu
        if (err) return handle(err);
        console.log('done');
      });
    });
  });
});

Nhược điểm: (1) khó đọc, (2) xử lý lỗi lặp lại ở mọi tầng, (3) khó chạy song song, (4) "inversion of control" — bạn giao quyền điều khiển cho hàm bên ngoài, không chắc nó gọi callback mấy lần. → Promise ra đời để giải quyết.

③ Promise

Một Promise là đối tượng đại diện cho kết quả tương lai của tác vụ bất đồng bộ. Nó có 3 trạng thái:

pending (đang chờ)→ fulfilled (thành công) hoặc rejected (thất bại)

Khi đã settled (fulfilled/rejected) thì không đổi nữa (immutable). Xử lý bằng .then(), .catch(), .finally() và quan trọng là có thể nối chuỗi (chaining).

promise-chain.jsJavaScript
findAvailableAgent(queueId)
  .then(agent => assignCall(agent, callId)) // return Promise → chain phẳng
  .then(call  => writeLog(call))
  .then(()    => notify())
  .then(()    => console.log('done'))
  .catch(err => handle(err))        // 1 chỗ bắt mọi lỗi trong chuỗi ✅
  .finally(() => cleanup());        // luôn chạy

// Tự tạo Promise (vd bọc một API callback cũ)
function delay(ms) {
  return new Promise((resolve, reject) => {
    setTimeout(resolve, ms);
  });
}
⚠️ Quy tắc chaining hay quên

Trong .then(cb), nếu cb return một Promise thì chuỗi sẽ chờ Promise đó. Nếu return giá trị thường → được bọc thành Promise đã resolve. Nếu quên return → mắt xích sau chạy sớm, sai thứ tự.

④ async / await

async/await là "đường cú pháp" trên Promise, cho phép viết code bất đồng bộ trông như đồng bộ — dễ đọc, dễ debug, dễ try/catch. Một hàm async luôn trả về Promise; await tạm dừng hàm cho tới khi Promise settle (nhưng không chặn luồng chính — Event Loop vẫn chạy việc khác).

async-await.jsJavaScript
async function routeIncomingCall(queueId, callId) {
  try {
    const agent = await findAvailableAgent(queueId);
    const call  = await assignCall(agent, callId);
    await writeLog(call);
    await notify(agent);
    return call;                // Promise resolve với 'call'
  } catch (err) {
    handle(err);                // bắt mọi lỗi await ở trên
    throw err;                  // ném tiếp cho caller nếu cần
  }
}
🐛 Bẫy: await trong vòng lặp làm chậm hệ thống
// ❌ TUẦN TỰ — mỗi agent chờ agent trước, tổng = tổng các thời gian
for (const id of agentIds) await notify(id);

// ✅ SONG SONG — gửi cùng lúc, tổng = thời gian lâu nhất
await Promise.all(agentIds.map(id => notify(id)));

Chỉ dùng await trong vòng lặp khi thực sự cần thứ tự hoặc cần giới hạn tải.

⑤ Event Loop — cơ chế chi tiết

Đây là phần cốt lõi. Event Loop là vòng lặp điều phối: nó lấy việc từ các hàng đợi và đẩy vào call stack để thực thi, theo một thứ tự ưu tiên nghiêm ngặt.

Các thành phần

📚 Call Stack

Ngăn xếp các hàm đang chạy. Đồng bộ, LIFO. Chỉ khi stack rỗng, Event Loop mới lấy task mới.

⚙️ Web APIs / libuv

Nơi xử lý I/O, timer, network "ngoài" luồng JS. Xong thì đẩy callback vào queue.

⚡ Microtask Queue

Ưu tiên cao nhất. Chứa callback của Promise (.then), queueMicrotask, process.nextTick.

⏲️ Macrotask Queue

Chứa setTimeout, setInterval, setImmediate, I/O callback. Ưu tiên thấp hơn microtask.

🔑 Quy tắc vàng của Event Loop

Sau mỗi một macrotask, Event Loop vét sạch TOÀN BỘ microtask queue trước khi lấy macrotask tiếp theo. Nghĩa là: microtask luôn chạy trước macrotask. Trong Node, process.nextTick còn ưu tiên hơn cả microtask Promise.

Thứ tự một "tick" của Event Loop (Node.js)

Sync code (stack)→ nextTick queue→ microtasks (Promise)→ 1 macrotask↻

⑥ Đoán thứ tự thực thi (câu hỏi phỏng vấn ruột)

ordering.jsJavaScript
console.log('1: sync');

setTimeout(() => console.log('2: setTimeout (macrotask)'), 0);

Promise.resolve().then(() => console.log('3: promise (microtask)'));

queueMicrotask(() => console.log('4: queueMicrotask'));

console.log('5: sync');

// OUTPUT:
// 1: sync        ← đồng bộ chạy trước
// 5: sync        ← đồng bộ
// 3: promise     ← microtask (vét sạch trước macrotask)
// 4: queueMicrotask
// 2: setTimeout  ← macrotask cuối cùng
ordering-node.jsNode.js
console.log('start');
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
console.log('end');

// start → end → nextTick → promise → (timeout/immediate tùy ngữ cảnh)
// nextTick > Promise microtask > macrotask

⑦ Promise combinators

CombinatorHành viDùng khi
Promise.allChờ tất cả; fail nhanh nếu 1 cái rejectCần TẤT CẢ thành công (vd load nhiều dữ liệu bắt buộc)
Promise.allSettledChờ tất cả; trả mảng kết quả (cả fulfilled & rejected)Muốn biết kết quả từng cái, không fail toàn bộ
Promise.raceTrả về cái settle đầu tiên (kể cả reject)Timeout, lấy nguồn nhanh nhất
Promise.anyTrả về cái fulfilled đầu tiên; reject nếu tất cả failCó nhiều nguồn, cần 1 cái thành công bất kỳ
combinators.jsJavaScript
// Tải đồng thời dữ liệu dashboard: agent, hàng đợi, thống kê
const [agents, queues, stats] = await Promise.all([
  getAgents(), getQueues(), getStats()
]);

// Timeout pattern với race
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('Timeout')), ms));
  return Promise.race([promise, timeout]);
}
await withTimeout(callExternalAPI(), 3000); // hủy nếu quá 3s

⑧ Pattern thực chiến

Giới hạn concurrency (rất hay hỏi)

Gửi 10.000 thông báo cùng lúc bằng Promise.all có thể làm sập service/DB. Cần giới hạn số tác vụ chạy đồng thời.

concurrency-limit.jsJavaScript
async function mapLimit(items, limit, fn) {
  const results = [];
  const executing = new Set();
  for (const item of items) {
    const p = Promise.resolve().then(() => fn(item));
    results.push(p);
    executing.add(p);
    p.finally(() => executing.delete(p));
    if (executing.size >= limit) await Promise.race(executing);
  }
  return Promise.all(results);
}
// Gửi cho 10.000 agent nhưng tối đa 50 request đồng thời
await mapLimit(agentIds, 50, id => notify(id));

Tuần tự khi cần thứ tự

sequential.jsJavaScript
// Ghi các sự kiện cuộc gọi đúng thứ tự thời gian
for (const event of callEvents) {
  await appendToTimeline(event); // phải xong cái này mới ghi cái sau
}

// reduce để xâu chuỗi promise tuần tự
await callEvents.reduce(
  (chain, e) => chain.then(() => appendToTimeline(e)),
  Promise.resolve()
);

⚠️ Lỗi thường gặp & Best practices

🚫 Quên await

Hàm trả Promise nhưng không await → lỗi không bắt được, thứ tự sai, "unhandled rejection".

🚫 await tuần tự khi nên song song

Dùng Promise.all cho các tác vụ độc lập.

🚫 forEach + async

forEach không chờ async. Dùng for...of + await hoặc map+Promise.all.

🚫 Nuốt lỗi

Luôn có .catch hoặc try/catch. Bắt cả unhandledRejection ở tầng process.

🚫 Tác vụ CPU nặng trên main thread

Vòng lặp tính toán lớn chặn Event Loop → dùng Worker Threads / chia nhỏ.

🚫 Tạo Promise nhưng không return

Trong .then quên return → mất chaining, sai thứ tự.

🧪 Bài tập

🧪 Bài 1 — Đoán output

Cho đoạn code: console.log('A'); setTimeout(()=>console.log('B')); Promise.resolve().then(()=>console.log('C')); console.log('D'); — output theo thứ tự nào?

Xem đáp án

A · D · C · B. Sync (A, D) trước; rồi microtask Promise (C); cuối cùng macrotask setTimeout (B).

🧪 Bài 2 — Promise.all vs allSettled

Bạn cần gửi thông báo cho 100 agent. Một số có thể fail nhưng bạn vẫn muốn gửi hết và thống kê bao nhiêu thành công. Dùng combinator nào? Viết đoạn xử lý.

Xem gợi ý 
const res = await Promise.allSettled(ids.map(notify));
const ok = res.filter(r => r.status === 'fulfilled').length;
console.log(`${ok}/${ids.length} thành công`);

allSettled không "fail nhanh", trả về kết quả từng cái → đúng yêu cầu.

🧪 Bài 3 — Promisify

Cho hàm callback kiểu Node db.query(sql, (err, rows) => ...). Hãy "promisify" nó để dùng được với async/await.

Xem gợi ý 
const query = (sql) => new Promise((res, rej) =>
  db.query(sql, (err, rows) => err ? rej(err) : res(rows)));
const rows = await query('SELECT * FROM agents');

Q4. Vì sao Node single-thread vẫn xử lý nghìn kết nối đồng thời?

Ngân hàng câu hỏi phỏng vấn

Bất đồng bộ & Event Loop là chủ đề bị hỏi nhiều nhất cho Node Fullstack.

Q1Event Loop là gì? Giải thích cách Node xử lý bất đồng bộ.Middle›

Trả lời: Event Loop là vòng lặp điều phối việc thực thi. Code đồng bộ chạy trên call stack. Khi gặp tác vụ bất đồng bộ (I/O, timer), Node giao cho libuv/OS xử lý ngoài luồng. Khi xong, callback được đưa vào hàng đợi (micro/macrotask). Event Loop, mỗi khi call stack rỗng, sẽ vét sạch microtask rồi lấy một macrotask, lặp lại liên tục.

⚠️ Bẫy: "Node đơn luồng hay đa luồng?" → JavaScript của bạn chạy đơn luồng, nhưng libuv có thread pool (mặc định 4) cho một số I/O như fs, crypto, dns.

Q2Phân biệt microtask và macrotask. Cho ví dụ.Middle›

Trả lời: Microtask (Promise callbacks, queueMicrotask, process.nextTick) có ưu tiên cao, được vét sạch sau mỗi tác vụ đồng bộ và trước mỗi macrotask. Macrotask (setTimeout, setInterval, setImmediate, I/O) ưu tiên thấp hơn, mỗi vòng chỉ lấy một.

Ví dụ: setTimeout(...0) luôn chạy sau một Promise.then dù khai báo trước.

Q3Callback hell là gì và cách khắc phục?Junior›

Trả lời: Là tình trạng lồng nhiều callback bất đồng bộ tạo "kim tự tháp" khó đọc, khó xử lý lỗi. Khắc phục: dùng Promise + chaining, async/await, tách hàm nhỏ, hoặc thư viện điều phối luồng.

Q4Promise có những trạng thái nào? Đã settle rồi có đổi được không?Junior›

Trả lời: 3 trạng thái: pending, fulfilled, rejected. Khi đã fulfilled hoặc rejected (settled) thì bất biến — không chuyển trạng thái nữa và giá trị/lỗi cố định.

Q5So sánh Promise.all, allSettled, race, any.Middle›

Trả lời: all: chờ tất cả, fail nhanh khi 1 reject. allSettled: chờ tất cả, trả kết quả từng cái (không fail toàn bộ). race: cái settle đầu tiên (cả reject). any: cái fulfilled đầu tiên, reject nếu tất cả fail (AggregateError).

Q6Vì sao không nên dùng await trong vòng lặp với tác vụ độc lập?Middle›

Trả lời: Vì nó chạy tuần tự — mỗi vòng phải chờ vòng trước xong, tổng thời gian cộng dồn. Với tác vụ độc lập, dùng Promise.all(items.map(fn)) để chạy song song, tổng = thời gian lâu nhất. Nếu lo quá tải, dùng concurrency limit.

Q7process.nextTick khác microtask Promise thế nào?Senior›

Trả lời: Trong Node, process.nextTick có hàng đợi riêng được xử lý trước microtask queue của Promise, sau mỗi thao tác. Lạm dụng nextTick đệ quy có thể "bỏ đói" (starve) Event Loop, khiến I/O không bao giờ được xử lý.

Q8Tác vụ CPU nặng ảnh hưởng Event Loop thế nào? Cách xử lý?Senior›

Trả lời: Tác vụ CPU nặng (vòng lặp lớn, mã hóa, xử lý ảnh) chạy đồng bộ trên main thread sẽ chặn Event Loop, làm mọi request khác bị treo. Giải pháp: dùng Worker Threads, đẩy sang message queue để worker khác xử lý, chia nhỏ tác vụ (chunk + setImmediate), hoặc tách thành microservice.

Q9Sự khác nhau giữa setTimeout(fn,0) và setImmediate(fn) trong Node?Senior›

Trả lời: Cả hai là macrotask nhưng ở pha khác nhau của Event Loop. setImmediate chạy ở pha "check" (sau pha I/O poll), setTimeout ở pha "timers". Trong một I/O callback, setImmediate thường chạy trước setTimeout(0). Ngoài I/O, thứ tự không đảm bảo.

Q10"Unhandled promise rejection" là gì và xử lý ra sao trong production?Middle›

Trả lời: Xảy ra khi một Promise reject mà không có .catch/try-catch. Từ Node mới, mặc định sẽ làm crash process. Xử lý: luôn bắt lỗi ở async function, và lắng nghe process.on('unhandledRejection', ...) để log + tắt graceful thay vì để app ở trạng thái không xác định.

Q11async/await có thực sự "đồng bộ hóa" code không? Nó chặn luồng chứ?Middle›

Trả lời: Không chặn luồng chính. await chỉ tạm dừng hàm async hiện tại và trả quyền điều khiển về Event Loop để chạy việc khác; khi Promise settle, hàm được tiếp tục. Code "trông như đồng bộ" nhưng bản chất vẫn bất đồng bộ, non-blocking.
