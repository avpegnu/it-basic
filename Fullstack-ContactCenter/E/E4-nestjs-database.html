NestJS + Database, Config & Validation

Tích hợp DB (TypeORM/Prisma), quản lý cấu hình theo môi trường và bật validation toàn cục — bộ khung chuẩn của một service Nest production.

🎯 Học xong chương này bạn sẽ

• Cắm DB vào Nest bằng TypeOrmModule.forRoot/forFeature hoặc PrismaService, và hiểu khác biệt cốt lõi giữa hai cách.

• Inject repository qua @InjectRepository và viết tầng truy vấn theo Repository pattern sạch, dễ test.

• Cấu hình ConfigModule theo namespace, đặt isGlobal, và validate biến môi trường bằng Joi để fail-fast khi boot.

• Bật ValidationPipe toàn cục với whitelist/transform và viết DTO bằng class-validator + class-transformer.

• Mô hình hoá entities & quan hệ (1-n, n-n) cho domain agent/call/ticket, và hiểu eager vs lazy loading.

• Cấu hình DB bất đồng bộ (useFactory + ConfigService), tuning connection pool và chạy migration.

💡 Liên hệ Contact Center

Một service Contact Center điển hình lưu rất nhiều dữ liệu quan hệ: agent thuộc nhiều team/queue, mỗi call/chat sinh ra một ticket, mỗi cuộc tương tác có hàng loạt event (ring, answer, transfer, hangup). Tầng persistence phải vừa nhanh (pool kết nối hợp lý, không N+1), vừa an toàn (DTO validate mọi payload từ agent/khách), vừa linh hoạt theo môi trường (dev dùng SQLite/Docker, prod dùng Postgres có read-replica). Chương này dựng đúng bộ khung đó.

① Tích hợp TypeORM / Prisma

Nest không tự ép bạn dùng ORM nào. Hai lựa chọn phổ biến nhất là TypeORM (ORM truyền thống dạng decorator, tích hợp sâu qua module hệ sinh thái Nest) và Prisma (query builder type-safe, sinh client từ schema). Hiểu rõ cách nối dây mỗi loại vào DI container là phần được hỏi nhiều nhất.

1.1 — TypeORM: forRoot ở root, forFeature ở từng module

Có hai lệnh gọi tách bạch:

  • TypeOrmModule.forRoot(options) — gọi một lần ở AppModule, thiết lập kết nối (DataSource): host, port, credentials, pool, danh sách entity. Module này được đánh dấu global nội bộ nên các module con không cần import lại.
  • TypeOrmModule.forFeature([Entity]) — gọi ở từng feature module, đăng ký các repository cho những entity mà module đó dùng. Đây là thứ khiến @InjectRepository hoạt động trong module hiện tại.
AppModule→ forRoot (DataSource + pool)→ CallModule→ forFeature([Call, CallEvent])→ Repository<Call>
app.module.tsTypeScript
import { Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';

@Module({
  imports: [
    TypeOrmModule.forRoot({
      type: 'postgres',
      host: process.env.DB_HOST,
      port: 5432,
      username: process.env.DB_USER,
      password: process.env.DB_PASS,
      database: 'contact_center',
      entities: [__dirname + '/**/*.entity{.ts,.js}'],
      synchronize: false,   // ⚠️ KHÔNG bật ở production
      poolSize: 20,         // số kết nối tối đa trong pool
    }),
  ],
})
export class AppModule {}
🐛 synchronize: true là cái bẫy chí mạng

Nó tự động ALTER schema cho khớp entity mỗi lần khởi động. Tiện lúc nghịch, nhưng ở production nó có thể xoá cột/bảng chứa lịch sử cuộc gọi mà không hỏi. Luôn để synchronize: false và dùng migration (mục ⑥).

1.2 — Prisma: bọc PrismaClient thành một provider

Prisma không có module Nest "chính chủ" — bạn tự bọc PrismaClient thành một service rồi đưa vào DI. Mẫu chuẩn là kế thừa PrismaClient và hook vào vòng đời của Nest để connect khi module khởi tạo và disconnect khi tắt.

prisma.service.tsTypeScript
import { Injectable, OnModuleInit, OnModuleDestroy } from '@nestjs/common';
import { PrismaClient } from '@prisma/client';

@Injectable()
export class PrismaService extends PrismaClient
  implements OnModuleInit, OnModuleDestroy {

  async onModuleInit() {
    await this.$connect();   // mở pool khi Nest boot
  }
  async onModuleDestroy() {
    await this.$disconnect(); // đóng sạch khi graceful shutdown
  }
}

Sau đó chỉ cần providers: [PrismaService] + exports: [PrismaService] trong một PrismaModule (đặt @Global() nếu muốn dùng khắp nơi), và inject thẳng vào service nghiệp vụ.

Đừng nói "Prisma tốt hơn TypeORM" hay ngược lại. Câu trả lời ghi điểm là: "Tuỳ ràng buộc dự án — type-safety/DX thì Prisma; cần repository pattern thuần và kiểm soát ORM sâu thì TypeORM. Cả hai đều nối vào DI của Nest, chỉ khác cách wiring."

② Repository pattern

Repository là tầng trừu tượng hoá việc truy cập dữ liệu: service nghiệp vụ không biết SQL hay ORM, nó chỉ gọi find, save, delete. Nhờ đó logic nghiệp vụ tách khỏi chi tiết lưu trữ — dễ test (mock repository), dễ thay ORM.

2.1 — Inject repository bằng @InjectRepository

Sau khi forFeature([Call]) đăng ký repository cho entity Call, bạn lấy nó vào constructor service qua token @InjectRepository(Call):

call.service.tsTypeScript
import { Injectable, NotFoundException } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Call } from './call.entity';

@Injectable()
export class CallService {
  constructor(
    @InjectRepository(Call)
    private readonly callRepo: Repository<Call>,
  ) {}

  findActiveByAgent(agentId: string) {
    return this.callRepo.find({
      where: { agentId, status: 'IN_PROGRESS' },
      order: { startedAt: 'DESC' },
      take: 50,
    });
  }

  async getOrFail(id: string): Promise<Call> {
    const call = await this.callRepo.findOne({ where: { id } });
    if (!call) throw new NotFoundException(`Call ${id} not found`);
    return call;
  }
}

2.2 — Các phương thức repository hay dùng

Phương thứcTác dụngGhi chú
find / findOneTruy vấn nhiều / một bản ghiNhận where, relations, order, take/skip
findAndCountTrả về [data, total]Lý tưởng cho phân trang danh sách ticket
saveInsert hoặc update (upsert theo PK)Chạy hook entity, trả về thực thể đã lưu
insert / updateThao tác thẳng, không load entityNhanh hơn save cho update hàng loạt

2.3 — Custom repository qua Query Builder

Báo cáo Contact Center hay cần thống kê — ví dụ "số cuộc gọi nhỡ theo từng queue trong giờ qua". Đây là lúc createQueryBuilder toả sáng:

call.repository.tsTypeScript
countMissedByQueue(since: Date) {
  return this.callRepo
    .createQueryBuilder('c')
    .select('c.queueId', 'queueId')
    .addSelect('COUNT(*)', 'missed')
    .where('c.status = :s', { s: 'MISSED' })
    .andWhere('c.startedAt >= :since', { since })
    .groupBy('c.queueId')
    .getRawMany();
}
⚠️ Luôn dùng tham số hoá, không nối chuỗi

Viết .where('c.status = :s', { s }) chứ tuyệt đối không nối `c.status = '${s}'` — nối chuỗi mở cửa cho SQL Injection. Query builder tham số hoá tự escape an toàn.

💡 Repository giúp test dễ thế nào

Vì service phụ thuộc Repository<Call> qua DI, trong unit test bạn cung cấp một mock đơn giản: { provide: getRepositoryToken(Call), useValue: mockRepo }. Không cần DB thật vẫn test được toàn bộ logic nghiệp vụ — đây là lợi ích lớn nhất của pattern.

③ ConfigModule & biến môi trường

Hard-code cấu hình (host DB, secret, port) vào code là tội nặng. Nguyên tắc 12-Factor App: config nằm trong môi trường, tách khỏi code. Nest cung cấp @nestjs/config bọc quanh process.env và file .env, thêm validate & namespace.

3.1 — Đăng ký ConfigModule với isGlobal

app.module.tsTypeScript
import { ConfigModule } from '@nestjs/config';

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,        // ConfigService dùng được khắp nơi, khỏi import lại
      envFilePath: [`.env.${process.env.NODE_ENV}`, '.env'],
      cache: true,           // cache lại để đọc env nhanh hơn
      load: [databaseConfig, redisConfig], // config theo namespace (3.3)
    }),
  ],
})
export class AppModule {}

Đặt isGlobal: true nghĩa là ConfigService được export ra phạm vi toàn ứng dụng — mọi module inject được mà không cần imports: [ConfigModule] ở từng chỗ.

3.2 — Validate schema env bằng Joi (fail-fast)

Đây là phần được hỏi nhiều: làm sao bảo đảm khi service boot mà thiếu DB_HOST hay JWT_SECRET thì nó dừng ngay, thay vì chạy rồi sập lúc đang phục vụ cuộc gọi? Câu trả lời: validationSchema bằng Joi.

env.validation.tsTypeScript
import * as Joi from 'joi';

export const envSchema = Joi.object({
  NODE_ENV: Joi.string().valid('development', 'production', 'test').default('development'),
  PORT: Joi.number().default(3000),
  DB_HOST: Joi.string().required(),
  DB_PORT: Joi.number().default(5432),
  DB_USER: Joi.string().required(),
  DB_PASS: Joi.string().required(),
  JWT_SECRET: Joi.string().min(32).required(),
  REDIS_URL: Joi.string().uri().required(),
});

// trong ConfigModule.forRoot:
// validationSchema: envSchema,
// validationOptions: { abortEarly: false }, // báo TẤT CẢ lỗi env một lượt
🐛 Vì sao fail-fast quan trọng với Contact Center

Giả sử deploy thiếu REDIS_URL — nếu không validate, service khởi động "thành công", agent đăng nhập bình thường, nhưng tới khi định tuyến cuộc gọi qua Redis mới sập. Lúc đó khách đã gọi vào và rớt cuộc. Validate env ở boot biến lỗi runtime thành lỗi deploy — phát hiện trước khi tải sản xuất chạm tới.

3.3 — Config theo namespace với registerAs

Khi config phình to, gom theo nhóm cho gọn và type-safe:

database.config.tsTypeScript
import { registerAs } from '@nestjs/config';

export default registerAs('database', () => ({
  host: process.env.DB_HOST,
  port: parseInt(process.env.DB_PORT ?? '5432', 10),
  user: process.env.DB_USER,
  pass: process.env.DB_PASS,
  poolSize: parseInt(process.env.DB_POOL ?? '20', 10),
}));

// Đọc lại: configService.get('database.host')
// hoặc inject typed:  @Inject(databaseConfig.KEY) cfg: ConfigType<typeof databaseConfig>

④ Validation với DTO

Mọi dữ liệu vào từ HTTP/WS đều là input không tin cậy. Trong Contact Center, một payload tạo ticket sai định dạng có thể làm sai cả luồng định tuyến. Nest validate bằng bộ ba: DTO class + class-validator (luật) + class-transformer (chuyển kiểu) + ValidationPipe (thực thi).

4.1 — Bật ValidationPipe toàn cục

main.tsTypeScript
import { ValidationPipe } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,             // loại bỏ field thừa không có trong DTO
      forbidNonWhitelisted: true, // ném 400 nếu có field lạ
      transform: true,             // biến plain object → instance DTO + ép kiểu
      transformOptions: { enableImplicitConversion: true },
    }),
  );
  await app.listen(3000);
}
OptionÝ nghĩaVì sao cần
whitelistBỏ field không khai báo trong DTOChặn mass-assignment (vd client gửi role: 'admin')
forbidNonWhitelistedBáo lỗi thay vì âm thầm bỏPhát hiện client gửi sai schema sớm
transformPlain object → instance DTOBật decorator @Type, ép kiểu, nested validation
enableImplicitConversionTự ép "5" → 5 theo kiểu TSQuery param luôn là string, cần số

4.2 — Viết DTO với class-validator

create-ticket.dto.tsTypeScript
import {
  IsString, IsEnum, IsOptional, IsUUID,
  Length, IsInt, Min, Max, IsArray,
} from 'class-validator';
import { Type } from 'class-transformer';

export enum TicketChannel { CALL = 'CALL', CHAT = 'CHAT', EMAIL = 'EMAIL' }

export class CreateTicketDto {
  @IsUUID()
  customerId: string;

  @IsEnum(TicketChannel)
  channel: TicketChannel;

  @IsString()
  @Length(3, 200)
  subject: string;

  @IsInt()
  @Min(1) @Max(5)
  @Type(() => Number)   // ép string→number trước khi validate
  priority: number;

  @IsOptional()
  @IsArray()
  @IsString({ each: true })
  tags?: string[];
}

4.3 — DTO validate chạy ở đâu trong vòng đời request?

Đây là câu hỏi "đánh giá chiều sâu". ValidationPipe là một Pipe, nên nó chạy sau Guard, trước khi vào method của Controller. Cụ thể request đi qua:

Middleware→ Guard→ Interceptor (before)→ Pipe (ValidationPipe)→ Controller handler

Nghĩa là khi code trong handler chạy, dữ liệu đã được validate & transform xong. Nếu DTO không hợp lệ, Pipe ném BadRequestException (400) trước khi handler được gọi — nghiệp vụ không bao giờ nhìn thấy dữ liệu bẩn. (Xem thêm thứ tự đầy đủ ở E3.)

⚠️ Validation cần metadata kiểu — đừng quên thư viện

class-validator/transformer dựa vào reflect-metadata và cấu hình emitDecoratorMetadata: true trong tsconfig. Thiếu nó, @Type và suy kiểu nested sẽ không hoạt động.

⑤ Entities & quan hệ

Entity là class ánh xạ tới một bảng. Decorator @Entity, @Column, @PrimaryGeneratedColumn mô tả cấu trúc; các decorator quan hệ mô tả mối liên kết. Mô hình hoá đúng quan hệ là xương sống của domain Contact Center.

5.1 — Entity cơ bản

agent.entity.tsTypeScript
import {
  Entity, PrimaryGeneratedColumn, Column,
  CreateDateColumn, Index, OneToMany, ManyToMany, JoinTable,
} from 'typeorm';

@Entity('agents')
export class Agent {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Column({ length: 80 })
  displayName: string;

  @Index()
  @Column({ default: 'OFFLINE' })
  status: string;   // OFFLINE | READY | ON_CALL | WRAP_UP

  @OneToMany(() => Call, (c) => c.agent)
  calls: Call[];

  @ManyToMany(() => Queue, (q) => q.agents)
  @JoinTable()                // agent ↔ queue: bảng nối agent_queues
  queues: Queue[];

  @CreateDateColumn()
  createdAt: Date;
}

5.2 — Các loại quan hệ trong domain

Quan hệVí dụ Contact CenterDecorator
One-to-ManyMột agent xử lý nhiều call@OneToMany ↔ @ManyToOne
Many-to-OneMỗi call thuộc một agent (giữ FK)@ManyToOne (phía "nhiều" giữ khoá ngoại)
One-to-OneMỗi call sinh đúng một ghi âm@OneToOne + @JoinColumn
Many-to-ManyAgent thuộc nhiều queue & ngược lại@ManyToMany + @JoinTable

Phía "nhiều" trong quan hệ ManyToOne là nơi giữ khoá ngoại. Ví dụ entity Call giữ cột agentId:

call.entity.tsTypeScript
@Entity('calls')
export class Call {
  @PrimaryGeneratedColumn('uuid') id: string;

  @ManyToOne(() => Agent, (a) => a.calls, { onDelete: 'SET NULL' })
  agent: Agent;

  @Column({ nullable: true })
  agentId: string;   // khoá ngoại tường minh — tiện query

  @OneToMany(() => CallEvent, (e) => e.call, { cascade: true })
  events: CallEvent[];

  @Column() status: string;
  @Column({ type: 'timestamptz' }) startedAt: Date;
}

5.3 — Eager vs Lazy & bẫy N+1

⚡ Eager loading

Quan hệ luôn được load kèm khi truy vấn entity gốc. Tiện nhưng dễ kéo thừa dữ liệu nặng (vd toàn bộ event của call).

🐢 Lazy / on-demand

Chỉ load khi cần, qua relations: ['events'] hoặc join. Kiểm soát tốt hơn — khuyến nghị mặc định.

🐛 Vấn đề N+1

Lấy 100 call rồi vòng lặp truy cập call.agent mà không join → 1 query lấy call + 100 query lấy agent = 101 query. Với dashboard realtime hiện hàng trăm cuộc gọi, đây là sát thủ hiệu năng. Khắc phục: load sẵn quan hệ bằng relations: ['agent'] hoặc leftJoinAndSelect trong một query duy nhất.

⑥ Async config & connection

Ở mục ① ta cấu hình DB bằng giá trị tĩnh (đọc thẳng process.env). Vấn đề: nó không tận dụng được ConfigService đã validate, không inject được provider khác. Giải pháp chuẩn production là async config với forRootAsync + useFactory.

6.1 — forRootAsync + useFactory + ConfigService

app.module.tsTypeScript
TypeOrmModule.forRootAsync({
  imports: [ConfigModule],          // cần để inject ConfigService
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    type: 'postgres',
    host: config.get('database.host'),
    port: config.get<number>('database.port'),
    username: config.get('database.user'),
    password: config.get('database.pass'),
    database: 'contact_center',
    autoLoadEntities: true,
    synchronize: false,
    extra: {
      max: config.get<number>('database.poolSize'), // pool size
      connectionTimeoutMillis: 5000,
    },
  }),
})

Vì useFactory được DI gọi sau khi ConfigModule đã load & validate env, ta chắc chắn các giá trị đã sạch. inject liệt kê provider mà factory cần; Nest tự resolve và truyền vào theo thứ tự.

6.2 — Connection pooling

Pool là tập kết nối DB được tái sử dụng. Mở kết nối mới cho mỗi query rất tốn (handshake TCP/TLS, auth). Pool giữ sẵn N kết nối, mượn–trả.

Tham sốÝ nghĩaLưu ý cho Contact Center
max (poolSize)Số kết nối tối đaQuá nhỏ → request xếp hàng giờ cao điểm; quá lớn → quá tải DB
connectionTimeoutChờ tối đa để lấy kết nốiĐặt hữu hạn để fail nhanh, tránh treo request
idleTimeoutĐóng kết nối nhàn rỗiGiải phóng tài nguyên lúc thấp tải (đêm)
⚠️ Pool × số instance

Nếu chạy 8 instance Node (sau load balancer) mỗi instance pool 20, tổng cộng 160 kết nối tới DB. Postgres mặc định giới hạn ~100 kết nối → cạn slot, instance mới không connect được. Tính pool theo tổng, hoặc đặt một connection pooler (vd PgBouncer) ở giữa.

6.3 — Migrations

Migration là các bước thay đổi schema có kiểm soát, có version — thay cho synchronize nguy hiểm. Mỗi migration là một file có up() (áp dụng) và down() (rollback).

1700000000-AddCallQueue.tsTypeScript
export class AddCallQueue1700000000 implements MigrationInterface {
  async up(q: QueryRunner) {
    await q.query(`ALTER TABLE calls ADD COLUMN queue_id uuid`);
    await q.query(`CREATE INDEX idx_calls_queue ON calls(queue_id)`);
  }
  async down(q: QueryRunner) {
    await q.query(`DROP INDEX idx_calls_queue`);
    await q.query(`ALTER TABLE calls DROP COLUMN queue_id`);
  }
}
Sửa entity→ migration:generate (diff)→ review file→ migration:run lúc deploy→ schema cập nhật an toàn

⚠️ Lỗi thường gặp & Best practices

🚫 Bật synchronize ở prod

Có thể tự xoá cột/bảng dữ liệu thật. Luôn false + migration.

🚫 Quên đăng ký ValidationPipe

DTO chỉ là decorator — không bật pipe thì không validate gì cả, dữ liệu bẩn lọt vào.

🚫 Không validate env

Thiếu secret/DB url chỉ phát hiện lúc runtime giữa giờ cao điểm. Dùng Joi fail-fast.

🚫 Bỏ qua whitelist

Cho phép mass-assignment — client gửi field thừa (vd isAdmin) lọt vào entity.

🚫 Quên forFeature

@InjectRepository báo "can't resolve dependency" vì module chưa đăng ký entity.

🚫 N+1 query

Lặp truy cập quan hệ không join. Dùng relations/leftJoinAndSelect.

🚫 Pool quá nhỏ/quá lớn

Tính pool theo tổng instance, đặt timeout để fail nhanh.

✅ Tách DTO request/response

Đừng trả entity thô (lộ field nội bộ). Map sang response DTO.

🧪 Bài tập

🧪 Bài 1 — Module Ticket hoàn chỉnh

Tạo TicketModule: entity Ticket (quan hệ ManyToOne tới Agent và Customer), đăng ký repository, một TicketService có create(dto) và paginate(page, size). DTO CreateTicketDto phải validate đầy đủ. Hỏi: vì sao service không nên nhận thẳng entity mà nên nhận DTO?

Gợi ý

Dùng TypeOrmModule.forFeature([Ticket]) trong module, @InjectRepository(Ticket) trong service. paginate dùng findAndCount với take/skip. Service nhận DTO vì DTO đã được validate & whitelist bởi pipe — nhận entity thô bỏ qua tầng kiểm soát và lộ field nội bộ (vd internalNote) cho client gán.

🧪 Bài 2 — Async DB config theo môi trường

Chuyển cấu hình DB tĩnh sang forRootAsync + ConfigService. Thêm validationSchema Joi cho DB_HOST/DB_USER/DB_PASS/DB_POOL. Đặt poolSize qua env. Hỏi: tại sao phải imports: [ConfigModule] trong forRootAsync dù đã isGlobal?

Gợi ý

Khi ConfigModule đặt isGlobal thì thực tế không cần import lại; nhưng khai báo tường minh trong forRootAsync.imports giúp đảm bảo thứ tự khởi tạo (ConfigService sẵn sàng trước khi factory chạy) và làm rõ phụ thuộc. Đặt poolSize bằng parseInt(env, 10) với default hợp lý.

🧪 Bài 3 — Diệt N+1 trên dashboard

Cho endpoint trả 200 cuộc gọi đang diễn ra kèm tên agent. Viết hai phiên bản: (a) lặp truy cập call.agent gây N+1, (b) một query với relations/join. Đo số query mỗi cách và giải thích chênh lệch.

Gợi ý

(a) find() rồi for (c of calls) c.agent.displayName nếu lazy → 1 + 200 query. (b) find({ relations: ['agent'] }) hoặc createQueryBuilder().leftJoinAndSelect('c.agent','a') → 1 query. Bật logging TypeORM để đếm. N+1 tăng tuyến tính theo số bản ghi nên rất nguy hiểm trên dashboard realtime.

Ngân hàng câu hỏi phỏng vấn

Persistence, config & validation — phần lõi của mọi service Nest production.

Q1Phân biệt forRoot và forFeature của TypeOrmModule.Junior›

Trả lời: forRoot gọi một lần ở root module để thiết lập kết nối (DataSource): host, credentials, pool, danh sách entity. forFeature gọi ở từng feature module để đăng ký repository cho các entity module đó dùng, làm cho @InjectRepository hoạt động trong phạm vi module. Một cái lo kết nối, một cái lo repository theo tính năng.

Q2Làm sao inject một repository vào service?Junior›

Trả lời: Đăng ký entity bằng TypeOrmModule.forFeature([Call]) trong module, rồi inject vào constructor service bằng @InjectRepository(Call) private repo: Repository<Call>. Token được Nest sinh từ entity. Với Prisma thì khác: inject PrismaService rồi gọi prisma.call.findMany().

⚠️ Bẫy: quên forFeature → "Nest can't resolve dependencies". Lỗi rất hay gặp khi tách module mới.

Q3Bật validation toàn cục như thế nào và DTO validate chạy ở đâu?Middle›

Trả lời: Đăng ký app.useGlobalPipes(new ValidationPipe({...})) trong main.ts (hoặc qua provider APP_PIPE). DTO validate chạy trong Pipe — sau Middleware/Guard/Interceptor-before, ngay trước khi vào Controller handler. Nếu DTO sai, Pipe ném BadRequestException trước khi nghiệp vụ chạy, nên handler luôn nhận dữ liệu sạch.

Q4Giải thích whitelist, forbidNonWhitelisted, transform.Middle›

Trả lời: whitelist loại field không khai báo trong DTO (chặn mass-assignment). forbidNonWhitelisted ném 400 nếu phát hiện field lạ thay vì âm thầm bỏ. transform biến plain object thành instance DTO và ép kiểu (kết hợp @Type để chuyển string→number, hỗ trợ nested DTO). Bộ ba này biến input thô thành dữ liệu sạch, đúng kiểu.

⚠️ Bẫy: chỉ khai DTO mà không bật ValidationPipe — không có gì được validate cả, decorator chỉ là metadata trơ.

Q5Cấu hình ConfigModule chuẩn gồm những gì? isGlobal để làm gì?Middle›

Trả lời: forRoot với isGlobal: true (để ConfigService dùng khắp nơi khỏi import lại), envFilePath theo môi trường, cache: true, load các config namespace (registerAs), và quan trọng nhất là validationSchema (Joi) + validationOptions: { abortEarly: false } để báo tất cả lỗi env một lượt. Đọc giá trị qua configService.get('database.host').

Q6Vì sao và làm sao validate biến môi trường?Middle›

Trả lời: Để fail-fast: thiếu/sai config (DB url, JWT secret, Redis url) phải khiến service dừng ngay lúc boot thay vì sập runtime giữa lúc phục vụ khách. Dùng validationSchema Joi với required(), default(), ràng buộc kiểu/độ dài. Với Contact Center, lỗi này nếu lọt qua sẽ rớt cuộc gọi thật — fail-fast biến nó thành lỗi deploy phát hiện sớm.

Q7Async DB config là gì? Khi nào cần forRootAsync?Senior›

Trả lời: Khi cấu hình DB phụ thuộc provider khác (vd ConfigService đã validate, hay một secret manager async), ta dùng forRootAsync({ imports, inject, useFactory }). Factory được DI gọi sau khi dependency sẵn sàng, nên giá trị đã sạch và type-safe. So với config tĩnh đọc thẳng process.env, cách async cho phép tái dùng config namespace, dễ test và đổi nguồn cấu hình.

Q8Connection pooling là gì? Cấu hình thế nào cho hệ realtime?Senior›

Trả lời: Pool là tập kết nối DB được tái sử dụng để tránh chi phí mở kết nối mỗi query. Tham số chính: max (số kết nối tối đa), connectionTimeout (fail nhanh thay vì treo), idleTimeout. Quan trọng: tính pool theo tổng số instance — N instance × pool có thể vượt giới hạn DB. Giải pháp là cân pool hợp lý hoặc đặt connection pooler (PgBouncer) ở giữa. Pool quá nhỏ gây xếp hàng giờ cao điểm, quá lớn làm quá tải DB.

⚠️ Bẫy: chỉ chỉnh pool ở một instance mà quên nhân với số instance sau load balancer.

Q9Migration vs synchronize? Vì sao prod luôn dùng migration?Senior›

Trả lời: synchronize: true tự ALTER schema cho khớp entity mỗi lần boot — tiện lúc dev nhưng có thể xoá cột/bảng chứa dữ liệu thật mà không hỏi. Migration là các bước thay đổi schema có version, review được, rollback được (up/down), chạy có kiểm soát lúc deploy. Production luôn synchronize: false + migration để bảo toàn dữ liệu lịch sử cuộc gọi/ticket.

Q10Vấn đề N+1 query là gì? Cách phát hiện và khắc phục trong TypeORM?Senior›

Trả lời: N+1 là khi load N entity rồi lặp truy cập quan hệ của từng cái, sinh thêm N query (tổng N+1). Phát hiện bằng bật logging TypeORM hoặc APM thấy hàng loạt query giống nhau. Khắc phục: load sẵn quan hệ bằng relations: ['agent'] trong find, hoặc leftJoinAndSelect trong query builder để gộp về một query. Với dashboard realtime hiển thị hàng trăm cuộc gọi, N+1 là sát thủ hiệu năng do tăng tuyến tính theo số bản ghi.

Q11TypeORM hay Prisma — bạn chọn cái nào và vì sao?Middle›

Trả lời: Tuỳ ràng buộc dự án, không có cái "tốt hơn" tuyệt đối. Prisma mạnh về type-safety và DX (schema-first, client suy kiểu chính xác, migrate gọn). TypeORM mạnh khi cần repository pattern thuần, kiểm soát ORM sâu, query builder cho join phức tạp. Cả hai đều nối vào DI của Nest — TypeORM qua @nestjs/typeorm + @InjectRepository, Prisma qua một PrismaService tự bọc. Mình nêu tiêu chí team-skill, độ phức tạp truy vấn và yêu cầu type-safety để quyết.

Q12Tại sao không nên trả entity thô ra response? Cách xử lý?Middle›

Trả lời: Entity có thể chứa field nội bộ nhạy cảm (hash, internal note, FK kỹ thuật) và kết cấu của nó gắn chặt với schema DB — đổi schema vô tình đổi luôn API. Nên map sang response DTO riêng (dùng class-transformer với @Exclude/@Expose hoặc ClassSerializerInterceptor). Điều này tách contract API khỏi lưu trữ, kiểm soát đúng dữ liệu lộ ra cho agent/khách.

⚠️ Bẫy: trả thẳng repo.findOne() ra controller — lộ field như passwordHash nếu entity có.
