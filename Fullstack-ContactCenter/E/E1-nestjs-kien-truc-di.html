Kiến trúc NestJS & Dependency Injection

NestJS — framework có cấu trúc, TypeScript-first, được nhiều công ty Contact Center chọn. Bắt đầu từ triết lý kiến trúc và Dependency Injection.

🎯 Học xong chương này bạn sẽ

• Giải thích triết lý NestJS: opinionated, modular, TypeScript-first, lấy cảm hứng từ Angular — và vì sao điều đó giúp đội ngũ scale.

• Mô tả kiến trúc phân tầng Controller → Service → Repository và trách nhiệm từng tầng.

• Hiểu IoC (Inversion of Control) và DI container: Nest tự khởi tạo & tiêm phụ thuộc thay vì bạn tự new.

• Biết Provider là gì (@Injectable), token, scope, và cách Nest resolve dependency graph.

• Nắm vai trò Module (@Module với imports/exports/providers/controllers) và ranh giới đóng gói.

• Hiểu quy trình bootstrap (main.ts, NestFactory) và Nest chạy trên nền Express/Fastify ra sao; biết khi nào KHÔNG cần Nest.

💡 Liên hệ hệ thống Contact Center

Một hệ thống Contact Center thường có hàng chục domain: quản lý agent, định tuyến cuộc gọi (call routing), hàng đợi (queue), chat realtime, ticket/CRM, báo cáo. Khi nhiều team cùng làm trên một codebase lớn, Express "tự do" dễ dẫn tới mỗi người một kiểu. NestJS áp một khuôn khổ chung: mỗi domain là một module, mỗi tầng có trách nhiệm rõ ràng, DI giúp ghép nối lỏng & test dễ. Đó chính là lý do framework này được ưa chuộng cho backend nghiệp vụ phức tạp như Contact Center.

① Vì sao NestJS?

NestJS là framework backend cho Node.js, viết bằng TypeScript, được mô tả là opinionated (có quan điểm rõ ràng về cách tổ chức code). Trong khi Express chỉ cho bạn một bộ "lego" tối giản và để bạn tự quyết định mọi thứ, thì Nest mang tới một kiến trúc đã định sẵn lấy cảm hứng từ Angular: module, controller, provider, decorator, DI.

Bốn trụ cột triết lý

🧭 Opinionated

Có "đường ray" sẵn: đặt file ở đâu, tầng nào làm gì. Bớt tranh luận, code các team trông giống nhau → onboard nhanh.

🧩 Modular

Mọi tính năng gói trong module có ranh giới rõ. Domain call, chat, ticket... tách bạch, dễ tách thành microservice sau này.

🅰️ Lấy cảm hứng Angular

Dùng decorator (@Controller, @Injectable, @Module) và DI container giống Angular phía frontend → fullstack đồng nhất tư duy.

🟦 TypeScript-first

Type, decorator metadata là công dân hạng nhất. IntelliSense tốt, refactor an toàn, bắt lỗi lúc compile thay vì lúc khách đang gọi.

Vì sao chọn Nest thay vì Express trần?

Express không "sai" — nó nhẹ, linh hoạt, hoàn hảo cho service nhỏ. Nhưng khi hệ thống lớn dần và đội ngũ đông lên, sự tự do của Express trở thành gánh nặng:

  • Cấu trúc rõ ràng: Nest áp đặt phân tầng, nên một dev mới mở repo Contact Center là biết ngay logic định tuyến cuộc gọi nằm ở routing.service.ts, không phải tìm trong 2000 dòng app.js.
  • Dễ test: Nhờ DI, bạn thay CallRepository thật bằng mock chỉ trong 1 dòng → viết unit test cho service mà không cần DB thật.
  • Dễ scale theo team: Module là ranh giới sở hữu. Team Voice giữ CallModule, team Messaging giữ ChatModule, ít giẫm chân nhau.
  • Hệ sinh thái tích hợp: Guard (auth), Interceptor (logging/transform), Pipe (validate), WebSocket Gateway, Microservices... đều có "khuôn" sẵn (xem E3, E6).
⚠️ Nest không phải "Express xịn hơn"

Nest mặc định chạy trên Express (HTTP adapter), nhưng nó là một tầng kiến trúc phía trên: thêm DI, decorator, lifecycle, module system. Bạn vẫn dùng được mọi middleware Express, nhưng cách tổ chức hoàn toàn khác.

② Kiến trúc tổng thể

NestJS khuyến khích kiến trúc phân tầng (layered). Một request đi qua các tầng có trách nhiệm tách bạch — đây là separation of concerns ở mức kiến trúc:

HTTP Request→ Controller→ Service→ Repository→ Database
TầngTrách nhiệmKHÔNG nên làm
ControllerNhận HTTP/WS, đọc params/body, gọi service, trả response. Tầng "mỏng".Không chứa logic nghiệp vụ, không truy vấn DB trực tiếp.
ServiceLogic nghiệp vụ: quy tắc định tuyến cuộc gọi, tính SLA, điều phối nhiều repository.Không biết tới req/res của HTTP; không gắn với chi tiết transport.
RepositoryTruy cập dữ liệu: query DB, gọi API ngoài. Trừu tượng hóa nguồn dữ liệu.Không chứa quy tắc nghiệp vụ phức tạp.

Ví dụ một luồng "phân công cuộc gọi cho agent rảnh" trong Contact Center, được tách 3 tầng rõ ràng:

call.controller.tsTypeScript
import { Controller, Post, Body } from '@nestjs/common';
import { CallService } from './call.service';

@Controller('calls')
export class CallController {
  // DI: Nest tự tiêm CallService qua constructor
  constructor(private readonly callService: CallService) {}

  @Post('assign')
  assign(@Body() dto: AssignCallDto) {
    // Controller chỉ điều phối — logic nằm ở service
    return this.callService.assignToAvailableAgent(dto.callId);
  }
}
call.service.tsTypeScript
@Injectable()
export class CallService {
  constructor(
    private readonly agents: AgentRepository,
    private readonly calls: CallRepository,
  ) {}

  async assignToAvailableAgent(callId: string) {
    const agent = await this.agents.findFirstAvailable();
    if (!agent) throw new ConflictException('Không có agent rảnh');
    // Quy tắc nghiệp vụ: gán + đổi trạng thái agent sang BUSY
    await this.agents.setStatus(agent.id, 'BUSY');
    return this.calls.assign(callId, agent.id);
  }
}
💡 Vì sao tách tầng lại đáng?

Ngày mai cuộc gọi đến từ HTTP, ngày kia từ WebSocket, ngày khác từ message queue. Nếu logic phân công nằm ở service (không gắn transport), bạn chỉ cần viết controller/gateway/consumer mỏng gọi lại cùng một assignToAvailableAgent(). Tái sử dụng & test cực kỳ thoải mái.

③ IoC & Dependency Injection

Inversion of Control (IoC) — "đảo ngược quyền điều khiển" — là nguyên lý: thay vì code của bạn chủ động tạo và quản lý các phụ thuộc, bạn giao quyền đó cho framework. Nest có một IoC container (còn gọi là DI container) đứng ra khởi tạo object và "tiêm" (inject) chúng vào nơi cần.

Không có DI vs Có DI

Hãy nhìn sự khác biệt. Cách "tự xoay sở" (tight coupling):

không-có-DI.tsTypeScript
class CallService {
  private agents = new AgentRepository(
    new PostgresClient(process.env.DB_URL)   // tự new từng tầng → cứng nhắc
  );
  // Test? Phải kết nối Postgres thật. Đổi nguồn dữ liệu? Sửa khắp nơi.
}

Cách Nest làm — bạn chỉ khai báo mình cần gì ở constructor, container lo phần còn lại:

có-DI.tsTypeScript
@Injectable()
class CallService {
  // "Tôi cần một AgentRepository" — Nest tự tạo & truyền vào
  constructor(private readonly agents: AgentRepository) {}
}

Nest đọc type của tham số constructor (nhờ emitDecoratorMetadata của TypeScript) để biết cần inject gì, rồi tra trong container ra instance phù hợp. Toàn bộ ứng dụng tạo thành một dependency graph mà container resolve theo đúng thứ tự lúc khởi động.

CallControllercần CallServicecần AgentRepositorycần DbConnection

Container resolve từ phải sang trái: tạo DbConnection → tạo AgentRepository (tiêm db vào) → tạo CallService (tiêm repo vào) → tạo CallController. Mặc định mỗi provider là singleton (1 instance dùng lại toàn app).

Lợi ích của DI

🔗 Loose coupling

Service phụ thuộc vào abstraction (interface/token), không vào cách tạo cụ thể. Đổi Postgres → Mongo chỉ cần đổi binding ở module.

🧪 Test dễ với mock

Trong test, override provider bằng mock: useValue: mockAgentRepo. Không cần DB thật, test nhanh & tất định.

♻️ Singleton tự quản

Container giữ vòng đời. Một connection pool dùng chung cho cả app thay vì mỗi nơi tự mở.

🧱 Dễ mở rộng

Thêm logging, caching, retry... bằng cách bọc provider — nơi gọi không cần biết.

Minh họa sức mạnh test nhờ DI — kiểm thử CallService mà không chạm DB:

call.service.spec.tsTypeScript
const mockAgents = { findFirstAvailable: jest.fn(), setStatus: jest.fn() };

const moduleRef = await Test.createTestingModule({
  providers: [
    CallService,
    { provide: AgentRepository, useValue: mockAgents }, // thay thật bằng mock
    { provide: CallRepository,  useValue: { assign: jest.fn() } },
  ],
}).compile();

const service = moduleRef.get(CallService);
mockAgents.findFirstAvailable.mockResolvedValue(null);

await expect(service.assignToAvailableAgent('c1'))
  .rejects.toThrow('Không có agent rảnh'); // test thuần logic, < 5ms
🐛 Bẫy về metadata

DI dựa trên reflect-metadata + cờ emitDecoratorMetadata: true & experimentalDecorators: true trong tsconfig.json. Thiếu chúng, Nest không "đọc" được type tham số → lỗi "Cannot resolve dependency" dù code trông đúng.

④ Providers

Provider là bất cứ thứ gì có thể được tiêm qua DI: service, repository, factory, value, helper, hằng cấu hình... Provider phổ biến nhất là một class gắn @Injectable() — decorator này đánh dấu "class này có thể tham gia DI container".

ℹ️ Provider vs Service

"Service" chỉ là một loại provider hay gặp. Provider là khái niệm rộng hơn: mọi thứ container quản lý vòng đời và có thể inject. Controller không phải provider (không inject được vào nơi khác) nhưng nhận provider qua constructor.

Bốn kiểu provider

providers.tsTypeScript
providers: [
  CallService,                                // 1) Class — Nest tự new (phổ biến nhất)

  { provide: 'QUEUE_CONFIG',                  // 2) useValue — hằng/cấu hình
    useValue: { maxWait: 30, priority: 'VIP' } },

  { provide: AgentRepository,                  // 3) useClass — đổi cài đặt theo token
    useClass: process.env.DB === 'mongo'
      ? MongoAgentRepository : PgAgentRepository },

  { provide: 'CACHE',                          // 4) useFactory — tạo động, có deps
    useFactory: (cfg: ConfigService) => new RedisCache(cfg.get('REDIS_URL')),
    inject: [ConfigService] },
]

Với provider không phải class (token là string/symbol), inject bằng @Inject():

queue.service.tsTypeScript
@Injectable()
export class QueueService {
  constructor(
    @Inject('QUEUE_CONFIG') private cfg: QueueConfig,  // token string
    @Inject('CACHE') private cache: RedisCache,
  ) {}
  // VIP chờ tối đa cfg.maxWait giây trước khi ưu tiên vượt hàng
}

Provider scope (vòng đời)

ScopeSố instanceDùng khi
DEFAULT (singleton)1 cho cả appGần như luôn dùng. Stateless service, repository, cache.
REQUEST1 mỗi requestCần dữ liệu riêng theo request (vd tenant ID của khách hàng, trace context).
TRANSIENTMới mỗi lần injectHiếm. Provider cần trạng thái riêng cho từng nơi tiêu thụ.
⚠️ REQUEST scope "lây lan" hiệu năng

Một provider REQUEST-scoped khiến toàn bộ chuỗi inject phía trên nó cũng phải tạo mới mỗi request → mất lợi thế singleton, tăng overhead. Trong Contact Center tải cao, ưu tiên truyền context qua tham số thay vì lạm dụng REQUEST scope.

⑤ Modules

Module là đơn vị tổ chức cao nhất của Nest — một "khối" gói các provider, controller liên quan thành một ranh giới đóng gói. Mỗi app có ít nhất một AppModule (root), và bạn chia tiếp theo domain: CallModule, ChatModule, TicketModule, AgentModule...

call.module.tsTypeScript
@Module({
  imports:     [AgentModule, DatabaseModule],  // dùng provider EXPORT từ module khác
  controllers: [CallController],               // endpoint HTTP/WS của domain này
  providers:   [CallService, CallRepository],  // service nội bộ module
  exports:     [CallService],                  // cho module khác inject lại CallService
})
export class CallModule {}
KhóaÝ nghĩa
providersCác provider được tạo & chỉ dùng nội bộ module (trừ khi export).
controllersCác controller (endpoint) thuộc module — Nest đăng ký route từ đây.
importsModule khác mà module này phụ thuộc, để dùng provider đã được export của chúng.
exportsProvider "mở cửa" cho module khác. Không export thì module ngoài không inject được — đây là encapsulation.
🐛 Lỗi kinh điển: quên exports

Bạn khai báo CallService trong CallModule.providers, rồi ReportModule import CallModule và cố inject CallService → "Nest can't resolve dependencies". Lý do: provider mặc định private với module. Phải thêm vào exports mới chia sẻ ra ngoài được.

Cấu trúc module của một Contact Center

AppModule (root)→ AuthModule AgentModule CallModule ChatModule TicketModule ReportModule

Nhiều module dùng chung tiện ích (logger, config, DB). Ta gom vào module dùng chung và đánh dấu @Global() để khỏi import lặp lại khắp nơi:

core.module.tsTypeScript
@Global()                                // provider export ở đây dùng được mọi nơi
@Module({
  providers: [LoggerService, ConfigService],
  exports:   [LoggerService, ConfigService],
})
export class CoreModule {}
💡 Dynamic module

Nhiều thư viện (DB, config, JWT) cung cấp module cấu hình động qua forRoot() / forRootAsync() / forFeature(). Ví dụ TypeOrmModule.forRoot({...}) nhận config rồi trả về một module đã được "may đo". Đây là pattern bạn sẽ gặp nhiều ở E4.

⑥ Bootstrap & so với Express

Mọi app Nest khởi động từ main.ts qua NestFactory. Factory này nhận AppModule, đọc toàn bộ cây module, resolve dependency graph, khởi tạo mọi singleton, rồi tạo HTTP server.

main.tsTypeScript
import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);   // nền Express mặc định

  app.useGlobalPipes(new ValidationPipe({ whitelist: true }));
  app.enableCors();                              // cho phép web agent gọi từ origin khác

  // Graceful shutdown: đóng socket/queue cuộc gọi trước khi tắt
  app.enableShutdownHooks();
  await app.listen(3000);
}
bootstrap();

Nest chạy trên gì?

Nest không tự viết HTTP server. Nó dùng một platform adapter:

🚂 @nestjs/platform-express

Mặc định. Bên dưới là Express. Tương thích toàn bộ middleware Express, ổn định, tài liệu nhiều.

⚡ @nestjs/platform-fastify

Đổi sang Fastify để tăng throughput, hợp tải cao. API Nest gần như không đổi nhờ tầng adapter.

Chính tầng adapter này khiến cùng một code Nest có thể chạy trên Express hoặc Fastify chỉ bằng đổi một dòng NestFactory.create(AppModule, new FastifyAdapter()) — minh chứng cho việc Nest là tầng kiến trúc phía trên server.

⚠️ Khi nào KHÔNG cần Nest?

Một function serverless nhỏ, một CLI, một proxy/gateway siêu mỏng, một prototype 1 endpoint — Nest có thể là "dùng dao mổ trâu giết gà": tốn thời gian dựng module/DI cho thứ chẳng có gì để tổ chức. Khi đó Express/Fastify trần hoặc thậm chí http thuần lại gọn hơn. Nest tỏa sáng khi độ phức tạp & quy mô đội ngũ tăng lên.

⚠️ Lỗi thường gặp & Best practices

🚫 Quên exports

Provider không export thì module khác không inject được → "can't resolve dependencies". Chỉ export cái thực sự cần chia sẻ.

🚫 Circular dependency

ModuleA import ModuleB và ngược lại → vòng lặp. Dùng forwardRef(), hoặc tốt hơn là tách phần chung ra module thứ ba.

🚫 Logic nghiệp vụ trong controller

Controller phải "mỏng". Nhồi business logic vào đó làm khó test & khó tái dùng cho WS/queue.

🚫 Lạm dụng REQUEST scope

"Lây" sang cả chuỗi inject, giết lợi thế singleton. Truyền context qua tham số khi có thể.

🚫 Thiếu cờ tsconfig

Quên emitDecoratorMetadata/experimentalDecorators → DI vỡ dù code đúng.

✅ 1 domain = 1 module

Chia theo nghiệp vụ (call, chat, ticket), không theo kỹ thuật (controllers/, services/). Dễ tách microservice sau.

🧪 Bài tập

🧪 Bài 1 — Tách tầng đúng chuẩn

Cho một endpoint "tạo ticket từ cuộc gọi vừa kết thúc": nhận callId + nội dung, kiểm tra cuộc gọi tồn tại, sinh mã ticket, lưu DB, trả về ticket. Hãy phân chia phần nào thuộc Controller, phần nào Service, phần nào Repository.

Gợi ý

Controller: nhận body (DTO), gọi ticketService.createFromCall(dto), trả kết quả — không hơn. Service: kiểm tra cuộc gọi tồn tại (gọi callRepo.findById), áp quy tắc sinh mã ticket, gọi ticketRepo.create. Repository: chỉ thao tác DB (findById, create), không chứa quy tắc nghiệp vụ. Lý do: nếu mai cuộc gọi đến từ WebSocket, ta chỉ viết gateway mỏng gọi lại cùng service.

🧪 Bài 2 — Chia sẻ provider giữa module

ReportModule cần dùng CallService (đang khai báo trong CallModule) để tính số cuộc gọi mỗi agent. Liệt kê 2 thay đổi bắt buộc để inject thành công, và giải thích vì sao cần cả hai.

Gợi ý

(1) Thêm CallService vào exports của CallModule — mở encapsulation. (2) Thêm CallModule vào imports của ReportModule — để DI graph của Report "nhìn thấy" provider đã export. Thiếu (1) thì dù import vẫn không resolve được; thiếu (2) thì module Report không biết tìm provider ở đâu.

🧪 Bài 3 — useFactory cho cache

Viết một provider token 'CALL_CACHE' dùng useFactory để tạo RedisCache với URL lấy từ ConfigService. Vì sao không dùng useClass ở đây?

Gợi ý

{ provide: 'CALL_CACHE', useFactory: (cfg) => new RedisCache(cfg.get('REDIS_URL')), inject: [ConfigService] }. Dùng useFactory vì cần logic khởi tạo động phụ thuộc giá trị runtime (URL từ config); useClass chỉ hợp khi Nest có thể tự new mà không cần truyền tham số tùy biến.

Ngân hàng câu hỏi phỏng vấn

Kiến trúc & DI của NestJS — chủ đề "tủ" để đánh giá chiều sâu backend.

Q1NestJS là gì? Nó khác Express ở đâu?Junior›

Trả lời: NestJS là framework backend cho Node.js, viết bằng TypeScript, opinionated và modular, lấy cảm hứng từ Angular (decorator, DI, module). Express là thư viện HTTP tối giản, không áp đặt cấu trúc và không có DI container. Nest chạy trên Express (hoặc Fastify) và bổ sung một tầng kiến trúc phía trên: Controller, Service/Provider, Module, DI, guard, interceptor, pipe.

Q2Vì sao dự án chọn NestJS thay vì Express trần?Junior›

Trả lời: Khi hệ thống lớn & team đông, Express "tự do" dễ thành mỗi người một kiểu. Nest cho: cấu trúc rõ ràng (module/tầng định sẵn) → onboard nhanh; DI → loose coupling & test dễ; module → ranh giới sở hữu rõ giúp scale theo team; hệ sinh thái tích hợp (auth, validation, WS, microservices). Với backend nghiệp vụ phức tạp như Contact Center, lợi ích này lớn hơn chi phí học.

⚠️ Bẫy: trả lời "Nest nhanh hơn Express" là sai trọng tâm — Nest mặc định chạy trên Express nên không nhanh hơn; giá trị nằm ở kiến trúc, không phải tốc độ.

Q3Giải thích IoC (Inversion of Control).Middle›

Trả lời: IoC là nguyên lý đảo ngược quyền điều khiển việc tạo & gắn kết phụ thuộc: thay vì code của bạn chủ động new các dependency, bạn giao quyền đó cho framework. Nest có một IoC container đứng ra khởi tạo object theo dependency graph và "tiêm" vào nơi cần. DI (Dependency Injection) là cách triển khai cụ thể của IoC — tiêm phụ thuộc qua constructor.

Q4Lợi ích của Dependency Injection là gì?Middle›

Trả lời: (1) Loose coupling — class phụ thuộc abstraction/token, không vào cách tạo cụ thể, đổi cài đặt (Postgres→Mongo) không sửa nơi tiêu thụ. (2) Test dễ — override provider bằng mock (useValue), test logic không cần DB thật. (3) Quản lý vòng đời tập trung — singleton tự động, connection pool dùng chung. (4) Dễ mở rộng — bọc/thay provider để thêm logging/cache mà nơi gọi không đổi.

Q5Provider trong Nest là gì? Có những loại nào?Middle›

Trả lời: Provider là bất cứ thứ gì container quản lý vòng đời và có thể inject: service, repository, factory, value, helper... Phổ biến là class gắn @Injectable(). Bốn kiểu khai báo: useClass (class, mặc định), useValue (hằng/đối tượng có sẵn), useClass (đổi cài đặt theo token), useFactory (tạo động, có thể inject deps). Với token không phải class (string/symbol) thì inject bằng @Inject('TOKEN').

Q6Module trong Nest đóng vai trò gì? Giải thích imports/exports/providers/controllers.Middle›

Trả lời: Module là đơn vị đóng gói cao nhất, gom provider & controller liên quan theo domain. providers: tạo & dùng nội bộ. controllers: các endpoint. imports: module khác mà module này phụ thuộc (để dùng provider đã export của chúng). exports: provider mở cho module ngoài inject. Mặc định provider private với module — đó là encapsulation; muốn chia sẻ phải export.

Q7NestJS chạy trên nền tảng gì? Có đổi được không?Junior›

Trả lời: Nest không tự viết HTTP server mà dùng một platform adapter. Mặc định là @nestjs/platform-express (nền Express); có thể đổi sang @nestjs/platform-fastify để tăng throughput, chỉ cần truyền FastifyAdapter vào NestFactory.create. Nhờ tầng adapter, code Nest gần như không đổi khi chuyển nền.

Q8Mô tả quy trình bootstrap của một app Nest.Middle›

Trả lời: Từ main.ts, gọi NestFactory.create(AppModule). Factory đọc cây module bắt đầu từ root, dựng dependency graph, khởi tạo mọi provider singleton theo đúng thứ tự phụ thuộc, đăng ký route từ controller, áp các global pipe/guard/interceptor, rồi app.listen(port) để mở server. Thường thêm enableShutdownHooks() cho graceful shutdown — quan trọng với Contact Center để không rớt cuộc gọi khi deploy.

Q9Provider scope là gì? Vì sao cẩn thận với REQUEST scope?Senior›

Trả lời: Scope quyết định số instance: DEFAULT (singleton, mặc định), REQUEST (mỗi request một instance), TRANSIENT (mỗi lần inject một instance). REQUEST scope "lây lan": mọi provider trong chuỗi inject phía trên một REQUEST-scoped provider cũng buộc phải tạo mới mỗi request → mất lợi thế singleton, tăng overhead/độ trễ. Ở tải cao nên truyền context (tenant, trace) qua tham số thay vì lạm dụng REQUEST scope.

⚠️ Bẫy: tưởng REQUEST scope "an toàn hơn" nên dùng mặc định — thực ra nó kéo hiệu năng và làm phình bộ nhớ ở hệ thống nhiều request.

Q10Circular dependency giữa hai module xảy ra thế nào và xử lý ra sao?Senior›

Trả lời: Xảy ra khi ModuleA cần provider của ModuleB và ngược lại (hoặc service A inject B và B inject A). Container không resolve được vòng. Cách xử lý: dùng forwardRef(() => OtherModule) / @Inject(forwardRef(...)) như giải pháp tạm; nhưng giải pháp tốt là tái cấu trúc — tách phần dùng chung ra module/service thứ ba để cắt vòng phụ thuộc. Vòng phụ thuộc thường là dấu hiệu ranh giới domain bị vẽ sai.

Q11Vì sao kiến trúc Controller–Service–Repository giúp hệ thống realtime dễ bảo trì?Senior›

Trả lời: Tách transport (controller/gateway) khỏi logic nghiệp vụ (service) khỏi truy cập dữ liệu (repository). Nhờ đó logic "phân công cuộc gọi", "tính SLA" nằm ở service, không gắn HTTP — có thể tái dùng cho HTTP, WebSocket Gateway và message-queue consumer cùng lúc. Test service thuần logic không cần transport/DB. Khi đổi DB hay thêm cache, chỉ repository thay đổi. Đây là separation of concerns ở mức kiến trúc, giảm chi phí thay đổi.

Q12Khi nào KHÔNG nên dùng NestJS?Middle›

Trả lời: Khi thứ cần xây quá nhỏ để hưởng lợi từ kiến trúc: một function serverless đơn, một CLI, một proxy/gateway siêu mỏng, một prototype 1–2 endpoint. Lúc đó dựng module/DI/decorator là chi phí thừa, làm chậm tiến độ; Express/Fastify trần hoặc http thuần gọn hơn. Nest đáng giá khi độ phức tạp nghiệp vụ & quy mô đội ngũ tăng — đúng hồ sơ của một backend Contact Center.
