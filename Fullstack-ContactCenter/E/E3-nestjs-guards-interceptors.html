Guards, Interceptors, Pipes & Filters

Vòng đời request trong Nest đi qua guards → interceptors → pipes → handler → filters. Nắm rõ để cài đặt auth, validation, transform, logging đúng chỗ.

🎯 Học xong chương này bạn sẽ

• Vẽ được thứ tự vòng đời request của Nest: middleware → guards → interceptors (trước) → pipes → handler → interceptors (sau) → exception filters.

• Phân biệt rạch ròi Guard vs Middleware vs Interceptor vs Pipe vs Filter — mỗi loại giải quyết đúng một việc, không lẫn lộn.

• Viết được Guard cho auth/RBAC dựa trên CanActivate + Reflector + SetMetadata.

• Dùng Interceptor (AOP) để chuẩn hóa response, logging, caching, timeout và đo thời gian xử lý.

• Cấu hình ValidationPipe + class-validator để chặn dữ liệu bẩn ngay tại cổng vào.

• Bắt và định dạng lỗi tập trung bằng Exception Filter, tạo custom param decorator như @CurrentUser().

💡 Liên hệ hệ thống Contact Center

Một request "agent chuyển cuộc gọi sang queue khác" đi qua rất nhiều tầng cắt ngang: xác thực agent (Guard), kiểm tra agent có quyền transfer (RBAC Guard), validate queueId và callId (Pipe), ghi log audit + đo độ trễ (Interceptor), và nếu queue đầy thì trả lỗi 409 có cấu trúc (Filter). Cùng một logic cắt ngang này lặp lại ở mọi endpoint — đó chính là lý do Nest tách chúng thành các thành phần riêng để tái dùng, thay vì copy-paste vào từng controller.

① Vòng đời một request trong NestJS

Đây là sơ đồ quan trọng nhất của cả chương. Khi một HTTP request đi vào Nest, nó không nhảy thẳng vào hàm xử lý (handler) của controller, mà chạy qua một pipeline có thứ tự cố định. Hiểu thứ tự này giúp bạn đặt mỗi logic đúng chỗ và giải thích được vì sao một số thứ "chạy trước", một số "chạy sau".

Request đến→ Middleware→ Guards→ Interceptors (trước)→ Pipes→ Handler (controller)→ Interceptors (sau)→ Response
Bất kỳ chỗ nào ném lỗi→ Exception Filters→ Response lỗi đã định dạng

Diễn giải từng chặng:

  • Middleware — chạy sớm nhất, ở tầng Express/Fastify. Nó chưa biết request sẽ vào controller/handler nào (chưa có ngữ cảnh route của Nest). Hợp cho việc rất tổng quát: gắn requestId, CORS, helmet, parse cookie, log thô.
  • Guards — quyết định cho hay không cho request đi tiếp. Trả về true thì qua; trả false hoặc ném lỗi thì dừng (mặc định 403). Đây là nơi đặt xác thực (đã đăng nhập chưa?) và phân quyền (có vai trò phù hợp không?). Guard đã có ngữ cảnh route nên đọc được metadata gắn trên handler.
  • Interceptors (chiều đi vào) — chạy trước handler. Có thể chuẩn bị dữ liệu, bắt đầu đo thời gian, kiểm tra cache (nếu trúng cache thì trả luôn, bỏ qua handler).
  • Pipes — biến đổi và kiểm tra tham số đầu vào (body, query, param) ngay trước khi handler nhận. Ví dụ ép kiểu "42" thành số, hoặc validate DTO. Sai thì ném lỗi 400.
  • Handler — phương thức trong controller, chứa logic nghiệp vụ thật sự.
  • Interceptors (chiều đi ra) — chạy sau handler, trên luồng RxJS. Đây là nơi gói lại response, log thời gian, ghi audit, hoặc map lỗi.
  • Exception Filters — bắt mọi exception ném ra từ bất kỳ chặng nào ở trên (guard, pipe, handler, interceptor) và chuyển thành response lỗi có cấu trúc thống nhất.
⚠️ Một mẹo ghi nhớ thứ tự

"Ai gác cổng trước, ai dọn dẹp sau": Guard gác cổng (cho vào hay không) trước khi tốn công validate. Vì vậy nếu chưa đăng nhập, Nest trả 401 ngay mà không cần chạy ValidationPipe. Còn Filter luôn ở "lưới an toàn" cuối cùng. Một bẫy phỏng vấn hay gặp: nhiều người tưởng pipe chạy trước guard — thực ra guard chạy trước pipe.

Phạm vi áp dụng (scope)

Mọi thành phần (guard, interceptor, pipe, filter) đều có thể gắn ở 3 phạm vi, từ rộng tới hẹp:

🌍 Global

Áp cho toàn app. Đăng ký qua app.useGlobalGuards() hoặc provider APP_GUARD trong module (cách thứ hai cho phép inject dependency).

🧩 Controller

Gắn @UseGuards() trên class controller — áp cho mọi handler trong nó.

🎯 Handler

Gắn ngay trên một phương thức — chỉ áp cho route đó.

💡 Mẹo production

Trong Contact Center, ta thường để JwtAuthGuard và ValidationPipe ở global (mặc định mọi endpoint đều cần đăng nhập + validate), rồi "mở ngoại lệ" cho vài route công khai bằng decorator @Public(). Cách này an toàn hơn việc nhớ gắn guard cho từng route — quên một chỗ là lộ API.

② Guards — gác cổng cho auth & phân quyền

Guard là class triển khai interface CanActivate, có đúng một phương thức canActivate() trả về boolean (hoặc Promise/Observable<boolean>). Nest gọi nó trước handler: true → cho qua, false → chặn (403 Forbidden). Nếu Guard tự ném UnauthorizedException thì client nhận 401.

jwt-auth.guard.tsTypeScript
import { Injectable, CanActivate, ExecutionContext, UnauthorizedException } from '@nestjs/common';

@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private jwt: JwtService) {}

  async canActivate(ctx: ExecutionContext): Promise<boolean> {
    const req = ctx.switchToHttp().getRequest();
    const token = req.headers.authorization?.replace('Bearer ', '');
    if (!token) throw new UnauthorizedException('Thiếu token');
    try {
      const payload = await this.jwt.verifyAsync(token);
      req.user = payload;            // gắn agent vào request để dùng sau
      return true;
    } catch {
      throw new UnauthorizedException('Token không hợp lệ');
    }
  }
}

Điểm cốt lõi: ExecutionContext là một "bao" thông tin về ngữ cảnh thực thi. Nhờ switchToHttp() (hoặc switchToWs() cho WebSocket, switchToRpc() cho microservice) mà cùng một guard có thể tái dùng cho cả HTTP lẫn WebSocket — rất quan trọng với Contact Center vì cả REST API lẫn kênh realtime đều cần xác thực agent.

RBAC: Guard + SetMetadata + Reflector

Phân quyền theo vai trò (Role-Based Access Control) là ứng dụng kinh điển của Guard. Ý tưởng gồm 3 mảnh ghép:

  • SetMetadata(key, value) — gắn "nhãn" metadata lên handler (vd: route này cần vai trò supervisor).
  • Reflector — công cụ Nest cung cấp để đọc lại metadata đó từ trong guard.
  • RolesGuard — so khớp vai trò của agent (từ req.user) với vai trò yêu cầu.
roles.guard.ts + roles.decorator.tsTypeScript
// 1) Decorator tiện dụng bọc SetMetadata
export const ROLES_KEY = 'roles';
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

// 2) Guard đọc metadata bằng Reflector rồi so khớp
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(ctx: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
      ctx.getHandler(), ctx.getClass(),   // đọc cả ở method lẫn controller
    ]);
    if (!required) return true;        // route không yêu cầu vai trò → cho qua
    const { user } = ctx.switchToHttp().getRequest();
    return required.some(r => user?.roles?.includes(r));
  }
}

// 3) Sử dụng trên controller cuộc gọi
@Post(':id/force-disconnect')
@Roles('supervisor', 'admin')   // chỉ giám sát/admin mới ngắt cuộc gọi
forceDisconnect(@Param('id') callId: string) { ... }
⚠️ getAllAndOverride vs get

reflector.get() chỉ đọc metadata ở một chỗ. getAllAndOverride() đọc ở nhiều nơi (handler + class) và lấy giá trị "gần nhất" thắng — hợp khi bạn đặt @Roles mặc định trên controller rồi override ở vài method. Còn getAllAndMerge() thì gộp lại. Dùng sai sẽ khiến phân quyền hoạt động không như mong đợi.

🐛 Vì sao bắt buộc @Injectable() trên guard?

Vì RolesGuard cần inject Reflector (và JwtAuthGuard cần inject JwtService). Không có @Injectable(), Nest không quản lý được nó qua DI container, không tự dựng được dependency. Nếu đăng ký guard global bằng app.useGlobalGuards(new RolesGuard(...)) thì bạn phải tự tay truyền dependency — vì vậy cách khuyến nghị là đăng ký qua provider APP_GUARD để Nest tự inject.

③ Interceptors — lập trình hướng khía cạnh (AOP)

Interceptor là class triển khai NestInterceptor với phương thức intercept(ctx, next). Nó bao quanh handler theo kiểu "bánh sandwich": code trước next.handle() chạy trước handler, code gắn vào luồng RxJS trả về chạy sau handler. Đây là hiện thân của AOP (Aspect-Oriented Programming) — tách các "khía cạnh cắt ngang" (logging, đo thời gian, transform) ra khỏi logic nghiệp vụ.

Những việc Interceptor làm rất tốt:

📦 Transform response

Bọc mọi kết quả vào { data, meta } để client nhận format thống nhất.

⏱️ Đo thời gian / log

Tính độ trễ mỗi request, ghi log audit "agent X làm hành động Y".

⚡ Caching

Trúng cache thì trả ngay, bỏ qua handler (tiết kiệm DB).

⌛ Timeout

Hủy request nếu xử lý quá lâu, tránh treo client.

🔁 Map lỗi

Bắt lỗi trên stream và chuyển đổi (vd lỗi DB → lỗi nghiệp vụ).

🧹 Lọc field nhạy cảm

Xóa password, token khỏi object trước khi trả về.

transform.interceptor.tsTypeScript
// Chuẩn hóa MỌI response: { data, timestamp } — frontend chỉ cần parse 1 dạng
@Injectable()
export class TransformInterceptor<T> implements NestInterceptor<T, { data: T }> {
  intercept(ctx: ExecutionContext, next: CallHandler): Observable<{ data: T }> {
    return next.handle().pipe(
      map(data => ({ data, timestamp: new Date().toISOString() })),
    );
  }
}
logging.interceptor.tsTypeScript
// Đo độ trễ + audit log cho thao tác trên cuộc gọi / queue
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  private logger = new Logger('Audit');

  intercept(ctx: ExecutionContext, next: CallHandler): Observable<any> {
    const req = ctx.switchToHttp().getRequest();
    const start = Date.now();
    const who = req.user?.sub ?? 'anon';

    return next.handle().pipe(
      tap(() => {
        const ms = Date.now() - start;
        this.logger.log(`agent=${who} ${req.method} ${req.url} +${ms}ms`);
      }),
    );
  }
}
timeout.interceptor.tsTypeScript
// Cuộc gọi lookup thông tin khách qua dịch vụ ngoài — chặn treo quá 5s
@Injectable()
export class TimeoutInterceptor implements NestInterceptor {
  intercept(_ctx: ExecutionContext, next: CallHandler) {
    return next.handle().pipe(
      timeout(5000),
      catchError(err => throwError(() =>
        err instanceof TimeoutError
          ? new RequestTimeoutException('Dịch vụ phản hồi quá chậm')
          : err,
      )),
    );
  }
}
💡 Interceptor là điểm "bọc 2 đầu"

Khác Guard (chỉ chạy trước, không thấy response) và Pipe (chỉ thấy input), Interceptor là thành phần duy nhất thấy cả input lẫn output và có thể can thiệp luồng RxJS. Vì vậy mọi logic dạng "trước + sau" như đo thời gian, transaction, retry, cache đều thuộc về Interceptor. Khi đăng ký nhiều interceptor: thứ tự đi vào theo thứ tự khai báo, thứ tự đi ra ngược lại (giống stack).

④ Pipes & Validation — chặn dữ liệu bẩn ở cổng vào

Pipe có hai vai trò: transformation (biến đổi input, vd ép "42" → 42) và validation (kiểm tra input, nếu sai thì ném lỗi). Nest chạy pipe ngay trước khi handler nhận đối số, nên handler luôn nhận dữ liệu "sạch và đúng kiểu".

Built-in pipes

🔢 ParseIntPipe

Ép param/query thành số nguyên, sai thì 400. Có anh em ParseBoolPipe, ParseUUIDPipe.

🆔 ParseUUIDPipe

Đảm bảo callId đúng định dạng UUID trước khi truy DB.

✅ ValidationPipe

"Ngôi sao" — validate cả DTO object bằng class-validator.

calls.controller.tsTypeScript
@Get(':id')
getCall(@Param('id', ParseUUIDPipe) id: string) {
  // tới đây id chắc chắn là UUID hợp lệ
  return this.calls.findOne(id);
}

@Get()
list(@Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number) {
  return this.calls.paginate(page);
}

ValidationPipe + class-validator

Đây là cơ chế validate mạnh nhất. Bạn khai báo luật ngay trên DTO bằng decorator của class-validator, rồi bật ValidationPipe global. Khi request đến, Nest dùng class-transformer để chuyển plain object thành instance DTO, rồi class-validator quét các decorator để kiểm tra.

transfer-call.dto.tsTypeScript
export class TransferCallDto {
  @IsUUID()
  callId: string;

  @IsUUID()
  targetQueueId: string;

  @IsOptional()
  @IsString()
  @MaxLength(280)
  note?: string;

  @IsIn(['normal', 'urgent'])
  priority: string;
}
main.tsTypeScript
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,            // tự loại field KHÔNG có trong DTO
  forbidNonWhitelisted: true, // gửi thừa field lạ → báo lỗi 400
  transform: true,            // tự chuyển plain → instance DTO, ép kiểu
  transformOptions: { enableImplicitConversion: true },
}));
🐛 whitelist là tuyến phòng thủ chống mass-assignment

Giả sử agent gửi thêm field lạ { isSupervisor: true } hòng leo thang quyền. Nếu không bật whitelist, field rác có thể lọt vào object và bị code dùng nhầm. Bật whitelist: true sẽ tự động loại bỏ mọi field không khai báo trong DTO; thêm forbidNonWhitelisted thì còn báo lỗi luôn. Đây là best practice bắt buộc cho hệ thống xử lý dữ liệu khách hàng.

Bạn cũng có thể viết custom pipe khi cần logic đặc thù, ví dụ chuẩn hóa số điện thoại của khách về E.164 trước khi lưu:

phone-normalize.pipe.tsTypeScript
@Injectable()
export class PhoneNormalizePipe implements PipeTransform {
  transform(value: string) {
    const e164 = toE164(value);
    if (!e164) throw new BadRequestException('Số điện thoại không hợp lệ');
    return e164;          // handler nhận giá trị đã chuẩn hóa
  }
}

⑤ Exception Filters — bắt & định dạng lỗi tập trung

Khi bất cứ đâu ném exception, Nest có một global exception filter mặc định bắt nó và trả JSON lỗi. Nhưng để có response lỗi nhất quán trên toàn hệ thống (cùng một schema cho frontend), ta thường tự viết Exception Filter.

Phân cấp HttpException

Nest cung cấp sẵn các lớp lỗi HTTP có mã trạng thái tương ứng. Ném đúng lớp là Nest trả đúng status:

ExceptionStatusDùng khi
BadRequestException400Dữ liệu vào sai (thường do pipe)
UnauthorizedException401Chưa đăng nhập / token sai
ForbiddenException403Đã đăng nhập nhưng không đủ quyền
NotFoundException404Không tìm thấy cuộc gọi/ticket
ConflictException409Queue đầy, trạng thái xung đột
all-exceptions.filter.tsTypeScript
@Catch()   // không tham số = bắt MỌI exception
export class AllExceptionsFilter implements ExceptionFilter {
  private logger = new Logger('Exception');

  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const res = ctx.getResponse();
    const req = ctx.getRequest();

    const status = exception instanceof HttpException
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;

    const message = exception instanceof HttpException
      ? exception.getResponse()
      : 'Lỗi hệ thống';

    if (status >= 500) this.logger.error(exception);  // chỉ log 5xx

    res.status(status).json({
      success: false,
      statusCode: status,
      path: req.url,
      timestamp: new Date().toISOString(),
      error: message,
    });
  }
}
⚠️ @Catch() có và không có tham số

@Catch(HttpException) chỉ bắt một loại lỗi cụ thể (lọc theo type). @Catch() rỗng bắt tất cả — dùng cho filter "lưới an toàn" cuối cùng. Bạn có thể có nhiều filter chuyên biệt (vd QueryFailedError của TypeORM → 409) kết hợp với một filter tổng. Filter ở phạm vi hẹp hơn (handler) được ưu tiên hơn filter global.

🐛 Đừng để lộ stack trace ra client

Với lỗi 500, tuyệt đối không trả message gốc/stack cho client (lộ cấu trúc DB, đường dẫn nội bộ). Hãy trả thông điệp chung chung và chỉ logger.error chi tiết ở server. Đây vừa là vấn đề bảo mật vừa là trải nghiệm người dùng.

⑥ Custom decorators — đường dẫn ngữ cảnh sạch sẽ

Sau khi JwtAuthGuard gắn req.user, mọi handler thường viết lặp const user = ctx.switchToHttp().getRequest().user. Ta gói nó vào một custom param decorator để code controller gọn và rõ nghĩa:

current-user.decorator.tsTypeScript
export const CurrentUser = createParamDecorator(
  (data: string | undefined, ctx: ExecutionContext) => {
    const user = ctx.switchToHttp().getRequest().user;
    return data ? user?.[data] : user;   // @CurrentUser('sub') lấy 1 field
  },
);

// Dùng trong controller — sạch hơn hẳn
@Post('transfer')
transfer(@CurrentUser() agent: Agent, @Body() dto: TransferCallDto) {
  return this.calls.transfer(agent.id, dto);
}

Ta cũng có thể gộp nhiều decorator thành một bằng applyDecorators — tạo một "decorator tổng" cho route cần bảo vệ:

auth.decorator.tsTypeScript
// Gộp guard + role + metadata vào 1 decorator dùng lại khắp nơi
export function Auth(...roles: string[]) {
  return applyDecorators(
    Roles(...roles),
    UseGuards(JwtAuthGuard, RolesGuard),
  );
}

@Auth('supervisor')   // = vừa đăng nhập, vừa đúng vai trò
@Get('dashboard')
dashboard() { ... }
💡 SetMetadata + Reflector là nền của rất nhiều thứ

Cặp đôi này không chỉ dùng cho RBAC. Decorator @Public() (đánh dấu route bỏ qua auth), @CacheKey(), @RateLimit()... đều theo cùng công thức: decorator gắn metadata → guard/interceptor đọc lại bằng Reflector → hành xử tương ứng. Hiểu pattern này là bạn tự mở rộng được Nest theo nhu cầu.

⚠️ Lỗi thường gặp & Best practices

🚫 Nhồi nghiệp vụ vào Guard

Guard chỉ trả lời "cho qua hay không". Đừng gọi DB ghi dữ liệu trong guard — việc đó thuộc service/handler.

🚫 Validate trong handler

Kiểm tra if (!dto.callId) thủ công là dấu hiệu thiếu DTO + ValidationPipe. Đẩy validate ra pipe.

🚫 Quên @Injectable()

Guard/interceptor cần inject dependency mà thiếu decorator → DI không dựng được, lỗi runtime khó hiểu.

🚫 Đăng ký global bằng new khi cần DI

useGlobalGuards(new G()) không inject được. Dùng provider APP_GUARD để Nest tự inject.

🚫 Quên bật transform/whitelist

Không có transform thì number trong DTO vẫn là string; không có whitelist thì lọt field rác.

🚫 Lẫn lộn Interceptor & Middleware

Cần thấy response/biết route → Interceptor. Việc tầng HTTP thô, không cần ngữ cảnh route → Middleware.

✅ Auth global + @Public()

Mặc định khóa hết, mở ngoại lệ có chủ đích — an toàn hơn nhớ gắn guard từng route.

✅ Một schema lỗi duy nhất

Dùng một Exception Filter để mọi lỗi có cùng format — frontend xử lý dễ, log đồng nhất.

🧪 Bài tập

🧪 Bài 1 — @Public() bỏ qua auth global

Giả sử JwtAuthGuard đã đăng ký global. Hãy thiết kế decorator @Public() để route POST /auth/login và GET /health không yêu cầu token, trong khi mọi route khác vẫn bị bảo vệ. Cần sửa gì trong guard?

Gợi ý

export const Public = () => SetMetadata('isPublic', true);. Trong JwtAuthGuard.canActivate, dùng reflector.getAllAndOverride('isPublic', [getHandler(), getClass()]); nếu true thì return true ngay (bỏ qua kiểm tra token). Đây chính là pattern SetMetadata + Reflector — guard global vẫn đọc được metadata của từng route.

🧪 Bài 2 — Interceptor đo & cảnh báo độ trễ

Viết một interceptor đo thời gian xử lý mỗi request; nếu vượt 1000ms thì log warning kèm route và id agent. Vì sao việc này nên là interceptor chứ không phải middleware?

Gợi ý

Bắt start = Date.now() trước next.handle(), trong .pipe(tap(() => ...)) tính ms và so ngưỡng. Phải là interceptor vì cần đo trọn vẹn tới khi handler trả kết quả (sau handler) và cần ngữ cảnh route + req.user đã được guard gắn — middleware chạy quá sớm, chưa có những thứ đó.

🧪 Bài 3 — RBAC nhiều tầng

Một controller CallsController mặc định chỉ cho agent, nhưng route force-disconnect chỉ cho supervisor. Đặt @Roles ở đâu và dùng phương thức nào của Reflector để route con override controller?

Gợi ý

Đặt @Roles('agent') trên class controller và @Roles('supervisor') trên method. Dùng getAllAndOverride(ROLES_KEY, [getHandler(), getClass()]) — vì handler đứng trước trong mảng nên giá trị ở method "thắng", override controller. Nếu muốn gộp cả hai vai trò thì dùng getAllAndMerge thay thế.

Ngân hàng câu hỏi phỏng vấn

Guards, Interceptors, Pipes, Filters — bộ câu hỏi "đo chiều sâu" NestJS.

Q1Hãy mô tả vòng đời một request trong NestJS.Middle›

Trả lời: Request đi qua: Middleware → Guards → Interceptors (chiều vào) → Pipes → Handler (controller) → Interceptors (chiều ra) → Response. Nếu bất kỳ chặng nào ném lỗi, Exception Filter bắt và định dạng response lỗi. Middleware ở tầng HTTP thô (chưa biết route), Guard quyết định cho đi tiếp, Pipe validate/transform input ngay trước handler, Interceptor bọc 2 đầu handler.

⚠️ Bẫy: nói "pipe chạy trước guard" là sai — guard luôn chạy trước pipe.

Q2Guard là gì? Interface và phương thức của nó?Junior›

Trả lời: Guard là class triển khai interface CanActivate với phương thức canActivate(ctx) trả về boolean | Promise<boolean> | Observable<boolean>. Trả true thì request đi tiếp, false thì Nest trả 403; nếu guard ném UnauthorizedException thì trả 401. Dùng chủ yếu cho xác thực và phân quyền.

Q3Phân biệt Guard vs Middleware vs Interceptor.Middle›

Trả lời: Middleware chạy sớm nhất ở tầng Express/Fastify, chưa biết route nào sẽ xử lý, không thấy response của Nest — hợp cho việc tổng quát (requestId, CORS, log thô). Guard đã có ngữ cảnh route, trả true/false để quyết định cho qua — chuyên cho auth/RBAC, không can thiệp response. Interceptor bọc cả trước và sau handler, thấy cả input lẫn output, can thiệp được luồng RxJS — cho transform, logging, cache, timeout. Khác biệt cốt lõi: middleware không biết route, guard không thấy response, interceptor thấy cả hai chiều.

⚠️ Bẫy: dùng middleware để bọc response/đo thời gian trọn vẹn — middleware không thấy kết quả handler, nên dùng interceptor.

Q4Interceptor dùng để làm gì? Cho ví dụ.Middle›

Trả lời: Interceptor hiện thực AOP — tách logic cắt ngang khỏi nghiệp vụ. Các ví dụ: chuẩn hóa response (map vào { data }), logging/đo thời gian (tap), caching (trúng cache thì trả luôn, bỏ qua handler), timeout (timeout(5000)), retry, bọc transaction, map lỗi (catchError), lọc field nhạy cảm. Nó triển khai NestInterceptor.intercept(ctx, next) và thao tác trên next.handle() (một Observable).

Q5ValidationPipe hoạt động thế nào? Vai trò của class-validator & class-transformer?Middle›

Trả lời: Khi request đến, ValidationPipe dùng class-transformer để chuyển plain object thành instance của DTO, sau đó class-validator quét các decorator (@IsUUID, @IsIn...) trên DTO để kiểm tra. Sai luật thì ném BadRequestException (400) với danh sách lỗi. Các option quan trọng: whitelist (loại field không khai báo), forbidNonWhitelisted (báo lỗi field lạ), transform (ép kiểu, chuyển plain→instance). Thường đăng ký global trong main.ts.

Q6Pipe có mấy vai trò? Phân biệt với Guard.Junior›

Trả lời: Pipe có hai vai trò: transformation (biến đổi input, vd ParseIntPipe ép "42"→42) và validation (kiểm tra, sai thì 400). Nó chạy ngay trước khi handler nhận đối số và chỉ thấy input. Guard thì khác hẳn: trả true/false quyết định request có được đi tiếp không, chuyên cho auth/quyền, không biến đổi dữ liệu. Guard chạy trước Pipe trong pipeline.

Q7Exception Filter là gì? Khi nào tự viết thay vì dùng mặc định?Middle›

Trả lời: Exception Filter triển khai ExceptionFilter.catch(exception, host) để bắt lỗi và tạo response. Nest có filter mặc định, nhưng ta tự viết khi cần: schema lỗi nhất quán cho frontend, log tập trung, map lỗi đặc thù (vd QueryFailedError→409), che giấu chi tiết 5xx. Dùng @Catch(SomeException) để lọc theo loại, hoặc @Catch() rỗng để bắt tất cả. Đăng ký được ở global hoặc theo route.

Q8RBAC trong Nest cài đặt thế nào với Guard + Reflector?Senior›

Trả lời: Ba mảnh: (1) decorator @Roles('supervisor') bọc SetMetadata('roles', [...]) gắn nhãn lên handler/class; (2) một RolesGuard inject Reflector, dùng reflector.getAllAndOverride('roles', [ctx.getHandler(), ctx.getClass()]) để đọc vai trò yêu cầu; (3) so khớp với req.user.roles (do JwtAuthGuard đã gắn) — trùng thì cho qua. Cần đảm bảo guard auth chạy trước guard role. Khi đăng ký global, dùng provider APP_GUARD để Nest tự inject Reflector.

⚠️ Bẫy: dùng reflector.get() thay vì getAllAndOverride() — sẽ không xử lý đúng trường hợp metadata đặt cả ở class lẫn method.

Q9Đăng ký guard global thế nào? Khác nhau giữa useGlobalGuards và APP_GUARD?Senior›

Trả lời: Có hai cách. app.useGlobalGuards(new MyGuard()) trong main.ts — đơn giản nhưng phải tự truyền dependency, không inject được qua DI. Cách thứ hai là khai báo provider { provide: APP_GUARD, useClass: MyGuard } trong một module — Nest quản lý qua DI container nên guard có thể inject Reflector, service... Đây là cách khuyến nghị khi guard cần dependency. Cùng nguyên tắc với APP_INTERCEPTOR, APP_PIPE, APP_FILTER.

Q10Vì sao guard/interceptor cần @Injectable()?Junior›

Trả lời: Vì chúng thường cần inject dependency (Reflector, JwtService, repository...). @Injectable() đánh dấu class để Nest đưa vào DI container, tự dựng và tiêm dependency. Nếu đăng ký bằng new thủ công thì không cần DI nhưng phải tự truyền tham số — bất tiện và không chia sẻ được instance singleton. Vì vậy chuẩn là gắn @Injectable() và đăng ký qua provider.

Q11ExecutionContext là gì? Vì sao quan trọng cho hệ thống vừa REST vừa WebSocket?Senior›

Trả lời: ExecutionContext kế thừa ArgumentsHost, gói thông tin ngữ cảnh thực thi và cho biết transport hiện tại. Nhờ switchToHttp(), switchToWs(), switchToRpc(), cùng một guard/interceptor có thể tái dùng cho HTTP, WebSocket và microservice — lấy request/socket tương ứng. Với Contact Center vừa có REST API vừa có kênh realtime, một AuthGuard viết theo ExecutionContext có thể xác thực cả hai mặt phẳng, tránh trùng lặp logic. Ngoài ra nó cung cấp getHandler()/getClass() để Reflector đọc metadata.

Q12Khi đăng ký nhiều interceptor, thứ tự thực thi ra sao?Senior›

Trả lời: Phần code trước next.handle() chạy theo thứ tự đăng ký (global → controller → handler). Phần gắn vào Observable trả về (sau handler) chạy theo thứ tự ngược lại, giống cơ chế stack/onion: interceptor đăng ký ngoài cùng "vào trước, ra sau". Hiểu điều này quan trọng khi kết hợp transform + logging: bạn cần biết logging đo được response trước hay sau khi transform. Tương tự, exception filter ở scope hẹp (handler) ưu tiên hơn filter global.
