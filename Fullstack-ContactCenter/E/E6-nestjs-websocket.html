NestJS WebSocket Gateway & Microservices

Dựng tầng realtime bằng WebSocket Gateway của Nest và mở rộng hệ thống bằng microservices — đúng yêu cầu realtime của Contact Center.

🎯 Học xong chương này bạn sẽ

• Dựng được WebSocket Gateway trong Nest với @WebSocketGateway, lắng nghe sự kiện bằng @SubscribeMessage và lấy dữ liệu qua @MessageBody/@ConnectedSocket.

• Phân biệt emit / broadcast / room và áp dụng cho hàng đợi cuộc gọi, kênh chat, bảng trạng thái agent.

• Hiểu lifecycle hooks của gateway (OnGatewayInit, OnGatewayConnection, OnGatewayDisconnect) và xác thực kết nối WebSocket bằng Guard.

• Biết vì sao cần Redis adapter khi chạy nhiều instance và cách cắm IoAdapter tùy biến.

• Nắm Nest Microservices: transporter (TCP/Redis/NATS/Kafka/RabbitMQ), @MessagePattern vs @EventPattern, ClientProxy và mô hình hybrid app.

• Trả lời được nhóm câu hỏi phỏng vấn kinh điển: gateway vs controller, scale WS, request-response vs event, chọn transporter.

💡 Liên hệ thực tế Contact Center

Một tổng đài hiện đại sống nhờ realtime: agent thấy ngay cuộc gọi mới rơi vào hàng đợi, supervisor theo dõi bảng trạng thái live, khách chat được trả lời tức thì, ticket cập nhật mà không cần F5. Phần REST (đăng nhập, lịch sử, báo cáo) đã có ở các chương trước; chương này lo phần kênh hai chiều luôn mở — và làm sao nó vẫn đúng khi hệ thống có nhiều node sau load balancer.

① WebSocket Gateway là gì?

Trong Nest, Gateway là lớp tương đương Controller nhưng cho giao thức WebSocket thay vì HTTP. Controller ánh xạ route HTTP → handler; Gateway ánh xạ tên sự kiện WS → handler. Cùng triết lý DI, module, guard, pipe, interceptor — bạn dùng lại gần như nguyên vẹn tư duy đã học ở E2 và E3.

Khía cạnhController (HTTP)Gateway (WebSocket)
Decorator lớp@Controller('calls')@WebSocketGateway()
Khai báo handler@Get(), @Post() theo route@SubscribeMessage('event') theo tên sự kiện
Mô hình giao tiếpRequest → Response, kết nối đóng sau mỗi lầnKết nối giữ mở, hai chiều, push bất cứ lúc nào
Lấy dữ liệu vào@Body, @Param, @Query@MessageBody, @ConnectedSocket
Trả về clientreturn body HTTPemit, hoặc return (ack), hoặc Observable stream

Nest hỗ trợ hai nền tảng WS: Socket.IO (mặc định — có room, ack, fallback, reconnect) và ws thuần (nhẹ, chuẩn WebSocket). Phần lớn Contact Center chọn Socket.IO vì room và reconnect là tính năng đắt giá cho hàng đợi cuộc gọi. Trong chương này mặc định dùng Socket.IO.

queue.gateway.tsTypeScript
import { WebSocketGateway, SubscribeMessage, MessageBody } from '@nestjs/websockets';

// cors + namespace + path — cấu hình ngay trên decorator lớp
@WebSocketGateway({
  namespace: '/queue',        // gom nghiệp vụ hàng đợi vào 1 namespace riêng
  cors: { origin: '*' },     // production phải whitelist domain, không để '*'
})
export class QueueGateway {
  @SubscribeMessage('agent:ready')
  handleAgentReady(@MessageBody() data: { agentId: string }) {
    // agent bấm "Sẵn sàng" → đủ điều kiện nhận cuộc gọi mới
    return { ok: true, agentId: data.agentId };  // giá trị return = ack gửi về client
  }
}
⚠️ Gateway phải nằm trong providers của Module

Gateway không tự được Nest quét. Bạn phải đăng ký nó trong providers của một Module (giống một service), nếu không handler sẽ không bao giờ chạy. Đây là lỗi "im lặng" hay gặp nhất khi mới làm gateway.

Cấu hình hay dùng trên @WebSocketGateway

🏷️ namespace

Chia logic thành các "kênh" độc lập: /queue, /chat, /supervisor. Mỗi namespace có tập room và handler riêng.

🛣️ path

Đường dẫn endpoint WS (mặc định /socket.io). Đổi khi reverse proxy yêu cầu route riêng.

🔒 cors

Whitelist origin của frontend. Để * trên production là rủi ro bảo mật.

🚪 port

Có thể cho WS chạy port riêng. Thường vẫn dùng chung HTTP server để qua một load balancer duy nhất.

② Subscribe & emit: nghe và đẩy sự kiện

Trái tim của gateway là cặp nhận sự kiện (@SubscribeMessage) và đẩy sự kiện (emit). Bốn decorator tham số bạn cần nhớ:

DecoratorLấy vềDùng khi
@SubscribeMessage('x')Đăng ký handler cho sự kiện tên xClient gọi socket.emit('x', payload)
@MessageBody()Payload client gửi kèmĐọc dữ liệu nghiệp vụ (agentId, callId, message...)
@ConnectedSocket()Đối tượng socket của client gọiCần join room, lấy socket.id, đọc handshake
@WebSocketServer()Instance server (io)Broadcast tới mọi/nhiều client (mục ③)

Ba cách trả dữ liệu về client

Khi một handler chạy xong, có ba cách "đáp lại" — chọn đúng giúp code gọn và đúng ngữ nghĩa:

↩️ return (ack)

Giá trị return được gửi về chính client đã gọi, dạng callback acknowledgement. Hợp cho "đã nhận?".

📡 emit/broadcast

Chủ động đẩy sự kiện tới client khác (room, all). Hợp khi 1 hành động ảnh hưởng nhiều người (cuộc gọi mới vào hàng đợi).

🌊 Observable

Return một Observable → Nest stream nhiều message liên tiếp tới client. Hợp cho luồng dữ liệu liên tục.

chat.gateway.tsTypeScript
@WebSocketGateway({ namespace: '/chat' })
export class ChatGateway {
  @WebSocketServer() server: Server;

  @SubscribeMessage('chat:send')
  async onSend(
    @MessageBody() dto: { conversationId: string; text: string },
    @ConnectedSocket() client: Socket,
  ) {
    const msg = await this.chatService.save(dto, client.data.userId);

    // đẩy tin nhắn tới TẤT CẢ người trong phòng hội thoại (trừ người gửi)
    client.to(`conv:` + dto.conversationId).emit('chat:new', msg);

    // đồng thời trả ack cho chính người gửi: tin đã lưu thành công
    return { delivered: true, messageId: msg.id };
  }
}
🐛 Đừng nhét logic nghiệp vụ vào gateway

Gateway chỉ nên là tầng vận chuyển: nhận sự kiện, validate, gọi service, đẩy kết quả. Lưu DB, tính toán, gọi service ngoài phải nằm trong @Injectable() service (tái dùng được cho cả REST lẫn WS, dễ test). Gateway phình to là dấu hiệu vi phạm trách nhiệm đơn lẻ.

Validate payload bằng Pipe

Sự kiện WS đến từ client không đáng tin y như body HTTP. Bạn dùng lại ValidationPipe + DTO như ở REST. Lỗi validate sẽ được ném dưới dạng WsException (không phải HttpException) và gửi về client qua sự kiện exception.

validate-ws.tsTypeScript
@UsePipes(new ValidationPipe({ whitelist: true, transform: true }))
@SubscribeMessage('call:transfer')
onTransfer(@MessageBody() dto: TransferCallDto) {
  // dto đã được validate; sai schema → WsException tự động
  return this.callService.transfer(dto);
}

③ Server, broadcast & rooms cho hàng đợi cuộc gọi

Đây là phần "ăn tiền" với Contact Center. Room (phòng) là một nhãn logic gom nhiều socket lại để có thể đẩy một sự kiện tới cả nhóm chỉ bằng một lệnh. Một socket có thể ở nhiều room cùng lúc.

Phổ broadcast — gửi cho ai?

Cú phápGửi tớiVí dụ Contact Center
client.emit('e', d)Chỉ chính client đóBáo riêng agent "bạn vừa được gán call #123"
server.emit('e', d)Tất cả client trong namespaceThông báo bảo trì hệ thống cho toàn bộ agent
server.to(room).emit(...)Mọi client trong room (kể cả người gây ra)Cập nhật độ dài hàng đợi cho mọi supervisor
client.to(room).emit(...)Mọi client trong room trừ người gửiTin chat mới cho người khác trong hội thoại
server.to(socketId).emit(...)Một socket cụ thể (mỗi socket tự là 1 room)Định tuyến cuộc gọi tới đúng 1 agent

Mô hình room điển hình của tổng đài

Một thiết kế room sạch giúp việc định tuyến trở nên đơn giản. Quy ước đặt tên có tiền tố rõ ràng (queue:, agent:, conv:) để tránh đụng độ:

socket agent A→ room agent:A+ room queue:sales+ room tenant:42
📞 room hàng đợi

queue:sales — mọi agent của nhóm + supervisor. Cuộc gọi mới vào → broadcast độ dài hàng đợi.

👤 room cá nhân

agent:A — chứa mọi tab/thiết bị của agent A. Đẩy "call được gán cho bạn" tới đúng người, kể cả khi họ mở nhiều tab.

🏢 room tenant

tenant:42 — cách ly multi-tenant. Không bao giờ rò sự kiện sang khách hàng khác.

queue.gateway.ts (rooms)TypeScript
@WebSocketServer() server: Server;

@SubscribeMessage('agent:join')
joinQueue(
  @MessageBody() { agentId, queueId, tenantId }: JoinDto,
  @ConnectedSocket() client: Socket,
) {
  client.join(`agent:` + agentId);    // room cá nhân (nhiều tab cùng vào)
  client.join(`queue:` + queueId);    // room nhóm hàng đợi
  client.join(`tenant:` + tenantId);  // room cách ly tenant
}

// Một cuộc gọi mới rơi vào hàng đợi (gọi từ service, không phải client)
onCallEnqueued(call: Call) {
  this.server
    .to(`queue:` + call.queueId)
    .emit('queue:update', { waiting: call.position, callId: call.id });
}

// Gán đích danh một cuộc gọi cho một agent
assignCall(agentId: string, call: Call) {
  this.server.to(`agent:` + agentId).emit('call:assigned', call);
}
💡 Vì sao room cá nhân quan trọng hơn socketId

Một agent thường mở nhiều tab/thiết bị → nhiều socket. Nếu bạn lưu một socketId duy nhất cho mỗi agent, gửi tới đúng tab đang dùng là chuyện may rủi. Dùng room agent:A giải quyết gọn: mọi socket của A đều nhận được sự kiện, không cần bạn quản lý danh sách socket thủ công.

⚠️ Room sống trong RAM của từng instance

Danh sách room mặc định nằm trong bộ nhớ của chính process Node đó. Nếu chạy 2 node, server.to('queue:sales') ở node 1 sẽ không chạm tới socket đang nối vào node 2. Đây chính là lý do cần Redis adapter ở mục ⑤.

④ Gateway lifecycle hooks

Nest cung cấp ba interface vòng đời để bạn móc vào các thời điểm quan trọng của gateway. Implement chúng và Nest sẽ tự gọi đúng lúc:

InterfaceMethodGọi khiDùng để
OnGatewayInitafterInit(server)Server WS khởi tạo xongCấu hình middleware io, gắn adapter, log "gateway ready"
OnGatewayConnectionhandleConnection(client)Một client vừa kết nốiXác thực, gắn client.data, join room mặc định, tăng đếm online
OnGatewayDisconnecthandleDisconnect(client)Một client ngắt kết nốiĐặt agent về "offline/away", dọn presence, ghi log
presence.gateway.tsTypeScript
@WebSocketGateway({ namespace: '/presence' })
export class PresenceGateway
  implements OnGatewayInit, OnGatewayConnection, OnGatewayDisconnect {

  afterInit(server: Server) {
    // middleware io: chạy 1 lần cho MỖI kết nối trước khi vào handler
    server.use((socket, next) => {
      const token = socket.handshake.auth?.token;
      if (!token) return next(new Error('unauthorized'));
      next();
    });
  }

  async handleConnection(client: Socket) {
    const user = await this.auth.verify(client.handshake.auth.token);
    client.data.userId = user.id;                // lưu để các handler sau dùng
    client.join(`agent:` + user.id);
    this.presence.setOnline(user.id);
  }

  handleDisconnect(client: Socket) {
    if (client.data.userId) {
      this.presence.setOffline(client.data.userId);  // agent rớt mạng → away
    }
  }
}

Xác thực WebSocket bằng Guard

WS không có header mỗi request như HTTP — chỉ có handshake lúc kết nối. Có hai tầng để chặn người lạ:

  • Lúc connect: middleware io trong afterInit hoặc logic trong handleConnection — chặn ngay nếu token sai, kết nối không bao giờ "vào" được hệ thống.
  • Mỗi sự kiện: @UseGuards(WsAuthGuard) trên handler — kiểm tra quyền cho từng hành động (vd chỉ supervisor mới call:barge-in).
ws-auth.guard.tsTypeScript
@Injectable()
export class WsAuthGuard implements CanActivate {
  constructor(private jwt: JwtService) {}

  canActivate(ctx: ExecutionContext): boolean {
    // LƯU Ý: với WS phải lấy client qua switchToWs(), KHÔNG phải switchToHttp()
    const client: Socket = ctx.switchToWs().getClient();
    const token = client.handshake.auth?.token;
    try {
      client.data.user = this.jwt.verify(token);
      return true;
    } catch {
      throw new WsException('Token không hợp lệ');  // KHÔNG dùng UnauthorizedException của HTTP
    }
  }
}
🐛 Hai bẫy kinh điển khi auth WS trong Nest

① Trong Guard/Filter của WS phải dùng ctx.switchToWs() chứ không phải switchToHttp() — gọi nhầm sẽ trả về undefined.
② Lỗi phải ném bằng WsException, không phải HttpException; dùng HttpException trong gateway thì client WS không nhận được thông báo lỗi đúng cách. Nếu cần xử lý lỗi gọn, viết một WsExceptionFilter riêng.

⑤ Adapter & scaling nhiều instance

Mặc định Nest dùng IoAdapter bọc Socket.IO trên cùng HTTP server. Để tùy biến hành vi WS (CORS phức tạp, xác thực handshake, hay quan trọng nhất — scale ngang), bạn cung cấp adapter riêng qua app.useWebSocketAdapter(...) trong main.ts.

Vấn đề: một instance không đủ

Contact Center thật chạy nhiều node Node sau load balancer (PM2/K8s) để chịu tải và sống sót khi 1 node chết. Nhưng như đã nói ở mục ③, danh sách room nằm trong RAM của từng node:

Agent A → Node 1× server.to('queue:sales') ở Node 2→ Agent A KHÔNG nhận được

Hai socket trong cùng "room logic" nhưng nằm trên hai process khác nhau sẽ không thấy nhau. Sự kiện broadcast ở node này không tới socket ở node kia. Hệ quả: agent thấy hàng đợi nhấp nháy, mất tin nhắn, presence sai.

Giải pháp: Redis adapter (pub/sub backplane)

Redis adapter biến Redis thành "đường truyền chung" giữa các node. Khi node 1 broadcast tới một room, nó publish sự kiện lên Redis; mọi node khác subscribe và phát lại cho socket cục bộ của mình. Kết quả: room hoạt động như thể tất cả socket đang ở chung một process.

Node 1 emit→ Redis PUB/SUB→ Node 2 phát lại+ Node 3 phát lại
redis-io.adapter.tsTypeScript
import { IoAdapter } from '@nestjs/platform-socket.io';
import { createAdapter } from '@socket.io/redis-adapter';
import { createClient } from 'redis';

export class RedisIoAdapter extends IoAdapter {
  private adapterConstructor: ReturnType<typeof createAdapter>;

  async connectToRedis(url: string) {
    const pub = createClient({ url });
    const sub = pub.duplicate();         // 1 client publish, 1 client subscribe
    await Promise.all([pub.connect(), sub.connect()]);
    this.adapterConstructor = createAdapter(pub, sub);
  }

  createIOServer(port: number, options?: any) {
    const server = super.createIOServer(port, options);
    server.adapter(this.adapterConstructor);  // cắm Redis vào tầng broadcast
    return server;
  }
}

// main.ts
const redisAdapter = new RedisIoAdapter(app);
await redisAdapter.connectToRedis(process.env.REDIS_URL);
app.useWebSocketAdapter(redisAdapter);
⚠️ Sticky session vẫn cần với Socket.IO

Redis adapter giải quyết broadcast giữa node, nhưng quá trình handshake của Socket.IO (HTTP long-polling rồi nâng cấp lên WS) cần đi tới cùng một node. Vì thế load balancer phải bật sticky session (theo IP hoặc cookie). Thiếu sticky session → client liên tục bị "Session ID unknown". Nếu ép client dùng thuần WebSocket (bỏ long-polling) thì yêu cầu này nhẹ đi nhiều.

💡 Redis adapter làm gì và KHÔNG làm gì

Có: đồng bộ broadcast/room giữa các node. Không: lưu lịch sử tin nhắn, không đảm bảo delivery khi client offline, không thay thế DB. Nếu cần "gửi lại tin khi agent online lại", đó là việc của tầng lưu trữ + logic resync, không phải của adapter.

⑥ Nest Microservices

Khi hệ thống lớn lên, một số phần (gửi SMS/email, xử lý ghi âm, tính báo cáo) tách ra thành dịch vụ riêng. Nest Microservices cho phép các service Nest nói chuyện với nhau qua một transporter thay vì HTTP — với cùng phong cách decorator quen thuộc.

Hai mô hình giao tiếp

🔁 Request–Response

@MessagePattern('x') ở phía nhận, client.send('x', data) ở phía gọi. Trả về một Observable chứa kết quả. Dùng khi cần câu trả lời (vd "kiểm tra agent này còn slot không?").

📣 Event-based

@EventPattern('x') ở phía nhận, client.emit('x', data) ở phía gọi. Fire-and-forget, không chờ trả lời. Dùng khi chỉ cần báo "đã xảy ra việc gì đó" (vd "call.ended" → service báo cáo tự cập nhật).

@MessagePattern (send)@EventPattern (emit)
Ngữ nghĩaHỏi & chờ trả lờiThông báo, không chờ
Trả giá trịCó (Observable)Không
Ghép cặp (coupling)Chặt hơn — bên gọi phụ thuộc kết quảLỏng — nhiều consumer cùng nghe được
Hợp vớiTra cứu đồng bộ, orchestrationSự kiện domain, broadcast nội bộ, choreography
reporting.controller.ts (service nhận)TypeScript
@Controller()
export class ReportingController {
  // REQUEST-RESPONSE: caller chờ con số trả về
  @MessagePattern({ cmd: 'queue.length' })
  getQueueLength(@Payload() { queueId }: { queueId: string }) {
    return this.report.countWaiting(queueId);  // giá trị này gửi ngược về caller
  }

  // EVENT: chỉ ghi nhận, không trả gì
  @EventPattern('call.ended')
  async onCallEnded(@Payload() call: CallEndedEvent) {
    await this.report.recordCall(call);   // cập nhật AHT, talk-time...
  }
}
call.service.ts (bên gọi — ClientProxy)TypeScript
@Injectable()
export class CallService {
  constructor(@Inject('REPORT_SVC') private client: ClientProxy) {}

  getWaiting(queueId: string) {
    // send → Observable; await firstValueFrom(...) để lấy kết quả
    return this.client.send({ cmd: 'queue.length' }, { queueId });
  }

  endCall(call: Call) {
    // emit → fire-and-forget, không quan tâm ai xử lý
    this.client.emit('call.ended', call);
  }
}

Chọn transporter

Nest hỗ trợ nhiều transporter; lựa chọn phụ thuộc nhu cầu về độ bền message, throughput và topology:

RedisPub/sub nhẹ, đã có sẵn cho cache/adapterSự kiện nhẹ, latency thấp, không cần lưu trữ message lâu
NATSCực nhanh, hỗ trợ request-reply, JetStream cho persistenceMicroservices nhiều, cần tốc độ cao
RabbitMQHàng đợi bền, ack, routing key, dead-letterCần đảm bảo xử lý (job email/SMS, retry), tải đều worker
KafkaLog bền, throughput rất lớn, replay, nhiều consumer groupSự kiện khối lượng lớn, audit, phân tích, event sourcing
💡 Tư duy chọn theo bài toán Contact Center

• Gửi SMS/email/notification cần retry và không mất việc → RabbitMQ (queue bền, ack).
• Sự kiện cuộc gọi khối lượng lớn để analytics/báo cáo, cần replay → Kafka.
• Tra cứu đồng bộ nội bộ giữa vài service nhẹ → TCP/NATS.
Đừng dùng Kafka cho mọi thứ: nó mạnh nhưng nặng vận hành. Chọn công cụ vừa đủ.

Hybrid application — vừa REST/WS vừa microservice

Một ứng dụng Nest có thể đồng thời là HTTP server + WebSocket gateway + microservice listener. Đó gọi là hybrid app: bạn connectMicroservice() rồi startAllMicroservices() bên cạnh app.listen().

main.ts (hybrid)TypeScript
const app = await NestFactory.create(AppModule);   // HTTP + WS gateway

// đồng thời lắng nghe message qua RabbitMQ
app.connectMicroservice<MicroserviceOptions>({
  transport: Transport.RMQ,
  options: { urls: [process.env.RMQ_URL], queue: 'calls' },
});

await app.startAllMicroservices();   // bật listener microservice
await app.listen(3000);             // bật HTTP/WS

Monolith hay Microservices?

✅ Bắt đầu monolith (modular)

Đội nhỏ, domain chưa rõ, cần ra mắt nhanh. Giữ code module hóa tốt trong một deployable: dễ refactor, một lần deploy, debug đơn giản. Hầu hết tổng đài giai đoạn đầu nên ở đây.

⚠️ Tách microservices khi…

Có ranh giới scale/đội rõ ràng (recording xử lý nặng riêng, báo cáo tải lớn riêng), cần deploy độc lập, công nghệ khác nhau. Đổi lại: thêm hạ tầng (broker), khó debug phân tán, nhất quán dữ liệu phức tạp hơn.

⚠️ Microservices không miễn phí

Tách dịch vụ thêm độ phức tạp: tracing phân tán, message bền, retry/idempotency, eventual consistency. Đừng tách vì "nghe sang"; tách vì có lý do scale/tổ chức cụ thể. Một monolith module hóa tốt thường là điểm khởi đầu đúng đắn.

⚠️ Lỗi thường gặp & Best practices

🚫 Quên Redis adapter khi scale

Chạy nhiều node mà không có adapter → broadcast chỉ tới socket cùng node. Hàng đợi nhấp nháy, mất tin.

🚫 Thiếu sticky session

Socket.IO handshake bị nhảy node → "Session ID unknown", reconnect liên tục.

🚫 Logic nghiệp vụ trong gateway

Gateway phình to, không tái dùng cho REST, khó test. Đẩy vào service @Injectable.

🚫 Dùng HttpException trong WS

Phải ném WsException và dùng switchToWs() trong guard/filter.

🚫 CORS * trên production

Cho phép mọi origin kết nối WS là lỗ hổng. Whitelist domain frontend.

🚫 Không cleanup khi disconnect

Quên đặt agent offline / dọn presence → bảng trạng thái sai, "ma" online.

🚫 Event không idempotent

Microservice xử lý lại message khi retry → ghi trùng. Cần idempotency key.

✅ Quy ước đặt tên rõ

Tiền tố room (queue:, agent:, tenant:) và sự kiện (call:, chat:) tránh đụng độ.

🧪 Bài tập

🧪 Bài 1 — Gateway hàng đợi cuộc gọi

Thiết kế một QueueGateway: agent gửi agent:join để vào room hàng đợi của nhóm, supervisor gửi supervisor:watch để theo dõi. Khi có sự kiện call.enqueued (do service gọi tới), broadcast độ dài hàng đợi mới cho cả nhóm và supervisor. Liệt kê các room và sự kiện bạn dùng.

Gợi ý

Room: queue:<id> cho agent, sup:<queueId> cho supervisor (hoặc cho supervisor join luôn queue:<id>). Khi enqueued: server.to('queue:'+id).emit('queue:update', {...}). Agent join trong handler agent:join bằng client.join(...). Nhớ lấy tenantId để cách ly và validate payload bằng DTO + ValidationPipe.

🧪 Bài 2 — Scale lên 3 node

Hệ thống đang chạy 1 node, sắp lên 3 node sau load balancer. Liệt kê những thứ phải thay đổi để realtime vẫn đúng. Vì sao chỉ thêm node thôi là chưa đủ?

Gợi ý

(1) Thêm Redis adapter để broadcast/room đồng bộ giữa node — vì room mặc định nằm trong RAM từng process. (2) Bật sticky session ở load balancer cho handshake Socket.IO. (3) Đưa presence/state ra store chung (Redis), không giữ trong RAM một node. (4) Cân nhắc ép transport WebSocket để giảm phụ thuộc sticky.

🧪 Bài 3 — Chọn cơ chế giao tiếp microservice

Cho 3 tình huống: (a) gửi email xác nhận ticket có thể retry, (b) báo "cuộc gọi đã kết thúc" cho nhiều consumer (báo cáo, billing, audit), (c) hỏi "agent này còn slot trống không?" trước khi định tuyến. Mỗi tình huống dùng @MessagePattern hay @EventPattern, transporter nào, vì sao?

Gợi ý

(a) @EventPattern qua RabbitMQ — queue bền + ack + retry, không cần trả lời. (b) @EventPattern qua Kafka — một sự kiện, nhiều consumer group cùng đọc, replay được. (c) @MessagePattern request-response qua TCP/NATS — cần câu trả lời đồng bộ tức thì, độ trễ thấp.

Ngân hàng câu hỏi phỏng vấn

WebSocket Gateway & Microservices trong Nest — nhóm câu phân loại chiều sâu realtime.

Q1Gateway khác Controller ở điểm nào?Junior›

Trả lời: Cả hai là tầng vào của ứng dụng và đều dùng DI, guard, pipe, interceptor. Khác biệt: Controller xử lý HTTP request-response (kết nối đóng sau mỗi lần, ánh xạ route bằng @Get/@Post); Gateway xử lý WebSocket — kết nối giữ mở hai chiều, ánh xạ theo tên sự kiện bằng @SubscribeMessage, và có thể chủ động push dữ liệu cho client bất cứ lúc nào qua emit.

Q2Kể các decorator chính của một WebSocket Gateway.Junior›

Trả lời: @WebSocketGateway() đánh dấu lớp (cấu hình namespace/cors/path), @SubscribeMessage('event') đăng ký handler cho một sự kiện, @MessageBody() lấy payload, @ConnectedSocket() lấy socket client đang gọi, @WebSocketServer() tiêm instance server để broadcast. Gateway phải được đăng ký trong providers của một Module.

Q3Phân biệt emit, broadcast và room. Cho ví dụ Contact Center.Middle›

Trả lời: client.emit gửi chỉ cho chính client đó. server.emit gửi cho toàn bộ client trong namespace. server.to(room).emit gửi cho mọi client trong room (gồm cả người gây ra), còn client.to(room).emit gửi cho room trừ người gửi. Room là nhãn logic gom socket. Ví dụ: cuộc gọi mới vào hàng đợi → server.to('queue:sales').emit('queue:update') cho cả nhóm; gán call cho một agent → server.to('agent:A').emit('call:assigned') (room cá nhân để trúng mọi tab của agent A).

Q4Làm sao scale WebSocket gateway ra nhiều node?Senior›

Trả lời: Cần một backplane để đồng bộ broadcast giữa các process — phổ biến nhất là Redis adapter cho Socket.IO: mỗi broadcast được publish lên Redis pub/sub, các node khác subscribe và phát lại cho socket cục bộ. Kèm theo: bật sticky session ở load balancer cho handshake Socket.IO, đưa state/presence ra store chung (Redis) thay vì RAM một node, và theo dõi số kết nối.

⚠️ Bẫy: nói "chỉ cần thêm node sau load balancer" là sai — room mặc định nằm trong RAM từng process nên broadcast sẽ không xuyên node nếu thiếu adapter.

Q5Vì sao cần Redis adapter, nó làm và KHÔNG làm gì?Senior›

Trả lời: Cần vì danh sách room/socket sống trong bộ nhớ từng node; muốn broadcast tới một room khi socket nằm rải trên nhiều node thì phải có kênh chung. Redis adapter dùng pub/sub: node phát → Redis → các node khác phát lại. Nó không lưu lịch sử message, không đảm bảo delivery khi client offline, không thay DB. Việc "gửi lại khi online lại" là của tầng lưu trữ + logic resync, không phải adapter.

Q6Xác thực một kết nối WebSocket như thế nào?Middle›

Trả lời: WS không có header mỗi request, chỉ có handshake lúc connect. Hai tầng: (1) Lúc connect — đọc token từ handshake.auth trong middleware io (server.use) hoặc handleConnection, verify, gắn user vào client.data, từ chối nếu sai. (2) Mỗi sự kiện — @UseGuards(WsAuthGuard) để kiểm tra quyền cho từng hành động. Trong guard nhớ dùng ctx.switchToWs().getClient() và ném WsException khi lỗi.

⚠️ Bẫy: dùng switchToHttp() hoặc ném HttpException trong ngữ cảnh WS là sai.

Q7Các lifecycle hooks của gateway và dùng để làm gì?Middle›

Trả lời: OnGatewayInit.afterInit(server) chạy khi server WS sẵn sàng — gắn middleware io, cấu hình. OnGatewayConnection.handleConnection(client) khi client kết nối — xác thực, join room mặc định, tăng đếm online, gắn client.data. OnGatewayDisconnect.handleDisconnect(client) khi ngắt — đặt agent offline, dọn presence, log. Với Contact Center, connect/disconnect là nơi cập nhật presence của agent.

Q8Request-response và event-based khác nhau ra sao trong Nest Microservices?Middle›

Trả lời: Request-response dùng @MessagePattern ở phía nhận và client.send ở phía gọi — trả về Observable chứa kết quả, bên gọi chờ câu trả lời (coupling chặt hơn). Event-based dùng @EventPattern + client.emit — fire-and-forget, không trả lời, nhiều consumer cùng nghe được (coupling lỏng). Dùng send khi cần tra cứu đồng bộ; dùng emit khi chỉ báo "việc gì đó đã xảy ra".

Q9Chọn transporter cho microservice dựa trên gì?Senior›

Trả lời: Dựa trên độ bền message, throughput, mô hình consumer và độ phức tạp vận hành. TCP: đơn giản, point-to-point, không broker — hợp dev/vài service. Redis: pub/sub nhẹ, latency thấp, không bền. NATS: rất nhanh, có request-reply, JetStream cho persistence. RabbitMQ: queue bền + ack + retry + dead-letter — hợp job cần đảm bảo (email/SMS). Kafka: log bền, throughput lớn, replay, nhiều consumer group — hợp event khối lượng lớn/analytics. Nguyên tắc: chọn công cụ vừa đủ, đừng dùng Kafka cho mọi thứ.

Q10Hybrid application là gì?Middle›

Trả lời: Là một ứng dụng Nest vừa là HTTP server (và WebSocket gateway) vừa lắng nghe message qua transporter microservice cùng lúc. Tạo bằng NestFactory.create, rồi app.connectMicroservice(...), gọi startAllMicroservices() cùng với app.listen(). Hữu ích khi một service vừa phục vụ client (REST/WS) vừa tiêu thụ sự kiện nội bộ (vd nhận call.ended từ broker để đẩy cập nhật realtime cho supervisor).

Q11Khi nào nên monolith, khi nào tách microservices?Senior›

Trả lời: Bắt đầu bằng monolith module hóa tốt khi đội nhỏ, domain chưa ổn định, cần ra mắt nhanh — dễ refactor, một lần deploy, debug đơn giản. Tách microservices khi có ranh giới scale/đội rõ ràng (xử lý ghi âm nặng riêng, báo cáo tải lớn riêng), cần deploy độc lập hoặc khác công nghệ. Đổi lại phải chấp nhận tracing phân tán, message bền, retry/idempotency, eventual consistency. Tách vì lý do scale/tổ chức cụ thể, không vì xu hướng.

⚠️ Bẫy: "microservices luôn tốt hơn monolith" — sai; phần lớn dự án giai đoạn đầu hợp với monolith module hóa.

Q12Vì sao cần idempotency với event-based microservice?Senior›

Trả lời: Broker (RabbitMQ/Kafka) thường đảm bảo at-least-once — một message có thể được giao lại khi consumer crash trước ack hoặc khi rebalance. Nếu handler không idempotent, xử lý lại call.ended sẽ ghi trùng bản ghi, tính sai báo cáo, gửi email hai lần. Giải pháp: dùng idempotency key (vd callId + eventType), kiểm tra "đã xử lý chưa" trước khi ghi, hoặc thiết kế thao tác upsert/đặt trạng thái thay vì cộng dồn.
