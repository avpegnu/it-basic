Modules, Controllers & Providers

Đào sâu ba khối nền tảng của Nest và cách container DI phân giải phụ thuộc, scope và provider tùy biến.

🎯 Học xong chương này bạn sẽ

• Hiểu Module là đơn vị đóng gói (encapsulation): vai trò của imports / exports / providers / controllers và tại sao mặc định một provider không rò rỉ ra ngoài module.

• Viết Controller chuẩn REST: @Get/@Post/@Put/@Delete, trích tham số với @Param/@Query/@Body, đặt status code đúng.

• Đặt toàn bộ business logic vào Service (provider) mỏng – testable – tái dùng, để controller chỉ là lớp vận chuyển HTTP.

• Phân biệt ba injection scope (DEFAULT singleton, REQUEST, TRANSIENT) và đánh đổi hiệu năng của chúng.

• Tạo custom provider bằng useClass / useValue / useFactory / useExisting + injection token cho cấu hình động.

• Dựng dynamic module kiểu forRoot / forFeature và phá vòng phụ thuộc bằng forwardRef.

💡 Liên hệ hệ thống Contact Center

Một nền tảng Contact Center thường được cắt thành các module nghiệp vụ rõ ràng: AgentsModule (trạng thái tổng đài viên), CallsModule (vòng đời cuộc gọi), ChatModule, QueueModule (hàng đợi & định tuyến), TicketsModule (phiếu hỗ trợ). Mỗi module đóng gói service riêng và chỉ exports đúng những gì module khác cần. Hiểu cơ chế Module + Provider giúp bạn thiết kế ranh giới rõ ràng, tránh "module thần thánh" ôm hết mọi thứ và tránh phụ thuộc vòng giữa Calls ↔ Queue.

① Modules sâu — đơn vị đóng gói của Nest

Trong Nest, mọi thứ bắt đầu từ một module. Module không chỉ là "thư mục gom code" — nó là một biên đóng gói (encapsulation boundary) mà container DI tôn trọng nghiêm ngặt. Một module được khai báo bằng decorator @Module() với bốn thuộc tính cốt lõi:

Thuộc tínhÝ nghĩaVí dụ Contact Center
controllersCác controller được khởi tạo trong module này (lớp nhận HTTP request)CallsController
providersCác provider Nest sẽ khởi tạo & quản lý vòng đời, dùng nội bộ moduleCallsService, CallRepository
importsModule khác mà module này cần — để dùng những provider mà module đó exportsimports: [QueueModule]
exportsProvider được "công khai" cho module nào import nóexports: [CallsService]

Đóng gói (Encapsulation) — quy tắc vàng

Đây là điểm hay bị hiểu sai nhất. Một provider khai báo trong providers của module A chỉ nhìn thấy được bên trong A. Để module B dùng được provider đó, bạn phải:

  1. Module A đưa provider vào exports.
  2. Module B đưa A vào imports.

Thiếu một trong hai bước, Nest sẽ ném lỗi quen thuộc khi khởi động: Nest can't resolve dependencies of ... Please make sure that the argument X is available in the Y context. Đây không phải bug — đó là encapsulation đang làm đúng việc của nó: ngăn module này thò tay vào nội bộ module kia.

calls.module.tsNestJS
import { Module } from '@nestjs/common';
import { CallsController } from './calls.controller';
import { CallsService } from './calls.service';
import { QueueModule } from '../queue/queue.module';

@Module({
  // QueueModule phải EXPORT QueueService thì dòng này mới có tác dụng
  imports: [QueueModule],
  controllers: [CallsController],
  providers: [CallsService],
  // Cho CallsService "thoát" ra ngoài để TicketsModule/Gateway dùng lại
  exports: [CallsService],
})
export class CallsModule {}
⚠️ exports KHÔNG sao chép provider

Khi A export CallsService và B import A, B dùng cùng một instance singleton mà A đã tạo (với scope mặc định). Không có chuyện "mỗi module một bản". exports chỉ mở quyền nhìn thấy, không nhân bản đối tượng.

Shared module vs Global module

Có hai cách chia sẻ provider cho nhiều module:

📦 Shared module

Module bình thường có exports. Module nào cần thì phải imports tường minh. Rõ ràng, dễ truy vết phụ thuộc — nên ưu tiên.

🌍 Global module

Đánh dấu @Global(): chỉ cần import một lần (thường ở module gốc), sau đó mọi nơi dùng được mà không cần import lại.

logger.module.tsNestJS
@Global()           // dùng tiết kiệm — chỉ cho thứ thật sự dùng khắp nơi
@Module({
  providers: [CallLoggerService],
  exports: [CallLoggerService],
})
export class LoggerModule {}

// Sau khi import LoggerModule ở AppModule, mọi service trong app
// đều inject được CallLoggerService mà KHÔNG cần import LoggerModule lại.
🐛 Đừng lạm dụng @Global()

Global module phá vỡ tính tường minh: nhìn vào imports của một module bạn không còn biết nó thực sự phụ thuộc gì. Chỉ dùng cho hạ tầng dùng khắp nơi (logger, config, DB connection). Module nghiệp vụ (Calls, Tickets) thì không bao giờ nên global.

Module gốc và cây phụ thuộc

Ứng dụng có một module gốc (thường là AppModule) — điểm Nest dùng để dựng cây phụ thuộc. Từ gốc, Nest duyệt imports đệ quy, khởi tạo provider theo thứ tự đúng, rồi mới chạy server.

AppModule→ CallsModule→ QueueModule→ DatabaseModule

② Controllers & routing

Controller là lớp vận chuyển HTTP: nhận request, lấy dữ liệu cần thiết, gọi service, trả response. Quy tắc thiết kế: controller phải mỏng — không chứa business logic, không truy vấn DB trực tiếp. Mọi thứ "thông minh" nằm ở service.

Decorator định tuyến & trích tham số

DecoratorVai trò
@Controller('calls')Đặt prefix route cho cả class → mọi route bắt đầu bằng /calls
@Get() @Post() @Put() @Patch() @Delete()Ánh xạ HTTP method + subpath tới method của class
@Param('id')Lấy tham số đường dẫn, vd /calls/:id
@Query('status')Lấy query string, vd ?status=active
@Body()Lấy toàn bộ (hoặc một trường) request body
@HttpCode(204)Ép status code trả về (mặc định GET=200, POST=201)
@Headers() @Ip() @Req() @Res()Truy cập header, IP, hay object request/response thô (hạn chế dùng @Res)
calls.controller.tsNestJS
import {
  Controller, Get, Post, Patch, Delete,
  Param, Query, Body, HttpCode, ParseIntPipe,
} from '@nestjs/common';

@Controller('calls')        // prefix: /calls
export class CallsController {
  // Service được TIÊM qua constructor — controller không tự "new" nó
  constructor(private readonly calls: CallsService) {}

  @Get()                       // GET /calls?status=active&page=1
  findAll(
    @Query('status') status?: string,
    @Query('page') page = 1,
  ) {
    return this.calls.findAll({ status, page });
  }

  @Get(':id')                  // GET /calls/42
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.calls.findOne(id);
  }

  @Post()                      // POST /calls  → mặc định 201 Created
  create(@Body() dto: CreateCallDto) {
    return this.calls.create(dto);
  }

  @Patch(':id/transfer')      // PATCH /calls/42/transfer
  transfer(
    @Param('id', ParseIntPipe) id: number,
    @Body('toAgentId') toAgentId: number,
  ) {
    return this.calls.transfer(id, toAgentId);
  }

  @Delete(':id')
  @HttpCode(204)               // 204 No Content khi xoá thành công
  remove(@Param('id', ParseIntPipe) id: number) {
    return this.calls.remove(id);
  }
}
💡 Để Nest tự lo response

Nếu method trả về một giá trị (object/Promise/Observable), Nest tự serialize sang JSON và đặt status mặc định. Hãy tránh @Res() + res.json() thủ công vì nó vô hiệu hóa interceptor, serialization và exception filter của Nest. Chỉ dùng @Res({ passthrough: true }) khi thật sự cần (vd set cookie) mà vẫn để Nest xử lý response.

Mã trạng thái & wildcard, sub-route

  • Mặc định: @Get=200, @Post=201. Đổi bằng @HttpCode(n).
  • Đặt header với @Header('Cache-Control','no-store').
  • Route con: @Get('active/count') → /calls/active/count.
  • Thứ tự khai báo quan trọng: route tĩnh @Get('summary') nên đặt trước route động @Get(':id'), nếu không summary sẽ rơi vào :id.

③ Providers & Services

Provider là bất cứ thứ gì container DI có thể khởi tạo và tiêm: service, repository, factory, helper, hằng số cấu hình... Service là loại provider phổ biến nhất — nơi chứa business logic. Một class trở thành provider khi gắn @Injectable() và được liệt kê trong providers của một module.

calls.service.tsNestJS
import { Injectable, NotFoundException } from '@nestjs/common';

@Injectable()                 // đánh dấu: class này do container quản lý
export class CallsService {
  // Các phụ thuộc khác cũng được tiêm vào đây
  constructor(
    private readonly repo: CallRepository,
    private readonly queue: QueueService,   // đến từ QueueModule (đã export)
  ) {}

  async create(dto: CreateCallDto) {
    const call = await this.repo.insert({ ...dto, status: 'ringing' });
    // Business logic: đẩy cuộc gọi vào hàng đợi định tuyến
    await this.queue.enqueue(call.id, dto.skill);
    return call;
  }

  async findOne(id: number) {
    const call = await this.repo.findById(id);
    if (!call) throw new NotFoundException(`Call ${id} không tồn tại`);
    return call;
  }
}
💡 Vì sao tách controller ↔ service?

Tách lớp cho phép test logic độc lập với HTTP (unit test service không cần khởi động server), tái dùng logic ở nhiều entrypoint (REST controller, WebSocket gateway, message consumer), và giữ controller dễ đọc. Ví dụ: cùng CallsService.transfer() có thể được gọi từ REST endpoint lẫn từ một sự kiện realtime trên WebSocket.

Token phân giải mặc định

Khi bạn viết constructor(private repo: CallRepository), Nest dùng chính class CallRepository làm token để tra trong container. Đây là lý do tham số constructor cần kiểu cụ thể (không phải interface — interface biến mất khi compile TS). Muốn tiêm theo interface, bạn phải dùng injection token tường minh (xem mục ⑤).

④ Injection scopes

Scope quyết định vòng đời và số lượng instance của một provider. Nest có ba scope:

ScopeSố instanceVòng đờiHiệu năng
DEFAULT (singleton)Đúng 1 cho cả appTạo lúc khởi động, sống suốt đời appTốt nhất — không có chi phí tạo lại
REQUEST1 instance mỗi requestTạo khi request đến, hủy khi response xongTốn — tạo lại cây phụ thuộc mỗi request
TRANSIENT1 instance mỗi nơi injectMỗi consumer nhận một bản riêngTốn bộ nhớ nếu inject nhiều nơi
scopes.tsNestJS
import { Injectable, Scope } from '@nestjs/common';

@Injectable()                                 // = Scope.DEFAULT (singleton)
export class CallsService {}

@Injectable({ scope: Scope.REQUEST })   // mỗi request một bản
export class RequestContextService {
  // Hữu ích để giữ traceId / agentId của ĐÚNG request hiện tại
  traceId: string;
}

@Injectable({ scope: Scope.TRANSIENT }) // mỗi consumer một bản
export class ScopedLogger {}
🐛 "Scope bubbling" — bẫy hiệu năng nguy hiểm

Nếu một singleton inject một provider REQUEST-scoped, thì cả singleton đó cũng bị nâng lên REQUEST scope — và lan ngược lên cả chuỗi phụ thuộc, kể cả controller. Hệ quả: Nest phải tạo lại cây đó mỗi request, giết chết lợi ích singleton. Với Contact Center tải cao (hàng nghìn cuộc gọi đồng thời), điều này có thể tăng GC pressure và latency đáng kể. Hãy giữ provider ở DEFAULT bất cứ khi nào có thể; cần dữ liệu theo request thì cân nhắc dùng AsyncLocalStorage thay cho REQUEST scope.

⚠️ Khi nào dùng REQUEST scope?

Chỉ khi provider thật sự cần state riêng theo từng request mà không thể truyền qua tham số — ví dụ multi-tenancy (mỗi request một tenant DB), hoặc cần inject REQUEST object để đọc user hiện tại sâu trong cây service. Ngay cả vậy, AsyncLocalStorage thường rẻ hơn.

⑤ Custom providers

Cú pháp ngắn providers: [CallsService] chỉ là đường tắt cho dạng đầy đủ { provide: CallsService, useClass: CallsService }. Khi cần linh hoạt hơn — tiêm hằng số, chọn implementation theo môi trường, khởi tạo bất đồng bộ — bạn dùng custom provider với một trong bốn dạng:

DạngCung cấp gìDùng khi
useClassMột class để Nest newĐổi implementation theo điều kiện (vd mock vs real)
useValueMột giá trị có sẵn (object, hằng, mock)Cấu hình, hằng số, tiêm mock trong test
useFactoryKết quả của một hàm (có thể async, có thể inject)Khởi tạo cần logic/phụ thuộc/đọc env
useExistingBí danh (alias) tới provider đã cóTạo token thứ hai trỏ về cùng instance

Injection token — phân giải theo interface

TypeScript interface không tồn tại lúc runtime, nên không thể làm token. Giải pháp: dùng một string/symbol token và inject bằng @Inject('TOKEN'). Đây là chìa khóa để lập trình theo abstraction (Dependency Inversion).

storage.module.tsNestJS
// Tách abstraction để dễ thay implementation (S3, local, mock)
export interface RecordingStorage {
  save(callId: number, data: Buffer): Promise<string>;
}
export const RECORDING_STORAGE = 'RECORDING_STORAGE'; // injection token

@Module({
  providers: [
    // 1) useClass: chọn implementation theo môi trường
    {
      provide: RECORDING_STORAGE,
      useClass: process.env.NODE_ENV === 'production'
        ? S3RecordingStorage
        : LocalRecordingStorage,
    },
    // 2) useValue: tiêm cấu hình thuần
    {
      provide: 'CALL_CONFIG',
      useValue: { maxRingSeconds: 30, recordByDefault: true },
    },
    // 3) useFactory: khởi tạo cần logic + phụ thuộc khác (async OK)
    {
      provide: 'REDIS_CLIENT',
      useFactory: async (cfg: ConfigService) => {
        const client = createRedis({ url: cfg.get('REDIS_URL') });
        await client.connect();
        return client;
      },
      inject: [ConfigService],   // phụ thuộc của factory, truyền theo thứ tự
    },
    // 4) useExisting: bí danh — cùng MỘT instance, hai token
    { provide: 'LEGACY_STORAGE', useExisting: RECORDING_STORAGE },
  ],
  exports: [RECORDING_STORAGE, 'CALL_CONFIG', 'REDIS_CLIENT'],
})
export class StorageModule {}
recordings.service.tsNestJS
@Injectable()
export class RecordingsService {
  constructor(
    // Inject theo TOKEN, kiểu là INTERFACE → code phụ thuộc abstraction
    @Inject(RECORDING_STORAGE) private storage: RecordingStorage,
    @Inject('CALL_CONFIG')    private cfg: { maxRingSeconds: number },
  ) {}
}
💡 useFactory là vũ khí mạnh nhất

useFactory cho phép khởi tạo bất đồng bộ (chờ kết nối DB/Redis sẵn sàng trước khi app phục vụ) và inject phụ thuộc qua mảng inject. Đây cũng là cơ chế đứng sau forRootAsync của hầu hết thư viện Nest. Trong test, bạn override provider bằng useValue để tiêm mock — không cần đụng tới class thật.

⑥ Dynamic modules

Module tĩnh luôn cấu hình giống nhau. Nhưng nhiều module hạ tầng cần tham số khác nhau tùy nơi dùng — ví dụ DatabaseModule cần connection string, QueueModule cần tên hàng đợi. Giải pháp là dynamic module: module phơi ra một static method trả về một DynamicModule được cấu hình theo tham số truyền vào.

Quy ước forRoot / forFeature

🌱 forRoot()

Cấu hình toàn cục, một lần tại module gốc — kết nối DB, thiết lập client Redis. Thường trả về module global.

🔧 forFeature()

Đăng ký tài nguyên cục bộ cho từng module nghiệp vụ — vd repository cho entity Call, Ticket.

queue.module.tsNestJS
import { Module, DynamicModule } from '@nestjs/common';

export interface QueueOptions { url: string; prefix: string; }

@Module({})              // rỗng — mọi thứ do static method dựng động
export class QueueModule {
  static forRoot(opts: QueueOptions): DynamicModule {
    return {
      module: QueueModule,
      global: true,                          // dùng được khắp app
      providers: [
        { provide: 'QUEUE_OPTIONS', useValue: opts },
        QueueService,
      ],
      exports: [QueueService],
    };
  }

  // forFeature: đăng ký một hàng đợi nghiệp vụ cụ thể
  static forFeature(name: string): DynamicModule {
    const provider = {
      provide: `QUEUE_${name}`,
      useFactory: (svc: QueueService) => svc.channel(name),
      inject: [QueueService],
    };
    return { module: QueueModule, providers: [provider], exports: [provider] };
  }
}
app.module.tsNestJS
@Module({
  imports: [
    QueueModule.forRoot({ url: process.env.QUEUE_URL!, prefix: 'cc' }),
    CallsModule,   // bên trong dùng QueueModule.forFeature('voice')
    ChatModule,    // bên trong dùng QueueModule.forFeature('chat')
  ],
})
export class AppModule {}
💡 forRootAsync — cấu hình từ ConfigService

Khi tham số phải lấy từ biến môi trường/secret, dùng biến thể forRootAsync với useFactory + inject: [ConfigService]. Đây chính là pattern bạn thấy ở TypeOrmModule.forRootAsync, JwtModule.registerAsync... (xem chi tiết ở E4 và E5).

Circular dependency & forwardRef

Đôi khi hai service/module phụ thuộc lẫn nhau: CallsService cần QueueService để đẩy cuộc gọi, còn QueueService lại cần CallsService để cập nhật trạng thái khi định tuyến xong. Nest khởi tạo theo thứ tự nên gặp vòng phụ thuộc sẽ không biết tạo cái nào trước → lỗi undefined hoặc "circular dependency". Công cụ thoát hiểm là forwardRef(): bảo Nest "tham chiếu cái này muộn", phá vỡ vòng tại thời điểm phân giải.

forward-ref.tsNestJS
// --- ở MODULE: hai module import lẫn nhau ---
@Module({
  imports: [forwardRef(() => QueueModule)],
  providers: [CallsService],
  exports: [CallsService],
})
export class CallsModule {}

// --- ở PROVIDER: hai service inject lẫn nhau ---
@Injectable()
export class CallsService {
  constructor(
    @Inject(forwardRef(() => QueueService))
    private queue: QueueService,
  ) {}
}
🐛 forwardRef là "băng dán", không phải kiến trúc tốt

Vòng phụ thuộc thường là dấu hiệu thiết kế chưa chuẩn: hai class biết quá nhiều về nhau. Trước khi reach for forwardRef, hãy cân nhắc: (1) tách phần dùng chung ra một service/module thứ ba, (2) đảo chiều phụ thuộc qua event (CallsService phát sự kiện, QueueService lắng nghe — xem Phần F), (3) dùng ModuleRef để lấy phụ thuộc lười (lazy) khi cần. forwardRef chỉ nên là lựa chọn cuối.

⚠️ Lỗi thường gặp & Best practices

🚫 Quên export provider

Provider dùng được nội bộ nhưng module khác import lại lỗi "can't resolve". Phải đưa vào exports.

🚫 Logic trong controller

Controller phình to, khó test. Đẩy hết business logic xuống service; controller chỉ điều phối HTTP.

🚫 Lạm dụng @Global()

Mất tính tường minh của phụ thuộc. Chỉ global hóa hạ tầng dùng khắp nơi (logger/config).

🚫 Scope bubbling vô tình

Singleton inject REQUEST-scoped → cả cây bị nâng scope, hỏng hiệu năng. Giữ DEFAULT khi có thể.

🚫 Inject interface thiếu token

Interface không tồn tại runtime → phải dùng injection token + @Inject('TOKEN').

🚫 Route động che route tĩnh

Khai báo @Get(':id') trước @Get('summary') làm summary không bao giờ chạy. Đặt route tĩnh trước.

🚫 Lệ thuộc forwardRef

Coi nó là kiến trúc thay vì sửa thiết kế. Ưu tiên tách module / dùng event.

✅ Một module một nghiệp vụ

Mỗi domain (Calls, Tickets, Queue) một module với ranh giới rõ; export tối thiểu cần thiết.

🧪 Bài tập

🧪 Bài 1 — Thiết kế biên module

Bạn có ba module: CallsModule, TicketsModule, QueueModule. Cả Calls lẫn Tickets đều cần đẩy việc vào hàng đợi qua QueueService. Hãy ghi rõ mỗi module cần providers, exports, imports gì để vừa đúng vừa không rò rỉ provider thừa.

Gợi ý

QueueModule: providers: [QueueService], exports: [QueueService]. CallsModule: imports: [QueueModule], providers: [CallsService], exports: [CallsService] (nếu nơi khác cần). TicketsModule: imports: [QueueModule], providers: [TicketsService]. QueueService là singleton dùng chung — cả Calls và Tickets nhận cùng instance. KHÔNG đặt QueueService vào providers của Calls/Tickets (sẽ tạo instance riêng, sai).

🧪 Bài 2 — Custom provider theo môi trường

Viết một custom provider cho token RECORDING_STORAGE: dùng S3RecordingStorage ở production, LocalRecordingStorage ở dev, và một mock useValue khi chạy test. Giải thích vì sao cách này giúp test dễ hơn.

Gợi ý

Dùng { provide: RECORDING_STORAGE, useClass: env==='production' ? S3... : Local... }. Trong test, override module bằng .overrideProvider(RECORDING_STORAGE).useValue(mockStorage). Vì service phụ thuộc token + interface chứ không phải class cụ thể, ta thay implementation mà không sửa một dòng nào trong RecordingsService — đó là Dependency Inversion thực chiến.

🧪 Bài 3 — Phá vòng phụ thuộc

CallsService gọi QueueService.enqueue(), và khi định tuyến xong QueueService muốn gọi CallsService.markRouted(). Hãy nêu hai cách xử lý: một dùng forwardRef, một dùng event — và lập luận cách nào tốt hơn.

Gợi ý

Cách 1: @Inject(forwardRef(() => CallsService)) ở QueueService + forwardRef ở imports hai module. Hoạt động nhưng giữ coupling chặt. Cách 2: QueueService phát event call.routed qua EventEmitter2; CallsService lắng nghe và tự markRouted. Cách 2 tốt hơn: xóa hẳn vòng phụ thuộc, hai service không cần biết nhau, dễ mở rộng thêm subscriber (vd ghi log, gửi notification).

✅ Quiz kiểm tra nhanh

Q1. Để module B dùng được CallsService của module A, cần làm gì?
Chỉ cần đặt CallsService vào providers của B
A exports CallsService và B imports A
Đánh dấu CallsService bằng @Global()
Export + import. Encapsulation chặn provider rò rỉ; phải mở cả hai phía. Đặt service vào providers của B sẽ tạo instance riêng (sai).
Q2. Scope mặc định của một provider Nest là?
DEFAULT (singleton — một instance cho cả app)
REQUEST (một instance mỗi request)
TRANSIENT (một instance mỗi nơi inject)
Singleton. Hiệu năng tốt nhất, tạo một lần lúc khởi động. REQUEST/TRANSIENT chỉ dùng khi thật cần.
Q3. Dạng custom provider nào cho phép khởi tạo bất đồng bộ và inject phụ thuộc khác?
useValue
useClass
useFactory (kèm mảng inject)
useFactory. Trả về kết quả của một hàm có thể async; inject truyền phụ thuộc theo thứ tự tham số.
Q4. Điều gì xảy ra khi một singleton inject một provider REQUEST-scoped?
Nest báo lỗi và từ chối khởi động
Singleton bị nâng lên REQUEST scope, tạo lại mỗi request
Provider REQUEST tự động hạ xuống singleton
Scope bubbling. Scope "đắt" hơn lan ngược lên toàn chuỗi phụ thuộc, làm mất lợi ích singleton và hại hiệu năng.
Q5. Vì sao không inject trực tiếp một interface làm kiểu cho phụ thuộc?
Vì Nest cấm dùng interface
Interface biến mất khi compile TS → không có token runtime; phải dùng injection token + @Inject
Vì interface luôn tạo TRANSIENT scope
Không có token runtime. TS interface chỉ tồn tại lúc compile. Dùng string/symbol token để phân giải theo abstraction.

Ngân hàng câu hỏi phỏng vấn

Modules, Providers & DI nâng cao — phần lõi hay được đào sâu khi phỏng vấn NestJS.

Q1Bốn thuộc tính của @Module() là gì và mỗi cái làm gì?Junior›

Trả lời: controllers liệt kê các controller của module; providers liệt kê service/provider mà module khởi tạo và dùng nội bộ; imports kéo vào các module khác để dùng những provider mà module đó exports; exports công khai một số provider cho module nào import module này. Bốn thuộc tính này định nghĩa cả nội dung lẫn biên đóng gói của module.

Q2exports dùng để làm gì? Nó có nhân bản provider không?Junior›

Trả lời: exports mở quyền cho module khác (đã import module này) được inject provider đó. Nó không tạo bản sao — với scope mặc định, mọi nơi vẫn dùng chung một instance singleton. Export chỉ thay đổi "khả năng nhìn thấy", không thay đổi số lượng instance.

⚠️ Bẫy: nói "mỗi module được một bản riêng" là sai với singleton.

Q3Tại sao controller nên mỏng còn service nên dày?Junior›

Trả lời: Tách trách nhiệm: controller lo HTTP (định tuyến, lấy param/body, status), service lo business logic. Lợi ích: unit test service không cần khởi động server; tái dùng logic ở nhiều entrypoint (REST, WebSocket gateway, message consumer); controller dễ đọc, dễ thay đổi tầng vận chuyển. Trong Contact Center, cùng CallsService.transfer() được gọi cả từ REST lẫn từ event realtime.

Q4Tại sao provider mặc định là singleton? Đánh đổi là gì?Middle›

Trả lời: Singleton là mặc định vì nó rẻ và đủ dùng cho phần lớn service stateless: tạo một lần lúc khởi động, tái dùng suốt đời app, không có chi phí khởi tạo lặp lại, tận dụng cache/connection pool hiệu quả. Đánh đổi: provider phải không giữ state riêng theo request (nếu giữ sẽ rò rỉ dữ liệu giữa các request). Khi cần state theo request thì mới cân nhắc REQUEST scope hoặc AsyncLocalStorage.

Q5So sánh DEFAULT, REQUEST, TRANSIENT scope và đánh đổi hiệu năng.Middle›

Trả lời: DEFAULT = một instance toàn app, rẻ nhất. REQUEST = một instance mỗi HTTP request, hữu ích cho state theo request (multi-tenant, user context), nhưng tốn vì phải dựng lại cây phụ thuộc mỗi request. TRANSIENT = mỗi consumer (mỗi chỗ inject) một bản, tốn bộ nhớ nếu inject nhiều nơi, dùng khi mỗi nơi cần state biệt lập (vd logger có context riêng). Quy tắc: mặc định DEFAULT, chỉ nâng scope khi có lý do rõ ràng.

⚠️ Bẫy: REQUEST scope "lây" lên toàn chuỗi (scope bubbling) — nói được điểm này sẽ ghi điểm.

Q6Custom provider có những dạng nào? Khi nào dùng useFactory?Middle›

Trả lời: Bốn dạng: useClass (chọn class để new, vd theo môi trường), useValue (tiêm giá trị/hằng/mock), useFactory (kết quả của hàm, có thể async + inject phụ thuộc), useExisting (alias trỏ về provider đã có). Dùng useFactory khi khởi tạo cần logic, cần đợi I/O (kết nối Redis/DB) hoặc cần inject phụ thuộc khác qua mảng inject. Đây là cơ chế đứng sau các forRootAsync/registerAsync.

Q7Injection token là gì? Vì sao cần khi muốn lập trình theo interface?Middle›

Trả lời: Injection token là khóa (class, string hoặc symbol) mà container dùng để tra cứu provider. Với class, chính class làm token. Nhưng TypeScript interface bị xóa khi biên dịch nên không thể làm token — do đó để inject theo abstraction (interface), ta tạo một string/symbol token, đăng ký provider với provide: TOKEN, và inject bằng @Inject(TOKEN) với kiểu khai báo là interface. Nhờ vậy service phụ thuộc abstraction, dễ thay implementation/mock.

⚠️ Bẫy: viết constructor(private s: IStorage) rồi mong Nest tự phân giải interface — sẽ lỗi vì không có token runtime.

Q8Dynamic module là gì? Phân biệt forRoot và forFeature.Senior›

Trả lời: Dynamic module là module được cấu hình lúc chạy qua một static method trả về DynamicModule (chứa providers/exports/imports tùy tham số). Quy ước: forRoot(options) cấu hình một lần ở module gốc cho toàn app (kết nối, client, thường global); forFeature(...) đăng ký tài nguyên cục bộ cho từng module nghiệp vụ (vd repository cho entity cụ thể). Biến thể forRootAsync dùng useFactory + inject để lấy cấu hình từ ConfigService.

Q9Circular dependency xảy ra khi nào? forwardRef giải quyết ra sao?Senior›

Trả lời: Xảy ra khi hai provider/module phụ thuộc lẫn nhau (A cần B, B cần A). Nest khởi tạo theo thứ tự nên không biết tạo cái nào trước → một bên nhận undefined hoặc lỗi circular. forwardRef(() => X) bảo Nest hoãn việc phân giải token X tới khi cả hai đã được khai báo, phá vòng tại runtime. Dùng ở cả imports (cấp module) lẫn @Inject(forwardRef(...)) (cấp provider).

⚠️ Bẫy: dừng ở "dùng forwardRef là xong". Người phỏng vấn senior muốn nghe rằng vòng phụ thuộc là mùi thiết kế, nên ưu tiên tách module hoặc đảo chiều bằng event trước.

Q10Global module là gì? Khi nào nên và không nên dùng?Senior›

Trả lời: Module gắn @Global() (hoặc global: true trong dynamic module): chỉ cần import một lần, sau đó mọi module dùng được provider nó export mà không import lại. Nên dùng cho hạ tầng dùng khắp nơi: logger, config, kết nối DB/Redis. Không nên dùng cho module nghiệp vụ vì nó che giấu phụ thuộc thật — nhìn imports không còn biết module phụ thuộc gì, khó refactor và dễ tạo coupling ngầm. Nguyên tắc: tường minh là tốt; global hóa là ngoại lệ có chủ đích.

Q11Làm sao thiết kế ranh giới module cho một hệ thống Contact Center?Senior›

Trả lời: Cắt theo bounded context nghiệp vụ: AgentsModule, CallsModule, ChatModule, QueueModule (định tuyến/hàng đợi), TicketsModule, cộng các module hạ tầng global (ConfigModule, LoggerModule, DatabaseModule). Mỗi module export tối thiểu cần thiết (thường chỉ service mặt tiền). Hạn chế phụ thuộc trực tiếp giữa các domain; khi cần liên lạc chéo, ưu tiên event-driven (Calls phát call.ended, Tickets lắng nghe để tạo phiếu) thay vì gọi thẳng — vừa giảm coupling, vừa tránh vòng phụ thuộc, vừa dễ scale theo microservice sau này.

Q12Mặc định { provide: X, useClass: X } và useExisting khác gì nhau?Senior›

Trả lời: Cú pháp ngắn providers: [X] tương đương { provide: X, useClass: X } — Nest tạo một instance mới của X dưới token X. useExisting ngược lại không tạo instance mới mà alias một token khác về một provider đã tồn tại — cả hai token trỏ về cùng một instance. Dùng useExisting khi muốn cung cấp tên gọi khác (vd token legacy) cho cùng một service mà không nhân đôi đối tượng.
