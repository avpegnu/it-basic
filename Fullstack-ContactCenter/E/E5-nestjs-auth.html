NestJS Authentication & Authorization

Cài đặt xác thực JWT bằng Passport và phân quyền RBAC bằng Guard + Reflector — bản dựng thực tế của yêu cầu "xác thực và phân quyền" trong JD.

🎯 Học xong chương này bạn sẽ

• Phân biệt rõ Authentication (bạn là ai) và Authorization (bạn được làm gì) — hai khái niệm hay bị lẫn.

• Hiểu kiến trúc Passport trong NestJS: Strategy → validate() → AuthGuard → req.user.

• Tự viết JWT strategy: trích token từ header, verify chữ ký, gắn payload vào request.

• Cài RBAC bằng @Roles (SetMetadata) + RolesGuard đọc Reflector.

• Thiết kế refresh token có rotation, và route @Public cho endpoint mở.

• Áp dụng best practice bảo mật: httpOnly cookie, bcrypt, throttler, helmet.

💡 Liên hệ thực tế hệ thống Contact Center

Một Contact Center có nhiều vai trò: agent (nhận cuộc gọi/chat), supervisor (giám sát hàng đợi, nghe lén cuộc gọi), admin (cấu hình IVR, quản lý người dùng). Cùng một API GET /calls/:id nhưng agent chỉ xem cuộc gọi của mình, supervisor xem cả team, admin xem tất cả. Đây chính là bài toán mà JWT + RBAC Guard giải quyết: token chứng minh "bạn là agent #42", còn Guard quyết định "agent có được nghe lén không". Toàn bộ chương này là khung xương cho lớp bảo mật đó.

① Passport & strategies

Passport là thư viện xác thực phổ biến nhất của hệ Node, và NestJS bọc nó qua package @nestjs/passport. Triết lý của Passport rất gọn: mỗi cách đăng nhập là một strategy (chiến lược). Bạn cài chiến lược nào thì hệ thống "biết" xác thực kiểu đó — đăng nhập bằng username/password (local), bằng JWT (jwt), bằng Google OAuth (google)... Tất cả đều có chung một giao diện: nhận thông tin xác thực, kiểm tra, rồi trả về một object user.

Trong NestJS, một strategy là một provider kế thừa PassportStrategy(StrategyBase) và bắt buộc cài đặt hàm validate(). Giá trị mà validate() return sẽ được Passport gắn vào request.user — đây là điểm mấu chốt cần nhớ.

Client gửi credentials→ AuthGuard kích hoạt Strategy→ Strategy.validate()→ return user→ req.user

Local strategy — đăng nhập username/password

Chiến lược local dùng cho bước đăng nhập đầu tiên: client gửi email + mật khẩu, ta xác minh trong DB, nếu đúng thì phát hành JWT. Hàm validate() của local nhận đúng hai tham số (mặc định username, password).

local.strategy.tsNestJS
import { Strategy } from 'passport-local';
import { PassportStrategy } from '@nestjs/passport';
import { Injectable, UnauthorizedException } from '@nestjs/common';

@Injectable()
export class LocalStrategy extends PassportStrategy(Strategy) {
  constructor(private auth: AuthService) {
    super({ usernameField: 'email' }); // đổi field mặc định 'username' → 'email'
  }

  // validate() chạy MỖI lần qua AuthGuard('local')
  async validate(email: string, password: string) {
    const agent = await this.auth.verifyAgent(email, password);
    if (!agent) throw new UnauthorizedException('Sai email hoặc mật khẩu');
    return agent; // → gắn vào req.user, controller dùng để ký JWT
  }
}
⚠️ validate() trả về gì = req.user là cái đó

Đừng trả về cả entity có passwordHash! Hãy loại bỏ trường nhạy cảm trong verifyAgent hoặc map sang DTO gọn (id, email, roles). Bất cứ thứ gì lọt ra req.user đều có nguy cơ bị log hoặc serialize ra response.

Đăng ký strategy trong module

Strategy chỉ là provider — phải khai báo trong providers của module thì DI mới khởi tạo và Passport mới "thấy" nó.

auth.module.tsNestJS
@Module({
  imports: [
    PassportModule,
    JwtModule.register({ secret: process.env.JWT_SECRET, signOptions: { expiresIn: '15m' } }),
    AgentsModule,
  ],
  providers: [AuthService, LocalStrategy, JwtStrategy], // strategy phải nằm ở đây
  controllers: [AuthController],
})
export class AuthModule {}

② JWT strategy

Sau khi đăng nhập thành công, server ký một JWT (JSON Web Token) và trả về client. Mọi request sau đó client đính kèm token này; server chỉ cần verify chữ ký là biết người gọi là ai mà không cần truy DB — đó là sức mạnh của JWT (stateless).

Cấu trúc JWT gồm 3 phần ngăn bởi dấu chấm: header.payload.signature. Payload chứa các claim như sub (subject = id người dùng), roles, exp (hết hạn). Signature bảo đảm payload không bị sửa.

jwt.strategy.tsNestJS
import { ExtractJwt, Strategy } from 'passport-jwt';
import { PassportStrategy } from '@nestjs/passport';

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor() {
    super({
      // trích token từ header: "Authorization: Bearer <token>"
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,           // hết hạn thì từ chối
      secretOrKey: process.env.JWT_SECRET, // dùng để verify chữ ký
    });
  }

  // Chỉ chạy SAU KHI token đã verify chữ ký + còn hạn.
  // 'payload' chính là phần đã giải mã của JWT.
  async validate(payload: { sub: number; email: string; roles: string[] }) {
    // return → req.user. Có thể truy DB ở đây nếu cần dữ liệu tươi.
    return { id: payload.sub, email: payload.email, roles: payload.roles };
  }
}
🔎 Thứ tự xử lý bên trong passport-jwt

1) Trích token từ Authorization: Bearer ... → 2) verify chữ ký bằng secretOrKey → 3) kiểm tra exp → 4) chỉ khi mọi bước trên hợp lệ mới gọi validate(payload). Nếu token sai/hết hạn, validate() không chạy và Passport tự ném 401 Unauthorized. Vì vậy bên trong validate() bạn chỉ cần lo "payload này map ra user nào".

Ký token khi đăng nhập

Sau khi LocalStrategy xác minh xong, controller dùng JwtService để ký token với đúng các claim mà JwtStrategy.validate mong đợi.

auth.service.tsNestJS
@Injectable()
export class AuthService {
  constructor(private jwt: JwtService) {}

  issueAccessToken(agent: Agent) {
    const payload = { sub: agent.id, email: agent.email, roles: agent.roles };
    return this.jwt.sign(payload); // expiresIn lấy từ JwtModule.register
  }
}

③ AuthGuard & @UseGuards

Strategy biết cách xác thực, nhưng cái kích hoạt nó ở từng route là Guard. @nestjs/passport cung cấp factory AuthGuard('tên-strategy') sinh ra một Guard chạy đúng strategy đó. Bạn gắn Guard vào route/controller bằng decorator @UseGuards.

Nhắc lại từ E3: Guard chạy sau middleware, trước interceptor và pipe; nó trả về true/false (hoặc Promise/Observable) để quyết định request có được vào handler hay không.

auth.controller.tsNestJS
@Controller('auth')
export class AuthController {
  // Bước đăng nhập: dùng AuthGuard('local') để chạy LocalStrategy
  @UseGuards(AuthGuard('local'))
  @Post('login')
  login(@Req() req) {
    // req.user do LocalStrategy.validate() trả về
    return this.auth.issueAccessToken(req.user);
  }
}

@Controller('calls')
@UseGuards(AuthGuard('jwt')) // áp cho TẤT CẢ route trong controller
export class CallsController {
  @Get()
  myCalls(@Req() req) {
    return this.calls.findByAgent(req.user.id); // req.user từ JwtStrategy
  }
}

💡 Global Guard kiểu "secure by default"

Mẫu phổ biến trong dự án thật: đăng ký JwtAuthGuard ở mức global qua APP_GUARD để mọi route mặc định phải có token, rồi mở ngoại lệ cho vài route public bằng decorator @Public (xem mục ⑤). Như vậy quên gắn guard sẽ là "đóng" chứ không phải "mở" — an toàn hơn nhiều so với phải nhớ gắn từng route.

app.module.ts (global guard)NestJS
@Module({
  providers: [
    { provide: APP_GUARD, useClass: JwtAuthGuard }, // chạy DI bình thường
  ],
})
export class AppModule {}

Một mẹo hay: tạo lớp JwtAuthGuard kế thừa AuthGuard('jwt') để có thể tùy biến (vd: bỏ qua route public). Đây cũng là nơi ta override canActivate/handleRequest.

jwt-auth.guard.tsNestJS
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  // có thể override handleRequest để custom thông điệp lỗi
  handleRequest(err, user, info) {
    if (err || !user) {
      throw err || new UnauthorizedException('Token không hợp lệ hoặc đã hết hạn');
    }
    return user;
  }
}

④ RBAC với Guard + Reflector

Đến đây ta đã biết người gọi là ai (authentication). Bước tiếp theo là Authorization: người này được làm gì? Mô hình phổ biến nhất là RBAC (Role-Based Access Control) — gán mỗi route một danh sách vai trò được phép, rồi so khớp với req.user.roles.

Kỹ thuật: dùng SetMetadata để "đính" metadata vai trò lên route, rồi viết một RolesGuard dùng Reflector để đọc lại metadata đó lúc runtime.

@Roles('supervisor')→ SetMetadata gắn vào route→ RolesGuard.canActivate→ Reflector đọc metadata→ so khớp req.user.roles

Decorator @Roles (SetMetadata)

roles.decorator.tsNestJS
import { SetMetadata } from '@nestjs/common';

export const ROLES_KEY = 'roles';
// @Roles('admin','supervisor') → gắn metadata ['admin','supervisor']
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

RolesGuard đọc Reflector

Reflector là tiện ích của Nest để đọc metadata. Hai hàm hay dùng: get() (đọc 1 chỗ) và getAllAndOverride() (đọc cả method lẫn class, method ưu tiên — rất hợp khi vừa gắn @Roles ở controller vừa ở route).

roles.guard.tsNestJS
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {} // Reflector inject qua DI

  canActivate(ctx: ExecutionContext): boolean {
    // đọc metadata từ method, fallback sang class
    const required = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
      ctx.getHandler(), // route method
      ctx.getClass(),   // controller class
    ]);

    // route không yêu cầu role nào → cho qua (chỉ cần đã đăng nhập)
    if (!required || required.length === 0) return true;

    const { user } = ctx.switchToHttp().getRequest();
    // user do JwtStrategy gắn vào — so khớp ít nhất 1 role
    const ok = required.some((r) => user?.roles?.includes(r));
    if (!ok) throw new ForbiddenException('Bạn không có quyền thực hiện thao tác này');
    return true;
  }
}

Kết hợp AuthGuard + RolesGuard

Hai guard này phối hợp theo thứ tự khai báo: JwtAuthGuard chạy trước để xác thực và gắn req.user; rồi RolesGuard chạy sau mới có user.roles để so khớp. Đảo thứ tự là sai.

supervisor.controller.tsNestJS
@Controller('monitor')
@UseGuards(JwtAuthGuard, RolesGuard) // thứ tự: xác thực TRƯỚC, phân quyền SAU
export class MonitorController {

  @Roles('supervisor', 'admin')
  @Post('calls/:id/barge-in') // nghe lén/chen vào cuộc gọi
  bargeIn(@Param('id') id: string, @Req() req) {
    return this.monitor.bargeIn(id, req.user.id);
  }

  @Roles('admin')
  @Delete('queues/:id') // chỉ admin được xóa hàng đợi
  removeQueue(@Param('id') id: string) {
    return this.queues.remove(id);
  }
}
🐛 RBAC chưa đủ cho "ownership"

RBAC trả lời "agent có được xem cuộc gọi không", nhưng không trả lời "agent có được xem cuộc gọi của người khác không". Cần thêm kiểm tra resource-level (ABAC): trong service, so call.agentId === req.user.id, hoặc cho supervisor xem theo team. Đừng tin RBAC giải quyết mọi thứ — đó là bẫy phỏng vấn rất hay gặp.

⑤ Refresh token & route @Public

Access token nên sống ngắn (vd 15 phút) để giảm thiệt hại nếu bị lộ. Nhưng bắt agent đăng nhập lại mỗi 15 phút thì tệ. Giải pháp: cấp thêm refresh token sống dài (vd 7 ngày), lưu an toàn, dùng để xin access token mới khi cái cũ hết hạn.

Strategy & endpoint riêng cho refresh

Tách hẳn một jwt-refresh strategy với secret riêng (JWT_REFRESH_SECRET), trích token từ cookie thay vì header, và một endpoint POST /auth/refresh được bảo vệ bằng strategy đó.

jwt-refresh.strategy.tsNestJS
@Injectable()
export class JwtRefreshStrategy extends PassportStrategy(Strategy, 'jwt-refresh') {
  constructor(private auth: AuthService) {
    super({
      jwtFromRequest: ExtractJwt.fromExtractors([
        (req) => req?.cookies?.refresh_token, // lấy từ httpOnly cookie
      ]),
      secretOrKey: process.env.JWT_REFRESH_SECRET,
      passReqToCallback: true, // để truy lại raw token trong validate
    });
  }

  async validate(req, payload) {
    const token = req.cookies.refresh_token;
    // so token với hash đã lưu trong DB → chống token cũ/bị thu hồi
    const agent = await this.auth.validateRefreshToken(payload.sub, token);
    if (!agent) throw new UnauthorizedException();
    return agent;
  }
}

Rotation — xoay token mỗi lần refresh

Refresh token rotation: mỗi lần dùng refresh token, cấp luôn refresh token mới và vô hiệu hóa cái cũ. Nếu kẻ tấn công trộm được token cũ và dùng lại, hệ thống phát hiện "token đã bị xoay" → coi như bị lộ → thu hồi cả phiên.

auth.controller.ts (refresh)NestJS
@UseGuards(AuthGuard('jwt-refresh'))
@Post('refresh')
async refresh(@Req() req, @Res({ passthrough: true }) res) {
  const agent = req.user;
  const access = this.auth.issueAccessToken(agent);
  const refresh = await this.auth.rotateRefreshToken(agent); // xoay + lưu hash mới

  res.cookie('refresh_token', refresh, {
    httpOnly: true, secure: true, sameSite: 'strict',
  });
  return { access_token: access };
}

@Public — mở ngoại lệ cho global guard

Khi đã dùng global JwtAuthGuard, các route như login, health-check cần "miễn xác thực". Ta tạo decorator @Public đánh metadata, rồi cho guard bỏ qua khi gặp metadata đó.

public.decorator.ts + guardNestJS
export const IS_PUBLIC = 'isPublic';
export const Public = () => SetMetadata(IS_PUBLIC, true);

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private reflector: Reflector) { super(); }

  canActivate(ctx: ExecutionContext) {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC, [
      ctx.getHandler(), ctx.getClass(),
    ]);
    if (isPublic) return true; // bỏ qua xác thực
    return super.canActivate(ctx); // còn lại chạy JWT như thường
  }
}

// dùng: @Public() @Post('login') login() {...}

⑥ Bảo mật & best practices

Cài đúng cơ chế chưa đủ — phải cài an toàn. Dưới đây là những lớp phòng thủ tối thiểu cho một service xác thực thực tế.

🔒 bcrypt cho mật khẩu

Không bao giờ lưu mật khẩu thô. Băm bằng bcrypt (salt + cost factor ~10–12). Đây là tác vụ CPU dùng thread pool.

🍪 httpOnly cookie

Refresh token để trong cookie httpOnly + secure + sameSite → JS không đọc được, chống XSS đánh cắp token.

⏱️ Throttler (rate limit)

@nestjs/throttler chặn brute-force login: vd tối đa 5 lần thử / phút / IP cho /auth/login.

🛡️ helmet

Đặt các HTTP header bảo mật (CSP, HSTS, X-Frame-Options...) chỉ với 1 dòng app.use(helmet()).

🔑 Secret qua env

JWT_SECRET đủ dài, ngẫu nhiên, lưu trong biến môi trường/secret manager — không hard-code, không commit.

⌛ Token sống ngắn

Access ngắn hạn + refresh rotation giảm cửa sổ tấn công nếu token bị lộ.

main.ts (lớp bảo vệ hạ tầng)NestJS
const app = await NestFactory.create(AppModule);
app.use(helmet());                 // security headers
app.use(cookieParser());           // đọc refresh_token cookie
app.enableCors({ origin: process.env.CLIENT_URL, credentials: true });
app.useGlobalPipes(new ValidationPipe({ whitelist: true }));
await app.listen(3000);
throttler trên loginNestJS
@UseGuards(ThrottlerGuard)
@Throttle({ default: { limit: 5, ttl: 60000 } }) // 5 lần / 60s
@Public()
@Post('login')
login(@Body() dto: LoginDto) { /* ... */ }
⚠️ JWT stateless = khó "đăng xuất ngay"

Vì access token tự verify được, ta không thể hủy nó trước hạn chỉ bằng cách xóa ở client. Muốn "đăng xuất tức thì" hoặc "khóa tài khoản ngay" cần: token sống thật ngắn, hoặc duy trì một blacklist/deny-list (lưu jti bị thu hồi trong Redis), hoặc dùng cơ chế phiên qua refresh token. Đây là đánh đổi cố hữu của stateless auth.

⚠️ Lỗi thường gặp & Best practices

🚫 Quên đăng ký strategy

Strategy không nằm trong providers → AuthGuard('jwt') báo "Unknown strategy". Phải khai báo provider.

🚫 Đảo thứ tự guard

Đặt RolesGuard trước JwtAuthGuard → chưa có req.user → phân quyền luôn fail. Xác thực trước.

🚫 Lộ passwordHash ra req.user

validate() trả nguyên entity → hash lọt vào response/log. Map sang DTO gọn.

🚫 Để secret trong code

Hard-code JWT_SECRET rồi commit → toàn bộ token bị giả mạo được. Dùng env/secret manager.

🚫 Tin RBAC giải quyết ownership

RBAC chỉ check vai trò, không check "của ai". Thêm kiểm tra resource-level trong service.

🚫 Refresh token sống mãi, không rotate

Token dài hạn bất biến → lộ là toang lâu dài. Luôn rotation + lưu hash để thu hồi được.

🧪 Bài tập

🧪 Bài 1 — Guard chỉ cho supervisor cùng team

Viết một TeamGuard đảm bảo supervisor chỉ xem được cuộc gọi của agent trong team mình, không phải mọi team. Cần đọc gì từ req.user và req.params? Vì sao RBAC thuần không đủ?

Gợi ý

RBAC chỉ xác nhận "là supervisor". TeamGuard cần lấy req.user.teamId và id cuộc gọi từ req.params, truy DB để biết cuộc gọi thuộc team nào, rồi so khớp. Đây là resource-level / ABAC — phụ thuộc dữ liệu nên thường đặt trong guard hoặc service, không thể tĩnh hóa bằng metadata.

🧪 Bài 2 — Tự cài RolesGuard từ đầu

Cài đặt lại @Roles decorator + RolesGuard sao cho hỗ trợ cả gắn ở controller lẫn route, route ưu tiên hơn controller. Dùng hàm nào của Reflector? Trả về gì khi route không khai báo role?

Gợi ý

Dùng reflector.getAllAndOverride(ROLES_KEY, [getHandler(), getClass()]) — phần tử đầu (method) thắng. Nếu kết quả là undefined/rỗng nghĩa là route không yêu cầu role cụ thể → return true (chỉ cần đã đăng nhập).

🧪 Bài 3 — Refresh rotation phát hiện reuse

Thiết kế luồng phát hiện "refresh token bị dùng lại sau khi đã xoay". Khi phát hiện reuse, hệ thống nên làm gì với phiên của agent đó?

Gợi ý

Mỗi refresh token lưu hash + trạng thái (active/used). Khi nhận token đã ở trạng thái used → đây là dấu hiệu bị lộ → thu hồi toàn bộ refresh token của agent (xóa hết phiên), buộc đăng nhập lại, và ghi log cảnh báo bảo mật.

Ngân hàng câu hỏi phỏng vấn

Auth/Authz trong NestJS — chủ đề gần như chắc chắn được hỏi cho vị trí backend.

Q1Phân biệt Authentication và Authorization.Junior›

Trả lời: Authentication (xác thực) trả lời "bạn là ai" — kiểm tra danh tính qua mật khẩu/JWT. Authorization (phân quyền) trả lời "bạn được làm gì" — kiểm tra quyền truy cập tài nguyên/thao tác. Trong Nest, xác thực thường do AuthGuard/JwtStrategy lo, phân quyền do RolesGuard + @Roles lo.

⚠️ Bẫy: nói chúng giống nhau, hoặc gộp làm một guard duy nhất. Chúng là hai lớp tách biệt, chạy nối tiếp.

Q2Mô tả luồng của một Passport strategy trong NestJS.Junior›

Trả lời: Request đi qua route có @UseGuards(AuthGuard('jwt')) → guard kích hoạt strategy tương ứng → strategy trích thông tin xác thực (token từ header/credentials từ body), kiểm tra → gọi validate() → giá trị return được gắn vào req.user. Nếu thất bại, Passport ném 401. Strategy là provider kế thừa PassportStrategy và khai trong providers.

Q3JWT strategy trích token từ đâu và xác minh thế nào?Middle›

Trả lời: Cấu hình jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken() để lấy token từ header Authorization: Bearer. Passport verify chữ ký bằng secretOrKey, kiểm tra exp (vì ignoreExpiration: false), rồi mới gọi validate(payload). Payload là phần đã giải mã, ta map ra object user gắn vào req.user. Có thể trích từ cookie qua fromExtractors nếu cần.

Q4req.user được gắn ở đâu? Ai gắn?Junior›

Trả lời: Passport gắn req.user bằng giá trị return của Strategy.validate(). Sau khi guard cho qua, handler đọc req.user (hoặc qua custom decorator @CurrentUser()) để biết người gọi. Nội dung của nó hoàn toàn do bạn quyết định trong validate().

Q5Tự cài một RolesGuard — bạn sẽ làm thế nào?Middle›

Trả lời: (1) Tạo @Roles(...roles) = SetMetadata(ROLES_KEY, roles). (2) Viết RolesGuard implements CanActivate, inject Reflector. (3) Trong canActivate dùng reflector.getAllAndOverride(ROLES_KEY, [getHandler(), getClass()]) đọc role yêu cầu; nếu rỗng thì cho qua. (4) Lấy req.user.roles và so khớp some(); không khớp thì ném ForbiddenException. (5) Áp guard cùng JwtAuthGuard theo đúng thứ tự.

Q6Reflector dùng để làm gì? getAllAndOverride khác get ra sao?Middle›

Trả lời: Reflector đọc metadata mà SetMetadata/decorator đã gắn lên handler hoặc class lúc runtime. get(key, target) đọc 1 chỗ. getAllAndOverride(key, [handler, class]) đọc nhiều cấp và lấy giá trị đầu tiên tìm thấy (method ưu tiên hơn class) — hữu ích khi metadata có thể gắn ở cả controller và route. Còn getAllAndMerge thì gộp mảng lại.

Q7Khi kết hợp AuthGuard và RolesGuard, thứ tự quan trọng không? Vì sao?Middle›

Trả lời: Rất quan trọng. Guard chạy theo thứ tự liệt kê trong @UseGuards. Phải để JwtAuthGuard trước để xác thực và gắn req.user; rồi RolesGuard mới có user.roles để so khớp. Đảo lại thì RolesGuard chạy khi chưa có req.user → luôn fail hoặc lỗi.

⚠️ Bẫy: nói "guard chạy song song" hay "thứ tự không quan trọng" — sai.

Q8Làm sao tạo route public khi đã có global JwtAuthGuard?Middle›

Trả lời: Tạo decorator @Public() = SetMetadata('isPublic', true). Trong JwtAuthGuard.canActivate, dùng Reflector đọc metadata này; nếu là public thì return true bỏ qua xác thực, ngược lại gọi super.canActivate(). Áp @Public() lên login, health-check... Cách này giữ "secure by default" mà vẫn linh hoạt.

Q9Refresh token là gì? Triển khai trong NestJS thế nào?Senior›

Trả lời: Refresh token sống dài, chỉ dùng để xin access token mới khi access (ngắn hạn) hết hạn. Trong Nest: tạo strategy riêng jwt-refresh với secret riêng, trích token từ httpOnly cookie, validate() so token với hash đã lưu trong DB. Endpoint POST /auth/refresh bảo vệ bằng strategy đó, cấp access mới và rotate refresh (xoay token + lưu hash mới, vô hiệu cái cũ). Lưu hash giúp thu hồi được — bù cho việc JWT vốn stateless.

Q10RBAC có đủ để bảo vệ "agent chỉ xem cuộc gọi của mình" không?Senior›

Trả lời: Không. RBAC chỉ xác nhận vai trò ("là agent"), không biết tài nguyên cụ thể thuộc về ai. Cần thêm kiểm tra resource-level/ownership (một dạng ABAC): trong service hoặc guard, so call.agentId === req.user.id, hoặc cho supervisor xem theo team. Phân quyền tốt thường kết hợp RBAC (thô) + kiểm tra ownership (mịn).

⚠️ Bẫy: trả lời "chỉ cần @Roles('agent') là xong" — bỏ sót tầng ownership.

Q11JWT stateless — làm sao "đăng xuất ngay" hoặc khóa tài khoản tức thì?Senior›

Trả lời: Vì access token tự verify được nên không hủy trực tiếp được. Giải pháp: (1) access token sống thật ngắn để cửa sổ nhỏ; (2) duy trì deny-list (lưu jti bị thu hồi trong Redis, guard kiểm tra mỗi request — đánh đổi tính stateless); (3) quản phiên qua refresh token: thu hồi refresh là chặn gia hạn. Tùy yêu cầu mà chọn — đây là đánh đổi cố hữu giữa stateless (nhanh, dễ scale) và khả năng thu hồi tức thì.

Q12Những lớp bảo mật nào bạn luôn thêm cho service auth?Senior›

Trả lời: Băm mật khẩu bằng bcrypt (salt + cost), không lưu mật khẩu thô; rate limit login bằng @nestjs/throttler chống brute-force; helmet đặt security header; refresh token trong httpOnly+secure+sameSite cookie; secret đủ mạnh qua env/secret manager; access ngắn hạn + refresh rotation; ValidationPipe(whitelist) lọc input; CORS giới hạn origin. Quan trọng là phối hợp nhiều lớp (defense in depth) chứ không trông cậy một biện pháp.
