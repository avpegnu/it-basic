HTTP thuần & REST API cơ bản

Dựng HTTP server bằng module http thuần để hiểu điều mà framework che giấu, rồi thấy vì sao Express ra đời.

🎯 Học xong chương này bạn sẽ

• Dựng được một HTTP server không cần framework bằng module http thuần, hiểu rõ vòng đời request/response.

• Đọc đúng req.method, req.url, req.headers và ghi response bằng writeHead / setHeader / end.

• Tự viết routing thủ công theo URL + method, và cảm nhận tận xương vì sao ta cần Express/NestJS.

• Đọc body từ stream (chunks), parse JSON an toàn, giới hạn payload chống tấn công.

• Nắm các nhóm status code (1xx–5xx), header quan trọng, và cấu hình CORS / preflight đúng cách.

• Phân biệt HTTP vs HTTPS, keep-alive, statelessness — những câu hỏi phỏng vấn kinh điển.

💡 Liên hệ thực tế hệ thống Contact Center

Mọi thao tác của tổng đài viên (agent) đều là HTTP request: tải danh sách hội thoại đang chờ, nhận một ticket, gửi tin nhắn vào cuộc chat, cập nhật trạng thái cuộc gọi. Realtime (WebSocket) lo phần đẩy sự kiện tức thời, nhưng xương sống REST vẫn lo CRUD: tạo ticket, đọc lịch sử, phân công agent. Hiểu HTTP ở tầng thấp giúp bạn biết đặt status code nào khi queue đầy (503), khi agent thao tác trùng (409), và vì sao một request "treo" có thể do quên gọi res.end().

① Module http thuần

Node tích hợp sẵn module http — không cần cài gì thêm. Mọi framework web (Express, Fastify, NestJS) đều xây bên trên module này. Hàm cốt lõi là http.createServer: nó nhận một request listener được gọi mỗi khi có request đến, với hai tham số (req, res).

Client (browser/agent app)→ TCP socket→ http server (Node)→ request listener (req,res)→ res.end()
server.jsNode.js
const http = require('http');

// request listener: chạy MỖI khi có request tới
const server = http.createServer((req, res) => {
  // req = IncomingMessage (readable stream) — dữ liệu KHÁCH gửi lên
  // res = ServerResponse (writable stream) — dữ liệu TA gửi về
  res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Contact Center API đang chạy');
});

server.listen(3000, () => {
  console.log('Server lắng nghe tại http://localhost:3000');
});
⚠️ Bắt buộc gọi res.end()

Nếu không gọi res.end() (hoặc res.write() rồi end()), response không bao giờ kết thúc — client treo cho tới khi timeout. Đây là lỗi "request bị pending" kinh điển. Một request → đúng một lần kết thúc response.

Một điểm hay bị nhầm: createServer chỉ tạo server, phải gọi listen(port) nó mới thực sự mở socket và nhận kết nối. server là một EventEmitter — bạn có thể nghe các sự kiện như 'request', 'connection', 'clientError' (xem lại Events ở B3).

② Request & Response

Hai object req và res là trung tâm của mọi xử lý. req là một readable stream (đọc dữ liệu khách gửi lên), còn res là một writable stream (ghi dữ liệu trả về). Hiểu chúng là stream giải thích vì sao body không đến ngay mà phải gom dần — sẽ nói ở phần ④.

req.urlĐường dẫn + query string (KHÔNG gồm domain)'/api/tickets?status=open'

🐛 req.url KHÔNG phải URL đầy đủ

Trong server HTTP, req.url chỉ là phần path + query (vd /api/calls?agent=42), không có http://host. Muốn tách path và query, dùng new URL(req.url, 'http://'+req.headers.host) rồi đọc url.pathname và url.searchParams.

res — ServerResponse

res.setHeader(k, v)Đặt 1 header — phải gọi TRƯỚC khi gửi body
res.writeHead(code, headers)Đặt status + nhiều header cùng lúc (cách 2, gọn)

reqres.jsNode.js
const server = http.createServer((req, res) => {
  // Tách pathname & query an toàn
  const url = new URL(req.url, `http://` + req.headers.host);
  const pathname = url.pathname;            // '/api/tickets'
  const status = url.searchParams.get('status'); // 'open'

  // Trả JSON đúng chuẩn
  const body = JSON.stringify({ pathname, method: req.method, status });
  res.writeHead(200, {
    'Content-Type': 'application/json; charset=utf-8',
    'Content-Length': Buffer.byteLength(body) // tính theo BYTE, không phải ký tự
  });
  res.end(body);
});
⚠️ "Headers already sent"

Header chỉ gửi được một lần, trước body. Nếu gọi setHeader/writeHead sau khi đã write body, Node ném ERR_HTTP_HEADERS_SENT. Quy tắc: set status + header trước → write body → end.

③ Routing thủ công

Module http không có khái niệm route. Bạn chỉ nhận được một listener cho mọi request. Muốn phân biệt "GET danh sách ticket" với "POST tạo ticket", bạn phải tự kiểm tra req.method và req.url bằng tay — thường là một chuỗi if/else hoặc switch dài.

router-tay.jsNode.js
const server = http.createServer((req, res) => {
  const { method } = req;
  const url = new URL(req.url, `http://` + req.headers.host);
  const path = url.pathname;

  // GET /api/tickets — danh sách ticket trong queue
  if (method === 'GET' && path === '/api/tickets') {
    return sendJson(res, 200, { tickets: [] });
  }

  // POST /api/tickets — tạo ticket mới
  if (method === 'POST' && path === '/api/tickets') {
    return handleCreateTicket(req, res);
  }

  // GET /api/tickets/:id — KHỔ SỞ: phải tự match param bằng regex/split
  const m = path.match(/^\/api\/tickets\/(\w+)$/);
  if (method === 'GET' && m) {
    const id = m[1];
    return sendJson(res, 200, { id });
  }

  // Không khớp route nào → 404
  sendJson(res, 404, { error: 'Not Found' });
});

function sendJson(res, code, obj) {
  const body = JSON.stringify(obj);
  res.writeHead(code, { 'Content-Type': 'application/json; charset=utf-8' });
  res.end(body);
}
🐛 Vì sao routing thủ công "mệt" → cần framework

Với 3 route đã thấy rối; một Contact Center thật có hàng trăm route (agents, calls, chats, queues, tickets, reports). Tự tay bạn phải lo: match path động (:id), parse query, gom body, xử lý 404/405, chạy logic chung (auth, log, CORS) cho mọi route. Tất cả lặp lại, dễ sai, khó test. Express ra đời chính để giải quyết việc này: cung cấp router, middleware, param matching, body parser sẵn. Xem chương C1.

④ Đọc body & parse

Đây là phần khiến nhiều người mới bối rối nhất. Khác với req.url hay req.headers (có ngay), body không có sẵn. Vì req là một readable stream, dữ liệu đến theo từng chunk (mẩu Buffer) qua sự kiện 'data', và chỉ khi sự kiện 'end' bắn ra bạn mới có đủ body.

req (stream)→ 'data' → chunk 1→ 'data' → chunk 2…→ 'end'→ Buffer.concat → parse
read-body.jsNode.js
// Đọc body, parse JSON, GIỚI HẠN payload chống tấn công
function readJsonBody(req, limitBytes = 1_000_000) {
  return new Promise((resolve, reject) => {
    const chunks = [];
    let size = 0;

    req.on('data', (chunk) => {
      size += chunk.length;
      if (size > limitBytes) {                // payload quá lớn → cắt sớm
        reject(Object.assign(new Error('Payload too large'), { status: 413 }));
        req.destroy();                       // đóng kết nối, ngừng nhận thêm
        return;
      }
      chunks.push(chunk);
    });

    req.on('end', () => {
      const raw = Buffer.concat(chunks).toString('utf8');
      if (!raw) return resolve({});         // body rỗng cũng hợp lệ
      try {
        resolve(JSON.parse(raw));        // PHẢI bọc try/catch — JSON hỏng làm crash
      } catch {
        reject(Object.assign(new Error('Invalid JSON'), { status: 400 }));
      }
    });

    req.on('error', reject);          // lỗi mạng giữa chừng
  });
}

// Dùng khi tạo ticket mới
async function handleCreateTicket(req, res) {
  try {
    const data = await readJsonBody(req);
    if (!data.subject) return sendJson(res, 400, { error: 'subject là bắt buộc' });
    const ticket = { id: genId(), subject: data.subject, status: 'open' };
    sendJson(res, 201, ticket);   // 201 Created + nên kèm Location header
  } catch (err) {
    sendJson(res, err.status || 500, { error: err.message });
  }
}
⚠️ Ba điều luôn phải nhớ khi đọc body

(1) Try/catch quanh JSON.parse — client gửi JSON hỏng là chuyện thường, không được để crash server.
(2) Giới hạn kích thước — không giới hạn thì kẻ xấu gửi 10GB làm cạn RAM (DoS). Đặt limit và trả 413.
(3) Kiểm tra Content-Type — chỉ parse JSON khi header là application/json; form thì khác.

Express che toàn bộ đoạn này sau một dòng app.use(express.json({ limit: '1mb' })). Hiểu rõ cơ chế gốc giúp bạn biết tham số limit thực sự bảo vệ điều gì, và vì sao đôi khi req.body bị undefined (do quên middleware hoặc sai Content-Type).

⑤ Status code & headers

Status code là hợp đồng giữa server và client: nó nói kết quả request thuộc loại gì để client phản ứng đúng (hiển thị lỗi, thử lại, redirect…). Chia làm 5 nhóm theo chữ số đầu.

NhómÝ nghĩaVí dụ trong Contact Center
1xx InformationalTạm thời, request đang xử lý101 Switching Protocols khi nâng cấp lên WebSocket
2xx SuccessThành công200 đọc lịch sử chat · 201 tạo ticket · 204 xóa, không body
3xx RedirectCần đi nơi khác / dùng cache301 đổi domain API · 304 Not Modified dùng cache
4xx Client ErrorLỗi do client400 body sai · 401 chưa đăng nhập · 403 agent không đủ quyền · 404 không có ticket · 409 nhận trùng ticket · 429 gọi quá nhanh
5xx Server ErrorLỗi do server500 bug · 502/504 upstream lỗi/timeout · 503 queue quá tải / đang bảo trì
💡 401 vs 403 vs 409 — hay bị nhầm

401 Unauthorized: bạn chưa xác thực (thiếu/hết hạn token) → đăng nhập đi.
403 Forbidden: bạn đã xác thực nhưng không có quyền (agent thường cố mở dashboard của supervisor).
409 Conflict: trạng thái xung đột — vd hai agent cùng bấm "nhận" một ticket; người sau nhận 409.

Header quan trọng

HeaderVai trò

Content-LengthĐộ dài body tính theo byte. Tính bằng Buffer.byteLength(), không dùng .length của chuỗi (tiếng Việt nhiều byte)

⚠️ Content-Length tính theo BYTE

Chuỗi 'Xin chào' có 8 ký tự nhưng nhiều hơn 8 byte ở UTF-8 (dấu tiếng Việt là 2–3 byte). Dùng str.length sẽ báo sai độ dài → client cắt cụt body hoặc treo. Luôn dùng Buffer.byteLength(str).

⑥ CORS & bảo mật cơ bản

CORS (Cross-Origin Resource Sharing) là cơ chế của trình duyệt: theo Same-Origin Policy, trang web ở origin A (vd https://agent.app) không được đọc response từ API ở origin B (https://api.app) trừ khi server B cho phép qua các header Access-Control-Allow-*. Đây là bảo vệ ở phía browser, không phải xác thực — vẫn cần auth riêng.

ℹ️ Preflight là gì?

Với các request "không đơn giản" (method PUT/PATCH/DELETE, hoặc có header tùy chỉnh như Authorization, hoặc Content-Type application/json), trình duyệt gửi trước một request thăm dò OPTIONS — gọi là preflight. Server phải trả về quyền cho phép; nếu hợp lệ, browser mới gửi request thật. Bạn sẽ thấy 2 request trong Network tab: một OPTIONS, rồi một POST.

Browser (agent.app)→ OPTIONS (preflight)→ Server trả Allow-*→ POST thật→ Response
cors.jsNode.js
const ALLOWED = ['https://agent.app', 'https://supervisor.app'];

function applyCors(req, res) {
  const origin = req.headers.origin;
  // CHỈ cho phép origin trong whitelist — đừng dùng '*' với API có auth
  if (ALLOWED.includes(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
    res.setHeader('Vary', 'Origin');          // để cache phân biệt theo origin
    res.setHeader('Access-Control-Allow-Credentials', 'true');
  }
  res.setHeader('Access-Control-Allow-Methods', 'GET,POST,PATCH,DELETE,OPTIONS');
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type, Authorization');
  res.setHeader('Access-Control-Max-Age', '600'); // cache preflight 10 phút
}

const server = http.createServer((req, res) => {
  applyCors(req, res);

  // Trả lời preflight NGAY — không vào logic route
  if (req.method === 'OPTIONS') {
    res.writeHead(204);  // 204 No Content
    return res.end();
  }
  // ... routing thật ở đây
});
🐛 Bảo mật cơ bản — đừng quên

• Đừng đặt Access-Control-Allow-Origin: * cho API có cookie/credentials — kết hợp với Allow-Credentials: true là cấu hình bị trình duyệt từ chối và là lỗ hổng. Dùng whitelist.
• Luôn giới hạn payload (413), validate input (400), rate-limit (429) để chống DoS/abuse.
• Dùng HTTPS ở production: HTTP gửi token/dữ liệu cuộc gọi dưới dạng plaintext, ai bắt gói tin cũng đọc được.

💡 Statelessness của HTTP

HTTP không nhớ gì giữa các request — mỗi request là độc lập, server không biết request này đến từ "phiên" nào trừ khi client tự gửi kèm thông tin (cookie/token). Vì vậy auth phải đính token vào mỗi request. Tính stateless này chính là thứ giúp ta scale ngang dễ dàng: request có thể rơi vào bất kỳ instance Node nào sau load balancer, không cần "dính" một server cố định (trừ khi dùng session in-memory — khi đó cần sticky session hoặc store dùng chung).

⚠️ Lỗi thường gặp & Best practices

🚫 Quên res.end()

Response không đóng → client treo tới timeout. Mọi nhánh xử lý phải kết thúc response đúng một lần.

🚫 JSON.parse không try/catch

Body hỏng làm crash cả process. Luôn bọc try/catch và trả 400.

🚫 Không giới hạn body

Kẻ xấu gửi payload khổng lồ làm cạn RAM. Đặt limit, trả 413.

🚫 Set header sau khi gửi body

ERR_HTTP_HEADERS_SENT. Set status + header TRƯỚC khi write.

🚫 Dùng str.length cho Content-Length

Sai với UTF-8 nhiều byte. Dùng Buffer.byteLength.

🚫 Trả 200 cho cả lỗi

Status code phải phản ánh đúng kết quả để client xử lý đúng (retry, hiện lỗi).

🚫 Allow-Origin: * + credentials

Bị browser chặn và là rủi ro bảo mật. Dùng whitelist origin.

✅ Tách lớp sớm

Khi route > vài cái, chuyển sang Express/Fastify thay vì if/else tay.

🧪 Bài tập

🧪 Bài 1 — Mini REST API không framework

Dùng module http thuần, viết server hỗ trợ: GET /api/tickets (trả mảng), POST /api/tickets (tạo ticket từ JSON body, validate subject), GET /api/tickets/:id. Trả đúng status code (200/201/400/404) và Content-Type: application/json.

Gợi ý

Dùng new URL(req.url, 'http://'+req.headers.host) để lấy pathname; match :id bằng regex /^\/api\/tickets\/(\w+)$/. Tái sử dụng hàm readJsonBody và sendJson ở phần ④. Lưu ticket vào một Map trong bộ nhớ. Nhớ nhánh cuối trả 404.

🧪 Bài 2 — Chặn payload & JSON hỏng

Mở rộng POST /api/tickets: nếu body > 100KB trả 413; nếu JSON sai cú pháp trả 400 với thông báo rõ ràng, và server không được crash. Tự test bằng curl gửi JSON hỏng và file lớn.

Gợi ý

Đếm size += chunk.length trong sự kiện 'data', vượt limit thì reject + req.destroy(). Bọc JSON.parse trong try/catch. Gán err.status để hàm xử lý lỗi chọn đúng code. Test: curl -X POST -d '{bad json' http://localhost:3000/api/tickets.

🧪 Bài 3 — Bật CORS cho app agent

Thêm CORS cho phép origin https://agent.app gọi API: xử lý preflight OPTIONS trả 204, cho phép method POST/PATCH và header Authorization. Giải thích vì sao gọi từ localhost:5173 (Vite dev) sẽ bị chặn.

Gợi ý

Đặt Access-Control-Allow-Origin khớp req.headers.origin nếu nằm trong whitelist; thêm Allow-Methods, Allow-Headers. Trả lời OPTIONS sớm bằng 204. localhost:5173 bị chặn vì không nằm trong danh sách origin cho phép → thêm nó vào whitelist khi dev.

Ngân hàng câu hỏi phỏng vấn

HTTP & REST nền tảng — hỏi để đo mức độ hiểu "dưới capo" của framework.

Q1Dựng HTTP server bằng module http thuần như thế nào?Junior›

Trả lời: Dùng http.createServer((req, res) => {...}) truyền một request listener, rồi gọi server.listen(port). Mỗi request đến, listener nhận req (IncomingMessage, readable stream chứa dữ liệu khách gửi) và res (ServerResponse, writable stream để trả về). Ghi response bằng res.writeHead(code, headers) rồi res.end(body). Mọi framework đều xây trên module này.

Q2Phân biệt HTTP và HTTPS.Junior›

Trả lời: HTTPS = HTTP chạy trên lớp TLS/SSL (cổng 443 mặc định). Nó mã hóa toàn bộ dữ liệu giữa client và server, xác thực danh tính server qua chứng chỉ, và đảm bảo toàn vẹn dữ liệu (chống sửa giữa đường). HTTP thường (cổng 80) gửi plaintext — ai bắt gói tin cũng đọc được. Với Contact Center mang token đăng nhập và nội dung cuộc gọi/chat nhạy cảm, HTTPS là bắt buộc ở production.

⚠️ Bẫy: HTTPS không tự xác thực người dùng — nó bảo vệ kênh truyền. Auth (token/cookie) vẫn cần riêng.

Q3Làm sao đọc body của POST request trong Node thuần?Middle›

Trả lời: Vì req là readable stream, body không có ngay. Phải lắng nghe sự kiện 'data' để gom các chunk (Buffer) vào một mảng, đếm tổng kích thước; khi 'end' bắn ra thì Buffer.concat(chunks).toString('utf8') rồi JSON.parse (bọc try/catch). Cần giới hạn kích thước để chống payload khổng lồ và xử lý sự kiện 'error'.

⚠️ Bẫy: quên try/catch quanh JSON.parse → JSON hỏng làm crash process. Và req.body chỉ tồn tại khi có middleware như express.json().

Q4Kể các nhóm status code và cho ví dụ.Junior›

Trả lời: 5 nhóm theo chữ số đầu: 1xx thông tin (101 nâng cấp WebSocket); 2xx thành công (200 OK, 201 Created, 204 No Content); 3xx chuyển hướng/cache (301 Moved, 304 Not Modified); 4xx lỗi client (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 429 Too Many Requests); 5xx lỗi server (500 Internal, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout).

Q5Khác nhau giữa 401, 403 và 409?Middle›

Trả lời: 401 Unauthorized: chưa xác thực (thiếu/hết hạn token) — cần đăng nhập. 403 Forbidden: đã xác thực nhưng không đủ quyền (vd agent cố mở dashboard supervisor). 409 Conflict: trạng thái tài nguyên xung đột với thao tác (vd hai agent cùng nhận một ticket). Mỗi mã dẫn client tới một xử lý khác nhau, nên không được trả nhầm.

⚠️ Bẫy: tên là "Unauthorized" nhưng 401 thực ra là "chưa xác thực"; "không đủ quyền" mới là 403.

Q6Vì sao header Content-Type quan trọng?Junior›

Trả lời: Nó cho client/server biết body là kiểu gì để parse đúng: application/json thì parse JSON, text/html thì render, application/x-www-form-urlencoded hay multipart/form-data cho form/upload. Nếu server trả JSON nhưng đặt text/plain, trình duyệt có thể không parse; nếu client gửi sai Content-Type, middleware như express.json() bỏ qua khiến req.body rỗng.

Q7CORS là gì? Preflight hoạt động ra sao?Middle›

Trả lời: CORS là cơ chế của trình duyệt, dựa trên Same-Origin Policy: trang ở origin A không được đọc response từ API origin B trừ khi B trả các header Access-Control-Allow-Origin/Methods/Headers. Với request "không đơn giản" (PUT/PATCH/DELETE, header tùy chỉnh, JSON), browser gửi trước một preflight OPTIONS; nếu server đáp ứng quyền (và có thể cache qua Access-Control-Max-Age), browser mới gửi request thật.

⚠️ Bẫy: CORS chỉ áp dụng trong browser — gọi từ server-to-server hay curl không bị CORS. Nó cũng không phải cơ chế bảo mật xác thực.

Q8Vì sao nên dùng Express thay vì http thuần?Middle›

Trả lời: http thuần bắt bạn tự làm tất cả: match path động bằng regex, phân biệt 404/405, gom body và parse, parse query, và lặp lại logic chung (auth, log, CORS) cho mọi route. Khi có hàng trăm route, code rối, dễ sai, khó test. Express cung cấp router với param (req.params.id), middleware chuỗi qua next(), body parser, req.query sẵn — gọn và chuẩn hơn. Hiểu http thuần giúp biết Express che giấu gì.

Q9HTTP keep-alive là gì? Vì sao quan trọng?Middle›

Trả lời: Keep-alive (mặc định ở HTTP/1.1) giữ kết nối TCP mở sau khi hoàn thành một request để tái sử dụng cho request tiếp theo, thay vì bắt tay TCP (và TLS) lại từ đầu mỗi lần. Điều này giảm độ trễ và tải đáng kể khi một agent app bắn nhiều request liên tục. Header Connection: keep-alive và Keep-Alive: timeout=... điều khiển hành vi này.

⚠️ Bẫy: HTTP/1.1 vẫn bị "head-of-line blocking" — một kết nối xử lý tuần tự từng request; HTTP/2 multiplexing mới giải quyết triệt để.

Q10Statelessness của HTTP nghĩa là gì? Liên hệ với scale.Senior›

Trả lời: HTTP không nhớ trạng thái giữa các request — mỗi request độc lập, server không tự biết request đến từ phiên nào trừ khi client gửi kèm token/cookie. Tính stateless này cho phép scale ngang dễ: request có thể rơi vào bất kỳ instance Node nào sau load balancer mà vẫn xử lý đúng. Hệ quả thiết kế: tránh lưu session in-memory trên từng instance (sẽ phải dùng sticky session hoặc store dùng chung như Redis); với realtime/WebSocket cần chú ý vì kết nối là stateful, thường cần adapter (Redis pub/sub) để các instance chia sẻ sự kiện.

Q11So sánh sơ lược HTTP/1.1 và HTTP/2.Senior›

Trả lời: HTTP/1.1 dạng text, một kết nối xử lý request tuần tự (keep-alive tái dùng kết nối nhưng vẫn head-of-line blocking), header lặp lại không nén. HTTP/2 dạng nhị phân, hỗ trợ multiplexing (nhiều request/response song song trên một kết nối TCP), nén header (HPACK), server push, ưu tiên stream — giảm độ trễ rõ rệt khi tải nhiều tài nguyên. Trade-off: vẫn dính TCP head-of-line ở tầng dưới (mất gói chặn cả kết nối), điều mà HTTP/3 (QUIC trên UDP) khắc phục.

Q12Một API tạo ticket nên trả status và header gì để đúng REST?Senior›

Trả lời: Tạo thành công trả 201 Created, kèm header Location trỏ tới URL tài nguyên mới (vd /api/tickets/abc123) và body chứa ticket vừa tạo. Body sai/thiếu trường → 400; chưa auth → 401; không đủ quyền → 403; trùng (idempotency key đã dùng) → 409; quá tải/limit → 429/503. Đặt Content-Type: application/json và cân nhắc idempotency key để client retry an toàn không tạo ticket trùng.

⚠️ Bẫy: trả 200 cho mọi thứ (kể cả tạo mới hay lỗi) là phản REST — client mất khả năng phản ứng đúng theo status.
