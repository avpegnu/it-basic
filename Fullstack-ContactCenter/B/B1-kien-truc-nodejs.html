Kiến trúc Node.js

Hiểu bên dưới nắp capo của Node.js: V8, libuv, các pha Event Loop, thread pool và process. Đây là kiến thức phân biệt người "biết viết Express" với người thực sự hiểu vì sao hệ thống realtime của mình nhanh hay chậm, treo hay mượt.

🎯 Học xong chương này bạn sẽ

• Giải thích Node.js là runtime, gồm V8 + libuv + Node API — không phải ngôn ngữ hay framework.

• Mô tả 6 pha của Event Loop trong Node và việc gì chạy ở pha nào.

• Hiểu libuv thread pool, vì sao một số tác vụ "I/O" lại dùng thread.

• Dùng process (env, argv, signals) và biết Worker Threads vs cluster vs child_process.

① Node.js là gì?

Node.js là một runtime cho phép chạy JavaScript ngoài trình duyệt — trên server. Nó không phải ngôn ngữ (ngôn ngữ vẫn là JavaScript) và không phải framework (Express/NestJS mới là framework).

⚡ V8

Engine của Google (cũng dùng trong Chrome) — biên dịch JS sang mã máy, quản lý bộ nhớ/GC.

🔁 libuv

Thư viện C cung cấp Event Loop, non-blocking I/O, thread pool — "trái tim" bất đồng bộ.

📦 Node APIs

fs, http, net, crypto... — API bằng C++/JS để thao tác hệ thống.

② Kiến trúc tổng thể

Khi bạn gọi fs.readFile, hành trình diễn ra qua nhiều tầng:

Code JS của bạn→ Node API (JS)→ C++ bindings→ libuv (Event Loop + thread pool)→ OS / kernel
💡 Mấu chốt

V8 thực thi JavaScript của bạn (đơn luồng). libuv lo phần bất đồng bộ: đăng ký I/O với OS, quản lý hàng đợi callback, và có một thread pool để xử lý các tác vụ không có API non-blocking gốc của OS (vd fs, crypto, DNS).

③ Các pha của Event Loop (Node)

Event Loop của Node (qua libuv) chạy theo các pha tuần tự, mỗi pha có hàng đợi callback riêng:

#PhaXử lý gì
1timersCallback của setTimeout, setInterval đã tới hạn
2pending callbacksMột số callback I/O bị hoãn từ vòng trước
3idle, prepareNội bộ libuv
4pollLấy I/O event mới, thực thi callback I/O (đây là nơi "chờ" nếu rảnh)
5checkCallback của setImmediate
6close callbackssocket.on('close')...
⚠️ microtask chen giữa các pha

Giữa mỗi callback, Node vét sạch process.nextTick queue rồi tới microtask Promise. Vì vậy nextTick > Promise > (các macrotask theo pha). Xem lại chương A2.

④ libuv & Thread Pool

Một hiểu lầm phổ biến: "Node hoàn toàn đơn luồng". Đúng là code JS chạy đơn luồng, nhưng libuv có thread pool (mặc định 4 thread, đổi qua UV_THREADPOOL_SIZE) để xử lý các tác vụ không thể non-blocking ở tầng OS.

🧵 Dùng thread pool

fs.* (file I/O), crypto (pbkdf2, bcrypt), zlib (nén), DNS lookup.

🌐 Không dùng thread pool

Network I/O (TCP/UDP/HTTP) dùng cơ chế non-blocking gốc của OS (epoll/kqueue/IOCP).

🐛 Hệ quả thực tế cho Contact Center

Nếu mỗi cuộc gọi cần hash mật khẩu/băm bản ghi nặng (CPU + crypto), bạn có thể làm cạn 4 thread của pool → các thao tác fs/crypto khác bị xếp hàng. Giải pháp: tăng UV_THREADPOOL_SIZE, hoặc đẩy việc nặng sang Worker Threads / message queue.

⑤ process & global objects

Trong Node không có window/document. Thay vào đó có global, và quan trọng nhất là object process — cầu nối với môi trường runtime.

process.jsNode.js
process.env.NODE_ENV;        // biến môi trường (config)
process.argv;                // tham số dòng lệnh
process.pid;                 // process id
process.cwd();               // thư mục làm việc
process.memoryUsage();       // theo dõi RAM

// Graceful shutdown — đóng kết nối DB/socket trước khi tắt
process.on('SIGTERM', async () => {
  await closeDbAndSockets();
  process.exit(0);
});

// Bắt lỗi không lường trước — log rồi tắt an toàn
process.on('unhandledRejection', (err) => { log(err); process.exit(1); });

// __dirname / __filename (CommonJS) — đường dẫn file hiện tại
console.log(__dirname);

💡 Trong thực tế production

Thường người ta không tự viết cluster mà để PM2 hoặc Kubernetes chạy nhiều instance Node, đặt sau load balancer. Worker Threads dành cho CPU-bound trong cùng service. Việc nền (gửi email, xử lý ghi âm cuộc gọi) thì đẩy sang message queue (xem Part F).

⑦ Khi nào Node.js phù hợp?

✅ Rất hợp

Hệ thống I/O-bound, nhiều kết nối đồng thời: API, realtime (chat, call), streaming, microservices, BFF. Chính là hồ sơ của một Contact Center.

❌ Kém hợp

Tác vụ CPU-bound nặng kéo dài (xử lý video, ML training) — sẽ chặn Event Loop. Khi đó cần Worker Threads, ngôn ngữ khác, hoặc dịch vụ chuyên dụng.

⚠️ Lỗi thường gặp & Best practices

🚫 Chặn Event Loop

Vòng lặp tính toán lớn, JSON.parse file khổng lồ đồng bộ → treo server.

🚫 Dùng *Sync trong request

readFileSync trong handler chặn mọi request khác. Chỉ dùng lúc khởi động.

🚫 Bỏ qua graceful shutdown

Tắt đột ngột làm rớt cuộc gọi/mất dữ liệu. Luôn xử lý SIGTERM/SIGINT.

🚫 Rò rỉ bộ nhớ

Listener không gỡ, cache vô hạn → RAM tăng dần. Theo dõi memoryUsage.

🧪 Bài tập

🧪 Bài 1 — Đọc env an toàn

Viết hàm getEnv(key, fallback?) đọc process.env, ném lỗi nếu biến bắt buộc bị thiếu. Vì sao nên kiểm tra env lúc khởi động?

Gợi ý

Kiểm tra env khi boot để fail-fast: nếu thiếu config (DB_URL, JWT_SECRET) thì dừng ngay thay vì lỗi giữa lúc phục vụ khách. Dùng if (val == null && fallback === undefined) throw ....

🧪 Bài 2 — CPU-bound

Giải thích vì sao tính số Fibonacci(45) đệ quy trong một HTTP handler làm cả server treo, và 2 cách khắc phục.

Gợi ý

Vì nó chạy đồng bộ trên main thread, chiếm call stack lâu → Event Loop không xử lý request khác. Khắc phục: (1) Worker Threads, (2) đẩy sang queue/worker riêng, (3) thuật toán/cache tốt hơn.

Ngân hàng câu hỏi phỏng vấn

Kiến trúc Node — hay được hỏi để đánh giá chiều sâu.

Q1Node.js là gì? Gồm những thành phần nào?Junior›

Trả lời: Node.js là runtime để chạy JavaScript phía server, xây trên engine V8 (thực thi JS) và libuv (Event Loop, non-blocking I/O, thread pool), kèm bộ Node API (fs, http, net, crypto...). Nó hướng sự kiện và non-blocking, hợp cho ứng dụng I/O-bound.

Q2Node single-thread hay multi-thread? Giải thích.Middle›

Trả lời: Code JavaScript của bạn chạy trên một luồng (Event Loop). Nhưng libuv có thread pool (mặc định 4) cho một số tác vụ như fs, crypto, zlib, DNS. Ngoài ra có thể tự mở rộng bằng Worker Threads, cluster, child_process. Network I/O không dùng thread pool mà dùng cơ chế non-blocking của OS.

⚠️ Bẫy: nói "hoàn toàn đơn luồng" là sai — chỉ tầng JS đơn luồng.

Q3Các pha của Event Loop trong Node là gì?Senior›

Trả lời: 6 pha lặp tuần tự: timers (setTimeout/Interval), pending callbacks, idle/prepare (nội bộ), poll (I/O), check (setImmediate), close callbacks. Giữa mỗi callback, Node vét nextTick queue rồi microtask Promise. Hiểu pha giúp giải thích thứ tự setImmediate vs setTimeout, vì sao nextTick ưu tiên.

Q4UV_THREADPOOL_SIZE là gì? Khi nào cần chỉnh?Senior›

Trả lời: Là số thread trong thread pool của libuv (mặc định 4). Khi app làm nhiều fs/crypto/zlib song song, pool có thể trở thành nút cổ chai — tăng size (giới hạn ~ số core) có thể cải thiện. Nhưng tăng vô tội vạ gây tranh chấp CPU; tốt hơn là giảm tải hoặc dùng Worker/queue.

Q5Phân biệt Worker Threads, cluster, child_process.Middle›

Trả lời: Worker Threads: nhiều luồng trong 1 process, hợp CPU-bound, có thể chia sẻ bộ nhớ. cluster: fork nhiều process Node cùng nghe 1 port để tận dụng nhiều core (web server). child_process: chạy tiến trình con bất kỳ (kể cả lệnh ngoài), giao tiếp qua IPC. Production thường dùng PM2/K8s nhân bản process thay vì tự viết cluster.

Q6Vì sao Node hợp cho hệ thống realtime nhưng kém với CPU-bound?Middle›

Trả lời: Mô hình non-blocking + Event Loop cho phép một luồng phục vụ hàng nghìn kết nối I/O-bound (chat, call, DB) hiệu quả. Nhưng tác vụ CPU-bound chạy đồng bộ sẽ chiếm luồng và chặn Event Loop, làm mọi request khác bị treo. Vì vậy phải tách CPU-bound ra Worker/queue.

Q7Graceful shutdown là gì? Vì sao quan trọng với Contact Center?Middle›

Trả lời: Là quy trình tắt service có kiểm soát: ngừng nhận kết nối mới, hoàn tất request đang xử lý, đóng DB/WebSocket/queue, rồi mới exit. Lắng nghe SIGTERM/SIGINT. Với Contact Center, tắt đột ngột làm rớt cuộc gọi đang diễn ra, mất tin nhắn chưa lưu — graceful shutdown giảm thiểu mất mát khi deploy/scale.

Q8Giải thích pha poll trong Event Loop. Khi poll queue rỗng thì điều gì xảy ra?Senior›

Trả lời: Pha poll là nơi Event Loop lấy và thực thi các callback I/O đã sẵn sàng. Nếu poll queue rỗng: nếu có setImmediate đang chờ, loop chuyển sang pha check; nếu không và có timer sắp tới hạn, loop quay lại pha timers; nếu không có gì, loop có thể chặn (block) tại poll chờ I/O mới tới (đây chính là lúc tiến trình "ngủ" thay vì quay vòng tốn CPU).

Q9Phân biệt concurrency và parallelism trong ngữ cảnh Node.js.Middle›

Trả lời: Concurrency là xử lý nhiều việc xen kẽ trên một luồng (Event Loop luân phiên giữa các tác vụ I/O — Node rất giỏi việc này). Parallelism là thực thi đồng thời thật sự trên nhiều core/luồng. Node đạt concurrency cao nhờ non-blocking I/O, nhưng để parallelism thật cho CPU-bound thì cần Worker Threads, cluster hoặc nhiều tiến trình.

Q10Một endpoint khiến TOÀN BỘ server chậm đột ngột. Bạn nghi gì và debug Event Loop ra sao?Senior›

Trả lời: Nghi ngờ hàng đầu là chặn Event Loop (tác vụ CPU-bound đồng bộ: vòng lặp lớn, JSON.parse payload khổng lồ, regex thảm họa, mã hóa đồng bộ) hoặc cạn libuv thread pool (nhiều fs/crypto song song). Cách debug: đo event loop lag (perf_hooks.monitorEventLoopDelay), profiling bằng --prof / clinic.js / flame graph, kiểm tra UV_THREADPOOL_SIZE, và rà các lời gọi *Sync trong đường xử lý request. Khắc phục: đẩy việc nặng sang Worker/queue, dùng API bất đồng bộ, chia nhỏ tác vụ.

⚠️ Bẫy: nếu chỉ một endpoint chậm còn endpoint khác vẫn nhanh thì thường là I/O chậm của riêng nó (DB query, API ngoài); còn khi MỌI endpoint cùng chậm mới là dấu hiệu Event Loop bị chặn.
