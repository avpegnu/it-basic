Module system, npm & môi trường

Hiểu sâu hệ module của Node, cách npm quản lý phụ thuộc, semver, lockfile và cấu hình môi trường chuẩn 12-factor cho một service Contact Center.

🎯 Học xong chương này bạn sẽ

• Phân biệt rõ CommonJS và ESM: cú pháp, thời điểm phân giải, caching và circular dependency.

• Mô tả cơ chế phân giải module của Node — từ core module, file, đến leo lên node_modules.

• Đọc/viết package.json chuẩn, phân biệt dependencies / devDependencies / peerDependencies.

• Hiểu semver (^, ~, exact), vai trò package-lock.json và vì sao CI dùng npm ci.

• Cấu hình môi trường chuẩn 12-factor: process.env, dotenv, validate fail-fast lúc boot.

• Đánh giá rủi ro chuỗi cung ứng và dùng npm audit để giữ dependency an toàn.

💡 Liên hệ thực tế — vì sao chương này quan trọng với Contact Center

Một service Contact Center điển hình (gateway WebSocket cho agent, service định tuyến cuộc gọi, worker xử lý ticket) phụ thuộc vào hàng trăm package: driver DB, client Redis, thư viện SIP/WebRTC, SDK telephony. Chỉ cần một bản nâng cấp ^ "vô hại" kéo theo breaking change, hoặc một package bị nhiễm mã độc trong chuỗi cung ứng, là cả tổng đài có thể rớt cuộc gọi giữa giờ cao điểm. Quản lý module & dependency chặt chẽ chính là tuyến phòng thủ đầu tiên cho độ ổn định realtime.

① Module: CommonJS vs ESM

Node hỗ trợ hai hệ module song song: CommonJS (CJS) — hệ "cổ điển" có từ ngày đầu của Node, và ECMAScript Modules (ESM) — chuẩn chính thức của ngôn ngữ JavaScript. Hiểu khác biệt giữa chúng là điều bắt buộc vì bạn sẽ gặp cả hai trong mọi codebase thực tế.

1.1 CommonJS — require / module.exports

CJS dùng require() để nạp module và module.exports để xuất. Đặc điểm cốt lõi: nạp đồng bộ (synchronous) và phân giải tại thời điểm chạy (runtime) — nghĩa là require có thể nằm trong if, trong hàm, được gọi với đường dẫn tính toán động.

callRouter.jsCommonJS
// Xuất bằng module.exports (gán cả object)
function routeCall(call) { /* ... chọn agent rảnh ... */ }
module.exports = { routeCall };

// hoặc gán từng phần qua exports (alias của module.exports)
exports.maxRetries = 3;
gateway.jsCommonJS
const { routeCall } = require('./callRouter');
const redis = require('ioredis');          // package từ node_modules
const fs = require('fs');                  // core module

// require ĐỘNG — chỉ nạp adapter telephony khi cần (lazy load)
if (process.env.PROVIDER === 'sip') {
  const sip = require('./adapters/sip');
}

1.2 Hai cơ chế quan trọng: exports vs module.exports

Một bẫy kinh điển: exports chỉ là một biến tham chiếu trỏ tới module.exports. Nếu bạn gán lại exports = ... thì nó chỉ đổi biến cục bộ, không đổi giá trị thật mà Node trả về. Luôn nhớ: cái Node trả về cho require là module.exports.

⚠️ Sai lầm hay gặp

exports = function(){} → module trả về {} rỗng. Muốn xuất một hàm/đối tượng duy nhất, phải viết module.exports = function(){}.

1.3 Module caching

Node cache module sau lần require đầu tiên. Lần thứ hai trở đi, require trả về chính object đã cache trong require.cache (key là đường dẫn tuyệt đối đã phân giải) — code module không chạy lại. Đây là nền tảng cho pattern singleton rất hữu ích.

dbPool.jsNode.js
// File này chạy ĐÚNG MỘT LẦN dù được require ở 50 nơi
const { Pool } = require('pg');
const pool = new Pool({ connectionString: process.env.DB_URL });

console.log('Pool DB khởi tạo (chỉ in 1 lần)');
module.exports = pool;   // mọi nơi dùng chung 1 connection pool — singleton
💡 Ứng dụng Contact Center

Connection pool DB, client Redis, instance logger, hay registry các agent đang online — đều nên là singleton qua module cache. Nếu mỗi request tự tạo pool mới, bạn sẽ nhanh chóng làm cạn kết nối DB.

1.4 Circular dependency (phụ thuộc vòng)

Khi A.js require B.js mà B.js lại require A.js, ta có vòng phụ thuộc. Node không treo, nhưng xử lý theo cách nguy hiểm âm thầm: module đang nạp dở sẽ trả về exports chưa hoàn chỉnh (đúng những gì đã gán tới thời điểm đó).

agent.js ↔ ticket.jsCircular
// agent.js
const ticket = require('./ticket');   // lúc này ticket.exports CÓ THỂ rỗng
exports.assign = (t) => ticket.close(t);  // gọi LÚC RUNTIME → ok

// ticket.js
const agent = require('./agent');
console.log(agent.assign);  // có thể là undefined nếu chạy lúc nạp!
exports.close = (t) => { /* ... */ };
🐛 Tại sao đáng sợ

Nếu bạn dùng giá trị từ module kia ngay lúc nạp (top-level), bạn có thể nhận undefined → lỗi x is not a function khó truy. Nếu chỉ dùng trong hàm (gọi lúc runtime, sau khi mọi module đã nạp xong) thì thường an toàn. Cách chữa tận gốc: tách phần dùng chung ra module thứ ba, hoặc đảo lại thiết kế để bỏ vòng.

1.5 ESM — import / export

ESM là chuẩn của ngôn ngữ. Khác biệt then chốt so với CJS:

  • Tĩnh (static): import phải ở top-level, được phân giải lúc biên dịch/parse, không thể đặt trong if. Nhờ vậy bundler làm được tree-shaking (loại bỏ code chết).
  • Bất đồng bộ: đồ thị module được nạp async; hỗ trợ top-level await.
  • Live binding: import là tham chiếu sống tới biến được export, không phải bản sao giá trị.
queue.mjsESM
// Named export & default export
export function enqueue(call) { /* ... */ }
export const MAX_WAIT = 120;
export default class CallQueue { /* ... */ }

// gateway.mjs
import CallQueue, { enqueue, MAX_WAIT } from './queue.mjs';
import { readFile } from 'node:fs/promises';  // core module dùng prefix node:

// top-level await — chỉ ESM mới có
const cfg = await readFile('./routing.json', 'utf8');

1.6 Bật ESM & interop với CJS

Node quyết định một file là CJS hay ESM theo quy tắc:

Tín hiệuKết quả
Đuôi .mjsLuôn là ESM
Đuôi .cjsLuôn là CommonJS
"type": "module" trong package.jsonFile .js được coi là ESM
Mặc định (không có type)File .js là CommonJS
⚠️ Interop — các luật đau đầu

• Từ ESM có thể import module CJS: module.exports sẽ thành default export (đôi khi cả named export nhờ phân tích tĩnh, nhưng không bảo đảm).

• Từ CJS không dùng được require() cho package "ESM-only" (vì require đồng bộ còn ESM async) — phải dùng const m = await import('pkg') (dynamic import).

• ESM không có __dirname, __filename, require, module. Thay bằng import.meta.url + fileURLToPath.

② Cơ chế phân giải module

Khi bạn viết require('x') hay import 'x', Node phải biến chuỗi 'x' thành một file cụ thể trên đĩa. Quy trình này gọi là module resolution. Hiểu nó giúp bạn debug lỗi Cannot find module và biết package thực sự được nạp từ đâu.

2.1 Ba loại định danh

🧩 Core module

fs, path, http, crypto... Node nhận diện ngay, có ưu tiên cao nhất. Prefix node: ép buộc dùng core.

📁 Đường dẫn tương đối

Bắt đầu bằng ./, ../ hoặc / → tìm file ngay tại vị trí đó.

📦 Package (bare)

'ioredis', 'express'... → tìm trong node_modules, leo dần lên cây thư mục.

2.2 Thuật toán phân giải (rút gọn)

Là core module?→ Bắt đầu ./ / ?→ Tìm node_modules leo lên→ Khớp file / thư mục→ Lỗi MODULE_NOT_FOUND

Với đường dẫn file, Node thử lần lượt:

  1. Đúng tên file: ./callRouter → callRouter.js
  2. Thêm đuôi: .js → .json → .node
  3. Nếu là thư mục: đọc package.json của thư mục đó, lấy field main (hoặc exports)
  4. Không có main → thử index.js, index.json...

2.3 Cơ chế "leo lên" node_modules

Với package bare như require('ioredis') từ file /app/services/gateway/index.js, Node tìm theo thứ tự:

resolution-ordernode_modules lookup
/app/services/gateway/node_modules/ioredis   // 1. gần nhất
/app/services/node_modules/ioredis           // 2. leo lên 1 cấp
/app/node_modules/ioredis                    // 3. gốc project (hay gặp nhất)
/node_modules/ioredis                        // 4. tới root hệ thống
// hết → throw Error [MODULE_NOT_FOUND]
💡 Vì sao điều này quan trọng trong monorepo

Trong monorepo Contact Center (gateway, routing-service, ticket-worker chung một repo), cơ chế leo lên cho phép hoisting: các package chung được đặt ở node_modules gốc, mỗi service chỉ giữ riêng package có version đặc thù. Đây chính là nền tảng của npm workspaces.

2.4 Field main vs exports

Trong package.json của một package:

  • "main": entry point cổ điển (vd "dist/index.js"). Mọi đường dẫn con của package đều truy cập được.
  • "exports": bản đồ chính xác những gì package cho phép import — gọi là encapsulation. Có thể định nghĩa entry khác nhau cho CJS và ESM (conditional exports).
package.json (của package)exports map
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",   // khi ESM import
      "require": "./dist/index.cjs"    // khi CJS require
    },
    "./adapters/sip": "./dist/sip.js"  // chỉ cho phép import path này
  }
}
⚠️ Bẫy "exports" chặn deep import

Nếu package khai báo exports, bạn không thể import file nội bộ không liệt kê (vd require('pkg/lib/internal') sẽ lỗi ERR_PACKAGE_PATH_NOT_EXPORTED) — kể cả file đó tồn tại. Đây là tính năng, không phải bug.

③ npm & package.json

npm (Node Package Manager) gồm 3 thứ: một CLI, một registry (kho package online) và một chuẩn manifest là package.json. Đây là "tờ khai" mô tả project: tên, version, scripts, và quan trọng nhất — cây phụ thuộc.

3.1 Cấu trúc package.json

package.jsoncontact-center gateway
{
  "name": "cc-gateway",            // tên (lowercase, kebab-case)
  "version": "2.4.1",             // theo semver
  "type": "module",               // bật ESM cho file .js
  "main": "src/index.js",        // entry point
  "engines": { "node": ">=20" },  // chốt version Node
  "scripts": {
    "start": "node src/index.js",
    "dev": "node --watch src/index.js",
    "test": "vitest run"
  },
  "dependencies": {        // CẦN khi chạy production
    "socket.io": "^4.7.0",
    "ioredis": "^5.3.2",
    "pg": "^8.11.0"
  },
  "devDependencies": {     // CHỈ cần khi dev/build/test
    "vitest": "^1.4.0",
    "eslint": "^9.0.0"
  }
}

3.2 Ba loại phụ thuộc

LoạiKhi nào càiVí dụ Contact Center
dependenciesCần để chạy production. Luôn được cài.socket.io, ioredis, pg, SDK telephony
devDependenciesChỉ cần lúc dev/test/build. Bị bỏ qua với npm install --production / NODE_ENV=production.vitest, eslint, typescript, nodemon
peerDependenciesPackage của bạn yêu cầu host cung cấp, không tự cài. Tránh trùng bản.Một plugin Socket.IO khai báo socket.io là peer
🐛 Đặt nhầm chỗ = lỗi production

Để nhầm một runtime dependency (vd dotenv) vào devDependencies → build production tối ưu bỏ qua nó → service crash ngay khi boot vì Cannot find module 'dotenv'. Quy tắc vàng: thứ gì code require/import lúc chạy phải nằm trong dependencies.

3.3 peerDependencies — vì sao tồn tại

Hình dung một plugin định tuyến dành cho framework gateway của bạn. Plugin cần dùng đúng cùng một instance của framework mà ứng dụng đang chạy — nếu plugin tự cài bản riêng, sẽ có hai instance khác nhau trong bộ nhớ, state không chia sẻ, gây bug khó hiểu (vd hai registry agent tách biệt). peerDependencies giải quyết: plugin tuyên bố "tôi cần host có framework ^4", host chịu trách nhiệm cung cấp một bản duy nhất.

④ Versioning & semver

Semantic Versioning (semver) là quy ước đánh số MAJOR.MINOR.PATCH mang ý nghĩa rõ ràng — giúp bạn biết một bản nâng cấp có an toàn hay không chỉ bằng cách nhìn số.

PhầnTăng khiÝ nghĩa
MAJOR (X.0.0)Có breaking changeNâng cấp có thể làm hỏng code của bạn — phải đọc changelog
MINOR (0.X.0)Thêm tính năng, tương thích ngượcAn toàn nâng cấp
PATCH (0.0.X)Sửa lỗi, tương thích ngượcAn toàn, nên nâng

4.1 Range: caret ^ vs tilde ~ vs exact

Trong package.json, số version thường đi kèm ký hiệu range quy định npm được phép nâng tới đâu khi cài:

Khai báoCho phépKhoảng (với 4.7.2)
^4.7.2 (caret)Nâng MINOR + PATCH, giữ nguyên MAJOR>= 4.7.2 và < 5.0.0
~4.7.2 (tilde)Chỉ nâng PATCH, giữ MAJOR + MINOR>= 4.7.2 và < 4.8.0
4.7.2 (exact)Cố định tuyệt đốiĐúng 4.7.2
* / latestBất kỳ — RẤT NGUY HIỂMMọi version
⚠️ Đặc thù version 0.x

Với version 0.y.z (chưa "ổn định"), ^0.5.3 chỉ cho phép tới < 0.6.0 — caret hành xử như tilde, vì semver coi mỗi bước MINOR ở 0.x là có thể breaking. Nhiều bug nâng cấp đến từ hiểu nhầm chỗ này.

💡 Mặc định npm và lựa chọn cho production

npm install pkg mặc định ghi ^. Với một gateway xử lý cuộc gọi trực tiếp, nhiều team thích pin chặt hơn (tilde hoặc exact) ở các package nhạy cảm để tránh một bản MINOR "vô tình" thay đổi hành vi realtime. Dù vậy, thứ thật sự đảm bảo tái lập là lockfile, không phải range.

4.2 package-lock.json — nguồn sự thật

Range trong package.json chỉ nói "tôi chấp nhận khoảng này". Còn version thực sự được cài là gì thì package-lock.json ghi lại — chính xác tới từng package con (transitive), kèm hash integrity để chống bị thay nội dung.

🐛 "Works on my machine"

Không có lockfile (hoặc không commit nó), hai lần npm install cách nhau vài ngày có thể cài hai cây phụ thuộc khác nhau (vì có bản PATCH mới). Hậu quả: code chạy ở máy dev nhưng vỡ ở CI/production. Luôn commit package-lock.json.

4.3 npm install vs npm ci

💡 Trong pipeline deploy Contact Center

Dockerfile build image cho service nên dùng npm ci --omit=dev: đảm bảo mọi lần build cho ra đúng cùng một cây phụ thuộc (deterministic), bỏ devDependencies cho image gọn nhẹ và giảm bề mặt tấn công. Dev mới dùng npm install khi thêm package.

⑤ Scripts & npx

Field scripts biến package.json thành task runner — cách chuẩn hóa các lệnh thường dùng để cả team gõ giống nhau.

5.1 npm scripts & lifecycle hooks

Ngoài script tự đặt, npm có các lifecycle hook chạy tự động theo vòng đời. Quan trọng là cặp pre* / post*: npm tự chạy prebuild trước build, và postbuild sau đó.

scriptspackage.json
"scripts": {
  "prestart": "node scripts/check-env.js",   // tự chạy TRƯỚC start
  "start":    "node src/index.js",
  "lint":     "eslint src",
  "test":     "vitest run",
  "migrate":  "node-pg-migrate up"
}
// Gọi: npm run lint  |  npm start  |  npm test (start/test/install có alias)
// Truyền cờ: npm run test -- --coverage
🐛 Cảnh báo bảo mật: lifecycle install hooks

Hook preinstall/postinstall của package phụ thuộc chạy tự động khi cài — đây là vector tấn công supply chain phổ biến (mã độc chạy ngay lúc npm install). Trong CI nhạy cảm có thể cân nhắc npm ci --ignore-scripts rồi chạy build thủ công.

5.2 npx — chạy package không cần cài global

npx thực thi binary của một package: nếu đã có trong node_modules/.bin thì dùng luôn, nếu chưa thì tải tạm rồi chạy. Lợi ích: không "ô nhiễm" global, luôn dùng đúng version dự án.

npx-usageshell
npx create-vite cc-dashboard       # scaffold không cần cài trước
npx prisma migrate dev             # chạy CLI từ devDependency của dự án
npx -p typescript tsc --noEmit     # chạy 1 lần với version chỉ định

5.3 Workspaces (monorepo)

npm workspaces cho phép một repo chứa nhiều package liên quan (gateway, routing, ticket, shared-utils) dùng một node_modules gốc và một lockfile. Package nội bộ liên kết với nhau bằng symlink — sửa shared-utils là các service thấy ngay, không cần publish.

package.json (root)workspaces
{
  "name": "contact-center",
  "private": true,                // root không publish
  "workspaces": ["services/*", "packages/*"]
}
// Cài cho riêng 1 workspace:
//   npm install pg -w services/gateway
// Chạy script ở tất cả workspace:
//   npm run test --workspaces

⑥ Quản lý môi trường & config

Một service phải chạy ở nhiều môi trường: máy dev, staging, production. Cách bạn quản lý config (DB URL, secret, cổng, feature flag) quyết định độ an toàn và khả năng deploy.

6.1 Nguyên tắc 12-factor: config trong môi trường

Phương pháp 12-factor app nêu: "Lưu config trong môi trường (env vars), không hardcode trong code." Lý do:

  • Tách config khỏi code: cùng một artifact (image Docker) chạy được ở mọi môi trường, chỉ đổi env.
  • Bảo mật: secret (DB password, JWT key, token telephony) không bao giờ lọt vào git.
  • Linh hoạt: đổi cấu hình không cần build lại.

6.2 process.env & dotenv

Node đọc biến môi trường qua process.env (mọi giá trị đều là chuỗi). Lúc dev, gói dotenv nạp file .env vào process.env để khỏi phải set tay.

.env (KHÔNG commit)dotenv
NODE_ENV=development

REDIS_URL=redis://localhost:6379
JWT_SECRET=super-secret-change-me

⚠️ Quy tắc bắt buộc

• .env phải nằm trong .gitignore — không bao giờ commit secret.

• Commit một file mẫu .env.example (chỉ tên biến, không giá trị thật) để onboard dev mới.

• Production thật không dùng file .env mà inject env qua orchestrator (Kubernetes Secret, biến môi trường container). Node 20+ còn hỗ trợ node --env-file=.env sẵn, không cần gói dotenv.

6.3 Validate env lúc boot — fail-fast

Đây là một trong những best practice giá trị nhất. Thay vì để service crash giữa lúc phục vụ cuộc gọi vì thiếu một biến, hãy kiểm tra toàn bộ config ngay khi khởi động và dừng ngay nếu sai (fail-fast). Một module config tập trung, đã được ép kiểu và validate, là chuẩn mực.

config.jsfail-fast config
import { z } from 'zod';

// Khai báo schema: kiểu, bắt buộc, mặc định, ép kiểu
const schema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']),
  PORT: z.coerce.number().default(8080),       // string → number
  DB_URL: z.string().url(),                       // bắt buộc, đúng định dạng URL
  REDIS_URL: z.string().url(),
  JWT_SECRET: z.string().min(16),                  // chặn secret quá yếu
  MAX_AGENTS_PER_QUEUE: z.coerce.number().default(50)
});

const parsed = schema.safeParse(process.env);
if (!parsed.success) {
  console.error('❌ Config sai — dừng khởi động:', parsed.error.flatten().fieldErrors);
  process.exit(1);   // FAIL-FAST: thà chết lúc boot còn hơn giữa giờ cao điểm
}

export const config = parsed.data;  // đã typed & validate — phần code khác dùng yên tâm
💡 Quy ước dùng config

Phần còn lại của ứng dụng không bao giờ đọc process.env trực tiếp — luôn import từ module config này. Như vậy mọi biến đã được kiểm tra một chỗ, có gợi ý kiểu, và bạn không bị lỗi typo tên biến rải rác khắp codebase.

⑦ Bảo mật dependency

Một project Node trung bình kéo theo hàng nghìn package gián tiếp. Mỗi package là một mẩu code lạ chạy với quyền của service bạn — kể cả quyền đọc env có secret. Đây là supply chain risk: lỗ hổng không chỉ ở code bạn viết mà còn ở mọi dependency.

7.1 npm audit

npm audit đối chiếu cây phụ thuộc với cơ sở dữ liệu lỗ hổng đã biết và báo cáo mức độ (low → critical).

auditshell
npm audit                       # liệt kê lỗ hổng đã biết
npm audit --omit=dev            # chỉ quan tâm dependency chạy production
npm audit fix                   # tự nâng bản trong range an toàn
npm audit fix --force           # cho phép cả breaking change — CẨN THẬN
npm audit --audit-level=high    # chỉ fail CI khi có high/critical

7.2 Phòng thủ chuỗi cung ứng — checklist

🔒 Commit lockfile

Cố định cây phụ thuộc + hash integrity → chống bị thay nội dung package âm thầm.

🤖 npm ci trong CI

Cài tái lập, không tự nâng bản — phát hiện ngay khi lockfile lệch.

📉 Giảm số dependency

Mỗi package thêm vào là thêm rủi ro. Cân nhắc tự viết tiện ích nhỏ thay vì kéo cả thư viện.

⏳ Cẩn thận với bản mới ra

Tránh nâng ngay version vừa phát hành (typosquatting, package bị chiếm). Đợi cộng đồng kiểm chứng.

🚫 --ignore-scripts khi nghi ngờ

Chặn postinstall script độc hại chạy lúc cài trong môi trường nhạy cảm.

🔁 Bot cập nhật tự động

Dependabot/Renovate mở PR nâng bản đều đặn + chạy test → vá lỗ hổng có kiểm soát.

🐛 Vì sao đặc biệt nguy với Contact Center

Service tổng đài thường giữ secret nhạy cảm (token nhà mạng, khóa ghi âm, dữ liệu khách hàng — có thể là PII). Một package bị nhiễm trong cây phụ thuộc có thể đọc process.env và rò rỉ toàn bộ. Vì vậy kỷ luật dependency ở đây không phải "nice to have" mà là yêu cầu compliance.

⚠️ Lỗi thường gặp & Best practices

🚫 Gán lại exports

exports = {...} không xuất gì cả. Muốn xuất nguyên object phải dùng module.exports = ....

🚫 Dùng giá trị circular lúc nạp

Đọc export của module kia ở top-level khi có vòng → undefined. Chỉ dùng trong hàm, hoặc phá vòng.

🚫 Không commit lockfile

Mất tính tái lập, "works on my machine". Luôn commit package-lock.json.

🚫 Range quá lỏng (*, latest)

Một bản nâng cấp lén có thể phá production. Pin bằng range hợp lý + lockfile.

🚫 Đặt nhầm dependency vào devDeps

Build production bỏ qua → crash khi boot. Thứ chạy runtime phải ở dependencies.

🚫 Đọc process.env khắp nơi

Khó kiểm soát, dễ typo. Tập trung vào một module config đã validate.

🚫 Commit file .env

Rò rỉ secret vĩnh viễn trong git history. Phải .gitignore + xoay vòng secret nếu lỡ.

🚫 install trong CI thay vì ci

CI có thể tự nâng bản, cài không xác định. Dùng npm ci cho build/deploy.

🧪 Bài tập

🧪 Bài 1 — Giải mã semver range

Cho khai báo "ioredis": "^5.3.2" và "pg": "~8.11.0". Với mỗi bản phát hành mới sau đây, npm có cài tự động khi chạy lại không (giả sử không có lockfile)? ioredis 5.9.0, ioredis 6.0.0, pg 8.11.5, pg 8.12.0.

Gợi ý

^5.3.2 = >=5.3.2 <6.0.0 → ioredis 5.9.0 CÓ, 6.0.0 KHÔNG (đổi MAJOR). ~8.11.0 = >=8.11.0 <8.12.0 → pg 8.11.5 CÓ, 8.12.0 KHÔNG (đổi MINOR). Lưu ý: có lockfile thì không tự nâng dù range cho phép — phải npm update.

🧪 Bài 2 — Validate config fail-fast

Viết một module config đọc PORT (số, mặc định 8080), DB_URL (bắt buộc, URL), JWT_SECRET (bắt buộc, tối thiểu 16 ký tự). Nếu thiếu/sai phải in lỗi rõ ràng và process.exit(1). Giải thích vì sao validate lúc boot tốt hơn validate rải rác.

Gợi ý

Dùng schema (zod/joi) hoặc kiểm tra tay: ép Number(process.env.PORT) || 8080, ném lỗi nếu !DB_URL hoặc JWT_SECRET.length < 16. Validate lúc boot = fail-fast: lỗi config lộ ra trước khi nhận traffic, thay vì làm rớt cuộc gọi giữa giờ cao điểm; lại tập trung một chỗ, dễ audit. Tham khảo lại ý tưởng getEnv ở B1.

🧪 Bài 3 — Phá vòng phụ thuộc

Module agent.js và queue.js require lẫn nhau và bạn gặp TypeError: queue.push is not a function lúc khởi động. Đề xuất 2 cách sửa và giải thích cách nào tốt hơn.

Gợi ý

(1) Lazy require: chuyển require('./queue') vào trong hàm thay vì top-level → lúc gọi thì module đã nạp xong. (2) Tách module thứ ba chứa phần dùng chung (vd types.js / store.js), cả hai cùng phụ thuộc vào nó, phá vòng hẳn. Cách (2) tốt hơn vì xử lý nguyên nhân gốc (thiết kế kết dính chéo), còn (1) chỉ né triệu chứng.

Ngân hàng câu hỏi phỏng vấn

Module system, npm & cấu hình — chủ đề "đời thường" nhưng lộ rõ ai thực sự vận hành production.

Q1Phân biệt CommonJS và ESM.Junior›

Trả lời: CommonJS dùng require/module.exports, nạp đồng bộ và phân giải tại runtime (có thể require động trong if). ESM dùng import/export, tĩnh tại parse-time, nạp bất đồng bộ, hỗ trợ top-level await và tree-shaking. Node chọn hệ theo đuôi file (.mjs/.cjs) hoặc "type": "module". ESM không có __dirname, dùng import.meta.url thay thế.

Q2require cache hoạt động thế nào? Tận dụng ra sao?Middle›

Trả lời: Lần đầu require một module, Node chạy code của nó và lưu module.exports vào require.cache (key là đường dẫn tuyệt đối). Những lần sau trả về chính object đã cache, không chạy lại. Nhờ vậy ta tạo singleton: connection pool DB, client Redis, logger — chỉ khởi tạo một lần dù require ở nhiều nơi, tránh cạn kết nối.

⚠️ Bẫy: vì cache theo đường dẫn đã phân giải, hai đường dẫn khác nhau (vd qua symlink, hay khác casing trên hệ phân biệt chữ hoa/thường) có thể tạo HAI instance — phá vỡ giả định singleton.

Q3Circular dependency là gì? Node xử lý ra sao và cách phòng tránh?Senior›

Trả lời: Là khi A require B và B require A. Node không treo: khi gặp vòng, module đang nạp dở trả về module.exports tại trạng thái hiện tại — có thể chưa đầy đủ. Nếu bạn dùng export của module kia ngay lúc nạp (top-level), có thể nhận undefined → lỗi x is not a function. Nếu chỉ dùng trong hàm (gọi sau khi mọi module đã nạp) thì thường an toàn. Cách phòng: tách phần chung ra module thứ ba, lazy require trong hàm, hoặc thiết kế lại để bỏ vòng.

Q4Mô tả cơ chế phân giải module của Node.Middle›

Trả lời: Node phân loại định danh: (1) core module (fs, path...) ưu tiên cao nhất; (2) đường dẫn tương đối ./ ../ / → tìm file ngay đó, thử thêm đuôi .js/.json/.node, nếu là thư mục thì đọc main/exports hoặc index.js; (3) package bare → tìm node_modules bắt đầu từ thư mục hiện tại rồi leo dần lên cây cho tới root. Hết mà không thấy thì ném MODULE_NOT_FOUND.

Q5Giải thích semver và khác nhau giữa ^ và ~.Junior›

Trả lời: Semver là MAJOR.MINOR.PATCH: MAJOR tăng khi breaking change, MINOR khi thêm tính năng tương thích ngược, PATCH khi sửa lỗi. ^1.2.3 cho nâng MINOR + PATCH, giữ MAJOR (<2.0.0). ~1.2.3 chỉ cho nâng PATCH (<1.3.0). Exact 1.2.3 cố định tuyệt đối.

⚠️ Bẫy: với 0.x, caret hành xử như tilde — ^0.5.3 chỉ tới <0.6.0 vì semver coi 0.x là chưa ổn định.

Q6package-lock.json để làm gì? Có nên commit không?Middle›

Trả lời: Nó khóa lại version chính xác của toàn bộ cây phụ thuộc — kể cả các package gián tiếp (transitive) — kèm hash integrity. Mục đích: cài đặt tái lập, đảm bảo mọi dev/CI/production có cùng cây phụ thuộc, tránh "works on my machine". Phải commit lockfile. Range trong package.json chỉ nói "chấp nhận khoảng nào", còn lockfile mới là cái thực sự được cài.

Q7npm ci khác npm install thế nào? Khi nào dùng?Middle›

Trả lời: npm install giải range, có thể cập nhật lockfile và cài tăng dần — dùng khi phát triển/thêm package. npm ci bám chính xác lockfile (không sửa), bắt buộc có lockfile và lockfile phải khớp package.json, xóa sạch node_modules rồi cài lại — nhanh và tái lập. Dùng npm ci trong CI/CD và Docker production (kèm --omit=dev).

Q8Phân biệt dependencies, devDependencies, peerDependencies.Junior›

Trả lời: dependencies cần để chạy production (luôn cài). devDependencies chỉ cần lúc dev/test/build (bỏ qua với --omit=dev/production). peerDependencies là thứ package của bạn yêu cầu host cung cấp — không tự cài — để tránh trùng instance (vd plugin cần đúng một bản framework mà app đang dùng).

⚠️ Bẫy: nhầm một runtime dep vào devDependencies → build production bỏ qua → service crash lúc boot.

Q9peerDependencies giải quyết vấn đề gì? Cho ví dụ.Senior›

Trả lời: Nó tránh tình trạng nhiều bản trùng của một thư viện cùng tồn tại trong cây phụ thuộc, vốn gây bug khó hiểu khi cần chia sẻ một instance duy nhất (state, singleton, kiểm tra instanceof). Ví dụ: một plugin cho framework gateway khai báo framework là peer ^4 — host chịu trách nhiệm cung cấp một bản, đảm bảo plugin và app dùng chung instance, chung registry. Nếu khai báo là dependency thường, plugin có thể kéo bản riêng → hai registry agent tách biệt.

Q10Bạn quản lý config/secret cho một service Node thế nào theo 12-factor?Middle›

Trả lời: Config lưu trong env vars chứ không hardcode → cùng một artifact chạy mọi môi trường. Dev dùng .env (đã .gitignore, có .env.example mẫu) nạp qua dotenv hoặc node --env-file; production inject env qua orchestrator (K8s Secret). Tôi gom toàn bộ vào một module config đã validate + ép kiểu bằng zod/joi và fail-fast (process.exit(1)) nếu thiếu/sai lúc boot; phần code khác chỉ import từ module này, không đụng process.env trực tiếp.

Q11Interop CJS ↔ ESM có những vướng mắc gì?Senior›

Trả lời: Từ ESM có thể import module CJS: module.exports trở thành default export (named export đôi khi được suy ra nhưng không bảo đảm). Từ CJS không dùng require() được cho package ESM-only (vì require đồng bộ, ESM async) — phải dùng dynamic await import(). ESM thiếu __dirname/__filename/require; thay bằng import.meta.url + fileURLToPath. Nhiều package nay phát hành "dual" qua conditional exports (entry riêng cho import và require).

⚠️ Bẫy: hiện tượng "dual package hazard" — nếu một thư viện được nạp cả ở dạng CJS lẫn ESM, có thể tồn tại hai bản state riêng biệt.

Q12Bạn giảm rủi ro supply chain cho dependency npm thế nào?Senior›

Trả lời: (1) Commit lockfile để cố định cây + hash integrity. (2) Dùng npm ci trong CI để cài tái lập, phát hiện lockfile lệch. (3) Chạy npm audit --audit-level=high trong pipeline và để Dependabot/Renovate mở PR nâng bản có test. (4) Giảm số dependency, tránh nâng ngay version vừa ra (phòng typosquatting/package bị chiếm). (5) Cân nhắc --ignore-scripts để chặn postinstall độc hại trong môi trường nhạy cảm. (6) Pin chặt các package nhạy cảm. Với service tổng đài giữ secret nhà mạng và PII khách hàng, kỷ luật này là yêu cầu compliance, không chỉ là tốt-nên-có.
