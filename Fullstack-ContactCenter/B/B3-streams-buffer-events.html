Streams, Buffer & EventEmitter

Xử lý dữ liệu nhị phân (bản ghi cuộc gọi), sự kiện và luồng dữ liệu lớn mà không nuốt hết bộ nhớ — nền tảng cho mọi hệ thống I/O hiệu năng cao.

🎯 Học xong chương này bạn sẽ

• Hiểu Buffer là gì, vì sao Node cần nó để xử lý dữ liệu nhị phân (audio, ảnh, file), và các kiểu encoding utf8/base64/hex.

• Nắm EventEmitter — mô hình hướng sự kiện (on/emit/once), cách phát hiện rò rỉ listener, đây là nền móng của socket và stream.

• Phân biệt rõ 4 loại Stream (Readable, Writable, Duplex, Transform) và dùng pipe() / pipeline() đúng cách.

• Giải thích backpressure: vì sao cần, highWaterMark, cơ chế pause/resume, và vì sao pipe tự lo việc này.

• Biết khi nào stream file thay vì readFile cả file, áp dụng cho log cuộc gọi, CSV danh bạ, upload bản ghi.

💡 Liên hệ thực tế hệ thống Contact Center

Một Contact Center sống bằng dữ liệu lớn chảy liên tục: file ghi âm cuộc gọi vài chục MB, log sự kiện hàng trăm nghìn dòng/ngày, file CSV import danh bạ vài triệu liên hệ, gói âm thanh streaming theo thời gian thực. Nếu nạp nguyên cả file vào RAM (readFile), chỉ vài chục cuộc gọi tải song song là server OOM (hết bộ nhớ) ngay. Streams + Buffer chính là công cụ để xử lý từng mảnh nhỏ mà bộ nhớ luôn ổn định — đây là kiến thức gần như chắc chắn bị hỏi khi phỏng vấn backend realtime.

① Buffer & dữ liệu nhị phân

JavaScript thuần được sinh ra cho trình duyệt, nơi mọi thứ chủ yếu là chuỗi và số. Nhưng server thì phải đụng tới dữ liệu nhị phân thô: byte của file ghi âm, gói TCP, ảnh, payload mã hóa. Trước khi có TypedArray, JS không có cách biểu diễn dãy byte cố định. Node giải quyết bằng class Buffer — một vùng nhớ cố định, nằm ngoài V8 heap, đại diện cho một dãy byte.

🧱 Là gì

Một mảng byte có kích thước cố định, mỗi phần tử là số 0–255. Phân bổ ngoài V8 heap nên không bị giới hạn heap nhỏ.

🔢 Vì sao cần

String JS là UTF-16 và bất biến — không hợp để thao tác byte thô như audio/ảnh/crypto. Buffer cho phép đọc/ghi từng byte.

🌊 Liên hệ Stream

Dữ liệu chảy qua stream mặc định là các chunk Buffer. Hiểu Buffer là tiền đề để hiểu Stream.

Tạo và đọc Buffer

buffer-basics.jsNode.js
// Cách tạo Buffer (Buffer.alloc/from — KHÔNG dùng new Buffer cũ, không an toàn)
const a = Buffer.alloc(8);              // 8 byte, đã zero-fill (an toàn)
const b = Buffer.allocUnsafe(8);        // nhanh hơn nhưng chứa rác → phải ghi đè ngay
const c = Buffer.from('Xin chào', 'utf8'); // từ chuỗi
const d = Buffer.from([0x48, 0x49]);       // từ mảng byte → "HI"

console.log(c.length);            // 9 — "à" tiếng Việt chiếm nhiều byte hơn 1 ký tự!
console.log(c[0]);              // 88 — byte đầu (mã của 'X')
console.log(c.toString('utf8'));  // "Xin chào" — giải mã ngược
⚠️ .length của Buffer là số BYTE, không phải số ký tự

Với ký tự đa byte (tiếng Việt có dấu, emoji), một ký tự hiển thị có thể chiếm 2–4 byte UTF-8. Đây là nguồn bug kinh điển khi cắt chuỗi bằng cách cắt buffer giữa chừng — bạn có thể cắt đứt một ký tự thành 2 nửa byte vô nghĩa.

Encoding — cùng một dãy byte, nhiều cách biểu diễn

Một Buffer là dãy byte trung lập. Encoding là quy ước để chuyển byte ↔ chuỗi. Cùng một mảng byte, đọc theo encoding khác nhau ra chuỗi khác nhau. Ba encoding hay gặp nhất trong backend Contact Center:

💡 Audio ghi âm & base64

Khi cần đẩy một mẩu âm thanh ngắn (vd "voicemail preview") qua WebSocket dạng JSON, ta encode Buffer audio sang base64 để truyền như chuỗi, rồi decode lại ở client. Lưu ý base64 phình ~33% kích thước — với file ghi âm dài, hãy dùng binary frame của WebSocket hoặc tải qua URL, đừng base64 cả file vài chục MB.

② EventEmitter — xương sống hướng sự kiện

Phần lớn API bất đồng bộ của Node được xây trên một mô hình: một đối tượng phát ra sự kiện, nhiều nơi đăng ký lắng nghe. Class EventEmitter trong module events là hiện thân của mô hình đó. Server HTTP, socket, và mọi Stream đều kế thừa từ EventEmitter — vì vậy hiểu nó là điều kiện tiên quyết để hiểu phần còn lại của chương.

emitter.jsNode.js
const { EventEmitter } = require('events');

// Mô hình hoá vòng đời một cuộc gọi như một emitter
class Call extends EventEmitter {}
const call = new Call();

// on: lắng nghe MỖI lần sự kiện phát ra
call.on('audio-chunk', (chunk) => writeToRecorder(chunk));

// once: chỉ chạy LẦN ĐẦU rồi tự gỡ
call.once('connected', () => log('Cuộc gọi đã kết nối'));

// emit: phát sự kiện, kèm dữ liệu (chạy ĐỒNG BỘ, tuần tự theo thứ tự đăng ký)
call.emit('connected');
call.emit('audio-chunk', packet);

// Gỡ listener khi cuộc gọi kết thúc — TRÁNH rò rỉ bộ nhớ
function onHangup() { /* cleanup */ }
call.on('hangup', onHangup);
call.removeListener('hangup', onHangup);  // hoặc call.off(...)

Các đặc tính cần nhớ khi phỏng vấn

⏱️ emit là đồng bộ

emit gọi lần lượt từng listener ngay lập tức, đồng bộ, đúng thứ tự đăng ký. Listener nặng sẽ chặn — muốn async thì tự bọc setImmediate/Promise.

💥 sự kiện error đặc biệt

Nếu emit 'error' mà KHÔNG có listener nào, Node sẽ throw và làm sập tiến trình. Luôn gắn .on('error', ...).

🔁 once vs on

once tự gỡ sau lần đầu — hợp cho sự kiện một-lần như 'connected', 'ready'. on cho sự kiện lặp lại như 'data'.

🚨 maxListeners = 11 cảnh báo

Quá 10 listener cùng tên trên một emitter → warning "possible EventEmitter memory leak". Đây là tín hiệu rò rỉ, không phải lỗi vô hại.

🐛 Rò rỉ listener trong Contact Center

Tình huống kinh điển: mỗi khi một agent kết nối, bạn gắn bus.on('new-ticket', ...) nhưng quên gỡ khi agent ngắt kết nối. Sau vài giờ, cùng một emitter có hàng nghìn listener → RAM tăng dần, mỗi event xử lý chậm dần, cuối cùng OOM. Node nhắc bạn bằng warning MaxListenersExceededWarning. Cách đúng: cứ on thì phải có off tương ứng ở vòng đời ngược lại; dùng once cho sự kiện một-lần; hoặc dùng AbortController/signal để gỡ hàng loạt.

cleanup-pattern.jsNode.js
function attachAgent(bus, agentId) {
  const handler = (ticket) => routeTo(agentId, ticket);
  bus.on('new-ticket', handler);

  // Trả về hàm dọn dẹp — gọi khi agent disconnect
  return () => bus.removeListener('new-ticket', handler);
}

const detach = attachAgent(bus, 'agent-42');
// ... khi agent rời:
detach();   // listener được gỡ sạch, không rò rỉ

③ Streams — xử lý dữ liệu theo từng mảnh

Một Stream là trừu tượng hóa cho dữ liệu được xử lý từng mảnh (chunk) theo thời gian, thay vì gom hết vào bộ nhớ rồi mới xử lý. Hãy hình dung một file ghi âm 200 MB: nếu readFile bạn cần 200 MB RAM ngay lập tức; nếu stream, bạn chỉ giữ vài chục KB mỗi lần và để dữ liệu "chảy" qua. Vì Stream kế thừa EventEmitter, nó phát các sự kiện như 'data', 'end', 'error'.

Bốn loại Stream

LoạiVai tròVí dụ Node tích hợpTrong Contact Center
ReadableNguồn để đọc dữ liệu rafs.createReadStream, req (HTTP), process.stdinĐọc file ghi âm, đọc body upload
WritableĐích để ghi dữ liệu vàofs.createWriteStream, res (HTTP), process.stdoutGhi log cuộc gọi, lưu file ghi âm
DuplexVừa đọc vừa ghi, hai chiều độc lậpnet.Socket (TCP)Kết nối socket signaling giữa agent ↔ server
TransformDuplex mà output được biến đổi từ inputzlib.createGzip, crypto cipherNén log, mã hóa bản ghi, đổi mã hóa audio
🔎 Duplex vs Transform — khác nhau ở đâu?

Cả hai đều hai chiều. Duplex: chiều đọc và chiều ghi không liên quan nhau (như socket — bạn gửi gì không quyết định bạn nhận gì). Transform: cái bạn đọc ra chính là cái bạn ghi vào sau khi đã biến đổi (nén, mã hóa, parse). Transform là loại bạn tự viết nhiều nhất.

pipe() — nối nguồn vào đích

Sức mạnh thực sự của Stream nằm ở việc ghép chúng lại như đường ống. readable.pipe(writable) tự động đọc từng chunk từ nguồn và ghi vào đích, tự xử lý backpressure (mục ④). Bạn có thể nối nhiều Transform ở giữa thành một dây chuyền:

📁 ReadStream (file ghi âm)→ 🔄 Transform (gzip nén)→ 🔄 Transform (mã hóa)→ 💾 WriteStream (lưu trữ)
pipe.jsNode.js
const fs = require('fs');
const zlib = require('zlib');

// Nén một file log cuộc gọi lớn mà KHÔNG nạp cả file vào RAM
fs.createReadStream('./calls-2026-06-09.log')
  .pipe(zlib.createGzip())              // Transform: nén từng chunk
  .pipe(fs.createWriteStream('./calls.log.gz'));

// VẤN ĐỀ: pipe KHÔNG tự forward lỗi & KHÔNG tự dọn dẹp tốt.
// Nếu giữa chừng đích lỗi, nguồn có thể bị rò rỉ (không đóng).

stream.pipeline() — bản nâng cấp xử lý lỗi

Nhược điểm lớn của pipe() là không lan truyền lỗi giữa các stream và không tự đóng các stream còn lại khi một mắt xích lỗi (dễ rò rỉ file descriptor). stream.pipeline() ra đời để khắc phục: nó nối chuỗi, tự bắt lỗi ở mọi mắt xích, tự gọi destroy/cleanup, và báo lỗi qua một callback (hoặc Promise với pipeline từ stream/promises).

pipeline.jsNode.js
const { pipeline } = require('stream/promises');
const fs = require('fs');
const zlib = require('zlib');

async function archiveCallLog(src, dest) {
  try {
    await pipeline(
      fs.createReadStream(src),
      zlib.createGzip(),
      fs.createWriteStream(dest)
    );
    log('Lưu trữ log xong:', dest);
  } catch (err) {
    // MỌI lỗi ở bất kỳ mắt xích nào đều rơi về đây; các stream đã được dọn dẹp
    log('Lưu trữ thất bại:', err.message);
  }
}
💡 Quy tắc thực chiến

Trong code production, ưu tiên pipeline() hơn pipe(). pipe chỉ ổn cho ví dụ nhanh hoặc khi bạn chủ động gắn .on('error') cho từng stream. pipeline giúp bạn không bao giờ rò rỉ file descriptor khi client ngắt kết nối giữa chừng — chuyện xảy ra liên tục với upload bản ghi.

Hai chế độ của Readable: flowing vs paused

Một Readable hoạt động ở một trong hai chế độ. Hiểu rõ điều này giúp bạn không bị "mất dữ liệu" hoặc "không thấy data đâu":

🌊 Flowing (chảy)

Dữ liệu được đẩy tới bạn tự động qua sự kiện 'data'. Kích hoạt khi gắn .on('data'), gọi .resume(), hoặc .pipe().

⏸️ Paused (tạm dừng)

Bạn chủ động kéo dữ liệu bằng .read() trong sự kiện 'readable'. Mặc định Readable bắt đầu ở chế độ này.

flowing-vs-async-iter.jsNode.js
// Cách 1 — flowing qua 'data' (cẩn thận backpressure phải tự lo)
stream.on('data', (chunk) => process(chunk));
stream.on('end', () => log('Hết dữ liệu'));

// Cách 2 (hiện đại, khuyên dùng) — for await...of: backpressure tự nhiên,
// dừng đọc khi vòng lặp còn bận xử lý chunk hiện tại
async function readCalls(stream) {
  for await (const chunk of stream) {
    await saveChunk(chunk);   // stream tự "đợi" — không tràn
  }
}

Object mode — stream không chỉ là byte

Mặc định stream chảy các chunk Buffer/string. Bật objectMode: true để mỗi chunk là một object JS bất kỳ — cực hữu ích khi xử lý theo bản ghi (record). Ví dụ: đọc CSV danh bạ và biến mỗi dòng thành một object liên hệ qua một Transform.

④ Backpressure — chống nghẽn đường ống

Backpressure (áp lực ngược) là tình huống nguồn tạo dữ liệu nhanh hơn đích tiêu thụ. Hãy hình dung bạn đọc một file ghi âm từ SSD (rất nhanh) rồi ghi qua mạng tới object storage (chậm hơn nhiều). Nếu cứ đọc và đẩy không kiểm soát, dữ liệu chưa kịp ghi sẽ bị chất đống trong bộ nhớ đệm nội bộ → RAM phình lên → OOM. Backpressure là cơ chế để nguồn biết khi nào nên chậm lại.

🐛 Vì sao đây là vấn đề sống còn

Không xử lý backpressure là một trong những nguyên nhân OOM phổ biến nhất ở server Node. Với Contact Center: 50 agent cùng upload bản ghi dài, nếu mỗi luồng buffer vô tội vạ, RAM bốc hơi trong vài giây. Triệu chứng: bộ nhớ tăng tuyến tính theo lưu lượng, không tự hạ.

Cơ chế hoạt động: highWaterMark & giá trị trả về của write()

Mỗi Writable có một bộ đệm nội bộ với ngưỡng highWaterMark (mặc định 16 KB cho byte stream, 16 object cho object mode). Khi bạn gọi writable.write(chunk):

  • Trả về true → đệm còn chỗ, cứ ghi tiếp thoải mái.
  • Trả về false → đệm đã vượt ngưỡng, bạn nên dừng đọc và chờ sự kiện 'drain' (đệm đã vơi) mới ghi tiếp.
read chunk→ write() trả false?→ pause() nguồn→ chờ 'drain'→ resume() nguồn
manual-backpressure.jsNode.js
// Xử lý backpressure THỦ CÔNG (để hiểu pipe làm gì hộ bạn)
readable.on('data', (chunk) => {
  const ok = writable.write(chunk);
  if (!ok) {
    readable.pause();                 // đích nghẽn → ngừng đọc
    writable.once('drain', () => {
      readable.resume();             // đệm vơi → đọc tiếp
    });
  }
});
💡 pipe() / pipeline() làm TẤT CẢ việc trên cho bạn

Đây chính là lý do nên dùng pipe/pipeline: chúng tự động gọi pause/resume dựa trên highWaterMark của đích. Tương tự, for await...of trên Readable cũng tôn trọng backpressure tự nhiên. Bạn gần như không bao giờ nên tự viết vòng write thủ công trong code thật — trừ khi đang học hoặc tối ưu rất sâu.

⑤ File System — streaming vs đọc cả file

Module fs cho hai nhóm API thao tác file. Chọn nhầm là sai lầm hiệu năng kinh điển bị soi rất kỹ khi phỏng vấn.

CáchBộ nhớ dùngPhù hợp khiTránh khi

fs.createReadStream≈ highWaterMark (vài chục KB), ổn địnhFile lớn, audio, log, CSV; cần xử lý lúc đang đọcKhi bạn thật sự cần toàn bộ nội dung trong RAM cùng lúc
⚠️ readFileSync trong request handler = thảm họa

Nhắc lại từ B1: *Sync chặn Event Loop. readFileSync một file ghi âm 100 MB trong handler sẽ làm mọi cuộc gọi khác bị treo cho tới khi đọc xong. readFile bất đồng bộ đỡ hơn nhưng vẫn ngốn 100 MB RAM. Đáp án đúng cho file lớn gần như luôn là stream.

serve-recording.jsNode.js · Express
// Phục vụ file ghi âm cho agent nghe lại — stream thẳng tới response
app.get('/recordings/:id', (req, res) => {
  const path = recordingPath(req.params.id);
  res.setHeader('Content-Type', 'audio/mpeg');

  const file = fs.createReadStream(path);
  // pipeline tự đóng file nếu agent ngắt kết nối giữa chừng (rất hay xảy ra)
  pipeline(file, res, (err) => {
    if (err) log('Stream ghi âm lỗi:', err.message);
  });
});

⑥ Ứng dụng trong hệ thống Contact Center

Ghép tất cả lại bằng ba kịch bản thật sự xuất hiện trong một Contact Center, mỗi cái cho thấy tư duy thiết kế: yêu cầu, lựa chọn, đánh đổi.

1) Đọc & xử lý log cuộc gọi cực lớn

Yêu cầu: đếm số cuộc gọi rớt (status=DROPPED) trong file log 5 GB. Lựa chọn: đọc cả file (bất khả thi, 5 GB RAM) vs stream theo dòng. Chọn stream + đọc theo dòng để bộ nhớ phẳng.

count-dropped.jsNode.js
const readline = require('readline');
const fs = require('fs');

async function countDropped(file) {
  const rl = readline.createInterface({
    input: fs.createReadStream(file),  // stream → bộ nhớ không phụ thuộc kích thước file
    crlfDelay: Infinity
  });
  let dropped = 0;
  for await (const line of rl) {       // xử lý từng dòng, backpressure tự nhiên
    if (line.includes('"status":"DROPPED"')) dropped++;
  }
  return dropped;
}

2) Import CSV danh bạ vài triệu liên hệ

Yêu cầu: nạp file CSV danh bạ rất lớn vào DB, không sập RAM, có validate từng dòng. Thiết kế: dùng Transform ở object mode để chuyển CSV → object liên hệ, ghép pipeline với một Writable đẩy theo batch vào DB. Đánh đổi: ghi theo batch (vd 500 dòng) để giảm round-trip DB, vẫn giữ backpressure để DB chậm thì pipeline tự chậm theo.

import-contacts.jsNode.js
const { pipeline } = require('stream/promises');
const { Transform } = require('stream');
const csv = require('csv-parse');   // stream parser CSV (object mode)

// Transform: validate + chuẩn hoá từng liên hệ
const normalize = new Transform({
  objectMode: true,
  transform(row, _enc, cb) {
    if (!row.phone) return cb();  // bỏ dòng thiếu SĐT, không đẩy xuống
    cb(null, { name: row.name?.trim(), phone: e164(row.phone) });
  }
});

await pipeline(
  fs.createReadStream('./contacts.csv'),
  csv.parse({ columns: true }),
  normalize,
  batchInsertWritable(db, 500)    // Writable gom 500 rồi insert một lần
);

3) Nhận upload bản ghi và lưu trữ

Yêu cầu: agent upload file ghi âm; lưu vào storage đồng thời nén lại. Thiết kế: chính req đã là một Readable — pipe thẳng qua gzip rồi tới Writable của storage, không bao giờ giữ cả file trong RAM. Backpressure đảm bảo nếu storage chậm thì Node ngừng đọc từ network, tránh phình bộ nhớ.

📤 req (Readable upload)→ 🔄 gzip (Transform)→ ☁️ storage.WriteStream
💡 Tư duy chung của cả ba kịch bản

Mẫu số chung: dữ liệu lớn + bộ nhớ phải ổn định + xử lý vừa-chảy-vừa-làm → Stream + pipeline + (Transform khi cần biến đổi). Khi phỏng vấn, nếu đề bài có chữ "file lớn", "log khổng lồ", "real-time audio", "import hàng triệu dòng" — gần như chắc chắn câu trả lời đúng phải nhắc tới stream và backpressure.

⚠️ Lỗi thường gặp & Best practices

🚫 Quên gắn .on('error')

Stream/emitter emit 'error' không ai nghe → sập tiến trình. Luôn xử lý lỗi trên mọi stream, hoặc dùng pipeline.

🚫 Dùng pipe không bắt lỗi

pipe không forward lỗi, dễ rò rỉ file descriptor khi client ngắt giữa chừng. Ưu tiên pipeline().

🚫 readFile file lớn

Nạp cả file vào RAM → OOM khi nhiều request song song. File lớn/không rõ size → stream.

🚫 Bỏ qua backpressure

Vòng write bất chấp giá trị trả về → đệm phình → OOM. Tôn trọng false + 'drain', hoặc để pipe lo.

🚫 Rò rỉ listener

Cứ on mà không off → cảnh báo maxListeners, RAM tăng dần. Có on phải có off; dùng once cho sự kiện một-lần.

🚫 Cắt Buffer giữa ký tự đa byte

Cắt chunk ngay giữa một ký tự UTF-8 → ký tự hỏng. Dùng string_decoder hoặc ghép buffer trước khi decode.

🧪 Bài tập

🧪 Bài 1 — Transform viết hoa log

Viết một Transform stream nhận log cuộc gọi dạng text, biến mỗi chunk thành chữ HOA, rồi pipeline từ một file vào process.stdout. Vì sao nên dùng pipeline thay vì hai .pipe() nối nhau?

Gợi ý

Tạo new Transform({ transform(chunk, enc, cb){ cb(null, chunk.toString().toUpperCase()) } }). Dùng pipeline(readStream, upper, process.stdout, errCb) vì nó lan truyền lỗi và tự dọn dẹp mọi stream khi có lỗi — điều mà .pipe() không làm, dễ rò rỉ file descriptor.

🧪 Bài 2 — Phát hiện rò rỉ listener

Đoạn code đăng ký bus.on('new-call', handler) mỗi lần một agent đăng nhập nhưng không bao giờ gỡ. Mô tả triệu chứng sẽ thấy sau vài giờ chạy và viết bản sửa đúng vòng đời.

Gợi ý

Triệu chứng: warning MaxListenersExceededWarning sau 10 listener, RAM tăng dần, mỗi event xử lý chậm dần (vì gọi nhiều handler trùng). Sửa: lưu tham chiếu handler, khi agent logout gọi bus.removeListener('new-call', handler). Hoặc gom theo AbortController để gỡ hàng loạt khi session kết thúc.

🧪 Bài 3 — Chọn API đọc file

Bạn cần (a) đọc file cấu hình config.json 4 KB lúc khởi động, và (b) phục vụ file ghi âm 80 MB cho agent nghe lại. Với mỗi trường hợp, chọn readFileSync, readFile, hay createReadStream và giải thích.

Gợi ý

(a) readFileSync chấp nhận được vì chạy một lần lúc boot, file nhỏ, fail-fast nếu thiếu config. (b) createReadStream + pipeline tới response: file lớn, nhiều agent có thể nghe song song; bộ nhớ chỉ ~highWaterMark và tự đóng nếu agent ngắt kết nối.

✅ Quiz kiểm tra nhanh

Q1. Buffer trong Node là gì?
Một kiểu chuỗi đặc biệt của V8
Vùng nhớ cố định ngoài V8 heap, đại diện cho một dãy byte
Một loại stream chỉ đọc
Dãy byte cố định. Buffer biểu diễn dữ liệu nhị phân thô (audio, ảnh, gói mạng), phân bổ ngoài heap V8.
Q2. Có mấy loại stream trong Node?
2 — đọc và ghi
4 — Readable, Writable, Duplex, Transform
3 — input, output, error
4 loại. Transform là Duplex mà output được biến đổi từ input (nén, mã hóa, parse).
Q3. writable.write(chunk) trả về false nghĩa là?
Ghi thất bại, mất chunk
Đệm nội bộ đã vượt highWaterMark — nên dừng đọc, chờ 'drain'
Stream đã đóng
Backpressure. Chunk vẫn được nhận nhưng đệm đầy; tôn trọng tín hiệu để tránh phình RAM.
Q4. Ưu điểm chính của pipeline() so với pipe()?
Chạy nhanh hơn nhiều lần
Tự lan truyền lỗi và dọn dẹp (destroy) mọi stream khi có lỗi
Cho phép nối nhiều hơn 2 stream
Xử lý lỗi & cleanup. pipe không forward lỗi nên dễ rò rỉ file descriptor; pipeline khắc phục điều đó.
Q5. Cảnh báo "possible EventEmitter memory leak" xuất hiện khi nào?
Khi emit sự kiện 'error' không có listener
Khi một emitter có hơn 10 listener cùng một tên sự kiện
Khi dùng once thay vì on
Quá maxListeners (mặc định 10). Đây là tín hiệu nghi rò rỉ — thường do quên removeListener.

Ngân hàng câu hỏi phỏng vấn

Streams, Buffer, Events — chủ đề kinh điển để đánh giá độ "hiểu sâu" backend Node.

Q1Buffer là gì và vì sao Node cần nó?Junior›

Trả lời: Buffer là vùng nhớ cố định, phân bổ ngoài V8 heap, đại diện cho một dãy byte (mỗi byte 0–255). Node cần nó vì server phải xử lý dữ liệu nhị phân thô — file ghi âm, ảnh, gói TCP, dữ liệu mã hóa — mà chuỗi JS (UTF-16, bất biến) không phù hợp. Buffer cho phép đọc/ghi từng byte và chuyển đổi qua các encoding như utf8/base64/hex.

Q2Phân biệt Buffer và string. Khi nào dùng cái nào?Junior›

Trả lời: String là chuỗi ký tự (UTF-16, bất biến), hợp cho văn bản. Buffer là dãy byte thô, hợp cho dữ liệu nhị phân. Dùng string khi xử lý text (tin nhắn, JSON); dùng Buffer khi thao tác byte (audio, ảnh, crypto, gói mạng). Lưu ý: buffer.length là số byte, không phải số ký tự — một ký tự tiếng Việt/emoji có thể chiếm nhiều byte.

⚠️ Bẫy: tin rằng length = số ký tự. Sai với ký tự đa byte UTF-8.

Q3Liệt kê 4 loại stream và cho ví dụ mỗi loại.Junior›

Trả lời: (1) Readable — nguồn đọc, vd fs.createReadStream, req HTTP. (2) Writable — đích ghi, vd fs.createWriteStream, res HTTP. (3) Duplex — vừa đọc vừa ghi độc lập, vd net.Socket. (4) Transform — Duplex mà output được biến đổi từ input, vd zlib.createGzip, cipher của crypto.

Q4Backpressure là gì và xử lý thế nào?Middle›

Trả lời: Backpressure là khi nguồn tạo dữ liệu nhanh hơn đích tiêu thụ, khiến dữ liệu chất đống trong bộ đệm nội bộ → phình RAM, có thể OOM. Cơ chế: writable.write() trả về false khi đệm vượt highWaterMark; khi đó ta pause() nguồn và chờ sự kiện 'drain' rồi resume(). Trong thực tế dùng pipe()/pipeline() hoặc for await...of để Node tự xử lý.

Q5Khác nhau giữa pipe() và stream.pipeline()?Middle›

Trả lời: pipe() nối nguồn vào đích và tự xử lý backpressure, nhưng không lan truyền lỗi và không tự đóng các stream còn lại khi một mắt xích lỗi → dễ rò rỉ file descriptor. pipeline() nối chuỗi, bắt lỗi ở mọi mắt xích, tự gọi destroy/cleanup, và báo lỗi qua callback (hoặc Promise với stream/promises). Production nên ưu tiên pipeline.

⚠️ Bẫy: nói "pipe tự bắt lỗi giúp" — không, pipe không forward lỗi giữa các stream.

Q6Khi nào dùng stream thay vì đọc cả file?Middle›

Trả lời: Dùng stream khi file lớn hoặc kích thước không kiểm soát (log, upload, audio), khi cần xử lý ngay lúc đang đọc, hoặc khi muốn bộ nhớ ổn định (~highWaterMark) bất kể file lớn cỡ nào. Dùng readFile khi file nhỏ, biết chắc kích thước, và thật sự cần toàn bộ nội dung trong RAM cùng lúc (config, template). readFileSync chỉ nên dùng lúc khởi động, không bao giờ trong request handler.

Q7EventEmitter memory leak là gì? Làm sao phát hiện và phòng tránh?Middle›

Trả lời: Là tình huống listener cứ được thêm vào một emitter mà không gỡ → mảng listener phình, RAM tăng dần, xử lý chậm dần. Node phát hiện bằng warning MaxListenersExceededWarning khi vượt 10 listener cùng tên trên một emitter. Phòng tránh: mỗi on phải có off/removeListener tương ứng ở vòng đời ngược lại; dùng once cho sự kiện một-lần; dùng AbortController để gỡ hàng loạt khi session kết thúc.

Q8Transform stream dùng để làm gì? Cho ví dụ trong Contact Center.Middle›

Trả lời: Transform là stream vừa đọc vừa ghi, trong đó dữ liệu output được biến đổi từ input theo từng chunk. Dùng để nén/giải nén (gzip), mã hóa/giải mã, đổi mã hóa audio, hoặc parse/chuẩn hóa bản ghi. Ví dụ Contact Center: một Transform object-mode chuyển mỗi dòng CSV danh bạ thành object liên hệ đã validate, đặt giữa pipeline đọc-file → ghi-DB. Hoặc nén log cuộc gọi trên đường ghi ra ổ đĩa.

Q9Phân biệt chế độ flowing và paused của Readable.Senior›

Trả lời: Flowing: dữ liệu được tự động đẩy tới qua sự kiện 'data'; kích hoạt khi gắn .on('data'), gọi .resume(), hoặc .pipe(). Paused (mặc định ban đầu): bạn chủ động kéo dữ liệu bằng .read() trong sự kiện 'readable'. Có thể chuyển qua lại bằng pause()/resume(). Hiện nay khuyến nghị dùng for await...of để có backpressure tự nhiên và code dễ đọc.

⚠️ Bẫy: gắn .on('data') rồi quên rằng nó đã chuyển stream sang flowing — nếu xử lý đồng bộ chậm có thể mất kiểm soát backpressure.

Q10Object mode là gì và khi nào hữu ích?Senior›

Trả lời: Mặc định stream chảy các chunk Buffer/string. Bật objectMode: true để mỗi chunk là một object JS bất kỳ. Hữu ích khi xử lý theo bản ghi: parse CSV thành object từng dòng, đẩy từng message qua một pipeline xử lý, hay nối các stage logic nghiệp vụ. Lưu ý highWaterMark ở object mode tính theo số object (mặc định 16) chứ không theo byte.

Q11Vì sao sự kiện 'error' của EventEmitter đặc biệt nguy hiểm?Senior›

Trả lời: Nếu một emitter emit('error', err) mà không có listener nào cho 'error', Node sẽ throw lỗi đó như một exception chưa bắt và làm sập cả tiến trình. Đây là khác biệt với các sự kiện khác (bị bỏ qua nếu không ai nghe). Vì vậy mọi stream/socket đều phải gắn .on('error', ...), hoặc dùng pipeline để gom xử lý lỗi tập trung. Trong Contact Center, một stream ghi âm lỗi không được xử lý có thể làm sập service đang phục vụ hàng trăm cuộc gọi.

⚠️ Bẫy: chỉ bắt lỗi ở stream cuối mà quên các stream trung gian — mỗi stream trong chuỗi pipe cần error handler riêng (lý do nên dùng pipeline).

Q12Thiết kế luồng phục vụ nghe lại file ghi âm lớn cho nhiều agent đồng thời.Senior›

Trả lời: Yêu cầu: nhiều agent nghe file ghi âm hàng chục MB cùng lúc, bộ nhớ phải ổn định, hỗ trợ tua (seek) và ngắt giữa chừng. Thiết kế: dùng fs.createReadStream với option { start, end } theo HTTP Range để hỗ trợ tua; pipeline(file, res) để stream thẳng và tự đóng file khi agent ngắt; đặt Content-Type, Accept-Ranges: bytes. Đánh đổi: stream giữ RAM phẳng (~highWaterMark mỗi kết nối) thay vì nạp cả file (sẽ OOM khi nhiều agent). Backpressure đảm bảo agent mạng chậm không làm phình bộ nhớ server. Có thể đặt sau CDN hoặc dùng presigned URL của object storage để giảm tải hẳn cho service.
