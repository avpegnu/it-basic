Express & Middleware

Express là framework tối giản phổ biến nhất cho Node. Trái tim của nó là middleware — hiểu rõ luồng (req, res, next) là hiểu Express.

🎯 Học xong chương này bạn sẽ

• Giải thích Express là một lớp mỏng bọc quanh module http của Node, và phân biệt app với Router.

• Hiểu middleware là gì: một hàm (req, res, next), vai trò của next() và next(err).

• Giải thích vì sao thứ tự đăng ký middleware quyết định toàn bộ luồng request.

• Phân loại middleware: application-level, router-level, error-handling, built-in, third-party.

• Viết được error-handling middleware đúng chuẩn 4 tham số và biết vì sao 4 tham số là bắt buộc.

• Xử lý đúng lỗi bất đồng bộ (async) để chúng không bị "nuốt" mất mà rơi vào error handler.

💡 Liên hệ hệ thống Contact Center

Một API Contact Center điển hình phục vụ rất nhiều endpoint: gán cuộc gọi cho agent, lấy hàng đợi (queue), tạo ticket, ghi chú cuộc trò chuyện (chat). Mọi request đều cần đi qua một chuỗi xử lý chung: xác thực token agent, kiểm tra quyền, log để truy vết, parse JSON, rồi mới tới logic nghiệp vụ. Express gọi mỗi mắt xích đó là một middleware. Hiểu chuỗi này là nền tảng cho mọi chương REST API sau (C2, C4).

① Express là gì?

Express là một framework web tối giản (minimalist) cho Node.js. Bản chất nó chỉ là một lớp mỏng (thin layer) bọc quanh module http có sẵn của Node, bổ sung ba thứ giúp đời lập trình viên dễ thở hơn: routing (định tuyến URL + method tới hàm xử lý), middleware (chuỗi hàm xử lý request), và một loạt tiện ích trên req/res (như res.json(), res.status()).

Để thấy Express "mỏng" cỡ nào, hãy so sánh cùng một server viết bằng http thuần và bằng Express:

http-thuan.jsNode.js
const http = require('http');

http.createServer((req, res) => {
  // Phải tự parse URL, method, tự set header, tự stringify...
  if (req.url === '/agents' && req.method === 'GET') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify([{ id: 1, name: 'Agent A' }]));
  } else {
    res.writeHead(404); res.end();
  }
}).listen(3000);
express.jsNode.js
const express = require('express');
const app = express();

app.get('/agents', (req, res) => {
  // res.json: tự set Content-Type + stringify, gọn hơn nhiều
  res.json([{ id: 1, name: 'Agent A' }]);
});

app.listen(3000, () => console.log('API on :3000'));

app vs Router

Khi gọi express() bạn nhận về một đối tượng app — đó là "ứng dụng" gốc, cũng đồng thời là một hàm request-handler để truyền vào http.createServer. Còn express.Router() tạo ra một mini-app độc lập: nó cũng có .get/.post/.use nhưng chỉ là một "cụm route" có thể gắn vào app ở một tiền tố (prefix) nào đó. Đây là công cụ để chia nhỏ một API lớn thành module.

💡 Vì sao nên dùng Router

Trong một Contact Center API thực, bạn sẽ có hàng chục endpoint cho /agents, /calls, /queues, /tickets, /chats. Nhồi tất cả vào một file app.js sẽ thành "địa ngục nghìn dòng". Mỗi domain một Router giúp code rõ ràng, dễ test và dễ gắn middleware riêng (vd chỉ /tickets cần kiểm tra quyền supervisor).

② Middleware — đơn vị xử lý của Express

Middleware là một hàm có chữ ký (req, res, next) được thực thi trong quá trình Express xử lý một request, trước khi (hoặc thay cho) handler cuối cùng trả response. Mỗi middleware có toàn quyền với ba đối tượng:

  • req — đối tượng request: đọc/ghi được. Middleware có thể "đính kèm" dữ liệu, vd req.user = agent để các middleware sau dùng lại.
  • res — đối tượng response: dùng để trả kết quả (res.json(), res.status()...).
  • next — một hàm callback để chuyển quyền điều khiển sang middleware kế tiếp trong chuỗi.

Hình dung request như một dây chuyền lắp ráp: mỗi middleware là một trạm, làm một việc nhỏ rồi gọi next() để đẩy sản phẩm sang trạm sau. Một middleware có đúng ba lựa chọn:

➡️ Gọi next()

Chuyển sang middleware tiếp theo. Request đi tiếp trong chuỗi.

✅ Kết thúc response

Gọi res.send()/json()/end() → trả kết quả, không gọi next. Chuỗi dừng.

🔴 Gọi next(err)

Truyền lỗi → Express bỏ qua mọi middleware thường, nhảy thẳng tới error handler.

🐛 Cấm kỵ số 1: quên next()

Nếu một middleware không gọi next() mà cũng không kết thúc response, request sẽ treo vĩnh viễn — client chờ tới timeout. Đây là một trong những bug khó chịu nhất với người mới. Luật bất di bất dịch: mỗi middleware phải hoặc gọi next(), hoặc kết thúc response — chọn đúng một.

middleware-co-ban.jsNode.js
// Middleware log: ghi lại mọi request tới Contact Center API
function requestLogger(req, res, next) {
  console.log(`[${new Date().toISOString()}] ${req.method} ${req.url}`);
  next();                       // → bắt buộc, nếu không request treo
}

// Middleware xác thực agent: gắn req.agent rồi cho đi tiếp
function requireAgentAuth(req, res, next) {
  const token = req.headers.authorization;
  if (!token) {
    return res.status(401).json({ error: 'Thiếu token agent' }); // kết thúc, KHÔNG next
  }
  req.agent = verify(token);  // đính kèm dữ liệu cho middleware sau dùng
  next();
}

app.use(requestLogger);       // áp dụng cho MỌI request
app.get('/queues', requireAgentAuth, (req, res) => {
  res.json({ agent: req.agent.id, queues: listQueues() });
});
📌 Mẹo dùng return next()

Hãy đặt return trước next() hoặc res.json() khi nó nằm trong nhánh if. Quên return sẽ khiến code chạy tiếp xuống dưới và có thể gọi next() hai lần hoặc trả response hai lần → lỗi ERR_HTTP_HEADERS_SENT.

③ Thứ tự thực thi — luật tối quan trọng

Express chạy middleware theo đúng thứ tự bạn đăng ký chúng. Đây không phải chi tiết nhỏ — nó là nguyên lý vận hành của cả framework. Express duy trì một stack (ngăn xếp) các middleware; khi một request đến, nó duyệt stack từ trên xuống, gọi từng hàm khớp với path + method, và chỉ đi tiếp khi middleware trước gọi next().

Request đến→ helmet→ cors→ express.json()→ logger→ auth→ route handler→ res gửi về

Hệ quả thực tế: nếu bạn đặt express.json() sau route handler thì req.body trong handler sẽ là undefined — vì lúc handler chạy, middleware parse body còn chưa được gọi. Tương tự, middleware auth phải đứng trước các route cần bảo vệ.

thu-tu-quan-trong.jsNode.js
// ✅ ĐÚNG: parse body TRƯỚC khi handler đọc req.body
app.use(express.json());
app.post('/tickets', (req, res) => {
  res.json(createTicket(req.body)); // req.body có dữ liệu ✓
});

// ❌ SAI: handler chạy trước, req.body === undefined
app.post('/tickets', (req, res) => {
  res.json(createTicket(req.body)); // 💥 undefined
});
app.use(express.json());            // quá muộn
⚠️ Ba "vị trí thứ tự" cần thuộc lòng

1. Middleware bảo mật/parse (helmet, cors, json) → đặt đầu tiên.
2. Route handler nghiệp vụ → đặt giữa.
3. Middleware 404 (catch-all) và error handler (4 tham số) → đặt cuối cùng, sau mọi route.

Mặt đối ngẫu: matching theo path

Một middleware đăng ký bằng app.use(fn) (không có path) sẽ khớp với mọi request. Còn app.use('/admin', fn) chỉ khớp với các URL bắt đầu bằng /admin. Khác với route (app.get), app.use khớp theo tiền tố chứ không phải khớp chính xác toàn bộ path.

④ Các loại middleware

Express tài liệu hóa năm loại middleware. Phân biệt được chúng giúp bạn trả lời gọn câu hỏi phỏng vấn kinh điển "kể các loại middleware".

4.1 — Application-level

Gắn trực tiếp vào app. Có thể không kèm path (chạy cho mọi request) hoặc kèm path (chỉ chạy theo tiền tố).

application-level.jsNode.js
// Chạy cho MỌI request: gắn một id để truy vết log xuyên hệ thống
app.use((req, res, next) => {
  req.requestId = randomUUID();
  next();
});

// Chỉ chạy cho /admin/*: chặn nếu không phải supervisor
app.use('/admin', (req, res, next) => {
  if (req.agent?.role !== 'supervisor')
    return res.status(403).json({ error: 'Chỉ supervisor' });
  next();
});

4.2 — Router-level

Giống application-level nhưng gắn vào một express.Router(). Hữu ích để đóng gói cả route lẫn middleware của một domain vào một file (đã xem ở mục ①).

4.3 — Built-in

Express đóng gói sẵn vài middleware quan trọng:

  • express.json() — parse body có Content-Type: application/json thành req.body.
  • express.urlencoded() — parse body từ form HTML (application/x-www-form-urlencoded).
  • express.static() — phục vụ file tĩnh (ảnh avatar agent, file ghi âm tải xuống...).

Các loại còn lại (error-handling, third-party) được dành riêng cho mục ⑤ và ⑥ vì chúng đủ quan trọng để bàn sâu.

⑤ Error-handling middleware

Error-handling middleware là middleware có đúng bốn tham số: (err, req, res, next). Đây là điểm Express nhận diện "đây là hàm xử lý lỗi, không phải middleware thường". Cơ chế này dựa vào số lượng tham số (fn.length): Express kiểm tra length === 4 để phân biệt.

🐛 Vì sao "đúng 4 tham số" là bắt buộc

Nếu bạn viết hàm xử lý lỗi nhưng chỉ khai báo 3 tham số (req, res, next) — dù bên trong có dùng tới biến lỗi hay không — Express sẽ coi nó là middleware thường, không bao giờ đẩy lỗi vào đó. Ngược lại, nếu bạn không dùng next bên trong thì vẫn phải khai báo đủ 4 tham số (đặt tên next dù không gọi), nếu không Express không nhận diện được. Đây là cái bẫy bị hỏi rất nhiều khi phỏng vấn.

Cơ chế kích hoạt: khi bất kỳ middleware nào gọi next(err) với một đối số khác undefined, Express bỏ qua toàn bộ middleware và route thường còn lại trong stack, nhảy thẳng tới error handler đầu tiên (4 tham số).

middleware A→ next(err) 💥⤵ middleware B (bỏ qua) route handler (bỏ qua)→ error handler (err,req,res,next)
error-handler.jsNode.js
// Route ném lỗi đồng bộ — Express tự bắt và đưa vào error handler
app.get('/calls/:id', (req, res) => {
  const call = findCall(req.params.id);
  if (!call) {
    const err = new Error('Không tìm thấy cuộc gọi');
    err.status = 404;
    throw err;           // throw đồng bộ → Express tự next(err)
  }
  res.json(call);
});

// 404 catch-all: đặt SAU mọi route, TRƯỚC error handler
app.use((req, res, next) => {
  const err = new Error('Endpoint không tồn tại');
  err.status = 404;
  next(err);
});

// ⭐ ERROR HANDLER — đúng 4 tham số, đặt CUỐI CÙNG
app.use((err, req, res, next) => {
  console.error(`[${req.requestId}]`, err.message);
  res.status(err.status || 500).json({
    error: err.message,
    requestId: req.requestId,   // trả id để hỗ trợ tra cứu khi khách phàn nàn
  });
});
💡 Một error handler tập trung = nhất quán

Thay vì mỗi route tự res.status(500).json(...) theo kiểu riêng, hãy ném lỗi (throw / next(err)) và để một error handler trung tâm định dạng response. Lợi ích: format lỗi nhất quán cho toàn API (quan trọng với client là dashboard agent), log tập trung kèm requestId, và che giấu chi tiết nhạy cảm (stack trace) khỏi client trong môi trường production.

⑥ Middleware phổ biến (third-party)

Hệ sinh thái npm cung cấp các middleware "phải có" cho hầu hết API production. Biết vai trò của chúng là kiến thức nền cho mọi backend Node.

🛡️ helmet

Đặt một loạt HTTP security header (CSP, HSTS, X-Frame-Options...) để giảm rủi ro tấn công web phổ biến.

🌐 cors

Bật Cross-Origin Resource Sharing — cho phép dashboard agent (origin khác) gọi API của bạn từ trình duyệt.

📝 morgan

HTTP request logger gọn nhẹ — ghi method, path, status, thời gian phản hồi ra console/file.

🍪 cookie-parser

Parse header Cookie thành req.cookies — hữu ích cho session/refresh token.

🚦 express-rate-limit

Giới hạn số request theo IP/agent — chống lạm dụng endpoint nhạy cảm (login, gửi OTP).

🗜️ compression

Nén gzip response — giảm băng thông khi trả danh sách cuộc gọi/ticket lớn.

app.js — bộ middleware production điển hìnhNode.js
const express = require('express');
const helmet  = require('helmet');
const cors    = require('cors');
const morgan  = require('morgan');

const app = express();

// THỨ TỰ là tất cả: bảo mật → cors → log → parse → route → lỗi
app.use(helmet());                              // 1. security header
app.use(cors({ origin: 'https://agent.example.com' })); // 2. cho phép dashboard
app.use(morgan('tiny'));                       // 3. log request
app.use(express.json());                       // 4. parse JSON body

app.use('/agents', require('./routes/agents'));  // 5. route theo domain
app.use('/calls',  require('./routes/calls'));

app.use(errorHandler);                       // 6. error handler (4 tham số) — CUỐI
⚠️ CORS — bẫy "vì sao request bị chặn?"

Khi dashboard agent (origin https://agent.example.com) gọi API ở origin khác, trình duyệt áp dụng Same-Origin Policy và gửi preflight OPTIONS. Nếu thiếu middleware cors, response thiếu header Access-Control-Allow-Origin → trình duyệt chặn. Lưu ý: CORS chỉ chặn ở trình duyệt; gọi từ server-to-server (hay Postman) thì không bị ảnh hưởng.

⑦ Xử lý lỗi bất đồng bộ (async)

Đây là phần "tách người biết Express với người hiểu Express". Ở Express 4 (phiên bản phổ biến nhất trong nhiều năm), cơ chế tự bắt lỗi chỉ áp dụng cho lỗi đồng bộ. Nếu một handler là async và một Promise bị reject (hoặc bạn throw bên trong async), Express 4 KHÔNG tự đưa lỗi đó vào error handler — request sẽ treo và bạn thấy cảnh báo UnhandledPromiseRejection.

async-loi-bi-nuot.jsExpress 4
// ❌ NGUY HIỂM ở Express 4: lỗi async không vào error handler
app.get('/tickets/:id', async (req, res) => {
  const ticket = await db.findTicket(req.params.id); // nếu reject...
  res.json(ticket);   // 💥 lỗi rơi ra ngoài → request treo, không tới error handler
});

Cách 1 — try/catch + next(err)

async-trycatch.jsNode.js
app.get('/tickets/:id', async (req, res, next) => {
  try {
    const ticket = await db.findTicket(req.params.id);
    if (!ticket) return next({ status: 404, message: 'Ticket không tồn tại' });
    res.json(ticket);
  } catch (err) {
    next(err);          // ✅ chuyển lỗi vào error handler thủ công
  }
});

Cách 2 — wrapper (DRY, sạch hơn)

Viết try/catch ở mọi route rất lặp. Một higher-order function bọc handler async và tự gắn .catch(next) sẽ giúp code gọn:

asyncHandler.jsNode.js
// Bọc 1 handler async → mọi Promise reject tự chảy vào next(err)
const asyncHandler = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

// Dùng: không cần try/catch nữa
app.get('/tickets/:id', asyncHandler(async (req, res) => {
  const ticket = await db.findTicket(req.params.id);
  res.json(ticket);   // nếu reject → .catch(next) → error handler ✓
}));
📌 Express 5 thay đổi điều này

Từ Express 5, framework đã hỗ trợ tự bắt lỗi từ handler async (Promise reject sẽ tự chuyển vào error handler). Tuy nhiên, vì rất nhiều hệ thống production vẫn chạy Express 4, câu hỏi phỏng vấn vẫn xoay quanh hành vi của Express 4 và cách dùng wrapper. Thư viện express-async-errors hoặc các asyncHandler như trên là giải pháp phổ biến cho Express 4.

⚠️ Lỗi thường gặp & Best practices

🚫 Quên next()

Middleware không gọi next cũng không kết thúc response → request treo tới timeout.

🚫 Error handler 3 tham số

Thiếu tham số err đầu → Express coi là middleware thường, lỗi không bao giờ vào.

🚫 Đặt sai thứ tự

express.json() sau route → req.body undefined. Error handler trước route → vô dụng.

🚫 Lỗi async bị nuốt

Express 4 không tự bắt Promise reject → dùng try/catch hoặc asyncHandler.

🚫 Gọi response 2 lần

Quên return trong nhánh if → ERR_HTTP_HEADERS_SENT.

✅ Best practice

Mỗi domain một Router; một error handler tập trung; gắn requestId để truy vết.

🧪 Bài 1 — Middleware đo thời gian xử lý

Viết một middleware application-level đo thời gian từ lúc request đến tới lúc response gửi xong, rồi log method url status ms. Gợi ý: cần "hook" vào sự kiện response hoàn tất, không thể chỉ đo trước next().

Gợi ý

Ghi const start = Date.now() đầu hàm, gọi next(), và lắng nghe res.on('finish', () => { ... }) để biết khi response đã gửi xong. Trong callback finish tính Date.now() - start và log kèm res.statusCode. Đây chính xác là cách morgan hoạt động bên trong.

🧪 Bài 2 — Auth + RBAC bằng middleware

Viết hai middleware: requireAuth (chặn nếu thiếu token, gắn req.agent) và requireRole(role) (factory trả về middleware, chặn nếu req.agent.role không khớp). Áp dụng để chỉ supervisor mới DELETE /tickets/:id được.

Gợi ý

requireRole phải là hàm trả về hàm: const requireRole = (role) => (req, res, next) => { if (req.agent.role !== role) return res.status(403)...; next(); }. Đăng ký: app.delete('/tickets/:id', requireAuth, requireRole('supervisor'), handler). Thứ tự quan trọng: auth phải chạy trước để có req.agent.

🧪 Bài 3 — asyncHandler + error handler

Tạo một route POST /calls/:id/transfer gọi một hàm async transferCall() có thể reject. Dùng asyncHandler để lỗi tự vào một error handler trung tâm trả JSON { error, requestId }.

Gợi ý

Bọc handler bằng asyncHandler (như mục ⑦). Trong transferCall, ném Object.assign(new Error('Agent đích bận'), { status: 409 }). Error handler đọc err.status || 500. Kiểm tra: khi reject, response phải là 409 JSON, request không treo.

Ngân hàng câu hỏi phỏng vấn

Express & middleware — chủ đề "ruột" của mọi vòng phỏng vấn Node backend.

Q1Express là gì? Nó khác module http thuần của Node thế nào?Junior›

Trả lời: Express là một framework web tối giản cho Node, là lớp mỏng bọc quanh module http. Nó thêm routing (định tuyến URL + method), middleware (chuỗi xử lý request), và tiện ích trên req/res (res.json, res.status). Với http thuần bạn phải tự parse URL/method, tự set header, tự stringify; Express giảm hết phần lặp đó.

Q2Middleware là gì? Mô tả vai trò của next().Junior›

Trả lời: Middleware là hàm (req, res, next) chạy trong quá trình xử lý request. Nó có thể đọc/ghi req/res, làm một việc (log, auth, parse) rồi gọi next() để chuyển sang middleware kế tiếp. Một middleware có 3 lựa chọn: gọi next() để đi tiếp, kết thúc response (res.json()...) để dừng chuỗi, hoặc gọi next(err) để nhảy tới error handler.

Q3Thứ tự đăng ký middleware có quan trọng không? Cho ví dụ.Junior›

Trả lời: Cực kỳ quan trọng — Express chạy middleware theo đúng thứ tự đăng ký. Ví dụ: nếu đặt express.json() sau route thì req.body trong route sẽ undefined. Middleware auth phải đứng trước route cần bảo vệ. Error handler và 404 catch-all phải đặt cuối cùng, sau mọi route.

⚠️ Bẫy: ứng viên hay nói "thứ tự không quan trọng vì cùng là middleware". Sai — thứ tự quyết định luồng.

Q4Phân biệt app.use() và app.get().Middle›

Trả lời: app.get() gắn handler cho method GET và khớp path chính xác. app.use() gắn middleware cho mọi method và khớp theo tiền tố path (vd app.use('/admin') khớp /admin, /admin/x...). app.use() không kèm path sẽ khớp mọi request. Nói ngắn: get dành cho endpoint cụ thể, use dành cho middleware chung/nhóm.

Q5Error-handling middleware khác middleware thường ở điểm nào?Middle›

Trả lời: Error handler có đúng 4 tham số (err, req, res, next). Express dựa vào số tham số (fn.length === 4) để nhận diện. Nó chỉ được gọi khi có lỗi truyền qua next(err) (hoặc throw đồng bộ). Phải đặt nó cuối cùng, sau mọi route và middleware thường.

⚠️ Bẫy: viết handler lỗi với 3 tham số → Express coi là middleware thường, lỗi không bao giờ vào. Phải khai báo đủ 4 dù không dùng next.

Q6Một request đi qua middleware chain như thế nào? Mô tả luồng.Middle›

Trả lời: Express duy trì một stack middleware. Khi request đến, nó duyệt stack từ trên xuống, gọi từng middleware khớp với path + method. Mỗi middleware xử lý phần việc của mình rồi gọi next() để đẩy request sang mục kế tiếp; nếu gọi res.send/json thì chuỗi dừng và response được gửi; nếu gọi next(err) thì Express bỏ qua phần còn lại và nhảy tới error handler. Trong Contact Center điển hình: helmet → cors → json → logger → auth → route handler → error handler.

Q7Phân biệt app và express.Router(). Khi nào dùng Router?Middle›

Trả lời: app (từ express()) là ứng dụng gốc, có .listen(), là điểm vào server. Router là một mini-app có .get/.post/.use riêng nhưng không tự lắng nghe; bạn gắn nó vào app ở một prefix: app.use('/calls', callRouter). Dùng Router để chia API lớn thành module theo domain (agents, calls, tickets), gắn middleware riêng cho từng nhóm, và giữ code gọn — thay vì một file app.js khổng lồ.

Q8Liệt kê các loại middleware trong Express.Junior›

Trả lời: Năm loại: (1) application-level — gắn vào app.use/app.METHOD; (2) router-level — gắn vào express.Router(); (3) error-handling — hàm 4 tham số; (4) built-in — express.json, express.urlencoded, express.static; (5) third-party — cài qua npm như cors, helmet, morgan.

Q9Tại sao lỗi trong handler async không tự vào error handler ở Express 4? Cách xử lý?Senior›

Trả lời: Express 4 chỉ bao quanh việc gọi handler bằng try/catch đồng bộ. Khi handler là async, một Promise reject xảy ra sau khi hàm đã trả về (trả về một Promise pending), nên try/catch đồng bộ của Express không bắt được → lỗi rơi thành UnhandledPromiseRejection, request treo. Cách xử lý: (1) bọc body trong try/catch rồi next(err); (2) dùng wrapper asyncHandler = fn => (req,res,next) => Promise.resolve(fn(req,res,next)).catch(next); (3) dùng express-async-errors. Express 5 đã hỗ trợ tự bắt lỗi async.

⚠️ Bẫy: nói "Express tự bắt mọi lỗi" — chỉ đúng với lỗi đồng bộ ở v4, hoặc với v5.

Q10Khác biệt giữa middleware và route handler là gì?Middle›

Trả lời: Về bản chất chúng giống nhau — đều là hàm (req, res, next). Khác biệt là vai trò và vị trí: route handler thường là mắt xích cuối trong chuỗi, có nhiệm vụ tạo response cho một endpoint cụ thể; middleware là các mắt xích trước đó, làm việc dùng chung (log, auth, parse) và thường gọi next() để đi tiếp. Một route có thể có nhiều middleware xếp trước handler: app.post('/x', mwA, mwB, handler).

Q11Bạn thiết kế xử lý lỗi tập trung cho một API Contact Center thế nào?Senior›

Trả lời: Tôi không để mỗi route tự định dạng lỗi. Thay vào đó: (1) định nghĩa các lớp lỗi nghiệp vụ kèm status (vd NotFoundError 404, ConflictError 409); (2) trong route chỉ ném lỗi (throw / next(err)), dùng asyncHandler cho async; (3) một error handler trung tâm (4 tham số, đặt cuối) đọc err.status || 500, trả JSON nhất quán { error, requestId }, log kèm requestId để hỗ trợ tra cứu khi khách phàn nàn; (4) ở production che giấu stack trace, chỉ trả thông điệp an toàn. Thêm một middleware 404 catch-all ngay trước error handler. Cách này cho format lỗi đồng nhất — rất quan trọng vì client là dashboard agent cần xử lý lỗi nhất quán.

Q12CORS là gì và liên quan thế nào tới middleware Express?Senior›

Trả lời: CORS (Cross-Origin Resource Sharing) là cơ chế cho phép một trang web ở origin này gọi API ở origin khác qua trình duyệt, vượt qua Same-Origin Policy. Trình duyệt gửi preflight OPTIONS và đọc các header Access-Control-Allow-* từ response. Trong Express ta xử lý bằng middleware cors đặt ở đầu chuỗi, cấu hình origin cho phép (vd domain dashboard agent), methods, credentials. Điểm quan trọng: CORS chỉ là cơ chế của trình duyệt — gọi server-to-server hay từ Postman không bị chặn, nên đừng nhầm CORS là một lớp bảo mật server.

⚠️ Bẫy: coi CORS là "bảo mật API". CORS bảo vệ người dùng trình duyệt, không thay thế auth/authorization.
