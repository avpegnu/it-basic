Thiết kế RESTful API chuẩn

Thiết kế API rõ ràng, nhất quán, đúng ngữ nghĩa HTTP — kỹ năng được soi rất kỹ khi phỏng vấn backend.

🎯 Học xong chương này bạn sẽ

• Giải thích được 6 ràng buộc kiến trúc REST (Roy Fielding) và vì sao stateless là điều kiện sống còn để scale ngang.

• Đặt tên tài nguyên đúng chuẩn: danh từ số nhiều, lồng nhau hợp lý, không nhét động từ vào URL.

• Chọn đúng HTTP method dựa trên hai tính chất safe và idempotent; phân biệt PUT vs PATCH, POST vs PUT.

• Trả về đúng status code (200/201/204, 400/401/403/404/409/422/429, 5xx) thay vì "200 cho mọi thứ".

• Thiết kế versioning, pagination (offset vs cursor), filter và sort qua query string một cách nhất quán.

• Áp dụng tất cả để thiết kế bộ API thực chiến cho hệ thống Contact Center: agents, calls, tickets, conversations, queues.

💡 Liên hệ thực tế Contact Center

Một hệ thống Contact Center có rất nhiều client gọi vào cùng một backend: dashboard giám sát của supervisor, app của tổng đài viên (agent), widget chat trên website khách hàng, và cả service realtime đẩy sự kiện cuộc gọi. Nếu API không nhất quán — chỗ trả 200 kèm {error:...}, chỗ nhét /getAgentById vào URL, chỗ phân trang kiểu này chỗ kiểu khác — thì mỗi đội frontend phải đoán mò, bug tăng, onboard người mới rất chậm. REST chuẩn chính là hợp đồng (contract) chung giúp nhiều đội nói cùng một ngôn ngữ.

① Nguyên tắc REST

REST (REpresentational State Transfer) là một kiểu kiến trúc (architectural style) do Roy Fielding mô tả trong luận án tiến sĩ năm 2000 — không phải một giao thức hay một thư viện. Nó là tập hợp các ràng buộc (constraints) áp lên cách client và server giao tiếp qua HTTP. Tuân thủ càng nhiều ràng buộc, hệ thống càng dễ mở rộng, dễ cache, dễ tiến hóa độc lập.

6 ràng buộc kiến trúc

🔀 Client–Server

Tách bạch giao diện (client) khỏi lưu trữ/xử lý (server). Hai bên tiến hóa độc lập miễn là giữ nguyên hợp đồng API.

🚫 Stateless

Mỗi request chứa đủ thông tin để xử lý. Server không nhớ ngữ cảnh giữa các request (không session phía server).

📦 Cacheable

Response tự nói rõ nó có cache được không (qua header) để giảm tải, tăng tốc.

🎛️ Uniform Interface

Giao diện đồng nhất: tài nguyên có URI, thao tác qua method chuẩn, dữ liệu tự mô tả. Đây là ràng buộc cốt lõi.

🥞 Layered System

Client không biết mình đang nói với server gốc hay qua load balancer/cache/gateway. Cho phép chèn tầng trung gian.

💻 Code on Demand

(Tùy chọn) Server có thể gửi mã thực thi cho client. Hiếm dùng trong API thực tế.

⚠️ Stateless không có nghĩa là "không có state"

Dữ liệu (cuộc gọi, ticket) vẫn được lưu trong database — đó là application state. Cái mà REST yêu cầu là không lưu session state phía server cho từng client. Token xác thực (JWT) đi kèm mỗi request trong header Authorization, không phải lưu trong bộ nhớ server. Nhờ vậy bất kỳ instance Node nào trong cluster cũng xử lý được request — đây là điều kiện để scale ngang và đặt nhiều instance sau load balancer.

Uniform Interface có 4 nguyên tắc con

  • Identification of resources — mỗi tài nguyên định danh bằng một URI (vd /calls/42).
  • Manipulation through representations — client thao tác tài nguyên qua biểu diễn của nó (thường là JSON), không thao tác trực tiếp lên dữ liệu trong DB.
  • Self-descriptive messages — mỗi message tự mô tả: method, Content-Type, status code nói rõ phải hiểu nó thế nào.
  • HATEOAS (Hypermedia As The Engine Of Application State) — response chứa link để client biết hành động kế tiếp. Đây là mức cao nhất, ít dự án thực tế triển khai đầy đủ.

② Tài nguyên & URL

Trong REST, mọi thứ xoay quanh tài nguyên (resource) — một "danh từ" mà hệ thống quản lý: một cuộc gọi, một tổng đài viên, một ticket. URL chỉ định danh tài nguyên; hành động nằm ở HTTP method, không nằm trong URL.

💡 Lồng nhau bao sâu là vừa?

Quy tắc kinh nghiệm: không lồng quá 2 cấp. /calls/42/recordings đọc tốt. Nhưng /agents/77/calls/42/recordings/9/segments thì khó dùng — hãy phẳng hóa: /recordings/9/segments. Lồng nhau chỉ nên dùng khi tài nguyên con thực sự thuộc về cha và ít khi truy cập độc lập.

Sub-resource và "action" không tự nhiên

Đôi khi có thao tác không ánh xạ gọn vào CRUD — ví dụ "chuyển tiếp cuộc gọi" hay "kết thúc cuộc gọi". Có vài lựa chọn:

  • Coi action như một sub-resource trạng thái: POST /calls/42/transfers tạo một bản ghi chuyển tiếp.
  • Cập nhật trạng thái qua PATCH /calls/42 với body {"status":"ended"}.
  • Khi thực sự cần verb (hiếm), dùng quy ước rõ ràng: POST /calls/42/hangup — chấp nhận lệch REST thuần một chút để dễ hiểu hơn.

③ HTTP methods & tính chất

Mỗi HTTP method mang ngữ nghĩa riêng. Hai tính chất quan trọng nhất khi phỏng vấn:

  • Safe — không làm thay đổi state trên server (chỉ đọc). Có thể gọi thoải mái, prefetch, cache.
  • Idempotent — gọi 1 lần hay N lần liên tiếp cho cùng kết quả state. Cực kỳ quan trọng cho retry khi mạng chập chờn.
MethodÝ nghĩaSafeIdempotentCó body?
GETĐọc tài nguyênCóCóKhông
POSTTạo mới / kích hoạt xử lýKhôngKhôngCó
PUTThay thế toàn bộ tài nguyênKhôngCóCó
PATCHCập nhật một phầnKhôngThường không*Có
DELETEXóa tài nguyênKhôngCóHiếm
HEADNhư GET nhưng chỉ headerCóCóKhông
OPTIONSHỏi method/CORS được phépCóCóKhông
⚠️ Vì sao PATCH "thường không" idempotent?

Phụ thuộc nội dung patch. Nếu PATCH gửi giá trị tuyệt đối ({"priority":3}) thì lặp lại vô hại → idempotent. Nhưng nếu PATCH mang ngữ nghĩa tương đối ({"op":"increment","field":"attempts"}) thì gọi 2 lần ra 2 kết quả khác nhau → không idempotent. PUT thì luôn idempotent vì nó thay thế toàn bộ bằng cùng một representation.

PUT vs PATCH — minh họa với ticket

put-vs-patch.httpHTTP
# Giả sử ticket 88 hiện tại:
# { "id":88, "subject":"Không gọi được", "priority":2, "status":"open", "assignee":"agent-12" }

# PUT = THAY THẾ TOÀN BỘ. Thiếu field nào -> field đó bị xóa/đặt mặc định!
PUT /v1/tickets/88
Content-Type: application/json

{ "subject": "Không gọi được", "priority": 3, "status": "open", "assignee": "agent-12" }
# Gọi lại y hệt 5 lần -> ticket vẫn vậy => IDEMPOTENT

# PATCH = CHỈ SỬA PHẦN GỬI LÊN. Các field khác giữ nguyên.
PATCH /v1/tickets/88
Content-Type: application/json

{ "priority": 3 }
# Chỉ priority đổi thành 3; subject/status/assignee không đụng tới.
🐛 Cạm bẫy thực tế

Rất nhiều bug "tự dưng mất dữ liệu" đến từ việc frontend dùng PUT nhưng chỉ gửi vài field. Server thay thế toàn bộ, các field không gửi bị về null. Với ticket Contact Center, assignee hay tags biến mất là sự cố nghiêm trọng. Nguyên tắc: cập nhật một phần thì dùng PATCH, và validate kỹ ở C3.

④ Status code chi tiết

Status code là một phần của self-descriptive message. Trả đúng code giúp client xử lý đúng mà không cần đọc body. Nhóm theo lớp: 2xx thành công, 3xx chuyển hướng, 4xx lỗi phía client, 5xx lỗi phía server.

201CreatedPOST tạo mới thành công. Nên kèm header Location: /v1/calls/42.
202AcceptedNhận yêu cầu nhưng xử lý bất đồng bộ (vd: yêu cầu xuất bản ghi cuộc gọi, đẩy vào queue).
204No ContentDELETE thành công, hoặc cập nhật không cần trả body.
301Moved PermanentlyEndpoint đổi vĩnh viễn. Client nên cập nhật URL.
304Not ModifiedDùng với ETag/If-None-Match — tài nguyên chưa đổi, client dùng bản cache.

⚠️ 401 vs 403 — phân biệt rõ

401 = "tôi không biết bạn là ai" (chưa/sai xác thực) → client nên đăng nhập lại / refresh token. 403 = "tôi biết bạn là ai nhưng bạn không được phép" (đã xác thực, thiếu quyền) → đăng nhập lại cũng vô ích. Trả nhầm sẽ khiến frontend xử lý sai (vd cứ logout người dùng dù chỉ là thiếu quyền). Chi tiết phân quyền ở C4.

⚠️ 400 vs 422 — cú pháp vs nghiệp vụ

400: request không hợp lệ về cú pháp/cấu trúc — JSON parse lỗi, thiếu field bắt buộc, sai kiểu dữ liệu. 422: cú pháp đúng, parse được, nhưng vi phạm luật nghiệp vụ — vd priority: 99 trong khi chỉ chấp nhận 1–5, hay tạo cuộc gọi cho agent đã offline. Nhiều team gộp cả hai vào 400 cũng được, miễn nhất quán và body mô tả lỗi rõ ràng.

⑤ Versioning

API là hợp đồng công khai. Khi bạn cần thay đổi không tương thích ngược (breaking change) — đổi tên field, đổi kiểu, bỏ endpoint — bạn không được phá vỡ các client cũ đang chạy. Versioning cho phép vận hành song song nhiều phiên bản trong giai đoạn chuyển đổi.

CáchVí dụƯuNhược
URL path/v1/calls · /v2/callsRõ ràng, dễ test trên trình duyệt, dễ route/cacheKhông "thuần REST" (cùng tài nguyên, khác URI); lan ra mọi đường dẫn
HeaderAccept: application/vnd.cc.v2+jsonGiữ URI sạch, đúng tinh thần content negotiationKhó test bằng tay, dễ quên, cache phức tạp hơn
Query param/calls?version=2Đơn giảnDễ lẫn với filter; ít dùng cho versioning lớn
💡 Thực tế đa số chọn URL path

Versioning qua /v1, /v2 trong path là phổ biến nhất vì dễ hiểu, dễ vận hành, dễ định tuyến ở gateway. Quy tắc vàng: chỉ tăng version khi có breaking change. Thêm field mới (không bắt buộc) hay endpoint mới là tương thích ngược → không cần version mới. Hãy đặt version ngay từ ngày đầu (/v1/...) để sau này không phải refactor toàn bộ.

⑥ Pagination, filter, sort

Một endpoint danh sách như GET /calls không bao giờ được trả về toàn bộ hàng triệu bản ghi. Phải phân trang. Filter và sort được biểu diễn qua query string — vì chúng là cách xem collection, không tạo ra tài nguyên mới.

Offset vs Cursor pagination

Tiêu chíOffset (limit/offset, page)Cursor (keyset)
Ví dụGET /calls?limit=20&offset=40GET /calls?limit=20&cursor=eyJpZCI6OTl9
Cách hoạt độngDB bỏ qua N dòng đầu rồi lấy tiếpLấy các dòng "sau" một mốc (id/timestamp) đã mã hóa trong cursor
Hiệu năng khi offset lớnChậm dần (DB vẫn quét N dòng bỏ đi)Ổn định (dùng index, không quét thừa)
Dữ liệu thay đổi liên tụcLệch trang (bản ghi mới chèn vào làm trùng/sót)Ổn định
Nhảy tới trang bất kỳDễ (trang 7)Khó (chỉ tiến/lùi tuần tự)
Hợp vớiBảng admin, dữ liệu nhỏ/ổn định, cần số trangFeed realtime, log cuộc gọi, "tải thêm" vô hạn
🐛 Vì sao Contact Center hay chọn cursor cho log cuộc gọi

Log cuộc gọi sinh ra liên tục — mỗi giây thêm bản ghi mới ở đầu danh sách (sort theo thời gian giảm dần). Với offset, khi supervisor cuộn sang "trang 2", các cuộc gọi mới vừa chèn vào trang 1 sẽ đẩy mọi thứ xuống → trang 2 bị trùng bản ghi đã thấy hoặc sót bản ghi. Cursor (keyset, bám theo id/startedAt) không bị hiện tượng này và còn nhanh hơn ở dữ liệu lớn.

Quy ước query thống nhất

list-query.httpHTTP
# Filter: dùng tên field làm key
GET /v1/calls?status=missed&queue=sales&agentId=12

# Filter theo khoảng thời gian
GET /v1/calls?startedAfter=2026-06-01T00:00:00Z&startedBefore=2026-06-09T00:00:00Z

# Sort: dấu '-' = giảm dần, nhiều field ngăn bởi dấu phẩy
GET /v1/calls?sort=-startedAt,duration

# Pagination kiểu cursor
GET /v1/calls?limit=20&cursor=eyJpZCI6OTl9

# Chọn field trả về (sparse fieldset) để response gọn
GET /v1/calls?fields=id,status,startedAt,agentId

⑦ Thiết kế API Contact Center

Giờ ta gom mọi thứ lại để thiết kế một bộ API thực chiến. Tư duy thiết kế luôn đi theo trình tự: (1) liệt kê tài nguyên & quan hệ, (2) ánh xạ thao tác vào method, (3) chọn status code & phân trang, (4) cân nhắc đánh đổi.

Bước 1 — Mô hình tài nguyên & quan hệ

queues (hàng đợi)→ calls (cuộc gọi)→ recordings
agents (tổng đài viên)↔ calls→ tickets→ conversations / messages

Các tài nguyên gốc (top-level): agents, queues, calls, tickets, conversations. Sub-resource: recordings của một call, messages của một conversation.

Bước 3 — Code thực chiến: route Express tạo cuộc gọi

routes/calls.jsNode.js
const router = express.Router();

// POST /v1/calls — tạo cuộc gọi outbound. Idempotency-Key chống tạo trùng khi retry.
router.post('/calls', async (req, res) => {
  const { agentId, to, queue } = req.body;

  // 1) Validate cú pháp -> 400 (chi tiết ở C3)
  if (!agentId || !to) {
    return res.status(400).json({ error: { code: 'BAD_REQUEST', message: 'Thiếu agentId hoặc to' } });
  }

  const agent = await agents.find(agentId);
  if (!agent) {
    return res.status(422).json({ error: { code: 'AGENT_NOT_FOUND', message: 'Agent không tồn tại' } });
  }

  // 2) Xung đột trạng thái -> 409
  if (agent.status !== 'available') {
    return res.status(409).json({ error: { code: 'AGENT_BUSY', message: 'Agent đang không sẵn sàng' } });
  }

  // 3) Idempotency: cùng key -> trả về call đã tạo, không tạo mới
  const key = req.get('Idempotency-Key');
  const existing = key && await calls.findByIdempotencyKey(key);
  if (existing) return res.status(200).json(existing);

  const call = await calls.create({ agentId, to, queue, status: 'dialing', idempotencyKey: key });

  // 4) 201 + Location trỏ tới tài nguyên vừa tạo
  res.status(201).location(`/v1/calls/${call.id}`).json(call);
});
💡 Idempotency-Key — vũ khí cho POST không idempotent

POST vốn không idempotent: gọi 2 lần tạo 2 cuộc gọi. Nhưng mạng di động hay rớt → client retry. Giải pháp chuẩn: client sinh một Idempotency-Key (UUID) gửi kèm header; server lưu key này. Lần retry cùng key → server trả về kết quả cũ thay vì tạo mới. Cực kỳ quan trọng với thao tác "tốn tiền" như khởi tạo cuộc gọi hay gửi SMS.

Bước 4 — Đánh đổi & Richardson Maturity Model

Mức độ "RESTful" được đo bằng Richardson Maturity Model (4 level từ 0 tới 3):

⚠️ Lỗi thường gặp & Best practices

🚫 "200 cho mọi thứ"

Trả 200 kèm {success:false} khiến client không thể dựa vào status code. Dùng đúng 4xx/5xx.

🚫 Verb trong URL

/getCall, /createTicket — hành động thuộc về method, không thuộc URL.

🚫 PUT để cập nhật một phần

Làm mất các field không gửi. Dùng PATCH cho cập nhật bộ phận.

🚫 Quên phân trang

GET /calls trả triệu bản ghi → sập client và server. Luôn có limit mặc định.

🚫 Lẫn 401 và 403

Gây logout oan hoặc lộ thông tin. Phân biệt unauthenticated vs unauthorized.

🚫 Lưu session trong RAM server

Phá vỡ stateless → không scale ngang được. Dùng token tự chứa hoặc store ngoài.

✅ Format lỗi nhất quán

Luôn cùng một hình dạng {error:{code,message,...}} để client xử lý chung.

✅ Versioning từ ngày đầu

Đặt /v1 ngay từ đầu để sau này thêm /v2 không phải refactor.

🧪 Bài tập

🧪 Bài 1 — Sửa API "xấu" thành RESTful

Một dịch vụ cũ có các endpoint sau. Hãy thiết kế lại cho đúng chuẩn REST (method + path + status code):

  • POST /api?action=getAgent&id=12
  • POST /createTicket (luôn trả 200 {ok:false} khi lỗi)
  • GET /listAllCalls (trả toàn bộ, không phân trang)
Gợi ý

(1) GET /v1/agents/12 → 200 / 404. (2) POST /v1/tickets → 201 nếu OK, 422 nếu vi phạm nghiệp vụ, 400 nếu thiếu field; body lỗi dạng {error:{code,message}}. (3) GET /v1/calls?limit=20&cursor=...&sort=-startedAt → 200, có phân trang cursor và limit mặc định.

🧪 Bài 2 — Chọn method & status code

Cho mỗi tình huống, chọn method, path và status code hợp lý:

  • Agent đổi trạng thái sang busy.
  • Tạo cuộc gọi nhưng agent đang offline.
  • Xóa một bản ghi (recording) đã tồn tại.
  • Gửi tin nhắn vào hội thoại đã đóng.
Gợi ý

(1) PATCH /v1/agents/{id} body {"status":"busy"} → 200. (2) POST /v1/calls → 409 (Conflict) vì xung đột trạng thái, hoặc 422 nếu coi là vi phạm nghiệp vụ — miễn nhất quán. (3) DELETE /v1/recordings/{id} → 204 (No Content). (4) POST /v1/conversations/{id}/messages → 409 vì hội thoại đã đóng.

🧪 Bài 3 — Pagination cho log cuộc gọi

Supervisor cần xem log cuộc gọi realtime, cuộn vô hạn, dữ liệu liên tục thêm mới. Bạn chọn offset hay cursor? Thiết kế query và response.

Gợi ý

Chọn cursor vì dữ liệu thay đổi liên tục (tránh trùng/sót trang) và nhanh ở dữ liệu lớn. Query: GET /v1/calls?limit=20&cursor=...&sort=-startedAt. Response gồm data[] + pagination:{nextCursor,hasMore}. Cursor mã hóa mốc cuối (vd id hoặc startedAt) bằng base64.

Ngân hàng câu hỏi phỏng vấn

Thiết kế REST API — chủ đề được soi rất kỹ ở vòng backend.

Q1REST là gì? Nó là giao thức hay kiểu kiến trúc?Junior›

Trả lời: REST là một kiểu kiến trúc (architectural style) do Roy Fielding mô tả, không phải giao thức hay thư viện. Nó đặt ra các ràng buộc về cách client–server giao tiếp (thường qua HTTP): client-server, stateless, cacheable, uniform interface, layered system, và code-on-demand (tùy chọn). Mục tiêu là hệ thống dễ scale, dễ cache, dễ tiến hóa độc lập.

Q2Phân biệt safe và idempotent. Cho ví dụ.Junior›

Trả lời: Safe = không thay đổi state server (chỉ đọc) — GET, HEAD. Idempotent = gọi 1 hay N lần cho cùng kết quả state — GET, PUT, DELETE. Một method có thể idempotent mà không safe: PUT, DELETE đổi state nhưng lặp lại vô hại. POST thì không safe, không idempotent.

⚠️ Bẫy: "idempotent nghĩa là response giống nhau" — sai. DELETE lần 2 có thể trả 404 thay vì 204, nhưng state cuối vẫn là "đã xóa" → vẫn idempotent.

Q3PUT khác PATCH thế nào? Khi nào dùng cái nào?Middle›

Trả lời: PUT thay thế toàn bộ tài nguyên bằng representation gửi lên — thiếu field nào field đó bị xóa/đặt mặc định → luôn idempotent. PATCH cập nhật một phần — chỉ đụng field gửi lên. Dùng PUT khi client có và muốn ghi đè toàn bộ; dùng PATCH khi chỉ đổi vài trường (vd đổi priority ticket).

⚠️ Bẫy thực chiến: dùng PUT mà chỉ gửi vài field sẽ làm mất dữ liệu các field còn lại.

Q4PATCH có idempotent không?Middle›

Trả lời: Tùy nội dung. PATCH với giá trị tuyệt đối ({"priority":3}) thì lặp lại vô hại → idempotent. PATCH mang ngữ nghĩa tương đối ({"op":"increment"}) thì mỗi lần ra kết quả khác → không idempotent. Vì vậy spec nói PATCH "không bắt buộc idempotent".

Q5Phân biệt 401 và 403.Junior›

Trả lời: 401 Unauthorized thực ra là "unauthenticated" — chưa đăng nhập, token thiếu/sai/hết hạn; client nên đăng nhập lại. 403 Forbidden — đã xác thực nhưng không có quyền với tài nguyên này; đăng nhập lại không giúp được. Trong Contact Center: agent chưa có token → 401; agent cố sửa ticket team khác → 403.

Q6Khi nào trả 400 vs 422 vs 409?Middle›

Trả lời: 400: sai cú pháp/cấu trúc (JSON hỏng, thiếu field bắt buộc, sai kiểu). 422: cú pháp đúng nhưng vi phạm luật nghiệp vụ (priority ngoài khoảng, email sai định dạng). 409: xung đột state (agent đang busy mà nhận thêm call, trùng khóa duy nhất). Quan trọng là nhất quán trong toàn API; một số team gộp 422 vào 400 cũng được, miễn body mô tả rõ.

Q7Offset pagination khác cursor pagination ra sao? Khi nào chọn cái nào?Senior›

Trả lời: Offset (limit/offset) cho phép nhảy tới trang bất kỳ, dễ làm UI số trang, nhưng chậm khi offset lớn (DB vẫn quét rồi bỏ N dòng) và lệch trang khi dữ liệu thay đổi. Cursor (keyset) lấy các dòng sau một mốc đã mã hóa, nhanh và ổn định trên dữ liệu biến động, nhưng chỉ tiến/lùi tuần tự. Log cuộc gọi realtime → cursor; bảng admin nhỏ cần số trang → offset.

Q8"Stateless" trong REST nghĩa là gì? Vì sao quan trọng để scale?Senior›

Trả lời: Mỗi request phải mang đủ thông tin để xử lý; server không lưu session state riêng cho từng client giữa các request (token đi kèm mỗi request). Nhờ vậy bất kỳ instance nào sau load balancer cũng xử lý được request đó → scale ngang dễ dàng, instance chết không mất phiên. Lưu ý: dữ liệu nghiệp vụ vẫn nằm trong DB (application state), stateless chỉ nói về session.

⚠️ Bẫy: nói "REST không có state nào cả" là sai — chỉ là không có session state phía server.

Q9POST không idempotent — làm sao chống tạo trùng khi client retry?Senior›

Trả lời: Dùng Idempotency-Key: client sinh một UUID gửi kèm header; server lưu key cùng kết quả. Lần retry với cùng key, server trả lại kết quả cũ thay vì tạo bản ghi mới. Rất quan trọng với thao tác "tốn kém" như khởi tạo cuộc gọi, gửi SMS, thanh toán. Ngoài ra có thể dùng ràng buộc unique ở DB để chặn trùng ở tầng dữ liệu.

Q10REST vs GraphQL — đánh đổi là gì?Middle›

Trả lời: GraphQL cho client tự khai báo cần field nào → giảm over/under-fetching, hợp UI phức tạp nhiều màn hình. REST đơn giản, caching HTTP mạnh (theo URL + verb), hợp API công khai/CRUD nhiều client. Nhược GraphQL: caching khó (thường POST tới một endpoint), dễ bị query nặng, cần kiểm soát độ phức tạp. Thực tế hay lai: REST/gRPC cho service, GraphQL ở tầng BFF khi cần tổng hợp dữ liệu.

Q11Versioning API thế nào? URL hay header?Middle›

Trả lời: Phổ biến nhất là version trong URL path (/v1, /v2) vì rõ ràng, dễ test, dễ route/cache ở gateway. Cách "thuần REST" hơn là dùng header content negotiation (Accept: application/vnd.x.v2+json) nhưng khó test bằng tay. Nguyên tắc: chỉ tăng version khi có breaking change; thêm field optional hay endpoint mới là tương thích ngược, không cần version mới.

Q12HATEOAS là gì? Có cần triển khai trong thực tế không?Senior›

Trả lời: HATEOAS (Hypermedia As The Engine Of Application State) là mức cao nhất (level 3 Richardson): response chứa các link hành động kế tiếp, để client điều hướng theo hypermedia thay vì hard-code URL. Ví dụ object call trả kèm _links tới hangup, transfer. Thực tế đa số API dừng ở level 2 (dùng đúng verb + status code) vì HATEOAS làm response nặng và client thường vẫn hard-code đường dẫn. Biết khái niệm là đủ ghi điểm.
