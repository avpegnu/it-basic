MongoDB & Mongoose

Cơ sở dữ liệu document linh hoạt — phù hợp với tin nhắn chat, dữ liệu bán cấu trúc và mô hình phát triển nhanh.

🎯 Học xong chương này bạn sẽ

• Hiểu mô hình document/collection/BSON và vì sao MongoDB được gọi là "schema linh hoạt".

• Thành thạo CRUD và các query operators ($gt, $in, $set, $push...), projection.

• Viết được aggregation pipeline ($match, $group, $lookup, $unwind, $project) để tổng hợp báo cáo.

• Chọn đúng giữa embedding và referencing dựa trên read pattern, giới hạn 16MB và tính nguyên tử.

• Dùng Mongoose: Schema, model, validation, middleware pre/post, populate, virtuals, lean().

• Áp dụng các schema design patterns (bucket, subset, computed, extended reference) cho hệ thống thực.

💡 Liên hệ hệ thống Contact Center

Một Contact Center sinh ra lượng dữ liệu bán cấu trúc và biến thiên rất cao: lịch sử tin nhắn chat, metadata cuộc gọi, sự kiện hàng đợi (queue), trạng thái agent, payload webhook từ nhà mạng... Mỗi kênh (chat, call, email, social) có schema khác nhau và thay đổi liên tục. MongoDB hợp với những phần này nhờ schema linh hoạt và khả năng ghi nhanh; trong khi dữ liệu giao dịch chặt chẽ (ví ngân quỹ, hợp đồng) thường vẫn để bên SQL (xem D1). Chương này tập trung phần "document" của một kiến trúc dữ liệu lai (polyglot persistence).

① Mô hình document

MongoDB không lưu dữ liệu thành hàng/cột như cơ sở dữ liệu quan hệ. Đơn vị dữ liệu là document — một bản ghi dạng JSON lồng nhau (key/value), được nhóm lại trong collection (tương đương "bảng"), và các collection nằm trong một database. Không có khái niệm JOIN cứng hay khoá ngoại bắt buộc ở tầng lưu trữ.

Database⊃ Collection (≈ bảng)⊃ Document (≈ hàng, dạng JSON)⊃ Field (key/value, có thể lồng)

BSON — định dạng lưu trữ thật sự

Bên dưới, document không lưu dạng text JSON mà lưu dạng BSON (Binary JSON) — biểu diễn nhị phân, gọn và nhanh để duyệt/parse. BSON bổ sung các kiểu mà JSON thuần không có: ObjectId, Date, Decimal128, Binary, Int32/Int64... Một số điểm cần nhớ:

  • Mỗi document bắt buộc có _id; nếu không truyền, MongoDB tự sinh ObjectId (12 byte: timestamp + máy + counter) — gần như duy nhất toàn cục và chứa sẵn thời điểm tạo.
  • Một document tối đa 16MB. Đây là ràng buộc thiết kế quan trọng (sẽ bàn ở mục ⑤).
  • Date trong BSON là mốc thời gian UTC (mili-giây kể từ epoch) — luôn lưu UTC, chuyển múi giờ ở tầng ứng dụng.
message.document.jsonBSON / document
{
  "_id": ObjectId("66f1a2..."),     // tự sinh, chứa cả timestamp
  "conversationId": "conv_8821",
  "channel": "chat",               // chat | call | email | social
  "sender": { "type": "customer", "id": "cus_42" },
  "text": "Tôi chưa nhận được hoá đơn",
  "attachments": [],            // mảng — không cần bảng phụ
  "meta": { "ua": "iOS", "lang": "vi" }, // lồng tuỳ kênh
  "createdAt": ISODate("2026-06-09T03:14:00Z")
}

"Schema-less" — hiểu cho đúng

MongoDB thường được giới thiệu là schema-less. Câu này dễ gây hiểu lầm. Chính xác hơn: MongoDB không bắt buộc schema ở tầng lưu trữ, nhưng dữ liệu của bạn vẫn luôn có một schema ngầm mà ứng dụng phải hiểu. "Linh hoạt" nghĩa là:

🧬 Polymorphic

Hai document trong cùng collection có thể có tập field khác nhau — ví dụ message kênh call có duration, kênh chat thì không.

🚀 Evolvable

Thêm field mới không cần ALTER TABLE/migration đồng loạt; document cũ vẫn dùng được, code đọc cần xử lý field thiếu.

⚠️ Vẫn cần kỷ luật

Không có ràng buộc tầng DB nghĩa là ứng dụng phải giữ tính nhất quán — đây là lúc Mongoose validation lên tiếng (mục ⑥).

⚠️ "Linh hoạt" không phải là "không cần thiết kế"

Hệ thống thất bại với MongoDB thường không phải vì DB yếu, mà vì đội ngũ tưởng "schema-less = khỏi nghĩ". Vẫn phải quyết định embed hay reference, đặt index gì, document có phình tới 16MB không. Thiết kế document = thiết kế theo cách bạn đọc dữ liệu.

② CRUD & query operators

CRUD trong MongoDB xoay quanh các method trên collection. Điểm khác biệt lớn so với SQL: điều kiện lọc và phép cập nhật đều là document (object), dùng các operator bắt đầu bằng $.

Create — chèn dữ liệu

create.jsmongo shell
db.messages.insertOne({ conversationId: "conv_8821", text: "Xin chào", channel: "chat" });

db.messages.insertMany([
  { conversationId: "conv_8821", channel: "chat", text: "A" },
  { conversationId: "conv_8821", channel: "chat", text: "B" }
]);

Read — find, operator so sánh & projection

Các operator hay dùng nhất khi lọc:

OperatorNghĩaVí dụ (ngữ cảnh Contact Center)
$eq / $neBằng / khác{ status: { $ne: "closed" } } — ticket chưa đóng
$gt $gte $lt $lteSo sánh lớn/nhỏ{ waitSec: { $gt: 30 } } — chờ quá 30 giây
$in / $ninThuộc / không thuộc tập{ channel: { $in: ["chat","social"] } }
$and $or $norLogic{ $or: [{priority:"high"}, {waitSec:{$gt:60}}] }
$existsField có tồn tại không{ assignedAgent: { $exists: false } } — chưa gán agent
$regexKhớp biểu thức chính quy{ text: { $regex: /hoàn tiền/i } }
$elemMatchKhớp 1 phần tử mảng theo nhiều điều kiệnTìm conversation có tag vừa vip vừa vi
read.jsmongo shell
// Tìm các cuộc hội thoại chat đang mở, chờ > 30s, sắp xếp mới nhất, 20 dòng
db.conversations.find(
  { channel: "chat", status: "open", waitSec: { $gt: 30 } },
  { text: 1, waitSec: 1, _id: 0 }   // projection: chỉ lấy 2 field, bỏ _id
).sort({ createdAt: -1 }).limit(20);

Projection là cách chọn cột trả về: 1 = lấy, 0 = bỏ (không trộn lẫn được, trừ _id). Projection tốt giúp giảm băng thông và bộ nhớ — rất quan trọng khi document chứa mảng tin nhắn lớn.

Update — operator cập nhật

Khác SQL UPDATE, MongoDB dùng operator để mô tả cách thay đổi:

OperatorTác dụng
$setGán/ghi đè giá trị field
$unsetXoá field khỏi document
$incTăng/giảm số (nguyên tử) — đếm tin nhắn chưa đọc
$push / $pullThêm/xoá phần tử mảng
$addToSetThêm vào mảng nếu chưa tồn tại (tránh trùng tag)
$min / $maxChỉ cập nhật nếu nhỏ/lớn hơn giá trị hiện tại
update.jsmongo shell
// Gán agent cho ticket và tăng số lần được phục vụ — một thao tác nguyên tử
db.tickets.updateOne(
  { _id: ticketId, assignedAgent: { $exists: false } },  // chỉ gán nếu chưa ai cầm
  {
    $set:  { assignedAgent: "agent_07", status: "in_progress" },
    $inc:  { handoffCount: 1 },
    $push: { events: { type: "assigned", at: new Date() } }
  }
);

// Upsert: thêm tag không trùng vào conversation; tạo mới nếu chưa có
db.conversations.updateOne(
  { _id: convId },
  { $addToSet: { tags: "vip" } },
  { upsert: true }
);
💡 Cập nhật có điều kiện = chống race condition

Mẫu updateOne({ _id, assignedAgent: {$exists:false} }, {...}) ở trên là một compare-and-set nguyên tử ở cấp document. Khi hai agent cùng bấm "nhận cuộc" một lúc, chỉ một lệnh thành công (kiểm tra modifiedCount). Đây là kỹ thuật chống tranh chấp cực hữu ích trong phân phối hàng đợi mà không cần lock thủ công.

Delete

deleteOne / deleteMany theo filter. Trong thực tế Contact Center thường soft-delete (gắn deletedAt) thay vì xoá thật, để giữ lịch sử kiểm toán cuộc gọi/chat.

③ Aggregation pipeline

find chỉ lọc và trả document. Khi cần tổng hợp, nhóm, biến đổi dữ liệu (báo cáo SLA, đếm cuộc gọi theo agent, thời gian xử lý trung bình), ta dùng aggregation pipeline — một chuỗi stage, output của stage này là input của stage sau, giống một dây chuyền xử lý dữ liệu.

Documents→ $match→ $unwind→ $group→ $sort→ $project→ Kết quả
StageVai tròTương đương SQL
$matchLọc document (đặt sớm để giảm dữ liệu)WHERE
$groupNhóm theo khoá, tính tổng/đếm/trung bìnhGROUP BY + aggregate
$projectChọn/đổi tên/tính field mớiSELECT ... AS
$sortSắp xếpORDER BY
$limit / $skipPhân trangLIMIT / OFFSET
$unwind"Bung" mảng thành nhiều document (mỗi phần tử 1 dòng)≈ JOIN với bảng con

report-agent-sla.jsaggregation
// Báo cáo: với mỗi agent, số cuộc đã đóng hôm nay và thời gian xử lý trung bình
db.tickets.aggregate([
  { $match: {                       // 1) lọc trước cho rẻ — dùng được index
      status: "closed",
      closedAt: { $gte: ISODate("2026-06-09T00:00:00Z") }
  }},
  { $group: {                       // 2) gom theo agent
      _id: "$assignedAgent",
      total:     { $sum: 1 },
      avgHandle: { $avg: "$handleSec" },
      maxHandle: { $max: "$handleSec" }
  }},
  { $sort: { total: -1 } },         // 3) agent xử lý nhiều nhất lên đầu
  { $project: {                     // 4) định dạng đầu ra
      _id: 0,
      agent: "$_id",
      total: 1,
      avgHandleSec: { $round: ["$avgHandle", 0] }
  }}
]);

$lookup & $unwind — nối dữ liệu

$lookup cho phép "join" mềm sang collection khác — ví dụ gắn thông tin profile agent vào báo cáo. Kết quả là một mảng; thường theo sau bởi $unwind để làm phẳng.

lookup-agent.jsaggregation
db.tickets.aggregate([
  { $match: { status: "closed" } },
  { $lookup: {
      from: "agents",            // collection cần nối
      localField: "assignedAgent", // field bên tickets
      foreignField: "code",        // field bên agents
      as: "agent"               // kết quả là mảng "agent"
  }},
  { $unwind: "$agent" },        // làm phẳng mảng 1 phần tử
  { $project: { _id: 0, ticket: "$_id", team: "$agent.team" } }
]);
⚠️ $lookup không miễn phí

$lookup chạy mỗi document một lần tra cứu sang collection khác. Nếu join nhiều/không có index ở foreignField, chi phí tăng nhanh. Triết lý MongoDB là thiết kế để hạn chế join (embed dữ liệu hay đọc cùng nhau). Dùng $lookup cho báo cáo nền/analytics thì ổn; cho đường nóng (hot path) phục vụ realtime thì cân nhắc kỹ.

💡 Aggregation vs find — chọn cái nào?

Dùng find khi chỉ cần lấy ra document đúng tiêu chí (đọc lịch sử chat, lấy ticket theo id). Dùng aggregate khi cần biến đổi/tổng hợp nhiều document thành một hình dạng khác (đếm, nhóm, join, tính toán). Nguyên tắc tối ưu: đặt $match và $sort càng sớm càng tốt để tận dụng index, giảm khối lượng dữ liệu chảy qua các stage sau.

④ Index trong MongoDB

Không có index, mọi query phải quét toàn bộ collection (collection scan) — O(n). Index là cấu trúc B-tree giúp tìm document trong O(log n). Đây là yếu tố số một quyết định MongoDB nhanh hay chậm ở quy mô lớn.

🔑 Single field

{ conversationId: 1 } — index trên một field. 1 = tăng dần, -1 = giảm dần.

🧩 Compound

{ conversationId: 1, createdAt: -1 } — nhiều field. Thứ tự field cực kỳ quan trọng (quy tắc ESR).

📚 Multikey

Index trên field là mảng — MongoDB tự lập chỉ mục từng phần tử. Ví dụ index trên tags: [].

🔤 Text

Tìm kiếm toàn văn trên nội dung tin nhắn: { text: "text" }, dùng với $text.

⏳ TTL

{ createdAt: 1 }, { expireAfterSeconds: 86400 } — tự xoá document hết hạn (session, OTP, typing event).

⭐ Unique / Partial

unique chống trùng (email); partialFilterExpression chỉ index một phần dữ liệu để tiết kiệm.

indexes.jsmongo shell
// Truy vấn nóng nhất: lấy tin nhắn của 1 hội thoại theo thời gian giảm dần
db.messages.createIndex({ conversationId: 1, createdAt: -1 });

// TTL: typing/presence event tự huỷ sau 60 giây
db.presence.createIndex({ updatedAt: 1 }, { expireAfterSeconds: 60 });

// Unique: mỗi agent một mã code
db.agents.createIndex({ code: 1 }, { unique: true });

// Text: tìm kiếm trong nội dung chat
db.messages.createIndex({ text: "text" });

// Soi xem query có dùng index không — IXSCAN tốt, COLLSCAN xấu
db.messages.find({ conversationId: "conv_8821" }).explain("executionStats");
📐 Quy tắc ESR cho compound index

Thứ tự field trong compound index nên theo Equality → Sort → Range: field lọc bằng ($eq, $in) đặt trước, rồi field dùng để sort, cuối cùng field lọc khoảng ($gt, $lt). Với query "lấy tin nhắn của một conversation, sắp xếp theo thời gian", index { conversationId: 1, createdAt: -1 } đúng chuẩn: conversationId là equality, createdAt vừa sort vừa range.

🐛 Index không phải càng nhiều càng tốt

Mỗi index tốn dung lượng và làm chậm ghi (mỗi insert/update phải cập nhật mọi index liên quan). Trong hệ thống ghi nhiều như log tin nhắn, đừng tạo index bừa. Chỉ tạo index cho query thực sự chạy thường xuyên; dùng explain() để xác minh, và rà soát index không dùng định kỳ.

⑤ Embedding vs Referencing

Đây là quyết định thiết kế quan trọng nhất trong mô hình hoá dữ liệu MongoDB. Hai dữ liệu liên quan nhau: ta nhúng (embed) cái này vào trong cái kia (một document chứa cả con), hay tham chiếu (reference) bằng cách lưu _id và đọc ở hai collection riêng?

📦 Embedding (nhúng)

Ý tưởng: dữ liệu con nằm bên trong document cha.

Hợp khi: luôn đọc cùng nhau, quan hệ 1–ít (one-to-few), con không tồn tại độc lập, cần đọc 1 lần lấy hết.

Ví dụ: conversation nhúng vài participants; ticket nhúng mảng events trạng thái.

🔗 Referencing (tham chiếu)

Ý tưởng: lưu _id của document khác, nối khi cần.

Hợp khi: quan hệ 1–nhiều/nhiều–nhiều lớn, con tồn tại độc lập, con được dùng lại ở nhiều nơi, hay thay đổi riêng.

Ví dụ: message tham chiếu agentId; conversation tham chiếu khách hàng.

embed-vs-ref.jsonso sánh mô hình
// EMBED — đọc 1 lần lấy cả hội thoại lẫn participants (1-to-few)
{
  _id: "conv_8821",
  subject: "Hoá đơn",
  participants: [
    { id: "cus_42",   role: "customer" },
    { id: "agent_07", role: "agent" }
  ]
}

// REFERENCE — message chỉ giữ id; tin nhắn có thể lên tới hàng nghìn (1-to-many lớn)
{ _id: "msg_1", conversationId: "conv_8821", senderId: "agent_07", text: "..." }

Ba ràng buộc dẫn dắt quyết định

  • Read pattern (mẫu đọc): ưu tiên số một. Dữ liệu luôn đọc cùng nhau → embed (1 lần đọc đĩa). Đọc riêng lẻ → reference.
  • Giới hạn 16MB: nếu nhúng mảng tăng vô hạn (tin nhắn của một hội thoại dài) vào document cha, sớm muộn vượt 16MB và document phình to làm chậm mọi thao tác. Mảng vô hạn → reference (hoặc bucket, mục ⑦).
  • Tính nguyên tử (atomicity): ghi vào một document là nguyên tử mặc định. Nếu cần cập nhật cha + con cùng lúc đảm bảo nhất quán mà không dùng transaction, embed giúp việc đó "miễn phí".
⚠️ Anti-pattern: mảng vô hạn (unbounded array)

Nhúng toàn bộ tin nhắn của một hội thoại vào mảng messages: [] trong document conversation là sai lầm kinh điển. Một hội thoại hỗ trợ có thể có hàng nghìn tin → document phình, vượt 16MB, mỗi lần $push phải ghi lại cả document. Giải pháp đúng: để message thành collection riêng (reference) hoặc gom theo lô (bucket pattern, mục ⑦).

Tiêu chíNghiêng về EmbedNghiêng về Reference
Quan hệ số lượng1–một / 1–ít1–nhiều (lớn) / nhiều–nhiều
Cách đọcLuôn đọc cùng nhauĐọc độc lập, dùng lại nhiều nơi
Tần suất con thay đổiÍt, theo chaThường xuyên, độc lập
Kích thướcNhỏ, có giới hạnLớn, không giới hạn
Tính nguyên tử cha+conCần (embed cho free)Không bắt buộc / chấp nhận eventual

⑥ Mongoose ODM

MongoDB không bắt buộc schema, nhưng ứng dụng Node.js thường cần một lớp kỷ luật và tiện ích phía trên. Mongoose là ODM (Object Data Modeling) phổ biến nhất: nó cho ta định nghĩa Schema, sinh model, tự validate, chạy middleware, và ánh xạ document ↔ object JavaScript.

📐 Schema

Khai báo cấu trúc, kiểu dữ liệu, validation, default, index — schema ở tầng ứng dụng.

🏭 Model

Lớp đại diện cho collection; gọi .find(), .create()... và trả về document Mongoose.

🪝 Middleware

Hook pre/post chạy quanh save, validate, find...

message.model.tsMongoose / TS
import { Schema, model } from "mongoose";

const messageSchema = new Schema({
  conversationId: { type: String, required: true, index: true },
  channel: { type: String, enum: ["chat", "call", "email", "social"], required: true },
  senderId: { type: String, required: true },
  text: { type: String, maxlength: 4000 },
  readBy: { type: [String], default: [] }
}, { timestamps: true });  // tự thêm createdAt / updatedAt

// Compound index khớp truy vấn nóng nhất
messageSchema.index({ conversationId: 1, createdAt: -1 });

export const Message = model("Message", messageSchema);

Validation & middleware (pre/post hooks)

Validation chạy trước khi lưu: kiểu sai, thiếu field required, vượt maxlength, ngoài enum → ném lỗi, không ghi rác vào DB. Middleware cho phép cài logic chéo: chuẩn hoá dữ liệu, phát sự kiện, audit log.

hooks.tsMongoose
// pre('save'): chạy trước khi document được ghi
messageSchema.pre("save", function (next) {
  if (this.text) this.text = this.text.trim();  // chuẩn hoá
  next();
});

// post('save'): sau khi lưu — bắn realtime cho phòng hội thoại
messageSchema.post("save", function (doc) {
  io.to(doc.conversationId).emit("message:new", doc);
});
⚠️ Hook không chạy với mọi đường ghi

Middleware save chỉ kích hoạt qua doc.save() hoặc Model.create(). Các thao tác như updateOne, findOneAndUpdate, insertMany đi đường khác (query/bulk middleware) và không chạy pre('save'). Đây là nguồn bug âm thầm: tưởng đã validate/chuẩn hoá nhưng thực ra bị bỏ qua. Phải biết hook nào gắn vào đâu.

populate, virtuals, lean

  • populate: với field tham chiếu (ref), Mongoose tự thực hiện truy vấn phụ để "điền" document liên quan vào — như JOIN ở tầng ứng dụng. Tiện nhưng tốn thêm round-trip; cẩn thận N+1.
  • virtuals: field "ảo" được tính từ dữ liệu khác, không lưu trong DB (ví dụ fullName ghép họ + tên, hay quan hệ virtual populate).
  • lean(): trả về plain object thay vì document Mongoose đầy đủ → nhanh hơn nhiều, ít RAM, nhưng mất getter/virtual/method và khả năng save(). Dùng cho đường đọc (read-only) như render danh sách.
populate-lean.tsMongoose
// populate: điền profile agent từ tham chiếu, kèm lean cho đường đọc
const tickets = await Ticket.find({ status: "open" })
  .populate("assignedAgent", "name team")  // chỉ lấy name, team
  .sort({ createdAt: -1 })
  .limit(50)
  .lean();   // plain object — nhanh, dùng để trả API danh sách
🐛 populate trong vòng lặp = N+1

Gọi populate/truy vấn lồng trong vòng lặp danh sách dễ tạo N+1 query (1 query lấy danh sách + N query lấy chi tiết). Với màn hình hàng đợi cập nhật liên tục, đây là sát thủ hiệu năng. Hướng giải: populate theo lô (Mongoose gom $in sẵn), hoặc cân nhắc extended reference (lưu kèm vài field cần đọc, mục ⑦) để khỏi join.

Transaction trong MongoDB

Từ phiên bản hỗ trợ replica set, MongoDB có multi-document transaction (ACID đa document) qua session. Hữu ích khi buộc phải cập nhật nguyên tử nhiều collection (ví dụ trừ "credit" gọi thoại đồng thời tạo bản ghi cuộc gọi). Nhưng transaction có chi phí và độ phức tạp; triết lý MongoDB là thiết kế document sao cho phần lớn thao tác chỉ chạm một document (vốn đã nguyên tử), giảm nhu cầu transaction.

⑦ Schema design patterns

Đây là phần "tư duy thiết kế" tách người dùng MongoDB giỏi với người chỉ biết cú pháp. Vài pattern kinh điển rất hợp ngữ cảnh Contact Center:

Bucket Pattern — gom dữ liệu time-series

Vấn đề: mỗi tin nhắn một document → hàng triệu document nhỏ, index khổng lồ. Nhúng hết vào một mảng → mảng vô hạn (anti-pattern). Giải pháp dung hoà: gom các tin nhắn theo lô có giới hạn (ví dụ 50 tin / document, hoặc theo khung giờ). Mỗi "bucket" là một document chứa một mảng con giới hạn — vừa giảm số document, vừa tránh phình.

bucket.jsonbucket pattern
{
  _id: "conv_8821#bucket_3",
  conversationId: "conv_8821",
  count: 50,                // đầy thì sang bucket mới
  startAt: ISODate("2026-06-09T03:00:00Z"),
  messages: [               // mảng GIỚI HẠN — an toàn 16MB
    { id: "m151", senderId: "cus_42", text: "...", at: ISODate("...") }
    // ... tối đa 50 phần tử
  ]
}

Subset Pattern — chỉ nhúng phần hay đọc

Hội thoại có thể có hàng nghìn tin, nhưng màn hình thường chỉ cần vài tin gần nhất để hiển thị preview. Nhúng subset (ví dụ lastMessages: 10 tin cuối) vào document conversation để render danh sách nhanh, phần còn lại để ở collection message riêng.

Computed Pattern — tính sẵn khi ghi

Thay vì tính lại số tin chưa đọc / thời lượng cuộc gọi mỗi lần đọc (tốn aggregation), tính sẵn và lưu (unreadCount, messageCount) rồi cập nhật bằng $inc khi ghi. Đổi chi phí đọc rẻ lấy chút phức tạp khi ghi — hợp với hệ thống đọc nhiều hơn ghi.

Extended Reference — nhúng kèm vài field

Khi reference nhưng vẫn muốn tránh join lúc đọc: lưu kèm một vài field ổn định của document được tham chiếu. Ví dụ message lưu senderId và senderName (snapshot) để hiển thị mà không cần populate. Đánh đổi: nếu tên agent đổi, phải đồng bộ (chấp nhận eventual consistency cho dữ liệu lịch sử thì thậm chí snapshot lại là đúng).

💡 Mô hình lịch sử chat — tổng hợp các pattern

Một thiết kế thực tế cho lịch sử chat: collection conversations (metadata + subset tin gần nhất + computed messageCount), collection messages tổ chức theo bucket hoặc một-document-một-tin có index { conversationId: 1, createdAt: -1 }, mỗi message dùng extended reference lưu kèm senderName. Đọc danh sách hội thoại: chỉ chạm conversations (cực nhanh). Mở một hội thoại: query messages theo index, phân trang theo thời gian.

⚠️ Lỗi thường gặp & Best practices

🚫 Mảng vô hạn

Nhúng dữ liệu tăng mãi (tin nhắn) vào document cha → phình, vượt 16MB. Dùng reference/bucket.

🚫 Quên index hot query

Query nóng không có index → COLLSCAN, chậm dần khi dữ liệu lớn. Luôn explain() đường nóng.

🚫 Lạm dụng populate

Populate sâu/lồng vòng lặp → N+1, nhiều round-trip. Cân nhắc extended reference.

🚫 Tưởng schema-less khỏi thiết kế

Vẫn cần validation (Mongoose) và quyết định embed/reference. Linh hoạt ≠ tuỳ tiện.

🚫 Hook không chạy

updateOne/findOneAndUpdate bỏ qua pre('save'). Chọn đúng loại middleware.

✅ lean cho đường đọc

Read-only thì .lean() để bỏ overhead document Mongoose — nhanh hơn rõ rệt.

✅ $match sớm

Trong pipeline, lọc và sort đầu tiên để dùng index, giảm dữ liệu chảy qua stage sau.

✅ Thiết kế theo read pattern

Hỏi "ứng dụng đọc dữ liệu này thế nào?" trước khi quyết cấu trúc document.

🧪 Bài tập

🧪 Bài 1 — Mô hình hoá lịch sử chat

Bạn cần lưu hội thoại hỗ trợ có thể lên tới 5.000 tin nhắn. Màn hình danh sách chỉ cần 1 dòng preview; màn hình chi tiết cần phân trang. Hãy đề xuất cấu trúc collection và quyết định embed/reference, kèm index. Vì sao không nhúng hết tin vào conversation?

Gợi ý

Tách 2 collection: conversations (metadata + lastMessage theo subset pattern + messageCount theo computed) và messages (reference qua conversationId). Index { conversationId: 1, createdAt: -1 } trên messages để phân trang theo thời gian. Không nhúng hết vì 5.000 tin = mảng vô hạn → document phình, vượt 16MB, mỗi $push ghi lại cả document.

🧪 Bài 2 — Aggregation báo cáo SLA

Viết pipeline trả về: với mỗi channel, tổng số ticket đóng trong ngày, thời gian chờ trung bình (waitSec) và tỉ lệ ticket vi phạm SLA (waitSec > 60). Sắp xếp theo tổng giảm dần.

Gợi ý

$match theo status:"closed" + closedAt trong ngày → $group theo $channel với $sum:1, $avg:"$waitSec", và đếm vi phạm bằng $sum: { $cond: [ {$gt:["$waitSec",60]}, 1, 0 ] } → $project tính tỉ lệ violated/total rồi $sort.

🧪 Bài 3 — Chống tranh chấp khi nhận cuộc

Hai agent cùng bấm "nhận" một ticket trong hàng đợi. Viết một câu lệnh updateOne đảm bảo chỉ một người nhận được, không cần lock/transaction. Làm sao biết mình thắng?

Gợi ý

Dùng filter có điều kiện trạng thái hiện tại: updateOne({ _id, assignedAgent: {$exists:false} }, { $set: { assignedAgent, status:"in_progress" } }). Đây là compare-and-set nguyên tử ở cấp document. Kiểm tra result.modifiedCount === 1 → mình thắng; 0 → người khác đã nhận.

Ngân hàng câu hỏi phỏng vấn

MongoDB & Mongoose — phần được hỏi nhiều cho vị trí Fullstack realtime.

Q1So sánh SQL (quan hệ) và MongoDB (document)?Junior›

Trả lời: SQL lưu dữ liệu thành bảng có schema cố định, quan hệ qua khoá ngoại và JOIN, mạnh về tính toàn vẹn và truy vấn quan hệ phức tạp. MongoDB lưu document JSON/BSON lồng nhau trong collection, schema linh hoạt, ưu tiên thiết kế theo cách đọc và hạn chế JOIN. SQL hợp dữ liệu giao dịch chặt chẽ, quan hệ rõ; MongoDB hợp dữ liệu bán cấu trúc, biến thiên cao, phát triển nhanh, scale ngang theo collection.

⚠️ Bẫy: nói "MongoDB không có schema" — đúng là không bắt buộc ở tầng DB, nhưng dữ liệu vẫn có schema ngầm ứng dụng phải tuân.

Q2Embedding vs Referencing — chọn dựa trên gì?Middle›

Trả lời: Dựa trên ba yếu tố: (1) read pattern — dữ liệu luôn đọc cùng nhau thì embed (1 lần đọc), đọc riêng/dùng lại nhiều nơi thì reference; (2) kích thước & tăng trưởng — mảng tăng vô hạn phải reference vì giới hạn 16MB; (3) tính nguyên tử — ghi một document là nguyên tử, embed giúp cập nhật cha+con nhất quán mà khỏi transaction. Tóm lại: 1–ít, đọc chung, nhỏ → embed; 1–nhiều lớn, độc lập → reference.

Q3Aggregation pipeline là gì? Kể vài stage quan trọng.Middle›

Trả lời: Là chuỗi stage xử lý dữ liệu, output stage này là input stage sau. Stage hay dùng: $match (lọc, đặt sớm để dùng index), $group (nhóm + tính tổng/đếm/trung bình), $project (chọn/đổi/tính field), $sort, $unwind (bung mảng), $lookup (join sang collection khác). Dùng cho báo cáo, tổng hợp SLA, thống kê theo agent/kênh.

⚠️ Bẫy: đặt $match sau $group/$lookup sẽ bỏ lỡ index và xử lý thừa dữ liệu — luôn lọc sớm nhất có thể.

Q4$lookup là gì và có hạn chế gì?Middle›

Trả lời: $lookup là stage thực hiện left outer join sang collection khác qua localField/foreignField, trả về mảng kết quả (thường $unwind để làm phẳng). Hạn chế: tốn kém nếu không có index ở foreignField hoặc join số lượng lớn; vì vậy MongoDB khuyến khích thiết kế hạn chế join (embed dữ liệu đọc cùng nhau). Hợp cho báo cáo nền hơn là đường nóng realtime.

Q5Khi nào nên chọn NoSQL (MongoDB) thay vì SQL?Middle›

Trả lời: Khi dữ liệu bán cấu trúc/biến thiên (mỗi kênh chat/call/email có hình dạng khác nhau), schema thay đổi liên tục, cần ghi nhanh và scale ngang, quan hệ không quá phức tạp và phần lớn truy vấn đọc theo một khoá tự nhiên (conversationId). Ngược lại, dữ liệu giao dịch tài chính, ràng buộc toàn vẹn mạnh, nhiều quan hệ và truy vấn ad-hoc phức tạp thì SQL phù hợp hơn. Thực tế nhiều hệ dùng polyglot: SQL cho giao dịch, Mongo cho log/chat.

⚠️ Bẫy: chọn NoSQL vì "đang hot" hoặc "khỏi thiết kế schema" là sai lý do — phải bắt đầu từ read pattern thực tế.

Q6MongoDB có transaction không? Khi nào dùng?Senior›

Trả lời: Có — multi-document transaction (ACID) qua session trên replica set. Dùng khi buộc phải cập nhật nguyên tử nhiều document/collection (ví dụ trừ credit gọi thoại + tạo bản ghi cuộc gọi). Nhưng transaction có chi phí về hiệu năng và độ phức tạp; triết lý đúng là thiết kế document sao cho phần lớn thao tác chỉ chạm một document — vốn đã nguyên tử mặc định — để hạn chế cần transaction.

Q7"Schema-less" trong thực tế nghĩa là gì?Junior›

Trả lời: Nghĩa là MongoDB không bắt buộc schema ở tầng lưu trữ — hai document cùng collection có thể có tập field khác nhau, thêm field không cần migration đồng loạt. Nhưng dữ liệu vẫn có schema ngầm mà ứng dụng phải hiểu và giữ nhất quán. Trong dự án Node, ta thường dùng Mongoose để áp một schema có validation ở tầng ứng dụng, vừa giữ linh hoạt vừa có kỷ luật.

⚠️ Bẫy: hiểu "schema-less = không cần thiết kế dữ liệu" sẽ dẫn tới document hỗn loạn và bug khó lần.

Q8Có những loại index nào? Quy tắc đặt compound index?Senior›

Trả lời: Single field, compound, multikey (trên mảng), text (toàn văn), TTL (tự hết hạn), unique, partial. Với compound index theo quy tắc ESR: Equality (field lọc bằng) trước, rồi Sort (field dùng để sắp xếp), cuối là Range (field lọc khoảng). Ví dụ { conversationId: 1, createdAt: -1 } khớp truy vấn "tin nhắn của 1 hội thoại, sắp theo thời gian". Lưu ý index tốn dung lượng và làm chậm ghi — chỉ tạo cho query thực sự nóng, xác minh bằng explain().

Q9populate trong Mongoose là gì? Rủi ro?Middle›

Trả lời: populate tự thực hiện truy vấn phụ để thay field tham chiếu (ref, lưu _id) bằng document liên quan — như JOIN ở tầng ứng dụng. Rủi ro: thêm round-trip, và nếu lồng trong vòng lặp dễ gây N+1 query, ảnh hưởng hiệu năng hệ realtime. Giảm thiểu: chỉ select field cần, để Mongoose gom $in, hoặc dùng extended reference (snapshot vài field) để khỏi populate.

Q10Thiết kế mô hình lịch sử chat cho Contact Center?Senior›

Trả lời: Tách 2 collection. conversations: metadata + subset vài tin gần nhất cho preview + computed messageCount/unreadCount (cập nhật bằng $inc). messages: reference qua conversationId, index { conversationId: 1, createdAt: -1 }, có thể gom theo bucket nếu lượng tin cực lớn; mỗi message dùng extended reference lưu kèm senderName để hiển thị khỏi populate. Đọc danh sách chỉ chạm conversations (rất nhanh); mở hội thoại thì phân trang messages theo index. Thiết kế này tối ưu cho read pattern thực tế: nhiều lượt đọc danh sách, đọc chi tiết theo trang.

⚠️ Bẫy: nhúng toàn bộ tin vào conversation — mảng vô hạn, vượt 16MB, ghi lại cả document mỗi tin nhắn.

Q11Vì sao ghi một document là "nguyên tử" và tận dụng thế nào?Senior›

Trả lời: MongoDB đảm bảo một thao tác ghi trên một document là nguyên tử — hoặc thành công trọn vẹn hoặc không. Ta tận dụng bằng cách embed dữ liệu cần cập nhật cùng nhau vào một document (cha + con) để khỏi transaction, và dùng compare-and-set (filter kèm điều kiện trạng thái) để chống tranh chấp, ví dụ chỉ một agent nhận được một ticket qua updateOne({ _id, assignedAgent:{$exists:false} }, {...}) và kiểm tra modifiedCount.

Q12Middleware Mongoose: khi nào hook không chạy?Senior›

Trả lời: Hook gắn theo loại thao tác. pre/post('save') chỉ chạy với doc.save() và Model.create(). Các thao tác query/bulk như updateOne, findOneAndUpdate, updateMany, insertMany đi qua middleware khác và không kích hoạt pre('save'). Nếu logic validate/chuẩn hoá đặt ở save hook mà code lại ghi bằng updateOne, nó bị bỏ qua âm thầm. Phải đặt hook đúng loại hoặc thống nhất đường ghi.

⚠️ Bẫy: tin rằng "đã có pre('save') nên dữ liệu luôn được validate" — sai với các đường update trực tiếp.
