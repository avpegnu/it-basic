ORM & ODM thực chiến

TypeORM/Prisma/Mongoose giúp làm việc với DB bằng object có kiểu — tiện lợi nhưng có cạm bẫy như N+1 cần nắm rõ.

🎯 Học xong chương này bạn sẽ

• Giải thích được ORM ánh xạ object ↔ bảng quan hệ, ODM ánh xạ object ↔ document, và sự khác biệt.

• Phân biệt hai phong cách Active Record vs Data Mapper, biết khi nào dùng Repository pattern.

• Mô hình hóa quan hệ OneToMany/ManyToOne/ManyToMany và chọn đúng giữa eager vs lazy loading.

• Hiểu vì sao cần migrations để quản lý phiên bản schema, và vì sao tuyệt đối không bật synchronize ở production.

• Nhận diện và chữa được vấn đề kinh điển N+1 query bằng join, eager relations hoặc DataLoader.

• Biết khi nào nên rời bỏ ORM để viết raw SQL, và đánh đổi của việc dùng ORM.

💡 Liên hệ thực tế hệ thống Contact Center

Một Contact Center có hàng loạt thực thể quan hệ chặt chẽ: agent (tổng đài viên) thuộc nhiều queue (hàng đợi), mỗi call/chat gắn với một customer, sinh ra nhiều ticket và message. ORM giúp đội phát triển mô hình các quan hệ này bằng object có kiểu, viết logic nhanh và an toàn. Nhưng khi màn hình giám sát realtime cần liệt kê 500 cuộc gọi đang chờ kèm tên agent và queue, một câu lệnh ORM ngây thơ có thể bắn ra hàng nghìn query (N+1) làm DB nghẽn. Hiểu rõ ORM là ranh giới giữa hệ thống mượt và hệ thống "chậm không rõ lý do".

① ORM / ODM là gì?

ORM (Object–Relational Mapping) là một lớp trung gian ánh xạ giữa object trong code (class, thuộc tính) và bảng trong cơ sở dữ liệu quan hệ (table, column, row). Thay vì viết SQL thủ công và tự gắn kết quả về object, bạn làm việc với object có kiểu, ORM lo việc sinh SQL, ánh xạ kết quả về thực thể và theo dõi thay đổi.

ODM (Object–Document Mapping) làm điều tương tự nhưng cho cơ sở dữ liệu document (như MongoDB): ánh xạ object ↔ document JSON/BSON. Mongoose là ODM phổ biến nhất cho Node.js (xem lại D2).

🟦 TypeORM

ORM cho TS/JS, dùng decorator trên class. Hỗ trợ cả Active Record và Data Mapper. Quen thuộc với người dùng NestJS.

🔺 Prisma

ORM thế hệ mới: định nghĩa schema riêng (schema.prisma), sinh client type-safe. Truy vấn rất an toàn kiểu, DX tốt.

🍃 Mongoose

ODM cho MongoDB: định nghĩa Schema + Model, có validation, middleware (hooks), virtuals.

Bản chất công việc của một ORM/ODM gồm 4 nhiệm vụ:

  • Mapping — ánh xạ class ↔ table/collection, field ↔ column, kiểu dữ liệu JS ↔ kiểu DB.
  • Sinh truy vấn — từ lời gọi như repo.find() sinh ra câu SQL/MongoDB tương ứng.
  • Hydration — biến row/document thô thành object thực thể có đầy đủ phương thức và quan hệ.
  • Theo dõi thay đổi & vòng đời — biết object nào "bẩn" (đã sửa) để sinh UPDATE, quản lý transaction.
Object / Entity (code)→ ORM/ODM mapping→ SQL / lệnh Mongo→ Bảng / Collection
⚠️ Impedance mismatch

Thế giới object (kế thừa, tham chiếu, đồ thị) và thế giới quan hệ (bảng phẳng, khóa ngoại, join) không khớp hoàn hảo — gọi là object–relational impedance mismatch. ORM là cây cầu bắc qua khoảng cách đó, nhưng cầu nào cũng có giới hạn tải. Đó là lý do ORM tiện cho 80% trường hợp nhưng đôi khi "vướng" với 20% truy vấn phức tạp.

② Entity & Repository

Một Entity (thực thể) là class ánh xạ tới một bảng. Trong TypeORM, bạn dùng decorator để khai báo bảng, cột, khóa chính:

agent.entity.tsTypeORM
import { Entity, PrimaryGeneratedColumn, Column, CreateDateColumn, OneToMany } from 'typeorm';

@Entity('agents')            // ánh xạ tới bảng "agents"
export class Agent {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Column({ length: 120 })
  displayName: string;

  @Column({ type: 'enum', enum: ['available', 'busy', 'offline'], default: 'offline' })
  status: string;

  @OneToMany(() => Call, (call) => call.agent)
  calls: Call[];

  @CreateDateColumn()
  createdAt: Date;
}

Khi đã có entity, bạn truy cập dữ liệu qua một trong hai phong cách kiến trúc — đây là điểm hay bị hỏi trong phỏng vấn:

Trong dự án Node lớn (như backend Contact Center), người ta thường ưu tiên Data Mapper + Repository pattern vì entity được giữ "sạch", logic truy cập DB tập trung ở repository, dễ mock khi viết unit test cho service.

call.service.tsTypeORM · Data Mapper
// Repository do TypeORM cung cấp — entity vẫn là class dữ liệu thuần
const callRepo = dataSource.getRepository(Call);

// Tạo bản ghi cuộc gọi mới khi khách gọi vào
async function createIncomingCall(customerId: string, queueId: string) {
  const call = callRepo.create({ customerId, queueId, status: 'ringing' });
  return callRepo.save(call);   // sinh INSERT, trả về entity có id
}

// Tìm các cuộc gọi đang chờ trong một queue
async function findWaitingCalls(queueId: string) {
  return callRepo.find({
    where: { queueId, status: 'ringing' },
    order: { createdAt: 'ASC' },     // FIFO: ai chờ lâu nhất lên trước
    take: 50,
  });
}
💡 Repository pattern

Repository là một lớp trừu tượng đại diện cho "tập hợp" các entity, che giấu chi tiết lưu trữ. Lợi ích: service chỉ phụ thuộc vào interface repository (dễ thay DB, dễ mock test), và mọi truy vấn của một entity tụ về một chỗ — dễ tối ưu và bảo trì.

③ Quan hệ & loading strategy

Sức mạnh chính của ORM là mô hình hóa quan hệ giữa các bảng bằng thuộc tính object. Ba loại quan hệ cốt lõi:

Quan hệÝ nghĩaVí dụ Contact Center
OneToMany / ManyToOneMột bên "cha" có nhiều "con"; mỗi "con" thuộc một "cha"Một agent xử lý nhiều call; mỗi call thuộc một agent
ManyToManyNhiều ↔ nhiều, cần bảng nối (join table)Một agent thuộc nhiều queue; một queue có nhiều agent
OneToOneMột ↔ mộtMột call có một bản ghi recording (file ghi âm)
relations.entity.tsTypeORM
@Entity('calls')
export class Call {
  @PrimaryGeneratedColumn('uuid') id: string;

  // Nhiều call → một agent. lazy: chỉ tải khi truy cập
  @ManyToOne(() => Agent, (agent) => agent.calls)
  agent: Agent;

  // Một call → nhiều message (transcript chat/IVR)
  @OneToMany(() => Message, (m) => m.call)
  messages: Message[];
}

@Entity('agents')
export class Agent {
  @PrimaryGeneratedColumn('uuid') id: string;

  // Nhiều agent ↔ nhiều queue → TypeORM tự tạo bảng nối agents_queues
  @ManyToMany(() => Queue, (q) => q.agents)
  @JoinTable()
  queues: Queue[];
}

Eager vs Lazy loading

Khi tải một entity có quan hệ, câu hỏi quan trọng là: có tải luôn các quan hệ kèm theo không? Có hai chiến lược:

⚡ Eager loading

Tải entity và quan hệ của nó cùng lúc (thường bằng JOIN). Ưu: ít round-trip. Nhược: tải dư dữ liệu nếu không dùng, query nặng hơn.

🐢 Lazy loading

Chỉ tải entity gốc; quan hệ được tải khi bạn truy cập tới nó (query phụ). Ưu: nhẹ ban đầu. Nhược: dễ gây N+1 nếu lặp.

loading.tsTypeORM
// Cách tốt: nói rõ quan hệ cần tải bằng "relations" — sinh JOIN một lần
const calls = await callRepo.find({
  where: { status: 'ringing' },
  relations: { agent: true, messages: true },  // eager có chủ đích
  take: 50,
});

// Khai báo eager:true trong entity → LUÔN tải, kể cả khi không cần (cẩn thận!)
@ManyToOne(() => Agent, { eager: true })
agent: Agent;
🐛 Bẫy eager toàn cục

Đặt { eager: true } ngay trong entity nghe tiện nhưng nguy hiểm: mọi truy vấn entity đó đều kéo theo quan hệ, kể cả màn hình chỉ cần đếm số cuộc gọi. Khuyến nghị: để quan hệ ở chế độ lazy mặc định và chỉ định eager theo từng truy vấn (relations trong find hoặc leftJoinAndSelect trong query builder). Như vậy bạn kiểm soát được chính xác dữ liệu nào được kéo về.

④ Migrations — quản lý phiên bản schema

Schema database tiến hóa theo thời gian: thêm cột priority cho call, tạo bảng ticket, đổi kiểu cột. Migration là một file mô tả thay đổi schema dưới dạng code, có thể chạy tiến (up) và lùi (down), được đánh số/timestamp để áp dụng theo đúng thứ tự trên mọi môi trường (dev, staging, production).

Sửa entity→ Sinh migration→ Review SQL→ Commit vào git→ Chạy migration:run ở mỗi env
1700000000000-AddCallPriority.tsTypeORM Migration
import { MigrationInterface, QueryRunner } from 'typeorm';

export class AddCallPriority1700000000000 implements MigrationInterface {
  async up(q: QueryRunner): Promise<void> {
    await q.query(`ALTER TABLE calls ADD COLUMN priority INT NOT NULL DEFAULT 0`);
    await q.query(`CREATE INDEX idx_calls_priority ON calls(queue_id, priority DESC)`);
  }

  async down(q: QueryRunner): Promise<void> {
    await q.query(`DROP INDEX idx_calls_priority ON calls`);
    await q.query(`ALTER TABLE calls DROP COLUMN priority`);
  }
}
🐛 Vì sao TUYỆT ĐỐI không dùng synchronize: true ở production

TypeORM có tùy chọn synchronize tự động đồng bộ schema với entity mỗi lần khởi động — rất tiện khi prototype. Nhưng ở production nó cực kỳ nguy hiểm: nó có thể drop cột/bảng để khớp entity, dẫn tới mất dữ liệu thật (cả lịch sử cuộc gọi của khách). Nó cũng không kiểm soát được thứ tự thay đổi, không review được, không rollback được. Quy tắc: synchronize: false ở mọi môi trường thật, mọi thay đổi schema đi qua migration đã review.

✅ Migration cho

Versioning rõ ràng, rollback được, review trong PR, áp dụng nhất quán trên mọi env, audit lịch sử thay đổi schema.

⚠️ Migration dữ liệu

Đổi cấu trúc kèm chuyển dữ liệu (backfill) phải làm cẩn thận, theo bước, tính tới bảng lớn (khóa bảng, downtime).

⑤ Query Builder & raw SQL

Phương thức find() tiện cho truy vấn đơn giản, nhưng khi cần JOIN nhiều bảng, group, aggregate, điều kiện động — bạn dùng Query Builder: một API fluent để dựng SQL bằng code mà vẫn an toàn (tham số hóa, chống SQL injection).

queue-dashboard.tsTypeORM QueryBuilder
// Bảng giám sát: mỗi queue có bao nhiêu cuộc gọi đang chờ, thời gian chờ lâu nhất
const rows = await callRepo
  .createQueryBuilder('call')
  .select('call.queueId', 'queueId')
  .addSelect('COUNT(*)', 'waiting')
  .addSelect('MAX(NOW() - call.createdAt)', 'maxWait')
  .where('call.status = :status', { status: 'ringing' })
  .groupBy('call.queueId')
  .orderBy('waiting', 'DESC')
  .getRawMany();

Đôi khi ngay cả Query Builder cũng "vướng" — ví dụ window function, CTE đệ quy, gợi ý chỉ mục đặc thù, hoặc một truy vấn báo cáo phức tạp cần tối ưu tay. Khi đó raw SQL là lựa chọn đúng:

raw-report.tsRaw SQL (tham số hóa)
// Báo cáo: xếp hạng agent theo số cuộc gọi xử lý trong ngày, dùng window function
const result = await dataSource.query(
  `SELECT agent_id,
          COUNT(*) AS handled,
          RANK() OVER (ORDER BY COUNT(*) DESC) AS rnk
   FROM calls
   WHERE status = 'completed' AND created_at >= $1
   GROUP BY agent_id`,
  [startOfDay],   // LUÔN tham số hóa — không nối chuỗi để tránh SQL injection
);
⚠️ Khi nào nên dùng raw SQL?

Dùng raw khi: (1) truy vấn quá phức tạp ORM diễn đạt vụng/sinh SQL kém; (2) cần tính năng SQL nâng cao (window, CTE, full-text); (3) cần tối ưu hiệu năng đến từng câu lệnh cho hot path; (4) chạy báo cáo/migration dữ liệu lớn. Đánh đổi: mất type-safety, mất tính di động giữa các DB, tự chịu trách nhiệm tham số hóa. Đừng dùng raw chỉ vì "lười học query builder".

⑥ Vấn đề N+1 query

Đây là cạm bẫy hiệu năng số một của ORM và gần như chắc chắn được hỏi trong phỏng vấn. Tên gọi "N+1" mô tả: bạn chạy 1 query để lấy danh sách N bản ghi, rồi vô tình chạy thêm N query nữa (mỗi bản ghi một query) để lấy quan hệ.

nplus1-bad.ts❌ Anti-pattern
// 1 query: lấy 200 cuộc gọi đang chờ
const calls = await callRepo.find({ where: { status: 'ringing' } });

// N query: mỗi vòng lặp truy cập call.agent (lazy) → 1 SELECT phụ
for (const call of calls) {
  const agent = await call.agent;   // SELECT * FROM agents WHERE id = ? (lặp 200 lần!)
  console.log(call.id, agent?.displayName);
}
// Tổng cộng: 1 + 200 = 201 query cho MỘT màn hình. DB nghẽn.

Nguyên nhân gốc: ORM tải quan hệ một cách "lười" theo từng phần tử, nên lặp qua danh sách = lặp query. Với màn hình realtime cập nhật mỗi vài giây trong Contact Center, 201 query/lần × nhiều client = thảm họa cho database.

Ba cách chữa

Giải phápCách làmPhù hợp khi
JOIN / relationsTải quan hệ cùng truy vấn gốc bằng 1 JOINQuan hệ ManyToOne/OneToOne — gom về 1 query
Eager load có chủ đíchKhai báo relations trong find hoặc leftJoinAndSelectBiết trước cần quan hệ nào

nplus1-fix.ts✅ Fix bằng JOIN
// Chỉ 1 query — JOIN agents vào calls, ánh xạ sẵn quan hệ
const calls = await callRepo.find({
  where: { status: 'ringing' },
  relations: { agent: true },   // TypeORM sinh LEFT JOIN
});

for (const call of calls) {
  console.log(call.id, call.agent?.displayName);  // đã có sẵn, không query thêm
}
dataloader.ts✅ Fix bằng DataLoader
import DataLoader from 'dataloader';

// Gom mọi yêu cầu agent trong 1 tick thành 1 query IN (...)
const agentLoader = new DataLoader(async (ids: readonly string[]) => {
  const agents = await agentRepo.findBy({ id: In([...ids]) }); // 1 query duy nhất
  const map = new Map(agents.map((a) => [a.id, a]));
  return ids.map((id) => map.get(id) ?? null);   // đúng thứ tự ids
});

// 200 lời gọi .load() chỉ tạo ra 1 query batch
const agent = await agentLoader.load(call.agentId);
💡 Cách phát hiện N+1

Bật log query của ORM (logging: true trong TypeORM) khi dev — nếu thấy cùng một mẫu SELECT ... WHERE id = ? lặp lại hàng loạt, đó là N+1. Công cụ APM (như query analyzer) cũng cảnh báo. Quy tắc ngón tay cái: số query nên không phụ thuộc vào số bản ghi trả về.

⑦ Ưu & nhược điểm của ORM

ORM không phải "luôn tốt" hay "luôn xấu" — đó là một đánh đổi kỹ thuật. Người dùng giỏi là người biết rõ ranh giới của nó.

✅ Ưu điểm

• Năng suất: viết CRUD và quan hệ nhanh, ít boilerplate SQL.

• Type-safe: với TS (đặc biệt Prisma), lỗi schema bắt ngay lúc compile.

• Bảo mật: tự tham số hóa → giảm rủi ro SQL injection.

• Di động: đổi MySQL ↔ PostgreSQL ít sửa code.

• Tiện ích: migration, transaction, hooks, validation tích hợp sẵn.

❌ Nhược điểm

• Rò rỉ trừu tượng (leaky abstraction): vẫn phải hiểu SQL bên dưới để tránh N+1, query kém.

• Khó tối ưu truy vấn phức tạp; SQL sinh ra đôi khi không tối ưu.

• Chi phí học: nắm cả ORM lẫn DB; "magic" khó debug.

• Overhead: hydration, theo dõi thay đổi tốn CPU/RAM ở quy mô lớn.

⚠️ Leaky abstraction — câu nói kinh điển

"ORM giúp 80% công việc dễ hơn 10 lần, nhưng làm 20% còn lại khó hơn 10 lần." Bạn không thể dùng ORM tốt nếu không hiểu SQL — ORM che SQL chứ không thay thế hiểu biết về SQL. Đây là lý do chương này nằm sau D1 (SQL) là có chủ đích.

Transaction trong ORM

Một thao tác nghiệp vụ thường gồm nhiều bước phải nguyên tử (all-or-nothing). Ví dụ: khi gán một cuộc gọi cho agent, ta cần vừa cập nhật call.status = 'assigned' vừa đổi agent.status = 'busy' — nếu một bước lỗi thì cả hai phải rollback.

assign-call.tsTypeORM Transaction
await dataSource.transaction(async (manager) => {
  await manager.update(Call,  callId,  { status: 'assigned', agentId });
  await manager.update(Agent, agentId, { status: 'busy' });
  // Nếu bất kỳ lệnh nào throw → toàn bộ rollback, không có trạng thái nửa vời
});

⚠️ Lỗi thường gặp & Best practices

🚫 N+1 query

Lặp danh sách rồi truy cập quan hệ lazy. Sửa bằng relations/JOIN/DataLoader. Bật log query để phát hiện.

🚫 synchronize: true ở prod

Có thể drop cột/bảng, mất dữ liệu thật. Luôn false, dùng migration đã review.

🚫 Eager toàn cục

Đặt eager:true trong entity kéo dữ liệu dư mọi nơi. Hãy eager theo từng truy vấn.

🚫 Quên transaction

Thao tác nhiều bước không bọc transaction → dữ liệu nửa vời khi lỗi giữa chừng.

🚫 Nối chuỗi SQL

Tự ghép biến vào raw SQL → SQL injection. Luôn tham số hóa ($1, placeholder).

🚫 Lấy SELECT * mọi cột

Kéo cả cột nặng (recording blob, transcript) khi chỉ cần id/tên. Dùng select chỉ cột cần.

🚫 Không phân trang

find() không take/skip trên bảng lớn → kéo cả triệu dòng. Luôn phân trang.

✅ Hiểu SQL bên dưới

ORM là leaky abstraction. Bật logging, đọc SQL sinh ra, thêm index đúng cho truy vấn hot.

🧪 Bài tập

🧪 Bài 1 — Diệt N+1

Bạn có màn hình liệt kê 100 ticket gần nhất, mỗi ticket hiển thị tên agent phụ trách và tên customer. Đoạn code hiện tại lặp qua từng ticket và truy cập ticket.agent, ticket.customer. Hãy chỉ ra số query, và viết lại bằng TypeORM để chỉ còn 1 query.

Gợi ý

Code hiện tại sinh 1 + 100×2 = 201 query (mỗi ticket 2 quan hệ lazy). Sửa: dùng ticketRepo.find({ relations: { agent: true, customer: true }, take: 100, order: { createdAt: 'DESC' } }) để TypeORM sinh các LEFT JOIN trong một câu lệnh duy nhất. Nếu quan hệ là ToMany và sợ nhân dòng, cân nhắc DataLoader hoặc query riêng theo lô WHERE id IN (...).

🧪 Bài 2 — Migration an toàn

Cần thêm cột resolved_at TIMESTAMP NULL vào bảng tickets (đang có 5 triệu dòng) và một index trên (queue_id, resolved_at). Viết migration up/down và giải thích vì sao không dùng synchronize, cùng rủi ro khi thêm index trên bảng lớn.

Gợi ý

up: ALTER TABLE tickets ADD COLUMN resolved_at TIMESTAMP NULL; rồi CREATE INDEX .... down làm ngược lại (drop index trước, drop column sau). Không dùng synchronize vì nó không review/rollback được và có thể drop dữ liệu. Trên bảng lớn, tạo index có thể khóa bảng/tốn thời gian — cân nhắc CREATE INDEX CONCURRENTLY (PostgreSQL) và thực hiện trong khung giờ thấp tải để tránh ảnh hưởng cuộc gọi đang diễn ra.

🧪 Bài 3 — Chọn loading strategy

Cho 2 màn hình: (A) bảng giám sát realtime liệt kê 500 cuộc gọi đang chờ kèm tên agent; (B) trang chi tiết một cuộc gọi với toàn bộ transcript (có thể 300 message). Với mỗi màn hình, hãy chọn eager hay lazy, JOIN hay query riêng, và giải thích.

Gợi ý

(A) Quan hệ call → agent là ManyToOne → eager có chủ đích bằng JOIN (relations: { agent: true }) để tránh N+1, nhưng chỉ select cột cần (id, displayName). (B) Quan hệ call → messages là OneToMany với số lượng lớn → nếu JOIN sẽ nhân dòng và kéo cột nặng; tốt hơn là query riêng có phân trang cho transcript (messageRepo.find({ where:{ callId }, take:50, skip })). Bài học: loading strategy phụ thuộc vào loại quan hệ và khối lượng dữ liệu, không có lựa chọn "luôn đúng".

✅ Quiz kiểm tra nhanh

Q1. ODM khác ORM ở điểm nào?
ODM nhanh hơn ORM
ODM ánh xạ object ↔ document (Mongo), ORM ánh xạ object ↔ bảng quan hệ
ODM không cần schema
Object–Document vs Object–Relational. Mongoose là ODM cho MongoDB; TypeORM/Prisma là ORM cho DB quan hệ.
Q2. Vấn đề N+1 xảy ra khi nào?
Khi dùng quá nhiều index
Khi lấy N bản ghi rồi chạy thêm N query để tải quan hệ của từng bản ghi
Khi transaction bị rollback
1 query gốc + N query phụ. Sửa bằng JOIN/eager relations hoặc DataLoader batch.
Q3. Vì sao không dùng synchronize: true ở production?
Vì nó chạy chậm
Vì nó có thể drop cột/bảng để khớp entity → mất dữ liệu thật, không review/rollback được
Vì nó không hỗ trợ PostgreSQL
Mất dữ liệu. Production luôn synchronize:false và đi qua migration đã review.
Q4. Active Record khác Data Mapper thế nào?
Active Record dùng cho NoSQL, Data Mapper cho SQL
Active Record: entity tự chứa logic DB; Data Mapper: repository riêng lo đọc/ghi, entity sạch
Chúng hoàn toàn giống nhau
Vị trí logic truy cập DB. Data Mapper tách biệt hơn, hợp app lớn và unit test.
Q5. Khi nào nên dùng raw SQL thay vì ORM?
Luôn luôn, vì raw nhanh hơn
Khi cần truy vấn phức tạp (window/CTE), tối ưu hot path, hoặc ORM sinh SQL kém
Không bao giờ nên dùng raw SQL
Cho 20% phức tạp. Đánh đổi: mất type-safety và phải tự tham số hóa chống injection.

Ngân hàng câu hỏi phỏng vấn

ORM/ODM — chủ đề phân biệt người "dùng được" với người "hiểu đánh đổi".

Q1ORM là gì? Nêu ưu và nhược điểm.Junior›

Trả lời: ORM (Object–Relational Mapping) là lớp ánh xạ object trong code ↔ bảng trong DB quan hệ, giúp làm việc với DB bằng object có kiểu thay vì SQL thủ công. Ưu: năng suất cao, type-safe (nhất là TS), tự tham số hóa chống injection, di động giữa các DB, tích hợp migration/transaction. Nhược: là leaky abstraction (vẫn phải hiểu SQL để tránh N+1), khó tối ưu truy vấn phức tạp, có overhead, "magic" khó debug.

Q2Vấn đề N+1 query là gì và cách khắc phục?Middle›

Trả lời: N+1 là khi ta chạy 1 query lấy N bản ghi rồi vô tình chạy thêm N query để tải quan hệ của từng bản ghi (do lazy loading trong vòng lặp). Tổng 1+N query làm DB nghẽn. Khắc phục: (1) eager load có chủ đích bằng relations/leftJoinAndSelect để gom thành 1 JOIN; (2) DataLoader gom các yêu cầu lẻ thành 1 query WHERE id IN (...); (3) với ToMany lớn thì query riêng theo lô. Phát hiện bằng cách bật log query và tìm mẫu SELECT lặp.

⚠️ Bẫy: nói "chỉ cần bật eager:true là xong" — eager toàn cục lại gây tải dư mọi nơi; phải eager theo từng truy vấn.

Q3Vì sao cần migration? Khác gì với synchronize?Middle›

Trả lời: Migration là file mô tả thay đổi schema có up/down, được đánh số để áp dụng nhất quán và theo thứ tự trên mọi môi trường, review được trong PR, rollback được, có audit lịch sử. synchronize tự đồng bộ schema theo entity mỗi lần khởi động — tiện cho prototype nhưng nguy hiểm ở prod vì có thể drop cột/bảng gây mất dữ liệu, không kiểm soát thứ tự, không review/rollback. Quy tắc: prod luôn synchronize:false, mọi thay đổi qua migration.

Q4Lazy loading vs eager loading — khi nào dùng cái nào?Middle›

Trả lời: Lazy chỉ tải entity gốc, quan hệ tải khi truy cập — nhẹ ban đầu nhưng dễ gây N+1 khi lặp. Eager tải kèm quan hệ (thường JOIN) — ít round-trip nhưng có thể kéo dữ liệu dư. Nguyên tắc: dùng eager có chủ đích theo từng truy vấn khi biết chắc cần quan hệ (vd liệt kê call kèm tên agent); dùng lazy/query riêng khi quan hệ lớn hoặc ít khi cần (vd transcript hàng trăm message). Tránh đặt eager:true toàn cục trong entity.

Q5Phân biệt Active Record và Data Mapper.Middle›

Trả lời: Active Record: entity tự chứa phương thức truy cập DB (agent.save()) — nhanh để viết, hợp app nhỏ, nhưng trộn logic nghiệp vụ với truy cập DB. Data Mapper: entity là dữ liệu thuần, một Repository riêng lo đọc/ghi (agentRepo.save(agent)) — tách lớp rõ, dễ test/mock, hợp app lớn và DDD. TypeORM hỗ trợ cả hai; Prisma theo kiểu query client (gần Data Mapper); dự án Node lớn thường ưu tiên Data Mapper + Repository.

Q6Khi nào nên dùng raw SQL thay vì query builder/ORM?Senior›

Trả lời: Dùng raw khi: truy vấn quá phức tạp ORM diễn đạt vụng hoặc sinh SQL kém; cần tính năng SQL nâng cao (window function, CTE đệ quy, full-text); cần tối ưu hiệu năng đến từng câu cho hot path; chạy báo cáo/migration dữ liệu lớn. Đánh đổi: mất type-safety, mất tính di động giữa DB, phải tự tham số hóa để chống injection. Không dùng raw chỉ vì lười học query builder.

⚠️ Bẫy: quên tham số hóa và nối chuỗi biến vào SQL → mở cửa cho SQL injection.

Q7So sánh Prisma và TypeORM, bạn chọn cái nào cho dự án mới?Senior›

Trả lời: TypeORM dùng decorator trên class entity, hỗ trợ cả Active Record và Data Mapper, quen với hệ NestJS, nhưng type-safety có chỗ lỏng (relations, raw). Prisma định nghĩa schema declarative (schema.prisma) rồi sinh client type-safe rất chặt, DX tốt, migration mạnh, nhưng không có entity class kiểu OOP. Dự án mới ưu tiên an toàn kiểu và DX → tôi nghiêng về Prisma; nếu team đã dùng NestJS/decorator nặng hoặc cần entity class với logic domain → TypeORM. Lựa chọn cuối cùng tùy đội ngũ và độ phức tạp truy vấn.

Q8Transaction trong ORM hoạt động thế nào? Cho ví dụ.Middle›

Trả lời: Transaction bọc nhiều thao tác DB thành một đơn vị nguyên tử (all-or-nothing): nếu một bước lỗi thì tất cả rollback. Trong TypeORM dùng dataSource.transaction(async manager => {...}) — mọi thao tác qua manager nằm trong cùng transaction. Ví dụ gán cuộc gọi: cập nhật call.status='assigned' và agent.status='busy' trong cùng transaction để không bao giờ có trạng thái nửa vời (call đã gán nhưng agent vẫn rảnh). Cần lưu ý isolation level và tránh giữ transaction quá lâu gây khóa.

Q9"Leaky abstraction" của ORM nghĩa là gì?Senior›

Trả lời: Là việc ORM hứa che giấu hoàn toàn SQL, nhưng thực tế các chi tiết của tầng dưới (SQL, index, plan thực thi) vẫn "rò rỉ" lên và buộc bạn phải hiểu. Ví dụ N+1, query chậm vì thiếu index, SQL sinh ra không tối ưu — không thể giải quyết nếu chỉ biết API ORM mà không hiểu SQL. ORM giúp 80% trường hợp dễ hơn nhưng làm 20% phức tạp khó hơn. Kết luận: phải nắm vững SQL/DB song song với ORM.

Q10ODM (Mongoose) khác ORM thế nào? Schema có cần không khi Mongo "schemaless"?Middle›

Trả lời: ODM ánh xạ object ↔ document (BSON) cho DB document như MongoDB, còn ORM ánh xạ object ↔ bảng quan hệ. MongoDB không bắt buộc schema ở tầng DB, nhưng Mongoose áp schema ở tầng ứng dụng: định nghĩa kiểu field, validation, default, middleware (hooks), virtuals. Lợi ích là tính nhất quán và an toàn dữ liệu dù DB "schemaless". Khác biệt nữa: ODM không có JOIN gốc mạnh như SQL — quan hệ thường giải quyết bằng nhúng (embed) document hoặc populate (tham chiếu), và cũng có thể gặp dạng N+1 khi populate.

Q11Làm sao tránh kéo dữ liệu dư khi truy vấn entity lớn?Middle›

Trả lời: (1) Chỉ chọn cột cần bằng select thay vì lấy hết — đặc biệt tránh cột nặng như recording blob hay transcript dài. (2) Luôn phân trang (take/skip hoặc keyset pagination) trên bảng lớn. (3) Eager quan hệ có chủ đích, không bật eager toàn cục. (4) Với ToMany lớn, query riêng có phân trang thay vì JOIN gây nhân dòng. (5) Cân nhắc projection/DTO để chỉ trả về dữ liệu API thật sự dùng.

Q12Bạn debug một endpoint chậm nghi do ORM thế nào?Senior›

Trả lời: Bước 1: bật log query của ORM để xem số lượng và nội dung SQL thực sự chạy — phát hiện N+1 (mẫu SELECT lặp) hoặc query kéo cả triệu dòng. Bước 2: chạy EXPLAIN/EXPLAIN ANALYZE trên câu chậm để xem có full table scan, thiếu index không. Bước 3: thêm index phù hợp, sửa loading strategy (JOIN/DataLoader), giới hạn cột và phân trang. Bước 4: nếu ORM vẫn sinh SQL kém cho truy vấn phức tạp thì cân nhắc query builder hoặc raw SQL có tối ưu tay. Bước 5: đo lại bằng APM để xác nhận cải thiện. Tư duy: số query không nên phụ thuộc số bản ghi.
