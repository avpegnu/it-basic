Live Chat Omnichannel

Hợp nhất nhiều kênh (web, mạng xã hội, email) vào một mô hình hội thoại thống nhất, định tuyến và gán agent — bài toán trừu tượng hóa kênh kinh điển.

🎯 Học xong chương này bạn sẽ

• Phân biệt rõ omnichannel với multichannel, và vì sao "hợp nhất ngữ cảnh" mới là giá trị cốt lõi.

• Thiết kế được Channel Adapter Pattern để chuẩn hóa tin nhắn vào/ra của mọi kênh về một mô hình chung.

• Mô hình hóa hội thoại hợp nhất (conversation · participants · messages · channel metadata) ở tầng dữ liệu.

• Hiểu cách định tuyến và gán agent, quản lý capacity (một agent xử lý N chat), và bàn giao bot→người.

• Xử lý presence, typing, read receipt và bài toán delivery & ordering (idempotency, dedup, sequence).

• Trả lời tự tin các câu phỏng vấn dạng "hãy thiết kế một inbox omnichannel" theo tư duy đánh đổi.

💡 Liên hệ thực tế hệ thống Contact Center

Khách hàng nhắn web chat lúc sáng, gửi tin qua mạng xã hội buổi chiều, rồi email tối — nhưng họ kỳ vọng cùng một agent biết toàn bộ câu chuyện, không phải kể lại từ đầu. Một Contact Center hiện đại phải biến bốn ống dẫn khác nhau thành một dòng hội thoại liền mạch. Chương này là phần "lõi nghiệp vụ" của live chat — nơi tư duy trừu tượng hóa kênh quyết định hệ thống của bạn dễ mở rộng (thêm kênh mới) hay trở thành mớ if/else chằng chịt theo từng kênh.

① Omnichannel là gì?

Omnichannel (đa kênh hợp nhất) nghĩa là khách hàng có thể liên hệ qua nhiều kênh khác nhau, nhưng hệ thống coi tất cả là một hội thoại / một ngữ cảnh thống nhất. Điều này khác hẳn với multichannel (đa kênh rời rạc) — nơi mỗi kênh là một silo riêng, agent web chat không thấy được lịch sử email, và khách phải lặp lại vấn đề mỗi lần đổi kênh.

Tiêu chíMultichannel (đa kênh rời)Omnichannel (đa kênh hợp nhất)
Ngữ cảnh khách hàngTách rời theo từng kênhHợp nhất xuyên kênh, một hồ sơ duy nhất
Lịch sử hội thoạiMỗi kênh giữ lịch sử riêngMột timeline chung cho mọi kênh
Trải nghiệm đổi kênhKhách phải kể lại từ đầuTiếp nối liền mạch, không lặp lại
Góc nhìn agentMở nhiều ứng dụng/tab khác nhauMột inbox duy nhất, mọi kênh đổ về
Kiến trúc kỹ thuậtN hệ thống độc lập1 mô hình chung + N adapter
⚠️ Điểm hay nhầm khi phỏng vấn

"Hỗ trợ nhiều kênh" không tự động là omnichannel. Một app cho phép chat web và email nhưng hai luồng không liên thông chỉ là multichannel. Omnichannel = hợp nhất identity + hợp nhất hội thoại + hợp nhất ngữ cảnh. Khi trả lời, hãy nhấn vào từ "hợp nhất ngữ cảnh".

Các kênh tiêu biểu của một Contact Center

💬 Web chat

Widget nhúng website. Kết nối realtime (WebSocket). Kênh "của ta" nên kiểm soát đầy đủ giao thức.

📨 Mạng xã hội

Messenger, Zalo OA... Giao tiếp qua webhook + REST API của nền tảng, có giới hạn và quy tắc riêng.

✉️ Email

Bất đồng bộ, phiên dài (giờ/ngày), có subject/threading. Không có "online/offline".

📱 SMS

Giới hạn ký tự, không có typing/read receipt, định danh bằng số điện thoại.

🤖 Bot / IVR text

Tự động trả lời, gom thông tin, rồi handoff sang agent người khi cần.

⭐ Kênh khác

WhatsApp, review marketplace, app review... Mỗi kênh = một adapter mới cắm vào.

Điểm mấu chốt: mỗi kênh có khả năng (capabilities) khác nhau — web chat có typing indicator, SMS thì không; Messenger có "đã xem", email thì không. Hệ thống tốt phải mô hình hóa được sự khác biệt này thay vì giả định mọi kênh giống nhau.

② Channel Adapters

Đây là trái tim kỹ thuật của omnichannel. Channel Adapter Pattern đặt một lớp dịch (translation layer) giữa giao thức riêng của từng kênh và mô hình tin nhắn chung (canonical message model) của hệ thống. Lõi nghiệp vụ chỉ làm việc với mô hình chung, hoàn toàn không biết tin nhắn đến từ đâu.

Kênh ngoài (Messenger/Zalo/SMS/Email)→ Channel Adapter (in)→ Canonical Message→ Core: Conversation Engine
Core: Agent gửi reply→ Canonical Message→ Channel Adapter (out)→ API gốc của kênh

Mỗi adapter chịu trách nhiệm hai chiều:

  • Inbound (vào): nhận webhook/sự kiện từ kênh → xác thực chữ ký → normalize (chuẩn hóa) về canonical message → đẩy vào core.
  • Outbound (ra): nhận canonical message từ core → denormalize sang định dạng API của kênh → gọi API gửi đi → xử lý kết quả/lỗi/retry.

Giao diện adapter chung

channel-adapter.tsTypeScript
// Hợp đồng chung mà MỌI adapter phải tuân theo.
// Core chỉ phụ thuộc interface này — không biết kênh cụ thể.
export interface ChannelAdapter {
  channel: ChannelType;            // 'web' | 'messenger' | 'zalo' | 'sms' | 'email'
  capabilities: ChannelCapabilities;  // kênh này hỗ trợ typing? read receipt? đính kèm?

  // Inbound: webhook thô -> danh sách canonical message
  parseInbound(raw: unknown): CanonicalMessage[];

  // Outbound: canonical message -> gọi API kênh -> trả về kết quả gửi
  sendOutbound(msg: CanonicalMessage): Promise<DeliveryResult>;

  // Xác thực chữ ký webhook (mỗi kênh một cách)
  verifySignature(req: IncomingRequest): boolean;
}

interface ChannelCapabilities {
  typing: boolean;
  readReceipt: boolean;
  attachments: boolean;
  presence: boolean;
  maxLength: number | null;     // SMS bị giới hạn, web chat thì không
}

Một adapter cụ thể — chuẩn hóa inbound

messenger-adapter.tsTypeScript
class MessengerAdapter implements ChannelAdapter {
  channel = 'messenger' as const;
  capabilities = { typing: true, readReceipt: true, attachments: true, presence: false, maxLength: null };

  parseInbound(raw: MessengerWebhook): CanonicalMessage[] {
    return raw.entry.flatMap(e => e.messaging).map(m => ({
      externalId: m.message.mid,          // ID gốc -> dùng để dedup!
      channel: 'messenger',
      externalUserId: m.sender.id,         // PSID của nền tảng
      direction: 'inbound',
      type: m.message.attachments ? 'media' : 'text',
      text: m.message.text ?? '',
      sentAt: new Date(m.timestamp),
      channelMeta: { pageId: m.recipient.id },  // dữ liệu riêng của kênh
    }));
  }

  async sendOutbound(msg: CanonicalMessage): Promise<DeliveryResult> {
    const res = await callGraphApi({
      recipient: { id: msg.externalUserId },
      message: { text: msg.text },
    });
    return { externalId: res.message_id, status: 'sent' };
  }

  verifySignature(req): boolean {
    return hmacSha256(req.body, APP_SECRET) === req.headers['x-hub-signature-256'];
  }
}
💡 Vì sao pattern này quan trọng

Khi cần thêm một kênh mới (vd WhatsApp), bạn chỉ viết một adapter mới implement đúng interface — không đụng tới conversation engine, routing, hay UI agent. Đây chính là nguyên lý Open/Closed: mở để mở rộng, đóng để sửa đổi. Câu hỏi phỏng vấn "thêm kênh mới có dễ không?" được trả lời ngay bằng kiến trúc này.

③ Mô hình hội thoại hợp nhất

Khi mọi tin nhắn đã được chuẩn hóa, ta cần một schema dữ liệu chung để lưu và truy vấn xuyên kênh. Bốn thực thể cốt lõi:

🧵 Conversation

Một phiên hội thoại. Có trạng thái (open/assigned/closed), kênh khởi tạo, agent đang xử lý, contact liên quan.

👥 Participants

Người tham gia: customer, agent(s), bot. Mỗi participant có vai trò và định danh nội bộ.

💌 Messages

Các tin nhắn theo thứ tự, gắn externalId để dedup, seq để sắp xếp, hướng in/out.

🏷️ Channel metadata

Dữ liệu riêng từng kênh (pageId, threadId, phone, subject email...) tách khỏi phần lõi chung.

schema.sqlPostgreSQL
-- CONTACT: danh tính khách, hợp nhất nhiều identity của các kênh
CREATE TABLE contacts (
  id            uuid PRIMARY KEY,
  display_name  text,
  created_at    timestamptz DEFAULT now()
);

-- Một contact có NHIỀU identity theo kênh (PSID, số ĐT, email...)
CREATE TABLE channel_identities (
  id            uuid PRIMARY KEY,
  contact_id    uuid REFERENCES contacts(id),
  channel       text NOT NULL,        -- 'messenger' | 'sms' | ...
  external_id   text NOT NULL,        -- PSID / phone / email
  UNIQUE (channel, external_id)         -- 1 identity = 1 contact
);

CREATE TABLE conversations (
  id            uuid PRIMARY KEY,
  contact_id    uuid REFERENCES contacts(id),
  channel       text NOT NULL,        -- kênh khởi tạo
  status        text NOT NULL,        -- open | assigned | pending | closed
  assigned_to   uuid,                    -- agent đang xử lý
  last_seq      bigint DEFAULT 0,        -- bộ đếm thứ tự tin nhắn
  created_at    timestamptz DEFAULT now()
);

CREATE TABLE messages (
  id            uuid PRIMARY KEY,
  conversation_id uuid REFERENCES conversations(id),
  seq           bigint NOT NULL,      -- thứ tự ổn định trong hội thoại
  direction     text NOT NULL,        -- inbound | outbound
  sender_type   text NOT NULL,        -- customer | agent | bot | system
  body          text,
  external_id   text,                    -- ID gốc từ kênh -> chống trùng
  channel_meta  jsonb,                   -- phần riêng của từng kênh
  created_at    timestamptz DEFAULT now(),
  UNIQUE (conversation_id, external_id)  -- idempotency: webhook lặp không tạo trùng
);
⚠️ Quyết định thiết kế: channel_meta dạng JSONB

Phần chung (body, direction, seq...) nằm ở cột cứng để truy vấn nhanh; phần riêng từng kênh (subject email, sticker id, pageId...) nhét vào jsonb. Cách này giữ schema gọn mà vẫn uyển chuyển với đặc thù từng kênh — thêm kênh mới không cần đổi cấu trúc bảng. Đây là nguyên lý "schema chung + phần mở rộng linh hoạt".

Hợp nhất identity (identity resolution)

Một người dùng có thể là PSID trên Messenger, số điện thoại trên SMS, email khác nhau — nhưng đều là một con người. Bảng channel_identities ánh xạ nhiều identity về một contact. Khi tin nhắn mới đến, adapter tra (channel, external_id); nếu chưa có thì tạo identity mới (và có thể gợi ý gộp contact dựa trên email/số ĐT trùng). Đây là điều kiện tiên quyết để hội thoại thực sự "xuyên kênh".

④ Định tuyến & gán agent

Khi một hội thoại mới được tạo (hoặc một hội thoại đang chờ cần người xử lý), router quyết định agent nào nhận. Khác với cuộc gọi thoại (1 agent = 1 cuộc tại một thời điểm), chat cho phép một agent xử lý song song nhiều hội thoại — nên bài toán cốt lõi là quản lý capacity.

Các chiến lược định tuyến

Chiến lượcCách hoạt độngĐánh đổi
Round-robinChia lần lượt cho agent rảnhĐơn giản, nhưng không tính tải/kỹ năng
Least-busyGán cho agent đang ít chat nhấtCân tải tốt, cần theo dõi capacity realtime
Skill-basedKhớp kỹ năng/ngôn ngữ/nhóm với hội thoạiChất lượng cao, cấu hình phức tạp hơn
Sticky (gắn kết)Ưu tiên agent đã từng xử lý contact nàyLiền mạch ngữ cảnh, nhưng có thể lệch tải
💡 Mô hình capacity (sức chứa)

Mỗi agent có một hạn mức chat đồng thời, ví dụ tối đa 4. Router chỉ gán khi activeChats < maxConcurrent. Có thể tinh hơn: gán "trọng số" cho từng hội thoại (chat phức tạp tốn 2 slot). Hội thoại không gán được sẽ vào hàng đợi (queue) và chờ agent có slot.

router.tsTypeScript
// Least-busy + skill-based + capacity. Trả về agent phù hợp nhất.
async function routeConversation(conv: Conversation): Promise<AgentId | null> {
  const candidates = await getOnlineAgents({
    skills: conv.requiredSkills,       // vd: ['vi', 'billing']
    team: conv.team,
  });

  const available = candidates.filter(a => a.activeChats < a.maxConcurrent);
  if (available.length === 0) {
    await enqueue(conv);            // không ai rảnh -> vào hàng đợi
    return null;
  }

  // Sticky: ưu tiên agent từng phục vụ contact này (liền mạch ngữ cảnh)
  const sticky = available.find(a => a.id === conv.lastAgentId);
  const chosen = sticky ?? available.sort((a, b) => a.activeChats - b.activeChats)[0];

  await assign(conv.id, chosen.id);   // cập nhật assigned_to + activeChats++
  return chosen.id;
}

Bàn giao bot → người (bot handoff)

Nhiều hội thoại bắt đầu với bot (trả lời FAQ, gom thông tin). Khi bot không xử lý được — khách yêu cầu gặp người, độ tin cậy intent thấp, hay phát hiện cảm xúc tiêu cực — hệ thống handoff sang agent người, kèm toàn bộ ngữ cảnh đã thu thập.

Khách nhắn→ Bot xử lý→ Cần người? (intent thấp / yêu cầu / tức giận)→ Router gán agent→ Agent nhận kèm transcript bot
⚠️ Handoff phải bảo toàn ngữ cảnh

Sai lầm kinh điển: bot gom xong thông tin rồi agent vẫn hỏi lại từ đầu. Khi handoff, phải đính kèm transcript bot + biến đã thu thập (slots) vào hội thoại. Trong mô hình hợp nhất, bot chỉ là một participant với sender_type='bot' — transcript của nó vốn đã nằm trong cùng dòng messages, nên agent thấy ngay.

⑤ Presence & Typing

Ba tín hiệu thời gian thực tạo cảm giác "sống" cho live chat:

🟢 Presence

Trạng thái online/away/offline của agent và (với một số kênh) của khách. Ảnh hưởng định tuyến.

✍️ Typing indicator

"… đang soạn tin". Sự kiện ephemeral, không lưu DB, có debounce/timeout.

✔️ Read receipt

"đã xem". Cập nhật con trỏ đọc (read cursor) theo seq tin nhắn cuối đã xem.

💡 Tín hiệu ephemeral vs dữ liệu bền vững

Typing và presence là ephemeral — phát qua pub/sub realtime (Redis Pub/Sub, Socket.IO room), không ghi DB. Read receipt thì nên bền vững (lưu read cursor) vì nó là một phần lịch sử. Phân biệt hai loại này giúp tránh "ghi DB cho mọi keystroke" — một lỗi hiệu năng phổ biến.

typing.tsSocket.IO
// Typing: chỉ broadcast trong room hội thoại, có debounce + auto-stop.
socket.on('typing:start', ({ conversationId }) => {
  socket.to(`conv:${conversationId}`).emit('typing', {
    userId: socket.data.userId, isTyping: true,
  });
});

// Quan trọng: KHÔNG ghi DB. Tự tắt sau timeout nếu client mất kết nối.
socket.on('typing:stop', ({ conversationId }) => {
  socket.to(`conv:${conversationId}`).emit('typing', {
    userId: socket.data.userId, isTyping: false,
  });
});

// Read receipt: cập nhật con trỏ đọc theo seq (bền vững)
socket.on('read', async ({ conversationId, lastSeq }) => {
  await updateReadCursor(conversationId, socket.data.userId, lastSeq);
  socket.to(`conv:${conversationId}`).emit('read', { lastSeq });
});
🐛 Capability mismatch giữa các kênh

Web chat hỗ trợ typing/presence/read; SMS thì không. Adapter phải nuốt im lặng (no-op) các tín hiệu kênh không hỗ trợ thay vì gọi API gây lỗi. UI agent cũng nên ẩn các tín hiệu đó dựa trên capabilities của kênh. Đừng giả định mọi kênh đều có "đã xem".

⑥ Delivery & Ordering

Mạng không đáng tin: webhook bị gửi lại, client mất sóng rồi gửi lại, tin đến không đúng thứ tự. Ba bài toán phải giải:

1. Idempotency & dedup (chống trùng)

Nền tảng kênh thường at-least-once: một tin có thể đến nhiều lần. Dùng external_id (ID gốc của kênh) làm khóa idempotency, với ràng buộc UNIQUE(conversation_id, external_id). Tin trùng bị bỏ qua thay vì tạo bản ghi mới.

ingest.tsTypeScript
async function ingestInbound(msg: CanonicalMessage) {
  // INSERT idempotent: webhook lặp -> ON CONFLICT bỏ qua, không tạo trùng
  const seq = await nextSeq(msg.conversationId);  // bộ đếm nguyên tử
  const res = await db.query(`
    INSERT INTO messages (id, conversation_id, seq, direction, sender_type, body, external_id)
    VALUES ($1,$2,$3,'inbound','customer',$4,$5)
    ON CONFLICT (conversation_id, external_id) DO NOTHING
    RETURNING id`, [uuid(), msg.conversationId, seq, msg.text, msg.externalId]);

  if (res.rowCount === 0) return;        // đã tồn tại -> dừng, KHÔNG broadcast lại
  broadcastToRoom(msg.conversationId, { ...msg, seq });
}

2. Ordering (sắp xếp đúng thứ tự)

Không dựa vào created_at (lệch đồng hồ, độ trễ webhook). Dùng bộ đếm seq tăng dần đơn điệu trong phạm vi một hội thoại. Client sắp xếp theo seq; nếu phát hiện "lỗ" (nhận seq 5 mà chưa có 4) thì gọi API lấp khoảng trống. seq theo từng hội thoại (không cần toàn cục) giúp đơn giản và mở rộng tốt.

3. Đảm bảo gửi đi (outbound delivery)

Khi agent gửi reply, vòng đời tin nhắn đi qua các trạng thái: pending → sent → delivered → read (hoặc failed). Adapter cập nhật trạng thái từ phản hồi API và từ webhook trạng thái của kênh. Lỗi tạm thời thì retry có backoff + idempotency key để không gửi đôi.

pending→ sent (API nhận)→ delivered (webhook kênh)→ read ⤷ failed → retry/backoff
⚠️ Tóm tắt nguyên tắc

Dedup bằng external_id, order bằng seq, deliver bằng retry idempotent. Ba câu này là khung trả lời chuẩn cho mọi câu hỏi "đảm bảo tin nhắn nhất quán và đúng thứ tự thế nào".

⑦ Tư duy thiết kế: trừu tượng hóa nhiều kênh thành một mô hình

Đây là phần "system design" của chương. Giả lập một buổi phỏng vấn: "Hãy thiết kế inbox omnichannel cho Contact Center."

Bước 1 — Làm rõ yêu cầu

  • Chức năng: agent thấy mọi kênh trong một inbox; hội thoại liền mạch xuyên kênh; định tuyến + capacity; bot handoff; typing/read.
  • Phi chức năng: realtime (< vài trăm ms), tin nhắn không mất/không trùng/đúng thứ tự, dễ thêm kênh mới, scale theo số hội thoại đồng thời.
  • Quy mô: hàng nghìn agent, hàng chục nghìn hội thoại mở đồng thời, 5+ loại kênh.

Bước 3 — Sơ đồ kiến trúc

Web chat (WS) Messenger (webhook) SMS / Email → Ingress + Adapters → Canonical Message
Canonical Message→ Conversation Engine (dedup · seq · identity)→ DB (conversations · messages)
Conversation Engine→ Router (capacity · skill · sticky)→ Realtime layer (Socket.IO + Redis)→ Agent Inbox UI
💡 Lý do chọn — "một mô hình, N adapter"

Toàn bộ độ phức tạp riêng của từng kênh bị cô lập trong lớp adapter. Conversation engine, router, realtime layer và UI agent chỉ làm việc với canonical model. Hệ quả: thêm kênh mới rủi ro thấp; logic nghiệp vụ (định tuyến, capacity, handoff) viết một lần dùng cho mọi kênh; test dễ vì có thể mock adapter. Đây chính là trừu tượng hóa nhiều kênh thành một mô hình — thông điệp trung tâm của chương. Phần mở rộng realtime đa node xem thêm ở I1.

⚠️ Lỗi thường gặp & Best practices

🚫 if/else theo kênh khắp nơi

Logic kênh rò rỉ vào core. Đúng: cô lập trong adapter, core chỉ thấy canonical model.

🚫 Bỏ qua dedup webhook

Kênh gửi at-least-once → tin trùng. Luôn dùng external_id + UNIQUE.

🚫 Sắp xếp theo timestamp

Lệch đồng hồ + trễ webhook gây sai thứ tự. Dùng seq per-conversation.

🚫 Ghi DB cho typing

Mỗi keystroke một ghi DB = quá tải. Typing/presence phải ephemeral qua pub/sub.

🚫 Handoff mất ngữ cảnh

Bot gom xong, agent hỏi lại từ đầu. Đính kèm transcript + slots khi bàn giao.

🚫 Giả định mọi kênh giống nhau

SMS không có "đã xem". Mô hình hóa capabilities, no-op tín hiệu không hỗ trợ.

✅ Identity resolution sớm

Ánh xạ identity→contact ngay khi nhận tin để hội thoại thực sự xuyên kênh.

✅ Capacity rõ ràng

Đặt hạn mức chat đồng thời + hàng đợi để tránh agent quá tải, khách chờ vô định.

🧪 Bài tập

🧪 Bài 1 — Thiết kế canonical message

Cho 3 kênh: web chat, SMS, email. Hãy liệt kê những trường chung đưa vào canonical model và những trường riêng nên đẩy vào channelMeta. Giải thích vì sao tách như vậy giúp "thêm kênh mới" dễ hơn.

Gợi ý

Chung: externalId, channel, direction, senderType, text, sentAt, seq. Riêng: SMS → fromNumber; email → subject, inReplyTo, cc; web → browser, pageUrl. Tách vì lõi chỉ phụ thuộc phần chung → thêm kênh chỉ là thêm khóa trong channelMeta, không đổi schema lõi và không sửa conversation engine (Open/Closed).

🧪 Bài 2 — Idempotency cho webhook

Nền tảng mạng xã hội gửi lại webhook khi không nhận được 200 trong 5 giây. Hãy mô tả cơ chế đảm bảo một tin nhắn chỉ được lưu một lần và chỉ broadcast cho agent một lần, kể cả khi webhook đến 3 lần.

Gợi ý

Dùng external_id của tin làm khóa idempotency với UNIQUE(conversation_id, external_id) và INSERT ... ON CONFLICT DO NOTHING RETURNING id. Nếu rowCount === 0 nghĩa là đã tồn tại → return sớm, không broadcast lại. Trả 200 nhanh để nền tảng ngừng retry; xử lý nặng đẩy sang queue.

🧪 Bài 3 — Capacity & hàng đợi

Agent có maxConcurrent = 4. Có 10 agent online, 50 hội thoại mới ập đến cùng lúc. Thiết kế thuật toán gán sao cho cân tải, và xử lý phần dư. Điều gì xảy ra khi một agent đóng một chat?

Gợi ý

Tổng sức chứa = 10×4 = 40 slot → gán 40 theo least-busy, 10 hội thoại dư vào queue. Khi agent đóng một chat (activeChats--), phát sự kiện "slot freed" → lấy hội thoại đầu queue (ưu tiên theo thời gian chờ/SLA) và gán cho agent đó. Dùng khóa/atomic để tránh hai agent cùng nhận một hội thoại.

Ngân hàng câu hỏi phỏng vấn

Live chat omnichannel — câu hỏi system design "tủ" của vị trí Fullstack realtime.

Q1Omnichannel và multichannel khác nhau thế nào?Junior›

Trả lời: Multichannel là hỗ trợ nhiều kênh nhưng rời rạc — mỗi kênh một silo, khách đổi kênh phải kể lại từ đầu. Omnichannel hợp nhất: nhiều identity của khách ánh xạ về một contact, mọi kênh đổ vào một dòng hội thoại/ngữ cảnh chung, agent thấy toàn bộ lịch sử xuyên kênh trong một inbox.

⚠️ Bẫy: nói "omnichannel = nhiều kênh hơn" là sai — mấu chốt là hợp nhất ngữ cảnh.

Q2Bạn trừu tượng hóa các kênh khác nhau (web, social, SMS, email) thế nào?Middle›

Trả lời: Dùng Channel Adapter Pattern: mỗi kênh có một adapter implement interface chung (parseInbound, sendOutbound, verifySignature, capabilities). Adapter dịch giao thức riêng của kênh sang/từ canonical message model. Lõi nghiệp vụ chỉ phụ thuộc canonical model — không biết kênh cụ thể. Phần riêng từng kênh được giữ trong channelMeta (JSONB).

Q3Mô hình hóa "hội thoại hợp nhất" ở tầng dữ liệu ra sao?Middle›

Trả lời: Bốn thực thể: contacts (danh tính người) + channel_identities (nhiều identity/kênh → một contact) + conversations (phiên, trạng thái, agent gán, last_seq) + messages (seq, direction, sender_type, external_id, channel_meta). Phần chung ở cột cứng để truy vấn nhanh; phần riêng kênh ở JSONB. Ràng buộc UNIQUE trên (conversation_id, external_id) để idempotent.

Q4Đảm bảo tin nhắn nhất quán và đúng thứ tự xuyên kênh thế nào?Senior›

Trả lời: Ba nguyên tắc: (1) Dedup bằng external_id + UNIQUE + INSERT idempotent; (2) Order bằng bộ đếm seq tăng đơn điệu per-conversation (không dựa timestamp); (3) Delivery bằng máy trạng thái pending→sent→delivered→read và retry có backoff với idempotency key. Client phát hiện "lỗ" seq thì gọi API lấp khoảng trống.

⚠️ Bẫy: sắp xếp theo created_at — sai vì lệch đồng hồ giữa server và độ trễ webhook khác nhau.

Q5Một agent xử lý N chat đồng thời — thiết kế capacity & định tuyến thế nào?Senior›

Trả lời: Mỗi agent có maxConcurrent. Router lọc agent online theo skill/team, chỉ gán khi activeChats < maxConcurrent, chọn theo least-busy (có thể ưu tiên sticky agent đã từng phục vụ contact). Không ai rảnh → vào queue. Khi agent đóng chat, phát sự kiện "slot freed" → lấy hội thoại đầu queue (ưu tiên theo SLA/thời gian chờ). Dùng atomic/lock để tránh gán đôi.

Q6Thêm một kênh mới (vd WhatsApp) tốn bao nhiêu công? Vì sao?Middle›

Trả lời: Chỉ cần viết một adapter mới implement interface chung: parse webhook → canonical, gửi outbound qua API WhatsApp, khai báo capabilities, verify chữ ký. Không sửa conversation engine, router, realtime layer hay UI agent vì chúng chỉ làm việc với canonical model. Đây là minh chứng của nguyên lý Open/Closed — kiến trúc tốt khiến việc thêm kênh là rủi ro thấp.

Q7Bot handoff sang agent người hoạt động ra sao? Cần lưu ý gì?Middle›

Trả lời: Bot là một participant với sender_type='bot', transcript của nó nằm sẵn trong dòng messages. Khi bot không xử lý được (yêu cầu gặp người, intent confidence thấp, phát hiện tức giận), hệ thống chuyển trạng thái hội thoại sang cần-người và gọi router gán agent. Lưu ý: phải bảo toàn ngữ cảnh — agent thấy ngay transcript + các slot bot đã thu thập, không bắt khách kể lại.

Q8Typing, presence, read receipt khác nhau và nên lưu/truyền thế nào?Middle›

Trả lời: Typing và presence là ephemeral — phát qua pub/sub realtime trong room hội thoại, không ghi DB, có debounce và auto-timeout. Read receipt nên bền vững: lưu read cursor (seq tin cuối đã xem) để khôi phục khi reload. Phân biệt rõ tránh lỗi ghi DB cho mỗi keystroke.

Q9Các kênh có capability khác nhau (SMS không có "đã xem") — xử lý ra sao?Middle›

Trả lời: Mô hình hóa capabilities trong mỗi adapter (typing/readReceipt/attachments/maxLength...). Khi core phát một tín hiệu mà kênh không hỗ trợ, adapter no-op im lặng thay vì gọi API gây lỗi. UI agent đọc capabilities để ẩn/hiện các chỉ báo tương ứng và cảnh báo giới hạn (vd độ dài SMS). Không bao giờ giả định mọi kênh giống nhau.

Q10Hãy thiết kế một inbox omnichannel từ đầu (system design tổng hợp).Senior›

Trả lời: (1) Làm rõ yêu cầu: liền mạch xuyên kênh, realtime, không mất/trùng/đúng thứ tự, dễ thêm kênh, scale theo hội thoại. (2) Ingress + Adapters chuẩn hóa về canonical message. (3) Conversation Engine: identity resolution, dedup (external_id), gán seq, lưu DB. (4) Router: skill + capacity + sticky, queue khi đầy. (5) Realtime layer Socket.IO + Redis adapter để fan-out đa node. (6) Agent Inbox UI subscribe room. Nhấn đánh đổi: "một mô hình, N adapter" để cô lập độ phức tạp kênh.

⚠️ Bẫy: nhảy vào code/DB ngay mà bỏ qua bước làm rõ yêu cầu và nêu đánh đổi — interviewer đánh giá tư duy thiết kế hơn là chi tiết.

Q11Realtime layer scale ngang thế nào khi có nhiều node Socket.IO?Senior›

Trả lời: Mỗi node giữ một phần kết nối socket; dùng Redis adapter (pub/sub) để khi node A emit vào một room, các node khác giữ socket cùng room cũng nhận và đẩy tới client của mình. Cần sticky session ở load balancer (hoặc transport bền). Trạng thái presence/typing đi qua Redis; dữ liệu bền vững vẫn ở DB. Xem sâu hơn ở I1.

Q12Làm sao hợp nhất một khách dùng nhiều identity (PSID, số ĐT, email)?Senior›

Trả lời: Bảng channel_identities ánh xạ (channel, external_id) → contact_id. Khi tin mới đến, tra identity; nếu chưa có thì tạo và có thể gợi ý gộp contact khi phát hiện email/số ĐT trùng (deterministic) hoặc dựa heuristic. Việc gộp nên thận trọng/cho phép undo vì gộp nhầm hai người là lỗi nghiêm trọng. Identity resolution là điều kiện tiên quyết để hội thoại thật sự xuyên kênh.

⚠️ Bẫy: tự động gộp quá hung hăng → trộn lẫn dữ liệu của hai khách khác nhau, vi phạm quyền riêng tư.
