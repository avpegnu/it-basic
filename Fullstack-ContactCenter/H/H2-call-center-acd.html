Call Center: ACD, Định tuyến & Call State

Trái tim của tổng đài: phân phối cuộc gọi tự động (ACD), thuật toán định tuyến, IVR và máy trạng thái cuộc gọi. Trọng tâm tư duy thiết kế engine định tuyến.

🎯 Học xong chương này bạn sẽ

• Giải thích ACD (Automatic Call Distribution) là gì, vì sao nó là bộ não phân phối cuộc gọi của một Contact Center.

• So sánh các thuật toán định tuyến (round-robin, least-recently-used, least-busy, skill-based, priority, sticky agent) theo trục công bằng ⇄ hiệu quả.

• Thiết kế hàng đợi ưu tiên, ước lượng thời gian chờ, xử lý overflow và SLA khi tải tăng.

• Mô hình hóa IVR (cây menu, DTMF, tự phục vụ) và máy trạng thái cuộc gọi đầy đủ trạng thái + chuyển tiếp/hội nghị.

• Phác thảo engine định tuyến skill-based ở quy mô lớn: cấu trúc dữ liệu, cập nhật realtime, chọn agent kế tiếp, xử lý agent rớt giữa chừng.

• Tự tin trả lời câu hỏi phỏng vấn dạng "Thiết kế một hệ thống ACD".

💡 Liên hệ thực tế

Khi khách hàng gọi vào tổng đài, họ không quan tâm bên trong là Node.js hay gì. Họ chỉ muốn: không chờ lâu, gặp đúng người giải quyết được vấn đề, và không bị rớt. ACD chính là thành phần biến ba mong muốn đó thành thuật toán: nhận tín hiệu cuộc gọi → tra cứu kỹ năng cần thiết → chọn agent tối ưu trong số đang rảnh → nếu chưa ai rảnh thì xếp hàng có ưu tiên. Toàn bộ chương này là cách tư duy thiết kế phần lõi đó — thứ phân biệt ứng viên "đã làm form CRUD" với ứng viên "hiểu hệ thống realtime".

① ACD — Phân phối cuộc gọi tự động

ACD (Automatic Call Distribution) là cơ chế tự động nhận các tương tác đến (cuộc gọi, chat, email...) và phân phối chúng tới agent (nhân viên) phù hợp nhất theo một bộ quy tắc. Không có ACD, mọi cuộc gọi sẽ đổ về một chỗ và phải phân công thủ công — không thể chịu tải, không công bằng, không đo lường được.

Mục tiêu của ACD luôn là cân bằng ba lực kéo mâu thuẫn nhau:

⏱️ Hiệu quả

Khách chờ ngắn nhất, agent ít rảnh rỗi nhất (occupancy cao), throughput tối đa.

⚖️ Công bằng

Tải chia đều giữa agent — không ai bị dồn việc, không ai "ngồi chơi"; tránh burnout.

🎯 Chất lượng

Đúng kỹ năng → giải quyết ngay lần đầu (First Contact Resolution), không phải chuyển lòng vòng.

Một engine ACD nằm ở vị trí giao thoa giữa tín hiệu thời gian thực (cuộc gọi đến, agent đổi trạng thái) và quy tắc nghiệp vụ (kỹ năng, ưu tiên, SLA). Về mặt kiến trúc, nó là một dịch vụ giữ trạng thái sống của hệ thống:

Cuộc gọi đến→ IVR phân loại→ ACD: chọn agent / xếp hàng→ Agent nhận→ Wrap-up & ghi nhận
ℹ️ ACD vs PBX vs Routing Engine

Trong tổng đài truyền thống, PBX (Private Branch Exchange) lo phần tổng đài vật lý/kết nối; ACD là lớp logic phân phối nằm trên. Ngày nay với CCaaS (Contact Center as a Service), "ACD" thường được hiểu chính là routing engine — một dịch vụ phần mềm. Phần thiết kế ở mục ⑦ chính là tâm điểm phỏng vấn.

② Thuật toán định tuyến

Khi có cuộc gọi cần phân phối và có nhiều agent đủ điều kiện, chọn ai? Đó là câu hỏi của thuật toán định tuyến. Mỗi thuật toán tối ưu một mục tiêu khác nhau và có đánh đổi riêng.

Trong thực tế, một engine production hiếm khi dùng một thuật toán. Nó tổ hợp nhiều tầng: lọc theo kỹ năng (skill) → trong số đủ điều kiện thì áp dụng priority → rồi mới đến tie-breaker bằng least-busy hay LRU. Tư duy đúng là coi việc chọn agent như một hàm chấm điểm (scoring), không phải một quy tắc cứng.

routing-strategies.tsTypeScript
// Mỗi strategy nhận danh sách agent đủ điều kiện, trả về agent được chọn (hoặc null)
interface Agent {
  id: string;
  status: 'available' | 'busy' | 'wrapup' | 'offline';
  activeCalls: number;      // số cuộc đang xử lý
  lastAssignedAt: number;   // timestamp lần cuối nhận việc
  skills: Record<string, number>; // { 'billing': 0.9, 'tech': 0.6 } — độ thành thạo 0..1
}

type Strategy = (agents: Agent[]) => Agent | null;

// Round-robin (giữ con trỏ ngoài hàm)
let rrPointer = 0;
const roundRobin: Strategy = (agents) => {
  if (!agents.length) return null;
  const a = agents[rrPointer % agents.length];
  rrPointer++;
  return a;
};

// Least-recently-used: agent rảnh lâu nhất (lastAssignedAt nhỏ nhất)
const leastRecentlyUsed: Strategy = (agents) =>
  agents.reduce((best, a) => (a.lastAssignedAt < best.lastAssignedAt ? a : best), agents[0]) ?? null;

// Least-busy: ít cuộc đang xử lý nhất
const leastBusy: Strategy = (agents) =>
  agents.reduce((best, a) => (a.activeCalls < best.activeCalls ? a : best), agents[0]) ?? null;

Tốt hơn nữa: hợp nhất tất cả thành một điểm tổng hợp. Cách này giúp tinh chỉnh hành vi bằng trọng số thay vì viết lại logic.

scoring.tsTypeScript
// Chọn agent theo điểm: kỹ năng cao + đỡ bận + nghỉ lâu = điểm cao
function pickBestAgent(call: Call, agents: Agent[]): Agent | null {
  const eligible = agents.filter(
    (a) => a.status === 'available' && (a.skills[call.requiredSkill] ?? 0) >= call.minProficiency
  );
  if (!eligible.length) return null; // không ai phù hợp → xếp hàng

  const now = Date.now();
  return eligible
    .map((a) => {
      const skill   = a.skills[call.requiredSkill];          // 0..1 — càng cao càng tốt
      const idle    = (now - a.lastAssignedAt) / 60000;       // phút nghỉ — công bằng
      const loadPen = a.activeCalls;                          // càng bận càng bị trừ
      const score = skill * 3 + Math.min(idle, 5) * 0.5 - loadPen * 2;
      return { a, score };
    })
    .sort((x, y) => y.score - x.score)[0].a;
}
⚠️ Công bằng vs Hiệu quả

Tối ưu hiệu quả thuần (luôn chọn agent giỏi nhất, nhanh nhất) sẽ khiến vài agent gánh hết việc còn người mới ngồi không — vừa bất công vừa gây nghỉ việc. Tối ưu công bằng thuần (round-robin cứng) lại bỏ phí lợi thế kỹ năng. Engine tốt cho phép điều chỉnh trọng số để dịch chuyển trên trục này tuỳ chính sách từng tổ chức/khung giờ.

③ Quản lý hàng đợi

Khi không có agent nào rảnh phù hợp, cuộc gọi vào hàng đợi (queue). Hàng đợi không phải FIFO đơn giản — nó là hàng đợi ưu tiên có nhiều thuộc tính nghiệp vụ.

Các thành phần của một hàng đợi tốt

🔢 Ưu tiên (priority)

VIP, SLA sắp hết hạn, callback đã hẹn → lên trước. Thường biểu diễn bằng số priority + thời điểm vào hàng để chống đói.

📍 Vị trí (position)

"Bạn đang ở vị trí thứ 4" — cần tính được và thông báo cho khách để giảm sốt ruột.

⏳ EWT — Estimated Wait Time

Ước lượng thời gian chờ dựa trên tốc độ phục vụ và độ dài hàng.

🌊 Overflow

Khi hàng quá dài/chờ quá lâu → tràn sang nhóm khác, đề nghị callback, hoặc gửi sang voicemail/self-service.

Chống đói (starvation) cho khách ưu tiên thấp

Nếu luôn ưu tiên VIP, khách thường có thể chờ mãi không tới lượt. Giải pháp kinh điển là aging: điểm ưu tiên hiệu dụng tăng dần theo thời gian chờ.

priority-queue.tsTypeScript
interface QueuedCall {
  callId: string;
  basePriority: number;  // 0 = thường, 10 = VIP
  enqueuedAt: number;    // timestamp vào hàng
  requiredSkill: string;
}

// Điểm hiệu dụng = ưu tiên gốc + "tuổi chờ" (mỗi 30s chờ +1 điểm)
function effectiveScore(c: QueuedCall, now = Date.now()): number {
  const waitedSec = (now - c.enqueuedAt) / 1000;
  const aging = Math.floor(waitedSec / 30);
  return c.basePriority + aging;        // khách thường chờ lâu sẽ vượt VIP mới vào
}

// Lấy cuộc kế tiếp cho một skill: điểm cao nhất, hoà thì vào hàng trước
function dequeueFor(skill: string, queue: QueuedCall[]): QueuedCall | null {
  const candidates = queue.filter((c) => c.requiredSkill === skill);
  if (!candidates.length) return null;
  return candidates.sort((a, b) => {
    const diff = effectiveScore(b) - effectiveScore(a);
    return diff !== 0 ? diff : a.enqueuedAt - b.enqueuedAt; // FIFO tie-break
  })[0];
}

Ước lượng thời gian chờ (EWT)

Công thức trực giác hay dùng:

📐 EWT xấp xỉ

EWT ≈ (vị trí trong hàng) × AHT ÷ (số agent đang phục vụ skill này)

Trong đó AHT = Average Handle Time (thời gian xử lý trung bình một cuộc, gồm talk + hold + wrap-up). Ví dụ: bạn đứng thứ 6, AHT = 4 phút, có 3 agent → EWT ≈ 6 × 4 ÷ 3 = 8 phút.

Đây chỉ là ước lượng. Sản phẩm trưởng thành dùng thêm dữ liệu lịch sử theo khung giờ, tốc độ rời hàng (abandonment), và làm mượt bằng trung bình trượt để con số không nhảy giật. Quan trọng là thà ước lượng hơi cao (khách vui khi được phục vụ sớm hơn dự kiến) còn hơn hứa thấp rồi để khách chờ lâu hơn.

SLA và overflow

SLA thường phát biểu kiểu "80% cuộc gọi được trả lời trong 20 giây". Khi một cuộc sắp vi phạm ngưỡng đó, engine cần hành động: nâng priority, mở rộng pool (cho phép agent kỹ năng thấp hơn nhận), hoặc kích hoạt overflow.

Chờ > 20s?→ Nâng priority (aging)→ Chờ > 60s?→ Mở rộng pool kỹ năng→ Chờ > 120s?→ Đề nghị callback / voicemail

④ IVR — Interactive Voice Response

IVR là hệ thống menu thoại tương tác: "Nhấn 1 để gặp bộ phận cước, nhấn 2 cho kỹ thuật...". Nó giải quyết hai việc trước cả ACD: phân loại nhu cầu (để định tuyến đúng) và tự phục vụ (giải quyết luôn mà không cần agent — tra cứu dư nợ, đặt lại mật khẩu...).

Mô hình hóa cây IVR

Một IVR về bản chất là cây/đồ thị có hướng các node menu. Mỗi node có lời nhắc (prompt), các phím chấp nhận (DTMF — tín hiệu khi bấm phím) và hành động tương ứng: đi tới node con, định tuyến vào queue, hay thực thi một tác vụ tự phục vụ.

ivr-tree.tsTypeScript
type IvrAction =
  | { type: 'goto'; node: string }
  | { type: 'route'; skill: string; priority?: number }
  | { type: 'selfService'; handler: string }   // vd 'checkBalance'
  | { type: 'hangup' };

interface IvrNode {
  id: string;
  prompt: string;                        // câu thoại phát ra (TTS hoặc audio)
  options: Record<string, IvrAction>; // '1' -> action, '2' -> action
  timeoutMs: number;                     // không bấm gì thì sao
  onTimeout: IvrAction;
}

const tree: Record<string, IvrNode> = {
  root: {

      '1': { type: 'selfService', handler: 'resetPassword' },
      '2': { type: 'route', skill: 'tech', priority: 0 },
    },
    timeoutMs: 7000,

  },
};
💡 Nguyên tắc thiết kế IVR

• Phẳng > sâu: tránh menu lồng quá 2–3 cấp, khách dễ lạc và bực. • Luôn có lối thoát về người thật (phím 0). • Timeout phải có hành động an toàn chứ không cụt. • Tự phục vụ chỉ nên dùng cho tác vụ rõ ràng, có thể xác thực được; còn lại định tuyến cho agent.

⑤ Call State Machine — Máy trạng thái cuộc gọi

Một cuộc gọi (hay phiên chat) đi qua một loạt trạng thái có quy luật chuyển tiếp rõ ràng. Mô hình hóa nó bằng finite state machine (FSM) giúp code đúng đắn: chỉ cho phép những chuyển tiếp hợp lệ, dễ log/audit, dễ tính metric.

idle→ ringing→ queued→ assigned→ active→ hold→ wrap-up→ ended

Ngoài luồng chính còn có nhánh phụ: từ active có thể transfer (chuyển sang agent khác → quay lại queued/assigned) hoặc conference (thêm người vào). Từ queued khách có thể abandon (cúp máy → ended với lý do bỏ hàng).

Trạng tháiÝ nghĩaChuyển tiếp hợp lệ
idleChưa có gì xảy ra (slot cuộc gọi)→ ringing
ringingCuộc gọi đến, đang qua IVR/đổ chuông→ queued, → ended (khách cúp)
queuedĐang chờ trong hàng đợi→ assigned, → ended (abandon/overflow)
assignedĐã chọn agent, đang đổ chuông tới agent→ active, → queued (agent không nhận → re-route)
activeĐang nói chuyện→ hold, → wrap-up, → queued (transfer)
holdTạm giữ máy→ active
wrap-upSau cuộc gọi: agent ghi chú, gắn nhãn→ ended
endedKết thúc (lưu lý do)(terminal)
call-fsm.tsTypeScript
type CallState =
  | 'idle' | 'ringing' | 'queued' | 'assigned'
  | 'active' | 'hold' | 'wrapup' | 'ended';

// Bảng chuyển tiếp hợp lệ — nguồn duy nhất của sự thật
const TRANSITIONS: Record<CallState, CallState[]> = {
  idle:     ['ringing'],
  ringing:  ['queued', 'ended'],
  queued:   ['assigned', 'ended'],     // ended = abandon/overflow
  assigned: ['active', 'queued'],       // queued = agent không nhận, re-route
  active:   ['hold', 'wrapup', 'queued'], // queued = transfer
  hold:     ['active'],
  wrapup:   ['ended'],
  ended:    [],
};

class CallSession {
  state: CallState = 'idle';
  history: { state: CallState; at: number }[] = [];

  transition(to: CallState): void {
    if (!TRANSITIONS[this.state].includes(to)) {
      throw new Error(`Chuyển tiếp không hợp lệ: ${this.state} -> ${to}`);
    }
    this.history.push({ state: to, at: Date.now() });
    this.state = to;
    // phát event realtime để dashboard/agent UI cập nhật (xem H4)
  }
}
💡 Vì sao FSM quan trọng

Lịch sử trạng thái với timestamp chính là nguồn để tính mọi metric: thời gian chờ (ringing→active), AHT (active→ended), tỉ lệ abandon (queued→ended không qua active). Cấm chuyển tiếp sai cũng ngăn lỗi kiểu "đặt máy đang ended về active". Đây là một mẫu hỏi rất hay trong phỏng vấn.

⑥ Skill-based Routing

Skill-based routing ghép cuộc gọi với agent dựa trên kỹ năng cần thiết và độ thành thạo. Đây là cốt lõi tạo chất lượng dịch vụ: khách hỏi về cước thì gặp người rành cước, không phải bất kỳ ai rảnh.

Ba khái niệm

🏷️ Skill

Năng lực phân loại được: 'billing', 'tech', 'tiếng Anh', 'khách doanh nghiệp'...

⭐ Proficiency

Độ thành thạo (vd 1–5 hoặc 0..1). Agent có thể giỏi billing, trung bình tech.

📋 Requirement

Cuộc gọi đòi hỏi gì: skill nào, mức tối thiểu, ngôn ngữ, hạng khách.

Quá trình matching = lọc agent thỏa requirement → trong số đó ưu tiên proficiency cao và đỡ bận. Khi pool quá hẹp (chờ lâu), engine có thể nới yêu cầu dần: hạ mức proficiency tối thiểu, mở rộng sang skill lân cận, hoặc cho phép agent "có thể xử lý được" (dù không lý tưởng) nhận.

Routing theo presence

Một cuộc gọi chỉ nên tới agent đang thực sự sẵn sàng. Trạng thái hiện diện (presence) của agent — available / on-call / wrap-up / break / offline — là dữ liệu realtime mà engine phải bám sát. Agent đặt mình "Away" để đi ăn trưa thì không được nhận cuộc nào. Phần này khớp chặt với hệ thống realtime (WebSocket) ở các chương trước.

skill-match.tsTypeScript
interface CallRequirement {
  skill: string;
  minProficiency: number;   // 0..1
  language?: string;
}

function match(req: CallRequirement, agents: Agent[]): Agent[] {
  return agents
    .filter((a) => a.status === 'available')
    .filter((a) => (a.skills[req.skill] ?? 0) >= req.minProficiency)
    .filter((a) => !req.language || a.languages?.includes(req.language))
    .sort((x, y) => {
      const p = (y.skills[req.skill] ?? 0) - (x.skills[req.skill] ?? 0);
      return p !== 0 ? p : x.activeCalls - y.activeCalls; // giỏi hơn, rồi đỡ bận hơn
    });
}

// Nới yêu cầu khi chờ quá lâu (escalation)
function relaxRequirement(req: CallRequirement, waitedSec: number): CallRequirement {
  if (waitedSec > 60)  return { ...req, minProficiency: Math.max(0.4, req.minProficiency - 0.3) };
  if (waitedSec > 120) return { ...req, minProficiency: 0 }; // bất kỳ ai có skill
  return req;
}

⑦ Tư duy thiết kế Routing Engine

Đây là phần quan trọng nhất khi phỏng vấn. Câu hỏi điển hình: "Thiết kế engine định tuyến cho 10.000 agent, 50.000 cuộc gọi đồng thời." Cách trả lời tốt đi theo trình tự: làm rõ yêu cầu → chọn cấu trúc dữ liệu → mô tả luồng realtime → bàn về scale và lỗi.

Bước 1 — Làm rõ yêu cầu

  • Chức năng: định tuyến skill-based, hàng đợi ưu tiên, EWT, transfer, overflow, presence realtime.
  • Phi chức năng: độ trễ định tuyến thấp (< vài trăm ms), không mất cuộc gọi, công bằng tải, theo dõi được, chịu lỗi khi agent/instance rớt.
  • Quy mô: bao nhiêu agent, cuộc/giây cao điểm, bao nhiêu skill, bao nhiêu tenant (xem H6).

Bước 2 — Cấu trúc dữ liệu lõi

Hai tập trạng thái sống cần truy cập cực nhanh:

👥 Agent pool theo skill

Index skill → tập agent available để chọn ứng viên trong O(số agent của skill) thay vì quét toàn bộ.

📥 Hàng đợi theo skill

Mỗi skill một priority queue (heap) các cuộc đang chờ; pop ra cuộc điểm cao nhất.

engine-state.tsTypeScript
class RoutingEngine {
  // skill -> set agent đang available có skill đó
  availableBySkill = new Map<string, Set<AgentId>>();
  // skill -> priority queue các cuộc đang chờ
  queueBySkill = new Map<string, MinHeap<QueuedCall>>();
  agents = new Map<AgentId, Agent>();

  // Sự kiện: agent trở nên rảnh -> thử ghép ngay một cuộc đang chờ
  onAgentAvailable(agentId: AgentId) {
    const agent = this.agents.get(agentId)!;
    for (const skill of Object.keys(agent.skills)) {
      this.availableBySkill.get(skill)?.add(agentId);
    }
    this.tryDispatch(agent); // "pull": agent rảnh thì kéo việc về
  }

  // Sự kiện: cuộc mới vào hàng -> thử ghép ngay một agent
  onCallEnqueued(call: QueuedCall) {
    const agent = pickBestAgent(call, this.availableFor(call.requiredSkill));
    if (agent) this.assign(call, agent);
    else this.queueBySkill.get(call.requiredSkill)!.push(call);
  }
}

Điểm mấu chốt: định tuyến là hướng sự kiện. Có hai sự kiện kích hoạt việc ghép — cuộc mới đến hoặc agent vừa rảnh. Cả hai cùng cố gắng "khớp một cặp" rồi cập nhật cả hai index. Không quét định kỳ toàn bộ (lãng phí, trễ).

Bước 3 — Push vs Pull cho agent

Mô hìnhCách hoạt độngƯu / Nhược
PushEngine chọn agent và đẩy cuộc tới (đổ chuông)✅ Kiểm soát phân phối, công bằng, tối ưu toàn cục.
❌ Phải xử lý agent không bắt máy (timeout → re-route).
PullCuộc nằm trong hàng, agent rảnh tự "nhận cuộc kế tiếp"✅ Đơn giản, agent chủ động.
❌ Khó đảm bảo công bằng/ưu tiên, agent có thể "kén" việc.

Phần lớn ACD nghiêm túc dùng push (đảm bảo ưu tiên & công bằng), nhưng kèm cơ chế offer-accept có timeout: engine đề nghị → agent có vài giây để nhận → quá hạn coi như từ chối, cuộc quay lại hàng và agent có thể bị đánh dấu "không phản hồi".

Bước 4 — Realtime & xử lý lỗi

⚡ Cập nhật realtime

Agent đổi presence/online qua WebSocket → engine cập nhật index ngay. Dashboard nhận event để vẽ trạng thái hàng đợi.

💥 Agent rớt giữa định tuyến

Đã assigned nhưng agent mất kết nối/không nhận → timeout → trả cuộc về queued, đánh dấu agent offline, re-route.

🔁 Idempotency

Một cuộc chỉ được gán cho một agent. Dùng khóa/atomic để 2 sự kiện đồng thời không double-assign.

🗃️ Khôi phục state

Instance engine chết → khôi phục từ store (Redis/DB) hoặc event log để không mất hàng đợi.

🐛 Tình huống kinh điển: agent rớt ngay khi vừa được gán

Cuộc ở assigned, engine đang đổ chuông tới agent thì agent mất mạng. Nếu không có timeout, cuộc kẹt mãi ở assigned — khách chờ vô tận. Giải pháp: mỗi lần gán đặt một timer (vd 15s); hết hạn mà chưa thành active → tự động assigned → queued, hạ presence agent xuống offline, và nâng priority cuộc đó để bù thời gian đã chờ.

Bước 5 — Scale ở quy mô lớn

Khi vượt khả năng một process, ta cần phân mảnh và đồng bộ:

Gateway nhận cuộc→ Phân mảnh theo skill / tenant→ Engine shard (giữ state in-memory)→ Redis (presence + queue dùng chung)→ Pub/Sub realtime → Agent & Dashboard
  • Sharding: tách theo tenant hoặc nhóm skill để mỗi shard giữ một phần state, giảm tranh chấp. Một tenant lớn có thể chiếm shard riêng.
  • State dùng chung: presence và hàng đợi nên đặt ở store nhanh (Redis) để nhiều instance thấy nhất quán; in-memory chỉ là cache/index để chọn nhanh.
  • Atomic assign: dùng thao tác nguyên tử (Lua script trong Redis, hoặc hàng đợi message) để đảm bảo một cuộc chỉ tới một agent dù nhiều instance cùng xử lý.
  • Backpressure: khi quá tải, kích hoạt overflow/callback thay vì để hàng đợi phình vô hạn.
💡 Tư duy được đánh giá cao

Người phỏng vấn không tìm "đáp án đúng tuyệt đối" mà tìm cách bạn lập luận đánh đổi: vì sao chọn push thay vì pull, vì sao tách state ra Redis, làm sao đảm bảo không double-assign, xử lý agent rớt thế nào. Luôn nêu phương án — đánh đổi — lý do chọn. Đây cũng là mạch tư duy xuyên suốt phần thiết kế hệ thống (xem các chương I*).

⚠️ Lỗi thường gặp & Best practices

🚫 Quên chống đói (starvation)

Chỉ ưu tiên VIP/skill cao → khách thường chờ mãi. Phải có aging tăng priority theo thời gian chờ.

🚫 Không xử lý agent không nhận

Gán xong không có timeout → cuộc kẹt ở assigned. Luôn đặt timer offer-accept và re-route.

🚫 Double-assign

Hai sự kiện đồng thời gán cùng một cuộc cho 2 agent. Cần thao tác atomic/khóa.

🚫 Quét toàn bộ định kỳ

Polling toàn pool mỗi giây → trễ và tốn. Hãy hướng sự kiện: agent-rảnh / cuộc-đến.

🚫 IVR quá sâu, cụt timeout

Menu lồng nhiều cấp, không có phím 0 và không có hành động timeout → khách lạc và bực.

🚫 EWT giật cục

Hiển thị EWT nhảy loạn làm mất niềm tin. Làm mượt bằng trung bình trượt, thà ước lượng hơi cao.

🚫 Chuyển trạng thái tùy tiện

Không kiểm soát transition → state sai, metric sai. Dùng FSM với bảng chuyển tiếp hợp lệ.

🚫 Mất hàng đợi khi instance chết

State chỉ in-memory → restart mất hết cuộc đang chờ. Lưu ở store dùng chung + khôi phục.

🧪 Bài tập

🧪 Bài 1 — Hàng đợi ưu tiên có chống đói

Viết hàm nextCall(queue, skill) chọn cuộc kế tiếp cho một skill: ưu tiên cao trước, nhưng cuộc chờ > 90s phải được nâng để không bị "đói". Mô tả cách bạn chống starvation và tie-break thế nào.

Gợi ý

Dùng điểm hiệu dụng = basePriority + floor(waitedSec / 30). Sắp giảm dần theo điểm, hoà nhau thì lấy enqueuedAt nhỏ hơn (FIFO). Aging đảm bảo khách thường chờ đủ lâu sẽ vượt VIP mới vào, tránh starvation. Có thể thêm trần để VIP không bị vượt quá dễ.

🧪 Bài 2 — Offer-accept có timeout

Mô tả (bằng mã giả hoặc TS) luồng khi engine assigned một cuộc tới agent nhưng agent không bấm nhận trong 15s. Cuộc và agent phải về trạng thái nào? Vì sao cần nâng priority cuộc đó?

Gợi ý

Khi gán: lưu offer = { callId, agentId, expiresAt } và đặt timer. Nếu agent nhận trước hạn → assigned → active, huỷ timer. Nếu hết hạn → assigned → queued, đánh dấu agent unresponsive/offline, tăng basePriority của cuộc để bù thời gian đã chờ (giữ công bằng), rồi tryDispatch lại với agent khác.

🧪 Bài 3 — Máy trạng thái cuộc gọi

Cho FSM ở mục ⑤, hãy chỉ ra hai chuyển tiếp không hợp lệ mà code phải chặn, và viết một ca tính tỉ lệ abandon từ history. Abandon là gì xét theo chuỗi trạng thái?

Gợi ý

Không hợp lệ ví dụ: ended → active (cuộc đã kết thúc) hoặc idle → active (bỏ qua ringing/queued). Abandon = cuộc đi vào queued rồi tới ended mà không bao giờ qua active. Tỉ lệ abandon = (số cuộc queued-rồi-ended-không-active) ÷ (tổng cuộc từng vào queued).

Ngân hàng câu hỏi phỏng vấn

ACD & routing — chủ đề "đinh" cho vị trí fullstack realtime/Contact Center.

Q1ACD là gì? Nó giải quyết bài toán nào?Junior›

Trả lời: ACD (Automatic Call Distribution) là cơ chế tự động nhận các tương tác đến và phân phối tới agent phù hợp theo quy tắc. Nó giải quyết ba bài toán: phục vụ nhanh (chờ ngắn), đúng người (đúng kỹ năng), và công bằng (chia tải đều). Không có ACD thì phải phân công thủ công, không chịu tải và không đo lường được.

Q2So sánh round-robin, least-recently-used và least-busy.Junior›

Trả lời: Round-robin chọn agent kế tiếp theo vòng — đơn giản, công bằng số lượt nhưng không tính độ bận thực. LRU chọn agent rảnh lâu nhất — công bằng theo thời gian nghỉ. Least-busy chọn agent ít tải nhất (ít cuộc/occupancy thấp) — cân bằng tải tốt nhất nhưng cần đo occupancy realtime chính xác. Production thường tổ hợp: lọc skill trước rồi tie-break bằng least-busy/LRU.

Q3Mô hình skill-based routing hoạt động thế nào?Middle›

Trả lời: Mỗi agent có ma trận skill → proficiency. Mỗi cuộc có requirement (skill cần, mức tối thiểu, ngôn ngữ, hạng khách). Matching = lọc agent available thỏa requirement → ưu tiên proficiency cao + đỡ bận. Khi pool hẹp và chờ lâu, nới yêu cầu dần (hạ mức tối thiểu, mở skill lân cận) để không kẹt mãi.

⚠️ Bẫy: nếu yêu cầu quá chặt mà không có cơ chế nới, khách chờ vô hạn dù tổng đài còn agent rảnh.

Q4Làm sao đảm bảo công bằng hàng đợi mà vẫn ưu tiên VIP?Middle›

Trả lời: Dùng hàng đợi ưu tiên với aging: điểm hiệu dụng = priority gốc + hàm tăng theo thời gian chờ. VIP lên trước, nhưng khách thường chờ đủ lâu sẽ tích điểm vượt VIP mới vào → tránh starvation. Có thể đặt trần aging để VIP không bị vượt quá dễ. Tie-break bằng thứ tự vào hàng (FIFO).

Q5Ước lượng thời gian chờ (EWT) tính thế nào? Hạn chế?Middle›

Trả lời: Xấp xỉ EWT ≈ vị trí × AHT ÷ số agent phục vụ, với AHT là thời gian xử lý trung bình. Hạn chế: chỉ đúng khi tải ổn định; thực tế có abandonment, agent vào/ra, biến động giờ cao điểm. Cải thiện bằng dữ liệu lịch sử theo khung giờ + trung bình trượt để con số mượt; và nên ước lượng hơi cao để khách hài lòng khi được phục vụ sớm hơn.

Q6Hãy thiết kế một engine ACD ở mức cao.Senior›

Trả lời: (1) Làm rõ yêu cầu: skill-based, priority queue, EWT, transfer, overflow, presence realtime; phi chức năng: trễ thấp, không mất cuộc, công bằng, chịu lỗi. (2) Cấu trúc dữ liệu: index skill → set agent available + skill → priority queue cuộc chờ. (3) Hướng sự kiện: cuộc-đến hoặc agent-rảnh đều thử ghép một cặp rồi cập nhật index. (4) Dùng push + offer-accept timeout. (5) Realtime qua WebSocket/pub-sub; state dùng chung ở Redis; assign atomic; xử lý agent rớt bằng timer re-route. (6) Scale bằng sharding theo tenant/skill, backpressure khi quá tải.

Q7Push hay pull cho agent? Đánh đổi ra sao?Senior›

Trả lời: Push: engine chọn và đẩy cuộc tới agent — kiểm soát ưu tiên/công bằng/tối ưu toàn cục, nhưng phải xử lý agent không nhận (timeout, re-route). Pull: agent rảnh tự nhận cuộc kế — đơn giản nhưng khó đảm bảo công bằng/ưu tiên và agent có thể kén việc. ACD nghiêm túc dùng push kèm offer-accept có timeout: đề nghị → agent nhận trong vài giây → quá hạn coi như từ chối, cuộc về hàng.

Q8Agent rớt mạng ngay khi vừa được gán cuộc — xử lý thế nào?Senior›

Trả lời: Mỗi lần gán đặt một timer (vd 15s). Nếu cuộc không chuyển sang active trước hạn → tự động assigned → queued, đánh dấu agent offline/unresponsive (gỡ khỏi index available), và nâng priority cuộc để bù thời gian đã chờ. Sau đó re-dispatch tới agent khác. Nhờ FSM chỉ cho transition hợp lệ và timer, cuộc không bị kẹt vô hạn.

⚠️ Bẫy: nếu chỉ dựa vào "agent bấm hủy" mà không có timer, mất kết nối đột ngột sẽ làm cuộc kẹt mãi ở assigned.

Q9Vì sao nên mô hình hóa cuộc gọi bằng finite state machine?Middle›

Trả lời: FSM định nghĩa tập trạng thái (idle, ringing, queued, assigned, active, hold, wrap-up, ended) và bảng chuyển tiếp hợp lệ. Lợi ích: (1) chặn chuyển tiếp sai (vd ended→active); (2) lịch sử trạng thái + timestamp là nguồn tính mọi metric (thời gian chờ, AHT, abandon); (3) dễ audit và đồng bộ realtime tới dashboard/agent UI.

Q10Làm sao tránh "double-assign" — một cuộc tới hai agent?Senior›

Trả lời: Vì có hai sự kiện đồng thời (cuộc-đến và agent-rảnh) có thể cùng cố gán một cuộc, cần thao tác nguyên tử. Trong một process: serialize qua event loop / khóa logic. Khi scale nhiều instance: dùng atomic ở store dùng chung — ví dụ Lua script trong Redis "kiểm tra cuộc còn ở queued thì mới chuyển assigned", hoặc đưa qua một hàng đợi message để chỉ một consumer xử lý mỗi cuộc. Kèm idempotency key để retry không gán trùng.

Q11Thiết kế IVR cần lưu ý gì để trải nghiệm tốt?Junior›

Trả lời: Mô hình hóa IVR như cây node menu (prompt + options DTMF + timeout). Nguyên tắc: menu phẳng (tránh quá 2–3 cấp), luôn có lối thoát về người thật (phím 0), mọi timeout phải có hành động an toàn (đẩy về tổng đài viên chứ không cụt), và tự phục vụ chỉ dùng cho tác vụ rõ ràng/xác thực được.
