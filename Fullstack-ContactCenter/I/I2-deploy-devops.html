Deploy, Docker, CI/CD & Monitoring

Đưa service lên production an toàn: container hóa, pipeline CI/CD, chiến lược deploy không downtime và giám sát hệ thống.

🎯 Học xong chương này bạn sẽ

• Phân biệt container vs máy ảo, hiểu image/layer/Dockerfile và viết được multi-stage build gọn cho service Node.js.

• Dựng môi trường local với Docker Compose (app + database + Redis) và hiểu mạng/volume giữa các container.

• Mô tả một pipeline CI/CD đầy đủ: lint → test → build image → đẩy registry → deploy, và biết khi nào pipeline nên fail.

• So sánh các chiến lược deploy (recreate, rolling, blue-green, canary) và giải thích cách đạt zero-downtime.

• Nắm 3 trụ cột observability (metrics, logs, traces), thiết kế health check (liveness/readiness) và autoscaling.

• Hiểu vai trò reverse proxy (nginx), PM2 cluster, Kubernetes cơ bản và cách quản lý secret an toàn.

💡 Liên hệ thực tế — vì sao DevOps quan trọng với Contact Center

Một hệ thống tổng đài chạy 24/7: lúc nào cũng có cuộc gọi, phiên chat, agent đang trực. Mỗi lần deploy không khéo là rớt cuộc gọi đang diễn ra, mất tin nhắn chưa lưu, agent bị đăng xuất giữa ca. Chương này dạy cách ship code mà người dùng không hề biết: container hóa để chạy giống nhau ở mọi nơi, pipeline tự kiểm thử trước khi lên, chiến lược deploy không downtime, và giám sát để phát hiện sự cố trước khi khách hàng phàn nàn. Đây là phần kết hợp tư duy thiết kế của I1 với vận hành thực tế.

① Docker & Container

Vấn đề kinh điển: "chạy ngon trên máy tôi mà". Code chạy được trên laptop của bạn nhưng lên server lại lỗi vì khác phiên bản Node, thiếu thư viện hệ thống, khác biến môi trường. Container giải quyết bằng cách đóng gói code + runtime + thư viện + cấu hình thành một đơn vị bất biến, chạy giống hệt nhau ở mọi nơi.

Container vs Máy ảo (VM)

Cả hai đều cô lập ứng dụng, nhưng ở tầng khác nhau. VM ảo hóa phần cứng — mỗi VM có nguyên một hệ điều hành riêng. Container ảo hóa hệ điều hành — chia sẻ chung kernel của host, chỉ cô lập tiến trình.

💡 Vì sao Contact Center thích container

Hệ thống tổng đài gồm nhiều service nhỏ: call-service, chat-service, routing-engine, ticket-api... Mỗi cái cần scale độc lập theo tải. Container nhẹ, khởi động nhanh nên có thể thêm/bớt instance trong vài giây khi lượng cuộc gọi tăng đột biến giờ cao điểm — điều mà VM nặng nề khó làm kịp.

Image, Layer & Dockerfile

Cần phân biệt rõ 2 khái niệm cốt lõi:

📦 Image

Bản thiết kế bất biến (read-only), đóng gói filesystem + metadata. Giống "class" trong OOP.

▶️ Container

Một instance đang chạy của image, có thêm tầng ghi (writable layer). Giống "object".

Image được xây từ nhiều layer xếp chồng. Mỗi lệnh trong Dockerfile tạo ra một layer. Docker cache từng layer: nếu một layer không đổi, các build sau dùng lại cache thay vì xây lại. Đây là lý do thứ tự lệnh rất quan trọng — đặt phần ít thay đổi (cài dependency) lên trước, phần hay thay đổi (copy source code) xuống dưới.

Dockerfile (naïve — chưa tối ưu)Docker
FROM node:20
WORKDIR /app
COPY . .                  # copy CẢ source trước → mọi thay đổi code phá cache npm install
RUN npm install
EXPOSE 3000
CMD ["node", "src/index.js"]

Vấn đề: mỗi lần sửa 1 dòng code, COPY . . đổi → layer npm install phải chạy lại từ đầu (chậm). Sửa bằng cách tách package.json ra trước:

Dockerfile (tận dụng layer cache)Docker
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./       # chỉ copy manifest trước
RUN npm ci                  # layer này được cache nếu package.json không đổi
COPY . .                    # copy code sau → đổi code KHÔNG phá cache npm
EXPOSE 3000
CMD ["node", "src/index.js"]
📝 npm ci vs npm install

Trong môi trường build/CI nên dùng npm ci: nó cài chính xác theo package-lock.json, xóa node_modules cũ, nhanh và tái lập được (reproducible). npm install có thể cập nhật lock file ngoài ý muốn — không hợp cho build bất biến.

Multi-stage build — image production gọn & an toàn

Build app thường cần devDependencies (TypeScript, eslint, công cụ build) nhưng runtime production thì không. Multi-stage build dùng nhiều FROM: một stage để build, một stage runtime chỉ copy artifact đã build. Kết quả: image nhỏ hơn nhiều, ít lỗ hổng bảo mật hơn (ít gói thừa), không lộ source/công cụ build.

Dockerfile — multi-stage cho TS call-serviceDocker
# ---------- Stage 1: builder ----------
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                    # cài cả devDependencies để build
COPY . .
RUN npm run build            # tsc → xuất ra /app/dist

# ---------- Stage 2: runtime (gọn) ----------
FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev         # CHỈ dependencies production
COPY --from=builder /app/dist ./dist   # lấy artifact từ stage builder
USER node                    # không chạy bằng root → an toàn hơn
EXPOSE 3000
CMD ["node", "dist/index.js"]
⚠️ Đừng quên .dockerignore

Tạo .dockerignore để loại node_modules, .git, .env, log... khỏi build context. Nếu không, COPY . . sẽ kéo cả node_modules local (sai kiến trúc/OS) và có thể lộ secret trong .env vào image.

Registry — kho chứa image

Sau khi build, image cần được đẩy lên registry (Docker Hub, GitHub Container Registry, hoặc registry nội bộ) để server/cluster kéo về deploy. Image được gắn tag để định danh phiên bản.

build & pushbash
# build với 2 tag: số phiên bản cụ thể + git SHA (truy vết được)
docker build -t registry.example.com/call-service:1.4.0 \
             -t registry.example.com/call-service:$(git rev-parse --short HEAD) .

docker push registry.example.com/call-service:1.4.0
docker push registry.example.com/call-service:$(git rev-parse --short HEAD)
🐛 Đừng deploy bằng tag latest

Tag latest không bất biến — nó trỏ tới image khác nhau theo thời gian. Production phải dùng tag cố định (số phiên bản hoặc git SHA) để biết chính xác đang chạy code nào và rollback được. Dùng latest khiến không reproduce nổi sự cố.

② Docker Compose — dựng môi trường local

Một service thực tế hiếm khi đứng một mình. call-service cần một database (lưu cuộc gọi, ticket) và Redis (pub/sub realtime, cache trạng thái agent, hàng đợi). Chạy tay từng container rất phiền. Docker Compose mô tả nhiều service trong một file YAML và khởi động tất cả bằng một lệnh.

docker-compose.yml — app + db + redisYAML
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DB_URL=postgres://cc:secret@db:5432/contactcenter
      - REDIS_URL=redis://redis:6379
    depends_on:
      db:
        condition: service_healthy   # chờ db SẴN SÀNG, không chỉ "đã start"
      redis:
        condition: service_started

  db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_USER=cc
      - POSTGRES_PASSWORD=secret
      - POSTGRES_DB=contactcenter
    volumes:
      - db-data:/var/lib/postgresql/data   # dữ liệu tồn tại qua restart
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U cc"]
      interval: 5s
      retries: 5

  redis:
    image: redis:7-alpine

volumes:
  db-data:
📝 2 thứ Compose lo giúp bạn

Mạng nội bộ: Compose tạo một network chung; container gọi nhau qua tên service như hostname (db:5432, redis:6379) — không cần biết IP. Volume: dữ liệu DB nằm trong named volume db-data nên không mất khi container restart/rebuild.

⚠️ depends_on không đợi "sẵn sàng"

Mặc định depends_on chỉ chờ container start, không chờ DB chấp nhận kết nối. Postgres start xong vẫn cần vài giây để nhận query. Vì vậy phải kèm healthcheck + condition: service_healthy, và app vẫn nên có retry connect khi khởi động.

Lệnh hay dùng: docker compose up -d (chạy nền), docker compose logs -f app (xem log), docker compose down -v (dừng & xóa cả volume). Lưu ý: Compose tiện cho local/dev; production thường dùng orchestrator như Kubernetes.

③ CI/CD Pipeline

CI (Continuous Integration): mỗi lần push code, hệ thống tự động lint + test + build để phát hiện lỗi sớm. CD (Continuous Delivery/Deployment): tự động đóng gói image và đưa lên môi trường (staging/production). Mục tiêu: mỗi commit đều ở trạng thái deploy được, và việc lên production trở nên nhàm chán (theo nghĩa tốt — an toàn, lặp lại được).

push code→ lint→ test (unit + integration)→ build image→ push registry→ deploy

Mỗi bước là một cổng kiểm soát (gate): nếu lint fail hoặc test fail, pipeline dừng ngay, image không được build, code không lên production. Đây chính là giá trị cốt lõi — ngăn code lỗi tới tay người dùng.

.github/workflows/ci.yml (minh họa khái niệm)YAML
name: CI/CD
on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint        # gate 1: chuẩn code
      - run: npm test            # gate 2: hành vi đúng

  build-and-push:
    needs: test               # CHỈ chạy nếu test pass
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          docker build -t $REGISTRY/call-service:${{ github.sha }} .
          echo "$REG_TOKEN" | docker login $REGISTRY -u ci --password-stdin
          docker push $REGISTRY/call-service:${{ github.sha }}
        env:
          REG_TOKEN: ${{ secrets.REGISTRY_TOKEN }}   # secret, KHÔNG hard-code

  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - run: kubectl set image deploy/call-service app=$REGISTRY/call-service:${{ github.sha }}
🔍 Lint

Bắt lỗi cú pháp/style sớm, đồng nhất code base. Rẻ và nhanh nên đặt đầu pipeline.

🧪 Test

Unit (logic routing cuộc gọi) + integration (API ticket gọi DB thật/test container). Gate quan trọng nhất.

🚀 Deploy

Cập nhật image trên cluster. Có thể yêu cầu duyệt thủ công trước khi lên production.

💡 Nguyên tắc thiết kế pipeline tốt

Fail fast & rõ ràng: bước rẻ (lint) chạy trước bước đắt (test tích hợp, build). Bất biến: build một image rồi promote nguyên image đó qua staging → production (không build lại). Truy vết: gắn git SHA vào tag image để biết mỗi deploy tương ứng commit nào. Tự động hóa rollback: nếu health check sau deploy fail thì tự quay về phiên bản cũ.

④ Chiến lược deploy

Cùng một image mới, nhưng cách thay thế phiên bản cũ quyết định người dùng có bị gián đoạn không. Với Contact Center 24/7, đây là phần sống còn: chọn sai chiến lược là rớt hàng loạt cuộc gọi.

RecreateTắt hết bản cũ → bật bản mớiCóĐơn giản nhất nhưng có khoảng "chết". Chỉ hợp dev/job nền.
RollingThay từng phần instance, cũ & mới chạy song song một lúcKhôngZero-downtime mặc định của K8s. Nhưng 2 phiên bản chạy đồng thời → cần tương thích.

Rolling update — cơ chế zero-downtime

Rolling thay từng instance một, dựa vào 2 tham số: maxUnavailable (tối đa bao nhiêu instance được phép thiếu) và maxSurge (được tạo thêm bao nhiêu instance tạm thời). Kết hợp với readiness probe: instance mới chỉ nhận traffic khi đã "sẵn sàng", instance cũ chỉ bị tắt sau khi instance mới lên.

3× v1 (đang phục vụ)→ +1 v2 (chờ readiness)→ v2 ready → −1 v1→ lặp lại→ 3× v2
🐛 Bẫy lớn: hai phiên bản chạy đồng thời

Trong rolling và canary, v1 và v2 cùng chạy một khoảng. Nếu deploy có migration DB phá vỡ tương thích (vd đổi tên cột mà v1 vẫn đọc cột cũ), v1 sẽ lỗi giữa chừng. Quy tắc: migration phải tương thích ngược (backward-compatible) — thêm cột/bảng trước, đổi code đọc/ghi sau, xóa cột cũ ở deploy tiếp theo (expand–contract). Đây là tư duy thiết kế bắt buộc khi muốn zero-downtime.

Blue-Green vs Canary — chọn cái nào?

🔵🟢 Blue-Green

Hai môi trường hoàn chỉnh. Traffic chuyển toàn bộ một lúc. Ưu: rollback tức thì, kiểm thử green kỹ trước khi gạt. Nhược: tốn gấp đôi tài nguyên, "big bang" — lỗi thì 100% user dính ngay khi gạt.

🐤 Canary

Mở van traffic từ từ. Ưu: lỗi chỉ ảnh hưởng nhóm nhỏ, quan sát metrics (lỗi gọi, độ trễ) trước khi mở rộng. Nhược: cần hạ tầng định tuyến % + giám sát mạnh; thời gian rollout lâu hơn.

Với tổng đài: canary hợp khi đổi logic routing cuộc gọi hay tính phí (rủi ro cao, muốn thử trên ít cuộc gọi trước); blue-green hợp khi cần rollback cực nhanh và môi trường đủ tài nguyên.

⑤ Monitoring & Logging — 3 trụ cột Observability

Deploy xong không phải là hết. Bạn cần biết hệ thống đang khỏe hay ốm, và khi có sự cố thì vì sao. Observability (khả năng quan sát) dựng trên 3 trụ cột bổ sung cho nhau:

📊 Metrics

Số liệu theo thời gian: RPS, độ trễ p95/p99, CPU, số cuộc gọi đồng thời. Trả lời "cái gì đang xảy ra".

📜 Logs

Bản ghi sự kiện chi tiết (có traceId). Trả lời "vì sao nó xảy ra", phục vụ điều tra.

🔗 Traces

Hành trình một request qua nhiều service. Trả lời "ở đâu chậm/lỗi" trong chuỗi gọi.

Metrics — Prometheus & Grafana

Prometheus định kỳ "scrape" (kéo) metrics từ endpoint /metrics của từng service và lưu dạng time-series. Grafana vẽ dashboard và đặt cảnh báo. Service tự bóc tách (instrument) các chỉ số quan trọng:

metrics.js — đo nghiệp vụ tổng đàiNode.js
const client = require('prom-client');
client.collectDefaultMetrics();   // CPU, RAM, event loop lag...

// Counter: tổng số cuộc gọi đã nhận (chỉ tăng)
const callsTotal = new client.Counter({
  name: 'calls_total', help: 'Tổng cuộc gọi', labelNames: ['status'],
});
// Gauge: số cuộc gọi đang diễn ra (tăng/giảm)
const activeCalls = new client.Gauge({ name: 'active_calls', help: 'Cuộc gọi đang diễn ra' });
// Histogram: phân bố thời gian chờ trong hàng đợi
const queueWait = new client.Histogram({
  name: 'queue_wait_seconds', help: 'Thời gian chờ trước khi gặp agent',
  buckets: [1, 5, 15, 30, 60, 120],
});

app.get('/metrics', async (req, res) => {
  res.set('Content-Type', client.register.contentType);
  res.end(await client.register.metrics());
});
📝 3 loại metric cần phân biệt khi phỏng vấn

Counter chỉ tăng (tổng cuộc gọi, tổng lỗi). Gauge lên/xuống (cuộc gọi đang active, số agent online). Histogram đo phân bố để tính p95/p99 (thời gian chờ, độ trễ API) — trung bình che giấu đuôi xấu, nên realtime luôn nhìn percentile.

Logging tập trung & Tracing

Trong hệ phân tán, log nằm rải rác ở chục container. Log tập trung (gom về một nơi như ELK/Loki) cho phép tìm kiếm xuyên service. Quy tắc vàng: log có cấu trúc (JSON) và đính kèm traceId để nối các dòng log của cùng một request lại với nhau.

structured log + traceIdNode.js
// Tệ: log chuỗi tự do, không grep nổi xuyên service
console.log('call ' + callId + ' routed to agent ' + agentId);

// Tốt: JSON có cấu trúc, có traceId để nối chuỗi request
logger.info({
  event: 'call_routed',
  traceId: req.traceId,
  callId, agentId,
  queueWaitMs: 8200,
});

Tracing (OpenTelemetry) gắn mỗi request một traceId xuyên suốt: gateway → routing-engine → call-service → DB. Khi một cuộc gọi bị chậm 3 giây, trace cho thấy chính xác bước nào ngốn thời gian thay vì đoán mò.

Alerting — cảnh báo dựa trên triệu chứng

💡 Cảnh báo theo "triệu chứng" chứ không theo "nguyên nhân"

Đừng báo động "CPU 90%" (có thể vô hại). Hãy báo động khi người dùng thực sự đau: "tỷ lệ cuộc gọi thất bại > 2% trong 5 phút", "p99 thời gian kết nối > 3s", "không còn agent nào online". Cảnh báo tốt phải actionable (gắn với hành động cụ thể), tránh "alert fatigue" — báo nhiều quá đến mức ai cũng phớt lờ.

⑥ Health Check & Scaling

Liveness vs Readiness probe

Orchestrator (K8s) cần biết container có khỏe không, qua 2 loại probe khác mục đích:

💓 Liveness

"Tiến trình còn sống không?" Nếu fail → K8s restart container. Dùng để thoát deadlock/treo.

✅ Readiness

"Đã sẵn sàng nhận traffic chưa?" Nếu fail → tạm cắt traffic (không restart). Dùng khi đang warmup/mất kết nối DB.

health endpointsNode.js
// Liveness: chỉ cần process trả lời được là sống
app.get('/healthz', (req, res) => res.send('ok'));

// Readiness: kiểm tra phụ thuộc — DB, Redis kết nối được mới nhận traffic
app.get('/readyz', async (req, res) => {
  try {
    await db.ping();
    await redis.ping();
    res.send('ready');
  } catch (e) {
    res.status(503).send('not ready');  // tạm rút khỏi pool, không restart
  }
});
🐛 Bẫy cổ điển: nhầm readiness vào liveness

Nếu để liveness probe kiểm tra DB và DB sập 30 giây, K8s sẽ restart liên tục mọi container (dù bản thân app vẫn ổn) → biến sự cố nhỏ thành thảm họa lan rộng. Quy tắc: liveness chỉ kiểm tra bản thân tiến trình; phụ thuộc ngoài (DB, Redis) thuộc readiness.

Graceful shutdown — không rớt cuộc gọi khi deploy

Khi rolling update tắt một pod cũ, K8s gửi SIGTERM. App phải: (1) ngừng nhận request mới, (2) hoàn tất request/cuộc gọi đang xử lý, (3) đóng WebSocket/DB/queue, rồi mới exit. Nếu không, cuộc gọi đang diễn ra bị cắt đột ngột.

graceful shutdownNode.js
process.on('SIGTERM', async () => {
  ready = false;                 // /readyz trả 503 → K8s cắt traffic mới
  server.close();                  // ngừng nhận HTTP request mới
  await drainActiveCalls();      // chờ cuộc gọi đang diễn ra kết thúc (có timeout)
  await redis.quit();
  await db.end();
  process.exit(0);
});

Liên hệ chương B1 (xử lý tín hiệu process) — đây là ứng dụng thực tế của graceful shutdown trong vòng đời deploy.

Autoscaling — HPA

Horizontal Pod Autoscaler tự tăng/giảm số instance theo tải. Có thể scale theo CPU, hoặc tốt hơn là theo metric nghiệp vụ (số cuộc gọi đồng thời, độ dài hàng đợi). Giờ cao điểm → thêm pod; đêm vắng → bớt pod để tiết kiệm.

hpa.yamlYAML
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: { kind: Deployment, name: call-service }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } }
⚠️ Scale ngang chỉ hiệu quả khi service "stateless"

Thêm pod chỉ giúp được nếu state (phiên agent, trạng thái cuộc gọi) nằm ngoài pod — trong Redis/DB, không phải bộ nhớ pod. Đây là điểm nối với I1: kiến trúc realtime phải tách state ra (Redis pub/sub, sticky session hoặc shared adapter) thì autoscaling mới chạy đúng.

⑦ Reverse Proxy, PM2 & Kubernetes

Reverse Proxy (nginx)

Đặt nginx trước các instance Node để làm: TLS termination (kết thúc HTTPS), load balancing, nén, rate limiting, và nâng cấp WebSocket. Node tập trung vào nghiệp vụ, việc "lớp vỏ" giao cho proxy.

nginx.conf — proxy + WebSocket cho realtimenginx
upstream call_backend {
  server app1:3000;
  server app2:3000;       # load balance giữa các instance
}
server {
  listen 443 ssl;
  location /socket.io/ {
    proxy_pass http://call_backend;
    proxy_set_header Upgrade $http_upgrade;        # bắt buộc cho WebSocket
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;                       # kết nối realtime sống lâu
  }
  location / { proxy_pass http://call_backend; }
}
⚠️ WebSocket cần cấu hình đặc biệt

Quên 2 header Upgrade/Connection là WebSocket/Socket.IO không kết nối được — lỗi rất hay gặp trong hệ realtime. Ngoài ra timeout mặc định của proxy thường ngắn, phải nâng lên cho kết nối lâu dài (cuộc gọi/phiên chat).

PM2 — chạy nhiều instance khi chưa dùng K8s

Trên một máy chủ đơn lẻ, PM2 chạy Node ở chế độ cluster: fork nhiều process tận dụng đa nhân, tự restart khi crash, hỗ trợ reload không downtime. Đây là bậc thang trước Kubernetes.

ecosystem.config.jsPM2
module.exports = {
  apps: [{
    name: 'call-service',
    script: 'dist/index.js',
    instances: 'max',        // 1 process / 1 CPU core
    exec_mode: 'cluster',    // nhiều process cùng nghe 1 port
    max_memory_restart: '500M', // rò bộ nhớ → tự restart
  }],
};
// pm2 reload call-service  → reload từng instance, KHÔNG downtime

Kubernetes — cơ bản & quản lý secret

Khi nhiều service và nhiều máy, cần orchestrator. Kubernetes tự lên lịch container, tự healing (pod chết → tạo lại), rolling update, scaling. Vài khái niệm cốt lõi:

Khái niệmVai trò
PodĐơn vị nhỏ nhất, bọc 1 (hoặc vài) container chạy chung.
DeploymentQuản lý số bản sao của pod, lo rolling update & rollback.
ServiceTên/IP ổn định + load balance tới các pod (pod đến/đi liên tục).
ConfigMapCấu hình không nhạy cảm (URL, feature flag).
SecretDữ liệu nhạy cảm (mật khẩu DB, JWT secret, API key).
IngressĐịnh tuyến HTTP từ ngoài vào các Service (như reverse proxy của cluster).
🐛 Quản lý secret & env — đừng commit bí mật

Config tách khỏi code (12-factor): inject qua biến môi trường. Bí mật (mật khẩu DB, token) không bao giờ hard-code hay commit vào git — dùng Secret của K8s (hoặc Vault/cloud secret manager) và mount vào pod. Lưu ý K8s Secret mặc định chỉ base64 (không phải mã hóa) → cần bật encryption-at-rest và phân quyền RBAC chặt. Lộ .env chứa secret là một trong những sự cố bảo mật phổ biến nhất.

deployment.yaml — secret + probes + image cố địnhYAML
spec:
  containers:
    - name: app
      image: registry.example.com/call-service:1.4.0   # tag cố định, KHÔNG :latest
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: { name: cc-secrets, key: db-password }  # từ Secret
      livenessProbe:
        httpGet: { path: /healthz, port: 3000 }
        initialDelaySeconds: 10
      readinessProbe:
        httpGet: { path: /readyz, port: 3000 }

⚠️ Lỗi thường gặp & Best practices

🚫 Deploy bằng :latest

Không reproduce/rollback được. Luôn tag bằng version hoặc git SHA cố định.

🚫 Chạy container bằng root

Lỗ hổng escalation. Thêm USER node, dùng base image gọn (alpine/distroless).

🚫 Liveness kiểm tra DB

DB sập → restart bão cả cluster. DB thuộc readiness, không phải liveness.

🚫 Migration phá tương thích

Rolling/canary có 2 phiên bản chạy chung → dùng expand–contract, tương thích ngược.

🚫 Bỏ graceful shutdown

SIGTERM không xử lý → rớt cuộc gọi mỗi lần deploy. Drain rồi mới exit.

🚫 Commit secret vào git

Lộ mật khẩu/token. Inject qua env/Secret, có .dockerignore & .gitignore.

🚫 Cảnh báo theo CPU thuần

Alert fatigue. Báo động theo triệu chứng người dùng (lỗi gọi, p99).

🚫 Image phình to

Quên multi-stage & .dockerignore → image vài GB, nhiều CVE. Tách build/runtime.

🧪 Bài tập

🧪 Bài 1 — Tối ưu Dockerfile

Cho một Dockerfile dùng FROM node:20, COPY . . rồi npm install, chạy node src/index.js bằng root. Hãy chỉ ra 3 vấn đề và viết lại thành multi-stage gọn, an toàn.

Gợi ý

(1) Base image nặng → dùng node:20-alpine. (2) COPY . . trước npm install phá layer cache → tách COPY package*.json + npm ci trước. (3) Chạy root → thêm USER node. Thêm: multi-stage (builder build TS, runtime npm ci --omit=dev + copy dist), thêm .dockerignore, ENV NODE_ENV=production.

🧪 Bài 2 — Chọn chiến lược deploy

Bạn sắp deploy thay đổi lớn cho routing-engine (logic phân phối cuộc gọi cho agent). Rủi ro cao, traffic 24/7. Chọn chiến lược nào? Cần chuẩn bị gì để không rớt cuộc gọi?

Gợi ý

Chọn canary: cho bản mới nhận 5% cuộc gọi, theo dõi tỷ lệ định tuyến lỗi & thời gian chờ hàng đợi, rồi mới mở rộng. Chuẩn bị: readiness probe đúng, graceful shutdown (drain cuộc gọi), migration tương thích ngược, dashboard metrics nghiệp vụ + alert theo triệu chứng, cơ chế rollback tự động nếu lỗi vượt ngưỡng.

🧪 Bài 3 — Thiết kế health probe

chat-service phụ thuộc Postgres + Redis. Hãy thiết kế /healthz và /readyz sao cho: Redis sập 20s thì service tạm ngừng nhận tin nhắn nhưng không bị restart hàng loạt.

Gợi ý

/healthz (liveness) chỉ trả 200 nếu process sống — KHÔNG ping Redis. /readyz (readiness) ping Redis + Postgres, trả 503 nếu hỏng. Redis sập → readiness fail → K8s cắt traffic (pod bị rút khỏi Service) nhưng liveness vẫn ok nên không restart. Redis hồi → readiness pass → pod nhận traffic lại.

Ngân hàng câu hỏi phỏng vấn

Deploy, Docker, CI/CD & vận hành — phần đánh giá tư duy production.

Q1Container là gì? Khác VM thế nào? Vì sao nên dùng container?Junior›

Trả lời: Container đóng gói code + runtime + thư viện + cấu hình thành đơn vị bất biến, cô lập ở tầng tiến trình và chia sẻ kernel của host. VM thì ảo hóa phần cứng, mỗi VM có OS riêng nên nặng GB và khởi động chậm. Container nhẹ (MB), bật trong giây, mật độ cao trên một host. Ưu điểm: chạy giống nhau ở mọi môi trường ("hết cảnh works on my machine"), scale nhanh, hợp microservice & CI/CD. Với tổng đài, container cho phép thêm/bớt instance trong vài giây khi tải cuộc gọi tăng.

Q2Image vs Container? Layer cache hoạt động ra sao?Junior›

Trả lời: Image là bản thiết kế bất biến (read-only), container là instance đang chạy của image (có thêm writable layer) — giống class vs object. Mỗi lệnh Dockerfile tạo một layer; Docker cache từng layer và dùng lại nếu layer đó không đổi. Nên đặt phần ít thay đổi (copy package.json + npm ci) trước, phần hay đổi (copy source) sau, để sửa code không phá cache install — build nhanh hơn nhiều.

Q3Multi-stage build là gì? Vì sao quan trọng?Middle›

Trả lời: Dùng nhiều FROM trong một Dockerfile: stage builder cài cả devDependencies và build (vd tsc → dist), stage runtime chỉ copy artifact đã build và cài dependencies production (npm ci --omit=dev). Kết quả: image production nhỏ hơn nhiều, ít gói thừa nên ít lỗ hổng bảo mật, không lộ source/công cụ build. Kèm .dockerignore và USER node để gọn và an toàn.

⚠️ Bẫy: quên .dockerignore khiến COPY . . kéo cả node_modules local và có thể đưa .env chứa secret vào image.

Q4Mô tả một pipeline CI/CD đầy đủ. Mỗi bước để làm gì?Middle›

Trả lời: push → lint (chuẩn code, rẻ nên chạy đầu) → test (unit + integration, gate quan trọng nhất) → build image (tag bằng git SHA) → push registry → deploy. Mỗi bước là một gate: fail thì dừng, code không lên production. Nguyên tắc: fail fast, build một image rồi promote nguyên image qua staging→prod (không build lại), gắn SHA để truy vết, và rollback tự động nếu health check sau deploy fail.

Q5So sánh recreate, rolling, blue-green, canary.Middle›

Trả lời: Recreate: tắt cũ rồi bật mới — có downtime, chỉ hợp dev. Rolling: thay từng instance, cũ & mới chạy song song — zero-downtime, mặc định của K8s. Blue-green: dựng full môi trường mới rồi gạt toàn bộ traffic — rollback tức thì nhưng tốn gấp đôi tài nguyên. Canary: bản mới nhận % nhỏ traffic rồi tăng dần — giới hạn phạm vi lỗi, cần giám sát mạnh.

Q6Làm sao deploy zero-downtime cho hệ thống 24/7?Senior›

Trả lời: Kết hợp nhiều thứ: (1) rolling/blue-green/canary thay vì recreate; (2) readiness probe để instance mới chỉ nhận traffic khi sẵn sàng, instance cũ chỉ tắt sau đó; (3) graceful shutdown — bắt SIGTERM, ngừng nhận request mới, drain cuộc gọi đang xử lý rồi mới exit; (4) migration tương thích ngược (expand–contract) vì có lúc 2 phiên bản chạy chung; (5) state để ngoài (Redis/DB) để pod thay được mà không mất phiên. Reverse proxy/load balancer phối hợp rút pod cũ ra khỏi pool.

⚠️ Bẫy: chỉ trả lời "dùng rolling" là chưa đủ — phỏng vấn muốn nghe readiness + graceful shutdown + migration tương thích ngược.

Q7Blue-green vs canary — khi nào chọn cái nào?Senior›

Trả lời: Blue-green hợp khi cần rollback cực nhanh và đủ tài nguyên để chạy gấp đôi — gạt traffic toàn bộ, lỗi thì gạt ngược về blue tức thì; nhược là "big bang", 100% user dính ngay khi gạt. Canary hợp khi thay đổi rủi ro cao muốn thử trên nhóm nhỏ trước (vd logic routing/tính phí cuộc gọi) — phát hiện lỗi với phạm vi nhỏ, nhưng cần hạ tầng định tuyến % và giám sát mạnh, rollout lâu hơn.

Q83 trụ cột observability là gì? Phân biệt Counter/Gauge/Histogram.Middle›

Trả lời: Metrics (số liệu time-series — cái gì), Logs (sự kiện chi tiết — vì sao), Traces (hành trình request qua các service — ở đâu). Về metric: Counter chỉ tăng (tổng cuộc gọi, tổng lỗi); Gauge lên/xuống (cuộc gọi đang active, agent online); Histogram đo phân bố để tính p95/p99 (thời gian chờ, độ trễ). Realtime luôn nhìn percentile chứ không nhìn trung bình vì trung bình che giấu phần đuôi xấu.

Q9Liveness vs readiness probe khác nhau ra sao?Middle›

Trả lời: Liveness trả lời "process còn sống không" — fail thì K8s restart container (thoát treo/deadlock). Readiness trả lời "đã sẵn sàng nhận traffic chưa" — fail thì K8s cắt traffic tạm thời (không restart), dùng khi đang warmup hoặc mất kết nối DB/Redis. Quan trọng: liveness chỉ kiểm tra bản thân process; phụ thuộc ngoài (DB, Redis) thuộc readiness.

⚠️ Bẫy: để liveness ping DB. DB sập sẽ làm K8s restart bão toàn bộ pod dù app vẫn khỏe.

Q10Autoscaling (HPA) hoạt động thế nào? Điều kiện để scale ngang hiệu quả?Senior›

Trả lời: HPA tự tăng/giảm số replica theo metric (CPU, hoặc tốt hơn là metric nghiệp vụ như số cuộc gọi đồng thời/độ dài hàng đợi) trong khoảng min–max. Điều kiện cốt lõi: service phải stateless — state (phiên agent, trạng thái cuộc gọi) phải nằm ngoài pod, trong Redis/DB. Nếu state nằm trong bộ nhớ pod thì thêm pod không giúp được mà còn gây mất phiên khi scale. Cần kèm graceful shutdown để scale-in không rớt cuộc gọi.

Q11Quản lý secret và config thế nào cho an toàn?Middle›

Trả lời: Theo 12-factor: tách config khỏi code, inject qua biến môi trường. Config không nhạy cảm dùng ConfigMap; bí mật (mật khẩu DB, JWT secret, API key) dùng Secret (hoặc Vault/cloud secret manager) và mount vào pod. Tuyệt đối không hard-code/commit secret vào git; thêm .gitignore/.dockerignore cho .env. Lưu ý K8s Secret mặc định chỉ base64 (không phải mã hóa) → bật encryption-at-rest và siết RBAC. Nên xoay vòng (rotate) secret định kỳ.

Q12Vì sao nên container hóa thay vì deploy trực tiếp lên server?Junior›

Trả lời: Container đảm bảo môi trường nhất quán giữa dev/staging/production (không còn lệch phiên bản Node/thư viện), cô lập giữa các service trên cùng host, tái lập & rollback dễ (image bất biến có tag), tích hợp mượt với CI/CD và orchestrator (K8s tự healing, scaling, rolling update). Deploy thẳng lên server dễ gặp "drift" cấu hình, khó tái lập sự cố, scale và rollback chật vật.
