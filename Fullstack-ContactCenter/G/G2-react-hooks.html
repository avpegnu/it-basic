React Hooks

Hooks là cách quản lý state và side-effect trong function component. Nắm vững useEffect và các bẫy closure là chìa khóa viết React đúng.

🎯 Học xong chương này bạn sẽ

• Hiểu useState hoạt động ra sao: functional update, lazy init, vì sao state là bất biến (immutable).

• Đọc được useEffect như một bản đồ lifecycle — mảng deps, cleanup, mount/update/unmount — và tránh được infinite loop, stale closure.

• Dùng useContext để diệt prop drilling và useReducer để quản lý state phức tạp có nhiều nhánh.

• Phân biệt rõ useRef vs state, biết khi nào useMemo/useCallback thực sự đáng dùng (và khi nào chỉ là tối ưu sớm).

• Tự viết custom hook để tái sử dụng logic (useSocket, useFetch) và giải thích được Rules of Hooks trong phỏng vấn.

💡 Liên hệ hệ thống Contact Center

Màn hình của một agent (nhân viên trực) là cỗ máy hooks thu nhỏ: useState giữ trạng thái cuộc gọi (đang gọi / giữ máy / kết thúc), useEffect mở/đóng kết nối WebSocket tới hàng đợi (queue), useContext phát danh tính agent & quyền cho toàn cây, useReducer điều phối cỗ máy trạng thái (state machine) của một ticket. Hiểu sai cleanup là rò rỉ socket; hiểu sai deps là cuộc gọi hiển thị sai số liệu. Chương này dạy bạn viết đúng từ gốc.

① useState — đơn vị state nhỏ nhất

useState khai báo một biến state tồn tại qua các lần render. Nó trả về một mảng 2 phần tử: giá trị hiện tại và hàm cập nhật. Mỗi khi gọi hàm cập nhật, React lên lịch render lại component với giá trị mới.

CallButton.tsxReact + TS
function CallButton() {
  // [giá trị, hàm set] — destructuring mảng
  const [status, setStatus] = useState<'idle' | 'ringing' | 'talking'>('idle');

  return (
    <button onClick={() => setStatus('ringing')}>
      Trạng thái: {status}
    </button>
  );
}

Hai đặc tính quan trọng phải nhớ để không "đánh nhau" với React:

  • State là bất biến (immutable) theo quy ước. Không sửa trực tiếp arr.push(x) hay obj.x = 1. Phải tạo object/array mới (setArr([...arr, x])) để React biết "đã đổi" và render lại.
  • setState là bất đồng bộ và được gộp (batched). Trong cùng một event handler, gọi setX nhiều lần không cập nhật x ngay lập tức — React gộp lại rồi render một lần.

Functional update — khi state mới phụ thuộc state cũ

Đây là bẫy kinh điển. Vì state trong một render là một "ảnh chụp" (snapshot) cố định, nếu bạn tăng counter 3 lần liên tiếp bằng giá trị cũ, kết quả chỉ tăng 1.

missed-calls.tsxReact
// ❌ SAI — cả 3 lần đều đọc cùng một `missed` cũ → chỉ +1
setMissed(missed + 1);
setMissed(missed + 1);
setMissed(missed + 1);

// ✅ ĐÚNG — functional update, mỗi lần nhận giá trị mới nhất từ React → +3
setMissed(prev => prev + 1);
setMissed(prev => prev + 1);
setMissed(prev => prev + 1);
💡 Quy tắc vàng

Bất cứ khi nào state mới tính ra từ state cũ (đếm cuộc gọi nhỡ, thêm message vào mảng chat, toggle), hãy dùng dạng hàm setX(prev => ...). Nó còn giúp bạn không cần đưa state vào deps của useEffect — tránh được nguyên nhân số một của infinite loop.

Lazy initialization — khởi tạo tốn kém chỉ chạy 1 lần

Nếu giá trị khởi tạo phải tính toán nặng (đọc từ localStorage, parse JSON lớn), đừng truyền kết quả vào useState — vì nó sẽ tính ở mọi lần render dù chỉ dùng ở lần đầu. Hãy truyền một hàm.

agent-prefs.tsxReact
// ❌ readFromStorage() chạy MỌI render (lãng phí)
const [prefs, setPrefs] = useState(readFromStorage());

// ✅ Lazy init — hàm chỉ chạy ở lần render đầu tiên
const [prefs, setPrefs] = useState(() => readFromStorage());

② useEffect & vòng đời (lifecycle)

useEffect chạy side-effect — những việc nằm ngoài luồng tính toán UI thuần: gọi API, mở WebSocket, đăng ký event listener, thao tác trực tiếp DOM, đặt timer. Đây là hook bị hiểu sai nhiều nhất, nên hãy đọc thật chậm.

Giải phẫu một effect

useEffect-anatomy.tsxReact
useEffect(() => {
  // (A) THÂN effect — chạy SAU khi render được paint lên màn hình
  const id = setInterval(tick, 1000);

  return () => {
    // (B) CLEANUP — chạy trước lần effect kế tiếp & khi unmount
    clearInterval(id);
  };
}, [dep1, dep2]); // (C) MẢNG DEPS — quyết định KHI NÀO chạy lại

Mảng deps (C) là bộ não của effect. React so sánh nông (shallow / Object.is) từng phần tử với lần render trước; nếu có gì đổi, nó chạy cleanup cũ rồi chạy lại thân effect.

Mảng depsEffect chạy khi nàoÁnh xạ lifecycle (class cũ)
không truyền (bỏ trống)Sau mọi lần rendercomponentDidMount + componentDidUpdate
[] (mảng rỗng)Đúng một lần sau mount; cleanup chạy khi unmountcomponentDidMount + componentWillUnmount
[a, b]Sau mount, và mỗi khi a hoặc b đổicomponentDidUpdate (có điều kiện)
🧠 Tư duy đúng về effect

Đừng nghĩ "effect = chạy lúc mount/update/unmount". Hãy nghĩ: "effect đồng bộ hóa component với một hệ thống bên ngoài". Mỗi lần deps đổi nghĩa là "thông tin đồng bộ đã cũ" → React dọn (cleanup) bản cũ rồi tạo bản mới. Tư duy này khiến cleanup trở thành điều tự nhiên chứ không phải thứ "thêm cho có".

Cleanup — dây an toàn chống rò rỉ

Trong Contact Center, mỗi màn hình agent thường mở một WebSocket tới server realtime. Nếu không cleanup, mỗi lần component remount sẽ chồng thêm một kết nối/listener → memory leak, message bị xử lý nhiều lần.

useAgentSocket.tsxReact
useEffect(() => {
  const socket = connect(`/queue/${queueId}`);
  socket.on('call:incoming', onIncoming);

  return () => {
    // gỡ listener + đóng socket khi đổi queue hoặc rời màn hình
    socket.off('call:incoming', onIncoming);
    socket.close();
  };
}, [queueId]); // đổi queueId → đóng socket cũ, mở socket mới

Fetch dữ liệu trong effect & vấn đề race condition

Gọi API trong effect rất phổ biến, nhưng có một bẫy: nếu user đổi callId nhanh, hai request có thể về không đúng thứ tự — response cũ ghi đè response mới. Dùng cờ ignore hoặc AbortController để hủy.

useCallDetail.tsxReact
useEffect(() => {
  let ignore = false;            // cờ chống race
  fetchCall(callId).then((data) => {
    if (!ignore) setDetail(data); // chỉ set nếu vẫn còn "hiệu lực"
  });
  return () => { ignore = true; }; // cleanup vô hiệu response cũ
}, [callId]);
💡 Thực chiến

Đến G4 bạn sẽ thấy: thay vì tự fetch trong effect, người ta dùng React Query / SWR để có cache, retry, dedupe, chống race sẵn. Nhưng phỏng vấn vẫn hỏi bạn fetch tay trong effect để kiểm tra hiểu biết. Xem thêm G4 · Data fetching.

Hai bẫy chí mạng: infinite loop & stale closure

Infinite loop (vòng lặp vô tận). Xảy ra khi effect cập nhật một state mà state đó (hoặc một object/array tạo mới mỗi render) lại nằm trong deps. Render → effect → setState → render → effect…

infinite-loop.tsxReact
// ❌ filter là object MỚI mỗi render → deps luôn "đổi" → loop vô tận
const filter = { status: 'active' };
useEffect(() => {
  loadCalls(filter).then(setCalls);
}, [filter]); // 💥

// ✅ Cách 1: đưa giá trị nguyên thủy (primitive) vào deps
useEffect(() => {
  loadCalls({ status }).then(setCalls);
}, [status]);

// ✅ Cách 2: nếu cần object, bọc bằng useMemo (xem mục ⑤)

Stale closure (đóng gói giá trị cũ). Effect "nhớ" giá trị của state/props tại thời điểm nó được tạo. Nếu deps thiếu, callback bên trong (vd trong setInterval) sẽ mãi đọc giá trị cũ.

stale-closure.tsxReact
// ❌ count luôn = 0 bên trong interval (đóng gói lần đầu, deps rỗng)
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1); // `count` mãi là 0
  }, 1000);
  return () => clearInterval(id);
}, []);

// ✅ Dùng functional update — không cần count trong deps, luôn đọc mới nhất
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);
}, []);
🐛 Đừng "nói dối" mảng deps

Cám dỗ lớn nhất khi gặp warning exhaustive-deps là xóa biến khỏi deps cho hết cảnh báo. Đó là nói dối React — bug stale closure sẽ quay lại cắn bạn lúc khó debug nhất. Giải pháp đúng: (1) functional update, (2) useCallback/useMemo để giữ tham chiếu ổn định, (3) chuyển logic vào reducer, hoặc (4) dùng ref cho giá trị "không nên kích hoạt effect".

useEffect vs useLayoutEffect

Quy tắc: mặc định dùng useEffect. Chỉ đổi sang useLayoutEffect khi bạn cần đọc/sửa layout DOM ngay và thấy hiện tượng nhấp nháy.

③ useContext — diệt prop drilling

Prop drilling là khi bạn phải chuyền một prop qua nhiều tầng component trung gian chỉ để tới được nơi cần dùng. Context cho phép một component "phát sóng" giá trị xuống toàn bộ cây con mà không cần chuyền tay từng tầng.

App→ Layout (không dùng)→ Sidebar (không dùng)→ AgentBadge (cần currentAgent)

Với Context, App bọc <AgentContext.Provider> còn AgentBadge chỉ cần useContext(AgentContext) — không động gì tới Layout/Sidebar.

AgentContext.tsxReact + TS
// 1) Tạo context
const AgentContext = createContext<Agent | null>(null);

// 2) Provider bọc cây — phát giá trị xuống
<AgentContext.Provider value={currentAgent}>
  <Dashboard />
</AgentContext.Provider>

// 3) Tiêu thụ ở bất kỳ độ sâu nào — kèm hook bảo vệ
function useAgent() {
  const ctx = useContext(AgentContext);
  if (!ctx) throw new Error('useAgent phải nằm trong AgentProvider');
  return ctx;
}
⚠️ Context không phải state manager toàn năng

Mọi component tiêu thụ context sẽ render lại khi value đổi tham chiếu. Nếu nhét cả một object lớn thay đổi liên tục (vd toàn bộ danh sách cuộc gọi cập nhật mỗi giây) vào một context, bạn gây render lan rộng. Giải pháp: tách context (một cho state ít đổi như danh tính/theme, một cho dữ liệu hay đổi), useMemo cho value, hoặc dùng store chuyên dụng (Zustand/Redux) ở G4.

④ useReducer — state phức tạp có quy luật

Khi một mảnh state có nhiều trường liên quan và nhiều cách chuyển trạng thái, dùng nhiều useState rời rạc dễ sinh trạng thái mâu thuẫn (vd vừa isLoading vừa có error). useReducer gom toàn bộ logic chuyển trạng thái vào một hàm reducer thuần khiết — rất hợp với state machine của một cuộc gọi/ticket.

callReducer.tsReact + TS
type State = { phase: 'idle' | 'ringing' | 'talking' | 'wrapup'; duration: number };
type Action =
  | { type: 'INCOMING' } | { type: 'ANSWER' }
  | { type: 'TICK' }     | { type: 'HANGUP' };

function callReducer(state: State, action: Action): State {
  switch (action.type) {
    case 'INCOMING': return { ...state, phase: 'ringing' };
    case 'ANSWER':   return { ...state, phase: 'talking' };
    case 'TICK':     return { ...state, duration: state.duration + 1 };
    case 'HANGUP':   return { phase: 'wrapup', duration: 0 };
    default:        return state;
  }
}

// Trong component:
const [state, dispatch] = useReducer(callReducer, { phase: 'idle', duration: 0 });
// Phát hành động thay vì set từng trường:
<button onClick={() => dispatch({ type: 'ANSWER' })}>Trả lời</button>
DùngKhi nào
useStateState đơn giản, độc lập: 1 boolean, 1 chuỗi, 1 số. Logic cập nhật ngắn gọn.
useReducerNhiều trường liên quan; chuyển trạng thái theo "hành động"; muốn logic tách khỏi UI, dễ test; state machine.
💡 Reducer phải thuần khiết (pure)

Reducer chỉ được tính state mới từ (state, action) — không gọi API, không random, không sửa state cũ tại chỗ. Mọi side-effect đặt ở effect/event handler. Ưu điểm lớn: dispatch có tham chiếu ổn định (không đổi qua các render), nên đưa nó vào deps của effect là an toàn — giúp tránh stale closure.

⑤ useRef, useMemo, useCallback

useRef — chiếc hộp tồn tại qua render mà không gây render

useRef trả về một object { current } cùng một tham chiếu suốt vòng đời component. Sửa ref.current không kích hoạt render. Hai công dụng:

📦 Giá trị mutable

Lưu thứ "ngoài UI": id của timer, instance WebSocket, giá trị trước đó — đổi mà không cần vẽ lại.

🎯 Tham chiếu DOM

Gắn ref vào element để focus input, cuộn xuống message mới nhất, đo kích thước.

ChatScroll.tsxReact
const bottomRef = useRef<HTMLDivElement>(null);

// Mỗi khi có message mới → cuộn xuống đáy khung chat
useEffect(() => {
  bottomRef.current?.scrollIntoView({ behavior: 'smooth' });
}, [messages.length]);

return (
  <div>
    {messages.map(...)}
    <div ref={bottomRef} /> // điểm neo cuối khung
  </div>
);
⚠️ useRef vs useState

Hỏi: "Giá trị này khi đổi có cần vẽ lại UI không?" → Có thì dùng useState; Không (chỉ là dữ liệu nội bộ) thì dùng useRef. Đừng đọc ref.current trong lúc render để quyết định UI — vì ref đổi không kích hoạt render, UI sẽ "trễ một nhịp".

useMemo — nhớ một giá trị tính toán

useMemo(fn, deps) ghi nhớ kết quả của fn và chỉ tính lại khi deps đổi. Hai mục đích: (1) tránh tính toán nặng mỗi render; (2) giữ tham chiếu ổn định cho object/array để tránh vỡ memo/effect ở dưới.

QueueStats.tsxReact
// Tính toán nặng trên 5000 cuộc gọi — chỉ chạy lại khi `calls` đổi
const stats = useMemo(() => {
  return {
    avgWait: computeAvgWait(calls),
    abandoned: calls.filter(c => c.abandoned).length,
  };
}, [calls]);

useCallback — nhớ một hàm

useCallback(fn, deps) chỉ là useMemo(() => fn, deps). Nó giữ cùng một tham chiếu hàm qua các render (chừng nào deps không đổi). Đáng dùng khi hàm đó được truyền xuống một component con đã bọc React.memo, hoặc là dep của một effect.

AgentList.tsxReact
// Không có useCallback: handleSelect là hàm MỚI mỗi render
// → AgentRow (dù bọc React.memo) vẫn render lại vô ích.
const handleSelect = useCallback((id: string) => {
  dispatch({ type: 'SELECT_AGENT', id });
}, []); // dispatch ổn định → deps rỗng an toàn

{agents.map(a => (
  <AgentRow key={a.id} agent={a} onSelect={handleSelect} />
))}
🐛 Đừng tối ưu sớm (premature optimization)

Bản thân useMemo/useCallback cũng có chi phí (lưu deps, so sánh mỗi render). Bọc mọi thứ một cách máy móc làm code khó đọc mà không nhanh hơn. Chỉ dùng khi: (a) tính toán thật sự nặng, (b) cần tham chiếu ổn định cho React.memo / deps của effect, hoặc (c) bạn đã đo được vấn đề. Đo trước, tối ưu sau.

HookNhớ cái gìTrả về
useMemo(fn, d)Kết quả fn()Giá trị
useCallback(fn, d)Chính hàm fnHàm
useRef(v)Một hộp {current}Ref ổn định (không gây render)

⑥ Custom hooks — tái sử dụng logic

Custom hook chỉ là một hàm tên bắt đầu bằng use và gọi các hook khác bên trong. Nó không chia sẻ state giữa các component — mỗi lần gọi là một bản state độc lập; cái được chia sẻ là logic. Đây là cách "đóng gói" một mảng hành vi (mở socket, fetch, debounce) để dùng lại sạch sẽ.

useFetch.tsReact + TS
function useFetch<T>(url: string) {
  const [data, setData]   = useState<T | null>(null);
  const [error, setError] = useState<Error | null>(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    let ignore = false;
    setLoading(true);
    fetch(url).then(r => r.json())
      .then(d => { if (!ignore) setData(d); })
      .catch(e => { if (!ignore) setError(e); })
      .finally(() => { if (!ignore) setLoading(false); });
    return () => { ignore = true; };
  }, [url]);

  return { data, error, loading }; // "API" của hook
}
useSocket.tsReact + TS
function useSocket(channel: string, onMessage: (m: Msg) => void) {
  // Giữ callback mới nhất trong ref → tránh mở lại socket khi handler đổi
  const handlerRef = useRef(onMessage);
  handlerRef.current = onMessage;

  useEffect(() => {
    const s = connect(channel);
    s.on('message', (m) => handlerRef.current(m));
    return () => s.close();
  }, [channel]); // chỉ mở lại khi đổi kênh, KHÔNG vì onMessage đổi
}
🧠 Mẹo "latest ref" trong useSocket

Đây là kỹ thuật nâng cao hay được hỏi: lưu callback hay đổi vào một ref và cập nhật mỗi render, rồi trong effect gọi handlerRef.current. Nhờ vậy effect chỉ phụ thuộc channel (ít đổi) — socket không bị mở/đóng liên tục, mà bên trong vẫn luôn gọi handler mới nhất (không stale).

⑦ Rules of Hooks (Quy tắc Hooks)

Hai quy tắc bắt buộc, có plugin ESLint react-hooks kiểm tra giúp:

① Chỉ gọi ở top-level

Không gọi hook trong if, vòng lặp, hàm lồng, hay sau một return sớm. Luôn ở cấp cao nhất của component/hook.

② Chỉ gọi từ hàm React

Gọi hook trong function component hoặc trong custom hook khác — không gọi từ hàm thường, class, hay event handler.

Vì sao lại có quy tắc kỳ lạ này? React không nhận diện hook bằng tên. Nó dựa vào thứ tự gọi: lần render đầu, React tạo một danh sách "ô nhớ" theo đúng thứ tự bạn gọi hook (hook 1, 2, 3…). Các lần render sau, nó khớp giá trị theo cùng thứ tự đó. Nếu bạn đặt hook trong if và điều kiện đổi, thứ tự lệch → React gán state của hook A cho hook B → bug khó hiểu.

rules.tsxReact
// ❌ SAI — hook nằm trong if, thứ tự thay đổi giữa các render
if (isOnCall) {
  const [duration, setDuration] = useState(0); // 💥
}

// ✅ ĐÚNG — luôn gọi hook; đặt điều kiện BÊN TRONG
const [duration, setDuration] = useState(0);
useEffect(() => {
  if (!isOnCall) return;            // điều kiện ở trong thân
  const id = setInterval(() => setDuration(d => d + 1), 1000);
  return () => clearInterval(id);
}, [isOnCall]);

⚠️ Lỗi thường gặp & Best practices

🚫 Sửa state tại chỗ

arr.push() / obj.x=1 rồi setState — React không thấy đổi tham chiếu, không render. Luôn tạo bản sao mới.

🚫 Nói dối deps

Xóa biến khỏi deps để hết warning → stale closure. Sửa nguyên nhân, đừng giấu triệu chứng.

🚫 Quên cleanup

Không đóng socket/clearInterval → rò rỉ bộ nhớ, message xử lý trùng. Mọi subscribe phải có unsubscribe.

🚫 Object/array trong deps

Tạo mới mỗi render → effect chạy vô tận. Đưa primitive vào deps hoặc bọc useMemo.

🚫 Lạm dụng useMemo/useCallback

Bọc tất cả không làm nhanh hơn, chỉ rối. Đo rồi tối ưu chỗ cần.

🚫 Đặt async trực tiếp lên useEffect

useEffect(async ()=>...) sai vì trả về Promise, không phải cleanup. Khai báo hàm async bên trong rồi gọi.

✅ Functional update

Khi state mới phụ thuộc cũ, dùng setX(prev=>...) — đúng và bớt deps.

✅ Tách custom hook

Logic lặp lại (fetch, socket, form) → gom vào useXxx để test & tái dùng dễ.

🧪 Bài tập

🧪 Bài 1 — Sửa bộ đếm thời lượng cuộc gọi bị "đứng"

Một đồng nghiệp viết bộ đếm thời lượng cuộc gọi nhưng nó luôn nhảy 0 → 1 rồi đứng yên:

buggy-timer.tsx
useEffect(() => {
  setInterval(() => setSec(sec + 1), 1000);
}, []);

Chỉ ra 2 lỗi và viết lại cho đúng.

Gợi ý

Lỗi 1 — stale closure: sec bị đóng gói = 0 mãi mãi → dùng functional update setSec(s => s + 1). Lỗi 2 — không cleanup: mỗi lần mount tạo interval không bao giờ bị xóa → trả về () => clearInterval(id). Bản đúng: const id = setInterval(() => setSec(s => s+1), 1000); return () => clearInterval(id);

🧪 Bài 2 — Viết custom hook useDebouncedValue

Ô tìm kiếm agent gọi API mỗi phím gõ gây quá tải. Viết hook useDebouncedValue(value, delay) trả về giá trị chỉ cập nhật sau khi user ngừng gõ delay ms.

Gợi ý

Bên trong dùng một useState giữ giá trị "đã debounce", và một useEffect([value, delay]) đặt setTimeout cập nhật nó; cleanup clearTimeout để mỗi lần value đổi sẽ hủy timer cũ. Khi user ngừng gõ delay ms, timer mới chạy trọn vẹn và set giá trị. Component cha chỉ fetch theo giá trị đã debounce.

🧪 Bài 3 — Chọn đúng hook

Với mỗi nhu cầu, chọn useState, useRef hay useReducer và giải thích: (a) lưu instance WebSocket; (b) trạng thái ticket có 5 pha chuyển qua hành động; (c) ô input "đã nhập text chưa" để bật/tắt nút Gửi.

Gợi ý

(a) useRef — instance socket là dữ liệu mutable không cần render lại khi gán. (b) useReducer — nhiều pha + chuyển theo action, hợp state machine, dispatch ổn định. (c) useState — boolean đơn giản điều khiển UI, đổi là phải render lại nút.

Ngân hàng câu hỏi phỏng vấn

React Hooks — chủ đề được đào sâu để phân biệt người "dùng được" với người "hiểu rõ".

Q1Hook là gì? Vì sao React giới thiệu hooks?Junior›

Trả lời: Hook là các hàm đặc biệt (useState, useEffect...) cho phép function component dùng state và side-effect — những thứ trước đây chỉ class component mới làm được. Hooks ra đời để tái sử dụng logic có state dễ hơn (thay cho HOC/render-props rối rắm), gom logic liên quan vào một chỗ thay vì rải qua các lifecycle method, và tránh sự phức tạp của this trong class.

Q2Giải thích mảng deps và cleanup của useEffect.Junior›

Trả lời: Mảng deps liệt kê các giá trị mà effect phụ thuộc; React so sánh nông từng phần tử với render trước, nếu có gì đổi thì chạy lại effect. Không truyền deps → chạy mỗi render; [] → chạy một lần sau mount; [a] → chạy lại khi a đổi. Hàm trả về từ effect là cleanup: chạy trước lần effect kế tiếp và khi unmount, dùng để gỡ listener/đóng socket/clear timer — chống rò rỉ.

Q3Stale closure là gì? Cho ví dụ và cách khắc phục.Middle›

Trả lời: Là tình huống một callback "đóng gói" giá trị state/props tại thời điểm nó được tạo, nên về sau vẫn đọc giá trị cũ dù state đã đổi. Kinh điển: setInterval trong effect deps rỗng gọi setCount(count + 1) — count mãi là 0. Khắc phục: (1) functional update setCount(c => c + 1); (2) đưa đủ giá trị vào deps để effect tạo lại closure mới; (3) kỹ thuật "latest ref" — lưu giá trị/callback mới nhất vào ref.

⚠️ Bẫy: nhiều người "sửa" bằng cách xóa biến khỏi deps cho hết warning — càng làm stale closure trầm trọng hơn.

Q4Nguyên nhân infinite loop trong useEffect và cách phòng tránh?Middle›

Trả lời: Effect cập nhật một state → render lại → deps "đổi" → effect chạy lại → lặp mãi. Hai thủ phạm hay gặp: (a) đưa chính state mà effect set vào deps; (b) đưa object/array/hàm tạo mới mỗi render vào deps (so sánh nông luôn thấy khác). Phòng tránh: dùng functional update để khỏi cần state trong deps, đưa primitive vào deps thay vì object, bọc object/hàm bằng useMemo/useCallback, hoặc đưa logic vào reducer (dispatch ổn định).

Q5Phân biệt useMemo và useCallback. Khi nào thực sự đáng dùng?Middle›

Trả lời: useMemo nhớ giá trị trả về của một hàm tính toán; useCallback nhớ chính hàm đó. Thật ra useCallback(fn, d) chỉ là đường tắt của useMemo(() => fn, d). Đáng dùng khi: tính toán thật sự nặng; cần tham chiếu ổn định để truyền xuống React.memo (tránh render con vô ích); hoặc làm dep của effect để effect không chạy lại oan. Không nên bọc bừa vì bản thân chúng có chi phí lưu/so sánh deps — đo trước khi tối ưu.

Q6useRef khác useState thế nào? Cho 2 trường hợp dùng ref.Middle›

Trả lời: Cả hai giữ giá trị qua các render, nhưng đổi useState kích hoạt render còn đổi ref.current thì không. Dùng state khi giá trị thay đổi cần phản ánh lên UI; dùng ref khi là dữ liệu nội bộ không cần vẽ lại. Hai ca tiêu biểu: (1) tham chiếu DOM để focus/scroll/đo kích thước; (2) lưu giá trị mutable như id timer, instance WebSocket, hoặc giá trị "trước đó" để so sánh.

Q7Khi nào chọn useReducer thay vì useState?Middle›

Trả lời: Khi state phức tạp: nhiều trường liên quan, nhiều cách chuyển trạng thái theo "hành động", hoặc state kế tiếp phụ thuộc state trước theo logic không tầm thường (state machine của một cuộc gọi/ticket). Reducer gom logic chuyển trạng thái vào một hàm thuần, dễ test và dễ đọc hơn rải nhiều setX. Thêm lợi ích: dispatch có tham chiếu ổn định nên an toàn khi đặt vào deps của effect.

Q8Viết một custom hook. Custom hook có chia sẻ state giữa các component không?Middle›

Trả lời: Custom hook là hàm tên bắt đầu bằng use, gọi các hook khác bên trong, và thường trả về state + hàm điều khiển (vd useFetch(url) trả về {data, loading, error}). Nó không chia sẻ state — mỗi lần gọi tạo một bản state độc lập; thứ được tái sử dụng là logic. Muốn chia sẻ cùng một state giữa nhiều component thì cần Context hoặc store ngoài (Zustand/Redux).

⚠️ Bẫy: nhiều ứng viên tưởng hai component gọi cùng một custom hook sẽ dùng chung state — sai.

Q9Quy tắc Rules of Hooks là gì và vì sao tồn tại?Middle›

Trả lời: Hai quy tắc: (1) chỉ gọi hook ở top-level — không trong if/loop/hàm lồng/sau return sớm; (2) chỉ gọi hook từ function component hoặc custom hook. Lý do: React khớp state của hook theo thứ tự gọi qua các lần render chứ không theo tên. Nếu thứ tự thay đổi (do điều kiện), React sẽ gán nhầm ô nhớ state giữa các hook, gây bug khó lường. Plugin eslint-plugin-react-hooks giúp bắt vi phạm tự động.

Q10Quy tắc exhaustive-deps của ESLint nói gì? Có nên tắt nó không?Senior›

Trả lời: Rule yêu cầu mọi giá trị (state/props/hàm) dùng trong effect phải có mặt trong mảng deps, để effect luôn "nhìn thấy" dữ liệu mới nhất. Không nên tắt nó một cách tùy tiện — cảnh báo của nó gần như luôn chỉ ra một bug tiềm ẩn (stale closure). Cách xử lý đúng khi deps "phiền": dùng functional update để bỏ state khỏi deps, useCallback/useMemo để ổn định tham chiếu hàm/object, chuyển sang reducer, hoặc "latest ref" cho giá trị không nên kích hoạt effect. Tắt rule chỉ là giải pháp cuối khi bạn thực sự hiểu mình đang làm gì.

⚠️ Bẫy: trả lời "cứ tắt cho đỡ phiền" sẽ bị đánh trượt về tư duy.

Q11useEffect và useLayoutEffect khác nhau ra sao? Khi nào dùng cái nào?Senior›

Trả lời: useEffect chạy bất đồng bộ sau khi trình duyệt paint, không chặn vẽ — phù hợp cho hầu hết side-effect (fetch, subscribe, log). useLayoutEffect chạy đồng bộ trước khi paint, dùng khi cần đo DOM rồi điều chỉnh layout ngay để tránh user thấy nhấp nháy (vd đo chiều cao tooltip để định vị). Mặc định dùng useEffect; chỉ chuyển sang useLayoutEffect khi thực sự thấy hiện tượng nháy do thao tác layout. Lạm dụng useLayoutEffect làm chậm vì chặn paint.

Q12Trong một màn hình agent realtime, bạn mở WebSocket nhưng nó bị mở/đóng liên tục mỗi lần re-render. Debug thế nào?Senior›

Trả lời: Nguyên nhân điển hình là deps của effect mở socket chứa một giá trị tạo mới mỗi render — thường là một callback (vd onMessage) hoặc một object cấu hình không được memo hóa. Mỗi render tạo tham chiếu mới → cleanup đóng socket cũ → mở socket mới. Cách khắc phục: (1) đưa vào deps chỉ những primitive thật sự cần (vd channelId); (2) ổn định callback bằng useCallback; (3) tốt nhất là kỹ thuật "latest ref" — lưu onMessage vào ref cập nhật mỗi render và gọi ref.current bên trong, để effect chỉ phụ thuộc channelId. Đồng thời kiểm tra React StrictMode ở môi trường dev (cố tình mount/unmount 2 lần) — đảm bảo cleanup đóng socket đúng.

⚠️ Bẫy: quên rằng StrictMode dev chạy effect 2 lần là cố ý, dễ kết luận nhầm là bug.
