React Core: JSX, Components & State

Nền tảng React để dựng Dashboard, CRM và Call UI: component, props, state, Virtual DOM và cách React render.

🎯 Học xong chương này bạn sẽ

• Hiểu SPA là gì và vì sao React là thư viện (không phải framework), hướng component.

• Đọc/viết được JSX: nhúng biểu thức, gắn thuộc tính, render có điều kiện và danh sách.

• Phân biệt rạch ròi props (chỉ đọc, một chiều) với state (nội bộ, có thể thay đổi).

• Giải thích state bất biến, useState, và khi nào một component re-render.

• Hiểu Virtual DOM + reconciliation/diffing và vì sao key phải ổn định.

• Phân biệt controlled vs uncontrolled component khi xử lý form/input.

💡 Liên hệ thực tế hệ thống Contact Center

Giao diện một Contact Center là một màn hình sống: danh sách agent online, hàng đợi cuộc gọi nhấp nháy, khung chat realtime, bảng thông tin khách hàng (CRM) đổi liên tục. Tất cả đều là state thay đổi theo thời gian. React sinh ra để giải đúng bài toán này: bạn mô tả "UI nên trông thế nào ứng với state hiện tại", React lo việc cập nhật DOM tối thiểu cho mượt. Hiểu chắc các khái niệm chương này là điều kiện cần để dựng được Call UI realtime ở G6.

① SPA & React là gì?

Trước React, web truyền thống dùng mô hình MPA — Multi Page Application: mỗi lần điều hướng, trình duyệt tải lại cả trang HTML mới từ server, màn hình trắng rồi vẽ lại từ đầu. Với một bảng điều khiển Contact Center cần cập nhật từng giây, mô hình này quá chậm và mất ngữ cảnh (cuộc gọi đang nghe sẽ đứt).

SPA — Single Page Application nạp một trang HTML duy nhất cùng một bó JavaScript, sau đó mọi thay đổi giao diện diễn ra ngay trên trình duyệt bằng JS — không tải lại trang. Dữ liệu mới được lấy qua API (fetch/WebSocket) và chỉ phần UI liên quan được vẽ lại.

Vậy React chính xác là gì?

React là một thư viện JavaScript để xây dựng giao diện người dùng theo hướng component. Lưu ý cách diễn đạt: React là thư viện (library), không phải framework đầy đủ. Nó chỉ lo phần "view" — bạn tự chọn router (React Router), thư viện gọi dữ liệu (React Query), quản lý state (Redux/Zustand)... Đây là lý do người ta nói React là unopinionated: linh hoạt nhưng phải tự ráp hệ sinh thái.

🧩 Hướng component

UI = cây các khối tái sử dụng (Button, AgentCard, CallQueue) lồng vào nhau.

📝 Khai báo (declarative)

Bạn mô tả UI nên trông thế nào theo state, không tự tay thao tác DOM từng bước.

➡️ Dữ liệu một chiều

Dữ liệu chảy từ cha → con qua props. Dễ suy luận, dễ debug.

⚠️ Declarative vs Imperative

Với DOM thuần (imperative) bạn viết "tìm phần tử này, đổi text, thêm class". Với React (declarative) bạn chỉ nói "khi status === 'busy' thì hiện badge đỏ". React tự tính bước thay đổi DOM. Đây là khác biệt tư duy lớn nhất khi chuyển từ jQuery sang React.

② JSX — viết UI ngay trong JavaScript

JSX (JavaScript XML) là cú pháp mở rộng cho phép viết "thẻ giống HTML" ngay trong JavaScript. Nó không phải HTML và không chạy trực tiếp trong trình duyệt — phải qua một bộ biên dịch (Babel hoặc trình build như Vite/SWC) để biến thành lời gọi hàm JavaScript thuần.

jsx-compile.jsxJSX → JS
// Bạn viết JSX:
const el = <div className="agent">Xin chào</div>;

// Babel biên dịch thành (React 17+ với JSX transform mới):
const el = _jsx("div", { className: "agent", children: "Xin chào" });

// Cách cổ điển (React.createElement) — cùng ý nghĩa:
const el = React.createElement("div", { className: "agent" }, "Xin chào");

Nói cách khác, JSX chỉ là "đường ngọt" (syntactic sugar) cho React.createElement(...). Hàm này trả về một React element — một object JS thường mô tả thẻ, props và con. Đây là viên gạch của Virtual DOM (phần ⑥).

Các quy tắc JSX phải nhớ

  • Một phần tử gốc duy nhất: mỗi component trả về một node gốc. Cần nhiều node ngang hàng thì bọc bằng <div> hoặc Fragment <>...</>.
  • Đóng mọi thẻ: kể cả thẻ rỗng phải tự đóng — <img />, <br />.
  • camelCase cho thuộc tính: onClick, tabIndex, className (vì class là từ khóa JS), htmlFor (thay for).
  • Nhúng biểu thức bằng { }: bên trong ngoặc nhọn là biểu thức JS (trả về giá trị), không phải câu lệnh. Không viết if/for trực tiếp được.
AgentBadge.jsxJSX
function AgentBadge({ agent }) {
  const isOnline = agent.status === "online";
  return (
    <div className={`badge ${isOnline ? "green" : "red"}`}>
      {/* nhúng biểu thức: tên + số cuộc đang xử lý */}
      <span>{agent.name}</span>
      <small>{agent.activeCalls} cuộc</small>
      {isOnline && <span className="dot" />}      // render có điều kiện
      {agent.note ? <em>{agent.note}</em> : null}
    </div>
  );
}
🐛 Bẫy hay gặp với {cond && ...}

Nếu cond là số 0, React sẽ in ra "0" chứ không phải ẩn đi! Ví dụ {queue.length && <Badge/>} khi hàng đợi rỗng sẽ hiển thị "0". Sửa: ép boolean — {queue.length > 0 && <Badge/>} hoặc {!!queue.length && ...}.

③ Components & Props

Trong React hiện đại, component là một hàm JavaScript nhận vào một object props và trả về JSX. Tên component phải viết hoa chữ cái đầu (PascalCase) để React phân biệt với thẻ HTML thường.

CallCard.jsxReact
// Function component — nhận props, trả JSX
function CallCard({ caller, waitSeconds, onAnswer }) {
  return (
    <div className="call-card">
      <b>{caller}</b>
      <span>Đợi {waitSeconds}s</span>
      <button onClick={onAnswer}>Nghe</button>
    </div>
  );
}

// Dùng lại (composition): cha truyền dữ liệu xuống qua props
<CallCard caller="+84 90..." waitSeconds={42} onAnswer={handleAnswer} />

Props là gì và quy tắc vàng của props

Props (properties) là dữ liệu mà component cha truyền xuống component con. Hãy hình dung props giống tham số của một hàm: con nhận để dùng, nhưng tuyệt đối không được sửa.

🔒 Chỉ đọc (read-only)

Con không được gán props.x = .... Props là bất biến từ góc nhìn của con — sửa nó là vi phạm tư duy React.

➡️ Một chiều (top-down)

Dữ liệu chỉ chảy cha → con. Con muốn báo lên cha thì cha truyền xuống một callback (vd onAnswer).

Dashboard (cha)props ↓ CallQueueprops ↓ CallCardcallback ↑ Dashboard xử lý

Composition — ghép component như xếp hình

React khuyến khích ghép nối (composition) thay vì kế thừa. Một component lớn được xây bằng cách lồng nhiều component nhỏ. Prop đặc biệt children cho phép một component "bọc" nội dung bất kỳ:

Panel.jsxReact
function Panel({ title, children }) {
  return (
    <section className="panel">
      <h3>{title}</h3>
      {children}                // nội dung lồng bên trong sẽ rơi vào đây
    </section>
  );
}

// Sử dụng — mọi thứ giữa thẻ mở/đóng là children
<Panel title="Hàng đợi">
  <CallQueue />
  <QueueStats />
</Panel>
💡 Props vs State — một câu để nhớ đời

Props = dữ liệu đến từ bên ngoài (cha truyền, con chỉ đọc). State = dữ liệu do chính component sở hữu và thay đổi theo thời gian. "Bộ lọc đang chọn" trong header có thể là state của header, nhưng khi truyền xuống danh sách bên dưới thì nó trở thành props của danh sách đó.

④ State với useState

State là bộ nhớ riêng của một component — dữ liệu có thể thay đổi theo tương tác và khiến UI vẽ lại. Trong function component, ta khai báo state bằng Hook useState:

CallTimer.jsxReact
import { useState } from "react";

function ChatBox() {
  // [giá trị hiện tại, hàm cập nhật] — destructuring mảng
  const [text, setText] = useState("");     // giá trị khởi tạo = ""
  const [messages, setMessages] = useState([]);

  function send() {
    if (!text.trim()) return;
    // KHÔNG đẩy thẳng vào mảng cũ — tạo mảng MỚI (bất biến)
    setMessages([...messages, { id: Date.now(), text }]);
    setText("");                          // reset ô nhập
  }

  return (
    <div>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <button onClick={send}>Gửi</button>
    </div>
  );
}

useState(initial) trả về một mảng 2 phần tử: giá trị state hiện tại và hàm setter. Gọi setter sẽ làm 2 việc: (1) lưu giá trị mới, (2) lên lịch re-render component để UI phản ánh giá trị mới.

🐛 Vì sao state phải BẤT BIẾN (immutable)?

React quyết định re-render bằng cách so sánh tham chiếu (so sánh ===, tức "có phải cùng một object/mảng không"), chứ không soi từng phần tử bên trong. Nếu bạn messages.push(x) rồi setMessages(messages) thì tham chiếu không đổi → React tưởng "chẳng có gì mới" → không re-render. Vì vậy luôn tạo object/mảng mới: [...arr, x], {...obj, k:v}, arr.map(...), arr.filter(...).

⚠️ Cập nhật dựa trên state cũ — dùng dạng hàm

Khi state mới phụ thuộc state cũ (vd tăng số cuộc đã nhận), đừng dùng setCount(count + 1) nhiều lần liên tiếp — do batching, các giá trị count có thể bị "đóng băng" cũ. Hãy dùng dạng updater function: setCount(prev => prev + 1) để luôn nhận giá trị mới nhất.

Quy tắc của Hooks (xem sâu ở G2)

  • Chỉ gọi ở cấp cao nhất của component — không trong if, vòng lặp, hàm lồng. React dựa vào thứ tự gọi để khớp state.
  • Chỉ gọi trong function component hoặc custom hook — không gọi trong hàm JS thường.

⑤ Render & Re-render

"Render" trong React không có nghĩa là "vẽ lên màn hình" ngay. Render là việc React gọi hàm component để tính ra cây React element (mô tả UI mới). Sau đó mới tới bước "commit" — React áp những thay đổi cần thiết vào DOM thật. Tách hai bước này là chìa khóa hiểu performance.

Trigger (state/props đổi)→ Render (gọi component → element tree)→ Reconcile (diff)→ Commit (sửa DOM tối thiểu)

Khi nào một component re-render?

Nguyên nhânGiải thích
State đổiGọi setter của useState (với giá trị khác trước) → component đó re-render.
Props đổiComponent cha re-render và truyền props mới xuống.
Cha re-renderMặc định, cha render lại thì toàn bộ con cũng render lại — kể cả props không đổi (trừ khi tối ưu bằng React.memo, xem G3).
Context đổiComponent đang dùng một Context sẽ re-render khi giá trị context thay đổi.
⚠️ Re-render ≠ thao tác DOM

Một component re-render không đồng nghĩa DOM bị đụng vào. React render (tính element) rồi diff; nếu kết quả giống hệt, DOM không đổi gì cả. Render lại nhiều lần thường không "chậm" trừ khi cây con quá lớn hoặc tính toán nặng — khi đó mới cần memo hóa.

🐛 Tình huống Contact Center điển hình

Component <Dashboard> giữ state onlineCount nhận từ WebSocket cập nhật mỗi giây. Vì Dashboard re-render liên tục, mọi con bên dưới (kể cả bảng CRM nặng không liên quan) cũng render theo. Cách chữa: đẩy state xuống thấp (đặt onlineCount ở component nhỏ nhất cần nó), hoặc dùng memo. Nguyên tắc: "state ở càng gần nơi dùng càng tốt".

⑥ Virtual DOM & Reconciliation

Thao tác trực tiếp DOM thật rất tốn kém: đụng vào DOM kéo theo tính lại layout, vẽ lại (reflow/repaint). Nếu mỗi lần state đổi mà ta xóa và dựng lại cả khối DOM thì UI sẽ giật. Virtual DOM là giải pháp của React.

Virtual DOM là gì?

Virtual DOM là một bản sao DOM dưới dạng object JavaScript nhẹ nằm trong bộ nhớ. Khi render, React tạo ra một cây Virtual DOM mới mô tả UI mong muốn. Object này rẻ để tạo và so sánh hơn DOM thật rất nhiều.

react-element.jsObject JS
// Một React element thực ra chỉ là object JS thường như thế này:
{
  type: "div",
  props: {
    className: "call-card",
    children: [
      { type: "b", props: { children: "+84 90..." } },
      { type: "span", props: { children: "Đợi 42s" } }
    ]
  }
}

Reconciliation — quá trình "đối chiếu & cập nhật"

Reconciliation là thuật toán React dùng để so sánh (diff) cây Virtual DOM mới với cây cũ, tìm ra khác biệt tối thiểu, rồi chỉ vá đúng những chỗ đó vào DOM thật. Đây là lý do React nhanh: nó không vẽ lại cả trang, chỉ chạm vào phần thay đổi.

VDOM cũvs VDOM mới→ diff → danh sách thay đổi nhỏ nhất→ vá vào DOM thật

Heuristic diffing — vì sao nhanh?

So sánh hai cây tổng quát có độ phức tạp rất cao (O(n³)). React rút xuống gần O(n) bằng vài giả định thực dụng:

  • Khác type → thay nguyên cây con. Đổi từ <div> sang <section>, React hủy cả nhánh cũ và dựng nhánh mới (không cố sửa từng phần).
  • Cùng type → giữ node, chỉ cập nhật props khác nhau. Vd cùng <div> chỉ đổi className.
  • Danh sách phần tử con → dùng key để nhận diện phần tử nào là phần tử nào giữa hai lần render (dẫn sang phần ⑦).
📌 Phân biệt thuật ngữ kẻo bị bắt bẻ khi PV

Virtual DOM = cấu trúc dữ liệu (cây element trong bộ nhớ). Reconciliation = thuật toán đối chiếu cũ/mới. Diffing = bước so sánh bên trong reconciliation. Fiber = kiến trúc reconciler hiện đại của React cho phép chia nhỏ và tạm dừng công việc render (đề cập sâu ở G3).

⑦ Lists & Keys

Giao diện Contact Center đầy danh sách: hàng đợi cuộc gọi, lịch sử chat, danh sách ticket, agent online. Ta render danh sách bằng map() để biến mảng dữ liệu thành mảng phần tử JSX:

CallQueue.jsxReact
function CallQueue({ calls }) {
  return (
    <ul>
      {calls.map((call) => (
        // key: định danh ỔN ĐỊNH & DUY NHẤT của mỗi item
        <li key={call.id}>
          {call.caller} — đợi {call.waitSeconds}s
        </li>
      ))}
    </ul>
  );
}

Vì sao bắt buộc có key?

key là một thuộc tính đặc biệt giúp React nhận diện từng phần tử trong danh sách giữa hai lần render. Khi danh sách thay đổi (thêm/xóa/đảo thứ tự), React dùng key để biết: phần tử nào vẫn là cũ (chỉ cập nhật), phần tử nào mới (tạo), phần tử nào biến mất (gỡ). Không có key, React phải đoán theo vị trí — dễ sai.

🐛 Đừng dùng index làm key (trong danh sách động)

Dùng key={index} khi danh sách có thể thêm/xóa/sắp xếp lại sẽ gây lỗi tinh vi: state nội bộ và DOM của một dòng dính nhầm sang dòng khác. Ví dụ kinh điển trong Contact Center: một cuộc gọi ở đầu hàng đợi được nghe (gỡ khỏi mảng) → mọi index dịch lên → input "ghi chú" đang gõ ở dòng 2 bỗng nhảy sang dòng 1, hoặc ô đang nhập bị reset. Hãy dùng id ổn định từ dữ liệu (call.id, ticket.id).

⚠️ Quy tắc về key

• Key chỉ cần duy nhất giữa các anh em (siblings), không cần duy nhất toàn app. • Key không được truyền vào component như prop — muốn dùng giá trị đó bên trong phải truyền thêm prop riêng. • Key nên ổn định qua các lần render (cùng item → cùng key).

Render có điều kiện

JSX không cho viết if trực tiếp trong { }, nên ta dùng các kỹ thuật biểu thức:

QueueView.jsxReact
// 1) Toán tử 3 ngôi cho 2 nhánh
{calls.length === 0
  ? <p>Không có cuộc gọi chờ</p>
  : <CallQueue calls={calls} />}

// 2) Short-circuit && cho "có thì hiện" (nhớ ép boolean!)

// 3) Tách biến/early return cho logic phức tạp
if (loading) return <Spinner />;

Sự kiện & Synthetic Events

React không gắn listener trực tiếp lên từng DOM node theo cách thuần. Thay vào đó, mọi onClick, onChange... được bọc trong SyntheticEvent — một lớp bao chuẩn hóa event của trình duyệt, đảm bảo hành vi nhất quán trên mọi trình duyệt. React còn dùng event delegation (gắn listener ở gốc, từ React 17 là root của app) để hiệu quả.

  • Handler nhận SyntheticEvent: e.target.value, e.preventDefault(), e.stopPropagation() đều dùng được.
  • Truyền tham chiếu hàm, không gọi hàm: onClick={handleAnswer} (đúng) vs onClick={handleAnswer()} (sai — chạy ngay khi render).
  • Cần truyền tham số: bọc arrow — onClick={() => answer(call.id)}.

Controlled vs Uncontrolled component

Với input/form có 2 trường phái quản lý giá trị:

Tiêu chíControlled (được kiểm soát)Uncontrolled (không kiểm soát)
Nguồn sự thậtReact state giữ giá trịDOM tự giữ giá trị
Cú phápvalue={x} + onChangedefaultValue + ref để đọc khi cần
Ưu điểmValidate tức thì, format, disable nút gửi, dễ kiểm soátÍt code, ít re-render, hợp form đơn giản
Nhược điểmRe-render mỗi phím gõKhó validate realtime, khó đồng bộ
Hợp vớiÔ soạn chat, bộ lọc, form ticket có ràng buộcUpload file, form rất đơn giản
controlled-vs-uncontrolled.jsxReact
// CONTROLLED — state là nguồn sự thật
const [note, setNote] = useState("");
<input value={note} onChange={(e) => setNote(e.target.value)} />
<button disabled={!note.trim()}>Lưu ghi chú</button>

// UNCONTROLLED — DOM giữ giá trị, đọc qua ref khi submit
const ref = useRef(null);
<input defaultValue="" ref={ref} />
<button onClick={() => save(ref.current.value)}>Lưu</button>

⚠️ Lỗi thường gặp & Best practices

🚫 Sửa state trực tiếp

messages.push(x) rồi set lại → tham chiếu không đổi → không re-render. Luôn tạo bản mới.

🚫 index làm key

Với danh sách động gây dính state/DOM nhầm dòng. Dùng id ổn định từ dữ liệu.

🚫 Gọi hàm thay vì truyền tham chiếu

onClick={fn()} chạy ngay khi render. Đúng là onClick={fn} hoặc {() => fn(x)}.

🚫 {0 && ...} in ra "0"

Short-circuit với số 0 hiện "0". Ép boolean: {len > 0 && ...}.

🚫 Gọi Hook có điều kiện

Hook trong if/vòng lặp phá thứ tự gọi → state lẫn lộn. Luôn ở cấp cao nhất.

✅ Đặt state gần nơi dùng

Tránh để state cao quá khiến cả cây con re-render. "Lift up" chỉ khi nhiều con cùng cần.

✅ Component thuần (pure)

Cùng props/state → cùng kết quả; không tác dụng phụ trong khi render. Side effect để vào useEffect (G2).

✅ className không phải class

JSX dùng camelCase; class/for là từ khóa JS → className/htmlFor.

🧪 Bài tập

🧪 Bài 1 — Bộ đếm cuộc gọi đã nhận

Viết component AnsweredCounter có nút "Nhận cuộc". Mỗi lần bấm tăng số đếm thêm 1. Bấm 3 lần thật nhanh phải ra đúng +3. Giải thích vì sao setCount(count + 1) ba lần liền có thể sai và cách sửa.

Gợi ý

Do React gộp (batch) các cập nhật trong cùng một sự kiện, cả ba lần đều đọc cùng giá trị count cũ → chỉ +1. Dùng updater function: setCount(prev => prev + 1) để mỗi lần nhận giá trị mới nhất từ React.

🧪 Bài 2 — Danh sách ticket có key đúng

Render danh sách ticket từ mảng {id, subject, priority}. Thêm nút "Đóng" để xóa một ticket bất kỳ ở giữa. Mỗi dòng có một <input> ghi chú. Hãy thử với key={index} rồi với key={ticket.id} và quan sát ghi chú có "nhảy dòng" không.

Gợi ý

Với key={index}, khi xóa dòng giữa, index của các dòng sau dịch lên → React tái sử dụng DOM/state sai dòng, nội dung input nhảy lung tung. Với key={ticket.id}, React khớp đúng theo định danh nên ghi chú đi theo đúng ticket. Xóa bằng setTickets(ts => ts.filter(t => t.id !== id)) (bất biến).

🧪 Bài 3 — Ô soạn chat controlled

Dựng ô nhập tin nhắn controlled: nút "Gửi" bị disabled khi rỗng, tự xóa ô sau khi gửi, và đếm ký tự còn lại (tối đa 200). Sau đó thử chuyển sang uncontrolled và liệt kê những tính năng nào khó làm hơn.

Gợi ý

Controlled cho phép đọc giá trị mỗi lần gõ → dễ disabled={!text.trim()}, hiển thị 200 - text.length, chặn khi vượt 200. Uncontrolled (chỉ defaultValue + ref) không có giá trị realtime nên đếm ký tự / bật-tắt nút theo từng phím rất khó — minh họa rõ vì sao form tương tác nên dùng controlled.

Ngân hàng câu hỏi phỏng vấn

React core — bộ câu hỏi gần như chắc chắn xuất hiện ở vòng frontend.

Q1React là gì? Là thư viện hay framework?Junior›

Trả lời: React là một thư viện JavaScript để xây dựng giao diện người dùng theo hướng component, theo phong cách khai báo và dữ liệu một chiều. Nó chỉ lo phần "view" — các phần như định tuyến, gọi dữ liệu, quản lý state toàn cục do hệ sinh thái (React Router, React Query, Redux/Zustand...) đảm nhiệm. Vì thế React được gọi là unopinionated/linh hoạt.

⚠️ Bẫy: gọi React là "framework" có thể bị vặn lại. Nhấn mạnh "library" và nói rõ phần React không tự lo.

Q2JSX là gì? Nó biên dịch thành gì?Junior›

Trả lời: JSX là cú pháp mở rộng cho phép viết thẻ giống HTML trong JavaScript. Nó không phải HTML và không chạy trực tiếp trên trình duyệt; Babel/SWC biên dịch nó thành lời gọi React.createElement(type, props, ...children) (hoặc _jsx với JSX transform mới), trả về một React element — object JS mô tả UI. JSX chỉ là "syntactic sugar" cho các lời gọi đó.

Q3Phân biệt props và state.Junior›

Trả lời: Props là dữ liệu truyền từ cha xuống con, chỉ đọc với con (giống tham số hàm). State là dữ liệu nội bộ do chính component sở hữu và thay đổi được theo thời gian/tương tác; thay đổi state gây re-render. Một giá trị có thể là state ở component này nhưng trở thành props khi được truyền xuống con. Cả hai đổi đều có thể kích hoạt render lại.

Q4One-way data flow là gì và vì sao React chọn nó?Middle›

Trả lời: Dữ liệu chảy một chiều từ cha xuống con qua props. Con không sửa props; muốn báo ngược lên cha thì cha truyền xuống một callback và con gọi nó. Lợi ích: luồng dữ liệu dễ dự đoán & dễ debug — chỉ cần nhìn xem state nằm ở đâu và nó chảy xuống đâu. Trái với two-way binding (dữ liệu chạy hai chiều khó truy vết khi app lớn).

Q5Vì sao state trong React phải bất biến (immutable)?Middle›

Trả lời: React quyết định có re-render hay không bằng cách so sánh tham chiếu giữa state/props cũ và mới (shallow compare). Nếu bạn sửa trực tiếp object/mảng cũ (push, gán thuộc tính) rồi set lại, tham chiếu không đổi → React tưởng không có gì thay đổi → bỏ qua. Vì vậy phải tạo bản sao mới: [...arr, x], {...obj, k}, map/filter. Bất biến còn giúp tối ưu (memo, PureComponent) hoạt động đúng.

⚠️ Bẫy: nhiều người trả lời "vì lý do hiệu năng". Cốt lõi là cơ chế so sánh tham chiếu để phát hiện thay đổi.

Q6Virtual DOM là gì? Nó hoạt động ra sao?Middle›

Trả lời: Virtual DOM là bản mô tả UI dưới dạng object JS nhẹ trong bộ nhớ. Khi state/props đổi, React render ra một cây Virtual DOM mới, rồi diff với cây cũ (reconciliation) để tìm khác biệt tối thiểu, và chỉ vá đúng phần thay đổi vào DOM thật. Mục đích: tránh thao tác DOM thật trực tiếp (rất tốn vì gây reflow/repaint), giúp cập nhật hiệu quả và để lập trình viên viết theo kiểu khai báo.

⚠️ Bẫy: nói "Virtual DOM luôn nhanh hơn DOM thật" là sai — nó nhanh ở chỗ giảm số thao tác DOM, không phải tự nó là phép màu.

Q7Reconciliation & diffing diễn ra thế nào? Heuristic là gì?Senior›

Trả lời: Reconciliation là thuật toán đối chiếu cây cũ/mới. So sánh cây tổng quát là O(n³), React rút về ~O(n) bằng heuristic: (1) hai element khác type → vứt cả cây con cũ, dựng mới; (2) cùng type → giữ node, chỉ cập nhật props khác; (3) với danh sách con, dùng key để khớp phần tử giữa hai lần render. Kiến trúc reconciler hiện đại là Fiber, cho phép chia nhỏ công việc, tạm dừng/tiếp tục để giữ UI mượt.

Q8Vì sao cần key trong danh sách? Vì sao không nên dùng index?Middle›

Trả lời: key giúp React nhận diện phần tử nào là phần tử nào giữa hai lần render để tái sử dụng/ cập nhật/ gỡ đúng node, giữ đúng state nội bộ của từng dòng. Dùng index trong danh sách động (thêm/xóa/đảo) sẽ làm key đổi theo vị trí → React gắn nhầm DOM/state sang dòng khác (vd input đang gõ nhảy dòng, checkbox dính sai). Nên dùng id ổn định từ dữ liệu.

Q9Khi nào một component re-render?Middle›

Trả lời: Khi (1) state của nó thay đổi (gọi setter với giá trị khác), (2) props nhận từ cha thay đổi, (3) component cha re-render (mặc định con cũng render lại, kể cả props không đổi — trừ khi bọc React.memo), hoặc (4) một Context nó đang tiêu thụ đổi giá trị. Quan trọng: re-render là tính lại element; nếu diff không thấy khác biệt thì DOM không bị đụng.

Q10Render và commit khác nhau ra sao?Senior›

Trả lời: Render phase: React gọi (các) component để tính ra cây element mới và diff với cây cũ — đây phải là quá trình "thuần", không tác dụng phụ, và có thể bị React tạm dừng/hủy. Commit phase: React áp các thay đổi đã tính được vào DOM thật, rồi chạy các effect (useLayoutEffect đồng bộ, useEffect bất đồng bộ sau khi vẽ). Tách hai pha cho phép React làm việc kiểu ngắt quãng (concurrent) mà không gây nháy hình.

Q11Controlled vs uncontrolled component — khi nào dùng cái nào?Middle›

Trả lời: Controlled: React state giữ giá trị (value + onChange) — nguồn sự thật là state, cho phép validate realtime, format, bật/tắt nút gửi; hợp ô soạn chat, bộ lọc, form ticket có ràng buộc (đổi lại re-render mỗi phím gõ). Uncontrolled: DOM tự giữ giá trị, đọc qua ref khi submit; ít code, ít re-render, hợp form đơn giản hoặc input file (vốn buộc uncontrolled). Quy tắc: cần tương tác/validate liên tục → controlled.

Q12SyntheticEvent là gì? Khác event thuần ở điểm nào?Senior›

Trả lời: SyntheticEvent là lớp bao chuẩn hóa event của trình duyệt mà React truyền vào handler, đảm bảo cùng API và hành vi nhất quán cross-browser (preventDefault, stopPropagation, e.target...). React dùng event delegation — gắn listener ở gốc app (từ React 17 là container root, không còn ở document) thay vì từng node, giúp gắn/gỡ listener hiệu quả. Muốn lấy event gốc của trình duyệt dùng e.nativeEvent.

⚠️ Bẫy (lịch sử): trước React 17 SyntheticEvent bị "pooled" (tái sử dụng), không đọc được async. React 17+ đã bỏ pooling.
