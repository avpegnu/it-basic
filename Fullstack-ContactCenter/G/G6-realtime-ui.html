Realtime UI: Dashboard, CRM & Call UI

Kết nối WebSocket vào React để dựng bảng trạng thái agent, hàng đợi cuộc gọi và cửa sổ chat cập nhật thời gian thực — phần frontend đặc thù của Contact Center.

🎯 Học xong chương này bạn sẽ

• Mở một kết nối Socket.IO duy nhất trong React đúng vòng đời (useEffect + cleanup), không tạo nhiều kết nối thừa.

• Viết custom hook useSocket / useSocketEvent để tái sử dụng và đăng ký/gỡ listener an toàn.

• Cập nhật state theo sự kiện realtime mà không dính stale closure (functional update, ref).

• Dựng realtime dashboard: bảng trạng thái agent, hàng đợi cuộc gọi live, cửa sổ chat.

• Đồng bộ lại state sau khi reconnect và xử lý hiệu năng khi có hàng trăm update mỗi giây.

• Áp dụng Optimistic UI khi gửi tin nhắn để giao diện phản hồi tức thì.

💡 Liên hệ thực tế hệ thống Contact Center

Màn hình của một supervisor là một "phòng điều khiển": hàng chục agent đổi trạng thái (Available → On Call → Wrap-up) liên tục, cuộc gọi vào/ra hàng đợi mỗi giây, tin nhắn chat của khách nhảy real-time. Tất cả đến từ server đẩy sự kiện qua WebSocket (xem F1). Nhiệm vụ của frontend là biến luồng sự kiện đó thành UI mượt, chính xác, không lag và không "đứng hình" sau khi mạng chập chờn.

① Kết nối Socket.IO trong React

Trên backend bạn đã dựng Socket.IO server (Phần C). Phía React, thư viện là socket.io-client. Điểm mấu chốt: một kết nối WebSocket là tài nguyên có vòng đời — nó phải được mở khi component cần và đóng lại khi không cần nữa. Đặt sai chỗ là nguồn gốc của hầu hết bug realtime trong React.

Sai lầm kinh điển: tạo socket trong thân component

React re-render component rất nhiều lần. Nếu bạn gọi io(...) ngay trong thân hàm, mỗi lần render sẽ mở thêm một kết nối mới — server thấy hàng chục kết nối ma từ một tab trình duyệt.

DO-NOT.jsxReact
function AgentBoard() {
  // ❌ Mỗi lần render tạo MỘT socket mới → rò rỉ kết nối
  const socket = io('https://cc.example.com');
  socket.on('agent:update', handle); // listener cũng nhân bản
  return <Board />;
}

Vòng đời đúng: useEffect + cleanup

Kết nối nên được tạo trong useEffect với mảng phụ thuộc rỗng (chạy đúng một lần khi mount), và hàm cleanup phải gọi socket.disconnect() khi unmount.

useEffect-socket.jsxReact
import { io } from 'socket.io-client';

function AgentBoard() {
  const [status, setStatus] = useState('connecting');

  useEffect(() => {
    const socket = io('https://cc.example.com', {
      auth: { token: getToken() },   // JWT cho handshake
      transports: ['websocket'],        // bỏ qua long-polling nếu chắc chắn WS có sẵn
    });

    socket.on('connect',    () => setStatus('online'));
    socket.on('disconnect', () => setStatus('offline'));

    return () => {
      socket.disconnect();          // ✅ BẮT BUỘC — đóng kết nối khi unmount
    };
  }, []);                            // [] → chỉ chạy 1 lần

  return <div>Trạng thái: {status}</div>;
}
⚠️ React 18 StrictMode mount 2 lần

Ở môi trường dev, StrictMode cố tình mount → unmount → mount lại để phát hiện effect không cleanup. Nếu cleanup của bạn đúng (gọi disconnect()), socket cũ bị đóng sạch và chỉ còn một kết nối — đây chính là bài kiểm tra xem bạn cleanup đúng chưa. Nếu thấy 2 kết nối tồn tại song song, cleanup của bạn có vấn đề.

Vì sao chỉ nên có MỘT kết nối toàn app

Một WebSocket có thể truyền mọi sự kiện (agent, call, chat, ticket) qua các event name và room khác nhau. Mở nhiều socket cho mỗi component là lãng phí: tốn handshake, tốn tài nguyên server (mỗi kết nối là một entry trong adapter), và khiến việc quản lý reconnect/auth rối loạn. Giải pháp chuẩn là đưa socket vào React Context (singleton cấp app).

SocketProvider.jsxReact
const SocketContext = createContext(null);

export function SocketProvider({ children }) {
  const [socket, setSocket] = useState(null);

  useEffect(() => {
    const s = io('https://cc.example.com', { auth: { token: getToken() } });
    setSocket(s);
    return () => { s.disconnect(); };
  }, []);

  return (
    <SocketContext.Provider value={socket}>{children}</SocketContext.Provider>
  );
}

export const useSocketCtx = () => useContext(SocketContext);

Đặt <SocketProvider> bao quanh app ở gốc (gần root). Mọi component con dùng useSocketCtx() để lấy cùng một instance — không bao giờ tạo socket riêng.

<App>→ <SocketProvider> (1 kết nối)→ AgentBoard· CallQueue· ChatPanel

② Custom useSocket hook

Việc đăng ký một listener và gỡ đúng listener đó khi unmount lặp lại ở khắp nơi. Đóng gói nó vào hook giúp tránh quên off() — nguyên nhân số một gây rò rỉ listener và "double handler".

useSocketEvent — đăng ký một sự kiện

useSocketEvent.jsReact
import { useEffect, useRef } from 'react';
import { useSocketCtx } from './SocketProvider';

export function useSocketEvent(event, handler) {
  const socket = useSocketCtx();
  const savedHandler = useRef(handler);

  // Luôn giữ handler MỚI NHẤT trong ref → tránh stale closure
  useEffect(() => { savedHandler.current = handler; }, [handler]);

  useEffect(() => {
    if (!socket) return;
    const listener = (...args) => savedHandler.current(...args);
    socket.on(event, listener);
    return () => socket.off(event, listener); // ✅ gỡ đúng listener
  }, [socket, event]);  // KHÔNG phụ thuộc handler → không re-subscribe mỗi render
}
💡 Vì sao dùng ref ở đây?

Nếu để handler trong mảng phụ thuộc, mỗi lần component re-render sẽ tạo handler mới → off + on liên tục (đắt, dễ miss event giữa khoảng trống). Lưu handler vào ref và chỉ subscribe một lần theo event: listener ổn định, nhưng bên trong luôn gọi phiên bản handler mới nhất. Đây là pattern "latest ref" kinh điển khi gắn callback vào API ngoài React.

Dùng trong component — gọn gàng và an toàn

AgentStatus.jsxReact
function AgentStatus({ agentId }) {
  const [state, setState] = useState('unknown');

  useSocketEvent('agent:update', (payload) => {
    if (payload.agentId === agentId) setState(payload.status);
  });

  return <span className={`badge ${state}`}>{state}</span>;
}

Hook tự lo subscribe/unsubscribe. Component chỉ khai báo "khi có agent:update thì làm gì" — đúng tinh thần declarative của React.

Biến thể useSocket trả về instance + tiện ích emit

useSocket.jsReact
export function useSocket() {
  const socket = useSocketCtx();
  const emit = useCallback(
    (event, payload, ack) => socket?.emit(event, payload, ack),
    [socket]
  );
  return { socket, emit, connected: socket?.connected ?? false };
}

③ Cập nhật UI theo sự kiện

Trái tim của realtime UI là: nhận sự kiện → cập nhật state → React re-render. Nghe đơn giản, nhưng có một cái bẫy chết người: stale closure.

Bẫy stale closure với handler socket

Handler được tạo một lần (khi subscribe), nó "đóng băng" giá trị state tại thời điểm đó. Nếu bạn cập nhật dựa trên state cũ một cách trực tiếp, bạn sẽ luôn đọc giá trị cũ.

stale-closure.jsxReact
const [messages, setMessages] = useState([]);

useEffect(() => {
  const onMsg = (m) => {
    // ❌ `messages` ở đây là giá trị [] tại lúc subscribe — đứng yên!
    setMessages([...messages, m]);
  };
  socket.on('chat:message', onMsg);
  return () => socket.off('chat:message', onMsg);
}, []); // [] → onMsg chỉ thấy messages = [] mãi mãi
🐛 Triệu chứng

Khách gửi 5 tin nhắn, nhưng cửa sổ chat chỉ hiện tin cuối cùng (vì mỗi lần đều là [...[], m]). Đây là bug realtime phổ biến nhất khi onboard người mới vào dự án.

Cách 1 — Functional update (khuyên dùng)

Truyền hàm cho setter: React đưa cho bạn state mới nhất làm tham số. Không cần đọc biến closure.

functional-update.jsxReact
const onMsg = (m) => {
  setMessages((prev) => [...prev, m]); // ✅ prev luôn là bản mới nhất
};

Cách 2 — Latest ref (khi cần đọc nhiều state/prop)

Khi logic handler phụ thuộc nhiều giá trị (vd lọc theo selectedConversationId), dùng ref để luôn đọc giá trị mới.

latest-ref.jsxReact
const selectedRef = useRef(selectedId);
useEffect(() => { selectedRef.current = selectedId; }, [selectedId]);

useSocketEvent('chat:message', (m) => {
  if (m.conversationId === selectedRef.current) {
    setMessages((prev) => [...prev, m]);
  }
});

Cập nhật một map trạng thái agent

Bảng trạng thái agent thường là một object/Map keyed theo agentId — cập nhật một agent không nên đụng cả mảng.

agentMap.jsxReact
const [agents, setAgents] = useState({});   // { [id]: agent }

useSocketEvent('agent:update', (a) => {
  setAgents((prev) => ({
    ...prev,
    [a.id]: { ...prev[a.id], ...a },  // merge, giữ field cũ
  }));
});
💡 Reducer cho luồng sự kiện phức tạp

Khi có nhiều loại sự kiện cùng tác động lên một state (agent join/leave/update, call assigned/ended), useReducer gom logic về một nơi, dễ test và tránh nhiều setter rải rác. Mỗi sự kiện socket dispatch một action — coi như "event-sourcing nhẹ" cho UI.

Snapshot ban đầu + delta sau đó

Nguyên tắc vàng cho mọi realtime view: lấy ảnh chụp (snapshot) đầy đủ một lần qua REST/emit, rồi chỉ nhận thay đổi nhỏ (delta) qua sự kiện. Không bao giờ chỉ dựa vào delta từ con số 0 — nếu vào trễ bạn sẽ thiếu dữ liệu cũ.

Mount→ GET /queue (snapshot)→ render bảng đầy đủ→ socket on(delta)→ patch tại chỗ
CallQueue.jsxReact
function CallQueue() {
  const [queue, setQueue] = useState([]);

  // 1) Snapshot khi vào màn hình
  useEffect(() => {
    fetch('/api/queue').then(r => r.json()).then(setQueue);
  }, []);

  // 2) Delta theo thời gian thực
  useSocketEvent('queue:enqueue', (call) =>
    setQueue((q) => [...q, call]));

  useSocketEvent('queue:dequeue', ({ callId }) =>
    setQueue((q) => q.filter(c => c.callId !== callId)));

  return (
    <ul>
      {queue.map(c => (
        <li key={c.callId}>
          {c.from} · chờ <WaitTimer since={c.waitedAt} />
        </li>
      ))}
    </ul>
  );
}

⑤ Reconnection & sync state

Mạng của agent không hoàn hảo: WiFi chập chờn, laptop sleep, server deploy. Socket.IO tự reconnect, nhưng đó mới là một nửa câu chuyện. Nửa còn lại — phần khó — là đồng bộ lại state: trong lúc mất kết nối, thế giới đã thay đổi (agent đổi trạng thái, cuộc gọi mới vào). Nếu không resync, UI sẽ hiển thị dữ liệu cũ một cách âm thầm.

Vòng đời reconnect của Socket.IO

Sự kiện clientÝ nghĩaNên làm gì

reconnect_attemptĐang thử lại (backoff)Có thể đếm số lần thử
connect (lần 2+)Đã nối lại thành côngResync: tải lại snapshot, gỡ banner
⚠️ Phân biệt mount lần đầu vs reconnect

Sự kiện connect bắn cả lần kết nối đầu tiên và mỗi lần reconnect. Bạn cần resync ở mọi lần connect — không chỉ lần đầu. Cách an toàn nhất: gắn logic "tải snapshot" vào handler connect, để nó tự chạy bất kể là lần nào.

useResync.jsxReact
function CallQueue() {
  const [queue, setQueue] = useState([]);
  const [live, setLive]   = useState(false);

  const loadSnapshot = useCallback(() =>
    fetch('/api/queue').then(r => r.json()).then(setQueue), []);

  // Mỗi lần (re)connect → tải lại snapshot rồi mới tin vào delta
  useSocketEvent('connect', () => {
    setLive(true);
    loadSnapshot();          // ✅ resync
  });
  useSocketEvent('disconnect', () => setLive(false));

  useSocketEvent('queue:enqueue', (c) => setQueue(q => [...q, c]));
  useSocketEvent('queue:dequeue', ({ callId }) =>
    setQueue(q => q.filter(c => c.callId !== callId)));

  return (
    <>
      {!live && <div className="banner">⚠️ Mất kết nối — đang đồng bộ lại…</div>}
      <QueueList items={queue} />
    </>
  );
}

Chống mất delta trong khoảng "mù"

Có một khe hở tinh vi: giữa lúc bạn gọi loadSnapshot() và lúc nó trả về, vài delta mới có thể đến và bị ghi đè bởi snapshot. Có 2 hướng xử lý:

  • Versioning / sequence number: server gắn seq tăng dần cho mỗi delta. Snapshot kèm seq hiện tại. Client bỏ qua delta có seq ≤ snapshot, áp dụng delta mới hơn.
  • Server-driven resync: sau reconnect, client emit resync với lastSeq đã thấy; server gửi lại đúng các sự kiện đã miss (cần buffer ngắn ở server).
💡 Đánh đổi thực tế

Với dashboard "đọc là chính", cách đơn giản snapshot-on-connect (chấp nhận sai lệch <1s) thường đủ tốt và rẻ. Cơ chế seq/buffer chỉ cần khi bỏ lỡ một sự kiện là không chấp nhận được (vd lệnh điều phối cuộc gọi). Chọn độ phức tạp tương xứng với chi phí của việc mất một event.

⑥ Hiệu năng với update dày

Một supervisor giám sát 100 agent + hàng trăm cuộc gọi: có thể có vài trăm sự kiện mỗi giây. Nếu mỗi sự kiện gây một setState + một lần render toàn bảng, trình duyệt sẽ giật, fan quay vù vù. Đây là nơi phân biệt junior và người làm realtime thật.

Throttle KPI bằng requestAnimationFrame / interval

throttle-metrics.jsxReact
function useThrottledMetrics() {
  const [metrics, setMetrics] = useState(null);
  const latest = useRef(null);

  // Nhận liên tục → chỉ ghi vào ref (không render)
  useSocketEvent('metrics:tick', (m) => { latest.current = m; });

  // Mỗi 1s đẩy giá trị mới nhất ra UI
  useEffect(() => {
    const id = setInterval(() => {
      if (latest.current) setMetrics(latest.current);
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return metrics;
}

1000 sự kiện/giây vào, nhưng chỉ 1 render/giây ra. Số liệu KPI không cần mượt hơn thế.

Batching delta theo frame

Khi nhiều dòng đổi trong một burst, gom chúng vào một buffer và flush một lần mỗi animation frame (~16ms) thay vì render mỗi delta.

batch-updates.jsxReact
function useBatchedAgents() {
  const [agents, setAgents] = useState({});
  const buffer = useRef([]);
  const frame  = useRef(0);

  useSocketEvent('agent:update', (a) => {
    buffer.current.push(a);
    if (!frame.current) {
      frame.current = requestAnimationFrame(() => {
        const batch = buffer.current; buffer.current = []; frame.current = 0;
        setAgents((prev) => {
          const next = { ...prev };
          for (const a of batch) next[a.id] = { ...next[a.id], ...a };
          return next;        // 1 render cho cả batch
        });
      });
    }
  });

  return agents;
}

🐛 Cảnh báo: dùng index làm key

Với danh sách thay đổi liên tục (sắp xếp lại, chèn/xóa), dùng index làm key khiến React gán nhầm state vào sai dòng → trạng thái agent "nhảy lung tung". Luôn dùng id ổn định làm key.

⑦ Optimistic UI

Khi agent gửi tin nhắn cho khách, nếu phải đợi server xác nhận rồi mới hiện tin lên, UI cảm giác chậm chạp. Optimistic UI giả định thành công: hiện tin ngay lập tức (trạng thái "đang gửi"), rồi điều chỉnh khi server phản hồi.

Luồng optimistic gửi tin nhắn

User gõ & gửi→ thêm tin "pending" (tempId)→ emit + chờ ack→ ack: đổi sang "sent" (id thật)

Nếu lỗi: đổi tin sang trạng thái "failed" với nút "Gửi lại", hoặc rollback (xóa tin). Dùng tempId để khớp tin lạc quan với phản hồi server.

optimistic-send.jsxReact
function useSendMessage(conversationId) {
  const { emit } = useSocket();
  const [messages, setMessages] = useState([]);

  const send = (text) => {
    const tempId = crypto.randomUUID();
    const optimistic = { id: tempId, text, status: 'pending', mine: true };

    setMessages((m) => [...m, optimistic]);   // ① hiện ngay

    emit('chat:send', { conversationId, text, tempId }, (res) => {
      // ② ack từ server (callback của emit)
      setMessages((m) => m.map(msg =>
        msg.id === tempId
          ? (res.ok
              ? { ...msg, id: res.id, status: 'sent' }   // thành công
              : { ...msg, status: 'failed' })            // lỗi → cho gửi lại
          : msg
      ));
    });
  };

  return { messages, setMessages, send };
}
⚠️ Tránh tin nhắn xuất hiện 2 lần (echo)

Server thường broadcast tin mới cho cả phòng, kể cả người gửi. Nếu bạn vừa thêm tin lạc quan, vừa nhận lại qua chat:message, tin sẽ nhân đôi. Cách xử lý: khi nhận broadcast, kiểm tra tempId (server echo lại tempId) hoặc id đã tồn tại thì thay thế thay vì thêm mới.

dedupe-echo.jsxReact
useSocketEvent('chat:message', (m) => {
  setMessages((prev) => {
    const i = prev.findIndex(x => x.id === m.tempId || x.id === m.id);
    if (i !== -1) {                 // đã có (tin lạc quan) → thay thế
      const copy = [...prev]; copy[i] = { ...m, status: 'sent' }; return copy;
    }
    return [...prev, m];          // tin của người khác → thêm mới
  });
});
💡 Optimistic không chỉ cho chat

Pattern này áp cho mọi hành động "mong đợi thành công": gán cuộc gọi cho agent, đổi trạng thái sang Wrap-up, thêm note vào ticket. Quan trọng là luôn có đường rollback/báo lỗi khi server từ chối — đừng để UI nói dối người dùng.

⚠️ Lỗi thường gặp & Best practices

🚫 Tạo socket trong thân component

Mỗi render mở kết nối mới. Luôn đặt trong useEffect/Context và cleanup bằng disconnect().

🚫 Quên off() listener

Mỗi mount thêm một handler → callback chạy nhiều lần, rò rỉ. Cleanup phải gỡ đúng listener.

🚫 Stale closure trong handler

Đọc state cũ trong handler subscribe-một-lần. Dùng functional update hoặc latest ref.

🚫 Chỉ dựa vào delta

Vào trễ → thiếu dữ liệu cũ. Luôn lấy snapshot rồi mới áp delta; resync sau reconnect.

🚫 setState mỗi sự kiện khi update dày

Hàng trăm render/giây → giật. Throttle/batch và virtualize danh sách dài.

🚫 index làm key

Danh sách realtime đổi liên tục → state nhảy sai dòng. Dùng id ổn định.

🚫 Tin nhắn nhân đôi

Optimistic + echo broadcast. Dedupe theo tempId/id.

✅ Hiện trạng thái kết nối

Banner offline + khóa nút emit khi mất kết nối — người dùng cần biết UI có còn "live" không.

🧪 Bài tập

🧪 Bài 1 — Sửa bug stale closure

Một đồng nghiệp viết cửa sổ chat chỉ hiện đúng tin nhắn cuối cùng dù khách gửi nhiều tin. Code dùng setMessages([...messages, m]) trong handler subscribe với deps []. Hãy chỉ ra nguyên nhân và sửa bằng 2 cách (functional update và latest ref). Cách nào nên dùng mặc định?

Gợi ý

Handler đóng băng messages = [] tại lúc subscribe. Cách 1: setMessages(prev => [...prev, m]) — đơn giản, nên dùng mặc định. Cách 2: lưu messages vào ref và cập nhật trong effect, đọc ref.current trong handler — dùng khi cần đọc nhiều state/prop cùng lúc.

🧪 Bài 2 — Resync sau reconnect

Bảng hàng đợi cuộc gọi bị "đứng hình" sau khi laptop của agent thức dậy từ sleep: socket đã reconnect nhưng danh sách sai. Thiết kế cơ chế đồng bộ lại. Mô tả khe hở "mù" giữa snapshot và delta và một cách chống mất event.

Gợi ý

Gắn loadSnapshot() vào handler connect (bắn cả khi reconnect). Khe hở: delta đến trong lúc snapshot đang fetch có thể bị ghi đè. Chống: gắn seq tăng dần cho mỗi delta + snapshot, client bỏ qua delta seq ≤ snapshot; hoặc emit resync(lastSeq) để server gửi lại event đã miss.

🧪 Bài 3 — Optimistic + chống echo

Khi agent gửi tin, tin xuất hiện 2 lần (một bản pending, một bản từ broadcast của server). Sửa để chỉ còn một tin, có trạng thái "đang gửi" → "đã gửi", và xử lý trường hợp server trả lỗi.

Gợi ý

Dùng tempId khi emit; server echo lại tempId trong broadcast. Khi nhận chat:message, tìm theo tempId/id: nếu đã tồn tại thì thay thế (đổi status sang sent, gán id thật) thay vì push. Lỗi ack → đổi status failed kèm nút "Gửi lại".

Ngân hàng câu hỏi phỏng vấn

Realtime UI trong React — chủ đề "ăn điểm" của vị trí Fullstack realtime.

Q1Vòng đời của một socket trong React component là gì?Junior›

Trả lời: Tạo kết nối trong useEffect (deps []) khi component mount, gắn các listener, và trả về hàm cleanup gọi socket.disconnect() + gỡ listener khi unmount. Không tạo socket trong thân component vì mỗi render sẽ mở kết nối mới. Tốt nhất là đặt một socket duy nhất ở Context cấp app.

Q2Vì sao phải cleanup (disconnect/off) khi unmount?Junior›

Trả lời: Không cleanup thì mỗi lần mount để lại một kết nối và listener sống. Hệ quả: server đầy kết nối ma, một sự kiện kích hoạt handler nhiều lần (vì nhiều bản đăng ký), rò rỉ bộ nhớ. Trong React 18 StrictMode dev, mount-unmount-mount sẽ phơi bày bug này ngay nếu cleanup sai.

⚠️ Bẫy: nói "React tự dọn socket" — sai, socket là tài nguyên ngoài React, bạn phải tự đóng.

Q3Làm sao đảm bảo cả app chỉ có MỘT kết nối WebSocket?Middle›

Trả lời: Tạo socket một lần trong một SocketProvider (Context) đặt gần root, cleanup khi provider unmount. Mọi component dùng useContext để lấy cùng instance, không bao giờ tự gọi io(). Một kết nối truyền mọi loại sự kiện qua event name/room. Lợi ích: tiết kiệm handshake và tài nguyên server, quản lý auth/reconnect tập trung.

Q4Stale closure với handler socket là gì? Cách tránh?Middle›

Trả lời: Handler được tạo lúc subscribe (effect deps []) sẽ "đóng băng" giá trị state/prop tại thời điểm đó. Khi sự kiện đến sau, nó vẫn đọc giá trị cũ → bug (vd chỉ hiện tin cuối). Tránh bằng: (1) functional update setX(prev => ...) để luôn có state mới; (2) latest ref — lưu giá trị mới nhất vào ref và đọc ref.current trong handler khi cần nhiều giá trị.

⚠️ Bẫy: thêm state vào deps của effect subscribe sẽ làm off/on liên tục, dễ miss event — nên dùng functional update/ref thay vì re-subscribe.

Q5Thiết kế custom useSocketEvent như thế nào để an toàn?Middle›

Trả lời: Hook nhận event và handler. Lưu handler vào một ref và cập nhật ref mỗi render (để luôn gọi bản mới nhất). Subscribe trong effect chỉ phụ thuộc [socket, event], listener gọi ref.current(...args); cleanup gọi socket.off(event, listener). Như vậy listener ổn định (không re-subscribe mỗi render) nhưng logic luôn cập nhật, và luôn gỡ đúng listener.

Q6Sau khi mạng chập chờn và socket reconnect, làm sao đồng bộ lại state?Senior›

Trả lời: Đăng ký logic resync vào handler connect (bắn cả lần đầu và mỗi reconnect): tải lại snapshot đầy đủ qua REST/emit rồi mới tiếp tục áp delta. Trong lúc offline hiện banner và khóa nút emit. Chú ý khe hở "mù": delta đến trong lúc fetch snapshot có thể bị ghi đè — chống bằng sequence number (bỏ qua delta cũ hơn snapshot) hoặc server gửi lại event đã miss theo lastSeq.

⚠️ Bẫy: chỉ resync ở lần mount đầu (deps []) mà quên rằng connect còn bắn lại mỗi reconnect.

Q7UI nhận hàng trăm update/giây và bị giật. Bạn tối ưu thế nào?Senior›

Trả lời: Phối hợp nhiều kỹ thuật: throttle các số liệu liên tục (ghi vào ref, render mỗi N ms); batching nhiều delta thành một render mỗi animation frame; virtualization danh sách dài để chỉ render dòng trong viewport; React.memo + key id ổn định để chỉ dòng thay đổi mới re-render; chia state nhỏ để re-render khu trú. Đo bằng Profiler để biết nút thắt thật sự trước khi tối ưu.

Q8Hiển thị danh sách hàng nghìn dòng cập nhật liên tục — chiến lược?Senior›

Trả lời: Virtualize (react-window/react-virtuoso) để DOM chỉ giữ ~chục dòng. Lưu dữ liệu dưới dạng map keyed theo id để patch O(1) thay vì map cả mảng. Mỗi dòng là component memo nhận đúng object của nó. Batch cập nhật theo frame để tránh layout thrash. Dùng key id ổn định để tránh React gán nhầm state khi danh sách sắp xếp lại.

Q9Triển khai Optimistic UI cho gửi tin nhắn ra sao?Middle›

Trả lời: Khi gửi, tạo tempId và thêm ngay một tin trạng thái pending vào danh sách. Emit kèm tempId và chờ ack (callback của emit): ack ok → đổi tin sang sent và gán id thật; ack lỗi → đổi failed kèm nút gửi lại (hoặc rollback). Nhờ đó UI phản hồi tức thì mà vẫn phản ánh đúng kết quả thật.

Q10Với optimistic + server broadcast, làm sao tránh tin nhắn nhân đôi?Senior›

Trả lời: Server echo lại tempId trong broadcast. Khi nhận chat:message, tìm trong danh sách theo tempId hoặc id: nếu đã tồn tại (chính là tin lạc quan của mình) thì thay thế/cập nhật trạng thái thay vì thêm mới; nếu chưa có (tin của người khác) thì append. Đây là dedupe idempotent — áp dụng broadcast nhiều lần vẫn cho cùng kết quả.

⚠️ Bẫy: vừa append tin lạc quan vừa append tin từ broadcast → mỗi tin của mình hiện 2 lần.

Q11Vì sao snapshot + delta tốt hơn chỉ dùng delta cho realtime view?Middle›

Trả lời: Delta chỉ mô tả thay đổi; nếu client vào trễ hoặc miss event thì sẽ thiếu trạng thái nền (vd các cuộc gọi đã có sẵn trong hàng đợi từ trước). Lấy snapshot đầy đủ một lần làm "điểm xuất phát" rồi áp delta đảm bảo UI luôn có nền đúng. Cũng giúp resync sau reconnect: chỉ cần tải lại snapshot.

Q12Khi nào dùng throttle, khi nào debounce trong realtime UI?Junior›

Trả lời: Throttle đảm bảo chạy đều đặn tối đa một lần mỗi khoảng (vd cập nhật KPI/đồng hồ mỗi giây) — luôn có cập nhật mới nhất trong khi giới hạn tần suất. Debounce chỉ chạy sau khi sự kiện ngừng dồn dập một khoảng (vd ô tìm kiếm, indicator "đang gõ", auto-save) — gom burst thành một lần xử lý cuối. Realtime metric → throttle; input người dùng → debounce.
