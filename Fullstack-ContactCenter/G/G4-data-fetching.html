Data Fetching & State Management

Lấy dữ liệu đúng cách (React Query/SWR), quản lý server state vs client state, và optimistic update cho trải nghiệm realtime mượt.

🎯 Học xong chương này bạn sẽ

• Gọi API đúng cách với fetch/axios, biết khác biệt và cách hủy request bằng AbortController.

• Nhận diện và sửa các pitfall kinh điển khi fetch trong useEffect: race condition, double fetch, request waterfall, thiếu cleanup.

• Hiểu vì sao React Query / SWR thay thế phần lớn useEffect + useState: cache, stale-while-revalidate, dedup, refetch nền, mutation & invalidation.

• Quản lý đầy đủ các trạng thái UI: loading / error / empty / success và làm optimistic update kèm rollback.

• Phân biệt server state với client/UI state, và chọn đúng công cụ state management (Context, Redux, Zustand, Jotai) cho từng loại.

💡 Liên hệ thực tế hệ thống Contact Center

Màn hình của tổng đài viên (agent) là một "bảng điều khiển sống": danh sách hàng đợi (queue), thông tin khách đang gọi, lịch sử ticket, đoạn chat. Dữ liệu này do server làm chủ, thay đổi từng giây và có nhiều màn hình cùng xem. Nếu mỗi component tự fetch trong useEffect, bạn sẽ có request trùng lặp, dữ liệu lệch nhau, và UI giật khi mạng chậm. Đây chính là bài toán mà lớp data-fetching hiện đại sinh ra để giải.

① Fetch & Axios

Trình duyệt cung cấp sẵn fetch — một API dựa trên Promise để gọi HTTP. axios là thư viện bên thứ ba bọc thêm nhiều tiện ích. Hiểu rõ cả hai giúp bạn chọn đúng và trả lời tốt câu hỏi "tại sao team dùng axios".

⚠️ Bẫy lớn nhất của fetch

fetch chỉ reject khi lỗi mạng (mất kết nối, CORS chặn). Một response 404 hay 500 vẫn vào nhánh .then bình thường! Phải tự kiểm tra if (!res.ok) throw .... Quên điều này là lý do số một khiến UI "im lặng nuốt lỗi" — agent thấy danh sách rỗng mà không có thông báo gì.

fetch-client.tsTypeScript
// Bọc fetch thành 1 hàm chuẩn: ném lỗi rõ ràng, tự parse JSON
export async function apiGet<T>(url: string, signal?: AbortSignal): Promise<T> {
  const res = await fetch(url, {
    headers: { 'Authorization': `Bearer ${token}` },
    signal,                       // để hủy được request
  });
  if (!res.ok) {                  // 4xx/5xx KHÔNG tự reject → phải tự ném
    throw new Error(`HTTP ${res.status} khi gọi ${url}`);
  }
  return res.json() as Promise<T>;
}

// Dùng: lấy danh sách cuộc gọi đang chờ trong hàng đợi
const calls = await apiGet<Call[]>('/api/queues/sales/calls');
axios-instance.tsTypeScript
import axios from 'axios';

export const api = axios.create({
  baseURL: '/api',
  timeout: 8000,                  // 8s là tự huỷ → tránh agent chờ vô tận
});

// Interceptor: gắn token vào MỌI request — không lặp code ở từng nơi
api.interceptors.request.use((config) => {
  config.headers.Authorization = `Bearer ${getToken()}`;
  return config;
});

// Interceptor response: token hết hạn → refresh 1 lần rồi thử lại
api.interceptors.response.use(
  (res) => res,
  async (err) => {
    if (err.response?.status === 401 && !err.config._retry) {
      err.config._retry = true;
      await refreshToken();
      return api(err.config);     // phát lại request gốc
    }
    throw err;
  },
);
💡 Chọn cái nào?

Dự án nhỏ, ít endpoint → fetch + một wrapper mỏng là đủ, không thêm dependency. Dự án lớn cần interceptor (gắn token, auto-refresh, log, retry tập trung) → axios tiết kiệm rất nhiều code. Nhưng nhớ: dù chọn gì, ở tầng React bạn vẫn nên đặt nó bên dưới React Query/SWR — fetch/axios chỉ là "transport", còn cache & trạng thái để thư viện lo (mục ③).

② Pitfalls khi fetch trong useEffect

Cách "ngây thơ" mà ai cũng viết lúc đầu: useEffect + useState để gọi API. Nó chạy được nhưng ẩn chứa hàng loạt cạm bẫy. Hiểu chúng là nền tảng để hiểu vì sao React Query ra đời.

2.1 Race condition (điều kiện tranh chấp)

Người dùng đổi tham số nhanh (đổi hàng đợi từ sales sang support). Request cũ và mới chạy song song; request cũ có thể về sau request mới và ghi đè kết quả → agent thấy dữ liệu của hàng đợi sai.

Chọn "sales"→ fetch A bắt đầu→ Chọn "support"→ fetch B bắt đầu→ B về trước→ A về sau, GHI ĐÈ B ❌
QueuePanel.tsxReact
function QueuePanel({ queueId }: { queueId: string }) {
  const [calls, setCalls] = useState<Call[]>([]);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const ctrl = new AbortController();
    apiGet<Call[]>(`/queues/${queueId}/calls`, ctrl.signal)
      .then(setCalls)
      .catch((e) => {
        if (e.name !== 'AbortError') setError(e.message);
      });

    // CLEANUP: huỷ request cũ khi queueId đổi hoặc component unmount
    return () => ctrl.abort();
  }, [queueId]);   // deps đúng → effect chạy lại khi đổi hàng đợi

  // ...
}
⚠️ Hai cách chống race

(1) AbortController như trên — huỷ hẳn request cũ ở tầng mạng. (2) Cờ "ignore" — biến cục bộ let active = true, trong cleanup gán active = false, chỉ setState khi active. Cách (1) tiết kiệm băng thông hơn vì thật sự cắt request. Cả hai đều phải đặt trong hàm cleanup của effect.

2.2 Thiếu dependency & stale closure

Bỏ queueId khỏi mảng deps ([]) thì effect chỉ chạy một lần — đổi hàng đợi nhưng dữ liệu không cập nhật. Ngược lại, để nguyên một object/hàm trong deps mà nó tạo mới mỗi render thì effect chạy mỗi render → fetch liên tục. Quy tắc: đưa đủ giá trị thực sự dùng vào deps, và bọc hàm bằng useCallback, object bằng useMemo nếu cần (xem G2).

2.3 Double fetch trong StrictMode

React 18 StrictMode ở môi trường dev cố tình mount → unmount → mount lại component để lộ các effect chưa cleanup đúng. Hệ quả: bạn thấy request chạy hai lần. Đây không phải bug của bạn nếu cleanup đã đúng (request thừa bị abort). Nhưng nếu không cleanup, double fetch là dấu hiệu cảnh báo. Ở production StrictMode không nhân đôi.

2.4 Request waterfall (thác nước)

Lỗi hiệu năng kinh điển: component A fetch xong mới render B, B fetch xong mới render C — các request nối đuôi tuần tự dù lẽ ra độc lập. Tổng thời gian = tổng từng request thay vì request lâu nhất.

Waterfall: agent (300ms) → ticket (300ms) → chat (300ms) = 900ms
Song song: Promise.all([agent, ticket, chat]) = ~300ms ✅
💡 Cách phá waterfall

Gọi các request độc lập song song bằng Promise.all, hoặc nâng việc fetch lên cha rồi truyền xuống, hoặc dùng prefetch của React Query. Với router hiện đại (loader của React Router/Next.js) có thể fetch song song ngay ở tầng route trước khi render.

🐛 Tổng kết: vì sao useEffect-fetch không đủ

Bạn phải tự tay: quản lý loading/error, chống race, cleanup, chống double fetch, dedup request trùng, cache giữa các component, refetch khi quay lại tab... Lặp đi lặp lại ở mọi màn hình. Đó chính xác là phần việc mà React Query/SWR đã giải sẵn.

③ React Query / SWR

TanStack Query (React Query) và SWR là hai thư viện server-state management. Ý tưởng cốt lõi: bạn khai báo "dữ liệu này lấy từ đâu, key là gì", thư viện lo cache, đồng bộ, làm mới. Bạn không còn viết useEffect fetch thủ công nữa.

3.1 Các khái niệm trụ cột

🔑 Query key

Định danh duy nhất cho một mẩu dữ liệu, vd ['calls', queueId]. Cùng key → dùng chung cache; key đổi → tự fetch lại.

♻️ Stale-while-revalidate

Trả ngay dữ liệu cũ (stale) cho UI hiển thị tức thì, đồng thời fetch nền để làm mới. Đúng tên gọi của SWR.

🔁 Dedup

Nhiều component cùng yêu cầu một key trong khoảng ngắn → chỉ một request mạng thật được gửi.

⏱️ staleTime / gcTime

staleTime: bao lâu coi dữ liệu là "tươi" (không refetch). gcTime: bao lâu giữ cache khi không ai dùng rồi mới dọn.

🪟 Refetch nền

Tự fetch lại khi cửa sổ được focus lại, khi mạng kết nối lại, hoặc theo refetchInterval (polling).

✍️ Mutation + invalidation

Ghi dữ liệu (POST/PUT/DELETE) bằng useMutation, xong invalidate các query liên quan để chúng tự fetch lại.

3.2 useQuery — đọc dữ liệu

useCalls.tsReact Query
import { useQuery } from '@tanstack/react-query';

function useQueueCalls(queueId: string) {
  return useQuery({
    queryKey: ['calls', queueId],          // định danh cache
    queryFn: ({ signal }) =>                  // signal có sẵn để abort
      apiGet<Call[]>(`/queues/${queueId}/calls`, signal),
    staleTime: 5_000,                      // 5s coi là tươi
    refetchOnWindowFocus: true,           // agent quay lại tab → làm mới
  });
}

// Trong component — thay cho 30 dòng useEffect/useState
function QueuePanel({ queueId }: { queueId: string }) {
  const { data, isLoading, isError, error, isFetching } = useQueueCalls(queueId);
  if (isLoading) return <Skeleton />;
  if (isError)   return <ErrorBox msg={error.message} />;
  return <CallList calls={data} refreshing={isFetching} />;
}
ℹ️ isLoading vs isFetching

isLoading = lần đầu chưa có dữ liệu nào (hiện skeleton). isFetching = đang có request chạy (kể cả refetch nền khi đã có dữ liệu cũ). Dùng isFetching để hiện một spinner nhỏ "đang đồng bộ" mà không che mất danh sách hiện có — trải nghiệm mượt hơn hẳn.

3.3 useMutation — ghi dữ liệu & invalidation

useAssignTicket.tsReact Query
import { useMutation, useQueryClient } from '@tanstack/react-query';

function useAssignTicket() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: ({ ticketId, agentId }) =>
      api.post(`/tickets/${ticketId}/assign`, { agentId }),

    onSuccess: () => {
      // Báo cho cache: 2 danh sách này đã "cũ" → tự fetch lại
      qc.invalidateQueries({ queryKey: ['tickets'] });
      qc.invalidateQueries({ queryKey: ['agent-workload'] });
    },
  });
}

// Dùng:
const assign = useAssignTicket();
<button onClick={() => assign.mutate({ ticketId, agentId })}
  disabled={assign.isPending}>Gán ticket</button>
💡 Invalidation là "nguồn sự thật" duy nhất

Thay vì tự tay setState để chèn ticket mới vào danh sách (dễ lệch với server), bạn chỉ cần invalidate và để query tự lấy lại bản chuẩn từ server. Code ít hơn, dữ liệu luôn khớp DB. Khi cần phản hồi tức thì hơn nữa, kết hợp optimistic update (mục ④).

④ Loading, error, empty & optimistic update

Một màn hình "đúng" phải xử lý bốn trạng thái, không chỉ "thành công". Bỏ sót một trạng thái là cách nhanh nhất để UI trông kém chuyên nghiệp.

⏳ Loading

Ưu tiên skeleton (khung xương) thay vì spinner toàn trang — giữ bố cục ổn định, đỡ giật layout.

❌ Error

Thông báo rõ ràng + nút "Thử lại". Đừng để màn hình trắng. Log lỗi để theo dõi.

📭 Empty

"Hàng đợi đang trống — chưa có cuộc gọi nào chờ." Khác hẳn loading; đừng nhầm hai cái.

✅ Success

Dữ liệu thật. Kèm chỉ báo nhỏ khi đang refetch nền để người dùng biết hệ thống vẫn sống.

🐛 Lỗi hay gặp: nhầm empty với loading

Viết if (!data) return <Loading/> rồi khi server trả mảng rỗng [], data vẫn là mảng (truthy) nhưng độ dài 0 → nếu không có nhánh empty riêng, UI hiện danh sách trống không lời giải thích. Luôn phân biệt isLoading với data.length === 0.

4.1 Optimistic update & rollback

Optimistic update = cập nhật UI ngay lập tức theo kết quả mong đợi trước khi server trả lời, để cảm giác tức thì. Nếu server báo lỗi, ta rollback (hoàn tác) về trạng thái cũ. Cực kỳ quan trọng trong Contact Center: agent bấm "Kết thúc cuộc gọi" phải thấy phản hồi ngay, không chờ round-trip mạng.

Agent bấm "Resolve ticket"→ UI đổi sang Resolved NGAY→ Gửi request nền→ OK: giữ nguyên ✅
Lỗi: rollback về Open + báo "Không lưu được, thử lại"
useResolveTicket.tsReact Query
function useResolveTicket() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (id: string) => api.post(`/tickets/${id}/resolve`),

    // 1) Trước khi gửi: cập nhật cache lạc quan
    onMutate: async (id) => {
      await qc.cancelQueries({ queryKey: ['tickets'] }); // tránh refetch đè lên
      const prev = qc.getQueryData<Ticket[]>(['tickets']);
      qc.setQueryData<Ticket[]>(['tickets'], (old) =>
        old?.map((t) => t.id === id ? { ...t, status: 'resolved' } : t));
      return { prev };               // lưu lại để rollback
    },

    // 2) Lỗi: trả cache về như cũ
    onError: (_e, _id, ctx) => {
      if (ctx?.prev) qc.setQueryData(['tickets'], ctx.prev);
      toast('Không lưu được, đã hoàn tác');
    },

    // 3) Dù thành/bại: đồng bộ lại với server cho chắc
    onSettled: () => qc.invalidateQueries({ queryKey: ['tickets'] }),
  });
}
⚠️ Optimistic phải đi kèm 3 thứ

(1) Snapshot trạng thái cũ trước khi đổi. (2) Rollback trong onError. (3) Re-sync trong onSettled (invalidate) để chắc chắn cuối cùng UI khớp server. Thiếu rollback = dữ liệu "ma" còn lại khi lỗi; thiếu re-sync = UI có thể lệch nhẹ với DB.

⑤ State management

Không phải mọi state đều cần một thư viện. Câu hỏi quan trọng là: state này ai cần biết và sống ở đâu. Đi từ đơn giản đến phức tạp, chỉ "leo thang" khi thật sự cần.

⚠️ Bẫy Context: re-render hàng loạt

Context không tối ưu re-render. Khi giá trị Context đổi, mọi component đang useContext đều render lại, kể cả phần không dùng tới giá trị đó. Nhồi một object lớn hay đổi liên tục (vd state realtime của cuộc gọi) vào một Context duy nhất sẽ gây giật cả cây. Giải pháp: tách Context nhỏ theo mối quan tâm, hoặc dùng Zustand/Jotai vốn cho phép chọn (select) đúng phần cần.

🐻 Zustand

Store dạng hook, không cần Provider bao quanh. useStore(s => s.x) chỉ render lại khi x đổi. Ít boilerplate.

⚛️ Jotai

State theo atom nhỏ, bottom-up. Hợp khi state phân mảnh, mỗi mẩu độc lập, muốn tránh re-render rộng.

🧰 Redux Toolkit

Có quy ước rõ (slice, reducer, middleware), devtools time-travel mạnh. Đáng dùng cho team lớn, logic nhiều nhánh.

uiStore.tsZustand
import { create } from 'zustand';

type UiState = {
  activePanel: 'queue' | 'ticket' | 'chat';
  setPanel: (p: UiState['activePanel']) => void;
};

export const useUi = create<UiState>((set) => ({
  activePanel: 'queue',
  setPanel: (p) => set({ activePanel: p }),
}));

// Chỉ render lại khi activePanel đổi — không phải toàn store
const panel = useUi((s) => s.activePanel);
💡 Nguyên tắc vàng

Bắt đầu với useState cục bộ. Cần chia sẻ thì lift up. Sâu nhiều tầng và ít đổi thì Context. Cần global thật sự thì Zustand/Jotai. Chỉ chọn Redux khi độ phức tạp logic (chứ không phải "dữ liệu nhiều") biện minh cho boilerplate của nó. Quan trọng nhất: dữ liệu từ server thì đừng nhét vào bất kỳ store nào ở trên — để React Query lo (mục ⑥).

⑥ Server state vs Client state

Đây là khái niệm quan trọng nhất của cả chương, và là câu hỏi phỏng vấn phân loại trình độ. Lẫn lộn hai loại state này là gốc rễ của hầu hết bug dữ liệu trên frontend.

🐛 Anti-pattern phổ biến nhất

Nhét dữ liệu server vào Redux: dispatch(fetchTickets()) rồi tự viết reducer lưu loading/error/data. Bạn đang tự xây lại React Query bằng tay — nửa vời, đầy bug đồng bộ. Server state có vấn đề riêng (stale, cache, refetch) mà các thư viện client-state không sinh ra để giải. Hãy tách bạch: React Query cho dữ liệu server, store nhẹ cho UI state.

Server state → React Query Client/UI state → Zustand / useState Realtime (WebSocket) → đẩy vào cache React Query
💡 Realtime trong Contact Center khớp mô hình này thế nào

Khi WebSocket báo "có cuộc gọi mới vào hàng đợi", bạn không tạo store riêng — mà ghi thẳng vào cache của React Query: queryClient.setQueryData(['calls', queueId], updater) hoặc invalidateQueries. Như vậy realtime và HTTP cùng dùng một nguồn dữ liệu, UI không bị "hai bản sự thật". Chi tiết ở G6 · Realtime UI.

⚠️ Lỗi thường gặp & Best practices

🚫 Quên res.ok với fetch

404/500 lọt vào .then, lỗi bị nuốt. Luôn kiểm tra status hoặc dùng wrapper ném lỗi.

🚫 Không cleanup effect

Race condition + setState trên component đã unmount. Luôn abort trong cleanup.

🚫 Tự build cache trong Redux

Tái phát minh React Query. Tách server state ra thư viện chuyên dụng.

🚫 Nhầm empty với loading

Mảng rỗng vẫn truthy. Phân biệt isLoading và length === 0.

🚫 Request waterfall

Fetch nối đuôi tuần tự. Dùng Promise.all/prefetch cho request độc lập.

🚫 Optimistic không rollback

Lỗi mà UI giữ dữ liệu sai. Luôn snapshot + rollback + re-sync.

🚫 Object/hàm trong deps

Tạo mới mỗi render → fetch vô hạn. Bọc useMemo/useCallback.

✅ staleTime hợp lý

Đặt theo độ "tươi" cần thiết: hàng đợi vài giây, profile khách vài phút.

🧪 Bài tập

🧪 Bài 1 — Chống race condition

Component AgentDetail nhận prop agentId và fetch hồ sơ agent trong useEffect. Người dùng đổi agent rất nhanh. Hãy viết effect chống race bằng cả hai cách (AbortController và cờ ignore) và giải thích cách nào tốt hơn, vì sao.

Gợi ý

Cách cờ: let active = true; trong .then chỉ setState khi active; cleanup active = false. Cách abort: tạo AbortController, truyền signal vào fetch, cleanup gọi ctrl.abort() và bỏ qua AbortError. AbortController tốt hơn vì thật sự huỷ request mạng, tiết kiệm băng thông và tránh xử lý phản hồi thừa — quan trọng khi agent thao tác liên tục.

🧪 Bài 2 — Optimistic resolve ticket

Viết một useMutation để "resolve" một ticket với optimistic update đầy đủ: cập nhật cache ngay, rollback khi lỗi, và re-sync khi xong. Liệt kê 3 callback bạn cần và việc của từng cái.

Gợi ý

onMutate: cancelQueries → snapshot prev bằng getQueryData → cập nhật lạc quan bằng setQueryData → trả { prev }. onError: setQueryData(key, ctx.prev) để hoàn tác + toast. onSettled: invalidateQueries để chốt lại với server. Thiếu bất kỳ bước nào sẽ gây dữ liệu lệch khi mạng lỗi.

🧪 Bài 3 — Phân loại state

Cho các state sau trên màn hình agent: (a) danh sách cuộc gọi đang chờ, (b) panel đang được chọn, (c) hồ sơ khách đang gọi, (d) nội dung tin nhắn đang soạn, (e) trạng thái online/offline của agent (lưu ở server). Phân loại server vs client và chọn công cụ cho từng cái.

Gợi ý

Server state → React Query: (a) danh sách cuộc gọi, (c) hồ sơ khách, (e) trạng thái online/offline (server làm chủ; bấm đổi = mutation optimistic). Client/UI state → useState/Zustand: (b) panel đang chọn (UI thuần), (d) nội dung đang soạn (cục bộ, mất khi gửi). Mấu chốt: hỏi "ai là nguồn sự thật?".

Ngân hàng câu hỏi phỏng vấn

Data fetching & state — chủ đề "lọc" ứng viên frontend rất rõ.

Q1Khác biệt giữa fetch và axios?Junior›

Trả lời: fetch có sẵn, dựa trên Promise, nhưng phải tự gọi res.json() và không tự reject với 4xx/5xx — phải kiểm tra res.ok. axios là thư viện ngoài: tự parse JSON (res.data), tự reject khi status ≥ 400, có timeout, interceptor (gắn token, refresh), hỗ trợ progress. App lớn dùng axios để có interceptor tập trung; app nhỏ thì fetch + wrapper là đủ.

⚠️ Bẫy: nói "fetch tự ném lỗi với 404" là sai.

Q2React Query lợi gì so với useEffect + useState tự fetch?Middle›

Trả lời: Nó giải sẵn toàn bộ phần khó của server state: cache chia sẻ giữa component, dedup request trùng, stale-while-revalidate, refetch nền khi focus/reconnect, chống race & cleanup, quản lý loading/error/empty, mutation + invalidation, optimistic update. Với useEffect bạn phải tự viết lại tất cả ở mọi màn hình, dễ thiếu sót. React Query biến ~30 dòng thủ công thành một hook khai báo, giảm bug và code lặp.

Q3Server state và client state khác nhau thế nào? Cho ví dụ.Middle›

Trả lời: Server state do server/DB làm chủ, bất đồng bộ, có thể cũ, người khác cũng đổi được — vd danh sách ticket, hồ sơ khách, hàng đợi. Vấn đề của nó là cache/đồng bộ/làm mới → dùng React Query. Client/UI state do trình duyệt tạo, tức thời, chỉ session này biết — vd tab đang mở, dropdown, nội dung đang gõ, theme → dùng useState/Zustand. Tách bạch hai loại tránh được hầu hết bug đồng bộ.

⚠️ Bẫy: gộp dữ liệu server vào Redux là tự xây lại React Query nửa vời.

Q4Optimistic update là gì? Triển khai an toàn ra sao?Middle›

Trả lời: Là cập nhật UI ngay theo kết quả mong đợi trước khi server trả lời, để cảm giác tức thì. An toàn cần 3 bước: onMutate — huỷ query đang chạy, snapshot dữ liệu cũ, cập nhật cache lạc quan; onError — rollback về snapshot + báo lỗi; onSettled — invalidate để đồng bộ lại với server. Rất hợp cho thao tác agent như resolve ticket, kết thúc cuộc gọi.

Q5Cache invalidation là gì? Vì sao nói nó là một trong những bài toán khó?Senior›

Trả lời: Invalidation là đánh dấu dữ liệu cache đã "cũ" để được fetch lại — thường sau một mutation. Trong React Query làm bằng invalidateQueries({ queryKey }). Khó ở chỗ: phải biết mutation này ảnh hưởng những key nào (gán ticket có thể đụng cả danh sách ticket lẫn workload của agent); invalidate quá rộng gây refetch thừa, quá hẹp gây dữ liệu lệch. Thiết kế query key có cấu trúc tốt giúp invalidate chính xác.

Q6Race condition khi fetch trong useEffect là gì? Cách xử lý?Middle›

Trả lời: Khi tham số đổi nhanh, request cũ và mới chạy song song và request cũ có thể về sau, ghi đè kết quả mới → UI hiển thị dữ liệu sai. Xử lý: huỷ request cũ bằng AbortController (truyền signal, gọi abort() trong cleanup) hoặc dùng cờ ignore để bỏ qua phản hồi cũ. AbortController tốt hơn vì cắt request ở tầng mạng. React Query lo việc này tự động qua query key.

Q7Request waterfall là gì? Làm sao tránh?Middle›

Trả lời: Là các request độc lập bị chạy nối đuôi tuần tự (A xong mới B, B xong mới C) khiến tổng thời gian = tổng các request thay vì request lâu nhất. Thường do component con chỉ fetch sau khi cha render xong. Tránh bằng: gọi song song với Promise.all, nâng fetch lên cha, prefetch của React Query, hoặc fetch ở tầng route loader (React Router/Next.js) trước khi render.

Q8Khi nào nên dùng Redux thay vì Context hay Zustand?Senior›

Trả lời: Chọn theo độ phức tạp logic, không phải lượng dữ liệu. Redux Toolkit đáng dùng khi: state global lớn với nhiều luồng tương tác phức tạp, cần devtools time-travel, middleware (logging, side-effect), quy ước chặt cho team đông. Nếu chỉ cần global UI state nhẹ → Zustand/Jotai ít boilerplate hơn. Dữ liệu ít đổi nhiều nơi đọc → Context. Và dữ liệu server thì không để vào Redux mà dùng React Query.

⚠️ Bẫy: chọn Redux chỉ vì "dữ liệu nhiều" — sai tiêu chí; tiêu chí là độ phức tạp logic.

Q9Vì sao Context có thể gây vấn đề hiệu năng? Khắc phục thế nào?Senior›

Trả lời: Khi value của Context đổi, mọi component useContext đều re-render, không có cơ chế chọn lọc như selector. Nhồi object lớn/đổi liên tục vào một Context gây render cả cây. Khắc phục: tách Context theo mối quan tâm (giá trị ít đổi tách riêng giá trị hay đổi); memo hoá value provider; hoặc dùng Zustand/Jotai cho phép select đúng phần cần để chỉ render component liên quan.

Q10staleTime và gcTime khác nhau ra sao? Đặt thế nào cho hợp?Senior›

Trả lời: staleTime = bao lâu dữ liệu được coi là "tươi" — trong thời gian này React Query không refetch khi component dùng lại. gcTime (trước là cacheTime) = bao lâu giữ cache trong bộ nhớ sau khi không còn observer nào dùng, rồi mới dọn. Đặt staleTime theo độ tươi cần: hàng đợi cuộc gọi vài giây (thay đổi nhanh), hồ sơ khách vài phút (ít đổi). gcTime dài hơn để quay lại màn hình vẫn còn cache mượt.

Q11Trong app realtime (WebSocket), bạn lưu dữ liệu server đẩy về ở đâu?Senior›

Trả lời: Nên ghi thẳng vào cache của React Query (queryClient.setQueryData(key, updater)) hoặc invalidateQueries khi nhận sự kiện WebSocket, thay vì tạo một store riêng. Như vậy dữ liệu từ HTTP và từ realtime cùng một nguồn, UI không bị "hai bản sự thật". Vd: có cuộc gọi mới vào hàng đợi → cập nhật key ['calls', queueId]. Chi tiết thêm ở chương Realtime UI.

Q12Phân biệt isLoading và isFetching của React Query?Junior›

Trả lời: isLoading = true khi query chưa có dữ liệu nào và đang chạy lần đầu — lúc này hiện skeleton/loading toàn phần. isFetching = true bất cứ khi nào có request đang chạy, kể cả refetch nền khi đã có dữ liệu cũ — dùng để hiện một chỉ báo nhỏ "đang đồng bộ" mà không che danh sách hiện có. Phân biệt đúng giúp UI mượt, không nhấp nháy mỗi lần refetch.
