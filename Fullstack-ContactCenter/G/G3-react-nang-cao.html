React nâng cao & Performance

Tối ưu re-render, code splitting, error boundary và các mẫu tổ chức component — để Dashboard realtime nhiều dữ liệu vẫn mượt.

🎯 Học xong chương này bạn sẽ

• Liệt kê chính xác những nguyên nhân khiến một component re-render, và phân biệt re-render "cần thiết" với re-render "thừa".

• Dùng đúng React.memo, useMemo, useCallback để ổn định tham chiếu — và biết khi nào chúng vô ích hoặc có hại.

• Tối ưu Context (tách context, memoize value, đẩy state xuống) để tránh re-render lan toả cả cây.

• Tách bundle bằng React.lazy + Suspense, dựng Error Boundary để một widget hỏng không sập cả app.

• Nắm các render patterns (composition, children, render props, HOC, compound) và cách React reconciliation dùng key để diff.

• Đọc được flamegraph trong React DevTools Profiler để định vị component "nóng".

💡 Liên hệ hệ thống Contact Center

Một màn hình giám sát tổng đài thường có: danh sách hàng đợi cuộc gọi cập nhật mỗi giây, bảng trạng thái agent, ô chat nhiều cửa sổ, và biểu đồ KPI realtime. Mỗi event WebSocket (cuộc gọi mới, agent đổi trạng thái, tin nhắn đến) có thể kích hoạt setState. Nếu không tối ưu, một tin nhắn chat sẽ vẽ lại cả 300 dòng hàng đợi → UI giật, quạt CPU rít. Chương này dạy bạn cô lập re-render để chỉ phần thực sự đổi mới được vẽ lại.

① Nguyên nhân re-render

Re-render nghĩa là React gọi lại hàm component để tính ra cây phần tử mới (virtual DOM), rồi đem so sánh với cây cũ. Quan trọng: re-render KHÔNG đồng nghĩa với cập nhật DOM. React có thể chạy lại hàm của bạn mà cuối cùng không sửa một pixel nào trên màn hình — nhưng việc chạy lại đó vẫn tốn CPU, tạo rác cho GC, và có thể lan xuống con.

Một component sẽ re-render khi một trong bốn điều sau xảy ra:

🔄 State đổi

Gọi setState / setter của useState / dispatch của useReducer với giá trị mới.

📥 Props đổi

Cha truyền props mới xuống (theo nghĩa tham chiếu/giá trị khác sau khi cha re-render).

👆 Cha re-render

Khi cha render lại, mọi con mặc định render lại — kể cả khi props không đổi.

🌐 Context đổi

Mọi component useContext(C) sẽ re-render khi value của Provider C thay đổi tham chiếu.

⚠️ Hiểu lầm kinh điển

"Truyền prop mới xuống con thì con mới re-render." Sai. Mặc định, khi cha render lại thì tất cả con render lại, bất kể props có đổi hay không. React.memo mới là thứ chặn việc đó dựa trên so sánh props. Không có memo, prop "y nguyên" cũng không cứu được con khỏi việc render lại theo cha.

Re-render "thừa" trông như thế nào?

Trong Dashboard tổng đài, một component cha giữ nhiều mảnh state. Khi một mảnh nhỏ đổi (ví dụ ô tìm kiếm), cả cây render lại:

Dashboard.jsxReact
function Dashboard() {
  const [search, setSearch] = useState('');
  const [queue, setQueue]   = useState([]);   // 300 cuộc gọi chờ

  // Mỗi lần gõ phím vào ô search → Dashboard re-render →
  // <QueueTable> (300 dòng) cũng render lại dù queue KHÔNG đổi.
  return (
    <div>
      <SearchBox value={search} onChange={setSearch} />
      <QueueTable rows={queue} />        // 😱 nạn nhân vô tội
      <AgentPanel />
    </div>
  );
}

Đây là re-render thừa: queue không đổi nhưng QueueTable vẫn chạy lại toàn bộ. Ba hướng xử lý sẽ đi qua trong các mục tiếp theo: (1) bọc con bằng React.memo; (2) đẩy state xuống thấp nhất nơi nó được dùng; (3) dùng composition để con được truyền dạng children — khi đó cha re-render mà children giữ nguyên tham chiếu thì con không phải tính lại.

💡 Nguyên tắc đầu tiên: đo trước, tối ưu sau

Đừng rải memo/useCallback khắp nơi theo cảm tính. Mở React DevTools → Profiler, bấm record, thao tác, rồi đọc flamegraph: component nào màu vàng/cam và render lại nhiều lần là điểm nóng. Bật "Highlight updates when components render" để thấy đường viền nhấp nháy quanh phần đang vẽ lại — nếu cả màn hình nháy khi bạn chỉ gõ chat, đó là dấu hiệu re-render lan toả.

② React.memo & memoization

React.memo là một Higher-Order Component bọc quanh component và nói với React: "nếu props lần này so với lần trước giống nhau (so sánh nông), hãy bỏ qua render và tái dùng kết quả cũ."

QueueRow.jsxReact
const QueueRow = React.memo(function QueueRow({ call, onAssign }) {
  // Chỉ render lại khi `call` hoặc `onAssign` đổi tham chiếu
  return (
    <tr>
      <td>{call.phone}</td>
      <td>{call.waitSec}s</td>
      <td><button onClick={() => onAssign(call.id)}>Nhận</button></td>
    </tr>
  );
});

So sánh nông (shallow compare) nghĩa là React duyệt từng key của props và so bằng Object.is: với số/chuỗi/boolean là so giá trị; với object/array/function là so tham chiếu. Đây là mấu chốt khiến memo thường "không ăn": nếu cha tạo object/array/hàm mới mỗi lần render, tham chiếu luôn khác → memo luôn cho qua.

useMemo & useCallback — ổn định tham chiếu

Hai hook này tồn tại để giữ cùng một tham chiếu qua các lần render, miễn là dependency không đổi:

HookMemoize cái gìDùng khi
useMemo(fn, deps)Giá trị trả về của fn()Tính toán nặng (lọc/sắp xếp 1000 dòng), hoặc tạo object/array cần truyền cho con có memo
useCallback(fn, deps)Bản thân hàm (≡ useMemo(()=>fn, deps))Truyền callback cho con có memo, hoặc làm dep của useEffect
QueueTable.jsxReact
function QueueTable({ calls, filter, onAssign }) {
  // 1) Lọc + sắp xếp nặng → chỉ tính lại khi calls/filter đổi
  const visible = useMemo(() =>
    calls
      .filter(c => c.status === filter)
      .sort((a, b) => b.waitSec - a.waitSec),
    [calls, filter]
  );

  // 2) Hàm ổn định → QueueRow (có React.memo) không bị render oan
  const handleAssign = useCallback((id) => {
    socket.emit('assign', { id, agentId: me.id });
  }, [me.id]);

  return (
    <tbody>
      {visible.map(c => (
        <QueueRow key={c.id} call={c} onAssign={handleAssign} />
      ))}
    </tbody>
  );
}
🐛 Khi nào React.memo / useCallback có HẠI?

1) Mọi memoization đều tốn chi phí: lưu giá trị cũ + so sánh deps/props mỗi render. Với component nhẹ render lại nhanh, chi phí so sánh có khi đắt hơn chính việc render → tối ưu thành chậm hơn.

2) memo vô dụng nếu props vẫn đổi tham chiếu mỗi lần (truyền inline object/array/hàm mà không memoize). Bạn vừa tốn chi phí so sánh vừa luôn render lại.

3) Nếu component nhận children hay prop luôn đổi (vd timestamp, mảng mới từ server mỗi tick), memo gần như không bao giờ "hit". Composition hoặc đẩy state xuống thường tốt hơn.

💡 React 19 & React Compiler

React Compiler (trước đây gọi "React Forget") tự động chèn memoization lúc build, giúp bạn không phải viết tay useMemo/useCallback trong nhiều trường hợp. Nhưng trong phỏng vấn, bạn vẫn cần hiểu vì sao chúng tồn tại và cơ chế so sánh nông — đó là nền để dùng compiler đúng và debug khi nó không kick in.

③ Tối ưu Context

Context giải bài toán "prop drilling" nhưng mang theo một cạm bẫy hiệu năng lớn: khi value của Provider đổi tham chiếu, MỌI component useContext nó sẽ re-render — kể cả component chỉ dùng một phần nhỏ của value. Context không có cơ chế "selector" để chỉ lấy slice cần thiết.

⚠️ Lỗi value mới mỗi render

Tạo object inline làm value là sai lầm phổ biến nhất — tham chiếu mới mỗi lần Provider render, kéo theo toàn bộ consumer render lại.

CallContext.jsxReact
// ❌ SAI: { user, calls, dispatch } là object MỚI mỗi render
<CallContext.Provider value={{ user, calls, dispatch }}>...</>

// ✅ ĐÚNG: memoize value, chỉ đổi khi dữ liệu thật sự đổi
const value = useMemo(
  () => ({ user, calls, dispatch }),
  [user, calls]   // dispatch của useReducer vốn đã ổn định
);
return <CallContext.Provider value={value}>{children}</CallContext.Provider>;

Tách context theo nhịp thay đổi

Vấn đề sâu hơn: nếu nhồi cả state ít đổi (user đăng nhập) lẫn state đổi liên tục (danh sách cuộc gọi mỗi giây) vào một context, thì mỗi tick cuộc gọi sẽ làm các consumer chỉ cần user cũng render lại. Giải pháp: tách thành nhiều context theo tần suất đổi.

AppContext (1 context to) → tách → AuthContext (hiếm đổi) QueueContext (đổi mỗi giây) UiContext (theme, modal)

Một mẹo nữa: tách state và dispatch thành hai context. Component nào chỉ cần dispatch (gửi hành động) sẽ không render lại khi state đổi, vì dispatch luôn ổn định.

Tách contextMỗi nhịp đổi = 1 context riêngConsumer chỉ render khi đúng slice của nó đổi

💡 Khi nào KHÔNG nên cố cứu Context?

Context hợp cho state ít đổi, đọc rộng: theme, ngôn ngữ, user, quyền. Với state đổi nhanh và cần đọc theo slice (danh sách cuộc gọi realtime), một thư viện store có selector (Zustand, Redux Toolkit) sẽ gọn và nhanh hơn nhiều so với việc nhồi rồi tối ưu Context.

④ Code splitting & lazy

Một SPA tổng đài có nhiều màn hình: dashboard, lịch sử cuộc gọi, báo cáo, cài đặt, trình quay số... Nếu gói tất cả vào một bundle, người dùng phải tải mọi thứ trước khi thấy màn hình đầu tiên — thời gian tải tăng, chỉ số Web Vitals (LCP, TTI) xấu đi. Code splitting chia bundle thành các chunk tải theo nhu cầu.

React cung cấp React.lazy + Suspense. lazy nhận một hàm trả về import() động; Suspense hiển thị fallback trong lúc chunk đang tải.

routes.jsxReact
import { lazy, Suspense } from 'react';

// Mỗi màn hình nặng = 1 chunk riêng, chỉ tải khi điều hướng tới
const Reports  = lazy(() => import('./pages/Reports'));
const Dialer   = lazy(() => import('./pages/Dialer'));

function App() {
  return (
    <Suspense fallback={<PanelSkeleton />}>
      <Routes>
        <Route path="/reports" element={<Reports />} />
        <Route path="/dialer"  element={<Dialer />} />
      </Routes>
    </Suspense>
  );
}

Các mức tách & mẹo thực chiến

  • Tách theo route — phổ biến nhất, ranh giới tự nhiên. Mỗi trang một chunk.
  • Tách theo component nặng — biểu đồ KPI, trình soạn thảo, bản đồ heatmap chỉ tải khi mở.
  • Tách theo thư viện nặng — thư viện chart/PDF dung lượng lớn nên nằm trong chunk lazy riêng.
  • Preload thông minh — khi người dùng hover menu "Báo cáo", gọi trước hàm import để chunk tải nền, lúc bấm vào là tức thì.
⚠️ Suspense fallback và "nhấp nháy"

Nếu chunk tải quá nhanh, fallback hiện rồi biến mất ngay gây nháy khó chịu. Dùng skeleton có độ trễ tối thiểu, hoặc kết hợp startTransition để giữ UI cũ trong lúc tải nội dung mới (xem cơ chế concurrent ở mục ⑥). Luôn bọc lazy component bằng cả Suspense và Error Boundary — vì import() có thể thất bại khi mạng kém.

⑤ Error boundaries

Mặc định, một lỗi JS ném ra trong lúc render sẽ làm React unmount toàn bộ cây — màn hình trắng. Trong tổng đài, một widget biểu đồ lỗi không được phép làm sập cả bảng điều khiển khiến agent mất luôn danh sách cuộc gọi. Error Boundary là component bắt lỗi của cây con bên dưới và hiển thị UI dự phòng.

⚠️ Error Boundary phải là CLASS component

Tính đến hiện tại chưa có hook tương đương cho hai lifecycle getDerivedStateFromError và componentDidCatch, nên Error Boundary bắt buộc viết bằng class (hoặc dùng thư viện như react-error-boundary bọc sẵn).

ErrorBoundary.jsxReact
class ErrorBoundary extends React.Component {
  state = { hasError: false, error: null };

  // Đổi state để render fallback ở lần render tiếp theo
  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  // Tác dụng phụ: log lỗi về Sentry/server
  componentDidCatch(error, info) {
    logToServer({ error: error.message, stack: info.componentStack });
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="widget-error">
          ⚠️ Widget gặp sự cố.
          <button onClick={() => this.setState({ hasError: false })}>Thử lại</button>
        </div>
      );
    }
    return this.props.children;
  }
}

// Mỗi widget bọc boundary riêng → 1 cái hỏng không kéo cả app sập
<ErrorBoundary><KpiChart /></ErrorBoundary>
<ErrorBoundary><QueueTable /></ErrorBoundary>
🐛 Error Boundary KHÔNG bắt loại lỗi nào?

Nó chỉ bắt lỗi xảy ra trong render, trong lifecycle và trong constructor của cây con. Nó không bắt: lỗi trong event handler (dùng try/catch thường), lỗi trong code bất đồng bộ (setTimeout, fetch — dùng catch/then), lỗi khi server-side render, và lỗi ném ra từ chính Error Boundary. Với async, hãy setState cờ lỗi rồi để một render kế tiếp ném ra, hoặc dùng thư viện hỗ trợ.

💡 Đặt boundary ở đâu?

Theo tầng: một boundary "gốc" cho cả app (màn hình lỗi tử tế thay vì trắng trang), và nhiều boundary "cục bộ" bao quanh từng widget độc lập (chart, chat, ticket panel). Càng đặt sâu, phạm vi sập càng nhỏ, agent càng giữ được nhiều chức năng khi một phần lỗi.

⑥ Render patterns

Các mẫu tổ chức component giúp tái sử dụng logic, kiểm soát re-render và làm API component dễ dùng. Dưới đây là các mẫu hay được hỏi, kèm vai trò của chúng trong UI tổng đài.

① Composition & prop children

Thay vì hardcode con bên trong, truyền chúng vào qua children. Điều này không chỉ linh hoạt mà còn là mẹo tối ưu: khi cha re-render, nếu children được tạo ở component cấp trên thì tham chiếu của nó không đổi → React bỏ qua việc vẽ lại phần đó.

composition.jsxReact
// <ExpensiveTree/> được tạo ở App, KHÔNG render lại khi count đổi
function App() {
  return (
    <Counter>
      <ExpensiveQueueTree />   // children — tham chiếu ổn định
    </Counter>
  );
}
function Counter({ children }) {
  const [n, setN] = useState(0);
  return <div onClick={() => setN(n + 1)}>{n}{children}</div>;
}

② Render props

Component nhận một hàm qua prop (thường là children dạng function) và gọi nó với dữ liệu nội bộ. Cho phép chia sẻ logic mà bên dùng tự quyết cách render.

render-props.jsxReact
<AgentPresence agentId={id}>
  {(status) => status === 'online'
    ? <Badge color="green">Sẵn sàng</Badge>
    : <Badge color="red">Bận</Badge>}
</AgentPresence>

③ Higher-Order Component (HOC)

Một hàm nhận component và trả về component "được tăng cường": withAuth(Panel), withWebSocket(Chat). Mạnh nhưng dễ gây "wrapper hell" và khó truy vết props — nay phần lớn được thay bằng custom hooks.

④ Compound components

Một nhóm component phối hợp chia sẻ state ngầm qua context, cho API khai báo gọn gàng — kiểu <Tabs><Tab/></Tabs>:

compound.jsxReact
<CallTabs defaultTab="active">
  <CallTabs.List>
    <CallTabs.Tab id="active">Đang gọi</CallTabs.Tab>
    <CallTabs.Tab id="queue">Hàng đợi</CallTabs.Tab>
  </CallTabs.List>
  <CallTabs.Panel id="active">...</CallTabs.Panel>
</CallTabs>
PatternTái dùng cái gìTrạng thái hiện nay

HOCBọc/chèn props chéoCũ; ưu tiên hooks, trừ vài lib

💡 Render props vs Hooks

Trước hooks, render props/HOC là cách duy nhất chia sẻ logic có state. Hooks làm điều đó mà không thêm cấp component (tránh wrapper hell), không "callback lồng nhau", và dễ kết hợp nhiều logic. Vẫn còn lý do dùng render props khi bạn cần điều khiển vị trí/cách render dựa trên state nội bộ (vd component đo kích thước trả về {width} để bên ngoài tuỳ biến layout).

⑦ Reconciliation & keys

Reconciliation là thuật toán React dùng để so cây phần tử mới với cây cũ và quyết định thay đổi DOM tối thiểu cần làm. Vì so sánh hai cây tổng quát là chậm (O(n³)), React dùng vài heuristic để hạ về ~O(n):

  • Khác loại phần tử → vứt cả cây con cũ, dựng lại từ đầu (vd <div> đổi thành <section>, hay ChatPanel đổi thành CallPanel → unmount/mount, mất state nội bộ).
  • Cùng loại phần tử → giữ DOM node, chỉ cập nhật thuộc tính đổi, rồi đệ quy vào con.
  • Danh sách con → React ghép cặp phần tử cũ/mới theo key.

Tại sao key quan trọng?

key là danh tính ổn định của một phần tử trong danh sách qua các lần render. Nó giúp React biết phần tử nào được giữ, thêm, xoá, hoặc di chuyển — thay vì so theo vị trí (index).

🐛 Đừng dùng index làm key cho danh sách động

Nếu danh sách hàng đợi cuộc gọi thêm/bớt/sắp xếp lại, dùng key={index} khiến React ghép sai cặp: state nội bộ (ô input, checkbox "đã đọc", animation) dính nhầm sang dòng khác sau khi xoá phần tử đầu. Hãy dùng id ổn định từ dữ liệu (call.id). Index chỉ tạm chấp nhận khi danh sách tĩnh, không sắp xếp lại, không thêm/xoá giữa chừng.

keys.jsxReact
// ❌ key=index → xoá dòng đầu làm state lệch toàn bộ
{calls.map((c, i) => <QueueRow key={i} call={c} />)}

// ✅ key=id ổn định → React di chuyển/giữ đúng dòng
{calls.map((c) => <QueueRow key={c.id} call={c} />)}

// 💡 Đổi key để CỐ Ý reset state — vd chuyển sang chat khác,
// muốn xoá hết ô soạn tin/scroll position cũ:
<ChatWindow key={activeConversationId} />

Virtualization cho danh sách dài

Khi danh sách lên tới hàng nghìn dòng (lịch sử cuộc gọi, log tin nhắn), kể cả đã memoize, việc render mọi DOM node vẫn nặng. Virtualization (cuộn ảo) chỉ render những dòng nằm trong viewport cộng một ít đệm, tái dùng node khi cuộn — dùng react-window / @tanstack/react-virtual.

10.000 cuộc gọi→ chỉ render ~20 dòng thấy được→ DOM nhẹ, cuộn 60fps

Profiling với React DevTools

Tab Profiler ghi lại các lần render trong một thao tác. Đọc kết quả theo các chỉ báo:

  • Flamegraph — thanh càng rộng = render càng lâu; màu xám = không render lại lần này.
  • Ranked chart — xếp component theo thời gian render, lộ ngay điểm nóng.
  • "Why did this render?" — bật trong Settings để xem lý do: props đổi, hook đổi, hay cha render.
  • Highlight updates — viền nháy quanh phần đang vẽ lại; nếu cả màn hình nháy khi gõ chat → re-render lan toả cần cô lập.

⚠️ Lỗi thường gặp & Best practices

🚫 Rải memo khắp nơi

Tối ưu mù không đo. Đo bằng Profiler trước; memo chỗ thực sự nóng và render lại nhiều.

🚫 memo + props inline

Bọc memo nhưng truyền {}/[]/hàm inline → tham chiếu luôn đổi, memo vô dụng.

🚫 Context value mới mỗi render

Quên useMemo object value → toàn bộ consumer render lại. Nhồi mọi state vào 1 context.

🚫 Index làm key

Với list động → state nội bộ dính nhầm dòng. Dùng id ổn định từ dữ liệu.

🚫 State đặt quá cao

Một ô search ở cha làm cả cây render. Đẩy state xuống component thấp nhất dùng nó (colocation).

🚫 Lazy không có boundary

import() lỗi mạng làm trắng trang. Luôn bọc Suspense + Error Boundary.

🚫 Quên virtualization

Render 5.000 DOM node "vì đã memo rồi". Memo không cứu chi phí dựng DOM — phải cuộn ảo.

✅ Composition trước

Trước khi memo, thử đẩy state xuống / dùng children — thường giải quyết gọn hơn.

🧪 Bài tập

🧪 Bài 1 — Chặn re-render hàng đợi khi gõ chat

Một Dashboard giữ state chatDraft (ô soạn tin) và queue (300 dòng). Mỗi ký tự gõ vào ô chat làm cả QueueTable render lại. Hãy nêu ba cách độc lập để chặn, sắp theo thứ tự ưu tiên.

Gợi ý

(1) Colocation: đẩy chatDraft xuống chính ChatBox để Dashboard không render khi gõ — gọn nhất, không cần memo. (2) Composition: truyền <QueueTable/> dưới dạng children từ cấp trên để tham chiếu ổn định. (3) React.memo bọc QueueTable, đồng thời memoize props (useMemo cho mảng rows, useCallback cho handler). Luôn đo bằng Profiler trước/sau.

🧪 Bài 2 — Vì sao React.memo "không ăn"?

Đồng nghiệp bọc memo cho <QueueRow onAssign={() => assign(c.id)} style={{padding:8}} /> nhưng nó vẫn render lại mỗi lần. Chẩn đoán nguyên nhân và sửa.

Gợi ý

Cả onAssign (hàm inline) và style (object inline) tạo tham chiếu mới mỗi render ở cha → so sánh nông luôn "khác" → memo không bao giờ hit, lại tốn thêm chi phí so sánh. Sửa: dùng useCallback cho handler (truyền id qua tham số/closure ổn định), đưa style ra hằng số ngoài render hoặc useMemo.

🧪 Bài 3 — Tách Context cho dữ liệu realtime

Hiện có một AppContext chứa { user, queue, theme }. queue cập nhật mỗi giây qua WebSocket. Header chỉ đọc user nhưng render lại mỗi giây. Thiết kế lại context để khắc phục.

Gợi ý

Tách theo nhịp đổi: AuthContext (user — hiếm đổi), QueueContext (queue — đổi mỗi giây), UiContext (theme). Header chỉ useContext(AuthContext) nên không render khi queue tick. Mỗi value bọc useMemo. Nếu cần đọc slice nhỏ của queue, cân nhắc external store có selector (Zustand).

Ngân hàng câu hỏi phỏng vấn

React performance — phần phân loại nhanh ứng viên "biết dùng" với "hiểu cơ chế".

Q1Liệt kê các nguyên nhân khiến một component re-render.Junior›

Trả lời: Bốn nguyên nhân: (1) state nội bộ đổi (setState/dispatch); (2) props nhận được đổi; (3) component cha re-render (mặc định kéo theo mọi con); (4) một context mà nó useContext đổi value. Lưu ý re-render là việc React chạy lại hàm component để tính virtual DOM, không nhất thiết dẫn tới cập nhật DOM thật.

Q2Re-render và cập nhật DOM có phải một? Tại sao re-render thừa vẫn xấu nếu không đổi DOM?Middle›

Trả lời: Không. Re-render = chạy lại hàm component + diff (reconciliation). Cập nhật DOM chỉ xảy ra khi diff phát hiện khác biệt. Re-render thừa vẫn tốn: chạy lại logic/tạo object tạm (tăng GC), so sánh cây, và có thể lan xuống con. Trong UI realtime nhiều dữ liệu, các re-render thừa cộng dồn gây tụt khung hình dù DOM không đổi.

⚠️ Bẫy: nói "re-render luôn cập nhật DOM nên rất chậm" là sai bản chất — vấn đề là chi phí tính toán + lan toả, không phải DOM.

Q3React.memo hoạt động thế nào? Khi nào dùng nó là sai lầm?Middle›

Trả lời: memo bọc component và so sánh nông props giữa hai lần render; nếu giống, bỏ qua render, tái dùng kết quả cũ. Sai lầm: (1) dùng cho component nhẹ render lại rất nhanh — chi phí so sánh đắt hơn lợi ích; (2) props vẫn là object/array/hàm inline đổi tham chiếu mỗi render → memo không bao giờ hit, lại tốn thêm; (3) prop children hoặc dữ liệu luôn đổi mỗi tick. Phải đo bằng Profiler trước.

Q4Phân biệt useMemo và useCallback. Cho ví dụ dùng đúng.Junior›

Trả lời: useMemo(fn, deps) nhớ giá trị trả về của fn; useCallback(fn, deps) nhớ chính hàm (tương đương useMemo(()=>fn, deps)). Dùng useMemo cho tính toán nặng (lọc/sắp 1000 dòng) hoặc tạo object/array truyền cho con có memo. Dùng useCallback để giữ callback ổn định khi truyền xuống con có memo hoặc làm dependency của useEffect.

⚠️ Bẫy: dùng useCallback/useMemo nhưng phía nhận không có memo → vô ích, chỉ tốn bộ nhớ.

Q5Vấn đề re-render của Context là gì? Liệt kê các cách tối ưu.Senior›

Trả lời: Khi value của Provider đổi tham chiếu, mọi consumer render lại — Context không có selector lấy slice. Tối ưu: (1) useMemo object value để tránh tham chiếu mới vô nghĩa; (2) tách context theo nhịp đổi (auth ít đổi vs queue đổi mỗi giây); (3) tách state và dispatch thành hai context (component "chỉ ghi" không render khi state đổi); (4) với state đổi nhanh, dùng external store có selector (Zustand/Redux Toolkit) thay vì cố cứu Context.

Q6Code splitting là gì? Triển khai trong React thế nào và cần lưu ý gì?Middle›

Trả lời: Là chia bundle thành nhiều chunk tải theo nhu cầu để giảm thời gian tải ban đầu. Trong React dùng React.lazy(() => import('...')) + Suspense fallback. Thường tách theo route, theo component/lib nặng. Lưu ý: luôn bọc Error Boundary vì import() có thể lỗi mạng; cân nhắc preload khi hover; tránh fallback nhấp nháy với chunk tải quá nhanh.

Q7Error Boundary là gì? Vì sao phải là class? Nó không bắt loại lỗi nào?Senior›

Trả lời: Là component bắt lỗi render của cây con và hiển thị UI dự phòng thay vì để sập cả app. Phải là class vì dùng hai lifecycle chưa có hook tương đương: getDerivedStateFromError (đổi state để render fallback) và componentDidCatch (log lỗi). Nó không bắt lỗi trong event handler, code bất đồng bộ (setTimeout/fetch), SSR, và lỗi từ chính nó. Đặt boundary theo tầng: gốc + cục bộ quanh từng widget để cô lập phạm vi sập.

⚠️ Bẫy: tưởng Error Boundary bắt được lỗi trong onClick — không; phải try/catch hoặc set cờ lỗi vào state.

Q8Render props vs custom hooks — chọn cái nào và vì sao hooks thắng thế?Middle›

Trả lời: Cả hai chia sẻ logic có state. Render props/HOC thêm cấp component (wrapper hell), khó kết hợp, callback lồng nhau khó đọc. Custom hooks chia sẻ logic mà không thêm node cây, dễ kết hợp nhiều hook, props minh bạch — nên là mặc định ngày nay. Render props vẫn hợp khi cần cho bên ngoài tự quyết cách render dựa trên state nội bộ (vd component đo kích thước trả về {width,height}).

Q9Reconciliation là gì? Vai trò của key trong danh sách?Senior›

Trả lời: Reconciliation là thuật toán diff cây mới với cây cũ để áp thay đổi DOM tối thiểu, dùng heuristic: khác loại phần tử thì dựng lại cả cây con; cùng loại thì giữ node, cập nhật thuộc tính, đệ quy. Với danh sách, React ghép cặp phần tử theo key — danh tính ổn định giúp biết phần tử nào giữ/thêm/xoá/di chuyển thay vì so theo vị trí. key đúng giúp giữ state nội bộ và tối ưu thao tác DOM.

Q10Vì sao không nên dùng index làm key cho danh sách động?Middle›

Trả lời: Khi thêm/xoá/sắp xếp lại, index của một phần tử thay đổi, khiến React ghép sai cặp cũ/mới: state nội bộ (giá trị input, checkbox, animation) dính nhầm sang phần tử khác, có thể render sai và lỗi tinh vi. Dùng id ổn định từ dữ liệu (call.id). Index chỉ chấp nhận khi danh sách tĩnh, không sắp xếp lại, không thêm/xoá giữa chừng.

Q11Danh sách 50.000 cuộc gọi cần render. Tiếp cận thế nào để UI mượt?Senior›

Trả lời: Memo hay useCallback không đủ vì chi phí nằm ở việc dựng/giữ hàng chục nghìn DOM node. Dùng virtualization (react-window / react-virtual): chỉ render các dòng trong viewport + đệm, tái dùng node khi cuộn. Kết hợp: phân trang/infinite scroll từ server, memoize row, key ổn định, và nếu dữ liệu tới dồn dập thì gộp cập nhật (batching) hoặc startTransition để giữ UI phản hồi.

Q12Bạn dùng React DevTools Profiler để tìm điểm nóng như thế nào?Middle›

Trả lời: Mở tab Profiler, bấm record, thực hiện thao tác nghi ngờ (gõ chat, nhận event), dừng. Đọc flamegraph (thanh rộng = render lâu, xám = không render), ranked chart để xếp hạng component theo thời gian, và bật "Why did this render?" để biết lý do (props/hook/cha). Bật "Highlight updates" để thấy phần nháy. Từ đó quyết định: đẩy state xuống, composition, memo có chọn lọc, hay virtualization — rồi đo lại để xác nhận có cải thiện.

⚠️ Bẫy: tối ưu mà không đo trước/sau. Luôn so sánh số liệu để chắc thay đổi thực sự giúp, không phải cảm tính.
