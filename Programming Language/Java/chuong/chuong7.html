Chương 07 · Collections Framework

Collections Framework — List, Set, Queue

Mảng có kích thước cố định và gần như không có phương thức nào hữu ích. Collections Framework (nằm trong java.util) là bộ interface và class dựng sẵn để lưu trữ, thao tác và truy xuất nhóm đối tượng — thứ bạn sẽ dùng trong mọi chương trình Java từ giờ trở đi. Điều quan trọng nhất của chương này không phải là nhớ tên class, mà là chọn đúng cấu trúc cho đúng bài toán — vì sai lầm ở đây khiến chương trình chậm hàng trăm lần mà không có lỗi nào được báo ra.

Độ dài: ~1600 dòng Bài tập: 5 Quiz: 8 Prerequisites: Chương 1-6
🎯 Mục tiêu chương
  • Đọc được cây phân cấp Iterable → Collection → List/Set/Queue.
  • Phân biệt bốn nhóm: List (có thứ tự, cho trùng), Set (duy nhất), Queue (FIFO), Map (khoá-giá trị).
  • Biết khi nào ArrayList và khi nào LinkedList — và vì sao ArrayList gần như luôn thắng.
  • Chọn đúng giữa HashSet, LinkedHashSet, TreeSet.
  • Dùng ArrayDeque làm cả ngăn xếp lẫn hàng đợi; hiểu PriorityQueue.
  • Hiểu Iterator và nguồn gốc của ConcurrentModificationException.
  • Phân biệt Comparable và Comparator; viết bộ so sánh nhiều tiêu chí.
  • Thuộc bảng độ phức tạp — công cụ ra quyết định quan trọng nhất.
  • Biết các collection bất biến (List.of) và cạm bẫy của chúng.
  • Tránh các lỗi kinh điển: chọn sai cấu trúc, sửa khi đang duyệt, quên equals/hashCode.

1. Vì sao cần Collections Framework

MangVsList.java 
// ❌ Với mảng: thêm một phần tử là cả một thủ tục

// Muốn xoá phần tử giữa? Tự dịch chuyển mọi phần tử phía sau.
// Muốn kiểm tra "đã có chưa"? Tự viết vòng lặp.
// Muốn sắp xếp theo tiêu chí riêng? Tự cài thuật toán.

// ✅ Với Collections: tất cả đã có sẵn
List<String> ds2 = new ArrayList<>();
ds2.add("a"); ds2.add("b"); ds2.add("c");
ds2.add("d");                     // tự nới rộng
ds2.remove("b");                  // tự dịch chuyển
ds2.contains("c");                // có sẵn
Collections.sort(ds2);            // có sẵn
System.out.println(ds2);           // [a, c, d] — toString() tử tế

Collection chỉ chứa đối tượng, không chứa kiểu nguyên thủy

List<int> là bất hợp lệ — phải viết List<Integer>. Java tự autoboxing khi bạn add(5), nhưng phải trả giá: mỗi số là một object trên heap, tốn bộ nhớ hơn nhiều và tạo áp lực cho garbage collector.

Với dữ liệu số lượng lớn và thuần số, mảng nguyên thủy int[] vẫn nhanh hơn List<Integer> khoảng 4-6 lần và tốn bộ nhớ ít hơn khoảng 4 lần. Lý do sâu xa là type erasure — Chương 9 sẽ giải thích.

📌 Vì sao Map không nằm trong Collection

Vì Collection<E> mô tả "một nhóm phần tử đơn lẻ" — phương thức add(E) nhận một giá trị. Map lưu cặp khoá-giá trị, nên put(K, V) có chữ ký hoàn toàn khác. Ép chúng vào cùng một interface sẽ khiến cả hai đều xấu.

Nhưng chúng liên hệ chặt chẽ: map.keySet() trả về Set<K>, map.values() trả về Collection<V>, và map.entrySet() trả về Set<Map.Entry<K,V>> — đó là ba cây cầu nối hai thế giới. Chương 8 dành trọn cho Map.

⚠️ Bẫy kinh điển: remove() trên List<Integer>
RemoveBay.java
List<Integer> so = new ArrayList<>(List.of(10, 20, 30));

so.remove(1);                  // gọi remove(int index) → xoá phần tử ở vị trí 1 (số 20)
System.out.println(so);        // [10, 30]

so.remove(Integer.valueOf(10));  // gọi remove(Object) → xoá GIÁ TRỊ 10 ✅
System.out.println(so);            // [30]

Hai phương thức remove(int) và remove(Object) là nạp chồng, và với List<Integer> thì cả hai đều nhận được số nguyên. Java chọn remove(int) vì khớp chính xác được ưu tiên hơn autoboxing (chương 4). Muốn xoá theo giá trị, phải ép tường minh: remove(Integer.valueOf(10)).

Dùng ArrayList. Gần như luôn luôn. Về lý thuyết LinkedList thắng ở việc chèn/xoá đầu danh sách, nhưng trên phần cứng thật, ArrayList vẫn thường nhanh hơn ngay cả ở những thao tác đó — vì bộ nhớ liền kề tận dụng được cache CPU, còn con trỏ nhảy lung tung thì không. Nếu bạn cần chèn/xoá ở hai đầu, hãy dùng ArrayDeque, không phải LinkedList.

6. Queue và Deque

QueueDeque.java 
// ⭐ ArrayDeque — dùng làm CẢ hàng đợi lẫn ngăn xếp, nhanh nhất cho cả hai

// --- Dùng như QUEUE (FIFO — vào trước ra trước) ---
Queue<String> q = new ArrayDeque<>();
q.offer("A");          // thêm vào cuối (add() cũng được nhưng ném lỗi khi đầy)
q.offer("B");
q.offer("C");
q.peek();              // "A" — xem đầu, KHÔNG xoá
q.poll();              // "A" — lấy và XOÁ khỏi đầu
System.out.println(q);  // [B, C]

// --- Dùng như STACK (LIFO — vào sau ra trước) ---
Deque<String> st = new ArrayDeque<>();
st.push("A");           // thêm vào ĐẦU
st.push("B");
st.push("C");
st.peek();             // "C"
st.pop();              // "C"
System.out.println(st); // [B, A]

// --- Hai đầu đầy đủ ---
Deque<Integer> d = new ArrayDeque<>();
d.offerFirst(1);  d.offerLast(2);
d.peekFirst();     d.peekLast();
d.pollFirst();     d.pollLast();

Xoáremove() → NoSuchElementExceptionpoll() → null

📌 Đừng dùng Stack — dùng ArrayDeque

Class java.util.Stack có từ Java 1.0 và mắc ba vấn đề: nó kế thừa Vector nên đồng bộ hoá (chậm) dù bạn không cần; nó lộ luôn cả API của List nên có thể get(0) vào giữa ngăn xếp — phá vỡ khái niệm; và thứ tự duyệt của nó ngược với trực giác (từ đáy lên đỉnh).

Chính Javadoc của JDK khuyến nghị dùng ArrayDeque thay thế. Tương tự, Vector và Hashtable đều là di sản — dùng ArrayList và HashMap.

pq.poll();   // 10 — nhỏ nhất trước
pq.poll();   // 20

// ⚠️ toString() KHÔNG theo thứ tự sắp xếp — nó in cấu trúc heap bên trong

// Mẫu "top K phần tử lớn nhất" — chỉ giữ K phần tử trong bộ nhớ
PriorityQueue<Integer> topK = new PriorityQueue<>();   // min-heap
for (int x : duLieuRatLon) {

}   // Bộ nhớ O(K) thay vì O(n) — quan trọng với dữ liệu hàng tỷ phần tử

7. Iterator và ConcurrentModificationException

Iterator.java 
List<String> ds = new ArrayList<>(List.of("a", "b", "c", "d"));

// ❌ Xoá khi đang duyệt bằng for-each
for (String s : ds) {
    if (s.equals("b")) ds.remove(s);
}
// 💥 ConcurrentModificationException

// ✅ Cách 1: Iterator.remove() — cách chuẩn từ Java 1.2
Iterator<String> it = ds.iterator();
while (it.hasNext()) {
    if (it.next().equals("b")) it.remove();
}

// ✅ Cách 2: removeIf() — ngắn gọn nhất (Java 8+)
ds.removeIf(s -> s.equals("b"));

// ✅ Cách 3: duyệt ngược bằng chỉ số
for (int i = ds.size() - 1; i >= 0; i--) {
    if (ds.get(i).equals("b")) ds.remove(i);
}

// ✅ Cách 4: gom vào list mới rồi xoá một lượt
List<String> canXoa = ds.stream().filter(s -> s.equals("b")).toList();
ds.removeAll(canXoa);

modCount — cơ chế "fail-fast" bên dưới

Mỗi collection giữ một bộ đếm modCount, tăng lên mỗi khi cấu trúc thay đổi (thêm/xoá phần tử). Khi bạn tạo iterator, nó chụp lại giá trị hiện tại vào expectedModCount. Ở mỗi lần next(), iterator so sánh hai số — khác nhau nghĩa là ai đó đã sửa collection sau lưng nó, và nó ném ConcurrentModificationException ngay.

Đây gọi là hành vi fail-fast: thà báo lỗi ngay còn hơn duyệt sai âm thầm và trả kết quả không đúng. Iterator.remove() hoạt động được vì nó cập nhật cả hai bộ đếm.

Tên gọi hơi gây nhầm: ngoại lệ này xảy ra ngay cả trong chương trình một luồng — nó không chỉ liên quan tới đa luồng.

📌 Hợp đồng của compareTo
  • Đối xứng dấu: sgn(a.compareTo(b)) == -sgn(b.compareTo(a))

Bài tập

Đo hiệu năng ArrayList vs LinkedList

Viết benchmark so sánh hai cấu trúc với n = 10.000 / 100.000 / 1.000.000:

  1. Thêm n phần tử vào cuối.
  2. Thêm n phần tử vào đầu (add(0, x)).
  3. Truy cập ngẫu nhiên n lần bằng get(i).
  4. Duyệt tuần tự toàn bộ bằng for-each.
  5. Xoá n/2 phần tử ở giữa.

Lập bảng kết quả và trả lời: kết quả nào khớp với bảng độ phức tạp lý thuyết, kết quả nào không khớp? Giải thích chỗ không khớp.

Gợi ý

Bạn sẽ thấy phép "duyệt tuần tự" của ArrayList nhanh hơn LinkedList đáng kể dù cả hai đều là O(n) — vì bộ nhớ liền kề tận dụng được cache CPU, còn LinkedList phải nhảy tới địa chỉ ngẫu nhiên ở mỗi node (cache miss). Big-O không mô tả được yếu tố này, và đó là lý do ArrayList thắng trong thực tế nhiều hơn lý thuyết dự đoán.
Nhớ warm-up JIT: chạy vài lượt và bỏ kết quả đầu tiên.

Hệ thống quản lý thư viện

(f) là bài toán "cửa sổ trượt cố định" — ArrayDeque với if (size() > 10) pollLast(); sau mỗi addFirst().
(e) cần PriorityQueue với comparator hai tầng: ưu tiên trước, rồi tới thời điểm đăng ký — nếu chỉ so ưu tiên thì hai người cùng mức sẽ có thứ tự không xác định (heap không ổn định).

Xoá phần tử i: System.arraycopy(mang, i+1, mang, i, soLuong-i-1) rồi đặt mang[--soLuong] = null — bước gán null rất quan trọng, nếu quên thì object bị giữ tham chiếu và không được GC thu hồi (rò rỉ bộ nhớ).
Vì sao Object[]: không tạo được new E[n] do type erasure — chương 9 sẽ giải thích, và bản thân JDK cũng làm y hệt.

Bộ so sánh nhiều tiêu chí

Cho record NhanVien(String hoTen, String phongBan, long luong, LocalDate ngayVao, Integer tuoi) (chú ý tuoi có thể null), viết các bộ so sánh:

  1. Theo lương giảm dần.
  2. Theo phòng ban (A→Z), cùng phòng thì lương giảm dần.
  3. Theo thâm niên (vào lâu nhất trước), cùng ngày thì theo tên.
  4. Theo tuổi tăng dần, null xếp cuối.
  5. Theo họ (từ cuối trong hoTen), rồi tới tên.
  6. Theo độ dài tên, cùng độ dài thì theo bảng chữ cái, không phân biệt hoa thường.

Với mỗi bộ so sánh, viết test khẳng định thứ tự đúng — kể cả trường hợp có giá trị bằng nhau.

Gợi ý

(4): Comparator.comparing(NhanVien::tuoi, Comparator.nullsLast(Comparator.naturalOrder())).
(5): trích họ bằng hoTen.substring(hoTen.lastIndexOf(' ') + 1) — cẩn thận trường hợp tên chỉ có một từ (lastIndexOf trả −1, cộng 1 thành 0, vẫn đúng).
(6): Comparator.comparingInt(String::length).thenComparing(String.CASE_INSENSITIVE_ORDER) áp lên NhanVien::hoTen.
Kiểm tra hợp đồng: với mỗi comparator, khẳng định sgn(cmp(a,b)) == -sgn(cmp(b,a)) trên vài cặp.

Máy tính biểu thức bằng ngăn xếp

Dùng ArrayDeque cài đặt:

  1. boolean canBang(String s) — kiểm tra ngoặc ()[]{} cân bằng.
  2. List<String> sangHauTo(String trungTo) — chuyển trung tố sang hậu tố (thuật toán shunting-yard).
  3. double tinhHauTo(List<String> hauTo) — tính giá trị biểu thức hậu tố.
  4. double tinh(String bieuThuc) — ghép cả ba, hỗ trợ + - * / ^, ngoặc, số thực và số âm.

Xử lý lỗi tử tế: ngoặc không cân bằng, chia cho 0, ký tự lạ — mỗi loại một exception riêng với thông điệp chỉ rõ vị trí.

Gợi ý

Shunting-yard: duyệt token; số thì đẩy thẳng ra output; toán tử thì pop mọi toán tử có độ ưu tiên lớn hơn hoặc bằng ra output trước khi push (riêng ^ kết hợp phải sang trái nên chỉ pop khi lớn hơn hẳn); ( thì push; ) thì pop tới khi gặp (.
Số âm là ca khó nhất: dấu - là phép trừ hay dấu âm? Quy tắc: nếu nó ở đầu biểu thức, hoặc ngay sau (, hoặc ngay sau một toán tử khác → đó là dấu âm.

Q1

List, Set, Queue, Map khác nhau thế nào? Vì sao Map không kế thừa Collection?

Xem đáp án
✓ Đáp án
  • List — dãy có thứ tự, cho trùng lặp, truy cập theo chỉ số. Dùng khi thứ tự quan trọng.
  • Set — tập phần tử duy nhất, không có chỉ số. Dùng khi cần tính duy nhất và kiểm tra tồn tại nhanh.
  • Queue — xử lý theo thứ tự, thường FIFO; truy cập ở hai đầu. Dùng cho hàng đợi công việc, lập lịch.
  • Map — tập cặp khoá-giá trị; khoá duy nhất, giá trị được trùng. Dùng để tra cứu theo khoá.

Map không kế thừa Collection vì hai interface có hình dạng dữ liệu khác nhau: Collection<E> là nhóm phần tử đơn lẻ với add(E), còn Map lưu cặp với put(K, V). Ép chung một interface sẽ khiến cả hai đều gượng ép.

Chúng vẫn nối với nhau qua ba khung nhìn: keySet() → Set<K>, values() → Collection<V>, entrySet() → Set<Map.Entry>.

Q2

Khi nào dùng LinkedList thay ArrayList?

Xem đáp án
✓ Đáp án

Trong thực tế: gần như không bao giờ. Đây là câu trả lời gây bất ngờ nhưng đúng.

Về lý thuyết, LinkedList thắng ở chèn/xoá đầu danh sách (O(1) so với O(n)). Nhưng trên phần cứng thật, ArrayList vẫn thường nhanh hơn ngay cả ở đó, vì:

  • Cache CPU — mảng nằm liền kề, đọc một phần tử là kéo luôn cả vùng lân cận vào cache. LinkedList nhảy tới địa chỉ ngẫu nhiên ở mỗi node, gây cache miss liên tục.
  • Bộ nhớ — mỗi node LinkedList tốn 3 tham chiếu (giá trị + trước + sau) thay vì 1.
  • System.arraycopy được tối ưu ở mức lệnh máy, dịch chuyển hàng nghìn phần tử rất nhanh.

Nếu bạn cần thêm/xoá ở hai đầu, hãy dùng ArrayDeque — nó nhanh hơn LinkedList ở mọi mặt cho mục đích đó.
Chính Joshua Bloch (tác giả Collections Framework) từng nói đùa rằng ông không nghĩ ra được lý do nào để dùng LinkedList.

Mặc định HashSet — nhanh nhất và tốn ít bộ nhớ nhất. LinkedHashSet khi cần kết quả ổn định để hiển thị hoặc test. TreeSet khi cần thứ tự hoặc các truy vấn khoảng (floor, ceiling, subSet) — thứ hai loại kia không làm được.

Bẫy TreeSet: nó xác định trùng lặp bằng compareTo, không phải equals. Comparator chỉ so một trường sẽ khiến các phần tử khác nhau bị gộp — luôn thêm tiêu chí phụ để bộ so sánh nhất quán với equals.

Q4

ConcurrentModificationException xảy ra khi nào? Cách tránh?

Xem đáp án
✓ Đáp án

Xảy ra khi bạn sửa cấu trúc collection (thêm/xoá phần tử) trong lúc đang duyệt nó bằng iterator hoặc for-each.

Cơ chế: collection giữ bộ đếm modCount, tăng mỗi lần cấu trúc thay đổi. Iterator chụp giá trị này lúc tạo và so sánh ở mỗi next(). Khác nhau nghĩa là collection đã bị sửa sau lưng nó → ném ngoại lệ ngay (hành vi fail-fast: báo lỗi còn hơn duyệt sai âm thầm).

Bốn cách tránh:

  • ds.removeIf(x -> dieuKien) — ngắn gọn nhất (Java 8+).
  • Iterator.remove() — cách chuẩn, nó cập nhật cả hai bộ đếm.
  • Duyệt ngược bằng chỉ số — xoá phần tử i không ảnh hưởng các chỉ số nhỏ hơn.
  • Gom vào list mới rồi removeAll() một lượt.

Lưu ý: tên gọi gây hiểu lầm — ngoại lệ này xảy ra cả trong chương trình một luồng. Với đa luồng thật thì dùng CopyOnWriteArrayList hoặc ConcurrentHashMap (chương 12).

Q5

Comparable và Comparator khác nhau thế nào?

Xem đáp án
✓ Đáp án

Comparable<T> định nghĩa thứ tự tự nhiên của chính lớp đó. Cài đặt bên trong lớp, phương thức int compareTo(T o). Mỗi lớp chỉ có một thứ tự tự nhiên. Ví dụ: String theo bảng chữ cái, Integer theo giá trị.

Comparator<T> định nghĩa thứ tự bên ngoài, tuỳ ngữ cảnh. Viết thành lambda hoặc lớp riêng, phương thức int compare(T a, T b). Viết bao nhiêu cũng được, và dùng được cả với lớp bạn không sửa được mã nguồn.

Dung.java
ds.sort(null);                                // dùng Comparable
ds.sort(Comparator.comparing(SinhVien::ten));  // dùng Comparator
ds.sort(Comparator.comparingDouble(SinhVien::diem)
             .reversed().thenComparing(SinhVien::ma));   // nhiều tiêu chí

Cả hai đều cấm viết bằng phép trừ: (a, b) -> a - b tràn số với Integer.MIN_VALUE, và (int)(a - b) với double thì làm mất phần thập phân — 8.5 - 8.2 ép về int thành 0, tức "bằng nhau". Dùng Integer.compare / Double.compare / Comparator.comparingDouble.

Q6

Vì sao list.remove(1) và list.remove(Integer.valueOf(1)) cho kết quả khác nhau?

Xem đáp án
✓ Đáp án

Vì List có hai phương thức remove nạp chồng: remove(int index) — xoá theo vị trí, và remove(Object o) — xoá theo giá trị.

Với List<Integer>, gọi remove(1) thì trình biên dịch chọn remove(int) — vì khớp chính xác được ưu tiên hơn autoboxing (quy tắc chọn phương thức nạp chồng ở chương 4). Nên nó xoá phần tử ở vị trí 1, không phải giá trị 1.

Remove.java
List<Integer> ds = new ArrayList<>(List.of(10, 20, 30));
ds.remove(1);                      // xoá vị trí 1 → [10, 30]
ds.remove(Integer.valueOf(10));  // xoá giá trị 10 → [30]

Với List<String> thì không có vấn đề này, vì String không thể là int. Bẫy chỉ xuất hiện với List<Integer> — và nó là một trong những lỗi âm thầm khó chịu nhất, vì code vẫn chạy và chỉ cho kết quả sai.

Arrays.asList() là thứ dễ gây bất ngờ nhất: nó tạo một khung nhìn của mảng — kích thước cố định nhưng set() được, và sửa nó là sửa luôn mảng gốc.

Nên dùng: List.of() cho hằng số và giá trị trả về bất biến; new ArrayList<>(List.of(...)) khi cần list sửa được; List.copyOf(x) để tạo bản sao bất biến từ collection có sẵn. Tránh Arrays.asList() trừ khi bạn cố ý muốn khung nhìn của mảng.

Q8

Vì sao không nên dùng java.util.Stack?

Xem đáp án
✓ Đáp án

Ba lý do, và chính Javadoc của JDK cũng khuyến nghị thay thế:

  • Đồng bộ hoá không cần thiết — Stack kế thừa Vector, nên mọi phương thức đều synchronized. Bạn trả giá về tốc độ cho tính năng gần như chẳng bao giờ dùng tới.
  • Rò rỉ trừu tượng — vì là List, nó lộ luôn get(i), add(i, e), remove(i). Người dùng chọc được vào giữa ngăn xếp, phá vỡ chính khái niệm LIFO.
  • Thứ tự duyệt ngược trực giác — for (x : stack) duyệt từ đáy lên đỉnh, ngược với thứ tự pop(). Nguồn bug rất khó nhận ra.

Thay bằng ArrayDeque:

Stack.java
Deque<String> st = new ArrayDeque<>();
st.push("a");   st.pop();   st.peek();
// Nhanh hơn, API sạch hơn, duyệt đúng thứ tự đỉnh → đáy

Cùng lý do đó, tránh Vector (dùng ArrayList) và Hashtable (dùng HashMap) — cả ba đều là di sản từ Java 1.0, giữ lại chỉ vì tương thích ngược.

Tổng kết

Sau chương 7, bạn đã nắm:

  • Cây phân cấp: Iterable → Collection → List/Set/Queue; Map đứng riêng.
  • Bốn nhóm và tiêu chí phân biệt: thứ tự, trùng lặp, cách truy cập.
  • ArrayList là mặc định — LinkedList gần như không bao giờ cần, vì cache CPU.
  • Ba loại Set và bẫy TreeSet dùng compareTo thay equals.
  • ArrayDeque làm cả ngăn xếp lẫn hàng đợi; PriorityQueue cho ưu tiên và mẫu top-K.
  • Iterator và cơ chế fail-fast qua modCount; bốn cách xoá an toàn.
  • Comparable vs Comparator; chuỗi thenComparing; cấm viết compare bằng phép trừ.
  • Bảng độ phức tạp — và bài học "sai cấu trúc = chậm hàng nghìn lần mà không có lỗi nào".
  • Collection bất biến: List.of vs Arrays.asList vs unmodifiableList.
  • Class di sản cần tránh: Vector, Stack, Hashtable.
