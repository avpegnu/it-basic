Parallelism & MoE: partition models, place GPUs and scale fleets

Distinguish DP, TP, PP, SP/CP and EP; reason about memory/communication, read pipeline timelines, handle expert skew and operate complete GPU groups safely.

From workloads to operational layouts

  1. Define budgets

    Specify revisions, lengths, concurrency, quality and SLOs.

  2. Partition state and computation

    Partition tensors, layers, sequences or experts and identify communicating groups.

  3. Map onto topology

    Consider fast links, shared bottlenecks and replica fault domains.

  4. Measure and operate

    Profile tails, validate semantics and scale/drain whole groups.

Choose layouts using measured workloads and topology rather than the smallest weight-fitting GPU count.

  • A serving replica can be an entire GPU group; losing a required rank generally makes the group unavailable.
  • Memory fit, latency, throughput and failure isolation are distinct requirements that must work together.
  • TP trades tensor memory/computation for collectives; PP trades layer placement for handoffs and scheduling.
  • Total MoE parameters determine the weight inventory; selected experts explain only part of computation and communication costs.
  • Matching expert copies can preserve model selection; dropping contributions or choosing other experts changes computation.
  • Fleet capacity includes readiness delays, warm headroom, draining and correlated failures.

1. A replica need not be one GPU

Per-rank fit

  • Budget the most loaded rank, not just a cluster average.
  • Embeddings, output heads and uneven layers can unbalance stages.

Meet user targets

  • Queueing, prefill and transfers shape TTFT; decode tails shape smoothness.
  • Adding GPUs can increase overhead rather than reduce latency.

Survive failures

  • A missing rank can fail a whole group collective.
  • Replicas sharing a node/rack still have correlated failures.

A serving replica contains enough resources to evaluate the full model for its assigned requests. Small models can occupy one GPU; larger models distribute weights and work across ranks. A rank is a distributed process/member and is not universally identical to a physical device. The experiments assume one rank per GPU.

A dense 70B model at two bytes per weight has 140 billion raw weight bytes, about 130.39 GiB. This excludes KV, activations, workspaces, quantization metadata, duplicated tensors and allocator overhead. Ideal four-way sharding yields 32.60 GiB per GPU; unmeasured free space is not automatically safe request capacity.

2. Each parallelism strategy partitions a different axis

Inference DP uses equivalent model copies to process different requests. Unlike training DP, these groups do not require gradient synchronization or per-forward tensor collectives with one another. They can still share routers, artifact stores, control planes and networks, and routing must respect revisions/adapters.

TP partitions tensors/operators, PP partitions layer ranges, EP distributes experts, and SP/CP partition sequences/activations under specific algorithms. Combinations require explicit process groups. Do not blindly multiply every abbreviation: SP often uses TP groups, EP can reuse existing group dimensions, and expert TP can differ from attention TP.

3. Tensor parallelism and collective cost

For a two-linear-layer FFN, column partitioning of the first matrix creates independent hidden shards, while row partitioning of the second creates partial outputs that need summation. Attention heads can also be partitioned with a combined output projection. A particular Megatron-style forward layout uses two all-reduces per layer; SP, fusions and other layouts change the pattern.

For n ranks and S payload bytes, a ring all-reduce sends approximately2(n−1)S/n bytes per rank over2(n−1) rounds. T≈bytes/B_eff+rounds×latency omits overlap and contention. Small decode batches have small payloads but many sequential collectives, making round latency important; prefill has different payloads and compute shapes.

Mapping frequent communication onto fast links is a useful heuristic, not a prohibition on cross-node TP. Inspect effective bandwidth, GPU/NIC locality, switch bisection and concurrent traffic. Advertised bandwidth may be aggregate/bidirectional rather than one usable pairwise path. Summed HBM bandwidth is a roofline component rather than a linear TP speedup promise.

4. Explore placement, memory and node failure

This experiment separates communication arithmetic from end-to-end performance. The same GPU budget can increase TP to reduce weight shares with more collective overhead, or increase DP to serve more requests. PP reduces layers per stage while adding activation boundaries. No slider automatically selects an optimal configuration.

Default TP4 × PP1 × DP2 uses eight ranks packed into node 0, so losing that node loses both replicas. Separate-node placement retains at least one replica after a single-node failure in the fixture. This does not test rack/power/control-plane failures, spare throughput or state recovery. Surviving but overloaded replicas can still miss availability targets.

5. Pipeline parallelism: layers, bubbles and dependencies

PP passes activations between layer ranges within or across nodes. Placement balances memory, computation and handoffs. Equal layer counts do not ensure equal costs because embeddings/heads, attention contexts, MoE traffic and kernels differ. One slow stage can bottleneck a pipeline despite appealing average utilization.

For p equal-cost stages and m ready independent forward microbatches with transfers omitted, makespan=(m+p−1)×stageTime and average utilization=m/(m+p−1). This is neither a training forward/backward schedule nor a chat-sequence latency formula. Token t+1 depends on selecting token t; arbitrary splitting cannot invent future inputs. Independent requests or supported speculative/chunked work have their own dependencies.

6. Sequence and context parallelism are distinct concepts

Sequence parallelism names several algorithms. Conventional Megatron SP shards selected activations otherwise duplicated within TP groups, such as LayerNorm/dropout activations, coordinating gather/scatter with tensor operators. Megatron CP partitions context more broadly, with attention exchanging KV information across context partitions. Specify implementations and versions rather than using one generic label.

Long-context prefill offers many tokens to distribute but requires correct causal masks, positions and balance. Decoding one query over a long cache has a different work/communication shape. KV sharding depends on attention architecture, heads, replication and engines; training CP formulas do not automatically apply to every serving engine. Distributed attention may require block exchange and stable softmax combination rather than summing independently normalized outputs.

7. Trace requests and GPU-group lifecycles

Routers choose ready groups; group coordination preserves compatible sequence/model state and collective ordering. Membership cannot change arbitrarily during a forward pass. Trace a dense forward pass, MoE dispatch, scaling, rank failures or draining. This is a logical diagram rather than a fixed product layout.

Dense forward and decode

  1. Validate bounds/deadlines and choose a ready group with capacity evidence.
  2. Pin model revision and sequence state across the group.
  3. Schedule tensor shards with consistent collective ordering.
  4. Pass completed activations to the next pipeline stage.
  5. Complete output distributions and sampling under the engine contract.
  6. Emit committed tokens; subsequent tokens depend on valid prefixes.

Dispatch tokens through experts

  1. Compute router scores/top-k under pinned model semantics.
  2. Dispatch hidden vectors to selected experts and matching copies.
  3. Return contributions with token/expert identities and gating weights.
  4. Combine required selected outputs before downstream computation.

Scale out and verify readiness

  1. Allocate a compatible rank group under topology/failure policies.
  2. Load and verify revisions, metadata and shard layouts without mixing generations.
  3. Initialize collectives, KV and workspaces, then warm up and check group health.
  4. Publish healthy membership only after the whole group is ready.

A rank or node fails

  1. Collective stalls/errors or health signals mark the group unavailable.
  2. Remove the group from admission rather than continuing with missing shards.
  3. Retry under output/deadline contracts and replay required state on a healthy group.
  4. After streaming begins, use resumable semantics or explicit failure/restart.

Drain before scaling in

  1. Stop new admissions to the selected group.
  2. Retain active streams under bounded drain and cancellation policies.
  3. Finish or compatibly migrate state and confirm no outstanding kernels/references.
  4. Release the group safely while retaining a suitable warm recovery floor.

8. MoE: total weights, active experts and output combination

A sparse MoE block selects experts per token, evaluates them and combines outputs using model gating weights. Experts are typically per-layer FFN blocks rather than complete chat models or predetermined subject specialists. Selection can vary by token/layer, while attention, shared experts and other dense components still follow the architecture.

Total parameters describe the weight inventory; active parameters describe the subset used per token under a counting convention. Neither predicts wall-clock time alone: routing, transfers, attention, padding and matrix shapes also cost resources. Required weights must be available when needed; offloading/caching trades residency for transfers and latency. Inactivity on one token does not remove weights from the artifact.

9. Expert parallelism and a dispatch round

Preserve token and expert identity

  1. Select

    Pin router semantics and top-k assignments.

  2. Pack and dispatch

    Preserve identities, shapes, offsets and compatible copies.

  3. Evaluate

    Evaluate expert batches under capacity and skew.

  4. Return and combine

    Return to owners and combine required weighted contributions.

Correct byte counts cannot compensate for returning outputs to the wrong tokens.

EP places expert parameters across GPUs and sends token hidden vectors to selected experts. Top-k can produce several assignments per token; outputs return to the correct owner for weighted combination. All-to-all is a common logical pattern, not equal traffic on every pair or one mandatory collective call per layer. Dispatchers can use hierarchy, packing, fused kernels and overlap.

For N tokens, k selected experts per token, hidden width h and b bytes per activation, all-remote assignments with equal input/output widths move about2Nkhb payload bytes for dispatch plus return, before metadata/padding. Local work avoids inter-GPU paths and co-location/dispatch sharing can change actual traffic. A skewed traffic matrix makes aggregate bandwidth insufficient to describe congestion or the slowest destination.

10. Hot experts: replicate, queue or drop?

Routing skew varies by workload and window. Fleet averages can hide a hot expert GPU or small inefficient expert batches. Training balance objectives, router policies and capacity belong to model/training design; enabling an auxiliary loss during serving does not repair a trained distribution. Models can use learned balancing or shared experts rather than one universal top-k softmax.

Replicating a hot logical expert with matching parameters/revisions can preserve selected experts at additional memory/placement cost, subject to numerical tolerance checks. Sending work to different logical experts or dropping overflow contributions changes computation. Queueing/splitting can preserve selected outputs while increasing latency. Dropping/rerouting is not a quality-neutral optimization.

This experiment defines capacity from sixteen assignments and four experts, giving a baseline of four per copy; it is not an engine configuration. Skew creates logical loads8/3/3/2. Compare queues, matching copies and dropping to see different memory, communication and semantic effects. Work counts are not measured latency because shapes, kernels and topology still matter.

11. Build an explicit deployment budget

From arrivals to complete groups

  1. Normalize arrivals

    5000 requests/minute ÷ 60 ≈83.33 requests/s; this is an average rather than peak traffic.

  2. Set capacity budgets

    20× 0.70 =14 requests/s/group; ceil(83.33/14)=6 groups are needed with all groups healthy.

  3. Check one failed group

    Losing 1 of 6 groups leaves 70 requests/s under the same policy, below 83.33. At least 7 groups are needed to retain 6 healthy groups.

  4. Include peaks and topology

    At twice the arrivals, ceil(166.67/14)+1 =13 groups under the same N−1 policy. Check multi-group node/rack failures, readiness delays and cost.

Assume 20 requests/s/group within SLOs and a 70% normal operating policy; these are not measurements of a particular model. Retaining that 70% policy after failure makes the comparison explicit.

A dense 405B model at two bytes per weight needs 810 GB≈754.37 GiB of raw weights. Eight hypothetical 80 GiB GPUs total 640 GiB, insufficient even before runtime state. Ideal TP8×PP2 across sixteen GPUs gives≈47.15 GiB per rank, a weight-fitting candidate rather than proof of peak fit, latency or resilience. One-byte weights reduce raw storage to≈377.19 GiB, or 47.15 GiB per rank atTP8, still requiring metadata, kernel and quality checks.

Five thousand requests per minute average≈83.33 requests/s. Replica count needs measured per-group goodput under the actual workload/SLO plus peak/failure headroom, not division by GPU count. If one group delivers an assumed 20 requests/s within targets and normal operation uses 70% of that budget, ceil(83.33/14)=six groups is a starting point. N−1 and peaks need separate checks; this is not a 405B benchmark.

12. Fleet routing, cold starts and autoscaling

Scaling adds complete ready groups rather than arbitrary GPUs to running collectives, unless an engine supplies a supported reconfiguration protocol. Routing can consider queue age, estimated work, KV growth/headroom, prefix locality, priorities and deadlines. Least request count can mislead when lengths differ substantially.

Cold starts include group allocation, artifact reads, integrity/revision checks, decompression/conversion, device copies, collective/layout initialization, memory setup and warm-up/graph capture. Raw 140 GB over4 GB/s has an ideal 35-second transfer lower bound, not a startup guarantee. Local staging removes one bottleneck rather than all initialization. Readiness covers the group, not just a listening process or healthy rank0.

Autoscaling combines leading pressure with measured readiness delays, stabilization, a warm floor and capacity limits. GPU utilization alone does not reveal decode memory pressure, expert stragglers or SLO headroom. Scale-in stops admissions and drains streams under deadlines; migration requires compatible state and sound ownership. Avoid controller/routing feedback that oscillates traffic between cold and warm groups.

13. Rank failures, stream recovery and failure domains

A failed rank or mismatched collective order can leave peers waiting until timeout. Recovery needs bounded detection, fencing, admission removal and runtime-supported cleanup. Missing required tensor shards or expert contributions cannot simply be omitted. Replay to another group needs explicit prompt/prefix, revision, sampling and usage boundaries.

Once tokens are visible, replay can produce different text, duplicate chunks or repeated side effects. Define request/stream generations, sequencing, acknowledgements and cancellation, choosing explicit restart or supported resumption. Resumable delivery does not imply another replica already holds KV; recomputation/migration costs memory and time. Evaluate node/rack/power/network failures against actual placement rather than replica labels.

14. Profile and validate before choosing a layout

Choose candidates

  • Check peak state after weight fit; align heads, layers and kernel support.
  • Map communicating groups onto suitable topology.

Decide with evidence

  • Measure latency tails, cost and quality under supported traffic.
  • Exercise bursts, failures and draining before production scaling.

State revision triggers

  • Changed context mixes or expert skew can require new layouts.
  • Engine/hardware upgrades need fresh profiling rather than inherited numbers.

Build a workload matrix across lengths, concurrency, bursts, reuse and domains. Measure rank memory peaks, compute/communication time, link traffic, stage waiting, expert assignments, GPU step-time skew and latency/goodput tails. Compare layouts under matching quality, revisions, precision and traffic, separating warm/cold measurements. Small throughput tests or rank averages are insufficient.

Validate expert skew, long contexts, partial readiness, crashes within collectives, node loss, stale revisions, cancellations and drain timeouts. Recheck output/numerical tolerances after sharding, precision or dispatcher changes, treating dropping as a model behavior change. Load tests need controlled arrivals and realistic deadlines so client slowdown does not hide overload.

15. Questions with worked reasoning

If 70B BF16 fits on two 80 GiB GPUs, should TP2 be the default?

Raw weights are≈130.39 GiB, or≈65.19 GiB/rank ideally, leaving≈14.81 GiB before runtime state. Check KV growth, activation/workspace peaks, duplication and layout support, then compare measured latency/goodput against alternatives. Weight fit is only an initial filter.

Is TP8 always twice as fast as TP4?

No. Reduced compute/HBM shares compete with collective rounds, smaller kernel shapes and potentially slower paths. Under fixed budgets, TP8 also reduces DP copies. Single-sequence latency and fleet goodput can move in opposite directions.

What is utilization for four 10 ms stages and eight independent microbatches?

The forward fixture takes 110 ms with 320 busy stage-ms out of 440 available stage-ms, giving≈72.7% utilization. The first microbatch takes 40 ms. This is neither a kernel utilization benchmark nor a single-chat decoding guarantee.

Does a 13B-active MoE need only 26 GB of BF16 weights?

Not when the full model has more total parameters.26 GB is an active-weight count approximation rather than the full inventory. Plan resident/offloaded storage for experts/shared parts plus runtime state, then assess communication and expert batch shapes.

MoE p99 is poor despite reasonable average GPU utilization. What should be checked?

Check queues/lengths, KV pressure, network/collective tails and expert/rank timing before blaming skew. With evidence of a hot expert, evaluate matching copies, placement and batch shapes. Dropping or selecting different experts requires separate quality policies/evaluations.

Can two DP copies on one eight-GPU node survive node loss?

No. Packed TP4PP1DP2 shares one node, so losing it removes both copies. Separate nodes can preserve one group but still require spare capacity and routing recovery, with rack/power/network failures evaluated separately.

Why is CP more than enabling SP=true?

In Megatron terminology, SP shards selected activations within TP groups, whereas CP partitions context and exchanges attention state. Algorithms, groups, masks and memory footprints differ. Specify training/inference, engine versions and supported layouts first.

How many GPUs should an autoscaler add when queues grow?

Scale compatible groups using measured capacity and readiness delay. Account for arrival work, headroom, KV, targets and peak/failure reserve; stage weights, retain warm capacity and verify group readiness. Scale-in needs bounded draining.
