Designing File Sync: chunks, revisions and offline conflicts

Trace bytes through authoritative metadata to crash-safe device application; explore delta uploads, parent-revision CAS and keep-both to understand correct multi-device synchronization.

Remember the life of a file change

  1. Prepare bytes

    Chunk, verify, upload missing blocks and protect pending data.

  2. Commit a revision

    CAS the parent, atomically update metadata/journals and save retry results.

  3. Apply on devices

    Hint, replay, fetch, staged application and cursor checkpoint.

  4. Preserve data across faults

    Handle conflicts, offline retention, restores, collection and authorization.

Study bytes, commits, replay and recovery before optimizing storage and fanout.

  • Uploaded bytes are not committed files; protect blocks from collection before acknowledging referencing metadata.
  • File IDs survive renames; revisions, namespace cursors and locally applied state serve different roles.
  • CAS rejects stale parents; preserve local edits and resolve idempotently instead of silently overwriting.
  • Chunking savings depend on edits/data; CDC may resynchronize without guaranteeing small deltas.
  • Notifications are hints; durable replay, client correctness, collection protocols and deduplication privacy are central.

1. File sync joins three problems under one invariant

Bytes

  • Chunk, resume and verify; transfer only what is actually missing within the authorized scope.

Metadata

  • Stable file IDs, parent revisions, atomic heads/versions/journals and retry results.

Devices

  • Notifications are hints; local databases, cursors and replay drive convergence after crashes/offline periods.

Do not start with “put files in S3.” You need efficient byte transfer, authoritative metadata/version decisions and wake-ups for many idle devices. The baseline invariant is that acknowledged commits never reference non-durable or collected bytes, and stale edits never overwrite heads without a conflict signal. Durability is bounded by tested failure models, retention and recovery, not a promise against every possible disaster.

The baseline supports uploads/downloads, multiple devices, offline edits, revision history and shared folders. Files may be tens of GB, with a target sync latency of seconds when networks permit. Docs-style real-time co-editing and full-text search are outside the initial scope. Sharing an extension does not make two opaque binary files automatically mergeable.

2. Logical bytes, delta bytes and idle devices need separate estimates

Use 50 million users storing an average of 10 GB each, with 10 million DAU and two synchronized edits per day. Assume edited files average 1 MB, unique uploaded deltas are ten percent of the file and peak traffic is three times the average. These are sizing assumptions, not guaranteed chunking savings. Units are decimal: GB=10^9 B and PB=10^15 B.

The 500 PB is logical live data before deduplication, history, compression, coding, metadata and backups. A measured deduplication factor of 1.25 would imply 400 PB of unique live bytes, but cannot be assumed for every cohort. Downloads also depend on receiving devices and sharing fanout; two TB of daily upload deltas does not imply two TB of total egress.

Even with only a few hundred writes per second here, ten million devices polling every thirty seconds create about 333,333 requests/second, potentially mostly empty. Long polling/WebSockets reduce empty polling but add connection state and reconnection load. Size listings, journal pages, block-check batches and hot shared namespaces separately; file-edit RPS alone does not establish metadata load.

3. APIs separate byte upload from file commit

Every endpoint authenticates principals and namespace permissions, with quotas, batch/payload limits and policy-bound expiring capabilities. A client-provided SHA-256 does not establish ownership or read permission; block checks reveal existence only within authorized deduplication scopes. The upload service verifies digests/lengths from actual bytes rather than trusting names or claimed hashes.

The example uses a JSON parentRev and application conflict 409. A contract using HTTP If-Match normally returns 412 for a failed precondition; clients must not mix those contracts. Commit retries use stable operation IDs and payload fingerprints to return stored revisions/results, and reject reuse with different payloads.

              4. Two paths and one authoritative decision

              The block path transfers immutable bytes through block services/object storage. The metadata path decides names, parent folders, head revisions, tombstones and journals. A transactional database sharded by namespace is a convenient baseline because versions, heads, operation results, journal entries and outboxes can share a transaction. A shared folder can be its own namespace mounted into multiple directory trees.

              Diagram edges are logical calls, not a requirement that every byte traverse the same API process. Uploads/downloads may use scoped signed capabilities to access object storage directly while preserving authorization, verification and commit protection. A shared domain does not justify routing GB files through metadata workers.

              1. Commit op-42 for file-main with parentRev=5 and an ordered block list.
              2. Forward the command with its principal; check current permissions, not just upload-time permissions.
              3. A transaction checks retry results, CAS revisions and durable block protection; it writes version 6, the head, journal and outbox.
              4. Commit succeeds under its durability contract; recovery preserves block reachability.
              5. Acknowledge with the revision/cursor hint. If the ACK is lost, a retry returns the same result without another revision.

              Hints, journal replay and crash-safe application

              1. The relay reads committed outbox entries and may duplicate delivery.
              2. Namespace changed. B still periodically reconciles in case the final hint is lost.
              3. Read the journal after the applied cursor with pagination and current ACL checks.
              4. Read committed changes or return cursor-expired/resnapshot under retention rules.
              5. Return ordered entries and an opaque next cursor within the correct scope.
              6. Download locally missing blocks with authorization for the corresponding version.
              7. Read the correct immutable block version; verify received integrity.
              8. Return bytes; a timeout must not advance the applied cursor.
              9. Stage the file, apply idempotently, recover filesystem/local-database state, then checkpoint the cursor.

              Offline edits must not silently overwrite

              1. B also edited from parentRev=5 and commits after A.
              2. The commit has a different stable ID; it is not A’s retry.
              3. The current head is 6; the parent-5 CAS is no longer valid.
              4. Return a conflict without acknowledging success or discarding local bytes.
              5. Preserve the pending edit and ask the user or perform keep-both using a new idempotent operation.

              5. A manifest orders chunks; deduplication preserves positions

              A version stores ordered chunk IDs with lengths and optionally offsets, plus total size/checksums under its contract. A chunk can appear twice in a file: storage may retain one byte copy, but the manifest preserves both positions. Missing sets upload unique blocks not already present/authorized for reuse; they do not remove repeated file positions.

              Smaller chunks can reduce transfer for localized edits but increase hash/index entries, manifests, RPC/metadata and collection work. Larger chunks reduce bookkeeping but can retransmit more. Choose using file/edit workloads, CPU, memory, RTT and storage capabilities; no size is universally best. Hash caches avoid rereads when supported by safe evidence, but mtime plus size alone is insufficient because timestamps may be coarse or preserved.

              6. Fixed boundaries, CDC and re-exported files

              With fixed 4 MiB chunks, changing an in-place byte without changing file size normally changes only its containing chunk, including bytes next to a boundary. Inserting one byte at the start shifts subsequent boundaries and can change nearly every chunk. Do not equate these edits. The demo uses ASCII to make bytes and boundaries visible.

              CDC chooses content-based cut points with minimum/maximum bounds and may resynchronize with earlier boundaries downstream of an insertion. It does not guarantee “only the first chunk changes”: data, rolling-window state, bounds and edit location matter. A rolling boundary fingerprint differs from a cryptographic addressing/integrity digest. Measure deduplication with CPU throughput, tail chunk sizes and memory; one example does not prove CDC always wins.

              Media re-exports, compression streams and randomized encryption can change nearly all bytes after a small visible edit. Do not promise a 4 MiB upload for every edit to a 2 GB video. Copies and shared versions can also provide delta benefits; client-encrypted designs must specify chunking/encryption order and privacy policies.

              The editable comparison chunks actual UTF-8 from TextEncoder rather than JavaScript string lengths. Fixed size defaults to 32 bytes; content-defined cuts use a continuous eight-byte rolling window, zero low mask bits, an eight-byte minimum and a 64-byte maximum, with a possibly shorter tail. Fingerprints choose boundaries while exact byte equality decides fixture reuse. This is an independent teaching algorithm, not a FastCDC or Rabin implementation.

              Each method starts with server chunks from the baseline under its currently selected parameters. Prepending X to the default fixture produces 205 local bytes: fixed chunks need 205 new bytes, while content-defined chunks need 19 and reuse eight positions. Other data/masks can change the advantage. Counts exclude metadata, hashing CPU and commit protocols. Unique missing bytes never remove repeated ordered-manifest positions. Parameter changes recut both versions rather than simulating index migration.

              7. From uploaded blocks to committed files: close the GC gap

              Publication order for a file version

              1. Prepare bytes

                Verify digests/lengths and persist immutable blocks under pending protection.

              2. Commit truth

                CAS parents and transactionally write versions, heads, results, journals and outboxes.

              3. Recover protection

                Transfer reachability under a protocol; collectors cannot delete protected bytes.

              4. Notify and reconcile

                Hints may lag; journals and periodic catch-up drive convergence.

              Each step needs retry identities, timeouts and recovery; do not hold row locks throughout long uploads.

              Checking that a block exists before a later commit is insufficient: collection can remove it between the steps. The baseline uses durable expiring pending pins/receipts and a recoverable transition to committed reachability. Pins must remain valid at commit, and collectors must coordinate with the barrier/epoch or metadata used by commits. A safety delay helps only with proven upload/commit/recovery bounds.

              A SQL transaction does not automatically include object storage. Define a protocol: persist verified blocks and pins, validate protected receipts, commit metadata/heads/journals plus durable reachability intents, then reconcile the protection handoff while collectors respect both pending and committed intents. Without that protocol, a few SQL statements do not prove dangling heads are impossible.

              8. Stable identities differ from paths and cursors

              Use stable file IDs instead of paths as sole identities: renames change parents/names and journal entries without reuploading bytes. A namespace has its own tree, history and change order. Shared mounts reference their source namespace; cross-namespace moves may require explicit copy/delete workflows rather than a free global transaction.

              File revisions identify file versions; journal cursors record how far devices have applied scoped change feeds. They are not interchangeable. Opaque cursors can encode epochs, pagination and filters; clients must not demand consecutive integers when ACLs/filters/compaction hide entries. Contiguous-position designs need explicit skip/abort semantics.

              9. Journal replay needs snapshot barriers and correctly timed checkpoints

              A journal page completes only after durable device application

              1. Read after C40

                A hint or periodic reconciliation triggers a scoped, authorized page read.

              2. Fetch and verify

                Fetch and verify missing blocks for required versions; timeouts do not advance the applied cursor.

              3. Stage and apply

                Persist recoverable intents; handle temporary files/replacement and pending local edits under policy.

              4. Checkpoint C44

                Only after required changes through C44 have durable local state; crashes permit safe replay.

              Example: cursor C40 and a page ending at C44. Download completion alone cannot checkpoint C44; local filesystems and databases need recovery protocols.

              Snapshot, then replay

              • Bind a tree snapshot to barrier C100 and replay later journal changes even across paginated listings. Fetching a fresh cursor after an inconsistent listing can skip changes.

              Crash before checkpoint

              • If the file changed but the cursor remains C40, recovery identifies the intent and safely completes/replays it. Do not overwrite unsynchronized edits just to catch up a cursor.

              Bootstrap joins an initial tree snapshot to a consistent journal position. Read a snapshot at a barrier/cursor and replay later changes; paginated snapshots need consistency tokens or reconciliation that does not miss intervening renames/deletions. “List everything, then fetch the current cursor” can skip changes made during the listing.

              Devices replay in the required order, fetch blocks, verify, stage application and persist local state before advancing applied cursors. Filesystems and local databases generally lack a shared transaction: use recoverable operation logs, temporary files and platform-supported atomic replacement with appropriate file/directory persistence. After crashes, safely replay or finish operations instead of checkpointing early to appear fast.

              Long polling/WebSockets only signal changed namespaces and can coalesce events. Losing the final hint while a connection stays alive can leave a device stale indefinitely if recovery waits only for reconnects. Use periodic journal polls, watermark checks or another bounded recovery mechanism. Expired cursors require explicit resnapshotting that preserves pending local edits first.

              10. Two offline edits: reject stale parents and preserve both

              A and B both read revision 5. A commits revision 6; B later submitting parent 5 receives a conflict rather than overwriting. “First” means authoritative commit serialization order, not device clocks. B’s blocks may already be uploaded without changing the head; the client retains pending bytes and uses an explicit resolution policy.

              Keep-both creates a new file ID and a conflict-copy name that respects filesystem naming policies. Resolution operations are idempotent so retries do not create ten copies. Users can compare/merge in a format-aware application and commit a new version. Silent overwrites lose updates at the current head; surviving history is not a reason to omit conflict signals. OT/CRDT applies to suitable application models, not arbitrary binary merging.

              The three-way example below assumes a known field format and a shared base, not a generic text/binary merger. Even disjoint field edits can violate cross-field constraints, so validate the result. If the head changes again during resolution, the proposed commit must CAS against the current head or surface another conflict.

              11. Correct clients handle renames, placeholders and partial writes

              Unsynchronized bytes

              • Preserve them during resnapshotting and remote-delete/local-edit conflicts.

              Recoverable application

              • Staged operations have durable identities and crash completion/replay paths.

              Client rollout

              • Use canaries, model-based tests and kill switches for destructive reconciliation bugs.

              Filesystem watchers are hints and can coalesce/drop events; use durable local indexes and reconciliation scans. Applications may write temporary files then rename, modify files during hashing or preserve timestamps/sizes despite changed bytes. Validate file identities and hashed-snapshot stability, retrying under policy when files change during reads. No watcher event does not prove disk and server equality.

              Case-insensitive volumes, Unicode normalization, reserved names, symlinks and path traversal need explicit platform rules. Remote a.txt and A.txt may not coexist on a volume; use representable conflict names or recoverable errors. Do not blindly follow symlinks outside the sync root. Stable-ID renames avoid treating moves as deletion plus full reupload.

              Selective sync and online-only placeholders are not user deletions. Remote tombstones differ from undownloaded files; local state must distinguish hydrated files, placeholders, exclusions, pending edits and deletions. Preserve unsynchronized content before resolving remote-delete/local-edit conflicts. Test tombstone retention and cursor expiry against long-offline devices.

              Folder moves must preserve an acyclic tree as well as naming and permission rules. If root contains A and B and moving A under B commits first, a stale offline move of B under A must conflict or be resolved because A is now B’s descendant. Checking old ancestry before an independent parent write is insufficient. Serialize related moves or use same-authority concurrency/validation that preserves the invariant at commit; cross-namespace moves have separate boundaries.

              12. History, restores and collection share reachability rules

              Blocks referenced by current heads, retained versions, pending uploads/commits or backup policies cannot be collected merely because a path was deleted. Reference counting needs idempotent increments/decrements and recovery from lost/duplicate events; mark-and-sweep needs consistent reachability barriers/epochs. Choose and justify a protocol instead of merely saying “collect after twenty-four hours.”

              Restore creates a new head revision and journal event referencing a retained manifest, rather than decrementing revision counters or rewinding namespace cursors. Metadata work can be cheap, but cold-tier bytes may need hydration, authorization still applies and reads still take time. Versions whose retained bytes have expired cannot be promised restorable.

              Threefold replication stores three byte copies; ten data plus four parity shards have nominal 1.4-fold overhead before metadata, repair and headroom. For 500 PB of unique bytes, arithmetic yields 1,500 PB versus 700 PB. Overhead alone does not establish equivalent durability: placement, correlated failures, repair time, corruption detection and degraded-read latency determine reliability. Tiering old versions needs measured access distributions, restore SLOs and costs rather than a universal age threshold.

              13. Deduplication privacy, shared folders and hot namespaces

              Global deduplication/existence APIs can create an oracle revealing whether someone else stored content. User/tenant scopes, suitable authorization/proof-of-possession protocols and traffic policies trade bandwidth/storage against privacy; knowing a hash is insufficient to claim/download a file. Convergent encryption retains confirmation/dictionary risks for predictable content and is not a general privacy fix. Design randomized encryption, tenant keys, rotation and recovery alongside deduplication policies rather than inventing cryptography.

              Shared folders are live authorization boundaries: check ACLs on commits, journal pages and block downloads, including revocation between upload and commit. Signed capabilities need appropriate scopes/expiry but cannot recall bytes recipients already downloaded. Encryption at rest is not E2EE; E2EE changes sharing/key recovery, scanning and deduplication scopes.

              Namespace sharding keeps transactions local but very hot team folders can still bottleneck ownership/order. Batch/coalesce notifications, bound journal pages and apply admission/quotas/fair scheduling before splitting namespaces. Partitioning a namespace requires new ordering, rename/move atomicity and cursor semantics; consistent hashing alone supplies no cross-shard transaction. Home-region failover needs fencing and explicit durability/RPO contracts, not two writers independently assigning the same head revision.

              14. Test from acknowledged bytes to files appearing on disk

              Measure upload-to-commit, commit-to-device-applied, pending-operation ages, journal lag, stale-parent conflicts, integrity failures, orphan/pin ages, collection backlogs and restore success/time. Separate offline states, quotas, full disks and denied permissions from server errors. A 200 response does not establish synchronization if filesystem application failed. Segment by client version, platform and namespace size to detect rollout regressions.

              15. Interview questions and invariant-based reasoning

              Explain bytes, identities, ordering boundaries and recovery in each answer. Change an assumption and recheck guarantees rather than treating object storage plus Redis plus a queue as a complete answer.

              How much is uploaded after a one-byte edit to a 2 GB file?

              An in-place overwrite with fixed 4 MiB chunks normally changes one chunk. Upload it if absent from the authorized scope, then commit the manifest. An insertion near the start shifts boundaries and can change many chunks. CDC may resynchronize without guaranteeing a single changed chunk. Media re-exports can rewrite the entire file.

              Can an mtime-and-size hash cache miss changed bytes?

              Who wins when A and B both commit parentRev=5?

              The authority serializes CAS operations: the first accepted commit becomes revision 6 and the other stale commit conflicts. Device clocks do not decide. Preserve pending bytes; keep-both creates a new file ID idempotently, or a user merges with a format-aware application.

              Does checking blocks before a metadata transaction prevent missing bytes?

              No. Collection can delete blocks between those operations. Use pending pins/protected receipts and durable reachability handoffs with collectors/reconcilers; SQL transactions do not automatically include object stores. Test crashes and expiry at the gaps.

              Does a journal alone make devices catch up after a lost notification?

              A journal preserves authority but devices must still read it. Losing the last hint on a live socket needs periodic polling/watermarks or another bounded recovery trigger. Fetch, verify and apply before checkpointing; expired cursors require resnapshotting that preserves pending edits.

              Does renaming a large file require a full reupload?

              Not with stable identities and unchanged bytes: update parent/name and journals under concurrency rules. Paths should not be sole identities. Cross-namespace moves, name collisions and filesystem case/Unicode rules need explicit semantics.

              Should global deduplication be enabled for every tenant to save space?

              Not automatically. Existence/timing can reveal content presence, and digests do not establish read rights. Choose scopes, encryption and authorization under the privacy model. Convergent encryption does not remove confirmation/dictionary risks; balance bandwidth/storage with isolation.

              Does 10+4 coding have the same durability as three replicas?

              Shard counts alone cannot establish that. The 1.4-fold and threefold values are storage arithmetic; reliability depends on placement, correlated faults, repair, scrubbing and operational errors. Test degraded reads/restore SLOs alongside costs.

              Should restoring an old version lower the head revision?

              No. Create a new revision referencing a retained old manifest and append a journal event. This preserves monotonic history/cursor semantics; check authorization and byte availability, including cold-tier restore latency.
