LLM Gateway: policy-bound routing, streaming and trustworthy usage

Design shared AI traffic with aliases, qualified routes, replay boundaries, quotas, atomic reservations, per-attempt accounting, scoped caches and multi-region recovery.

From contracts to usage evidence

  2. Reserve / route

  3. Attempt / stream

  4. Reconcile

A request can fail before or after billable work; assign ownership to each transition.

  • An alias is a versioned, qualified contract; identical API shapes do not imply identical model behavior.
  • Filter data, region, capability and qualification constraints before ranking routes; fallback preserves those constraints.
  • No visible token does not establish replay safety; track visible output, tool effects and upstream uncertainty separately.
  • Reservations bound exposure; usage ledgers retain billable attempts and explicit pending evidence.
  • Rate buckets, concurrency caps and durable financial budgets are different controls.
  • Tenant cache scope and temperature zero do not establish authorization, freshness or determinism.

1. Centralize coordination while preserving application semantics

Application contract

  • Own task correctness, authorized tools and user-facing recovery.
  • Qualify changed model behavior with application-specific evaluations.

Gateway contract

  • Authenticate workloads, enforce routing/data policy and bound exposure.
  • Preserve identities needed for diagnosis and reconciliation.

Provider contract

  • Actual capabilities, limits, billing, retention and deployment locations.
  • Unknown outcomes do not establish zero work or zero cost.

Many teams introduce fragmented credentials, capacity limits, audit and cost attribution. A gateway centralizes traffic coordination while applications retain task semantics, user authorization, retrieval correctness and tool-effect authority. Compatible endpoints do not make models interchangeable.

Define supported modalities, streaming/tools/schemas, aliases, priorities, data rules, budgets and failure behavior. Choose measured workload-specific overhead targets rather than universal millisecond guarantees. Shared dependencies and correlated outages can defeat apparent multi-provider availability.

2. Estimate streams, tokens and logging separately

Assume 300 applications, 50 million logical calls/day, a 3× peak, 3000 input and 500 output tokens/call, and eight seconds of mean active streaming. These are illustrative workload inputs. Retries can increase upstream attempts. Little’s Law relates compatible average rates and mean residence times, not arbitrary tail percentiles.

A sustained peak of about 1736 calls/s with that mean duration implies roughly 13889 active streams. Size buffers, event overhead, heartbeats, TLS and slow consumers through load tests. Fourteen kilobytes of raw payload per call would produce 700 GB/day in decimal units; this is a storage estimate, not a recommendation to log every prompt.

3. Separate operation, attempt and configuration identities

Authenticate workloads instead of trusting browser-supplied tenant/team headers. These illustrative internal APIs are not universal provider contracts. Reject unsupported features rather than silently dropping tools, safety controls or output formats. Trusted entitlement mappings govern project attribution.

          4. Separate data, control and accounting planes

          Use bounded asynchronous data paths and usable route snapshots while giving reservation and ledger authorities explicit consistency contracts. Applications hold no provider secrets. Asynchronous metering requires durable delivery and backpressure, rather than losing evidence after a crash.

          A logical request can have multiple attempts and usage records

          Component map; the complete ordered request paths are explained below.

          Admit and stream a request

          1. Authenticate workloads and validate supported contracts.
          2. Reserve bounded quota and budgets under operation identities.
          3. Pin policies and required capabilities.
          4. Select eligible targets and create attempt identities.
          5. Dispatch under explicit provider feature profiles.
          6. Forward typed events with bounded buffers and lifecycle state.
          7. Expose generation identities and explicit terminal/error states.

          Fail over within replay and exposure policies

          1. Classify failures and retain attempt evidence.
          2. Check deadlines, attempts, visible effects and fallback eligibility.
          3. Dispatch permitted attempts with appropriate additional reservations.
          4. Return valid replacement generations or explicit errors.

          Settle evidenced attempts

          1. Persist provider usage and identities even for abandoned clients.
          2. Record usage under the self-hosted metering contract.
          3. Deduplicate and correct attempts without collapsing real retries.
          4. Settle known charges and retain unresolved holds under policy.
          5. Attribute scoped totals and explicit uncertainty.

          Roll out aliases and governance

          1. Publish qualified route versions and hard data rules.
          2. Rotate scoped credentials and capability profiles.
          3. Distribute entitlement and revocation epochs.
          4. Review canary quality, violations, timing and rollback.

          Reconcile disconnects and crashes

          1. Persist interruptions with unknown usage states.
          2. Find outstanding reservations using durable identities.
          3. Merge late evidence and reconcile against available upstream records.
          4. Adjust holds under reconciliation policy without assuming zero usage.

          5. An alias binds capabilities and qualified behavior

          Aliases need owners, capability/context/output limits, data rules and consuming-task quality gates. Pin revisions and compatible fallback sets. Tool support alone does not establish compatible schemas, parallel-call behavior, termination reasons, tokenization or error events.

          Normalize declared features while retaining provenance and unsupported states. Do not silently route tool requests to text-only models. Preserve needed provider distinctions instead of pretending all features are universal. Breaking changes need migration paths, and rollbacks need compatible credentials, schemas and capacity.

          6. Apply hard constraints before route preferences

          Filter entitlements, locations, data handling, capabilities, context size and task qualification before optimizing cost or latency. Healthy endpoints can still violate policy or quality requirements. Predictions are uncertain, and cheap routing must not silently lower quality. Validate fallback capacity and shared dependencies.

          7. Replay safety requires more than no visible token

          Distinguish validation/auth errors, capacity rejection, connection failure, server errors and unknown timeouts. A lost response can hide upstream execution. Policy may permit replay of generation while accepting duplicate computation or cost, but side effects need cooperating idempotency and recovery. A gateway request ID is not automatically honored by providers or tools.

          Track exposed events, tool effects and generation identity. After partial output, do not silently splice another run into the same answer. Report interruption or use an explicit application-supported replacement/resume protocol. Even pre-exposure retries must satisfy replay policy, remaining deadlines, attempt budgets and hard constraints.

          8. Request rates, token rates, concurrency and spend differ

          Request rates protect admission resources; token rates follow provider semantics; concurrency caps protect active work; durable spend budgets bound financial exposure. Providers can split input, output and cache accounting across different scopes. Do not assume one combined TPM bucket fits every deployment.

          Combine organization/provider, tenant/team/project and priority controls. Reserved shares need borrowing/reclaim rules and bounded queues. Parse available Retry-After information under the contract, respect it with bounded jitter, and avoid endless retries for hard caps. Coordinate SDK and gateway retries under one end-to-end budget.

          9. Reserve before dispatch and settle from evidence

          Owned reservation lifecycle

          1. Hold

            Create atomic operation-scoped holds before dispatch.

          2. Attempt

            Persist attempt, deployment and exposure identities.

          3. Evidence

            Merge known usage and retain missing final evidence as pending.

          4. Adjust

            Apply idempotent settlements, corrections and release rules.

          Crashes can occur between any steps; unknown is not settled zero.

          Reserve bounded exposure from input estimates, output caps, allowed attempts and pricing assumptions. Count the applicable tokenizer and overhead. Additional billable categories or unreserved retries can invalidate a claimed upper bound. Atomic check-and-hold prevents concurrent overspend, and idempotent admission binds operation scopes and payload hashes.

          Keep refillable rate buckets distinct from durable financial reservations. Financial holds must survive crashes, resist duplicate settlement/release and retain unresolved liabilities. Define available budget consistently as limits less settled exposure and outstanding holds, and handle actual usage that can exceed estimates.

          10. Distinguish requests, attempts and usage revisions

          A timed-out first attempt and successful fallback can both incur usage. Attribute through parent request IDs while metering child attempts. Deduplicate replayed evidence by attempt/event identity or cumulative revision, not just the parent request. Summing every cumulative usage sample also overcounts; adapters distinguish deltas, cumulative updates and final evidence.

          Retain upstream identities, model revisions, usage categories, currencies/rates, evidence sources, reconciliation states and corrections. Record adjustments with lineage. Reported usage can arrive late or differ from invoice rounding/categories, so reconcile available records. Disconnecting or cancelling does not establish that upstream work or billing stopped.

          11. Bound stream memory and expose explicit lifecycle states

          Use asynchronous I/O with bounded buffering, backpressure and slow-consumer limits. Incremental forwarding still requires protocol/TLS buffers. Configure proxy buffering, idle/overall timeouts, heartbeats, cancellation and graceful draining; load-test churn and stalled clients.

          A successful HTTP stream opening does not guarantee generation completion. Parse partial frames, versioned events, usage updates, errors and tool fragments under the adapter contract. Do not fabricate valid JSON or execute incomplete arguments. Continuation requires retained state and explicit idempotency rather than disguised replay.

          12. Cache identity includes authorization and freshness

          Response reuse needs eligible task semantics and identities for requests, context, tools, schemas, settings, models, access scope and dependencies. Temperature zero does not guarantee determinism. Exact keys can still serve stale data or bypass intended tools, and users within a tenant can have different permissions. Hits require current authorization and freshness checks.

          Semantic similarity does not establish equivalent questions, permissions or actions. Restrict reuse to eligible classes with validation and measured risk. Prefix KV caching is different: it can reuse compatible model state while generating new output. Revocations and freshness rules still apply during outages.

          13. Govern secrets, egress and minimized logs

          Centralized sensitive traffic increases the consequences of weak controls. Use workload identity, scoped credentials, rotation, separated administrative permissions and audited configuration. Data-location, retention and training rules must match actual endpoints. Self-hosting alone does not establish privacy or security.

          Prefer scoped usage, timing and error metadata over full payload logs. Redaction can miss secrets and does not replace minimization, access control or retention/deletion. Bounded debug capture needs explicit authorization and enforcement before transmission/storage. Metadata can also reveal sensitive identities, so govern it appropriately.

          14. Model authoritative records and consistency boundaries

          Version routes with targets, constraints, qualification and rollout epochs. Bind operations to authenticated scope, payload hashes, policies and deadlines. Attempts record dispatch, exposure and usage evidence. Reservations retain authoritative epochs and settlement lineage; adjustments bind evidence and rates.

          Trace IDs provide correlation, not automatic uniqueness or exactly-once effects. Enforce transitions through storage constraints and recovery-aware messaging. Define failures between reservation, dispatch, evidence and settlement rather than assuming cross-service atomicity. Fence reconciliation ownership to prevent duplicate corrections.

          15. Make regional and quota-outage trade-offs explicit

          Distributed data planes reduce some failures while shared DNS, identity, quota, secrets and upstream pools remain common dependencies. Bound cached configuration validity and revocation freshness. Stream recovery follows actual protocol support and can require an explicit new generation.

          Quota outages need explicit policy. Hard-budget tenants may fail closed; other tiers can use preallocated bounded local allowances with ownership controls. Regional allocation trades utilization and fairness for bounded exposure. Eventual counters alone cannot enforce strict global caps. Define availability, spending and incident-override authority before failures occur.

          16. Qualify routes with quality, cost and operational evidence

          Measure admission, queue, useful-output and completion timing alongside usage categories, route exhaustion, retries, rate-limit reasons, pending usage and policy violations. HTTP success alone misses schema/tool failures and quality regressions. Segment by workload and revision while retaining abandoned streams and explicit denominators.

          Model, prompt and adapter changes require task-specific evaluations, capacity validation, bounded rollout and rollback. Shadowing still incurs cost and data exposure and must prevent duplicate effects. Self-hosting economics include utilization, staffing, warm capacity and redundancy. Build or adopt according to measured policy, integration and operational needs.

          17. Practice LLM Gateway decisions

          What should happen when a primary returns 429 at peak?

          Classify the limiting scope, respect retry guidance and protect priorities under bounded deadlines and attempts. Use qualified fallbacks with available capacity and policy approval, avoiding retry multiplication or retries against hard caps.

          Is a timeout before the first token necessarily replay-safe?

          No. Upstream work can occur without a delivered response. Generation replay needs explicit duplicate-work policy; side effects need cooperating recovery and idempotency.

          Why is request-only usage deduplication insufficient?

          Requests can contain multiple billable attempts. Deduplicate attempt evidence and cumulative revisions while retaining parent attribution; request-only keys can undercount and missing dedup can overcount.

          Should all holds be refunded when a client disconnects without final usage?

          Do not assume zero usage. Retain pending evidence, reconcile reports and apply explicit risk/expiry policies. Cancellation does not establish zero billing; bound unresolved liabilities.

          Is failing open a good universal quota-outage policy?

          No. Hard caps can require rejection, while preallocated local allowances can bound selected risks. Choose policies and recovery rules in advance.

          Are temperature-zero caches with tenant keys necessarily safe?

          Not necessarily. Determinism, user permissions, dependency freshness and tool semantics require explicit eligibility and current checks.

          Does changing a fast alias need evaluation if the API shape stays the same?

          Yes. Quality, tools, schemas, errors and usage can differ despite matching shapes. Qualify tasks and versions with controlled rollout and rollback.

          How would you estimate concurrent streams from QPS?

          Use compatible average arrival rates and mean residence times in stable windows. Validate tails, slow consumers and resource headroom with measurements rather than arbitrary percentile arithmetic.
