KV Cache, Memory & Quantization: budget bytes and reuse the right state

Connect attention state to per-rank memory, paged allocation, prefix identity, copy-on-write, offloading and precision rollouts through four numerical experiments.

A budget across the request lifecycle

    Read layers, KV heads, dimensions, context policy and cache format.

  2. Budget each rank

    Budget weights, scales, KV, workspace and safe headroom.

  3. Manage pages

    Allocate, share, grow, copy on write and release safely.

  4. Measure and gate

    Evaluate quality, TTFT/TPOT, preemptions and realistic loaded capacity.

Separate logical tokens from physical bytes and state reuse from result reuse.

  • KV stores processed token/context state; it differs from weights and response caches.
  • Dense KV bytes depend on KV heads, dimensions, layers/context and dtype; the same formula does not fit every architecture.
  • Check each rank with head replication, workspace and future growth; aggregate HBM is not automatically a shared pool.
  • Paging reduces reservation waste without creating unlimited token capacity; shared mutable tails need copy-on-write.
  • Prefix hits require exact state identity and placement; they reduce reused prefill work without removing history reads during decode.
  • Quantization and offloading trade memory, quality, kernels and latency under measured workloads.

1. What does KV store?

Weights

  • Model/adapter parameters and formats/scales, usually shared by replica requests.

KV state

  • Token history and execution context determine state; memory follows live lengths or architectural windows.

Working memory

  • Activations, workspaces, graphs, communication buffers and allocation overhead need separate space.

Causal self-attention creates keys and values for processed tokens at each layer. Caching avoids recomputing their projections, while later attention still accesses the history retained by the architecture. Decode does not become independent of context. Weights are model parameters; KV is sequence state with a different lifetime and scaling behavior.

KV is not a stored completed answer. Prefix caching reuses state while new turns and outputs still require work; response caches reuse completed results under different contracts. Engines may release, retain, offload or recompute state between calls. An application session identity does not prove GPU residency.

2. Dense KV formulas and units

For a sequence, sum T_l × H_KV,l × (d_K,l × bytes_K,l + d_V,l × bytes_V,l) across dense attention layers. Uniform layers reduce this to 2 × L × H_KV × d × bytes/value × T. Sum sequence lengths for multiple sequences; maximum context times request count is a deliberate reservation/worst-case calculation, not actual live usage.

A hypothetical shape with L=80, H_KV=8, d=128 and two-byte BF16 uses 327,680 bytes/320 KiB per token and 10 GiB at 32,768 tokens. Use KV heads rather than query heads. Decimal GB and binary GiB differ: 70 billion two-byte weights occupy about 140 GB/130.39 GiB, excluding padding, scales, duplicated heads and workspaces.

uniform_dense_KV_bytes = 2 * layers * kv_heads * head_dim * bytes_per_value * live_tokens
logical_batch_KV_bytes = sum(KV_bytes(sequence) for sequence in live_sequences)
per_rank_required = rank_weights + rank_KV + rank_workspace + rank_runtime_reserve
# Check every rank, not only sum(all_GPU_memory).
# Sliding-window / hybrid / latent-attention caches need their own layout formula.

Logical payload is a starting point rather than a complete engine memory estimate.

3. MHA, GQA, MQA and exceptions

MHA has KV for each attention head; GQA shares KV across groups of query heads; MQA uses one KV head. These belong to the checkpoint/architecture, not arbitrary serving flags that preserve the same model. Architectural changes may require training/uptraining and quality validation. Changing cache dtype does not convert MHA into GQA.

Sliding-window layers retain architecture-defined history while global layers may keep growing. Hybrid recurrent/state-space and compressed/latent attention have other layouts, requiring model/backend inspection. FlashAttention improves attention IO/intermediates without eliminating all persistent autoregressive KV. Arbitrarily dropping old full-attention tokens changes semantics.

4. Per-rank memory and head replication

Tensor parallelism does not divide every tensor by TP. In a mapping that shards KV heads when possible and replicates beyond the head count, each rank retains at least one KV head. With eight KV heads, increasing TP from eight to sixteen doubles aggregate physical KV without further reducing local cache. Other mappings, pipeline layers, embeddings and uneven shards need engine-specific accounting.

FITS only means that assumed current payloads fit each rank. Real concurrency also depends on future outputs, graph/workspace peaks, speculative branches, adapters, communication and latency targets. A capacity count at one context length is not safe admission for a different length distribution.

5. Paged allocation and future growth

Each sequence maps logical blocks to physical pool pages instead of reserving one maximum-length contiguous region. Tail rounding and block-table/kernel costs remain. Small pages reduce slack but increase indirection, while larger pages coarsen sharing and copy-on-write. Choose sizes supported and measured by the backend.

A prompt that fits now may run out of pages during generation. Schedulers can reserve, preempt/recompute or queue under explicit policies. Paging does not promise unlimited concurrency at unchanged latency. Cancellation/completion must not free pages still referenced by other sequences or unfinished kernels.

6. Exact prefix reuse and copy-on-write

Later-block KV depends on preceding tokens/context, not only the block’s tokens. Bind ancestry and execution identity: weight revisions, adapters, positions/RoPE, cache formats/scales and multimodal inputs. Equal image-placeholder IDs do not establish equal image tensors. Use appropriate collision handling and trusted cache/tenant scope rather than requester-asserted identities.

In this full-block fixture, twelve cached tokens in a fourteen-token request leave two uncached tail tokens; changing token five preserves only the first four-token block. Engines may need tail/last-token work for logits and use different granularities. Sampling forks can share partial tails but require copy-on-write on append, unlike published full-block APC.

7. Trace KV across five paths

Cold and Warm show precisely which work reuse replaces. Decode still reads retained history and grows tails/pages. Offload and Release expose validity, ownership and asynchronous completion: correct CPU metadata does not prove GPU copies are ready. KV is not the durable source of truth for conversation history.

KV has identity, ownership and a lifetime

Component map; the complete ordered request paths are explained below.

Trace uncached prefill, reuse, decode growth, offloading and release separately. A cache hit is not a pre-generated answer.

Cold prefill

  1. Serialize the prompt and validate token/context bounds.
  2. Pass prompt/output budgets and pinned execution context.
  3. Look up a reusable prefix with correct identity and placement.
  4. On a miss, allocate uncached pages within budget.
  5. Run prefill on uncached context under the selected profile.
  6. Write KV with valid block ownership and reference counts.

Warm prefix, new tail

  1. Match token prefixes and compatible context, not merely similar text.
  2. Validate resident full blocks and pin them before reuse.
  3. Add references without mutating shared pages.
  4. Compute uncached tails/logits as required; future output still needs decoding.

Decode and page growth

  1. Schedule bounded decode work under fairness/latency budgets.
  2. Read retained attention context; cached prefixes still generate memory traffic.
  3. Appending needs tail capacity or copy-on-write when shared.
  4. Publish new KV with appropriate write ordering.
  5. Stream tokens and update live lengths/usage.

Preempt, transfer and resume

  1. Choose victims under SLO/fairness policy at safe points.
  2. Copy payload/context and reclaim only after completion and ownership checks.
  3. Reload the correct version/format/sequence within transfer budgets.
  4. Resume only when required state is ready; otherwise recompute or reject.

Cancel and safe release

  1. Cancellation or completion prevents new scheduling.
  2. Fence outstanding work; pages cannot be freed while kernels use them.
  3. Release references at a safe completion boundary.
  4. Unreferenced reusable blocks may remain cached or be evicted by policy.

8. Routing, locality and tenant isolation

Locality

  • Ask where cached state lives, whether it remains resident and how long its queue is.

KV identity

  • Bind exact execution/input context; retrieval similarity is not KV equality.

KV isolation

  • Enforce access/trusted scope before reuse and define retention/side-channel threats.

A warm replica can be overloaded; locality-only routing can worsen TTFT. Compare avoided prefill against queue/transfer costs and deadlines. Prefix hashing creates affinity but cannot guarantee residency after eviction/restarts. Disaggregated prefill/decode needs compatible state, ownership and transfer budgets.

Cache policy follows access boundaries rather than maximizing hits by removing scope. Similar text grants no private-prefix permission, and KV/timing signals may be sensitive. Eviction does not replace privacy/deletion policy across replicas, host tiers and logs. Stable instructions/schemas can help reuse when prompt semantics, permissions and freshness are preserved.

9. Preempt, offload or recompute?

HBM is finite. Host tiers can retain reusable or preempted state, but both outgoing and incoming copies cost bandwidth unless valid backing already exists. Payload/bandwidth arithmetic excludes queues, synchronization, conversion and contention. Layer-wise overlap can change latency, so peak bandwidth comparisons alone cannot establish SLOs.

Recomputation needs retained inputs/context and available budgets. Offloading resumes only matching, complete, correctly owned state. Reject stale payloads and avoid repeatedly evicting the same long-context users, which inflates tails and wasted compute despite attractive averages.

10. Weights, activations and KV are separate precision decisions

Weight-only INT4 reduces stored weight payload, not automatically KV or every multiplication. Metadata, packing, dequantization and supported kernels determine actual memory and speed. W8A8 also quantizes activations; FP8 and INT8 are distinct formats/paths. KV quantization has its own scales, calibration and backend requirements.

GPTQ uses approximate second-order information for post-training weight quantization; AWQ uses activation statistics to protect salient channels; LLM.int8() handles outlier-sensitive work in higher precision. These techniques do not guarantee universal quality or speed. Memory-traffic reductions can help decode while compute-bound prefill or conversion-heavy paths may benefit less or slow down.

12. Gate precision changes on quality

A gated precision change

  1. Freeze a baseline

    Pin model/data/workload versions and thresholds.

  2. Calibrate and evaluate

    Check scales, kernels, task slices and long-context tails.

  3. Load test and canary

    Measure TTFT/TPOT, memory peaks, errors and quality.

  4. Version and roll back

    Separate profile/cache namespaces with proven rollback.

Memory savings alone do not justify rollout.

Use representative languages, code/math, structured outputs/tools, long contexts/retrieval and failure-sensitive tasks. Keep calibration data separate from held-out evaluation to avoid tuning choices to the evaluation examples. Perplexity does not replace product correctness, safety or accepted regression thresholds.

Measure quality with matched workload latency, throughput and cost. Canary by profile/tier and keep rollback formats separate. Mathematical equivalence does not guarantee bitwise-identical outputs across kernels; use suitable deterministic setups, tolerances and product metrics.

13. Admit by bytes, tokens and deadlines

Request counts hide length differences. Admission considers physical pages, growth policies, per-rank limits, work and deadlines. Shared prefixes reduce duplication but referenced/pinned pages may not be evictable. Low compute utilization does not rule out memory capacity or bandwidth bottlenecks.

Distinguish live KV, evictable cache, pinned transfers, free pages and growth reservations. Queueing still costs deadlines; explicitly reject or degrade under policy when budgets cannot be met. Enforce understandable context/output limits on serialized tokens rather than truncating text to fit a memory chart.

14. Failure signals and verification

Track per-rank allocated/live/free/shared pages, workspace peaks, COW events, eligible-token prefix hits, evictions/transfers/preemptions and recomputed tokens. Correlate profile versions, lengths, queue/TTFT/TPOT tails and error types while governing sensitive tensors/prompts in logs.

Test cancellation during kernels, shared-prefix eviction, partial-tail forks, identity changes, failed transfers and worker restarts. Losing caches may require recomputation, while conversation/history durability belongs to a separate storage policy. An optimization cache must not be the only remaining source of recovery inputs.

15. Questions with reasoning and calculations

How much KV does an 80-layer / 8-KV-head / d128 / BF16 shape need at 32K tokens?

The shape uses 327,680 bytes / 320 KiB per token. Here 32K means 32,768 tokens, giving 10 GiB of logical payload; 32,000 tokens would differ. Per-rank physical accounting still needs placement/replication, pages/scales/workspaces and other live sequences.

Does increasing TP from 8 to 16 halve every KV allocation?

Not in this fixture’s eight-head mapping, which replicates beyond the head count. Both settings retain one local KV head per rank, so sixteen ranks double aggregate physical KV. Weight sharding and communication have separate behavior; inspect actual layouts instead of dividing total bytes by device count.

If current pages fit, can every request continue decoding?

No. With eight-token blocks and shared prefixes, current lengths use 72 slots and admit four requests, but eight more tokens each require 104 slots in a 96-slot pool. Reserving growth admits three in this fixture. Other policies must expose queueing, preemption and latency costs.

How much of a 12-token prefix can be reused after changing token 5?

With four-token full blocks, only the first four tokens remain reusable. Later blocks depend on preceding context even if their own tokens match. An unchanged twelve-token prefix in a fourteen-token request reuses twelve and computes two here, subject to actual engine tail/logit/granularity requirements.

Do INT4 weights make total memory one quarter of BF16?

Only raw weight payload may be one quarter. Metadata, packing and unquantized tensors add bytes; KV, workspaces, activations and graphs have separate formats. Measure loaded footprints and peaks, including dequantization, rather than inferring fourfold total-memory or speed gains.

Does offloading 4 GiB over 16 GB/s take only 250 ms?

One binary 4 GiB payload over decimal 16 GB/s takes about 268.4 ms per direction before overhead. A round trip is about 536.9 ms, or 540.9 ms with this fixture’s overhead. Existing valid CPU backing permits a roughly 270.4 ms reload. Contention and overlap still affect actual latency.

Should matching prompts reuse KV across tenants to improve hits?

Follow explicitly authorized cache-sharing policies, not text similarity alone. This fixture isolates tenants through trusted scope, so cross-tenant reuse is unsafe when that scope is omitted. Model, adapter, positional, multimodal and cache-format contexts must also match; hits do not grant permissions.

Compute utilization is 40% but KV is full: does more compute solve it?

Memory capacity or bandwidth may bind before FLOPs. Inspect per-rank live, evictable, pinned and reserved pages, lengths and growth policies. Evaluate reservations/paging, authorized reuse, quality-gated precision and memory/pool capacity under measured SLOs. Compute-only autoscaling misses queueing, TTFT/TPOT and preemption behavior.

Explain and compare the mechanisms

These open questions connect terminology to state, assumptions and failure boundaries. Try an example from your own work before comparing the explanation.

How do weight and KV quantization affect memory, speed and quality?

Lower precision can reduce weight or KV bytes and memory traffic, but these allocations are independent. Four-bit weights do not automatically quantize KV, activations or temporary state. Scales, zero points, packing, alignment and unquantized layers add overhead; supported kernels and dequantization can dominate latency beyond theoretical bit ratios.

Evaluate real tasks, languages, structured outputs and long contexts, including rare numerical cases. Compare matched configurations rather than assuming INT4 is always faster than BF16. Account for per-rank KV placement and page allocators; weight savings only help constraints that can use the headroom. Version the recipe and retain evaluation and rollback paths.
