Designing a Video Platform: uploads, ABR and CDNs

Separate ingestion/processing from playback; explore progressive publication, buffering under changing throughput and viewer/origin bandwidth to understand quality, availability and resource trade-offs.

  2. Encode and publish

  3. Adapt and deliver

1. Two systems: ingestion and playback

Time-to-playable

  • Completed upload is not playable publication: integrity, probing, encoding, packaging and gates remain.

Playback QoE

  • Measure startup, rebuffering, quality/switching and errors by device, ISP and region.

Bytes and authorization

  • CDNs reduce origin load without eliminating viewer egress; cached media still needs appropriate access policy.

A video platform has a pipeline turning uploads into playable assets and a delivery path sending bytes to viewers. Control APIs manage ownership, metadata, state and playback authorization; data planes handle object uploads, transcoding, CDNs and players. Separation supports independent scaling/failures and avoids proxying every GB through app servers in this baseline, rather than universally banning upload proxies.

The baseline is on-demand video with resumable uploads, compatible renditions/codecs, titles/thumbnails/captions and smooth playback. Live, recommendations, comments and advertising are separate scopes. Targets such as a first frame under two seconds or publication within minutes need device/network cohorts, file sizes and processing workloads rather than universal promises for all 4K files and slow networks.

2. Calculate egress, ingestion and rendition sizes separately

An example of 50 million DAU × five views × 600 seconds/view × 3 Mbit/second yields about 56.25 PB/day or 5.21 Tbit/second average viewer delivery. Watch time and delivered bitrate vary by product/device; views alone do not size bandwidth. CDN cache hits do not eliminate viewer-delivered bytes.

Five hundred thousand daily uploads × 300 MB raw gives 150 TB/day ingestion. Encoded storage is not inherently 1–1.5 times raw size: it is roughly Σ(duration × rendition bitrate / 8) plus audio, containers and metadata. A 600-second example and a summed 11.7 Mbit/second ladder produce about 877.5 MB/video or 438.75 TB/day if every rendition is generated. Generate appropriate source/client renditions rather than upscaling merely to fill a ladder.

3. Upload, completion and playback-session contracts

Create/complete operations use owner/session-scoped idempotency. Signed requests are limited to object/part/operation and expiry; refreshing a URL does not create another video. Issue part URLs in pages when appropriate. Verify storage completion, size, integrity and object version server-side rather than trusting a client’s part list.

            4. Separate control and data planes

            Metadata stores desired/publication state, source versions and pipeline generations. Raw/encoded buckets are not public authorization bypasses. Stable-identity processing jobs use durable admission; duplicate/out-of-order object events require source/session-version checks. Outboxes/reconciliation connect storage completion to database/job state because these usually lack one shared transaction.

            Playback APIs do not proxy every segment, and viewers do not access databases directly. APIs authorize published asset versions while CDNs/players transfer media. Define retry, deadlines and byte/state ownership at each arrow, especially when stale jobs finish after cancellation/deletion.

            Upload/processing and playback are separate paths

            Component map; the complete ordered request paths are explained below.

            APIs control authorization/state, object storage holds media bytes and CDNs serve playback. Publication requires valid artifacts and gates; this is a teaching architecture.

            Create and resume an upload

            1. Create a video with an idempotency key, metadata and expected size.
            2. Commit the owner/session in UPLOADING with an object key isolated from other uploads.
            3. Return the committed video/session identity.
            4. Issue scoped expiring part requests; refresh within the same session when needed.
            5. Upload parts directly, retry failed parts and retain checksums/progress.
            6. Storage acknowledges parts; final-object availability follows storage completion semantics.
            7. Request completion; the server verifies ownership/session and storage results.
            8. Complete/verify object size, integrity and exact source version.
            9. Return a validated object version rather than relying on a client claim.
            10. Record the verified source and processing intent/outbox under the recovery contract.
            11. Relay/admission publishes a stable-identity job after durable state.

            Encode before publishing a manifest

            1. Claim a source/pipeline version; retries cannot substitute a different source under one job ID.
            2. Read the verified source object version.
            3. Return source data for resource-bounded probing/parallel encoding.
            4. Write segments/derivatives into an immutable staging version and validate integrity, decode and timing.
            5. Artifacts exist and are readable before manifest references are published.
            6. Check the required ladder, validation and policy/rights gates for the current generation.
            7. Pass the gate; pending/blocked work cannot publish merely because encoding finished.
            8. Write an immutable manifest referencing valid assets only.
            9. The manifest version is ready.
            10. CAS the published pointer/READY by generation; stale jobs cannot overwrite DELETED/BLOCKED state.

            Authorize playback and fetch segments through a CDN

            1. Request playback with principal/device/context.
            2. Read desired/publication state and authorization policy.
            3. Return an allowed manifest version without treating PROCESSING as READY.
            4. Issue suitable manifest/session access with explicit expiry/revocation semantics.
            5. Request manifests/playlists/segments; each resource needs appropriate access control.
            6. An authorized cache hit returns bytes; ABR decides the next segment request.

            CDN miss and origin fill

            1. Request a published segment absent from the edge.
            2. After authorization/cache-key handling, a shield/origin request reads the correct immutable asset.
            3. Return the segment and cache under policy. Coalescing requires configuration rather than happening for every miss.
            4. Return bytes; the player observes download time/buffer, not merely API latency.
            Creator client
            Retains upload sessions/part progress for resumption; client completion alone does not prove valid media.
            Upload API
            Authorizes owners, creates sessions and signs appropriately scoped part requests. The baseline does not proxy media bytes.
            Metadata / state
            Stores video IDs, source versions, pipeline generations, desired state and published manifest pointers. Only services access the database.
            Playback API
            Checks visibility, entitlement, region and devices, then returns playback sessions/manifest access without raw-bucket access.
            Private raw objects
            Completes multipart uploads and validates size/checksums/source object versions. Lifecycle policies handle orphan/incomplete uploads.
            Processing jobs
            Durable jobs keyed by source/pipeline versions; idempotent admission handles duplicate/out-of-order storage events.
            Encode / package
            Probes, parallel encodes, packaging, audio/captions/thumbnails; task identity and immutable staged artifacts protect retries.
            Encoded origin
            Segments/manifests have immutable asset versions. CDN origin access is authorized; public URLs do not bypass publication gates.
            Publish gates
            Validation, policy/rights and required rendition coverage; READY cannot bypass mandatory gates.
            CDN / shield
            Caches by asset identity with appropriate authorization and configured miss coalescing.
            Viewer / ABR player
            Reads playlists/manifests, selects compatible renditions by throughput/buffer and reports sampled QoE.

            5. Resumable uploads are more than splitting files

            A resumable upload lifecycle

            1. Authorize and create a session

              Set ownership, keys, expected size and allowed operations.

            2. Upload parts

              Persist progress, retry failures and refresh scoped requests.

            3. Verify then enqueue

              Complete storage, pin source versions and durably schedule processing.

            A network failure should retry only necessary work; part success is not READY.

            Persist session IDs, part numbers/checksums and object identities for app-restart resumption. Retry failed parts rather than full files while tuning concurrency/part sizes to network/storage limits. Clean abandoned multipart uploads through lifecycle/abort policies; URL expiry does not mean every stored part is deleted. Part ETags are not universal whole-file integrity proofs.

            Verify the exact source object/version so old signed requests or late events cannot substitute a job’s input. If storage completion succeeds but DB updates fail, reconcile the correct processing intent. Direct upload still needs ownership, quota, container/file validation and bounded probing/decoding of malicious metadata.

            6. DAGs, task retries and progressive publication

            Probe sources, validate containers/streams, encode compatible renditions/codecs and package manifests/segments. Task identity includes source version, parameters and pipeline version. Use immutable staging or per-attempt namespaces with CAS-selected winners/manifest pointers rather than allowing workers to overwrite published bytes. Encoding retries are not inherently bit-for-bit deterministic.

            Parallel segment encoding needs compatible keyframes/GOPs, timebases, audio sync and packaging. Arbitrary byte splits do not ensure correct decoding or seams. Parallelism reduces wall time with enough capacity but adds scheduling/I/O/overlap overhead rather than proving unchanged total compute. Progressive publication can expose a minimum validated ladder before high renditions; all mandatory policy/rights gates still apply.

            Do not assume S3 multipart parts are a progressively readable final object. Encoding before upload completion needs suitable ingestion/fragments/container formats and a separate protocol, not simply starting a worker early. Measure ingestion, probing, queues, encoding, packaging and publication separately.

            The additional scheduler is independent of the earlier gate clock and the ABR bitrate ladder. Low/mid/high are illustrative work branches, not bitrate-derived encode times. Per source minute it assumes two worker-seconds of probing, 20/40/80 for encodes, and five for audio; packaging uses one worker-second per source minute plus five seconds. Each encode task adds entered overhead. Tasks occupy one worker, chunks have equal work and valid media boundaries are assumed. I/O, stragglers, codecs, external queues and failed attempts are excluded.

            For a ten-minute source, eight workers and two seconds overhead per encode task, one segment/rendition takes 837 seconds and 1,491 worker-seconds. Eight segments reduce the makespan to 243 seconds while raising work to 1,533 worker-seconds. There are 3S+3 tasks and packaging waits for every encode and audio task. Longest-ready-first scheduling is not guaranteed optimal. The model lower bound is max(work/workers, critical path); uploading, gates and viewer startup are outside that interval.

            7. Manifests must reference ready assets

            From task outputs to a published pointer

            1. Write staged assets

              Namespace by source/pipeline/attempt; required segments, initialization data, audio/captions exist.

            2. Validate and approve gates

              Validate integrity/timing/capabilities, policy epochs and the current generation.

            3. Manifest, then CAS pointer

              Write a manifest referencing valid assets and switch the pointer only if source/generation/desired state still match.

            4. Drain old versions

              Retain old assets for active players/caches under policy; cleanup must not revive taken-down versions.

            Immutable manifests and publication state are separate layers; mandatory gates still hold at the defined boundary.

            Write required segments/init/audio/captions first, validate availability/integrity/timing, publish immutable manifests and finally update pointer/READY under generation guards. Publishing READY before assets exist causes playback 404s; publishing stale jobs after takedown can revive content. Desired-state and processing generations prevent stale completion from overwriting BLOCKED/DELETED.

            Adding renditions creates another manifest version with valid references and conditionally updates its pointer. Retain old assets for suitable draining/cache lifetimes so active players do not break. Databases, object storage and caches do not automatically share a global transaction; test reconciliation, validation and rollout/rollback.

            -- Teaching sketch: approval/current epoch are in the same control authority.
-- The immutable manifest and referenced artifacts were already validated.
UPDATE videos
SET state = 'READY', published_manifest = :manifest_version
WHERE video_id = :video_id
  AND source_version = :verified_source
  AND processing_generation = :job_generation
  AND desired_state = 'ACTIVE'
  AND approved_generation = processing_generation
  AND approved_policy_epoch = current_policy_epoch;

-- Zero affected rows: stale/cancelled/blocked work must not force READY.
-- Keep its immutable output staged for reconciliation or safe cleanup.

            SQL pseudocode for a same-authority publication guard. Maintain approval/epochs atomically under the contract; this UPDATE creates no transaction across object storage, CDNs or external rights services.

            8. Codecs and ladders are conditional optimizations

            Codec choices depend on device/profile/level support, hardware decoding, quality targets, encoding latency and storage/egress. H.264, VP9 and AV1 do not have universal byte-saving ratios across content/encoders. Negotiate compatible playback instead of promising a universal codec, retaining necessary fallbacks without encoding every combination for every upload.

            Per-title/per-shot ladders adapt bitrate-quality trade-offs to content complexity: animation, talking heads and sports differ. Metrics such as VMAF aid quality assessment without replacing all human/device/latency concerns. Popular titles may justify expensive reencodes to save delivery bytes across many views, while the long tail uses cheaper initial ladders. Use measured quality, expected viewing and resource/cost budgets rather than a universal view threshold.

            9. ABR chooses quality using estimates and buffers

            HLS/DASH distribute media through playlists/manifests and suitable segments or byte ranges. Players choose supported renditions and switch at compatible boundaries. Throughput estimates describe the past, not future drops, while buffers buy reaction time. The highest bitrate does not necessarily maximize experience when startup/stalls worsen.

            ABR policies trade quality, startup, stalls and switching; the lab heuristic is not a production player. Short segments can react faster while adding request/container overhead. Prefetch can reduce startup when predictions are right and waste bytes/data when wrong. Real players impose buffer/pacing limits; the replay isolates download and drain arithmetic.

            The replay assigns available Mbps by segment index and holds it constant during each download rather than using wall-clock time. Different rule download times therefore must not be treated as one shared real-time network trace. The additional chart aligns network, chosen bitrate and rebuffer markers by segment index, while tables expose the predecision estimate; the buffer chart uses that index too. Production evaluation needs time-based traces and suitable transfer/RTT/pacing models.

            10. CDNs, shields and cache keys

            Immutable asset versions support long caching and safer pointer rollbacks than overwriting segments under the same URL. Edge → shield → origin reduces repeated cold fills with suitable keys/coalescing, not automatically one request per concurrent miss. Measure request and byte hit ratios separately; many small manifest hits do not prove good media-byte caching.

            Query tokens or varying headers can fragment caches. Do not strip authorization parameters and bypass access checks: edge authorization must validate requests before legitimately sharing media bytes. Cold caches, releases, multi-CDN failovers and origin outages require capacity/headroom and appropriate coalescing/backoff.

            Pre-positioning can warm predicted-popular asset versions in suitable regions/POPs before release, rather than copying the entire long tail to every edge. Warmup jobs need budgets/quotas and playback-compatible keys/versions without bypassing access/takedown policy. Measure useful versus wasted fill bytes, origin bursts and evictions; warming one tier does not establish hits at every viewer edge.

            11. Playback authorization, expiry and takedown

            Authorize playback sessions and protect required manifests, playlists, segments, captions/audio and key/license resources. Scoped expiring URLs/cookies cannot recall downloaded bytes, and metadata changes do not erase browser caches. Define revocation/takedown delay and coordinate edge policy, short-lived access, purges or suitable key/license controls.

            Configured CDN authorization can run before cache hits; neither assume hits are public nor assume they are authorized correctly. DRM/content encryption differs from access tokens and needs key/license lifecycle and device capabilities; it cannot universally prevent recording. Moderation/rights blocks must prevent new publication and policy-prohibited access even while old jobs run.

            12. Schemas and view events

            Metadata includes owner/visibility, desired state, verified source version, generation/pipeline version, rendition capabilities, manifest pointers and timestamps. Task/attempt records retain stages, artifacts/checksums and retry/errors rather than overwriting all evidence. Lifecycle policies cover orphans, incomplete uploads, unpublished derivatives and old published versions.

            Define a view as a play request, first frame or watched-time threshold. QoE telemetry and product view counts differ, with replay/bot/dedup policies. Asynchronous aggregation avoids hot metadata rows at scale, while exact/auditable counts may need stronger ledgers. Small deployments can use atomic counters; a scaling optimization is not a universal ban on UPDATE.

            Separate upload availability, time-to-playable and playback availability. Slow processing should not stop previously published content. Control outages may use bounded cached authorized state under the contract. Player CDN/quality fallbacks preserve asset/version/access compatibility, and origins cannot be assumed to absorb all viewer traffic after cold edges.

            14. Measure QoE and choose optimization levers

            Track upload completion/abandonment, stage queues, retries/waste, minimum-playable time and full-ladder time. Playback measures click-to-first-frame, rebuffer duration/ratio, switches, errors and delivered bitrate by device/codec/ISP/region/CDN. Fast API responses do not prove fast decoding or first frames.

            Separate ingestion/raw/encoded storage, encode/reencode compute, viewer delivery and origin fills. Higher bills need not reflect more views: watch time, bitrates, geography, cache fragmentation or provider contracts can change. Compare equivalent cohorts/QoE before reducing bitrates. Real-user-based multi-CDN routing needs bias checks and fallback capacity.

            15. Video interview questions and worked reasoning

            Trace an upload session to a durable source, a task retry, a publication pointer and a segment download. Then change network conditions or fail a high rendition to test guarantees.

            Does adding workers always reduce slow 4K time-to-publication?

            Not when ingestion, serial stages or indivisible tasks bottleneck. Profile stages, parallelize at valid boundaries and prioritize a compatible minimum ladder plus gates. Progressive publication can reduce first-playable time without skipping validation or inherently reducing total compute.

            Can READY be set before uploading segments to publish faster?

            Not under a playable contract. Viewers can fetch a manifest referencing absent assets. Persist/verify artifacts, publish an immutable manifest and finally CAS pointer/READY by generation. Stale jobs must not override deletion/blocking.

            Does a 95% CDN byte hit mean viewer egress drops to 5%?

            No. Viewers still receive the media bytes through the CDN; five percent represents origin-miss bytes in a simplified model. Request hits differ from byte hits. Caching/shields reduce origin work, while bitrate, watch time and codecs affect viewer bytes.

            Does choosing bitrate from estimated network speed eliminate stalls?

            No. Estimates describe the past; bandwidth drops, overhead, RTT and buffers matter. Safety margins/buffer-aware policies can help without guarantees, especially below the lowest rendition. Measure startup, rebuffering and quality by cohort.

            Can S3 multipart parts be encoded as a complete file before completion?

            Not by default. Object availability and container formats have their own semantics; partial uploads may lack required metadata/indexes. Early processing needs suitable ingestion/containers/protocols and validation. The baseline waits for a verified final source before scheduling.

            Does AV1 always cost less than H.264?

            No. It depends on content/quality/encoders, encode cost, views, device decoding and fallbacks. Compare saved bytes on compatible views against added compute/storage/energy; long-tail and popular titles can justify different decisions.

            Can signed-URL expiry recall every downloaded segment?

            No. It controls requests/access under provider policy, not received bytes or browser caches. Takedown/revocation has a delay and needs appropriate resource/key/license enforcement; metadata changes alone are insufficient.

            What should you inspect when CDN bills rise much faster than view counts?

            Separate bytes × unit price from origin fills. Inspect watch time/view, average bitrate, codecs/devices, geography/ISPs, cache keys, shielding and contracts. Views or request hit ratios alone do not establish the cause.
