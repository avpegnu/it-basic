Databases, indexes and sharding: design from access patterns and invariants

Compare database families, understand transactions/isolation, follow B-trees and LSMs, scale reads before sharding and handle hot keys, migration and cross-shard workflows.

Choosing a database does not replace designing transactions, indexes or shard keys. Each addresses a different kind of constraint.

  • Choose databases by queries, invariants and workload rather than broad SQL/NoSQL labels.
  • ACID does not make every transaction serializable; isolation levels and engine semantics determine remaining anomalies.
  • Indexes trade storage/write work for particular reads; evaluate them with plans and workloads.
  • Shard keys determine queries, hotspots and transaction boundaries; migration is part of the design.

1. Begin with an access-pattern table

Before choosing an engine, list entities, keys, critical queries, read/write rates, payloads, retention and invariants. “A scalable database” does not specify ID lookups, time-range scans, text search or graph traversal. A good schema supports reads/updates while preserving understandable ownership.

For orders, consider ID lookup, recent user orders, payment state and unique logical checkouts. A relational model can start with a (user_id, created_at, order_id) index and an idempotency constraint. Rich search/analytics may use separate projections with lag, unsuitable as payment-correctness authorities.

2. Database families and suitable boundaries

Relational databases support schemas/constraints, joins and transactions within declared scopes. Document stores manage document aggregates and may offer rich transactions/indexes; they are not automatically schema-free or non-ACID. Key-value systems suit key lookups, wide-column systems suit some partition/range patterns and graph traversal/analytics differ from OLTP.

Data models, storage engines, consistency and distribution are separate axes. SQL systems can use LSM engines; NoSQL systems may offer strong consistency within a scope. Choose explicit guarantees, queries, latency, cost and operational skills. Multiple databases add integration/backup/recovery burden; polyglot persistence needs justification.

3. ACID, BASE and transaction boundaries

Atomicity · Commit or abort together

  • Changes inside the transaction boundary form one unit.
  • A database write and a separate broker publish do not automatically share a transaction.

Isolation · Transaction interaction

  • Two atomic transactions may still produce write skew under an isolation level that permits it.
  • Choose isolation, constraints or locking for the invariant; handle retries when needed.

Atomicity provides all-or-nothing behavior within supported transaction scopes. Consistency preserves application/database invariants rather than discovering every business rule. Isolation governs concurrent interactions, and durability describes acknowledged data under configured failures. Each term needs a scope/configuration, not a marketing label.

BASE commonly describes systems accepting eventual consistency in pursuit of other goals; it is not an isolation level or a property of every NoSQL system. Eventual convergence needs mechanisms and acceptable lag, with explicit retries, versions and conflict handling.

Decrementing stock and creating an order should share an atomic boundary where possible. A provider call is outside a local database transaction even when code surrounds it with BEGIN/COMMIT. Long network calls under database locks do not make rollback undo charges. Cross-owner workflows need idempotency, state machines, outboxes and reconciliation/compensation.

4. Isolation: stable reads may still violate invariants

Read committed commonly prevents dirty reads while statements may observe different states, depending on the engine. Snapshot/repeatable-read semantics vary; stable snapshots do not inherently prevent cross-row write skew. Serializable requires equivalence to some serial ordering, using locking or detection/abort; applications must retry entire transactions where required.

Lost updates arise when writers use old values and overwrite changes; conditional updates/row locks can protect a resource. Write skew arises when transactions read a shared predicate and update different rows, escaping same-row write conflicts. Use constraints, invariant-level locks or serializable retries and test real interleavings.

5. B-trees, composite indexes and query plans

B-trees maintain high-fan-out balanced trees for key lookups and ordered ranges. Positioning costs roughly O(log_B N) page traversal, while output size and data-page fetching still cost work. Cached upper pages, selectivity, clustering and locality make real latency differ from one simple formula.

A (user_id, created_at, order_id) index fits recent-user-order queries with stable tie-breaking. Leading equality predicates often narrow scans effectively; optimizers may use indexes differently by engine/version, so avoid absolute “missing the first column means never usable” rules. Inspect plans, actual cardinality, filtered rows and IO on representative data.

Indexes add storage and write maintenance, increasing insert/update/delete work, IO and cache churn. Covering/index-only access depends on engine/visibility rules and is not free. Index important queries and measure trade-offs; sequential scans can be appropriate for most of a table.

CREATE INDEX orders_by_user_time
  ON orders (user_id, created_at DESC, order_id DESC);

SELECT order_id, created_at, state
FROM orders
WHERE user_id = :user_id
  AND (created_at, order_id) < (:last_time, :last_id)
ORDER BY created_at DESC, order_id DESC
LIMIT 20;

PostgreSQL-style example with adapter placeholders. The first page needs a cursor-free branch; validate cursors and authorize the user before querying.

5a. Index types and distributed ownership

Primary keys constrain identity/uniqueness within a scope; clustered organization is engine-specific physical layout. A primary key does not automatically sort every table physically. Secondary indexes provide other access paths; maintenance depends on affected structures and the engine, not a rule that every write rewrites every index byte.

Inverted indexes serve term lookup, spatial indexes support geometric/range operations and bitmap-oriented structures help some analytics workloads. Operator support, selectivity, updates and visibility determine plans beyond the name. Covering indexes may still need visibility/data access, so verify plans and IO.

Local secondary indexes live with their data shards: writes are more local, but queries without routing keys may scatter. Global indexes partition by indexed value for targeted lookup while updates reach another owner. Specify consistency, duplicate handling and rebuild/catch-up rather than assuming all global indexes are strong or eventual.

Distributed IDs provide algorithm-specific identity uniqueness, not business uniqueness such as one account per email across shards. Global business uniqueness needs a unique-key owner, constraint/index or suitable protocol. Two different IDs can still represent the same email.

6. LSMs: write buffers, SSTs and compaction

An LSM commonly logs writes for configured durability, updates memtables and flushes immutable sorted files. Append/batching reduces some random-write costs while creating versions/runs to merge. Compaction trades read, write and space amplification; backlog can stall writes and raise p99 at unchanged application rates.

Reads inspect memory and relevant files/ranges and resolve versions/tombstones. Bloom filters skip definitely absent keys but can false-positive; they return neither values nor authorization. The toy reads runs newest-first; real levels/partial compactions require more nuanced sequence/version semantics.

Deletion commonly writes a tombstone blocking older values. Remove it only when no required versions/snapshots/replicas still depend on it; premature removal can resurrect data. DELETE need not immediately free disk, and compaction needs IO/space while inputs and outputs coexist.

7. Scale reads before splitting data

Improve queries/indexes, pagination, batching and connection pools first. Freshness-aware caches reduce repeated work; replicas distribute reads but lag. Heavy reporting can use projections/warehouses to avoid OLTP IO contention. Remeasure bottlenecks after each change.

Read-your-writes can route to the primary or a replica meeting a commit position/session version. Waiting a fixed delay does not prove catch-up under all failures. Failover needs acknowledged durability and replication progress; arbitrary promotion risks multiple writers.

8. Shard keys, ranges, hashes, directories and skew

Ranges help scans/retention but monotonic time/IDs can heat the current shard. Hashes distribute keys while making ranges fan out and potentially remapping keys when topology changes. Directories/virtual shards add metadata ownership but support deliberate partition movement.

Tenant/user keys colocate related data and transactions but large tenants can exceed a shard. Composite/bucketed keys split load at the cost of query/transaction fan-out. Define local invariants, tenant limits and splitting before choosing; balanced key counts do not imply balanced bytes or traffic.

9. Life after sharding

A new shard needs more than a routing entry

  1. Prepare the destination

    Schema, capacity and routing version.

  2. Copy and catch up

    Snapshot/backfill plus new changes.

  3. Verify and cut over

    Validate data; transfer write authority.

  4. Observe and clean up

    Retain rollback before removing the old source.

A migration plan needs catch-up and verification; fencing/epochs protect ownership during write cutover. Details depend on the database and workload.

Queries need partition routing, with alternate-key lookups potentially requiring global directories/indexes. Cross-shard joins, aggregations and pagination need bounded fan-out, partial-failure policy and merging. The slowest shard often dominates tails; smaller shards do not guarantee fast global queries.

Cross-shard transactions can use supported distributed guarantees or stateful workflows/sagas. Choose by invariants/failures rather than always choosing 2PC or eventual consistency. Small atomic boundaries and explicit ownership reduce blast radius and retry complexity.

Rebalancing needs snapshots, change catch-up, ownership versions/fencing, cutover and rollback. Schemas must coexist across shard versions. Per-shard backups do not automatically create a globally consistent restore point; define restore semantics, directory metadata and relevant event positions.

10. Keep inventory within an atomic statement

Avoid unlocked read-then-write: two requests can see stock=1 and both sell. Under one database owner, a conditional update plus order creation can share an atomic boundary. The query below inserts only when reservation returns a row; quantity must be a positive integer and the actor authorized.

Use a unique (user_id, checkout_key) constraint; duplicate-checkout insertion failure rolls back the reservation in the statement. Adapters reconcile replays through stored outcomes/fingerprints rather than treating different payloads as success. Post-commit payment/network work uses workflows/outboxes outside this statement’s atomicity.

WITH reserved AS (
  UPDATE inventory
  SET available = available - :qty
  WHERE item_id = :item_id
    AND :qty > 0
    AND available >= :qty
  RETURNING item_id
)
INSERT INTO orders (order_id, user_id, item_id, quantity, checkout_key)
SELECT :order_id, :user_id, item_id, :qty, :checkout_key
FROM reserved
RETURNING order_id;

PostgreSQL-style example with driver placeholders; schema constraints and adapter retry/idempotency handling are required. No returned row means no inventory reservation.

11. Tune and operate with measurements

Measure query mix/latency, locks, transaction age, pool waits, buffer hits, IO, lag, disk headroom and compaction backlog where applicable. Query timeouts do not prove rollback everywhere; cancel/reconcile under driver/engine contracts. Long transactions can retain snapshots, locks or garbage unexpectedly.

Database choices include cost, restore tests, schema rollout, on-call skills and migration. Benchmark realistic data sizes, distributions, index counts and failures. Uniform-key point lookups do not prove suitability for product joins, hot tenants or failover.

11a. Denormalization and platform choices

Query-driven denormalization can keep hot paths local: conversation messages and user inboxes are different projections. Copies need ownership, event versions, idempotency, replay and repair. Global search should use a suitable projection rather than unbounded OLTP fan-out; deletion/revocation must reach relevant copies.

Building routing/sharding provides control but requires ownership of metadata, migration, restoration and failover. Distributed SQL or sharding platforms can supply mechanisms under their own cost/latency/operational contracts. Compare guarantees and real workloads, including failures, before leaving a simpler system that meets SLOs.

12. Interview drills and worked answers

Does ACID automatically prevent write skew?

No. Isolation and scope matter; snapshots can permit different-row updates based on an old predicate. Serializable or invariant-aware constraints/locking with retries may be required. The ACID label alone is insufficient.

Why may disk usage stay high after DELETE?

Engines may retain tombstones/old versions for snapshots, replication, recovery or compaction/vacuum. Reclamation has its own lifecycle/headroom; deleting a logical row is not immediately removing every physical copy/backup.

Does hash partitioning solve every hotspot?

It spreads many keys while one large key/tenant may retain one owner. Use caches/replicas for hot reads or invariant-compatible write splitting/aggregation. Measure partition traffic/bytes beyond row counts.

Is either B-tree or LSM always faster?

There is no universal winner. Points/ranges, update rates, caching, compaction, durability and hardware matter. Compare tails, amplification, space and maintenance on real workloads; “LSMs are write-optimized” does not guarantee little IO for every write.

What should be retried after a serialization failure?

Under the engine contract, usually retry the whole transaction with fresh reads, bounded attempts/backoff and stable logical identity. Do not merely retry COMMIT or repeat external charges inside it; external effects need idempotency/outboxes.

How would you choose an order shard key?

Start from user/order queries and atomic invariants. user_id localizes recent-user reads but leaves shared inventory/payment elsewhere; order_id spreads writes but needs a user-listing index/projection. Compare fan-out, skew, migration and transaction scopes first.

Explain and compare the mechanisms

These open questions connect terminology to state, assumptions and failure boundaries. Try an example from your own work before comparing the explanation.

Which questions should drive a SQL versus NoSQL choice?

Start with access patterns, invariants, transaction scope, query flexibility, skew and operational constraints. Relational systems support relations, constraints and composable queries without being inherently limited to vertical scaling. NoSQL groups very different data models and does not imply absent schemas, absent transactions or unlimited scaling. Compare concrete implementations and deployments.

Order or payment invariants may fit relational transactions, while append-heavy keyed access can suit a partitioned store with an appropriate contract. Account for indexes, joins, denormalization, backups, migrations and team expertise. A fast query benchmark does not establish safe hot partitions, recovery or cross-entity invariants.

What must a live database resharding preserve?

Define authority, routing epochs and consistency before migration. Build the target, snapshot at a coherent cut, catch up ordered changes with checkpoints and deduplication, and validate keys and invariants at comparable states. Requests need correct ownership or redirects, and the write protocol must prevent split-brain updates, lost writes and duplicate effects.

Gate and observe cutover by shard or tenant, fencing old owners when authority changes. Rollback after new writes needs safe reverse reconciliation. Disclose pauses or stale windows rather than promising zero downtime. Include backups, tombstones, transactions, schema compatibility and replay horizons; completed copying does not establish correct traffic migration.
