Designing a URL Shortener: codes, caching and reliability

From a Base62 namespace to conditional inserts, redirects, expiry and multiple regions; experiment with collisions and cached destination changes.

Four decisions behind a short link

  1. Choose a namespace

    Size code space and uniqueness; separate encoding from generation.

  2. Commit the mapping

    Conditional insertion and idempotency preserve invariants under retries/races.

  3. Resolve quickly

    Caches/stores supply mappings; readers check policy and return Location.

  4. Keep it correct

    Expiry, abuse, edits, analytics and restore need explicit contracts.

Follow the lifecycle: allocate a code, commit a mapping, serve redirects and manage later changes.

  • Base62 represents an ID; uniqueness comes from allocation or conditional writes.
  • Cache policy controls freshness and origin traffic; 301/302 alone is insufficient.
  • Expiry/status require serving-path checks; background cleanup is not enforcement.
  • Disjoint ranges protect generated codes, not alias ownership or cross-region read-after-create.
  • Analytics durability, revocation latency and hot-key protection are product/operational decisions, not technology names.

1. Specify behavior and invariants

Link capabilities

  • Create links, redirect through GET/HEAD, optionally accept aliases and expiry.
  • Only authorized principals can modify or disable a link; custom domains require ownership verification.

Quality contract

  • Teaching scenario: 100 million new links/day and ten times as many redirects; a target p99 of 50 ms at a defined service boundary.
  • Set separate redirect and creation SLOs; define regions, counted failures and the accepted revocation delay.

Required invariants

  • Two different mappings must not own the same (domain, code); a valid idempotent retry must not create another mapping.
  • Readers check expiry/status; delayed cleanup must not revive a link. Avoid reassigning a code while old URLs can still be accessed.

A URL shortener maintains a durable mapping from (domain, code) to a destination URL. The browser receives Location and makes a separate request to the destination; the service does not need to download that page. This makes the redirect path a key lookup followed by a small response.

Before drawing, ask whether destinations can change, how precisely expiry must be enforced, whether aliases/custom domains exist, whether links are public or private, and whether analytics is approximate or auditable. These choices determine freshness, authorization and event durability. An unguessable code alone does not protect a private resource; real privacy requires authentication and authorization.

2. Calculate traffic, storage and code length

Use 365 days/year for rough arithmetic, ten-year retention and a 500 B average record including the example URL and metadata. These figures are neither a database benchmark nor a capacity limit. The read:write ratio is 10:1 here, not a universal property of shorteners.

Logical storage is 182.5 TB in decimal units. Three full replicas make the payload alone 547.5 TB before indexes, WAL/logs, backups, headroom and engine overhead. Analytics can dwarf mappings; it is not included in the same 500 B. A peak factor of three is an assumption that can fail during a viral event.

3. Base62 encoding and collision are different problems

Encode a non-negative integer by repeatedly dividing by 62 and reading remainders in reverse order. Fix the alphabet: swapping a–z and A–Z changes the mapping. Codes are case-sensitive, so routers, database collations and custom-domain proxies must preserve case. An exact-L-character namespace can use zero padding; decoding gives the same integer, but a canonical format avoids unintended equivalent URLs.

Encoding is a bijection between an integer and its canonical representation; it neither provides secrecy nor generates IDs. Two writers using the same integer produce the same code. A Snowflake using up to 63 bits can require eleven Base62 characters, so such IDs do not always fit in seven. For a seven-character product limit, stop the allocator before 62^7 or choose a different namespace design.

4. Compare counters, randomness and hashing

For uniform random generation, the next-draw collision probability against n occupied codes is n/M. The probability of at least one collision among n raw draws is approximately 1 − exp(−n(n−1)/(2M)) when n is small relative to M. These answer different questions: a large namespace does not make its whole history collision-free. Generate and conditionally insert; retry conflicts within a budget instead of relying on a read-then-write check.

A truncated URL hash does not prove that two URLs are equal. If a code conflicts with a different target, compare the full input under a defined canonicalization policy, use a salt/nonce for another candidate, or increase length. Do not casually reorder query parameters, remove fragments or lowercase paths: these can change URL meaning. Deduplicate only in a defined owner + destination + options scope; different customers may want different tracking or expiry for the same URL.

5. Design APIs with explicit retries and ownership

Use /s/:code to avoid collisions with /api, /health and assets. For the shortest /:code route, reserve names and ensure dispatch cannot swallow API routes. Bound URL size, allow http/https schemes, define alias grammar and maximum expiry, and reject URL credentials and control characters. Verify custom-domain ownership before allowing mappings.

An Idempotency-Key is not URL deduplication. Store the tenant/principal-scoped key, a payload hash and the creation result for a retention window. The same key and payload returns the same mapping; the same key with another payload conflicts. A timeout after commit must not create another link on retry. If a transaction cannot cover both records/stores, use an operation state machine or an authoritative operation record.

POST /links

Create a mapping with an alias or generated code.

Idempotency-Key: create-2026-001

  • Use 400/422 for invalid input, 409 for an occupied alias or idempotency payload mismatch, and 429 for quota exhaustion; error codes distinguish these cases.

GET /s/{code}

  • Use 404 for missing links; use 410 for expiry if public policy allows, or 404 to reveal less. HEAD has the GET status/headers without a response body and should not automatically count as a human click.

6. Read-heavy architecture and request paths

Start with a stateless service, a database with a unique key and a cache when needed. Separate creation and redirect services when deployment, scaling or blast radius warrants it. An auto-increment key on an HA database can suffice at moderate scale; interviews alone are not a reason to reject it. Hundreds of billions of mappings require partitioning, backup and recovery planning, but SQL versus KV still depends on access patterns and operational capability.

A cache hit reduces store load without proving that status is current. Choose bounded mapping staleness and an abuse-revocation policy with adequate speed. If every request must observe immediate revocation, all layers that bypass authority must be changed or removed; best-effort invalidation plus a one-hour TTL does not meet that promise.

7. Allocate ID blocks without reissuing them after a crash

Range lifecycle

  1. Reserve durably

    Atomically advance the high-water mark before returning [start, end).

  2. Allocate locally

    A mutex/atomic operation protects next; never reuse an ID handed to a request.

  3. Crash or exhaustion

    Discard the remainder; restart with a new range. Never roll back allocation.

Separate range reservation, local consumption and recovery; gaps are an accepted cost.

The allocator durably updates next_id atomically and returns [start, end). With blocks of 10,000, 100 million daily links require roughly 0.116 block allocations/second before waste and prefetch. Writers consume local ranges with an atomic increment or mutex, allowing only one refill at a time. If two coroutines see exhaustion and both await an allocator without synchronization, refill logic can corrupt state or issue duplicate IDs.

Do not return expired leases to a pool: a paused writer can resume and continue allocating from an old block. An issued range is permanently consumed; a crash creates gaps, not permission to reuse it. Allocator failover or restore must not roll back its high-water mark. A writer holding several prefetched blocks can waste more than one block on a crash.

During an allocator outage, writers with ranges can create links within quota. Exhausted writers stop creation or return a retryable error; they must not invent random codes in the same namespace without uniqueness checks. Existing redirects should remain available during an allocator failure. Alert on namespace exhaustion and plan longer codes without rewriting old codes.

-- Example: one authoritative PostgreSQL row, durable transaction.
BEGIN;
UPDATE code_allocator
SET next_id = next_id + 10000
WHERE namespace = 'generated-v1'
  AND next_id + 10000 <= 3521614606208
RETURNING next_id - 10000 AS start_id, next_id AS end_exclusive;
COMMIT;
-- Return the range only after COMMIT succeeds. Zero rows: exhausted.
-- Lost reply: do not recycle the block; retry may reserve a new one.

An allocator-side block reservation, not a complete service. It requires a precreated row, appropriate permissions, HA/durability and commit-result handling. Writers still need local concurrency safety.

8. Schema, partitioning and custom aliases

A minimal record contains domain, code, target_url, created_at, expires_at, owner_id, status and version. Use a primary key/unique constraint on (domain, code), with case-sensitive comparison for the Base62 namespace. An owner + created_at index for dashboards is a separate access pattern, possibly a separate view; redirects must not scan an owner index. Aliases can have their own grammar/case policy, consistently enforced by router and store.

Hashing (domain, code) can distribute records with a good hash, but it does not distribute requests for one viral code. A lookup can route to one logical partition while still involving indexes, replication, networking and storage I/O; calling the whole operation O(1) does not describe real latency. Range partitioning directly on a counter can concentrate inserts on the last shard; evaluate hash partitioning or another key layout.

Two requests for one alias must not rely on a SELECT-not-found followed by an unconstrained INSERT. Make a unique constraint/conditional write the decision point so only one mapping commits. With eventual multi-region writes, local uniqueness does not imply global alias uniqueness. Route an alias namespace to a home owner or use appropriate global conditional coordination. Disjoint generated ranges solve generated-code collisions, not alias ownership.

9. 301, 302, 307, 308 and actual cache behavior

301/308 express permanent moves and can be heuristically cached without overriding directives. 302/307 are temporary but can still be cached when the response supplies permitted freshness. 307/308 preserve the method during automatic redirection; 301/302 allow historical POST-to-GET behavior. A GET/HEAD-only endpoint reduces the method issue while leaving cache policy important.

302 does not guarantee that every click reaches the origin, and 301 does not inherently prohibit analytics. Choose explicit Cache-Control and decide whether events are recorded at browser, edge or origin. no-store prohibits storing a new response; no-cache permits storage but requires validation before reuse; max-age allows reuse during freshness. CDN invalidation cannot erase issued browser cache entries, and switching to no-store today does not recall an old response that remains fresh.

10. Expiry, invalidation and newly created links

expires_at is a reader-enforced business rule, not merely a background cleanup schedule. A store and its cache can still return expired records awaiting deletion. Cached redirect TTLs must be bounded by remaining lifetime, with clock-skew margin when required. If stale-while-revalidate or stale-if-error is enabled, explicitly decide whether it may cross expiry or revocation.

An update can race with cache fill: a reader fetches v1, a writer commits v2 and invalidates, then the delayed reader fills v1. A single invalidation does not prevent this. Options include version-aware writes, an ordered change stream, bounded TTLs or authoritative reads. Hard-revocation policies require sufficiently fresh version/tombstone state on the serving path and a defined response when it cannot be checked.

Negative caching reduces lookups for scanned missing codes, but can hide a newly created link after a cached 404 or a lagging replica read. Use short bounded TTLs, keyspace limits against memory DoS and creation invalidation when suitable. Read-after-create can use home-region reads/fallback or routing hints; do not turn one lagging replica read into a persistent 404.

11. Viral links and analytics without blocking redirects

Hot-key protection

  • L1/edge caches reduce network hops; coalescing reduces concurrent same-key database reads on a miss.
  • Limit misses/scanners separately; measure shard-level rather than only cluster-level load.

Event durability has a cost

  • Best effort: accept and measure event loss.
  • Auditable: choose a durable acknowledgement boundary, deduplication and recovery, and charge the cost to the SLO.

Hash partitioning distributes keys while one hot key still loads one cache shard. Small reader-local caches, hot-key replication, TTL-bound edge caches and miss coalescing can reduce load. Each layer adds freshness obligations; mutable mappings need a staleness bound or version checks. A high average hit ratio is insufficient evidence when one shard is overloaded and the rest of the cluster is idle.

Best-effort asynchronous events keep redirects from waiting on analytics but can lose clicks during crashes or full queues. A durable local spool/outbox reduces loss while adding I/O and operations; durable enqueue before responding adds a latency/availability dependency. If every click must be durably recorded before redirection, the path cannot also promise never to wait for analytics durability. Specify the contract instead of treating async as a solution by itself.

Clicks are not people: retries, crawlers, preview bots, prefetch and HEAD requests differ from user intent. Event IDs deduplicate event delivery; unique-user analytics additionally needs identity/privacy rules, time windows and bot handling. Track event loss/drop rate, backlog age, duplicates and dashboard lag, and never allow an unbounded backlog to consume the redirect process memory.

12. Abuse, privacy and security boundaries

Phishing/malware control needs creation limits, reputation, reporting/takedown and a redirect enforcement policy. Asynchronous scanning creates an unknown-safety interval: choose quarantine, warning interstitials or an explicitly accepted risk window. One scan cannot guarantee future safety because content, DNS and redirect chains can change. Block decisions must reach every serving cache within the promised delay.

A pure redirect endpoint does not fetch a URL and therefore does not itself create SSRF; fetching scanners/preview workers can. Isolate egress, block private/link-local/metadata addresses, check DNS/IP at connection time and each redirect, bound response size/time/redirect count, and never attach internal credentials. A proper parser and scheme allowlist need network checks; string regexes alone do not stop DNS rebinding.

Sequential codes invite enumeration; randomness or permutation reduces guessing but is not access control. Avoid unnecessary logs/events containing token-bearing URLs, and consider referrer policy, retention and analytics access. Heavy abuse can get the short-link domain blocklisted, so reputation and takedown affect practical availability.

13. Multi-region serving, failover and data migration

Serving redirects across regions can reduce latency, but asynchronous replication creates two different problems: new links are absent remotely and disabled links remain usable there. Globally disjoint ID ranges prevent generated-code collisions; they do not solve replication lag, alias conflicts or conflicting target edits. Define mapping ownership/home region, replication versions and fallback behavior.

During a network partition, redirects may use bounded-stale mappings if policy permits, while suspected-abuse links may require fail-closed behavior. Alias creation and edits must preserve invariants through a quorum/home owner, potentially reducing availability. Make choices per operation instead of applying one AP/CP label to the whole system.

At 182.5 TB logical storage, hot/cold tiering is possible, but every live link still needs a lookup path that meets its p99 target. Migrate with checkpointed backfills, change capture, versions and a verified cutover; naive dual writes can diverge. Backup restore must preserve mappings/tombstones and a compatible allocator high-water mark to avoid reissuing IDs. Test restores and measure RPO/RTO instead of relying on green backup jobs.

14. Failure matrix and preproduction verification

Track redirect success/latency by status, cache tier and region; creation conflicts/idempotency replays; store saturation; allocator headroom; invalidation lag; stale redirects; and event loss. Define success carefully: a correct missing-code 404 differs from a replica-lag 404 for a new link. Dashboards must distinguish system failures from valid business outcomes.

15. Practice decisions through worked scenarios

Answer through requirements → invariants → mechanism → failure → trade-off. The worked answers are discussion starting points; changes in SLOs, retention or privacy require reconsideration rather than memorized service names.

If seven characters are enough, can random generation skip collision checks?

No. About 3.52 trillion available codes is capacity, not a guarantee of collision-free draws. With 365 billion occupied codes, a uniform next draw conflicts about 10.36% of the time. Conditional insertion protects uniqueness, with bounded retries for conflicts. Near-certain collisions somewhere in history do not imply that every request conflicts.

As occupancy rises, what does approximately 1/(1−n/M) expected attempts mean, and when should length grow?

Does an allocator outage break all redirects?

Not with proper separation. Existing links need only the mapping path; writers with ranges continue, exhausted writers fail creation. Alert on remaining ranges and ensure crash/restore never reissues blocks. A redirect that calls the allocator adds an unnecessary dependency.

Will changing 301 to 302 alone fix missing click analytics?

No. Inspect Cache-Control, browser/edge caching and the event capture point. A 302 with max-age can be cached; an old fresh 301 is not recalled by an origin change. New responses can use no-store or events can be logged at the edge, while bots, retries and event loss still need handling.

One viral link causes a 50-fold spike. Are more cache shards sufficient?

Not necessarily: one key still routes to one shard unless routing changes. Measure hot-key QPS and use L1/edge caching, hot-key replication or special routing; coalesce misses and preserve invalidation bounds. More readers can ease service CPU/network load while increasing pressure on the same shard.

What if two regions both win a local conditional write for alias sale?

Local uniqueness is not global uniqueness. Route aliases to one authority or use appropriate global conditional coordination/consensus; a partition may require rejecting one side. Disjoint generated-ID ranges do not solve user-chosen alias conflicts.

Can a user follow an expired link before database TTL cleanup?

The reader must check expires_at and refuse redirection even while the record exists. Previously issued cached responses must also have freshness bounded by the lifetime contract; changing the DB cannot recall a browser response with an excessive TTL. Expiry is an end-to-end serving policy; cleanup only reclaims storage.

Can deleted-link codes be reused to save namespace?

It is risky: old bookmarks, emails, QR codes and caches can send users to a new owner’s mapping. A simple policy never reissues codes and retains minimal tombstones under the data policy. Required reuse needs a versioned namespace or another ambiguity-free rule; an arbitrary delay cannot prove every URL copy has vanished.

Is “no lost clicks” compatible with never waiting for analytics?

Separate “not waiting for downstream processing” from “not waiting for durable recording.” A durable local log can precede asynchronous processing, but log I/O costs latency and a full log is a failure mode. Sending a response before any durable capture leaves a crash window that can lose the event; a best-effort contract must acknowledge it.
