Designing Autocomplete: prefixes, top-K and typing experience

Explore prefix indexes, ranking, Unicode, caching and versioned pipelines; experiment with top-K filtering and response races to understand backend and frontend correctness.

From typed characters to trustworthy suggestions

  1. Preserve input identity

    Normalize under policy, debounce and guard generations.

  2. Retrieve bounded candidates

    Walk/get candidates, then filter/rerank within a budget.

  3. Build scores and indexes

    Clean logs, compute decay/trends and validate versioned snapshots.

  4. Preserve freshness and privacy

    Cache by context, remove promptly and roll out coherently.

The lifecycle spans frontend races, index lookups and update pipelines.

  • Serve from prepared indexes with bounded filtering/reranking instead of scanning the corpus per keystroke.
  • Cached top-K trades memory for latency; filters and personalization make candidate recall a separate decision.
  • Input-generation guards prevent stale overwrites; cancellation/debounce cannot replace them.
  • Build/read must share normalization/context/version semantics; public caches must not contain private history.
  • Trending freshness, urgent removals and snapshot rollouts must account for caches and replica readiness.

1. Does autocomplete suggest queries or entities?

Latency between keystrokes

  • The budget includes debounce, networking, serving and rendering; a 100 ms debounce can consume a 100 ms input-to-results target by itself.

Freshness and safety

  • Popularity may lag; urgent removals need a separate path bounded across all caches.

Context determines caching

  • Locale, region, tenant, policy and private history can change one prefix’s results.

Query completion suggests popular search strings; entity typeahead suggests users, products or places with their own permissions. They differ in ranking, sources and caching. This baseline is public query-prefix completion: up to five suggestions, explicit locale, popularity with recency, hourly batch freshness and an end-to-end p99 target below 100 ms at a defined boundary. Fuzzy matching, full results and private people search are extensions.

“Up to K” is not always “exactly K”: rare prefixes, safety filters or missing index data can yield fewer. Define minimum prefix length, empty prefixes, typos, Unicode and removal delay. Personalized responses cannot all be treated as identical public results for one prefix.

2. Size requests and memory with the right units

Assume 50 million DAU, ten submitted searches per user per day and twenty input changes per search: ten billion raw keystroke events daily. If debounce/caching removes half of requests, five billion remain, about 57,870/second; a threefold peak is 173,611/second. The 50% reduction is a measurement-dependent assumption affected by typing cadence, IMEs, networking and UI, not a debounce guarantee.

One hundred million queries × 20 B gives only 2 GB of text if the average really is twenty bytes. This excludes trie nodes/edges, scores, IDs, candidate lists, allocator overhead and replicas. For P distinct prefix nodes, five eight-byte references use 40P bytes for references alone. P is bounded near total query length; 100 million twenty-code-point queries can approach two billion prefixes before sharing, or 80 GB of references in this illustrative upper bound. Compression/radix/FST choices change memory substantially, so measure serialization and loaded heap.

3. Prefix, context and index-version contracts

Validate length, locale and limits and normalize under the builder’s policy version. GET query strings can appear in proxy/access logs, so apply privacy-aware logging. Private history may need a separate authenticated endpoint and cache policy. A path resembling a public API does not justify shared caching of private results.

GET /suggest?q=ca&limit=5&locale=vi

Public query completion with contract-defined input length bounds.

Cache-Control: public, max-age=15

4. Separate serving from index construction

Serve from a prepared index instead of scanning/sorting the corpus per request. This does not mean “never compute”: normalization, safety, personalization and trending merges can require bounded work. Deadlines and candidate budgets prevent dynamic work from breaking latency. Start with simple process/index replicas and shard when memory, load or isolation requires it.

Submitted-search aggregation is a separate write path. A keystroke response does not prove that the user wanted a query; record submission/selection as distinct event types when permitted. Batch snapshots use checksums/versions, while trending overlays have their own freshness/TTLs under the same safety contract.

Fast serving and a versioned index-building pipeline

Component map; the complete ordered request paths are explained below.

Suggestion reads do not wait for batch jobs; submitted searches feed aggregation. Choose a trace for cache hits, lookups, snapshot publication and urgent removals.

Public suggestion: cache hit

  1. Request a debounced prefix with valid locale/context.
  2. Return a public response that is fresh under cache/removal policy without reaching the origin.

Cache miss and top-K lookup

  1. Send a prefix associated with a frontend input generation.
  2. On a miss, forward the complete request context.
  3. Pin an index version, normalize under its policy and walk/get a candidate list.
  4. Return bounded candidates with scores/IDs instead of scanning the corpus per keystroke.
  5. Apply sufficiently fresh removal policy; define overfetch/empty-result behavior when filters reduce K.
  6. Return decisions/version; handle policy freshness failures under the contract.
  7. Return results and cache policy only for the defined public context.
  8. Render only if the input generation/context still matches, regardless of response arrival order.

Submitted search to a new snapshot

  1. On a submitted search, emit an event with an ID under privacy/consent policy.
  2. Consumers deduplicate replays and compute event-defined counts/windows.
  3. Produce a scored query/entity dataset with locale and policy versions.
  4. Write all shards, checksums and a manifest; validate before publishing.
  5. Replicas load/warm the new snapshot; requests pin only ready versions.

Urgent removal and old cached results

  1. A new policy version removes a suggestion without waiting for a full rebuild.
  2. Purge/version caches or bound TTLs to meet removal delay; origin filtering alone cannot fix an old cache hit.
  3. Return a policy-valid response; local caches also need bounds/versions.

5. Tries, cached top-K and filter-induced underfilling

A trie walk costs O(p), where p counts symbols in the chosen representation. Traversing its entire subtree to find top-K adds candidate-dependent work. Precomputed ordered lists enable approximately O(p + K) serving with suitable child lookups, plus text bytes/serialization. A small K does not make the whole request constant-time.

If a cached list contains exactly K entries and an urgent filter removes one, only K−1 remain. Overfetch/continuation can help within candidate budgets, but build-time filtering cannot replace newly changed serving removals. Personalized ranking can need candidates absent from global top-K, so overfetch does not prove perfect recall.

6. Frontend debounce, cancellation and generation guards

Debouncing sends after a quiet interval and can delay results during continuous typing. Choose the interval for the UX and measure input-to-render time. It has no fixed request-saving ratio. Cancellation reduces waste but is not a correctness guard: resolved responses or running callbacks can outlive input changes. Increment generations as soon as input/context changes, not only when a timer sends a request.

IME composition is not one keydown per final character. Avoid sending/committing intermediate composition unless intentionally designed; use composition events and input state. Arrow navigation, Enter/Escape, focus, screen-reader combobox semantics and loading/empty/error states are part of UI correctness, not merely backend-diagram decoration.

7. Unicode normalization does not mean removing accents

NFC unifies canonically equivalent forms; NFKC adds compatibility folding that can remove distinctions the product wants to preserve. Lowercasing, case folding, accent stripping, transliteration and tokenization are separate policy steps, not an unspecified normalize operation implemented differently at build/read. Vietnamese đ does not become d simply through NFD; folding needs a separate relevance-tested rule.

UTF-16 code units, Unicode code points, grapheme clusters and UTF-8 bytes differ. Specify units for prefix walks, input limits, highlighting/cursors and memory sizing. CJK segmentation, emoji sequences and multiword completion need suitable analyzers. Store original display text separately from normalized lookup keys.

8. Popularity, time decay and feedback loops

A basic score is Σ count(t) × exp(−ln(2) × age/H), with half-life H in the same units as age. Contributions halve after H. Define windows/deduplication, event-time/late-data handling and deterministic tie-breaking. All-time frequency can entrench old queries, while strong decay makes results unstable and easier to manipulate.

Clicks/acceptances create feedback loops: the first item gets more exposure and clicks without necessarily being more relevant. Separate exposure, selection, submitted searches and downstream success. Evaluate by locale, prefix length and cohort with labeled offline sets and suitable online metrics. Resist bot/inflation using identity/session/budget policies that consider privacy rather than treating raw request counts as intent.

9. Build, publish and roll back snapshots

From query events to a servable index

  1. Clean and score

    Apply privacy, event deduplication, locale, decay and bot guards.

  2. Build and validate

    Validate all shards, candidate references, checksums, memory and recall.

  3. Warm and switch

    Pin versions, ensure capacity and switch routing with rollback.

Publish after validation/readiness and keep serving removals independent.

The pipeline ingests, cleans/privacy-filters, aggregates/scores, filters policy, builds shards/top-K, validates, publishes a manifest, warms replicas and switches serving. Check replay deduplication, schema/analyzer versions, safety, recall, loaded memory and complete shards. Immutable checksummed snapshots aid reproducibility and rollback, but rolling back an index must not revive a term blocked by current serving policy.

An atomic manifest pointer does not make every global process switch in the same nanosecond. Replicas load slowly, caches retain older versions and fanout can mix shards. Coherent requests pin/reroute to ready shards of one version, retaining the old version during draining and cutting over with enough capacity. Memory must cover old/new versions and loading transients.

10. Caching, hot prefixes and sharding

Client caches key by normalized query + locale/context, use TTLs/versions and must respect input generations. Edge caches fit global/public components; private history can blend client-side or through a separately authorized endpoint. Cache hits still obey urgent-removal bounds; origin blocklists cannot fix fresh edge/browser responses alone.

First-letter sharding can skew both data and QPS. Distribution-based ranges and hashed prefix KV address different aspects. Hashing many keys can distribute storage better, but one hot prefix remains a hot shard. Short prefixes may need dedicated caches/replicas; subtree-sharded indexes can need global precomputed lists or scatter/gather when prefixes are shorter than shard boundaries.

Fanout across shards needs consistent ranking semantics, versions and merge/dedup identities. Per-shard top-K suffices for global top-K when scores/order and eligibility are consistent; later personalization/filtering can reduce candidate recall. Define bounded deadlines, last-known-good fallbacks or fewer-than-K responses rather than waiting indefinitely for one shard.

11. Fast trending without rebuilding everything

Use stable baseline snapshots with small stream/window overlays. A rise from one to five has high relative lift without necessarily deserving exposure; require support, unique/quality signals, seasonality and anti-manipulation. Event-time windows, watermarks and late-update policies determine actual freshness. Measure trending overlays and edge TTLs together, or new origin data remains hidden behind old cache entries.

Merge baseline/trending/history with score calibration, identity deduplication, quotas and safety. No blend ratio is universally correct across locales/queries. On overlay failure, fall back to an acceptable baseline without disabling urgent removals. Trend freshness and suggestion relevance are different metrics.

12. Private queries, safety and removals

Submitted queries can contain emails, tokens, addresses, health information or rare names. Popularity thresholds alone do not guarantee privacy. Design support thresholds, PII/secret filters, retention/access policies and aggregate-release controls for the product. Avoid unnecessary raw user/session IDs in training logs and never place private history in public edge caches.

Use build-time and serving-time controls for urgent removals. Render text/highlights safely and protect sensitive logs. Normalization is not sanitization or authorization. Anti-abuse needs rate limits, query-inflation detection and review paths. Removals must hold across snapshot rollbacks, cached responses and overlays within the agreed removal SLA.

13. Measure UX and break the boundaries

Measure input-to-first-useful-render, serving p99, stale-response discards, empty/underfilled rates, relevance by locale, contextual cache hits, version skew, loaded memory and build freshness. A five-millisecond API cannot ensure a 100 ms UX if debounce/network/render consumes the rest. Alert separately on popularity pipeline backlog and urgent-removal propagation.

14. Interview questions with worked reasoning

Explain the input contract, one serving request, one index update and one failure. Use the models to test reasoning rather than substituting a tiny browser corpus for production measurement.

Does filtering cached top-K guarantee K results?

No. Removing an entry underfills the list. Overfetch/continuation helps within a budget, but enough filtered entries can still underfill it. Define maximum K, empty/fallback behavior and eligibility/ranking semantics rather than bypass safety to fill the list.

A ca response arrives after cat. Is a guard still needed after abort?

Yes. Callbacks can race or already be resolved. Increment an input/context generation immediately and apply only matching responses, including locale/tenant changes during debounce. Cancellation primarily reduces wasted resources.

Is a trie lookup O(1)?

Typically the walk is O(p), with additional K/byte costs. Without cached top-K, subtree traversal adds work; cached lists enable O(p+K) under appropriate child-lookup/list-access assumptions. Networks, filtering/reranking and serialization still affect latency.

Does hashing prefixes equalize every shard’s traffic?

It helps distribute many keys/data but does not divide one hot prefix across shards. Measure QPS skew, cache/replicate hot prefixes and route capacity accordingly. Subtree sharding also needs short-prefix handling through fanout or global precomputed lists.

How can breaking-news suggestions appear within minutes?

Add a bounded trending overlay with windows, support thresholds, seasonality and safety, then merge it with the baseline. Measure end-to-end freshness including edge/local TTLs, not just stream processing. Frequent rebuilds can also work for small affordable indexes; they are not categorically forbidden.

Can every language use NFKC followed by accent removal?

Not as an unreviewed default. Compatibility folding and accent removal can erase meaningful distinctions. Test locale/analyzer choices on relevance data, retain display text and policy versions, and keep build/read consistent. Vietnamese đ requires a separate rule if folding is desired.

Can mixed versions remain after an atomic manifest-pointer update?

Yes, if replicas/shards/caches are not ready together. The metadata update is only one boundary. Pin request versions, check shard readiness, warm capacity and define routing/fallbacks. An index rollback must still honor current urgent-removal policy.

Do 100 million twenty-byte queries imply a two-GB RAM index?

No. That is text payload alone, excluding nodes/edges, IDs, scores, per-prefix candidates, representation overhead, old/new snapshots and replicas. Measure distinct prefixes and loaded memory. Compression/radix/FST choices can help, but raw text size alone is insufficient.
