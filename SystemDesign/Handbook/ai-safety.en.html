AI Safety & Security: trust boundaries, authority and defense in depth

Model injection, disclosure, agency, output handling, poisoned data and consumption risks. Design privilege, typed boundaries, quarantine, moderation/evaluation and incident response with three bounded teaching simulations.

Reduce capabilities and exposure at specific boundaries rather than treating one mitigation as universal.

  • Outputs and external content cannot grant authority; enforce permissions and business rules at trusted boundaries.
  • Both direct and indirect injection can cross sessions when privileges and data architecture permit.
  • Delimiters, classifiers, alignment and human review reduce selected risks without universal guarantees.
  • Tool effects and browser-triggered resource loads are separate outbound paths.
  • Code controls depend on sound implementation, configuration, current authority and coverage; code can also be vulnerable.
  • Security evaluation needs severity, adversarial coverage, errors and ongoing response rather than average accuracy alone.

1. Threat-model assets, adversaries and consequences

Confidentiality

  • Scope user/tenant data and outbound paths.
  • Include caches, logs and model artifacts.

Integrity

  • Validate effects, evidence and resource versions.
  • Model agreement does not replace business validation.

Availability / harm

  • Bound tokens, tools, cost and autonomy.
  • Consider severity and harm beyond uptime.

Start with confidentiality, integrity and availability: protect data, constrain effects and bound resources/costs. Content safety overlaps with security without being identical. Polite prose can carry disclosure URLs, while models without tools can still produce harmful misinformation.

Inventory principals, delegation, sources, memory, outputs, destinations and human decisions. Identify adversarial control over inputs, documents, tools, memories and artifacts. Consequences depend on privileges and sinks rather than wording alone. Document assumptions and residual risk instead of declaring universal security.

3. Direct and indirect prompt injection

Which boundaries does source data cross?

  1. Untrusted source

    Sources may carry hostile textual or multimodal instructions.

  2. Model processing

    Model behavior may be redirected without certain detection.

  3. Policy boundary

    Check actions and authority independently of source claims.

  4. Output / effect

    Check rendering, tools, networks and actual effects.

Whether redirection becomes an effect depends on runtime and sink policies.

Direct injection uses user-facing inputs to redirect behavior beyond policy. Indirect injection embeds instructions in pages, mail, documents, images, code, memory or tool results. Instruction hierarchy and provenance cues can help without universally enforcing trust through delimiters alone.

Direct attacks can cross tenants or alter shared state when privileges permit. Indirect attacks can act through legitimate users without attacker login. Assess actual capabilities and data graphs rather than universally ranking attack types.

Security does not require exposing private reasoning. Observe proposals, effects, accessed objects, sinks and outcomes. A claim that an attack was ignored does not establish absence of malicious influence or disclosure paths.

4. Combine data, untrusted content and outbound capability deliberately

Combining private information, hostile content and outbound channels creates disclosure opportunities. Narrowing access, tools or automatic rendering can close specific paths, without proving absence of all other leakage or harm.

Models may carry information through weights, earlier retained state or artifacts, not just current inputs. Current-prompt minimization matters without proving the absence of prior sensitive knowledge; training, state, memory, caches and artifacts need their own policies.

5. Place trust boundaries in runtimes and renderers

The diagram separates source processing, authority, execution and rendering. Security depends on implementations, identity binding, infrastructure and change governance rather than arrows. Code can contain bugs, gaps or misconfiguration; test negative paths and retain residual-risk review.

Untrusted content must not become authority

Component map; the complete ordered request paths are explained below.

Trace model inputs, tool authority, browser output, quarantine and incident response. This teaching architecture has explicit assumptions rather than universal attack-resistance guarantees.

Read scoped data

  1. Resolve principal access at trusted boundaries.
  2. Parse untrusted sources and retain provenance.
  3. Admit suitable authorized material under data policies.
  4. Supply bounded evidence as data rather than authority.

Gate proposed effects

  1. Treat names and arguments as untrusted proposals.
  2. Resolve current authority/decisions through trusted channels.
  3. Enforce narrow privileges, exact payloads and preconditions.
  4. Apply destination/egress and idempotency contracts.
  5. Audit scoped blocked, committed and unknown outcomes.

Gate browser output

  1. Treat generated URLs and markup as untrusted.
  2. Encode text or sanitize permitted markup for its context.
  3. Remote loads are outbound data paths requiring policy.
  4. Record rejected sink behavior without raw secrets.

Quarantine with typed handoffs

  1. An unprivileged reader processes hostile sources.
  2. Store scoped objects/provenance and return opaque references.
  3. Validate fields/references and permitted operations in trusted code.
  4. Dispatch authorized narrow operations without promoting free text into authority.

Contain and review incidents

  1. Detect suspicious attempted effects or unknown outcomes.
  2. Observe blocked data paths and suspicious outputs.
  3. Disable affected capabilities/features and revoke credentials as needed.
  4. Review affected artifacts/caches and preserve authorized evidence/remediation.

6. Enforce privileges and business constraints at servers

Expose necessary tools, scope credentials and enforce object authorization in resource services. Reads can disclose data, and annotations do not establish actual privilege. Prefer narrow operations and use isolation, quotas and explicit network/filesystem rules for necessary execution.

Bind approvals to concrete actions, identities, payloads, revisions and validity. Untrusted text cannot grant consent. Revalidate current authority and conditions; confirmations remain subject to fatigue, deception and mistakes.

7. Understand what each defense layer actually covers

Hierarchy, descriptions, source marking and classifiers can reduce failures under measured conditions without guaranteeing adaptive, multilingual or multimodal resistance. Retrieval, adaptation and safety training do not replace runtime privilege boundaries.

Code policies enforce defined predicates when implemented correctly, yet layers cover different paths. URL rules do not revoke tool credentials, capability limits do not prevent all textual disclosures and sanitization does not establish truth. Compose and test controls by threat path rather than inferring whole-system security.

8. Quarantine and typed handoffs must preserve trust boundaries

Contracted handoffs instead of blind trust

  1. Untrusted material

    Retain source provenance.

  2. Restricted reader

    Remove action credentials and bound resources.

  3. Typed handoff

    Validate schemas, references and scope in trusted code.

  4. Narrow executor

    Dispatch only policy-authorized operations.

Opaque references help only with enforced access and permitted operations.

Separate unprivileged readers from privileged execution where useful. Trusted code can preserve content/provenance and expose constrained fields or opaque references. Privileged components must not freely dereference hostile text or promote it into instructions. This constrains channels with added complexity and task limitations.

Free-text reader summaries can reintroduce hostile instructions or claims to planners. Structured fields can also contain misleading semantics or destinations. Validate allowed operations/resources through trusted policy and test the complete system; multiple models alone are not isolation.

9. Treat generated output as untrusted at each sink

Use ordinary text sinks or framework escaping for text, not raw generated HTML. Text-node APIs are not universal encoders for executable or URL contexts. Rich content needs maintained parsing/sanitization and link/image policies. CSP supplements rather than replaces suitable sink handling.

Validate domain fields and bind query parameters instead of concatenating generated SQL. Code execution needs authorized isolation and limits. No generic sanitizer covers all markup, URL, SQL, shell and business semantics; tool results need equivalent treatment.

// Ordinary text display: keep element/context fixed.
summaryElement.textContent = generatedSummary;

// status comes from a domain enum validator, not arbitrary SQL.
const status = parseAllowedOrderStatus(proposedStatus);
await db.query("SELECT id FROM orders WHERE tenant_id=$1 AND status=$2",
  [trustedPrincipal.tenantId, status]);
// Object/row authorization, result bounds and audit remain required.

Illustrative text/query boundaries, not a complete security implementation.

10. URLs, remote resources and SSRF boundaries

Links, images, previews and fetch tools create outbound channels, including data-bearing URLs without scripts. Avoid unnecessary automatic loads and govern destinations and behavior. Host allowlists do not authorize arbitrary sensitive payloads or credential delegation.

Server fetches need parsed URL policy, actual destination validation and suitable connection binding. Separate unchecked resolution after validation can reopen the boundary. Disable or revalidate redirects and preserve network/proxy/TLS policy. The closed lab neither performs networking nor replaces production controls.

11. Moderation, jailbreaks and threshold trade-offs

Content policies need categories, severity, context and suitable review. Classifiers and refusals have errors and drift; scores are not automatically calibrated probabilities. Evaluate task/language/risk slices, and never treat unflagged content as authorization for effects.

Challenge-set precision does not automatically transfer to production. Under assumed stable conditional rates, prevalence changes positive predictive value to p·TPR/[p·TPR+(1−p)·FPR]. Rare harms can make false flags dominate. Small-sample rates are uncertain, and the fixture is not a deployment benchmark.

12. Protect retrieval, caches, memory and trained information

Authorize before data reaches models, rerankers, providers and logs. Revalidate current access/liveness and dependency revisions as needed, since indexes and caches can be stale. Scope by trusted identities and data policies; appropriately public sharing differs from private cross-user reuse.

Poisoning can enter training, indexes, memories and tools. Track admission and provenance, version artifacts and test regressions/rollback. Trusted origins can still be compromised or wrong. Training memorization requires separate artifact/deletion processes; removing a retrieval row does not unlearn weights.

13. Review supply chains and capability changes

Review artifact and integration provenance, integrity and loading behavior. Untrusted packages or serialized objects can execute under host permissions; use appropriate formats, settings, isolation and privilege. Hashes/signatures establish aspects of identity/integrity rather than benign behavior or vulnerability absence.

Integration metadata and capabilities can change. Maintain reviewed tool/revision/credential mappings and qualify material changes; negotiation does not authorize business actions. Local execution and remote delegation carry distinct risks. Tools and peer agents do not become trusted authorities merely by joining a graph.

14. Bound consumption and define kill-switch semantics

Bound inputs, turns, tokens, fan-out, parsing, rates, concurrency and spending. Reserve before admission and reconcile cancellation. Large or recursive workloads and retry loops can exhaust resources without harmful-language signals; request counts alone may not bound expensive modalities/tools.

Enforce scoped kill switches at admission/execution rather than only UI. Coordinator shutdown does not necessarily stop stale workers or undo remote effects. Define propagation, reconciliation, revocation and degraded behavior to avoid new unauthorized work.

15. Evaluate adversarial cases and respond to incidents

An owned response loop

  1. Exercise

    Exercise both adversarial and legitimate cases.

  2. Gate / monitor

    Gate releases and monitor scoped signals.

  3. Contain

    Disable capabilities and reconcile effects.

  4. Review / regress

    Review causes, remediation and regressions.

Detection needs bounded, reviewable response.

Evaluate reviewed adversarial and benign cases across sources, languages, scopes and sinks. Measure attempts, successful violations, exposure, effects, false blocks and consumption. Cover permissions, stale access, modalities, memory and recovery rather than one phrase. Passing fixtures does not establish absence of unknown attacks.

Contain affected flows, preserve minimal authorized evidence and assess affected principals, artifacts and effects under ownership. Avoid secret-bearing debug logs. Remediate causes, invalidate or revoke as appropriate and add reviewed regressions, while qualifying control changes against legitimate tasks.

16. Teaching policy decisions and security evidence APIs

These teaching contracts distinguish authority from model assertions without exposing live services. Derive trusted identities, pin policy revisions and verify bound decisions at execution; client safety booleans do not bypass checks.

POST /internal/policy-decisions

Evaluate actions, resources and payloads under current scope.

{ runId, actionId, toolRevision, payloadHash, resourceRefs, expectedPolicyRevision }
200 { decisionId, state: "ALLOW | DENY | REVIEW", boundPayloadHash, expiresAt, reasons }

    POST /internal/security-events

    Record scoped minimized attempt/outcome evidence.

    { requestId, decisionId, boundary, outcomeCode, severity, redactedEvidenceRef }
    202 { eventId, ownerRoute, retentionClass }
    • Acceptance does not resolve an incident; evidence references remain access-controlled.

    POST /internal/capability-controls/{capabilityId}/disable

    Authorized operators revise admission policies.

    { expectedRevision, reasonCode, scope }
    200 { controlRevision, newAdmission: "DENY", inFlightReconcileRequired: true }
    • Disabling does not undo prior commits or establish immediate remote abort.

    17. Practice AI security boundaries

    How would you secure an agent that browses and reads email?

    Map data, untrusted inputs and outbound sinks, constrain capabilities and validate/review concrete effects. Test attacks and legitimate tasks rather than relying only on prompts or detectors.

    Does disabling send_email prevent all leakage?

    No: rendering, text, other tools, logs and retained information create other channels. Closing a tool path is useful but not universal protection.

    Can authorization be skipped after human approval?

    No: bind decisions and independently revalidate current authority and conditions. Review errors require bounded blast radius.

    Does a two-model summary eliminate injection?

    No: summaries or unrestricted dereferencing can reintroduce taint. Trusted typed handoffs and constrained operations are required.

    Can a hostname containing docs.example.test be allowed?

    Substring matches do not establish authority. Validate parsed scope, connections, redirects, schemes and payload policy using suitable production controls.

    Does 60% challenge-set precision transfer to production?

    Not directly: prevalence and conditional errors change predictive value. Representative slices, severity, uncertainty and drift matter.

    Can valid generated JSON be executed as a tool action?

    Parsing is only one boundary; validate domain semantics, authority, preconditions, budgets, decisions and effects.

    Does a passing security suite establish absolute security?

    No: finite coverage, changes, bugs and adaptive attacks leave residual risks. Document assumptions and maintain monitoring, containment and reviewed updates.
