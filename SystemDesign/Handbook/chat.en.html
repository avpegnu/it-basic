Designing Chat: from a durable message to every device

Understand socket routing, idempotent sends, committed ordering, gap-aware sync and receipts; experiment with reconnects, stale registries and duplicated or reordered messages.

Follow the life of a message

  1. Accept durably

    Deduplicate commands, authorize and commit before ACK.

  2. Route to devices

    Find the correct session generation; live frames can be delayed or lost.

  3. Apply in order

    Buffer gaps, deduplicate and advance the correct conversation/device cursor.

  4. Recover and operate

    Reconnect with jitter, catch up, bound buffers and measure each milestone.

Read by guarantees rather than component names alone.

  • Sockets can be replaced; acknowledged history must survive under the agreed durability contract.
  • Accepted, delivered and read are distinct milestones, especially across multiple devices.
  • Order within a conversation; advance cursors only through fully processed positions, not the largest observed sequence.
  • Pub/sub and push accelerate or wake clients; authoritative history and sync recover lost live events.
  • Idempotency, append, sequence and outbox need an atomic boundary or equivalent state machine.

1. Start a chat design with user-visible guarantees

Accepted is not read

  • Accepted: the message and retry result have reached the server durability boundary.
  • Delivered: a device confirms under a defined contract; read: a client advances a marker after a specified reading action.

Ordering has a scope

  • A committed order within each conversation; no total order across all conversations is required.
  • Concurrent sends may be ordered by the owner’s commit order; client timestamps are metadata.

Durability needs a failure boundary

  • State whether ACKs survive a process crash, node loss or region loss; asynchronous replication does not automatically protect every region disaster.
  • Do not promise “never lost” without backup, replica and failover behavior that supports the invariant.

Chat has two kinds of state: durable message history and disposable, rebuildable connections/sessions. Server acceptance, device receipt and a person reading a message are three different events. A WebSocket-to-database diagram alone does not explain disconnections, retries or multiple devices.

The baseline covers 1:1 chat and groups up to 500 members, shared multi-device history, receipts, presence and offline push. Example targets are online-delivery p99 below 200 ms at a defined boundary, per-conversation committed ordering and acknowledgement after durable commit under an agreed failure model. Voice/video, million-member broadcasts and full-text search are outside the baseline and considered as extensions.

2. Size messages, sockets, heartbeats and fanout separately

With 100 million DAU and 40 messages per user per day, the example produces four billion messages daily. If 50 million users are online at peak with 1.4 connected devices per user, capacity must cover 70 million sockets, not 50 million. These factors are planning inputs, not a real product measurement. Media upload/download is separate and excluded from the 200 B text payload.

If a gateway has been benchmarked under your TLS, buffer, workload and resource limits at 100,000 sockets, and you target 70% utilization, 70 million / 70,000 requires 1,000 active gateways. This is conditional arithmetic, not a claim that every server holds 100,000 sockets. Add failure-domain headroom and test outbound bandwidth, descriptors, memory per connection, event-loop lag and reconnect rate.

Thirty-second heartbeats create about 2.33 million heartbeat arrivals/second at peak before replies. Handle liveness at gateways and batch/coalesce registry updates instead of globally writing on every ping. Delivery fanout grows with online recipients/devices; a message in a 500-person group is not as cheap as a 1:1 message.

3. Choose a transport and manage connection lifetime

A socket lifetime is not a message lifetime

  1. Connect and authenticate

    Check Origin/token/device and issue a session generation.

  2. Heartbeat and send frames

    Bound frame size/rate/buffers and track liveness and permissions.

  3. Reconnect and synchronize

    Back off with jitter, register anew and catch up from a durable cursor.

Connections can be replaced; committed history must outlive a gateway.

WebSocket fits frequent bidirectional frames. SSE plus HTTP sends can also support chat, and long polling is a viable fallback rather than inherently wrong. Choose based on latency, proxy/network compatibility, authentication and operations. L4 or L7 load balancing can work with proper transport support; examine connection timeouts, draining and resource limits rather than choosing by layer label alone.

The handshake authenticates a principal/device, but permissions are not permanent: tokens expire, accounts are revoked and group membership changes while sockets remain open. Refresh/re-authenticate or close according to policy, and check command permissions and appropriate membership versions. For cookie-authenticated browsers, validate Origin against cross-site WebSocket hijacking; avoid sensitive tokens in logged URLs. TLS secures a hop but does not provide E2EE.

4. Send, history and receipt contracts

Preserve clientMsgId across retries and scope it by (conversation, sender principal, clientMsgId). Store a payload hash so a reused key with a different body is not treated as a successful retry. Large sequence/message IDs travel as JSON strings to avoid JavaScript Number precision loss. Clients create another ID only for a genuinely new send action.

A conversation history cursor is not an account cursor. Synchronizing many conversations needs per-conversation cursors/a vector, or an opaque server-defined account change-log cursor. History snapshots and live streams need a high-water mark/barrier: subscribe and buffer, catch up, then merge with deduplication, or use an equivalent protocol that closes the gap between the paths.

      5. Separate connections, durable appends and live fanout

      A gateway owns socket state but should not be the only place storing an acknowledged message. A conversation owner can be a sharded service/actor or a transactional append path; ownership metadata/terms are real state even with stateless API frontends. A small deployment can use relational transactions. Sharding must preserve the append atomic boundary or introduce an equivalent log/state machine.

      Live pub/sub can lose messages when a subscriber disconnects. Durability survives if history is committed and clients have a recovery protocol. Delivery can still stall indefinitely if sync runs only on reconnect while the socket stays open after a lost bus frame. Use gap detection, periodic watermarks/catch-up or an appropriate delivery-retry/receipt policy.

      One message: durable acceptance before device delivery

      Component map; the complete ordered request paths are explained below.

      Send and receive a durable ACK

      1. Alice sends a frame with a stable clientMsgId.
      2. Forward the command with the authenticated principal; the owner rechecks conversation permissions.
      3. In one transaction: deduplicate, assign a committed sequence, append and create an outbox entry.
      4. The commit reaches the defined durability boundary. This says nothing yet about Bob’s devices.
      5. ACK includes the message ID and sequence; the same payload/key retry receives the same result.
      6. Alice changes pending → accepted, not directly to read.

      Fan out to an online device

      1. A worker reads the committed outbox job and an immutable or explicitly versioned message.
      2. Look up all authorized Bob sessions/devices.
      3. Return gateway B and a session generation; the snapshot can be stale.
      4. Publish a message-ID event to the gateway-B route.
      5. The gateway receives the frame/hint; history sync repairs a loss here.
      6. The frame reaches the correct device; the client deduplicates, applies and advances its contiguous cursor.
      7. The device sends a delivered receipt after local apply/persistence under the contract. This is not a read receipt.
      8. Validate the receipt’s membership/device and advance its appropriate monotonic marker.

      Offline: push is a hint, history is authoritative

      1. The outbox contains a message already acknowledged to Alice.
      2. Look up Bob’s sessions.
      3. The snapshot has no live session; a reconnect race can still exist.
      4. Send a notification under quiet-hours, privacy and collapse policies.
      5. The OS may display a notification or wake the app; push can be lost, delayed or collapsed.

      Reconnect and catch up after a cursor

      1. Reconnect with backoff/jitter; the gateway authenticates and registers a new generation.
      2. Upsert the session; old cleanup deletes only when its generation still matches.
      3. Request conversation history after the contiguous cursor; this may use HTTP separate from the socket.
      4. Check membership and read a page by committed log position under retention policy.
      5. Return a page and a server-defined cursor; do not mix sequences from different conversations.
      6. Merge the page with the live buffer, deduplicate message IDs/sequences and advance the contiguous cursor.
      Alice / sender
      Preserves clientMsgId on retry; stays pending until a committed ACK. Client clocks do not decide shared order.
      Gateway A
      Holds Alice’s socket, limits frame size/rate and forwards commands. Scaling does not automatically move an existing connection.
      Conversation owner
      Serializes appends within a conversation; checks membership, deduplicates and durably commits before ACK. Ownership is distributed across conversations.
      History + outbox
      One transactional boundary in the baseline: message, idempotency result, sequence and fanout job. Replication/commit durability follows the SLO.
      Fanout worker
      Reads the outbox after commit and retries using message IDs. A successful publish does not prove recipient receipt.
      Session registry
      Maps a user to multiple (device, gateway, generation) sessions. TTLs and compare-and-delete limit ghosts/stale cleanup; lag remains possible.
      Gateway delivery bus
      Routes by gateway. Ephemeral pub/sub accelerates live delivery; offline recovery depends on history.
      Gateway B
      Holds recipient sockets; validates session generations, bounds send buffers and handles slow clients.
      Bob / devices
      Applies by conversation + sequence/message ID; persists device cursors and resynchronizes after reconnect.
      Push notification
      A wake-up/new-message hint that can be delayed or duplicated. It is not authoritative history or a read receipt.

      6. Route to multiple devices with a stale registry

      A registry maps a user to a set of sessions rather than one user → gateway: phones, desktops and web tabs may be online simultaneously. Records include device/session ID, gateway, generation/epoch and expiry. A disconnect deletes only a still-matching generation; blindly deleting by user after reconnect can remove a new route. TTL cleanup converges ghost state but does not prove instantaneous presence.

      A routing miss or stale session does not delete a durable message. Workers can refresh and retry within a budget; clients catch up from history. Avoid broadcasting every event to every gateway at scale merely to bypass the registry. Use per-gateway subscriptions or partitioned routing and measure queueing/backpressure. A registry outage can degrade live delivery while durable sends/history continue under the contract.

      7. Make idempotent send atomic with the append

      Read dedup → allocate sequence → append → write dedup has races and crash windows. Concurrent requests can both miss deduplication; a crash after append commits but before recording the key lets a retry create another message. The baseline locks a conversation row/uses a serialized owner and atomically checks the key, appends, advances the committed sequence and writes the outbox. A post-commit retry returns the same sequence; payload mismatches must not silently overwrite data.

      If a dedup key expires while a long-offline client still retries, the idempotency promise also expires unless unique message identity remains in history. Publish a retry window or retain uniqueness for the appropriate retention period. An outbox relay may publish duplicates; gateways, clients and downstream side effects need stable identities. A fire-and-forget call after append can lose the fanout job on a crash.

      send(principal, command):
  validate(command)
  begin transaction on conversation owner/shard
    lock conversation row
    require current membership and send permission
    old = find(conversation, principal, command.clientMsgId)
    if old exists:
      require old.payloadHash == hash(command.payload)
      return old.result after finishing transaction
    seq = conversation.nextCommittedSeq
    insert message(conversation, seq, principal, clientMsgId, payloadHash, body)
    advance conversation.nextCommittedSeq
    insert outbox(messageId, fanoutVersion)
  commit to the declared durability boundary
  return ACK(messageId, seq)

relay: publish committed outbox jobs; retry with the same messageId

      Pseudocode for a same-shard transaction, not an existing API. Unique constraints protect identity; durability, failover/fencing and membership-race policy depend on the chosen database/owner.

      8. Committed ordering, gaps and reconnect cursors

      Client timestamps cannot establish shared order because of clock skew, offline sends and multiple devices. Choose per-conversation committed sequences/log positions. The baseline increments its counter within the append transaction to produce contiguous committed entries; an independent INCR-then-append allocator can leave a hole on a crash. Such designs need committed-log cursor semantics or explicit skips/tombstones/barriers rather than waiting forever for an entry that never existed.

      After applying sequence 1, receiving sequence 3 makes the highest received value 3 while the contiguous cursor stays 1. Buffer 3, fetch the gap, deduplicate and apply; advance only through fully processed positions. Edits/deletions need versioned events or tombstones so clients can synchronize changes, not just original messages. Permission-filtered history requires compatible server cursor semantics to avoid artificial gaps.

      9. Delivered, read and multiple devices need distinct markers

      Define delivery: bytes written to a socket, a frame received by an app, or persistence on the device? Choose a milestone and acknowledge it accordingly; a successful socket write only proves that the local network stack accepted bytes. Each device has its own delivered cursor. An account-level read marker can be the maximum device read marker if the product defines “read anywhere,” but it does not prove every device has downloaded the history.

      Use max(current, incoming) for monotonic markers subject to permission/bound checks, preventing late requests from rolling state back. lastSeq − readSeq is not a valid unread count when logs include system events, tombstones, permission filters or late membership joins. Count eligible messages or publish an approximation. Large groups should not fan every receipt to every member/device; aggregate or display only what the UI needs.

      10. Group fanout, presence and typing have different durability

      Committed messages

      • Durable history, retry idempotency and recovery after a lost live event.

      Approximate presence

      • Soft state with heartbeats/TTLs; track freshness and aggregate sessions.

      Disposable typing events

      • Ephemeral, rate-limited/coalesced and short-lived; no full offline replay is needed.

      Small groups often append one authoritative message and fan events out to gateways with online members, batching by gateway to reduce duplicate network work. Deliver only to members authorized under the chosen join/leave policy. Large groups can distribute watermarks/invalidations and let clients pull by cursor. The threshold is not universally 500 or 10,000; it depends on message rate, online fraction and receipt cost.

      Presence infers liveness from heartbeats/disconnects rather than proving a person is online. TTLs longer than heartbeat intervals tolerate jitter/network loss while creating false-online windows; short TTLs create flapping. Aggregate sessions so a desktop disconnect does not mark a user offline while their phone remains connected. Push only to active watchers, debounce and enforce invisible/last-seen privacy.

      11. History, inbox and media schemas

      The primary history lookup is conversation + cursor. Options include relational partitions or a wide-column layout ((conversation_id, bucket), seq), with buckets based on entry counts or time. Monthly buckets do not bound partition bytes for an extremely hot conversation; size them using traffic, payload and engine limits with a bucket directory. Late events/edits need bucket/version rules rather than timestamp sorting in place of committed order.

      The inbox is a per-user view of conversations, recent activity and unread metadata; it can be built from events with idempotent updates. Inbox lag does not imply missing history. Inbox pagination needs a stable tie-breaker and cursor rather than potentially equal timestamps alone. Store membership separately with versions/epochs and clear pre-join/post-leave history rules.

      Upload media through authorized object storage with separate completion handling; messages contain object references and attachment state. An existing WebSocket is not a reason to send large files through the message gateway. Scanning, signed access, retention and orphan cleanup need policies; E2EE may prevent plaintext-style server scanning.

      12. Gateway crashes, deployments and reconnect storms

      Gateway loss must not erase acknowledged history. Clients reconnect through a load balancer to another gateway, register a new generation and sync from their cursors. Registry TTL is cleanup, not a prerequisite for catch-up. With 100,000 simultaneous reconnects, authentication, TLS handshakes, registry writes and history reads can overload even at normal message rates. Test full-jitter backoff, admission control and paged sync together.

      Deployments drain: stop accepting new connections, retain old ones for a bounded period, then request jittered reconnection when needed. Do not promise zero dropped connections when sockets eventually must terminate. Slow clients need bounded queues: coalesce ephemeral events, prioritize durable-message hints, then disconnect/resync above a threshold. An unbounded buffer turns a slow phone into a gateway memory leak.

      13. E2EE, multiple regions and deletion

      E2EE changes key distribution, multi-device enrollment, recovery/backups and attachment encryption; it is not merely a ciphertext body field. A server without plaintext generally cannot use the same full-text search/moderation/preview mechanisms as a plaintext design; client-side or specialized mechanisms have their own trade-offs. E2EE does not automatically conceal metadata such as participants, timing or group membership. Use evaluated protocols/libraries rather than inventing cryptography from a chat diagram.

      A conversation home region can serialize writes while users connect to nearby gateways. Cross-region forwarding adds RTT to send acknowledgements and delivery, so a 200 ms target may not hold for all geographies. Home-owner failover needs term/fencing and a committed position. Promoting an asynchronously replicated copy missing an acknowledged suffix breaks an ACK-survives-region-loss promise. Choose synchronous durability, accept nonzero RPO or clearly limit the failure model.

      Deletion/edits need retention, legal hold and propagation rules for devices, caches, indexes and backups as appropriate. Tombstones can propagate and plaintext/media can be removed under policy, but screenshots or recipient copies outside the app cannot be reliably recalled. Compaction must preserve cursor/skip semantics so devices do not wait forever for deleted messages.

      14. Measure the message journey and test invariants

      Separate acceptance latency, committed-to-delivered latency and read-marker latency. Track reconnect success, history catch-up time, gaps, duplicate rates, outbox age, gateway buffer saturation and registry staleness. Measure connections and reconnect/sync rates by region/failure domain rather than total CPU alone. Presence accuracy has freshness metrics and is not evidence of durable delivery.

      Crash before commit, after commit before ACK and after ACK before publish; the three cases must produce contract-appropriate outcomes. Run concurrent sends with the same clientMsgId, inject duplicated/reordered frames, drop a frame while the socket stays open, take a device offline beyond retention and revoke membership between sync pages. Correctness tests should compare final history, identities and cursors rather than merely counting 200 responses.

      15. Practice with failure scenarios

      State scope and invariants, explain one message end to end, then break a point in the path. A technology list cannot prove a guarantee; identify the atomic boundary, owner and recovery behavior.

      TCP orders a WebSocket stream. Why are sequences and sync still needed?

      TCP orders bytes within one connection. Multiple devices, reconnects, bus/worker routes, retries and history fetches use different paths. Per-conversation committed sequences with deduplication/cursors let devices converge without a global order across the system.

      A client has sequences 1 and 3. What is wrong with saving cursor 3?

      An endpoint returning sequences after the cursor would skip message 2 forever. Keep the contiguous cursor at 1, buffer 3 and fetch the gap. If allocation permits holes that never commit, the protocol needs skips/barriers or committed-log cursors rather than blindly assuming contiguity.

      Are cached dedup keys enough for concurrent retries of one send?

      Not if read/check/append/set are non-atomic. Concurrent misses or a crash after append can create two messages. Keep unique identity and append/result in one transaction/serialized state machine; hash payloads to reject conflicting key reuse. Retention must match the retry window.

      Can an acknowledged message disappear when its gateway dies?

      The baseline commits history independently, so a gateway crash alone does not lose it. Sender retries merge with the same result and recipients reconnect/sync. This does not follow if durability is only gateway-local disk or asynchronous replicas lost in the same failure domain. Specify the failure model instead of unconditional “never lost.”

      The registry says online but the recipient receives nothing. What happens?

      Online is a potentially stale hint. Check the session generation, refresh/retry within a budget, and ensure catch-up through gaps/watermarks or reconnect. If the final bus frame is lost, no later frame reveals a gap; periodic watermarks or delivery retries are needed, not gap detection alone.

      Does a phone read receipt prove the desktop has finished syncing?

      No. An account read marker may advance when any device reads; the desktop still has its own lower cursor and needs sync. Using the read marker to skip desktop history can lose local data. Separate account read state from per-device applied/delivered positions.

      Should a 100,000-person group use the same fanout/receipts as a ten-person group?

      Usually it needs changes: batch by gateway, push watermarks and pull logs, target active subscribers and aggregate receipts. Decide using rate, online fraction, device count and latency rather than membership alone. A single conversation owner can bottleneck; partitioning or relaxing order must be explicit.

      Does E2EE automatically hide who is talking to whom?

      No. Payload encryption alone does not conceal routing metadata, timestamps, accounts/devices or membership. Reducing metadata requires additional design; search, moderation, backups and device enrollment also change. Use evaluated cryptographic implementations and explain the system’s limits instead of inventing a protocol.
