Designing an LLM Inference Platform: scheduling, streams and usage

Connect memory, iteration scheduling, prefix routing and token escrow to latency, cancellation, metering and SLO-constrained economics.

A generation has several resource contracts

  1. Admit

    Validate/count, reserve quota and bound queues.

  2. Place and execute

    Warm compatibility, hard allocation and execution.

  3. Stream and cancel

    Bound buffers with explicit attempts/outcomes.

  4. Meter and reconcile

    Authoritative usage, identities and safe release.

Preserve latency, memory and accounting together.

  • SLO/quality-constrained goodput differs from raw throughput.
  • Paged/prefix KV still needs per-rank capacity, compatible identities and hard allocation.
  • Continuous batching reduces idle slots while contexts/batches change execution cost.
  • Streaming/cancellation/retries need explicit ownership and partial-output semantics.
  • Queue rejections roll back reservations; final usage needs durable settlement/reconciliation.

1. Inference platforms own lifecycles beyond GPU endpoints

User latency

GPU resources

  • Compute, bandwidth, per-rank memory and topology.

Request lifecycle

  • Admission, attempt ownership, cancellation and final usage.

This generation service supports streams, model/adapter revisions, interactive/batch tiers, quotas and metering. Training, retrieval/tool orchestration and model research are separate scopes, with product-specific safety/security hooks. Inference fundamentals explain computation/memory; this case connects gateways, scheduling, KV ownership, streams and final accounting under explicit failure contracts.

Optimize useful output cost under latency/quality targets rather than raw throughput with timeouts. Define shapes, context distributions, input/output tails, concurrency, regions, availability and queue bounds. Tiny and very long requests differ in work/KV residency, so requests-per-second alone cannot represent cost.

2. Separate input capacity, decode capacity and occupancy

Assume 50 million daily requests, means of 1,000 input/300 output tokens and a threefold peak. Average demand is about 579 requests/s, 173.6K output tokens/s and 578.7K input tokens/s; peaks are roughly 1,736 requests/s, 521K output tokens/s and 1.736M input tokens/s. These are sizing inputs, not measurements. Prefill/decode need separate resource curves; caching can reduce prefill work without automatically changing logical usage or decode cost.

If a hypothetical validated SLO/workload benchmark yields 2,500 output tokens/s per eight-GPU decode replica, peak decode sizing is 209 replicas or 1,672 GPUs before reserves. This excludes prefill, redundancy, warming, skew and goodput losses. Little’s Law relates stable averages: roughly 579/s and an assumed 12-second mean imply about 6,944 requests in-system, not necessarily all KV-resident because admission queues precede GPU residency.

3. Request, attempt and stream events have distinct identities

This teaching API does not claim provider wire compatibility. Request identities retain intent/model parameters, attempt identities track execution generations and event sequences support explicitly implemented resume protocols. Headers alone cannot reconstruct KV, sampling state or missed output. HTTP/SSE chunks may contain multiple tokens, metadata or terminal states rather than one token each.

Before headers, validation/admission errors follow HTTP contracts. Once streaming begins, the status cannot become a fresh response; use terminal/error events when possible and persist server outcomes. Disconnects can hide final usage. Resume needs retained events/cursors and compatible execution state; otherwise expose interrupted partial output and explicit retries rather than silently splice new answers.

          4. Familiar gateways with different resource ownership

          Gateways authenticate/validate streams, admission reserves quota/bounds queues and schedulers select warm replicas before hard allocation. Colocated replicas own prefill/decode/KV, prefix caches enforce compatibility/isolation and registries pin all relevant versions. Durable metering is independent of client streams. Unbounded gateway RAM is not an admission strategy.

          Scheduler hints can be stale, so hard allocation must atomically reserve, preempt or reject before execution. Preserve identities and cleanup ownership across retries. Queue bounds include estimated token work/deadlines because request counts hide long contexts. Tier fairness must also address starvation.

          From admitted requests to final usage

          Component map; the complete ordered request paths are explained below.

          Generate and stream

          1. Submit model intent, output bounds and stable identities.
          2. Validate contexts/tokenization and reserve quota under admission rules.
          3. Bound queue insertion and refund rejected pre-start admissions by identity.
          4. Select eligible warm replicas using deadlines/work/KV evidence.
          5. Atomically admit capacity before prefilling prompts/suffixes.
          6. Hand off locally or transfer compatible KV under explicit protocols.
          7. Stream sequenced deltas with potentially multiple tokens per chunk and bounded buffers.
          8. Render partial output with explicit completion/error/cancellation states.

          Conditional prefix reuse

          1. Consider prefix signatures/scopes alongside load.
          2. Match effective tokens, versions, KV/position settings and tenant scopes.
          3. Pin reusable pages and prefill uncached suffixes.
          4. Decode still generates new output and grows KV state.

          Disconnect and cancel

          1. Disconnect or request cancellation without assuming terminal outcomes.
          2. Signal the current attempt and stop at safe execution boundaries.
          3. Publish terminal outcomes and authoritative counters after stopping/finalization.
          4. Deduplicate terminal events and settle usage/refunds, reconciling unknown outcomes.

          Record usage even after clients leave

          1. Record input/cache/generated counts, pinned versions and termination status.
          2. Apply identified settlements once without duplicate charges/refunds.
          3. Release reservations under policy, separately from rate-limit refill semantics.

          Warm models before accepting traffic

          1. Publish compatible revisions/configurations and eligibility metadata.
          2. Load/verify weights, templates and kernels before warm readiness.
          3. Warm pinned versions and drain old streams without incompatible KV reuse.
          App / SDK
          Tracks request identities, supported stream cursors, partial output and cancellation.
          Gateway / stream
          Authenticates and bounds requests/streams; disconnects trigger cancellation/reconciliation.
          Quota / admission
          Atomically reserves token budgets and bounds queues; rejection rolls back reservations.
          Tier / model queues
          Bounds token work/deadlines with fairness between interactive and batch traffic.
          GPU-aware scheduler
          Checks warm compatibility, queues/work, hard KV admission and bounded prefix affinity.
          Prefill execution
          Encodes prompts and builds compatible KV; chunking/transfers are workload-dependent choices.
          Decode execution
          Schedules iterations, generates tokens, counts output and processes cancellation.
          Paged KV / prefix
          Owns per-rank pages, pinned references, compatible keys and tenant isolation.
          Model / adapter registry
          Pins model/adapter/tokenizer/template versions and compatible kernels with verified readiness.
          Terminal usage log
          Durably records usage/status/attempt IDs with deduplication and reconciliation, independent of client receipt.
          Usage settlement
          Settles reservations under identities/policies and audits counters/refunds.

          5. What do TTFT, inter-token latency and goodput measure?

          Before first output

          • Queue age, tokenization/prefill/transfers and flushing.

          During generation

          • ITL tails, batching, KV reads and backpressure.

          Outcome

          • Completion/cancellation/errors in SLO denominators.

          Client TTFT includes networking, admission/tokenization, queues, prefill/transfers and initial generation/flush as implemented. Prefill completion need not equal visible output. ITL tracks defined event/token gaps; mean post-first-token TPOT can be defined as (last-token time − first-token time)/(output count −1) for at least two tokens, and does not replace gap distributions. Proxy buffering can burst otherwise regular engine output. Define denominators and handle single-token outputs separately.

          Prefill often emphasizes compute and small-batch decode bandwidth, but contexts, batching, attention, communication and multimodal work change bottlenecks. Goodput means useful work satisfying stated latency/quality/termination criteria. Completed-only metrics can hide overload by excluding abandoned or failed requests.

          6. Continuous batching reuses slots without creating free compute

          Static groups may retain capacity until completion while returning short results earlier. Iteration-level scheduling reuses freed slots across heterogeneous outputs. Real engines still have token/batch budgets, allocation and prefill scheduling. Adding sequences increases compute/attention/KV work; weight-reuse intuition is not a constant-cost performance law.

          The fixed-token-per-tick lab isolates occupancy rather than predict GPU speedups. Compare identical work/arrivals and early completion behavior first. Larger batches can improve throughput while worsening latency; optimize under SLOs rather than occupancy alone.

          7. Memory capacity needs correct shapes and per-rank budgets

          Full-attention KV payload per token is 2 ×layers ×KV heads ×head dimension ×bytes, using KV rather than query heads. An assumed 80-layer/eight-KV-head/128-dimensional/two-byte shape uses 320 KiB per token and roughly 426 MB or 406.25 MiB for 1,300 tokens before overheads. This is not universal across 70B models; other attention/state architectures need different accounting.

          140 GB of weights does not prove two 80 GB devices suffice after runtime, workspace, graphs, KV, communication and reserves. Aggregate memory cannot rescue per-rank OOMs. Parallel layouts can shard, replicate or pad KV, so validate actual ranks. Weight quantization does not automatically quantize KV, and total gains/quality/kernel compatibility require evaluation.

          Paging reduces some fragmentation and supports sharing but needs block tables, pinning and safe release. Maximum reservations are conservative; incremental growth needs reserves/preemption. Engines differ in queueing, recomputation/offload support and costs. Release KV at safe boundaries after confirmed cancellation.

          8. Prefix affinity needs load bounds and isolation

          Reuse requires exact effective token prefixes plus compatible models/adapters, positional/attention settings, KV formats and isolation namespaces. Templates/tokenizers can change the tokens for similar text. Cached pages occupy memory and active requests pin shared/private pages. Reuse saves eligible prefill work, not output generation or automatic quota discounts.

          Warm caches can be worse than idle cold replicas when backlog dominates. Routing considers compatibility, queue/work, KV and deadlines/tiers, followed by atomic allocation. The lab uses abstract work units; production predictions need calibration and fairness rather than raw queue counts.

          9. Choose chunking or disaggregation from evidence

          KV handoffs need ownership

          1. Prepare

            Targets reserve blocks and verify compatibility.

          2. Transfer

            Copy/check data under attempt identities.

          3. Accept

            Targets confirm usable state before source release.

          4. Recover

            Reconcile owners on timeouts/cancellation and reclaim safely.

          Do not release sources before targets own the state.

          Long unchunked prefills can delay mixed decode iterations. Chunking bounds prompt work per round while trading TTFT, ITL and overheads. Separate pools reduce interference and allow independent sizing/parallelism but add queues, handoffs and transfers. Actual scheduling may not process every prompt in one indivisible pass.

          At 320 KiB/token, an 8,192-token prompt has 2.5 GiB of KV. An assumed effective 50 GB/s link has a roughly 53.7 ms payload serialization lower bound before contention, latency or layout conversions. Nominal NIC rates are not end-to-end rates. Transfers need compatible layouts/versions, ownership/pinning and cancellation cleanup. Compare SLO goodput and total cost against colocated/chunked baselines.

          10. Reservations, usage and rate-limit refill differ

          Validate/count under pinned tokenizers and reserve bounded token or cost budgets. Queue rejection must roll back identified reservations rather than return an error after spending them. Fixed budgets, TPM limiters and monetary ledgers have distinct refill/refund semantics. Cache discounts and generated/hidden/reasoning token categories also require explicit policies.

          Final usage comes from trusted execution counters with request/attempt identities and status-specific policy. Cancellation requests alone cannot release ongoing exposure. Persist/deduplicate/reconcile terminal events despite worker/gateway failures or missing client receipts. Corrections need versioned policies rather than arbitrary last-arrival replacement.

          11. Stream retries depend on more than first output

          Before visible output, previous attempts can be running or buffering generated tokens. Blind failover can duplicate work/charges. Use execution ownership/fencing or contracts establishing nonacceptance, confirmed stopping or retained results. Partial streams cannot silently splice restarted generations. Explicit retries need new-attempt/output/accounting policies, and seeds alone do not guarantee identical outputs across execution changes.

          Disconnection/cancellation are delayed and kernels may stop only at safe boundaries. Record counts and release state under ownership. Worker loss can destroy volatile KV/sampling state, so resumption requires explicitly retained evidence. Slow consumers need bounded buffers and cancellation/spooling/backpressure policies rather than unlimited GPU/KV retention.

          12. Version models, adapters and execution configurations together

          Registries pin weights, tokenizers/templates, adapters, quantization, kernels and contexts. Readiness follows loading, verification and warmup rather than pod starts. Canary quality/latency and drain version-pinned streams before unloading, avoiding incompatible cache reuse. Measure cold starts across distribution/caching/allocation/warmup instead of assuming fixed durations.

          Data replication adds throughput while other parallel layouts change rank memory/communication. Weight-size division alone cannot choose GPU counts. Compatible LoRA adapters can share supported bases/kernels under registry/cache policies; full-weight fine-tunes do not automatically share base payloads. Adapter affinity/eviction needs fairness and verified execution support.

          13. Unit costs need SLOs and explicit cost boundaries

          Under hypothetical eight-GPU costs of $3/device-hour and 2,500 useful output tokens/s, decode-GPU-only cost is about $2.67 per million outputs at full sustained goodput, or $5.33 at half useful throughput with unchanged cost. These are not current prices or total costs: prefill, infrastructure, warming, redundancy and failures are excluded. Comparisons require matched quality, contexts, workloads and SLOs.

          Caching, quantization, speculation and batching affect different costs. Speculation adds drafting/verification and depends on acceptance; high batches or hard workloads may not benefit. Quantization changes numerical/kernel/quality behavior beyond size ratios. Flexible offline capacity needs interruption/deadline controls and is not automatically appropriate for interactive traffic.

          14. Warm capacity, fairness and safety budgets

          Scale from queued work/age, KV pressure, goodput, preemptions and model/tier skew. CPU/GPU utilization alone is insufficient but can still aid diagnosis. Warm reserves/prefetching and traffic smoothing account for provisioning delays. Shed at known nonacceptance boundaries rather than queue indefinitely.

          Bound tenant spending, context/output, parallelism, adapters, caches and retained output. Model artifacts/adapters need supply-chain controls. Safety stages add their own latency/throughput/cancellation behavior, potentially buffering output. Protect prompts/keys/logs and enforce cache isolation and retention as service requirements.

          15. Data models and failure evidence

          Requests retain tenant identities, pinned intents and attempts; attempts track ownership/cancellation/reservations/terminal usage. Events define counters, revisions, statuses and settlement versions. Replica observations need freshness/epochs and are not allocation locks. Final ledgers can avoid per-token hot paths without becoming best-effort fire-and-forget records.

          Drill reservation crashes, queue rejection, mid-stream loss, slow/disconnected clients, duplicate terminal events and rollouts. Verify conservation, settlement identity, KV ownership, compatible caches, bounded queues and visible partial outcomes. Include failures/abandonment and per-replica series rather than hide skew in fleet averages.

          16. Practice latency and failure boundaries

          Draw long prompts, overloaded prefix hits, partial-output disconnects and duplicate terminal events. Identify quota/KV ownership, execution authority and client knowledge at each stage, then specify measurements before changing batching/pools.

          Does good mean TPOT prove smooth streams?

          No. Gap tails, buffering, stalls and excluded failures can hide behind means. Define measurement boundaries/denominators and single-token behavior.

          Why can high cache hit rates coexist with poor TTFT?

          Affinity can create queue skew, and caching only reduces eligible prefill. Compare work/age, compatibility and hard memory admission against idle cold replicas.

          What happens when queues reject reserved requests?

          Roll back identified reservations exactly once. Error returns do not replace refunds; distinguish spending budgets, TPM refill and monetary settlement.

          Should disconnections immediately refund everything?

          Not while execution is active/unknown. Cancel, confirm authoritative terminal usage and settle/release under policy; visible text need not equal generated counts.

          Can pre-first-token requests blindly fall back?

          Not automatically: previous work may be running or buffered. Establish nonacceptance, stopping/fencing or execution deduplication/reconciliation, with explicit partial-output policies.

          Do 140 GB of weights justify two 80 GB GPUs?

          No. Per-rank runtime, KV, workspaces, communication, reserves and execution topology must fit and meet SLOs.

          Is disaggregation always better?

          No. It adds transfer, topology, allocation and failure costs. Compare against chunked colocation under matched quality/workload/SLO and total costs.

          Do broker usage events imply exactly-once billing?

          No. Durable outcomes must cooperate with identified/versioned sink settlement. Duplicates, lost replies, corrections and cancellation need recovery; arithmetic balance alone does not prove correct charges.
