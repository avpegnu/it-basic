Load balancing and consistent hashing: request distribution and ownership

Choose L4/L7, compare algorithms under long requests, handle health/draining and use a hash ring without confusing routing with data migration.

Request balancing selects where a request runs; consistent hashing determines key placement/ownership. The problems can be related without being identical.

  • Equal request counts do not imply equal compute, connections or latency.
  • L4 routes connections/flows; L7 can route HTTP requests using application metadata.
  • Consistent hashing limits remapping on membership changes but does not solve hot keys or migrate data by itself.
  • Health, readiness, overload and graceful draining need separate semantics; retries need budgets and idempotency.

1. Two problems that are easy to confuse

Choose a request executor

  • A stateless request may run on several eligible nodes.
  • Choose an algorithm based on service times, load and connection behavior.

Choose an owner by key

  • Keys have placement or ownership that must be located consistently.
  • Changing the mapping does not mean data migration has finished.

Load balancing chooses a request/connection destination to spread work. Data partitioning chooses a key’s owner to find the right data. Hashing can serve both, but their goals differ: a stateless web API can use any healthy node, while a cache/storage key needs its defined owner or replica.

Balancing may live at the edge, between services, inside clients or in a mesh. Multiple layers interact: an edge can maintain a long HTTP/2 connection to one proxy that balances requests again. To diagnose skew, identify whether each policy chooses by connection, request or key rather than relying on a round-robin label.

2. L4 and L7: what information is available?

L4 commonly selects by transport flow, IP/port and connection state. TLS pass-through does not expose encrypted HTTP paths/headers. An L7 proxy understands HTTP and can terminate TLS, route by host/path, enforce request limits and observe statuses/latency, at the cost of parsing, connection management and a plaintext trust boundary.

One HTTP/2 connection can carry many streams, so least connections need not represent active request load. WebSockets/long streams may last hours and retain buffers/state. Choose resource-relevant metrics such as active requests, queued work, connection memory or latency and benchmark policy stability.

3. Algorithms and actual workloads

Round robin is simple and can fit similar nodes/requests. Weighted round robin uses measured capacity shares rather than CPU counts alone when IO or memory limits work. Least connections counts connections; least outstanding/request counts active work under the proxy’s definition. Neither knows a new request’s duration in advance.

Power of two choices samples two candidates and chooses the lower-load metric. It avoids scanning the whole pool, while sampling, tie-breaking, weights and metric freshness affect results. Adaptive latency policies can react to slow nodes but need smoothing/slow start to avoid recovery floods and feedback oscillation.

4. Health checks, readiness and overload

Liveness asks whether a process is alive/progressing; readiness asks whether it should receive new work. Active checks probe periodically; passive detection observes real-request failures/timeouts. Use thresholds/hysteresis to avoid flapping on transient errors. Probes must be cheap and bounded so they do not create their own bottleneck.

A shared dependency failure can make every node unready. Panic-routing to all nodes or removing the entire pool changes user behavior dramatically; define and test the policy. Overload differs from node death: admission/load shedding can preserve health by rejecting some work instead of growing queues into mass timeouts.

Retry another node only under safe operation semantics and remaining deadline/budget. Node A timing out does not prove no commit; payments need the same idempotency key and reconciliation. Layered retries amplify outages, so balancing must not conceal every error with unlimited retries.

5. Graceful drain, slow start and sticky sessions

During deployment, drain a node by stopping new work, allowing in-flight requests a deadline and then closing. Long streams need application reconnect/resume and jitter; waiting for hours-long WebSockets is not practical. Preserve remaining-pool capacity throughout rolling deployment and new-node warm-up.

Sticky sessions improve locality or retain temporary sessions, but node loss still requires state recovery. IP affinity skews users behind NAT and changes with network switching. Externalize durable state and use affinity where measured locality benefits justify explicit failover semantics.

6. Global balancing and failover

Global routing selects a region/edge before local balancing selects an instance. DNS routing depends on caches/TTLs and existing connections. Anycast advertises one address from multiple locations, with network routes choosing entry; it does not guarantee geographic proximity or application health. Global/local layers need coordinated health and ownership policy.

Latency routing must respect residency and write ownership. Read failover can expose replication lag; write failover needs old-owner fencing and replication-position checks. Traffic switching alone cannot resolve split brain. Measure recovery including client/DNS caches and reconnect storms, not merely controller command time.

7. Consistent hashing, virtual nodes and hot keys

With hash(key) mod N, changing N remaps many keys. A consistent ring places node tokens and keys in one hash space; ownership goes to the first clockwise token. Adding a node takes only the intervals it claims, leaving other owners unchanged. This is a placement property, not proof that bytes migrated successfully.

Virtual nodes assign multiple tokens per physical node to reduce interval skew and represent weights. More tokens do not spread one hot key: its requests still use the policy’s owner. Hot reads can use replicas/caches; hot writes need invariant-compatible splitting/aggregation. Balanced key counts do not ensure balanced bytes or request costs.

Not all sharding is a ring. Redis Cluster uses 16,384 assigned hash slots; other systems may use directories or rendezvous hashing. Name the chosen mechanism rather than calling all sharding consistent hashing. Every mechanism still needs membership/routing versions and missing-owner policies.

8. Routing changed, but where is the data?

Rebuildable caches experience misses and cold-start pressure when ownership changes; bound warming, coalesce requests and protect the origin. Durable storage needs snapshots, write catch-up and versioned/fenced cutover; verify durability/rollback before removing old copies. Routing to an empty new node can appear to lose data still on the old node.

Replica placement must separate failure domains when tolerating rack/zone loss. The first ring owner does not automatically choose safe replicas; define replication, read/write semantics and suitable membership agreement. During partitions, a balancer timeout is insufficient evidence to allow another storage writer concurrently.

10. Operations and long-term decisions

Track per-upstream rates, active work, queue waits, latency, retries, connection errors, ejections and admission rejection. Aggregate latency can hide a bad tenant/shard; group by bounded dimensions such as region/route/cluster, not request-ID metric labels. Trace hops to distinguish proxy waits from server execution.

The balancer itself needs scaling and resilience: validated/canary configuration, certificate rotation, connection/buffer limits and rollback. Client-side balancing avoids a network hop but spreads policy/configuration across client versions. Managed balancing reduces local operations but requires quota, cost and feature understanding.

11. Interview drills and worked answers

Why can round robin create slow nodes with even request counts?

Requests differ in duration/CPU/memory and nodes differ in capacity. Long jobs build queues despite equal counts. Measure outstanding work, waits and durations, then test weighted/least-outstanding/P2C policies rather than promising a universal winner.

Do virtual nodes fix a hot key?

No: they divide key intervals, not one key. Hot keys need read caches/replicas or correctly designed write partitioning/aggregation. Additional nodes do not increase that key’s capacity if it still has one owner.

Does HTTP/2 make least connections an ideal metric?

Multiplexed streams make connection counts less representative. One connection may carry hundreds of active requests while another is idle. Use request/work metrics where L7 exposes them; L4 must account for its visibility limits and upstream multiplexing skew.

Exercise: adding D to an A/B/C ring may move which keys?

With old tokens preserved, only keys in D’s claimed intervals move to D; keys not moving to D keep their old owner. Roughly one quarter is an expectation under balanced placement with enough keys/tokens, not an exact fraction for every sample.

If an owner times out, should all writes move to its replica?

Not based only on a timeout. The old owner may still be live behind a partition; new write ownership needs agreement, fencing and replication semantics. Balancing routes traffic; it is not consensus or a transaction coordinator.

How would you deploy 100,000 streams without a reconnect storm?

Drain small batches with spare capacity and jittered/backoff reconnects, using application event resumption where supported. Set controlled connection-age/migration policies, watch connection/authentication load and avoid closing all nodes together. Both SSE and WebSockets require connection lifecycle management.

Open questions: explain the underlying mechanisms

Attempt an answer before reading, then change an assumption and reconsider the conclusion. Answers retain units and failure boundaries; the preceding sections provide diagrams and models.

What decision boundary distinguishes L 4 from L 7 load balancing?

L 4 routing primarily uses transport or network connections and visible metadata rather than HTTP paths or authenticated application identities. L 7 proxies understand applicable application fields, enabling host/path routing, request-aware policies and per-request observation. TLS handling, proxy chains and multiplexing change visibility and failure behavior.

L 4 can suit transport workloads, while L 7 adds flexibility with parsing, buffering, certificate and operational costs. Neither implies universal performance or security. With HTTP/2, balanced connection counts may hide stream skew. Use meaningful readiness, bounded draining and reconnect controls rather than treating a listening port as full service health.

How do consistent hashing and virtual nodes handle ownership changes?

A ring maps keys to positions and selects owners by a successor rule. Membership changes affect some intervals instead of broadly remapping keys as a changed modulo can. Virtual nodes distribute physical ownership over more positions, reducing variance across many keys and allowing weights. Placement alone does not define membership agreement, epochs or migration.

One hot key can still bottleneck its owner. Migrations need snapshots, catch-up, routing epochs and an appropriate fencing or dual-path contract, with verification and rollback. A cache may refill lost entries, while durable state must preserve acknowledged writes. Measure bytes and work per shard rather than key counts alone.

When are sticky sessions reasonable for long-lived workloads?

Affinity can reduce routing or local-state costs, and a WebSocket connection naturally remains attached during its lifetime. Failure or redeployment still requires reconnect and recovery; stickiness is neither durability nor high availability. Session state held only in node memory needs an explicit loss policy or appropriate shared/durable authority.

Assess heavy-user skew, fairness, draining and regional placement. Routing cookies are not authentication. Document or actor ownership may require routing by resource identity and epoch rather than user affinity; failover needs fencing and recovery. A sticky cookie does not replace a state-ownership protocol.
