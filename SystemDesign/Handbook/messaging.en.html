1. Async changes architecture and user experience

Messaging separates work creation from execution and completion. Clients may receive “accepted” before email delivery, image resizing or read-model updates. Distinguish persisted intent, publication, processing and side-effect completion: broker acknowledgement does not prove a payment provider charged.

Queues/logs absorb bursts within disk, retention and drain limits; they do not create free capacity. Sustained arrival above processing rate grows the backlog until resources or retention run out. A simple synchronous call may fit better when the caller needs the result immediately without replay or fan-out.

2. Queue versus log: ask about semantics, not product names

Queue · Distribute work

  • A logical job may be redelivered when acknowledgement is lost.
  • Visibility/acknowledgement deadlines and retries depend on the broker.

Log · Independent read progress

  • Groups keep separate offsets; replay still needs side-effect controls.
  • Retention/compaction determines what remains available for replay.

A command requests work; an event records a fact. A queue commonly distributes work to competing consumers and removes acknowledged deliveries. A log retains records for independent subscription/group progress and replay within retention. This distinguishes usage models, not every product’s capabilities.

Broker FIFO, delivery order and completion order differ. Prefetch, parallel workers, retries and requeueing can change effect order. If Cancel must follow Create, design per-key sequencing or consumer-side version/state-machine validation.

3. Partitions, keys and classic consumer groups

In a classic group, a partition is assigned to one member in a generation. Other groups maintain their own assignments/offsets, letting one event feed billing projections, analytics and notifications. Consumers beyond the partition count sit idle; internal worker pools can add concurrency but must preserve ordering and progress.

Keys commonly identify the aggregate needing order, such as an order ID. A shared key preserves log append order under current routing, not arbitrary business causality across producers. Producer sequencing, retry configuration, versions and changes to partition count can affect the required order.

4. Rebalances and holes in parallel processing

Group reassignment does not automatically stop a stale thread calling an external API. Stop admission, drain/cancel as appropriate and avoid commits after losing authority. Resource-side idempotency or fencing protects against stale workers still executing.

If offset 0 is unfinished while 1 and 2 are complete, committing 3 may skip 0 after a crash. Advance the next offset only through the contiguous durable prefix. An offset tracks partition progress; projection correctness and external effects remain separate responsibilities.

5. Acknowledgement placement determines loss or repetition

Acknowledging progress before the effect can lose work if a crash occurs between them. Applying the effect first permits redelivery but can duplicate it. A delivery guarantee needs a defined producer–broker–destination boundary.

Idempotency requires more than checking an event ID before work. The check and effect need an appropriate transaction/conditional-write contract; concurrent workers may both otherwise see an unseen event. Dedup retention must cover the promised replay/redelivery horizon.

6. Exactly-once has a scope

Kafka transactions can combine output records and consumer offsets within Kafka, with suitable committed-read configuration. Producer idempotence addresses certain producer-retry duplicates, not independent business requests expressing the same intent. Define APIs, transaction boundaries and isolation before claiming exactly-once.

A separate database/provider needs sink cooperation: effect-and-progress transactions, unique receipts, conditional updates or provider idempotency keys. Some connectors/sinks provide their own protocols. Kafka alone neither proves these guarantees nor makes every external exactly-once arrangement impossible.

7. Transactional outbox closes the dual-write gap

Saving an order and publishing its event are two writes to different systems. A crash after saving may omit publication. An order and outbox in one local transaction either both exist or both roll back. A relay/poller/CDC process then publishes committed outbox records using stable event IDs.

A relay can publish successfully and crash before marking publication, so consumers still need duplicate handling. Marking first reintroduces a loss window. Observe outbox age, retries, poison rows and retention, and preserve aggregate order where required instead of assuming more relays are safe.

8. Trace an event from commit to effect

Select each path to distinguish publication acknowledgement from effect completion. This example uses an internal projection, not an external charge pretending to share its transaction.

Order, outbox and an idempotent projection

Component map; the complete ordered request paths are explained below.

Commit and publish

  1. Store the order and outbox event in one transaction.
  2. Commit is confirmed; the API acknowledges the order without promising completed projections.
  3. The relay reads the committed event.
  4. Publish a stable event ID and await the broker acknowledgement contract.
  5. The broker acknowledges; the relay may record its publication checkpoint.

Effect and acknowledgement

  1. Deliver the event without considering its effect complete.
  2. A transaction saves the inbox ID and projection change; errors roll back both.
  3. Commit the receipt and effect.
  4. Acknowledge/commit progress after the durable effect under the contract.

Crash after effect

  1. An earlier acknowledgement was lost; redeliver the same event ID.
  2. The unique inbox receipt identifies an already committed logical event.
  3. Return the processed outcome without repeating the projection change.
  4. Acknowledge again; this boundary has absorbed the duplicate.
Order API
Receive the order intent and request ID; acknowledge the persisted business state.
Orders + outbox
One local transaction stores the order and stable event.
Relay / CDC
Read committed outbox records; republish the same event ID when outcome is unknown.
Event broker
Persist under the durability/retention contract and distribute to subscriptions/groups.
Projection worker
The consumer may receive duplicates and needs transactional effect/dedup.
Projection + inbox
Commit the receipt and projection update together; acknowledge progress afterwards.

9. Design retries, DLQs and ordering together

Where does a failed message go?

  1. Classify the failure

    Transient, invalid or unknown outcome?

  2. Retry within a budget

    Backoff, attempt cap and deadline.

  3. Park and investigate

    DLQ, ownership and diagnostic context.

  4. Redrive with controls

    Fix the cause, retain IDs and throttle.

Retry/redrive must preserve idempotency and ordering; do not remove records merely to clear a dashboard.

Transient failures need bounded retries, backoff, jitter and deadlines. Invalid schemas and deterministic bugs do not heal through infinite retries. A DLQ needs IDs, aggregate/version, errors, attempt counts and first/last times, with ownership, alerts, inspection and controlled redrive.

Moving a record to a retry topic/DLQ can let later records for its key overtake it. Strict ordering may require parking the aggregate, per-key retry lanes or state machines rejecting versions without predecessors. A DLQ is not a free solution to partition blocking.

10. Capacity, lag and recovery time

For rates λ and μ in events/s, backlog B drains only when μ>λ; under stable rates its drain time is approximately B/(μ−λ). With B=600,000, λ=2,000/s and μ=3,000/s, draining takes 600 seconds. Include replay/backfill, retries and event fan-out in the load.

Lag count helps capacity planning while event age/oldest-unprocessed age better tracks freshness under changing traffic. Observe both alongside processing latency and partition/key skew. Bound prefetch, in-flight work and memory. Visibility extension/heartbeats help long jobs but do not replace idempotency after lease expiry or pauses.

11. Sagas use local commits and compensation

Orchestration records workflow state and chooses the next step; choreography distributes reactions across events. Both need durable state, correlation, timeouts, idempotency and failure ownership. Choose for complexity, observability and ownership, not a claim that coordinators are always bad or events always loosely coupled.

Reserve → charge → ship can fail at each step. Releasing inventory or refunding is a new, fallible transaction; a shipped parcel cannot be rolled back by deleting a row. Represent pending, compensating and manual-review states rather than treating every timeout as cancellation.

12. Events are APIs; event sourcing is a separate decision

An envelope may carry an event ID, type/version, aggregate ID/version, occurrence time and correlation/causation IDs. Distinguish event time from processing time and define late-event handling. Test semantic as well as schema compatibility; a registry cannot detect a changed amount unit behind an unchanged field name.

Event-driven does not imply event sourcing. Event sourcing makes event history authoritative and reconstructs projections through replay, requiring evolution, snapshots, side-effect controls and sensitive-data handling. An outbox emitting events from database state can leave that database authoritative.

13. Operate through contracts and measurements

Assign owners for topics, schemas, retention, DLQs and redrive, and identify consumers before changes. Measure publication/commit latency, outbox age, consumer age, duplicates, failed compensation and replay headroom. Use low-cardinality alerts and controlled trace/log context for event IDs and sensitive data.

Inject faults at database-commit/publication, lost broker ACK, effect-commit/consumer-ACK, stale-worker ownership and old-event redrive after schema changes. Restoring a broker or completing replay is insufficient; verify projections and business invariants after recovery.

14. Questions with worked reasoning

A charge timed out: should you resend the event?

The outcome is unknown. Retain the logical payment intent ID, use the provider’s idempotency contract within its horizon, query status where supported and reconcile. Database event deduplication alone cannot prevent duplicate external charges.

Why might growing from 4 to 20 consumers not increase throughput?

Check partitions, hot keys and sink limits. Classic assignment has one member per partition; more members do not split a hot aggregate. Optimize handlers or use per-key concurrency while preserving contiguous progress and ordering. Measure before changing partition counts and key routing.

Why can an atomic outbox still produce duplicates?

Atomicity covers local state and outbox. A relay can publish and crash before checkpointing, then republish. Consumers need stable IDs and transactional dedup/idempotent operations, with retention covering the replay contract.

Does a DLQ preserve one order’s event order?

Not automatically. Parking version 2 while processing version 3 can produce invalid effects. Use aggregate parking, ordered retry lanes or version validation while preventing one broken order from stalling unrelated keys.

How long to drain 600,000 events at 3,000/s capacity and 2,000/s arrivals?

About 600 seconds under stable rates and comparable event costs. Failures or hot keys may reduce effective μ; if μ≤λ, it will not drain. Observe event age and recovery headroom rather than queue count alone.

When should you avoid adding Kafka or a queue?

When a synchronous path meets latency, load and failure requirements and callers need immediate results. Async adds intermediate states, replay, duplicates, schema/retention and operations. Introduce it when isolation, subscriptions or deferred work justify those costs.
