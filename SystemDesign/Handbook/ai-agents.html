Agents & Tool Use: vòng lặp, quyền và durable execution

Chọn workflow hay agent, thiết kế tools có contract, quản approval/budget/context và khôi phục external effects đúng cách. Có trace runtime, mô phỏng lost-response recovery và worksheet input-token growth.

Một task được thực thi có kiểm soát

  1. Scope task

    Principal, data/action scope và outcome criteria.

  2. Propose

    Model chọn next action với bounded context.

  3. Validate / admit

    Schema, auth, budget, preconditions và approval.

  4. Execute / record

    Stable intent, external receipt và durable observation.

  5. Continue / stop

    Verify outcome, detect loops, escalate hoặc reconcile.

Đừng gộp model proposal, authorization, approval và committed effect thành một trạng thái “tool success”.

  • Agent autonomy là cách chọn control flow; quyền và business constraints vẫn do code/runtime/resource server enforce.
  • Bắt đầu bằng bounded workflow khi phù hợp; thêm model-directed steps theo measured task needs, không vì tên kiến trúc.
  • Tool proposals và outputs là dữ liệu chưa đáng tin; schema-valid không có nghĩa authorized hoặc correct.
  • Durable checkpoint không atomically commit external API; stable intent và sink receipts/reconciliation xử lý crash window.
  • Budget/cancellation dừng future work, không tự undo effects đã commit hoặc xóa cost đã phát sinh.
  • Context growth, prompt caching, external memory và lossy summaries có assumptions/quality trade-offs khác nhau.

1. Workflow hay agent: chọn theo control flow và evidence

Workflow

  • Code chọn sequence, branches và allowed transitions.
  • Dễ kiểm contract hơn khi task structure rõ.

Bounded agent

  • Model đề xuất next action trong allowed space.
  • Cần trajectory evals, budgets và recovery.

Hybrid

  • Agentic exploration trong deterministic product boundaries.
  • Ví dụ research linh hoạt, refund theo policy code.

Workflow dùng code quyết định những bước và branches đã biết; model có thể classify, extract hoặc draft ở vài nodes. Agent cho model chọn next action/tool/subtask trong một phạm vi runtime cho phép. Đây là spectrum có thể phối hợp: workflow support ticket có một agentic research step rồi quay lại deterministic approval/payment rules. “Có nhiều model calls” không tự làm hệ thống thành autonomous agent.

So sánh với single-call/retrieval/workflow baseline trên task quality, reliability, latency/cost và operational complexity. Chọn autonomy khi dynamic search/planning mang lại lợi ích đo được; tasks known-step thường dễ test và bound bằng workflow hơn. Agent không đảm bảo giải được arbitrary task, và workflow cũng có thể lỗi, unbounded retries hoặc unsafe permissions nếu code sai.

2. Vòng lặp runtime và completion contract

Từ proposal tới verified observation

  1. Build context

    Goal, current evidence, schemas và limits.

  2. Model proposal

    Text hoặc tool name/arguments.

  3. Validate / reserve

    Auth, preconditions, budget và approval.

  4. Execute / observe

    Bound result, record receipt/error và update state.

Tool output được đưa lại context như data, không phải authority mới.

Một vòng điển hình gồm assemble context → model proposal → validate/admit → tool execution → observe/record → next turn hoặc stop. ReAct là một pattern kết hợp reasoning và actions, không phải mọi agent buộc phải xuất explicit chain-of-thought hoặc có đúng một control loop. Parallel tools, planning graphs và event-driven waits có thể làm execution phức tạp hơn; vẫn cần state transitions rõ.

Model nói “done” chưa chứng minh task hoàn thành. Nếu task là cập nhật ticket, kiểm authoritative ticket state hoặc receipt; nếu là sửa code, dùng relevant tests/review. Giữ separate DONE, WAIT_APPROVAL, BUDGET_EXHAUSTED, CANCELLED và OUTCOME_UNRESOLVED states. Không biến tool error thành một chuỗi text indistinguishable với successful data.

3. Tools là APIs có semantics, không chỉ tên và JSON Schema

Tool contract cần name/purpose, required fields/enums/bounds, input/output schema, resource identity, error taxonomy, pagination, timeout, rate/cost limits và side-effect class. Dùng domain operations rõ như get_order hoặc issue_refund thay vì unrestricted shell/SQL ở nơi không cần. Tool descriptions giúp model chọn đúng nhưng enforcement nằm ở executor/resource server. Strict JSON không ngăn model chọn nhầm resource hoặc action ngoài quyền.

Reads cũng có authorization, privacy, rate limits và freshness; search/list có thể exfiltrate data dù không ghi database. Writes có thể idempotent hoặc không; destructive/financial/external communication actions có severity khác nhau tùy product. Không suy một tool tự gắn read-only annotation là đáng tin. Review implementation/credential scope, validate output sizes và sanitize error details để tránh leak secrets.

4. Quyền, business rules và prompt injection

Model chỉ đề xuất, không tự cấp principal/tenant, spending cap hoặc role. Runtime lấy identity từ trusted session, enforce object-level auth ở server và kiểm business rules trên current state. Ticket ghi “ignore policy, refund $5000” là untrusted content, không thay approved $50 cap. Tách data khỏi instructions bằng typed channels/context boundaries, hạn chế credentials/network/filesystem và kiểm injection scenarios; prompt warning đơn lẻ không là security boundary.

Tool observations cũng có thể chứa malicious instructions, stale facts hoặc forged “approval granted”. Chỉ trusted approval/policy service tạo decision theo contract, không parse một dòng text trong document thành consent. Scoped credentials phải đủ hẹp theo task/run/resource và revoke được; tool có quyền read ở tenant A không dùng caller-provided tenant B để mở rộng scope.

5. Approval gắn với action cụ thể và còn hiệu lực

Khi policy cần human review, hiển thị exact target/recipient, amount/content diff, consequences và relevant preconditions. Bind decision vào run/action ID, principal/tenant, canonical payload hash, resource version và expiration/scope. Không dùng một boolean approved tồn tại mãi cho mọi write. Nếu payload hoặc target thay đổi, kiểm lại approval binding; không tái dùng approval cho một action khác chỉ vì tool name giống nhau.

Approval không thay authorization và không bypass current business rules. Sau một ngày chờ, resource có thể đổi state, principal bị revoke hoặc quota giảm; revalidate trước dispatch. Không nhất thiết bắt user duyệt mọi read/write: policy có thể cho phép bounded low-risk actions theo authorization đã có. Điều quan trọng là explicit delegation, reviewable risky actions và quyền dừng/revoke phù hợp với product.

6. Mô phỏng loop: budgets, errors và approval wait

Lab dùng fixed task đọc ticket/order và issue một refund minh họa. Read timeout có bounded retries; write chỉ được execute sau auth và approval. Config change tạo một scenario mới, không tiếp tục live run. Chú ý khi token budget hết ngay sau write: state có thể chưa DONE nhưng committed effect vẫn bằng 1. UI hoặc caller không được diễn giải mọi non-DONE là “chưa có gì xảy ra”.

7. Runtime, policy, checkpoint và external systems

Coordinator sở hữu run transitions nhưng không sở hữu atomic transaction của external tool. Policy/executor kiểm capability và effect contract; checkpoints giữ resumable evidence; resource server giữ authoritative outcome. Một graph có mũi tên giữa các node không tự làm các writes atomic. Xem recovery trace để thấy response có thể mất giữa sink commit và local checkpoint.

Model đề xuất, runtime kiểm soát execution

Sơ đồ các component; các luồng request được giải thích đầy đủ theo thứ tự bên dưới.

Theo dõi read, write approval, lost-response recovery, context recall và cancellation. Các boundaries giữ quyền, durable intent và external effects tách biệt với model output.

Một read có authorization

  1. Bind task/principal và allowed tool/data scope.
  2. Build context có provenance và bounded tool descriptions.
  3. Validate structured proposal, không lấy lời model làm auth.
  4. Issue scoped credentials và enforce timeout/output bounds.
  5. Query permitted rows/resources, giữ explicit freshness metadata.
  6. Return observation là data, không được nâng thành instructions.

Intent và approval trước effect

  1. Check tool args, business cap và current resource version.
  2. Persist intent/key/payload hash trước dispatch.
  3. Present exact action nếu policy cần human decision.
  4. Verify decision binding, freshness và current authorization.
  5. Dispatch authorized, approved intent không mutate payload.
  6. Sink atomically commit effect và receipt theo key/hash.

Response mất sau external commit

  1. Response có thể mất trước local receipt checkpoint.
  2. New worker resume durable unresolved intent, giữ identity.
  3. Lookup hoặc retry cùng intent theo sink contract.
  4. Existing receipt trả prior result, không tạo effect mới.
  5. Verify result và record evidence; unsupported lookup cần reconcile.

Recall và context compaction

  1. Retrieve authorized relevant facts; không tải mọi run history.
  2. Return bounded snippets, provenance/version và uncertainty.
  3. Keep critical approvals/intent/results ngoài lossy summaries.
  4. Assemble current context theo token/data policy.

Cancel không rollback external commit

  1. Mark stop requested, revoke further admission theo policy.
  2. Persist cancellation/fencing generation và in-flight identities.
  3. Stop undispatched work; cancel request không chứng minh remote abort.
  4. Reconcile in-flight receipts, không tạo blind replacement action.
  5. Record committed prior effect hoặc unresolved outcome cần owner.

8. Durable execution và crash window của side effects

Tách intent, effect và receipt

  1. Persist intent

    Stable action ID và exact payload hash.

  2. Dispatch

    Validate current auth/approval/preconditions.

  3. External commit

    Effect và sink receipt atomic nếu supported.

  4. Record / reconcile

    Lookup/replay receipt thay tạo action mới.

Crash có thể xảy ra giữa mọi hai bước; recovery cần hiểu boundary đã qua.

Persist task/config versions, current step, pending intents, approval state, effect receipts và completion evidence. Durable write cần thực sự hoàn tất theo chosen store contract trước dispatch nếu đó là recovery invariant; async checkpoint có crash-loss window. Khi worker resume, deterministic orchestration/replay và version compatibility phải được kiểm. In-memory checkpoint mất khi process restart không phải durable storage.

External API có thể commit rồi response mất trước checkpoint. Stable intent ID/payload hash persist trước dispatch giúp recovery lookup/retry cùng logical action. Sink cần atomic dedup/receipt theo contract và retention đủ dài; local key không có tác dụng nếu sink bỏ qua. Nếu external API không hỗ trợ, dùng business unique key, reconciliation hoặc manual review/compensation phù hợp; không hứa universal exactly-once bằng cách checkpoint sau mỗi tool.

9. Mô phỏng response mất, dedup và cancellation

Tắt durable intent nhưng giữ sink dedup: recovery tạo key mới, sink xem là request khác và có thể tạo effect thứ hai. Giữ key nhưng tắt sink dedup cũng có thể duplicate. Khi cancel sau commit, stop future dispatch nhưng reconcile prior receipt; cancellation không refund/undo tự động. Unknown outcome cần explicit owner/status, không suy “timeout = failed” hoặc blind retry bằng key khác.

10. Budgets, loop detection và concurrent admission

Bound model turns, tokens, wall time, tool requests, external spending và resource concurrency. Reserve trước admission, reconcile measured usage/receipts sau completion và giữ uncertain exposure nếu response chưa rõ. Với parallel tools/child runs, central atomic budget hoặc partitioned quotas phải tránh hai workers cùng tiêu phần budget cuối. Một counter chỉ kiểm sau tool call không ngăn overspend đã xảy ra.

Detect repeated failing (tool, normalized args, relevant state) và max consecutive errors; nhưng cùng args không luôn là loop vô ích, ví dụ bounded polling khi job state đang thay đổi. Dùng progress/state signals, backoff/jitter, error taxonomy và cancellation. Retry read timeout không đồng nghĩa retry arbitrary write; auth/validation failure thường không tự hết khi gọi lại y hệt. Escalation cần preserve partial results và unresolved effects.

11. Working context, summaries, run state và long-term memory

Working context

  • Input mà model thấy ở turn hiện tại.
  • Có token limit và context-selection trade-offs.

Durable run state

  • Intent IDs, receipts, approvals và versions.
  • Code kiểm invariants; không dựa vào summary text.

Retrieved memory

  • Facts/preferences/episodes được scope theo task.
  • Kiểm freshness, ACL và provenance.

Model call chỉ dùng information available trong selected context/state của serving interface. Conversation APIs có thể giữ server-side state; không vì vậy mà model tự nhớ mọi run/tenant. Runtime phải biết context assembly contract, truncation/compaction và exact evidence được gửi. Working context là bounded prompt; summaries là lossy representations; durable run state giữ authoritative action/approval/effect data; long-term memory là external records được retrieve theo scope.

Không để approval, spending ledger hoặc receipt ID chỉ tồn tại trong summary do model viết. Khi compress, giữ provenance, unresolved questions, resource versions và facts cần kiểm lại. Memory retrieval có ACL, freshness, deletion/retention và poisoning risks; user preference cũ không tự override instruction/authorization hiện tại. Compaction tốt về token count vẫn có thể giảm task quality.

12. Context growth và total token accounting

Nếu mỗi turn gửi full prior history, base context b và mỗi completed turn thêm h tokens, n turns có input tổng n×b+h×n(n−1)/2. Đây là quadratic growth dưới giả định history tăng đều và không compact, không là universal cost law cho mọi agent. Bounded windows, summaries, retrieval và provider-managed context thay arithmetic; caching có thể giảm billed input cost mà logical context vẫn lớn.

Output/tool/model-reasoning usage, retries, workers và storage cũng có costs; latency không suy trực tiếp từ total input tokens vì prefill/cache/decode/hardware khác nhau. So sánh cost per successful task với cùng success definition và distribution; tiết kiệm tokens nhưng tăng wrong actions hoặc failures chưa là product win. Lab chỉ tính input inventory với explicit parameters.

13. MCP: interoperability, capability và trust boundary

MCP là protocol client–host–server dùng JSON-RPC để trao đổi capabilities/context. Host quản clients, mỗi client kết nối một server; servers có thể expose tools, resources và prompts theo negotiated capabilities. Standard transports trong specification đã đối chiếu gồm stdio cho subprocess và Streamable HTTP cho remote/local service; implementation/version support cần kiểm trước integration. MCP không buộc mọi app có cùng approval UI hoặc mọi tool dùng cùng side-effect semantics.

Local stdio server là code được launch trên machine theo sandbox/OS permissions; remote server nhận data/credentials theo delegation được cấu hình. Cả tool descriptions/outputs và endpoint metadata cần trust review. Enforce minimal scope, audience/token validation, transport/auth policy, safe endpoint discovery và server identity; không dùng token passthrough tùy tiện. Capability negotiation không tự là end-user consent hoặc authorization cho mọi resource.

14. Routing, workers và evaluator loops có overhead

Routing chọn specialized model/tool path; parallel independent workers có thể giảm critical path; orchestrator–workers cho phép decomposition động; evaluator–optimizer lặp theo rubric/tests rõ. Những patterns này có thể là workflows hoặc bounded agents tùy quyền chọn control flow. Không mặc định thêm agents luôn tăng accuracy: shared blind spots, handoff loss và inconsistent state có thể làm tệ hơn.

Child tasks cần narrow scope, result schema/provenance, bounded budget và cancellation propagation. Shared writes cần ownership/version/fencing thay để workers sửa cùng resource không điều phối. Parent phải kiểm kết quả và authoritative effects, không coi worker nói “done” là proof. Measure duplication of context, synthesis cost, tail latency và failure recovery trước chọn multi-agent topology.

15. Đánh giá outcome, trajectory và attempted violations

Sandbox fixtures cần expected final resource state, allowed/forbidden effects, recovery scenarios, latency/cost bounds và adversarial observations. Đánh giá task success, effect correctness, authorization/preconditions, duplicate count, blocked attempts, tool errors và escalation appropriateness. Trajectory không bắt buộc giống một golden sequence duy nhất nếu có nhiều valid plans; enforce invariants và useful progress thay vì phạt mọi alternative hợp lệ.

Thử crash trước/giữa/sau external commit, response loss, stale approval, credential revocation, conflicting writes và cancellation. Report cost per successful task cùng overall failure/severity, không chỉ cost trên subset thành công. Bắt đầu shadow/read-only hoặc bounded actions theo risk, widen autonomy sau evidence gates; rollout cần stop/reconcile/rollback phù hợp với effects không đảo ngược.

16. Run, approval và action receipt APIs minh họa

Các internal contracts minh họa tách run execution khỏi external effect. Không triển khai live agent trong bài. Idempotency key được scope theo tenant/principal/action và payload binding; server-side policy không lấy approved=true từ request body làm trust decision.

POST /internal/agent-runs

Tạo scoped run có budget và task version.

{ taskId, taskRevision, idempotencyKey, toolProfile, budgetProfile }
202 { runId, state: "QUEUED", manifestHash }

    POST /internal/agent-runs/{runId}/decisions

    Record exact action decision sau authenticated review.

    { actionId, expectedPayloadHash, expectedResourceVersion, decision: "approve | reject" }
    200 { decisionId, boundActionId, expiresAt, principalScope }
    • Current auth/preconditions vẫn được kiểm trước execution.

    GET /internal/action-receipts/{actionId}

    Lookup authoritative receipt hoặc explicit unknown.

    200 { actionId, payloadHash, state: "COMMITTED | REJECTED | UNKNOWN", externalReceiptRef?, observedAt }
    • UNKNOWN không tự được retry bằng một action ID mới.

    POST /internal/agent-runs/{runId}/cancel

    Dừng new admission và reconcile in-flight actions.

    { expectedRunRevision, reasonCode }
    202 { runId, state: "CANCEL_REQUESTED", unresolvedActionIds }
    • Cancel requested không chứng minh remote tool đã abort hoặc committed effect bị undo.

    17. Luyện giải thích thiết kế agent runtime

    Agent đọc ticket và có thể refund: thiết kế guardrails thế nào?

    Tách deterministic classification/fetch/draft workflow và bounded dynamic step khi cần. Server enforce principal/order ownership, eligibility, amount caps, current version và approval policy. Persist exact intent; dùng supported sink receipts và reconcile unknown outcome. Sandbox/evaluate outcome, trajectory, injection và cost trước widen autonomy.

    Tool timeout sau refund: gọi lại được không?

    Timeout không chứng minh refund chưa commit. Lookup/retry cùng persisted identity theo actual sink contract, kiểm payload binding và retention. Nếu không có reliable dedup/lookup, giữ unresolved và reconcile/manual review; không tạo key mới cho cùng logical action.

    Checkpoint sau mỗi tool có đủ exactly-once không?

    Không vì sink commit và local checkpoint là hai boundaries. Response/crash gap có thể replay effect. Cần durable intent trước dispatch và effect-side dedup/lookup hoặc design phù hợp; phải nói rõ guarantee scope thay universal exactly-once.

    Approval hôm qua còn dùng được khi amount đổi không?

    Không tự được. Verify exact payload/principal/target/version, scope và expiry; changed action cần policy/review phù hợp. Authorization và business rules hiện tại vẫn độc lập, kể cả approval còn khớp.

    Budget hết sau write có nghĩa task không tác động gì không?

    Không. Dừng future turns không undo prior effect. Return partial state/receipt và unresolved actions; final narrative chưa tạo được không làm committed action biến mất. Reconcile rồi escalate theo policy.

    Vì sao chi phí tăng khi thêm vài turns?

    Nếu resend growing full history, input tổng có quadratic term; nhưng cần trace turns, context sizes, outputs, retries, cache rates và tool costs trước kết luận. Bounded context/caching đổi arithmetic và billing; kiểm quality khi compact.

    MCP server nói read-only thì có thể tin không?

    Annotation/description không thay implementation/credential review. Read có thể disclosure, endpoint hoặc tool outputs có malicious content. Enforce auth/scope, validate server/transport và data boundaries; interoperability không tạo trust.

    Cancel một run đang gọi external tool thì sao?

    Persist stop state, block future admission và propagate cancellation khi supported. Không suy request cancel = remote abort. Reconcile in-flight receipts, fence stale workers khi resource hỗ trợ và báo prior effects/unknowns. Compensation là action riêng theo policy, không automatic undo.
