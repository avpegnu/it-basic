Designing a News Feed: from one post to millions of timelines

Follow publishing, fan-out, reading and authorization; calculate write amplification, design a hybrid feed and handle retries, deletion and privacy changes.

How does a post reach a feed?

  1. Commit the post

    Post and outbox in one transaction.

  2. Distribute candidates

    Workers split work by recipient.

  3. Read the timeline

    Stable cursors and push/pull candidates.

  4. Filter, rank and hydrate

    Visibility, deletion and current payloads.

This is a typical push path; a hybrid may pull posts from high-fan-out authors at read time. Feed responses still enforce current visibility and state.

  • The post store is authoritative; a timeline holds rebuildable candidate IDs.
  • Push buys faster reads with write amplification; pull moves work to the moment a user opens the feed.
  • A cache hit does not replace authorization. Hydration must remove deleted, blocked or no-longer-visible posts.
  • A queue alone cannot provide end-to-end exactly-once behavior: the outbox, idempotent consumers and data invariants must work together.

1. Start with the right mental model

The post is authoritative content

  • Store the post, author and current state.
  • A timeline commonly keeps candidate IDs for hydration at read time.

The timeline is a read model

  • Push/pull produces a recipient’s candidate set.
  • Candidate presence does not prove the user still has permission to view it.

A News Feed is a personalized list of posts. A post is created once but can become a candidate for many readers. Source data and read-serving data therefore grow at different rates: storing one post does not imply one write across the system.

Think of a timeline as a library index: each entry points to a post. Content, media and access rules have separate authoritative owners. A damaged timeline cache can be rebuilt from posts and the follow graph; restarting Redis must not destroy original content.

Begin with a chronological feed, then extend it to ranking. A chronological feed needs stable ordering; a ranked feed also needs candidate generation, feature lookup, scoring, deduplication and diversity policies. They can share a write path while having different pagination semantics.

2. Scope, invariants and SLOs

This teaching design supports text posts with image/video references, follow/unfollow, home feeds and deletion. Media uploads use expiring URLs separately; publishing accepts media IDs only after ownership and readiness checks. Comments, ads, full-text search and recommender training are outside the initial scope.

Assume a 300 ms server-side p99 feed API target, 99.9% monthly read availability and under five seconds p99 from post commit to active-follower timeline delivery under normal load. These are design and measurement targets, not guarantees created by a diagram. The latency budget must cover candidate fetching, hydration, authorization and response serialization.

InvariantDesign consequence

Freshness and correctness are different

A follower seeing a post a few seconds late may satisfy the SLO. A blocked reader seeing a post because of a stale cache is a correctness failure; eventual consistency is not a blanket justification for both.

3. Estimate with explicit assumptions

Use 30 million DAU, 0.5 posts per user per day and ten feed reads per user per day. Assume 200 followers eligible for push per author on average. This is deliberately simplified: follower counts are highly skewed, and active authors may have more followers. A more accurate model sums posts_i × eligible_followers_i across authors rather than always multiplying two averages.

Each timeline keeps 500 candidate IDs at an assumed 16 bytes of payload per entry, covering a post ID and small sort metadata. The 240 GB below is payload only. Redis object overhead, allocation, indexes, replication, fragmentation, failover headroom and post contents are excluded; benchmark the actual representation before sizing a cluster.

At 300 million DAU with unchanged assumptions, these totals grow tenfold: about 1,736 post writes/s, 34,722 feed reads/s, assumed peak reads of 104,167/s, 347,222 full-push inserts/s and 2.4 TB of timeline payload. This is linear scaling of fixed inputs, not proof of Redis memory sufficiency or unchanged p99; remeasure skew, batching, hot shards and overhead.

4. API contracts and client retries

Endpoints derive user identity from the authenticated session/token; they do not trust client-supplied author_id or recipient_id. A cursor is a signed opaque token bound to the user, filters, feed session and expiration. Error bodies use stable codes so clients can distinguish retrying from correcting a request. Do not blindly retry every 4xx.

POST /v1/posts

Publish a post after checking quotas, audience and media ownership.

Idempotency-Key: 58f...
{ "text": "Hello", "mediaIds": ["m_1"], "audience": "followers" }
201 Created
{ "postId": "p_123", "createdAt": "2026-10-21T08:00:00Z", "state": "published" }
  • Replaying the same key and payload returns the same postId. Reusing a key with a different payload returns 409; invalid content returns 422, and unready media has a distinct domain error.
  • Persist the response and fingerprint in the transaction or a recoverable state machine. Set the idempotency record TTL to the documented retry window; expired keys no longer protect old replays.

GET /v1/feed?limit=20&cursor=...

Read a feed page; cap the limit on the server and avoid offsets for large changing datasets.

200 OK
{ "items": [{ "postId": "p_123", "author": { "id": "u_1" }, "text": "Hello" }],
  "nextCursor": "opaque-signed-token", "feedSessionId": "fs_17", "degraded": false }
  • Return authorized hydrated content, not just IDs. When candidates are filtered, refill within a bounded work budget; do not query indefinitely to fill a page.
  • An expired cursor returns an explicit error so the client can start a new session. Omit nextCursor when candidates are exhausted; define separate semantics for a temporarily empty page with slow sources.

PUT /v1/me/following/{authorId}

Create an idempotent follow relation; private accounts may instead create a pending request.

204 No Content
  • Backfill at most 100 recent posts in a separate post-commit job. Carry follow_version so an old job cannot corrupt a later unfollow/refollow cycle.

DELETE /v1/me/following/{authorId}

Remove a follow relation; feed reads must honor the new state while timeline cleanup is still running.

204 No Content
  • Repeated deletion still returns 204. Cleanup is not a security boundary; enforce access during hydration.

DELETE /v1/posts/{postId}

Only the owner or an authorized actor may delete; persist a tombstone before emitting cleanup events.

204 No Content
  • Define when deletion becomes effective, how post caches are invalidated and the TTL of media URLs. A CDN may retain old objects if only metadata is deleted.

5. Data model, indexes and partition keys

Design from access patterns: fetch a post by ID, recent posts by author, followers for fan-out and candidates by recipient. One database may suffice initially; the logical tables below do not require separate products or microservices.

Partitioning timelines by recipient_id keeps a timeline read on few shards. Publishing still writes across many shards, so bulk writes should group by shard with bounded concurrency. Partitioning posts by author_id helps pull recent posts; postId lookup needs routing encoded in the ID or an additional directory/index. Do not assume every access pattern is single-shard.

Entity / keyImportant fieldsAccess and invariant
posts(post_id)author_id, created_at, state, audience_version, text, media_idsLookup by postId; index (author_id, created_at DESC, post_id DESC) for author feeds.
follows(follower_id, followee_id)state, follow_version, created_atUnique relation; reverse index on followee_id to scan followers with a cursor.
timeline(recipient_id, post_id)author_id, sort_key, source_versionUnique recipient/post; index (recipient_id, sort_key DESC, post_id DESC); bounded retention.
outbox(event_id)aggregate_id, event_type, payload, created_at, delivered_atSame transaction as the post; the relay may publish duplicates, so consumers must deduplicate.
idempotency(user_id, key)fingerprint, state, post_id, response, expires_atUnique user/key; control concurrent retries with a constraint or lock.
feed_session(session_id)user_id, candidate_snapshot, ranking_version, expires_atOptional for stable ranked feeds; snapshot entries still require read-time authorization.

6. Architecture and request lifecycle

Separate durable publishing from work that grows with follower count. Publishing does not wait for every timeline insertion: otherwise one slow shard or a large account extends the whole request. Authors can see their own new posts through the author feed or a read overlay before fan-out finishes.

The publication trace chooses one execution order to show that client acknowledgement does not wait for fan-out. A relay may emit before or after the HTTP response reaches the client, provided it reads committed outbox entries. Durable post/outbox commit is required; HTTP response delivery is not a reliable trigger for recoverable work.

How does a post move through the system?

Component map; the complete ordered request paths are explained below.

Publish + push

  1. The client sends a post with an idempotency key; the API checks the actor and media.
  2. Write the post and outbox in one transaction and await the contractual durable commit.
  3. The database confirms commit; idempotent retries retain the same postId.
  4. Acknowledge publication with postId without waiting for all follower fan-out.
  5. The relay emits the event after commit; repeated publication preserves eventId.
  6. A worker consumes the post event and splits work into follower chunks.
  7. Read eligible followers; retain the cursor and required relationship versions.
  8. Upsert candidates by recipient/post, trim timelines and checkpoint.

Read + hydrate

  1. Request a feed using a cursor or create a new session.
  2. The feed service receives the user identity and deadline.
  3. Fetch candidate IDs by recipient with bounded overfetch.
  4. Batch hydrate posts while preserving candidate order.
  5. Remove deleted, blocked, unfollowed and disallowed-audience posts.
  6. Return authorized items and a signed cursor for the next page.

Hybrid / celebrity

  1. A reader opens the feed without waiting for celebrity-wide fan-out.
  2. The feed service loads the session push/pull source configuration.
  3. Read pushed candidates from ordinary authors.
  4. Pull a bounded number of recent posts from high-fan-out authors.
  5. Merge, deduplicate postId, hydrate and enforce permissions before ranking/returning.

Deletion / privacy

  1. The owner requests deletion or an audience change; the API checks authorization.
  2. Atomically persist a tombstone/audience version and outbox event.
  3. Emit a versioned invalidation event after commit to reject stale events.
  4. Workers clean up and invalidate caches; jobs may be replayed.
  5. Remove candidates to save work; read-time policy remains the authorization boundary.

7. Push, pull and hybrid: choose by cost

Fan-out on write pushes a post ID into follower timelines after publication. Reads are fast because candidates are prepared, but writes amplify and inactive followers still consume work. Fan-out on read pulls recent posts from followed authors and merges them; writes are cheaper, while read latency depends on source count, skew and batching.

A teaching rule compares posts/day × eligible followers × insertion cost with active follower reads/day × pull/merge cost. There is no universal celebrity threshold such as 10,000 followers. Frequent authors, inactive followers or overloaded shards may justify pulling earlier; profiling and SLOs determine the threshold.

A hybrid pushes ordinary authors and pulls large ones. During a mode switch, use mode_version and an overlap window to avoid gaps: allow both push and pull temporarily, deduplicate by postId, then retire the old source after a safe watermark. Instant switching without accounting for in-flight jobs can create missing or duplicated entries.

The added experiment examines one author and a hypothetical reader who follows them. Push inserts candidates for the chosen eligible follower count, rounded to an integer; pull adds no timeline candidate for this post and reads the author source on demand. Hybrid uses followers > threshold for the selected author; other pulled authors followed by the reader are a separate input. It does not simulate global follower distributions, privacy, ranking or cross-session mode migration.

For twenty million eligible followers, push adds twenty million timeline inserts, or 320 MB of ID payload at sixteen bytes/entry. An uncontended job using a full one-million-insert/s budget would have an ideal twenty-second drain, excluding queues/retries/I/O; this is not a freshness SLO forecast. A reader following three hundred authors pulls three hundred author sources under pure pull. Hybrid reads one timeline, eight other pulled authors and the selected author when pulled. Batching/caching means source counts are not directly RPC counts or milliseconds.

OptionBenefitCost / risk

8. Ranking, cursors and snapshots

For chronological feeds, use a keyset cursor (created_at, post_id), with post_id breaking timestamp ties. The next page selects keys below the cursor. An upper watermark fixed on the first page keeps new posts for a refresh rather than inserting them during scrolling. Timestamped IDs do not automatically provide global causal ordering under clock skew; define display semantics separately.

A ranked feed cannot rely only on the last timestamp when scores change between requests. One option stores a TTL-bound candidate/score snapshot per feed session; another uses a ranking_version, seed and bounded stability rules. Snapshots use memory but make ordering steadier; recalculation uses less state but requires explicit duplicate/gap semantics.

A useful pipeline is candidate retrieval → cheap eligibility filters → scoring → diversity/deduplication → final hydration/authorization → response. Scoring that requires text or features may need partial hydration earlier. Retain the final authorization check because state can change after a snapshot is created. Avoid N+1 queries: batch post and user-profile lookups and version feature caches appropriately.

A sort-key watermark does not freeze candidate membership. Late fan-out/backfill can insert an older post below a cursor already traversed, so that scrolling session may miss it. Promising a complete point-in-time snapshot requires membership snapshots or a suitable delivery/watermark barrier; a tuple cursor alone is insufficient. Snapshots must still recheck current deletion/authorization rather than freeze permissions with the list.

SELECT post_id, sort_key
FROM timeline
WHERE recipient_id = :reader
  AND (sort_key, post_id) < (:last_sort_key, :last_post_id)
  AND (sort_key, post_id) <= (:upper_sort_key, :upper_post_id)
ORDER BY sort_key DESC, post_id DESC
LIMIT :bounded_candidate_limit;

Illustrative subsequent chronological page with an upper tuple fixed from the first page. Tuple/index support depends on the database; verify the cursor before binding. The upper tuple bounds ordering, not membership snapshots or authorization.

9. Outbox, chunking and consumer idempotency

Writing a post and then failing to publish its event leaves it absent from timelines. Publishing before a post transaction rolls back creates references to nonexistent posts. A transactional outbox stores the post and publication intent together; a polling or CDC relay emits committed events. A crash after publishing but before marking delivery causes duplicates, so the outbox prevents a delivery gap without eliminating duplication.

Split followers into chunks, for example 1,000 recipients per job, but choose the size from measured latency and payload limits. A checkpoint records the author/post, chunk cursor, event version and status. Acknowledge the queue only after writes and checkpoints are sufficiently durable. A crash between writing and acknowledgement can cause replay; uniqueness or conditional upserts must make replay harmless.

Partitioning the event log by author_id preserves an author’s event order within one partition, but a hot author can still bottleneck it. Fan-out chunks can later be split by recipient shard after resolving post-version order. Preserve ordering where invariants require it, not across all messages globally. Tombstones/versions prevent a delayed create event from resurrecting a deleted post.

Retries use exponential backoff with jitter and a retry budget. Quarantine poison events with ownership, alerts and a replay tool after fixing the cause. A DLQ is not a wastebasket: it contains undelivered posts and needs a handling SLO. Track the age of the oldest event, not only message count.

10. Deletion, unfollow and privacy cannot rely on caches

From a candidate to content allowed to render

  1. Fetch candidate IDs

    Timeline or pull sources.

  2. Check state and permissions

    Deletion, blocks, audiences and follows.

  3. Rank and hydrate

    Use only currently eligible content.

Do not rely on fan-out cleanup or TTL to enforce privacy. The read path must enforce authorization using state fresh enough for the contract.

A timeline cache may retain invalid candidates; distinguish suggestion data from authorization data. During reads, post hydration checks tombstones and current audience, while policy checks blocks/follows through an authoritative source or a versioned/invalidation cache that meets the promised revocation window. If a private post’s authorization cannot be established, fail closed and return fewer items.

To apply deletion to reads beginning after its acknowledgement, every protected read path needs sufficiently current authority, such as a read barrier/version gate or authoritative tombstone/deny-set. Ordered invalidation rejects stale fills/events but is insufficient if it has not reached readers before acknowledgement.

Waiting for invalidation requires defined cache acknowledgements, stale-reader fencing and failure behavior, not merely emitting an event. One option consistently checks a deny-set on every protected read during replica/cache lag, without reusing stale cached “not deleted” results, then compacts after safe tombstone propagation. Account for latency/availability; metadata deletion cannot recall data already sent to clients.

Unfollowing need not make a public post inaccessible everywhere, but the home-feed behavior must be explicit: exclude that author’s candidates while a public profile may remain readable. For private accounts, follow/approval changes also change content access. Timeline cleanup and CDN object handling are separate tasks; long-lived signed URLs may still expose media after the API stops returning a post.

11. Failure modes and degradation

Design degradation per dependency. Do not send every failure to the database: a cache-cluster outage can otherwise overwhelm the durable source too. Bound concurrency and use request coalescing, priority warming and admission control to protect the origin.

12. Observability, testing and rollout

Measure rate, errors, duration and saturation separately for publishing and feed reads. Add commit-to-timeline freshness histograms, fan-out chunk retry rates, oldest-event age, shard-level cache hits/misses, hydration batch latency, candidate-filter reasons and empty-feed rates. A 200 response with a minutes-old timeline can still violate the user experience.

Link requestId, postId/eventId and fanoutJobId across asynchronous traces; avoid logging private text or access tokens. Do not use userId/postId as metric labels because cardinality explodes. Dashboards should distinguish global load from hot shards and include runbooks to reduce push, isolate poison backlog or roll back a ranking version.

Critical tests crash after database commit but before event publication, after timeline writes but before queue acknowledgement, deliver a delayed create after deletion, unfollow during backfill and paginate across equal timestamps. Shadow-read push/pull candidates before switching modes; roll out to small cohorts, measure gaps/duplicates and privacy regressions, then expand.

13. When scale or requirements grow

Multi-region operation needs explicit post/follow ownership and read-your-writes behavior. Writers may use a home region while posts/events replicate to read regions; session tokens can avoid replicas that have not observed a new post. Follow/unfollow conflict resolution needs intentional versions and semantics; wall-clock last-write-wins can be wrong under clock skew.

Separate retention policies: timeline candidates are short-lived, post storage follows product retention and deleted data has a separate removal process. Do not multiply post retention by follower count and call it post-store size; copying IDs and copying content have different costs. Media object storage and CDN egress typically need their own worksheet.

Advanced ranking adds a feature store, experiment assignment, model versions and feedback events. Impressions need event IDs for deduplication and a clear definition of display. Avoid future-data leakage in offline evaluation; assess fairness, content policy and feedback loops alongside click-through rate. Optimizing one engagement metric can reduce feed quality or diversity.

14. Interview drills and worked answers

Answer before opening the explanation. State the invariant, assumptions and conditions that would change your choice; naming a technology alone does not justify a design.

Why not copy the full post into every timeline?

Copying IDs keeps fan-out payloads small and simplifies edits/deletion through one authoritative content source. Reads then need batched hydration and a separate content cache. Content snapshots may fit audit or offline use cases, but require explicit version and revocation semantics.

What happens when a celebrity with 20 million followers posts?

Full push creates 20 million timeline inserts for one post before retries. Prefer pulling that author’s recent posts or pushing only active recipients; shard work, bound concurrency and merge/deduplicate on reads. Decide using posting rate, active follower reads and SLOs, not follower count alone.

If the queue supports exactly-once semantics, do we still need deduplication?

Yes. The guarantee may cover only transactions inside the broker. Writing a timeline in an external database, calling a policy service and acknowledging delivery are separate side effects. Consumers need idempotent writes or a supported transaction coupling offsets and outputs; otherwise crashes can still repeat work.

Why is a cursor preferable to an offset here?

Large offsets skip many rows, and inserts/deletions shift positions. A keyset cursor continues from a stable sort boundary; ranked feeds additionally need snapshots or ranking versions. Cursors do not solve changing privacy: items must still be reauthorized.

A deleted post reappears after a retry. What failed?

A delayed create may follow deletion, or the worker may blindly accept the last arriving event. Use monotonic versions/tombstones that reject stale events and check authoritative post state during hydration. Cleaning a timeline once does not stop in-flight jobs from reinserting a candidate.

Exercise: average followers increase from 200 to 800. What grows fourfold?

With 15 million posts/day and 100% push, timeline inserts rise from about 34,722/s to 138,889/s. Post writes remain about 174/s; timeline payload remains 240 GB if each of 30 million users still keeps 500 IDs. Backlog and trimming churn may increase even when retention bounds cache size.

When ranking times out, can we immediately return an old cached response?

Only if cached items still pass current authorization and meet freshness semantics. A simpler option is a bounded chronological fallback over valid candidates. Personalized response caches need identity/policy-version keys and must never be accidentally shared between users.

Would you begin with a monolith or microservices?

A modular service with a database and queue/outbox can be enough. Establish logical boundaries first: publishing, graph/policy, candidate retrieval, hydration and workers. Split deployments when ownership, scaling or isolation yields measurable benefits; premature network hops complicate consistency and operations.
