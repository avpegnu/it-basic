1. Separate interactions while preserving product boundaries

Inline completion

  • Respect short windows, snapshots and cancellation.
  • Bound output and preserve editor responsiveness.

Chat / agent

  • Support repository understanding and explicit tasks.
  • Bound execution and preserve artifact evidence.

Shared constraints

  • Enforce privacy, permissions, exclusions and routes.
  • Evaluate correctness and security alongside economics.

Inline suggestions bind to cursors, chat explains or proposes changes, and agents perform scoped work. Inline timing follows developer interaction, while longer tasks need bounded reviewable execution. Latency goals do not excuse security or universal usefulness assumptions.

Define supported editors/languages, scope, endpoints, execution and degradation. Ordinary editing must survive model outages. Data/training/retention policies need real enforcement rather than interface promises.

2. Plan requests separately from useful suggestions

Assume 100000 active developers, 150 admitted completions/day after debounce and a 4× peak. Each completion uses 1500 input/24 output tokens; six chat/agent turns use 7800 input/200 output each. These are hypothetical workload inputs rather than throughput or prices.

Fifteen million daily completions average 173.61 QPS and peak at 694.44. High input volume does not alone establish cost/compute dominance; caching, lengths, batching, hardware and cancellation evidence matter.

        5. Handle versions, supersession and late replies

        Debouncing trades fewer calls for delay. Invalidate proposals and request cancellation on edits, while checking response epochs, versions, ranges and context preconditions. The same file path does not establish snapshot validity.

        Respect client version, position and range contracts. Cancellation may not stop work; validity gates are separate correctness controls. Test undo/redo, tabs, branches and unsaved overlays.

Debounce reduces admissions and cancellation is only partly acknowledged, so snapshot guards remain necessary. This fixture establishes no measured compute savings, billing or universal usefulness deadline.

        7. Build bounded infilling context

        Infilling conditions on surrounding code under a supported profile; token formats differ. Choose necessary local context and relevant definitions/tests under actual budgets. More context can be stale, irrelevant or hostile, and local extraction is not cost-free.

        Count required content and formatting/headroom. Oversized required input needs deliberate reframing rather than budget bypass. Enforce exclusions before exposure; later server checks cannot undo prior transmission.

This does not rank README quality above tests or establish optimal packing. Account for actual tokenization, templates and output headroom before allocating input budget.

        8. Retrieve repository context with commits and unsaved overlays

        Version repository indexes by commits, hashes and processing profiles. Symbols can help while language services lag or parse incomplete code. Evaluate lexical, symbol and semantic retrieval rather than expecting one method to cover all cases.

        Open buffers can be newer than indexed commits. Apply overlays and staleness rules, with deliberate handling for paths, generated files, branches and exclusions. Retrieval similarity does not authorize arbitrary repository content.

        9. Scope prefix and suggestion caches

        Prefix reuse needs compatible token/model settings, isolation and residency. Layout and profile changes affect reuse, and stickiness only helps available healthy caches. Similar code is not identical model state.

        Response caches bind snapshots, context, settings, scope and policy. Retyping may reuse eligible suggestions without bypassing current validity. Measure actual input/cache/output usage rather than inferring universal cost dominance.

        10. Scope and bound agentic edits

        An edit loop with evidence

        1. Inspect / plan

          Define goals, bases, scope and checks.

        2. Propose edits

          Propose concrete isolated changes.

        3. Verify

          Record checks and artifact/environment identities.

        4. Review / apply

          Apply under current conditions and authority.

        Outcomes depend on exact artifacts and behavior, not completion claims.

        Bind goals and workspace snapshots, scope tools/paths and preserve user changes. Stop on meaningful completion or declared limits/conflicts. Green tests achieved by removing coverage or altering expectations do not establish success.

        Control evaluation oracles and review behavior, tests and scope. Repository content cannot grant credentials or external authority. Respect delegated local autonomy and concrete risk-based review rather than inventing prompts for every authorized change.

        11. Isolate generated code and repository scripts

        Builds, tests and dependencies can execute arbitrary repository code. Choose appropriate isolation with secret, resource, filesystem and network controls. Containers with host privileges or secret mounts do not automatically establish isolation.

        Provide controlled dependency access where needed, with destination and supply-chain policies. Scope and minimize artifacts/logs. Return bounded useful failures instead of unending installs or retries.

        12. Bind test and review evidence to exact artifacts

        Record bases, patch identities, paths, checks, environments and required decisions. Artifact changes can invalidate evidence, requiring appropriate requalification rather than inherited green badges. Tests establish only exercised properties.

        Check current revisions at commit, preventing precheck/write races. Multi-file operations have client-specific transaction and recovery semantics. Preserve conflicts and user changes rather than forcing apparent success.

        13. Evaluate functions, repository tasks and pass@k

        Function tests, static checks, security review and repository tasks cover different scopes. Use authorized representative holdouts and controlled environments, addressing contamination, drift and flaky tests. Passing does not establish all requirements or security.

        Pass@k assesses success with multiple candidates under defined tests, not first-suggestion adoption. An estimator for n≥k samples and c passes is 1−C(n−c,k)/C(n,k); n=10,c=2,k=2 gives about 37.8%. Compare matched harnesses, sampling, budgets and uncertainty.

        14. Adoption and retention are signals rather than truth

        Track the proposal funnel with explicit denominators. Adoption is selected by timing, length, interface and difficulty; retained characters do not prove correctness or productivity. Combine behavioral signals with outcomes, review burden, security and research.

        Experiments need suitable units, duration and guardrails, accounting for developer/repository dependence. Do not optimize trivial adoption at the expense of useful quality. Pseudonymous telemetry still carries privacy implications.

        15. Propagate exclusions and data policies

        Apply exclusions across extraction, indexing, generation, caches and diagnostics. Git ignore rules are not automatically privacy controls, and paths/pasted data need deliberate treatment. Detectors have errors; minimize exposure and privileges.

        Qualify actual endpoint, retention and training contracts. Outcome telemetry can avoid raw code while still containing sensitive metadata. Propagate policy changes to caches and queued work; later filtering cannot undo prior uploads.

        16. Degrade without blocking normal editing

        Under pressure, shorten output, omit optional context, use qualified alternatives or pause suggestions while preserving expectations. Longer tasks can queue, checkpoint or stop with evidence. Degradation choices remain task-dependent.

        Prioritize current work fairly, with measured cancellation and warmup behavior. Balance stickiness with load escape. Product service levels should include editor responsiveness and task quality as well as endpoint availability.

        17. Model artifacts, telemetry and release controls

        Manifests bind artifacts, environments, checks, scope, models and decisions. Telemetry binds requests, generations, timings, usage and adoption under privacy policy; absent raw code does not make metadata public.

        Qualify model, prompt, context and index releases across correctness, security, load and controlled rollout. Preserve compatible rollback profiles and minimized diagnostic evidence for actual end-to-end failures.

        18. Practice Coding Assistant decisions

        How would you keep completions useful under peak load?

        Measure useful valid timing, bound work and qualify model/cache choices with quality and privacy. Degrade deliberately without fixed speedup promises.

        Can R1 be shown after R3 because it is the same file?

        Not without matching current snapshots and preconditions. Cancellation does not erase responses; enforce validity across editing changes.

        What if required surrounding code exceeds budget?

        Do not bypass limits. Count overhead, reframe or decline under policy while preserving exclusions.

        What if the workspace changes after tests pass?

        Bind evidence and check current state at commit, handling conflicts and requalification without blind overwrites.

        Does higher acceptance prove a better model?

        No: selection, timing, length and task mix can shift. Combine adoption with correctness, security and controlled outcome evidence.

        Does sticky routing always preserve prefix reuse?

        No: eviction, profiles, exact tokens and load affect reuse. Monitor compatibility and capacity with escape paths.

        Is running tests on a laptop sufficient isolation?

        No: scripts can access host capabilities. Use suitable isolation and reviewed credentials, resources and networking.

        Does high pass@k establish good first suggestions?

        No: multi-candidate success differs from first-suggestion behavior and depends on sampling and tests. Evaluate product behavior separately.
