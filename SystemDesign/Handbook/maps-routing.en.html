1. Three cooperating systems rather than one large database

Rendering plane

  • Versioned tiles, bounded viewports and client/CDN caches.

Routing plane

  • Legal directed-graph paths, turn costs and coherent traffic weights.

Traffic plane

  • GPS sequences → matching → segment aggregates with freshness/privacy.

Mapping combines rendering, route computation and a location-to-traffic pipeline. Rendering distributes cached assets; routing computes over road graphs; traffic processes noisy, delayed streams. Each path needs different SLOs and scaling controls. This lesson covers driving maps, alternatives, ETA and rerouting; places/reviews, imagery and transit are outside scope. It is an educational architecture rather than a claim about any company’s private system.

Define route p99 by region/mode, completed tile-load rates, traffic freshness and ETA error by trip class. A percentage target is incomplete without ground truth, prediction horizon, trip populations and tail errors. Expose offline/stale estimates. Location uploads need explicit opt-in policies; not every feature requires long-lived raw traces.

2. Size each plane separately

Assume a billion daily users, five navigation minutes per user, one GPS fix/second, batches of fifteen fixes and one route request/day. This yields 300 billion fixes/day, about 3.47 million/second on average; twenty billion upload requests/day, about 231 thousand/second. Average route traffic is about 11.6 thousand/second, or 57.9 thousand at a fivefold peak. Batching reduces request overhead, not fix counts. Separately account for time-zone peaks, incomplete final batches, retries, reroutes and fan-out.

An XYZ pyramid has 4^z tiles at zoom z. Levels zero through twenty-one contain (4^22 − 1)/3 = 5,864,062,014,805 tiles. Assuming a constant decimal 25 KB each gives roughly 146.6 PB. This dense budget is not mandatory storage: sparse regions, shared empty tiles, content-addressed assets and on-demand generation change it. Measure CDN bytes, origin misses, device work, routing memory/CPU, streaming and privacy/storage rather than assuming one plane always dominates.

3. APIs expose versions, freshness and bounds

Separate quotas and concurrency pools for tiles, routes and location uploads so ingestion spikes cannot starve navigation. Route inputs include mode, avoidance, departure time and explicit units/coordinate order. Geocoding needs disambiguation, while snapping considers direction and access profiles. Responses carry route IDs, request generations, graph/profile/traffic versions and estimate times. Endpoints alone are insufficient cache keys when modes, departure times or avoidance differ.

GET /tiles/{mapVersion}/{source}/{z}/{x}/{y}.pbf

Immutable versioned/schema-aware vector tile with explicit authorization and cache headers.

200 binary tile + ETag + Cache-Control
  • Styles, glyphs and sprites need compatible versions too.

POST /v1/routes

Find legal routes by departure time/profile. Coordinates below use [longitude,latitude].

{ "origin": [105.84,21.03], "destination": [105.90,21.05], "mode": "car", "departAt": "2026-10-22T08:00:00Z", "requestGeneration": 7 }
200 { routeId, alternatives:[{polyline,distanceM,etaSec}], graphVersion, trafficVersion, estimatedAt, requestGeneration }
  • Clients discard stale response generations; this is the teaching platform API.

POST /v1/location-batches

Bounded opt-in batch with stable fix sequences for retries/deduplication.

{ sessionId, batchId, fixes:[{seq,observedAt,lon,lat,accuracyM,speedMps,headingDeg}] }
202 { batchId, acceptedAt, boundary: "replicated-log" }
  • The ACK proves the stated boundary rather than completed matching or traffic publication.

GET /v1/routes/{routeId}/updates?after={cursor}

Poll/SSE for ETA changes or alternatives with cursor/reconnection contracts.

200 { cursor, estimatedAt, trafficVersion, etaSec, alternative?, stale }

    4. Trace rendering, routes and traffic independently

    Tiles can be long-cached under immutable versions; route weights change quickly; raw GPS needs short retention. Manifests bind compatible versions rather than requiring every component to share an identical version number. A route request pins graph/profile and coherent weights for its calculation. Active routes may retain older generations under explicit policies after publication. The traces separate synchronous requests from asynchronous processing.

    Three paths with different rates of change

    Component map; the complete ordered request paths are explained below.

    Tiles use immutable map versions; routes use graph versions and weight snapshots; location processing preserves session locality before segment aggregation.

    Load the map

    1. The client selects a published manifest and pins a generation.
    2. Fetch viewport tiles with matching source/schema/version.
    3. Misses fetch published objects under explicit cache policies.
    4. The renderer combines compatible geometry/styles/glyphs/sprites.

    Compute a traffic-aware route

    1. Send endpoints, departure time, mode/profile and request generation.
    2. Apply separate route quotas and regional selection.
    3. Snap endpoints and request compatible graph/profile generations.
    4. Read coherent weights with closure constraints and freshness.
    5. Return legal candidate paths, distances, durations and metadata.
    6. Apply only current request generations and expose ETA confidence/staleness.

    Turn GPS into traffic evidence

    1. Upload a batch with session/fix IDs, timestamps, accuracy and consent scope.
    2. Validate batch sizes, clock bounds and upload permissions.
    3. Reach the durable acceptance boundary before ACKs; retries preserve IDs.
    4. Preserve sequence locality and handle duplicates/out-of-order/gaps before matching.
    5. Aggregate matched segments by time/version with quality/freshness metadata.

    Publish a map generation

    1. Verify immutable objects, schemas and dependencies before manifest publication.
    2. Warm compatible graphs/hierarchies/profiles without mixing new graphs and old shortcuts.
    3. Matching and traffic weights use segment mappings for the correct graph version.
    4. Switch generations under explicit route/offline compatibility or refresh policies.

    5. Tile pyramids and viewport caches

    XYZ/Web Mercator uses 2^z tiles along each axis at zoom z, with x increasing eastward and y southward. It clips near ±85.0511° latitude and distorts area rather than flattening the entire sphere without distortion. Clients request viewport intersections plus budgeted overscan/prefetch, not an entire level. Small pans reuse keys, while immutable version changes separate them.

    The experiment uses a synthetic grid and local cache without fetching external map assets. Fixed payload size isolates pyramid growth from caching. Real clients need bounded eviction, cancellation during rapid pans, visible-tile priorities and coalescing. Private tiles require cache keys and authorization that prevent cross-tenant exposure.

    6. Raster and vector move costs between components

    Raster tiles contain rendered images; clients mostly compose them with styles/labels often baked in. Vector tiles provide geometry/attributes for styled rendering, enabling flexible restyling, rotation and labels at the cost of device GPU/CPU, fonts, glyphs, sprites and schema compatibility. Vector payloads are not invariably smaller: geometry density, zoom, styles and compression matter. Test weak devices, constrained bandwidth and complex labels.

    7. Legal paths need more than nearby nodes

    A road network is directed: one-way streets, access restrictions and travel modes determine valid edges. Intersection nodes and segment weights alone do not represent every turn restriction. Edge-expanded graphs or states containing incoming edges can model prohibited turns, U-turns and penalties. Endpoints inside segments need profile-aware snapping and positions along edges; the nearest intersection can yield incorrect or unnecessarily long routes.

    Dijkstra handles fixed nonnegative weights but can explore many nodes. A* adds a heuristic in the same units as the cost; straight-line distance divided by a valid maximum feasible speed lower-bounds travel time. The toy graph uses a consistent heuristic and stops when the goal is settled. Overestimates, unit mistakes or changing weights during a query can invalidate the correctness argument. A* does not universally explore fewer nodes under every graph/tie rule: compare costs before work.

    8. Preprocessing and customization are different steps

    Serve a traffic update

    1. Validate

      Validate segment mappings, units, timestamps and quality.

    2. Customize

      Prepare compatible weights/overlays outside requests.

    3. Check and publish

      Run correctness probes and atomically switch serving pointers.

    4. Observe

      Track route quality/freshness and roll back when necessary.

    Urgent closures need a separate path when customization lags; fallbacks must not reopen prohibited roads.

    Contraction Hierarchies add shortcuts that bypass some nodes while preserving the prepared graph/cost model’s shortest-path semantics. Classic CH depends on metrics, so old shortcuts do not automatically remain valid after weight changes. Customizable hierarchy and multi-level partition families separate topology preparation from metric customization, enabling faster updates under appropriate conditions. Millisecond or second runtimes must be measured for actual graphs, hardware and updates rather than inferred from algorithm names.

    A snapshot binds compatible topology, access profiles, closures, weights and customized data. Publish by generation, warm before traffic switches and retain rollback. Queries must not mix new graphs with old shortcuts or segment IDs. Cross-region routes need boundary/overlay protocols that preserve correctness rather than independently choosing two local paths and hoping they form a global optimum. Bidirectional searches also need valid termination bounds, not merely their first frontier intersection.

    9. Turn GPS sequences into segment evidence

    GPS contains measurement noise, sampling gaps and clock errors; the nearest road to one fix may be wrong. Map matching considers position sequences, accuracy, headings, time gaps and plausible paths between candidates. HMMs are one way to represent emission/transition likelihoods, but no algorithm guarantees correct matches under arbitrarily sparse or noisy observations. Low-quality inputs may justify withholding speeds rather than forcing wrong segment assignments.

    Before matching, partition by session or another sequence-locality mechanism, using bounded reordering and duplicate/gap policies. Raw ingestion does not yet know segments reliably; repartition by graph version, segment and time bucket after matching. Filter impossible jumps, parked devices and outliers without discarding all slow observations, which may reflect real congestion. Probe populations vary by device, vehicle and coverage; large counts do not prove representativeness.

    10. Historical, live and arrival-time predictions

    ETA is more than distance divided by speed limit. It combines time-of-week history, live evidence with age/quality, turn/intersection delays and correction models. A segment reached thirty-five minutes into a forty-minute trip needs expected conditions on arrival rather than only current speeds. Time-dependent routing requires coherent semantics; common algorithms rely on FIFO assumptions, so arbitrary changing edge functions do not automatically preserve Dijkstra correctness.

    The lab uses simple speed blending to show trust declining with age and sample count. It is not a forecasting model or calibrated uncertainty estimator. Blending speeds before converting to time also differs from averaging travel times. Evaluate ETA by horizon/region/mode, distinguish route-selection from prediction errors and avoid future-data leakage. Closures remain hard constraints: missing live data must not fall back to history and reopen prohibited roads.

    11. Batching adds delay; rerouting needs hysteresis

    Uploading fifteen fixes per full batch cuts request counts roughly fifteenfold, while the oldest fix waits almost fifteen seconds before network, queue and matching delays. Devices need bounded buffers, consent, stable retry IDs, backoff/jitter and battery/network-aware sampling. Batching is not free under every freshness target. Keep local navigation feedback separate from analytics uploads: clients can check deviations against active routes before servers receive new batches.

    Noise near parallel roads can create false deviations. Use accuracy, heading, multiple observations and matched progress, with a fast path for genuine changes. Server alternatives should clear absolute/relative benefits, cooldown and uncertainty criteria to avoid flapping between near-equal routes. Closures can force reroutes regardless of savings thresholds. Stale responses require request-generation guards.

    12. Versioned identities and offline packages

    Minimum records include directional/access-aware segments and turn mappings, immutable tiles, map manifests, timestamped traffic evidence, route snapshots and sequenced fixes. Segment IDs need not survive every rebuild; traffic processors need version mappings or processing against new graphs. Active routes retain graph/profile generations and refresh/expiry policies. Rendering and routing may differ in detail but must satisfy the product’s compatibility commitments.

    Offline packages need manifests, checksums, compatible tiles/styles/glyphs and routing subgraphs/profiles if offline routing is promised. Tiles alone do not enable offline pathfinding. Quotas, partial-download recovery and atomic activation matter, while trips beyond package boundaries may be unsupported. During outages, retain active routes and expose stale traffic; historical offline estimates lack real-time closure coverage without updates.

    13. Location privacy and failure drills

    Location traces can reveal homes or workplaces despite rotating session IDs. Trimming trip ends, aggregation, sufficient distinct-device thresholds and limited retention mitigate some risks without guaranteeing anonymity. Apply consent/access policies, encryption, auditing, minimization, deletion and documented replica/backup retention. Keep raw coordinates and trace IDs out of unbounded metric labels. Administrative tools and logs also need access controls.

    Drill tile-origin failures, traffic lag, broken map publication, new closures, regional overload and sparse/noisy probes. Track visible-tile latency, byte hits, route p99/no-route rates, ETA errors, probe-to-weight lag and version mismatches. Routing itself changes traffic: sending everyone down one side road can invalidate predictions. Alternative policies must account for feedback and legal/community constraints. Adaptive routing is not proof of citywide optimality without models and evidence.

    14. Questions about correctness and freshness

    Trace a user action to its data/version boundary, then introduce network failures or stale data there. CDN/Kafka/cache names alone do not establish route correctness without map-version and weight-snapshot semantics.

    Why not download every tile at a zoom?

    World tiles grow as 4^z while viewports intersect few of them. Fetch visible keys with budgeted overscan, reuse caches and cancel obsolete requests. Full-pyramid storage differs from viewport fetching; sparse generation and sharing can reduce storage.

    Are vectors always cheaper than rasters?

    No. Vectors support restyling and dynamic labels while moving decoding/layout/rendering and dependencies to clients. Costs depend on geometry, style, zoom and devices. Measure bytes, CPU/GPU, memory and latency.

    Can A* use distance as a travel-time heuristic?

    Convert units and establish a valid lower bound, such as distance divided by maximum feasible speed. The lab is consistent because edges cost at least a minute/km and traffic only increases costs. Real turns/profiles/time dependence need careful bounds and snapshots.

    Can traffic weights change during an active search?

    Fixed-weight correctness arguments do not automatically survive such changes. Pin coherent snapshots or use explicit time-dependent algorithms/protocols. Graphs, customized data, profiles and closures need compatible generations with urgent-closure handling.

    Can raw fixes simply be partitioned by segment?

    Reliable segments are not known before matching. Preserve session locality, handle duplicates/gaps/reordering, match sequences and then repartition by version/segment/time. Nearest-road matching of one noisy fix is insufficient.

    Are fifteen-fix batches free in freshness terms?

    No. Request overhead falls while early fixes wait almost a batch interval plus transport/processing. Separate local navigation from analytics, measure end-to-end lag and choose battery/freshness policies. A 202 ACK does not prove traffic publication.

    Should expired live speeds remove all constraints?

    No. Speed estimates may fall back, but closures, access and turn restrictions remain separate constraints. Expose stale/offline evidence limits; history does not establish current road availability.

    Do rotating IDs and aggregation guarantee anonymity?

    No. Trajectories and sparse regions can still permit linkage. Minimize retention, enforce access/consent/deletion, validate distinct-device thresholds and constrain logs. Privacy needs threat models and policies beyond naming k-anonymity.
