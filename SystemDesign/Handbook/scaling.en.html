Scaling systems: from one server to multiple regions

Scale by measured bottlenecks: stateless APIs, database indexes, caches, queues, replicas, shards and multiple regions, including migrations and failures.

Every scaling step needs a trigger and a way back

  1. Keep a simple baseline

    A request path you can measure.

  2. Remove a measured bottleneck

    Queries, indexes, CPU, I/O or skew.

  3. Separate suitable work

    Stateless services, read models and async work.

  4. Partition ownership safely

    Shards, regions and migration.

This is a decision path, not a sequence every application must follow. Add complexity when measurements or invariants require it.

  • Scaling preserves latency/correctness requirements as workloads change, not merely adding servers.
  • Find bottlenecks using rate, latency, saturation and skew before choosing a remedy.
  • Stateless APIs are easier to scale; state still lives in sessions, databases, queues and caches.
  • Every additional distribution boundary brings consistency, migration and operational costs.

1. Start with the smallest adequate system

A modular backend, one database and object storage can serve an early product well. Single-database transactions simplify invariants, deployments have fewer boundaries and requests are easier to debug. Keep module boundaries clear for future separation without paying distributed-system costs prematurely.

Establish a representative baseline with p50/p95/p99 latency, throughput, CPU, memory, disk/IO, pools and query plans. More API replicas do not fix a missing database index. Benchmark correctness and resource limits alongside performance, avoiding tiny datasets or unrealistically warm caches.

2. Bottlenecks and Amdahl’s Law

Suppose a request uses 20 ms of application CPU and waits 180 ms for the database. Doubling application CPU speed reduces total time from 200 to 190 ms, not 100 ms. Amdahl’s Law highlights the unchanged part limiting speedup; measure critical paths and query counts before changing languages or buying CPUs.

CPU saturation suggests parallelism or less computation; lock waits suggest contention/transaction scope; disk IO may need indexes, layouts or RAM; network fan-out needs batching and fewer hops. Signals interact: low application CPU does not imply spare capacity when workers wait on downstreams and pools are exhausted.

3. Vertical and horizontal scaling

Vertical · A larger node

  • Usually requires fewer ownership and deployment changes.
  • Machine limits and the node’s failure domain remain.

Horizontal · More nodes

  • Requires distributing work, balancing traffic and locating state.
  • More nodes do not automatically split one hot key or contended transaction.

Vertical scaling adds CPU/RAM/IO to one node, often requiring little code change and working well for suitable workloads. Hardware/cost limits remain, and high availability is separate. Horizontal scaling adds nodes and helps when work is independent and routable; shared bottlenecks such as one write owner still limit the cluster.

Make APIs stateless by moving shared sessions to storage or using tokens with explicit revocation semantics; put uploads in object storage and background work in identified queue jobs. Sticky sessions can ease an immediate problem, but node failure still loses local state and large sessions skew load.

Load balancers need health/readiness checks and draining during deployments. A node with cold caches/pools should not immediately receive its full share. Graceful shutdown stops admission, waits for in-flight work within a deadline and then terminates deliberately. Autoscaling metrics should reflect bottlenecks and queues beyond CPU.

4. Read scaling: indexes, replicas and caches

Improve access patterns/indexes first: select necessary columns, avoid N+1 calls, use keysets and inspect query plans. Read replicas distribute reads but can lag; a recent writer may need the primary or a replica that has reached a required version/position. Replicas do not replace primary transaction semantics or inherently accelerate a heavy query.

Caches reduce repeated reads when hit rates and reuse windows justify them. Define the authoritative owner, TTL, invalidation, negative caching and outage behavior. Single-flight and jittered TTLs avoid simultaneous misses; a cache outage must not send unbounded traffic to the database.

Cacheability depends on personalization and authorization. Content-hashed static assets fit CDNs; personalized queries require user/tenant and appropriate policy-version keys. Never cache a private response under a URL-only key shared by everyone.

5. Writes and asynchronous work

Queues separate acknowledgement latency from email, indexing, thumbnails or fan-out that can finish later. They do not increase downstream capacity by themselves: sustained arrivals above service rate cause unbounded backlog. Define durable acknowledgement and completion visibility; 202 accepted differs from a fully created resource under a 201 contract.

Database-write/event-publication dual writes create a gap; outbox/CDC can persist event intent with the transaction. Consumers still need idempotency for at-least-once delivery. Batching lowers overhead but adds waiting and batch failure/retry complexity; bound sizes by latency, payload and contention.

6. Shard when one owner no longer suffices

Choose shard keys from access patterns and load distribution. tenant_id colocates tenant data but large tenants become hot; hash(user_id) spreads users but cross-user queries fan out; time ranges simplify retention but heat the current range. Directories or virtual shards can move ownership without changing every ID.

Migration needs authoritative shard ownership, snapshot copying, change catch-up and versioned/fenced cutover. Unreconciled dual writes diverge when only one side succeeds. Use scoped shadow reads/checksums, rollback plans and backfill rates that protect production traffic.

Cross-shard transactions and joins become harder; colocate invariants where possible. If booking and payment have separate owners, a saga/state machine with compensation and reconciliation may fit, but is not equivalent to one atomic transaction. Explain user-visible intermediate states.

7. Multiple regions: choose ownership first

One write owner per scope

  • Identify which region/partition can commit a write.
  • Failover needs data validation and fencing of the old owner.

Multiple write locations

  • Define conflict resolution before deployment.
  • Local latency may improve; cross-region invariants still need an explicit mechanism.

Multiple regions can serve geographic latency, disaster recovery or residency. One write region with read regions is simpler than active-active but adds delay for distant writers; active-active requires per-data-type conflict and partition semantics. Mergeable content differs from inventory that cannot be oversold.

Failover is more than changing DNS: establish replica progress, fence the old writer against split brain, update routing and inspect cache/event lag. Test allowed data loss (RPO) and recovery time (RTO) through restore/failover drills. Backups in the primary failure domain do not cover every disaster.

8. An expansion path with exit criteria

These stages are workload-driven options, not mandatory levels. Some systems work for years on one strong database; others need early partitioning for residency or volume. User count is not the only trigger.

One modular backend

Simple transactions and ownership; measure queries, indexes and resources.

SLOs, load tests and tested backup restoration exist.

Stateless APIs + replicas/caches

Distribute reads/compute while retaining session and object ownership.

Tolerate an API-node loss and bound cache-miss storms.

Intentional queues and shards

Separate asynchronous latency and partition by invariants/access patterns.

Retries/replays, hot shards and backfills preserve correctness.

Regions and recovery

Route by ownership, replication positions and failover policy.

RPO/RTO are measured and failover fences old writers.

8a. Scale ownership and the change process

A small team may operate a shared backend efficiently. With many teams, release coordination, schema ownership or on-call load may bottleneck before CPU. Service separation helps when domains, APIs and accountable owners exist; synchronized deployment of everything merely creates a distributed monolith.

Treat migration as a feature: expand schemas first, rate-limit backfills, scope dual/shadow verification, cut over with rollback and contract old schemas only after clients migrate. Use user-impact and invariant guardrails. Adding a cluster is not complete scaling until data and traffic move safely.

9. Review your scaling decisions

Does increasing a database pool from 100 to 1,000 always improve throughput?

No. Databases have an effective concurrency limit; more connections can increase lock contention, memory and context switching. Measure pool wait, execution time and saturation, then choose protective pool sizes with deadlines/admission.

Why does a read replica not fix a hot write key?

Replicas reduce reads; concurrent writes to one key still contend on a writer/lock or partition owner. Change the access pattern, serialize per key, aggregate under suitable semantics or split data where invariants permit. Arbitrarily splitting balances/stock can violate correctness.

Exercise: four nodes handle 400/s each and one-node failure is required. Is 1,600/s safe?

No. Losing one node leaves a theoretical 1,200/s before recovery overhead and latency headroom. Operate below measured degraded capacity under the SLO; autoscaling does not guarantee immediate capacity.

Should every module become a microservice as user count grows?

Only where ownership, isolation or independent scaling benefits are clear. Service splits add network latency, versioning, tracing and distributed consistency. Replicate a modular monolith first and separate evidenced bottlenecks later.
