Building an AI chat assistant: from one conversation to production

Build in stages: durable conversations, streaming, context, retrieval, tools, files/code sandboxes, voice/vision, custom assistants, memory and inference operations. Traces and labs explain failures, access and costs. This is a teaching architecture for this product category.

A message needs more than a model call

  1. Receive intent and context

    User, conversation, budget and cancellation.

  2. Orchestrate with controls

    Policy, retrieval and tools when needed.

  3. Generate and stream

    Admission, inference and backpressure.

  4. Persist and observe outcomes

    Turn state, usage, evaluation and recovery.

This is an educational chat application architecture. Retrieval and tools are optional branches; the application must enforce execution and storage permissions.

  • The orchestrator owns turn lifecycle, context, tools and state; the model is one dependency within the product.
  • Emitted output is a side effect: retrying after the first token cannot be hidden like retrying an ordinary GET.
  • The context window is finite; retrieval and history must leave room for output and tool results.
  • The model proposes tool calls; code validates identity, schema, permissions and consequences before execution.

1. Define the product and this build’s boundaries

The application owns behavior

  • Identity, permissions, history, quotas, cancellation and turn state.
  • Do not grant resource access merely because the model generated a request.

The model generates bounded output

  • Token budgets, structured output and model capabilities.
  • Evaluate concrete tasks; smooth streaming does not prove answer correctness.

We are building an authenticated application that creates conversations, accepts messages, streams responses, cancels generations and reloads history. Later stages add authorized-document retrieval and narrowly scoped tools. Training a foundation model is out of scope; an adapter can connect either a self-hosted engine or an external service through one contract.

A turn is a logical user request and the steps needed to complete it: input validation, context assembly, one or more model/tool rounds, persistence and completion. A conversation ID does not uniquely identify a generation: retries, edits and regeneration need distinct turn/generation IDs so the UI does not merge different answers.

Assume an initial p95 TTFT target under two seconds for short prompts when not overloaded, quota-bound output limits and persisted partial state on interruption. Retrieval/tool questions need separate SLOs because external dependencies add latency. Long prompts should not be promised the same latency as short ones.

The expanded scope includes document uploads, isolated code execution, image/voice input, configured assistants and user-controlled memory. These are optional capabilities: enable them for a use case with compatible model capabilities and operating boundaries, rather than giving every chat request a fully privileged agent.

2. Build stages with verifiable exit criteria

Each stage adds a capability and a failure class. Do not jump to a many-service architecture before validating ownership, retries and persistence for a simple turn. The exit criteria below determine when expansion is justified.

These 12 stages are capability gates for the teaching design, not a company history or a mandate for 12 microservices. Preserve existing functions while adding limits/authority for new capabilities; production teams may implement admission or safety earlier than this teaching sequence.

01 · Durable conversations

Begin with conversation/message/turn storage, ownership checks and idempotency. Multiple models and a vector database are unnecessary to validate basic chat.

Problem pressure: Refreshes, retries and branch edits need an authority independent of model responses.

Architectural decision: Persist input before inference; bind turn keys/fingerprints, ownership and generation CAS.

Costs and trade-offs: Storage I/O and retention policy; closed sockets do not imply completion.

When is the next step needed?: Users need early output and recovery after disconnects.

Refreshing preserves messages; submit retries do not duplicate turns; other users cannot read the conversation.

3. Data model and generation state machine

Separate conversation metadata, messages and generations. An input message can exist even when generation fails; a partial answer is not completed merely because the socket closed. Conditional transitions prevent two workers from completing the same generation or writing completed after cancelled without an explicit precedence rule.

An example state machine is queued → running → completed; queued/running can also become cancelled, failed or interrupted. Interrupted means the original streaming contract could not be completed or resumed reliably. Store finish_reason separately: stop, length, tool_request and policy_stop have different UI and billing meanings.

4. APIs: submit, stream, cancel and resume

One retry-friendly option creates a turn with POST and streams the generation through GET. Native EventSource uses GET and does not offer arbitrary Authorization headers like fetch; use appropriately protected cookies or fetch streaming with headers and an SSE parser. Avoid long-lived query-string tokens because URLs can appear in logs.

POST /v1/conversations/{id}/turns

Validate ownership, quotas and input size; create a turn/generation and return the stream location.

Idempotency-Key: turn_...

  • 202 acknowledges the request, not instantaneous GPU termination. Observe generation status or a terminal event for the outcome.

    Reserve token/cost allowance, bound queue age/concurrency and settle actual/pending usage.
    Conversations
    Authority for messages, generations and state. Enforces tenant ownership on every access.
    Orchestrator
    Owns turns, context budgets, model/tool rounds, deadlines and cancellation. Model output never directly controls the database.
    Inference
    Normalizes streams, usage, errors and cancellation; routes to intentional model revisions.
    File store
    Owner/version/retention-bound objects/artifacts; publish parser output after verification.
    Tool gateway
    Validates schemas, permissions and side effects with audit, timeouts, idempotency and task-specific approval.
    Output policy
    Applies product policy to output/commands. Streaming requires pre-release or chunk-based checks because emitted text cannot be retracted.
    Code sandbox
    Untrusted code in bounded isolated runs; hosts enforce mounts, egress and resources.
    User memory
    Selected facts with provenance, versions, current policy and anti-resurrection tombstones.
    Retrieval / ACL
    Retrieves authorized versioned chunks and provenance. Documents are untrusted data, not system instructions.

    6. Streaming, backpressure and event ordering

    SSE fits predominantly server-to-client output, with separate HTTP submission and cancellation. WebSockets suit continuous bidirectional interaction such as realtime audio or rich event exchange, but require connection, heartbeat and protocol-state management. Choose the transport for the product interaction; WebSockets do not inherently accelerate inference.

    Network-byte boundaries do not match UTF-8 characters, tokens or SSE events. A parser buffers across reads, decodes incrementally and parses JSON only after an event is complete. The UI uses sequence numbers to ignore duplicates and detect gaps; matching conversation IDs do not justify joining a new generation onto old output.

    Bound slow-client buffers. If the browser cannot keep up, the system can reduce flush frequency within latency limits, retain a replay log or cancel under policy. Proxies must not buffer the whole response before delivery; heartbeats help detect dead connections but do not replace application deadlines.

    Choose disconnection semantics intentionally: immediate cancellation saves compute but loses progress on flaky networks; a grace period enables resumption but needs output/event retention and quotas. After replay-log expiry, clients retrieve an output/status snapshot or start a new generation rather than pretending exact resumption.

    The lab uses fixed timestamps: primary content at 1000/1300 ms, a mid-stream error at 1600 ms and a first-content deadline of 3000 ms. A heartbeat at 500 ms only establishes transport activity. Fallback before visible content can preserve a generation; after partial output, retain failure state or visibly restart with a new generation instead of silently joining two answers.

    7. The context window is a budget

    Assume a 32,768-token window. Reserving 4,096 output tokens, 2,000 system/schema tokens and 1,000 for tools/templates leaves 25,672 for history, user input and evidence. Retrieving 20 chunks of 2,000 tokens exceeds the budget on evidence alone; top-k and chunk size must respect actual token limits.

    Retain recent and task-relevant messages, summarize older history under a policy and store summary provenance/version. Summaries can be wrong or omit details; they do not replace server authorization or audit history. Exact values such as amounts/IDs belong in structured state rather than only prose compression.

    Rebudget every tool round because tool outputs can be large. Bound result sizes, truncate by schema or store artifacts and inject only relevant parts. Do not cut JSON arbitrarily inside an object; provide explicit truncation markers and metadata for authorized pagination.

    The worksheet uses a separate fixture: system 2,048, tools 1,024, margin 512, 512-token evidence chunks and atomic turn groups. It distinguishes dropping old groups, summarizing and selecting history. It models accounting/data selection rather than running a real summarizer/retriever or guaranteeing correct answers.

    8. Retrieval and access control

    Ingestion reads authorized documents, parses/chunks them, creates embeddings and stores document_id, version, tenant_id and ACL with each chunk. Retrieval can combine lexical and vector search followed by reranking. Evaluate against questions with known evidence: relevant-chunk recall, ranking and evidence sufficiency. Similarity scores are not probabilities of answer correctness.

    Apply tenant/ACL filters before chunks enter the prompt; filtering after the model has seen data is too late. Recheck permissions when opening citations, propagate deletion/revocation to indexes/caches and use versions to reject stale chunks. External documents are untrusted data: a PDF saying “ignore all instructions” must not become privileged instructions.

    RAG does not guarantee factual accuracy. Insufficient or conflicting evidence can require the assistant to state limits, ask a question or abstain. Citations should identify the passage supporting the claim; listing a related document does not prove grounding.

    9. Tool execution and prompt injection

    A tool call is a proposal; the application decides execution

    1. Receive a proposal

      Tool name and arguments from the model.

    2. Check rights and schema

      User scope, resources and input limits.

    3. Execute with controls

      Budgets, deadlines and confirmation where needed.

    4. Record the outcome

      Receipt, audit and turn state.

    Retrieved data and model output are untrusted input. Validate server-side before side effects, and keep audit trails and idempotency for retryable actions.

    A model tool call is a structured proposal, not authorization. The gateway checks tool allowlists, argument schemas, tenant identity and resource-level permissions. Models must not select an admin userId or arbitrary network endpoint. Secrets belong in scoped execution environments, not prompts or tool results.

    For writes, preview/approval depends on product impact; bind an idempotency key to the logical action to prevent duplicate effects. Limit tool rounds, total tokens, wall-clock duration and cost. A model → tool → model loop can run indefinitely even if each call is valid; whole-turn budgets prevent runaway work.

    Do not treat “do not leak data” instructions as authorization. Injection in documents/tool outputs may cause bad proposals; code outside the model must enforce permissions. Combine least privilege, egress controls, schema validation, audit and adversarial testing; a text filter cannot be promised to eliminate injection entirely.

    9a. File uploads and code sandboxes

    Lifecycle of an answer’s file

    1. Scoped upload

      fileId + owner, digest and size; bytes remain untrusted.

    2. Parse and index

      Bound the parser; publish versioned manifests only when complete.

    3. Bounded execution

      Run identities, allowed mounts, limits and denied egress.

    4. Expose then expire

      Check current downloads, bound results, revoke and clean up.

    Object bytes, parsed evidence, sandbox sessions and output artifacts have separate lifecycles and access controls.

    Separate upload from model calls: allocate owner/tenant-scoped file IDs, store untrusted objects and parse in workers with CPU/memory/time limits. Parsing, archive expansion and OCR can hang or amplify data; bound decoded size/pages and depth as well as upload size. Uploaded differs from parsed/indexed and ready for use.

    Treat model-generated code as untrusted. Run it in an isolated worker or sandbox appropriate to the threat model, with session/tenant-scoped temporary filesystems, read-only inputs, limits on processes/CPU/RAM/disk/output and hard deadlines. Do not mount Docker sockets, host homes, credential stores or production networks. Containers or microVMs provide one isolation layer; enforce egress policy, host hardening and resource controls outside the guest as well.

    The tool gateway supplies only files/artifacts authorized for the actor; code cannot change identity through model-selected paths or URLs. Deny network access by default or use a controlled proxy, checking destinations after DNS/redirects against SSRF. Collect bounded structured results and owner/expiry-bound artifact references instead of all stdout/raw binaries in the prompt. Downloads check current access; cleanup TTL does not replace revocation at access boundaries.

    For CSV analysis, a user uploads F, parsing produces schema/version V, the model proposes an aggregate and the gateway grants run R read access only to F@V. The sandbox returns a result table and chart artifact A. Recheck ownership/current policy before exposing A in an answer or download. Pure computation can rerun within quotas; external writes require their own effect identities/receipts like other tool actions.

    9b. Voice/vision: media has time and versions

    A clear voice pipeline is microphone → speech-to-text → orchestration/model → text-to-speech → playback. A native multimodal model can combine steps, but the application still owns access, recording consent/retention, cancellation and playback state. Images have artifact IDs/versions, MIME/dimension/decoded-size limits and metadata policies; OCR/captions are fallible evidence rather than server instructions.

    Use distinct session, turn, generation and media sequence/timestamp identities. Partial transcripts have revisions and are not necessarily final user intent. On barge-in, the client stops old playback, advances its playback epoch and sends cancellation; late old audio is discarded by epoch. The server stops/cleans up under its contract. Already played audio cannot be recalled, and cancellation acknowledgments do not prove all inference has stopped.

    As a hypothetical serial example after the user finishes speaking: endpoint detection 180 ms + final STT 120 + queue/model-first-content 350 + TTS-first-audio 100 + playback/jitter 60 = 810 ms. Streaming/overlap can shorten the critical path, but do not add/subtract independent p99s or ignore endpoint errors: cutting early loses speech while waiting too long harms responsiveness. Measure end-of-user-speech → first audible response and interruption-to-silence alongside accuracy, not only HTTP TTFT.

    One-way text can use SSE; bidirectional media needs a suitable choice such as WebRTC or a WebSocket protocol with its own framing/backpressure. WebRTC does not define assistant turn/cancel semantics or grant microphone access. Test codecs, jitter, reconnection and device lifecycles. Version model capabilities, preprocessing and retention policies together in redacted traces.

    9c. Custom assistants: sharing configuration grants no extra authority

    Definition/version

    • Reviewed templates, model constraints and tool schemas; pin a version per generation.
    • Keep secrets out of prompts/public configurations.

    Current authority

    • Check caller identities, resource ACLs and delegated grants at gateways.
    • Assistant sharing and data sharing are separate decisions.

    Store assistant definitions with owners, immutable versions, instruction templates, model capability constraints, allowed tool schemas, knowledge manifests and sharing policies. Pin a definition version per generation for reproducible debugging; draft edits must not change a running turn’s tool behavior. Rolling back configuration does not undo sent email or payments; effects retain separate ledgers/receipts.

    Distinguish permission to use an assistant from permission to read knowledge or execute actions. Shared assistants do not implicitly inherit creators’ credentials. Tools normally act as the caller; delegated service identities require narrow grants, auditable scopes and clear representation of whom actions serve. Public definitions mentioning files do not make those files public; retrieval checks current document ACLs and intentional sharing policies.

    Requests combine controls through an intersection of authority: actor policy ∩ assistant-allowed tools ∩ resource policy ∩ current approval. Model arguments cannot enlarge that set. Knowledge indexes retain document/version, assistant versions and ACL evidence. Permission revocation blocks serving/caches under the declared consistency contract, with asynchronous index cleanup afterward.

    9d. Memory: durable data needs inspection, correction and deletion

    Save and revoke provenance-tracked memory

    1. Propose with provenance

      Accept facts/preferences from suitable sources under user settings/sensitive-data policy.

    2. Commit under ownership

      Version records with scope, retention and correction/deletion controls.

    3. Bounded recall

      Check current policy/version, select relevant facts and rebudget context.

    4. Delete and fence

      Tombstones block old serving/replay; invalidate derived data and clean up.

    Memory does not replace authoritative business state or action permissions.

    Conversation history records what was said; a summary compresses a branch; retrieval indexes locate evidence; persistent memory stores selected facts/preferences for later sessions. These layers differ in provenance, access and retention. Do not turn every user statement into a true fact or let untrusted documents store instructions/secrets in memory.

    Memory records can include IDs, owner/tenant, types, values, source turns/artifacts, confidence or confirmation, versions, timestamps/expiry and active/deleted state. Users need understandable saving behavior and controls to inspect/correct/delete or disable recall/writes. Temporary conversations need explicit policies for disabling durable writes and, when promised, reads; browser private mode does not enforce server policy.

    For example, M9@v3 stores timezone Asia/Ho_Chi_Minh. Deletion commits tombstone v4 at the authority; memory reads/prompt assembly must block v3 under current policy/version. Vector/cache cleanup may lag but late index events must not resurrect M9. Old conversations can still contain their own text until separately deleted. Explain memory deletion versus history deletion without promising immediate disappearance from every log/backup.

    Memory must not disappear from cache identity: answers depend on memory/source versions and current access. Deletion needs invalidation or serving fences for derived caches and affected summaries; retain tombstones across replay horizons. Test account switches, shared devices, worker retries after deletion and update/delete races, rather than only remembering a name.

    9e. Safety and authority need boundaries before disclosure

    Separate input policy, evidence/tool authorization and output-release policy. Prompt instructions can guide behavior but do not enforce tenant ACLs or sandbox networks. Define fail-closed or safe degraded routes when policy/retrieval/permission services fail; paid tiers do not justify skipping safety or tenant checks. Redact telemetry while retaining trace IDs/versions for controlled debugging.

    Output can be checked as a complete answer, through windows/chunks or with bounded holdback. Full buffering raises TTFT/memory; chunk checks reduce latency but can miss context spanning boundaries. Once text/audio reaches users, warnings or UI removal cannot recall observed/recorded data. Sensitive data or high-impact actions need suitable pre-release/explicit confirmation plus current resource authority before effects.

    Tool results, web pages, OCR and retrieved documents are untrusted data. Separate instructions/data, validate structured tool proposals, safely render output instead of executing arbitrary HTML and check URLs/artifact downloads before exposure. Safety classifiers have false positives/negatives; evaluate locales/modalities and adversarial cases rather than treating one moderation box as complete protection.

    10. Capacity, routing and cost

    Assume 10,000 concurrent users with 20% waiting for/generating an answer: there are 2,000 active turns in the system, not automatically 10,000 inference streams. At a stable 20-second turn duration, Little’s Law suggests around 100 turns/s. These are worked assumptions; telemetry must establish real activity and duration.

    At 100 turns/s with 2,000 input and 400 output tokens on average, demand is 200,000 input tokens/s and 40,000 output tokens/s before tool rounds. Size inference with mixed-workload TTFT/TPOT benchmarks; size the API edge by connections, buffer memory and egress. Long-lived streams make HTTP requests/s alone insufficient.

    Route by capability, context limit, latency and cost budget. Fallback models need compatible tool/schema/policy evaluations; changing models mid-stream can change content and semantics. Cache responses only when identity, prompt/model/evidence versions and freshness allow it; never share private responses across users.

    10a. Admission: reserve first, settle later

    A turn passes admission and settlement

    1. Validate scope

      Actor, capability, input size and prompt/tokenizer versions.

    2. Reserve with identity

      Atomically reserve allowance for the current attempt/round; retries remain bounded.

    3. Queue with deadlines

      Bound queue age/concurrency; priority retains suitable fairness and capacity isolation.

    4. Settle from evidence

      Actual receipts or pending estimates; cancellation does not establish zero further usage.

    Quotas do not create GPU capacity; queues still need deadlines and workload fairness.

    Bound three resource classes: requests/connections, token/cost budgets and inference capacity. Low RPM with very long prompts can still consume prefill/KV; multi-round agents continue consuming resources after the first model call. Tenant/user quotas, maximum queue age, active generations and per-turn budgets need explicit rejection or degradation paths.

    Reserve against the serialized prompt, output cap and allowed rounds before enqueueing. If a quota window has 100,000 tokens available and turns A/B reserve 8,000/4,000, admission availability becomes 88,000. Confirmed usage 3,200 for A releases 4,800, leaving 92,800 while B still reserves 4,000. If B cancels with unresolved usage, retain its pending 4,000 and reconcile; immediate full release can enable repeated spending. This is illustrative token accounting, not provider pricing.

    Store reservation IDs, generation/attempt identities, budget windows and settlement states. Idempotent transitions must not charge the same usage receipt twice. Inference retries can create new usage within one turn; delayed callbacks must bind to the correct attempt. Missing usage needs estimated/unconfirmed states and expiry/reconciliation policies, rather than rewriting history as zero cost.

    11. Failure modes, evaluations and rollout

    Track turn success, TTFT, ITL, queue age, cancellation propagation, tool failures, empty retrieval, tokens/cost per successful task and generations lacking terminal states. Link request, retrieval and model/tool rounds in traces while redacting secrets and sensitive content. Default full-conversation logging can create an uncontrolled private-data store.

    Evaluation suites cover ordinary questions, long histories, conflicting evidence, prompt injection, denied tools, duplicate effects and cancellation races. Version prompts/models/retrieval settings with results; canary by cohort with fast rollback and quality/cost monitoring. Model judges provide evidence, not infallible ground truth.

    11a. Decisions at system and organizational scale

    Managed inference speeds up delivery and reduces GPU operations but adds dependencies on quotas, regions, data handling and version behavior. Self-hosting offers scheduler/model/data-path control but requires utilization, spare capacity, patching and operators. Compare cost per task meeting quality/SLOs, not only price per million tokens.

    Separate interactive, agent-loop and offline traffic using deadlines, quotas and scheduling classes. Agents chain model/tool calls, so optimize whole-loop latency and bound runaway work; offline batches can wait longer. One tenant’s huge prompts should not slow all conversations without explicit bounds or policy.

    Version models, prompts, retrieval indexes and tool schemas independently while recording enough metadata to reproduce a turn. Canaries need fixed evaluations plus privacy-aware production measurement; rollback must preserve old messages/history. Migration cost, on-call ownership and audit are architectural concerns, not afterthoughts once services multiply.

    12. Interview angles and design exercises

    Why have an orchestrator when a model API exists?

    A model API generates output; the orchestrator owns product identity, context, tools, retries, cancellation, persistence, budgets and versions. It can be a backend module rather than a separate service. The boundary makes failed-turn tests independent of stochastic model output.

    Is an SSE event ID enough to resume generation?

    No. The server needs retained events after that ID, ordering/retention guarantees, owner authorization and generation state. Replaying saved events differs from continuing inference after worker/KV loss; define incomplete/regeneration behavior instead of promising unsupported recovery.

    Does RAG replace fine-tuning?

    They address different needs. RAG injects updateable authorized evidence into context; fine-tuning changes behavior or task skill from training examples. They can be combined and both require evaluation; fine-tuning is not a store for dynamic document permissions.

    Exercise: a tool call retries twice after a timeout. How do we avoid three tickets?

    The gateway assigns a stable logical-action ID/idempotency key, stores its fingerprint/state and has the target enforce uniqueness. Reconcile timeouts with the same key or status lookup. Without target deduplication, design reconciliation/compensation and state the limit; retries alone cannot promise exactly-once effects.

    What prevents reading another user’s conversation?

    Server-side conversation-membership and tenant authorization on every endpoint, stream reconnect, message lookup and artifact retrieval. Unguessable IDs reduce enumeration but do not replace permission checks. Neither the model nor its prompt decides resource access.

    Does a safe sandbox establish that model code is correct?

    No. Isolation bounds authority/resources while analytical logic can still be wrong. Validate schemas/input provenance, numerical invariants and expected outputs; output artifacts still need ACLs/retention. Host enforcement of network/mount/resource policy cannot be replaced by prompt instructions.

    Why might users hear old audio after interrupting?

    Cancellation propagates with delay while old packets/buffers can still arrive and remain queued. Fence by playback epoch/generation at clients, flush old queues and propagate cancellation; measure interruption-to-silence. Cancellation acknowledgments do not establish stopped upstream billing/compute.

    Does deleting memory automatically remove cached answers?

    No. Derived response caches, summaries and retrieval projections have separate lifecycles. Current-version/policy serving fences or invalidation must block revoked data, while tombstones prevent late replay resurrection. Define history/log/backup retention scopes instead of promising instant erasure everywhere.

    May a shared assistant call tools as its creator?

    Not by default. Separate definition access from resource/action authority; use caller identities or explicit bounded/audited delegation. Pin configuration versions but check current grants at effect boundaries because immutable configurations do not freeze user permissions.
