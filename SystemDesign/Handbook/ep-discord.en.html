Building Community Chat: guild ownership, fan-out and hot history

Twelve stages separate archives, gateways and media, with safe read merging, relay backpressure and versioned snapshot/live replay for large communities.

Preserve state while reducing copies

  1. Persist

    Current ACL → idempotent sends → durable messages/events.

  2. Distribute

    Guild owners → audience relays → bounded queues.

  3. Read

    Equivalent merging → bucket archives → authorized pages.

  4. Recover

    Cursor/snapshot watermarks → bridge → versioned application.

Each plane and authority needs explicit failure/recovery contracts.

  • Durable commits, live delivery and application are different ACKs.
  • Owners/relays need permission and ownership versions; subscriptions are not permanent grants.
  • Affinity and merge keys differ; scopes, cursors and versions establish equivalence.
  • Relays distribute owner work while egress and catch-up need separate budgets.
  • Replay horizons, live bridges and deletion versions prevent silent gaps/resurrection.

1. A community product has multiple planes

Message archive

  • Durable sends, stable pagination and versioned edits/deletes.

Live state / audiences

  • Guild ownership, current permissions, gateway cursors and relays.

Voice / video

  • Signaling, secure media transport, jitter/loss and SFU bandwidth.

We build a Discord-like community with guilds, channels, roles, durable messages, live updates, search and voice. Guilds group communities; channels bound conversation and permissions. Users have multiple devices and memberships. Online, actively viewing and authorized are different audience properties.

Twelve teaching stages use original diagrams/labs. MongoDB, Cassandra, ScyllaDB, Elixir, Rust and relays illustrate dated architectural directions rather than a current-stack inventory or product mandate. The existing Chat chapter provides identity/offline-sync foundations; this build deepens guild-scale fan-out, archive reads and media separation.

2. Which ACK and which authority?

Separate persistence, publication and application

  1. Authorize / claim

    Current scope and stable send intent.

  2. Commit

    Messages/mutations, results and durable event intent.

  3. Fan out

    Owner → relays → gateways → allowed audience.

  4. Apply / resync

    Version/cursor checks or authoritative catch-up.

Acknowledge only proven boundaries and expose gaps.

Client acceptance, durable commit, publication, enqueue, socket delivery and application are distinct states. Specify sender durability and receiver gap/resync policies. Scoped send nonces prevent duplicate intent, while message identity and mutation versions separate edits/deletes from new content.

Local actor serialization still needs durable recovery and fenced ownership; leases do not fence unaware sinks. Define permission freshness/revocation for reads, search and relays. Membership at connect does not grant lifetime authorization.

3. 12 stages: state ownership and copy amplification

Each stage includes diagrams, pressures, decisions, trade-offs and exit criteria. Ask who owns durable state and how one event amplifies copies/queries. Distinguish request, runtime, engine and disk mitigations; language rewrites do not replace permissions or delivery contracts.

Small chat with durable history

A modular MVP combines sockets, permissions and writes. Index histories by channel/order and retain mutation versions. Commit messages and keyed send results before ACKs; live delivery does not establish durability.

Problem pressure: Small groups need rooms, history, reconnect and defined deletion.

Architectural decision: Use one service/store with bounded buffers, command IDs and durable event intent.

Costs and trade-offs: Deploys interrupt sockets while history/fan-out compete for resources.

When is the next step needed?: Connections scale differently from APIs/storage and need explicit ownership.

Retries preserve message identity and disconnected clients catch up durably.

Separate search indexing from commits

4. Count writes, connections, copies and bytes separately

Assume a billion messages/day at one KB each with three copies: about 11,574 messages/second and three decimal TB/day before indexes, attachments, mutations, tombstones and compression. A fivefold peak is about 57,870 writes/second; one channel can overload despite low cluster averages. Calling this modest needs workload evidence.

Two million connections with sixteen KB raw state already require 32 GB before TLS, queues and runtime overhead. Multiple devices/memberships make user counts insufficient. A message to 5,000 eligible viewers has 5,000 recipient copies; four relays reduce owner copies to four, not the roughly five MB of viewer payload.

One message is not quadratic. If N users each emit a presence update per minute to all others, work is approximately N(N−1)/60 operations/second. Audience selection, ephemeral coalescing and lazy ranges reduce work while retaining permissions, mentions and unread semantics. Catch-up shifts work rather than removing it.

5. Trace sending, fan-out, history and media

Persistence traces expose durability; fan-out locates audience selection. Session sequences need not equal message identities or channel total order. Define mappings, streams and retention rather than infer private ordering from public APIs. These diagrams use teaching contracts.

Resume traces expose watermarks/live bridging; voice/search stay outside commit callbacks. Indexers consume versioned committed mutations; media uses current permissions and scoped credentials. Cached dependencies never justify bypassing authorization.

Messages, gateway events and voice use different paths

Component map; the complete ordered request paths are explained below.

Persist before acknowledging

  1. Send scoped nonces, content and channel identity, preserving retry intent.
  2. Validate current permission/state versions rather than stale subscriptions.
  3. Route writes through data ownership without merging writes by read keys.
  4. Commit messages/mutations, result identities and event intent.
  5. ACK declared durability without claiming all receivers applied it.

Fan out under audiences and permissions

  1. Relay committed mutations through outbox/CDC.
  2. Apply stable events/versions under ownership epochs.
  3. Send once per destination relay with policy/version context.
  4. Select authorized active viewers under distinct passive policies.
  5. Push sequenced events or mark bounded-queue gaps.

History and safe read merging

  1. Request cursors/queries with consistency requirements.
  2. Authorize and route by channel; merge full equivalent identities.
  3. Read bounded buckets/snapshots honoring minimum versions.
  4. Return correct scope/cursors/generations and required policy validation.

Resume or snapshot and bridge live

  1. Reconnect sessions/cursors and check validity/replay coverage.
  2. Reauthorize current membership/ACL despite valid-looking old tokens.
  3. Fetch watermarked authoritative snapshots for expired gaps.
  4. Bridge events after snapshot watermarks with bounded buffers/gap detection.
  5. Apply monotonic mutations/tombstones and ACK applied contiguous cursors.

Separate voice and search

  2. Issue scoped regional sessions and secure signaling.
  3. Send media directly through forwarding paths.

6. Example APIs and ordering contracts

These example endpoints are not Discord API guidance. Scope nonce/fingerprint/replay contracts and validate cursors carrying ordering, ties and generations as required. Time-sortable IDs do not establish causal commits under concurrent generators/skew; per-channel order requires explicit authority/protocols.

POST /channels/{id}/messages

Authorize and commit a scoped message.

{ "nonce":"send-17", "content":"hello", "attachmentRefs":[] }
201 { messageId, mutationVersion, committedAt, deliveryStatus: "queued" }
  • Reject changed keyed payloads; queued delivery does not establish client receipt.

GET /channels/{id}/messages?before={cursor}&limit=50

Read history under current permissions and snapshot/read floors.

200 { items, nextCursor, observedGeneration, watermark }
  • Merge only equivalent queries/scopes; read-your-writes may require minimum versions.

PATCH /messages/{id}

Versioned edits/deletes have separate permission checks.

{ "expectedVersion":7, "operationNonce":"edit-4", "content":"updated" }
200 { messageId, mutationVersion:8 } | conflict / forbidden
  • Deletion is a durable mutation propagated to history/index/projections, not just DOM removal.

WS /gateway (illustrative protocol)

Identify/resume, heartbeat, subscription and sequenced dispatch.

{ op:"resume", sessionId, lastAppliedSeq, subscriptionsVersion }
{ replay | snapshotRequired | invalidSession | forbidden, watermark }
  • Reauthorize on resume/focus; heartbeats/liveness and replay retention do not establish durability.

7. Buckets, cursors and mutation/deletion versions

Choose buckets by distribution, partition size and scan costs rather than one universal day count. Quiet channels need empty-bucket bounds/metadata; busy channels may need splits or dedicated admission. Pagination needs stable ordering/ties and declared behavior under concurrent writes/mutations and bucket crossings.

Deletion evidence must survive replication/replay horizons to avoid resurrection. Backfills and stale client pages need versions too. Replication counts do not independently define ACK durability or read-your-writes. Test repair, failures and restore against accepted-message/RPO contracts.

Same-page read storms differ from partition growth. Cached results and in-flight merging have different staleness, invalidation and cancellation rules. Engine changes do not repair authorization keys or unbounded queues.

8. Coalescing needs full query identity and consistency floors

Channel IDs create affinity, while merge keys include tenants, ranges, cursors/limits, filters/schema and equivalent authorization scope/version. Raw-storage merging still requires per-response authorization. A role name alone cannot establish identical visibility under private history, blocking or personal filters.

Read-your-writes may require a known version; pre-write in-flight snapshots can fail it. Do not join minimum-version-two readers to version-one work. Start/read suitable authority or expose approved staleness. Bound worker lifetimes/waiters, with cancellation policies that account for other waiters.

The mixed fixture shows that low query counts can be wrong. Shared coordination can merge across instances; hashing is one localization choice rather than the only possibility. Multiple arrival windows create multiple queries even for one key, not one perpetual channel query.

9. Active audiences, relays and bounded slow consumers

Distinguish content, unread, mentions, typing, presence and member diffs. Passive sessions may skip content while retaining coarse notifications. Cached subscriptions still need permission freshness/revocation and reauthorized history/search. Wrong audience contracts cause omissions or leaks.

Relays distribute copying without removing recipient egress. Bound queues by bytes, count and age. Coalesce ephemeral state where valid; mark durable-content gaps for cursor/history reconciliation rather than silently dropping with applied ACKs. Bound catch-up and resubscribe load so overload does not simply move to storage.

10. Resume watermarks and live races

Finite buffers cover only valid sessions/cursors and retained gaps. Expired gaps require snapshots/history, not an incomplete suffix. Watermarks bridge live arrivals during snapshot transfer or expose gaps. Last received is not applied contiguous progress under parallel application or holes.

Versions/tombstones prevent stale-page resurrection, retained through relevant horizons or replaced by resync generations. Current permissions may deny valid-looking old sessions. Servers cannot reclaim previously saved data/screenshots, so no-new-delivery differs from universal erasure.

11. Search, member ranges and read markers

Search consumes committed mutations, versioned bulk indexing and checkpoints, enforcing current scope. Filter stale/deleted candidates with explicit recall/page behavior. Cluster routing needs versioned mappings and complete rebalances. Index lag never waives deletion/permission correctness.

Lazy member windows need versions, stable ordering and rank-shift handling; insertions before a viewport may require rebasing. Read markers may be monotonic while mark-unread is a separate operation. Version dirty writeback so retries cannot regress current state.

Profiles may justify native sorted structures or narrow rewrites, with scheduler, lifetime/FFI and failure testing. Rust does not make every boundary crash/latency free. Historical GC results describe dated workloads rather than universal language rankings.

12. Voice/media bandwidth, subscriptions and failures

Signaling authorizes scoped media sessions. Media forwarding needs negotiated security, congestion handling, jitter/loss policies and NAT/relays. SFUs forward encoded streams while MCUs mix; device, group, processing and latency requirements guide choices. Forwarding still costs CPU and egress.

For twelve participants and three 32-Kbps speakers, SFU ingress is about 96 Kbps; forwarding each stream to eleven others needs about 1056 Kbps egress before overhead/redundancy. Selection/silence suppression can reduce this; video layers differ. Measure capture, encode, network, buffering, decode and playout rather than text p99.

Transport and end-to-end security have different trust/key boundaries. E2EE needs membership/device key management and affects processing. Forwarding encrypted media still involves signaling, metadata and authorization. Historical protocol choices are not current product-security guidance.

13. Store migration and disk optimization are distinct

The dated store evolution does not rank engines universally. Measure layouts, tombstones/compaction, replica settings and workload. Bound amplification before evaluating engines. Migrations need recoverable change capture, versions, tombstones, checkpointed backfills and comparisons; equal counts do not prove correct content/order.

Verify cutover frontiers and read semantics. Rolling back new-only mutations needs reverse sync/repair without resurrection. Tombstone-heavy ranges and skew can dominate backfills, so checkpoints, backoff and live reserves matter more than easy-range peak throughput. Apply retention/deletion policies across projections and copies.

Local read tiers with durable backing need ordering, flush/ACK semantics, bad-sector handling, trusted rebuilds and degraded alerts. Mirroring does not replace replication/backups. RAID/write-mostly illustrates I/O behavior, not executable universal disk guidance.

15. Practice deep dives through counterexamples

Ground answers in one send trace, one large-guild workload and fault windows. Define audiences and ACKs before listing products. These answers use teaching contracts; actual product protocols need version-specific validation.

Is one message to a million-member guild quadratic?

No. One message scales with recipients. Quadratic work requires event rate also grow with users, such as all-to-all presence. Audience selection reduces content and relays distribute ownership work without removing recipient bytes.

Why is channel-only merging unsafe?

Scopes, cursors, filters and consistency differ. Moderator data can leak, pages can mismatch and old snapshots can violate write visibility. Affinity can use channels while merging needs full equivalence or explicit per-response authorization.

Can merging work without affinity?

Local merging loses effectiveness across instances; shared coordination can merge globally, so affinity is not a mathematical requirement. Costs, availability, deadlines and equivalence remain, and multiple time windows still create multiple queries.

Does passive mode suppress every notification?

No. Content, unread, mentions, presence and push have separate audiences. Rejoining requires authorization and bridged catch-up without silent cursor gaps.

What can a snapshot followed by live subscription miss?

It can miss events between watermark and subscription activation. Buffer first or bridge the log after the watermark, resynchronizing expired gaps. ACK applied contiguous progress and retain mutation/deletion guards.

Does rewriting Go into Rust eliminate p99 spikes?

No. Historical GC profiles identify one cause; allocation, freeing, locks, I/O and queues remain. Profile current workloads, bound memory and test canaries. Native boundaries need scheduler and failure safety.

Does one uploaded SFU stream make bandwidth constant?

Per-sender ingress can be one stream, while egress scales with subscriptions. Three speakers, eleven receivers each and 32 Kbps require about 1056 Kbps. Selection, layers, decoding, jitter and key models need separate budgets.

Does mirroring or three replicas establish durability?

Not without ACKs, ordering/flush, consistency, correlated failures, repair and backups. Test pending writes under host/disk/region loss rather than infer durability from copy counts.
