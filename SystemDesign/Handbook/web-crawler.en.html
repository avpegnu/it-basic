Designing a Web Crawler: frontiers, politeness and coverage

Build a durable crawl loop and explore per-host scheduling and Bloom budgets; understand robots, URL identity, deduplication, traps, recrawls and recovery.

A bounded crawler loop

  1. Admit and prioritize

    Apply scope, URL identity, durable jobs and priorities.

  2. Wait for host readiness

    Enforce politeness, robots, DNS/IP and deadlines.

  3. Fetch, parse and persist

    Bound inputs, fingerprint, persist bodies/metadata and discover outlinks.

  4. Learn and recrawl

    Use freshness signals, trap/coverage metrics and recovery.

Optimize quality and freshness within budgets, not request rate alone.

  • Priority chooses valuable URLs; host readiness determines when fetching is allowed.
  • Host partitioning simplifies steady state without automatically solving stale owners or in-flight failover.
  • A Bloom positive is possibly seen, not exact membership when coverage matters.
  • URL canonicalization, content deduplication and trap defense are distinct layers with separate trade-offs.
  • Durable admissions/results/outlinks and recrawl identities must survive crashes; robots is not a security guard.

1. What is the crawl for and within which scope?

Budgeted coverage

  • Prioritize by purpose, URL quality and freshness value while retaining discovery provenance.

Politeness is an invariant

  • Bound host/origin rates/concurrency, optionally add shared-IP/domain guards, and back off on overload.

Hostile input is everywhere

  • Bound and validate URLs, DNS, headers, compressed bodies, HTML and redirects.

Search indexing, archiving and dataset acquisition have different priorities. This baseline fetches HTTP/HTTPS HTML from seeds/sitemaps, discovers links, stores bodies/metadata and recrawls for freshness. Ranking/indexing, media and JavaScript rendering are outside the baseline. Define domains/scope, retention, opt-outs, budgets and an identifiable user agent/contact before counting workers.

An operational web graph is effectively unbounded: calendars, facets and session URLs can generate unlimited nodes. Do not promise “the whole web”; measure coverage within important scope, freshness and resource use. Distributed crawlers still obey origin-specific policies; cluster throughput is not permission to increase load on an external site.

2. Size fetching, bandwidth, storage and concurrency

At two billion fetches per thirty-day month, the average is 771.6 fetches/second and a twofold peak is 1,543.2/second. Assuming 100,000 B average raw bodies and fivefold compression gives about 40 TB/month, or 1.44 PB over 36 months if every snapshot is retained without deduplication. These are illustrative inputs; measure body size, compression and change ratios on the actual corpus.

The peak raw payload is about 154 MB/second or 1.23 Gbit/second before headers, TLS, retries and storage writes. In steady state, Little’s Law gives mean in-flight work ≈ throughput × mean time: 1,543/second × two seconds is about 3,086 simultaneous fetches. This does not yet establish a safe socket/worker count because long tails, host-imposed idle time, DNS, parsing and backpressure matter.

3. Internal admission, lease and result contracts

A crawler may expose a control API, while its main data contracts are internal jobs. Admissions carry canonicalization versions, provenance and scope. One URL identity can have multiple fetch jobs across schedule epochs; retries preserve job IDs. Internal endpoints must not become public arbitrary-URL fetch proxies.

POST /frontier/admissions

Validate and durably admit seed/discovered URLs.

{ "url": "https://a.example/docs", "discovered_from": "seed:42", "scope_id": "public-docs", "canonical_policy": "url-v3" }
202 { "url_id": "u42", "admission": "queued-or-existing" }

    POST /frontier/leases

    Claim owner/epoch-qualified jobs; hosts not yet ready cannot be fetched immediately.

    { "worker_id": "w1", "owner_epoch": "7", "max_jobs": 20 }
    200 { "leases": [{ "job_id": "j42", "url_id": "u42", "lease_token": "t7", "deadline": "..." }] }

      POST /fetch-results

      Idempotently publish results by job; body references must exist before indexers read metadata.

      { "job_id": "j42", "status": 200, "final_url": "https://a.example/docs", "body_ref": "blob:42", "content_hash": "...", "etag": "opaque-validator" }
      201 { "result_id": "r42" }

        POST /frontier/jobs/{id}/complete

        Acknowledge with lease tokens and result/outlink checkpoints; stale owners cannot overwrite newer state.

        { "lease_token": "t7", "result_id": "r42", "outlink_checkpoint": "done" }
        204 | 409 stale lease

          4. The crawl loop needs durable admissions and results

          A frontier chooses eligible URLs, bounded fetchers read them, parsers process bodies and extractors discover links. An HTTP 200 is not enough to acknowledge an input whose result/outlinks remain only in RAM. Idempotent results and outbox/checkpoints let crash replays avoid lost work or unlimited duplicate discovery.

          Backpressure must propagate from storage/parsing to fetch admission: reduce fetching when parser queues fill instead of accumulating unbounded bodies in memory. DNS and robots precede network access; caches do not remove security or expiry checks. Stage time/size limits and queue age belong in capacity planning before scaling.

          A crawl loop with a durable frontier and bounded fetching

          Component map; the complete ordered request paths are explained below.

          Fetch and discover outlinks

          1. Lease a ready-host job with its job ID and ownership epoch.
          2. Check robots, DNS/IP, scope, budgets and the next allowed time.
          3. Allow the validated address/host; redirects require rechecking.
          4. HTTP GET with deadlines and response limits; slow hosts cannot occupy workers indefinitely.
          5. Receive bounded status/headers/body and classify errors separately.
          6. Parse the bounded body and fingerprint the chosen representation.
          7. Persist a new body when needed and publish metadata/body references recoverably/idempotently.
          8. The result reaches its durable boundary before the input job is acknowledged.
          9. Extract links using the base URL and scope of the final response.
          10. Normalize under policy and reserve/admit URLs with durable enqueue/outbox semantics.
          11. Publish stable-identity discovery jobs; replay must not lose URLs or create unbounded enqueue loops.
          12. Complete the lease after result/outlink obligations are satisfied; recrawls use distinct jobs/schedule versions.

          Seed admission

          1. Seeds also pass resolution/validation/scope guards and do not bypass network policy.
          2. Check URL identity and atomic admission; define coverage behavior for Bloom positives.
          3. Commit/publish durable work before acknowledging admission.

          Robots or scope denies access

          1. A worker receives a job but has not fetched its destination.
          2. Policy denies access or requires backoff because the origin is unavailable.
          3. Return a block/defer reason rather than a successful missing-page result.
          4. Record the decision/retry time without inventing a body.
          5. The decision is durable.
          6. Finish or reschedule under the recorded reason; this trace never calls the target.

          Conditional recrawl with a 304

          1. A recrawl becomes due; old discovery deduplication must not block all recrawls.
          2. Recheck eligibility, robots and politeness before another fetch.
          3. Allow a request using stored validators.
          4. Send If-None-Match or appropriate validators rather than assuming an unchanged body.
          5. A 304 follows conditional semantics without a new response body.
          6. Update fetch metadata/recrawl state and retain the appropriate earlier body reference.
          7. Commit result metadata by job identity.
          8. Acknowledge and schedule the next recrawl under freshness/budget policy.
          Seeds / sitemap input
          Initial URLs have provenance and scope; good seeds do not guarantee complete web discovery.
          Durable URL frontier
          Priority plus host readiness, job identities/leases, retries and recrawl schedules, not merely one FIFO queue.
          Bounded fetcher
          Bounds timeouts, concurrency, bytes/decompression and redirects; all network hops pass policy and network guards.
          Target origin
          An external server can be slow, fail, redirect or return malicious content. The crawler does not own its capacity.
          REP + DNS / egress
          Origin-scoped robots policy, connection-time DNS/IP validation and host budgets; each cache has its own freshness.
          Parser / fingerprints
          Parses within size/depth/time budgets; exact and near-duplicate decisions use different policies.
          Bodies + metadata
          Immutable blobs and URL/fetch metadata with status, validators, fingerprints and body references; publication/recovery preserve results.
          Resolve / scope filter
          Resolves relative links against the correct base and applies versioned canonicalization, trap and scope guards.
          URL admission store
          Bloom aids membership checks; exact reservation/durable enqueue preserves state. Discovery dedup differs from recrawl eligibility.

          5. Priority and per-host readiness are separate decisions

          Front queues rank work by importance, freshness, scope and budget; back queues/host state decide when fetching may start. A next_allowed_at min-heap and per-host in-flight limits select ready hosts. One host with millions of URLs must not monopolize queues or block others; use fairness/aging to avoid starving lower-priority work.

          Start-to-start intervals differ from completion-to-next-start delays. The model uses a minimum start interval plus one in-flight fetch per host. Production can adapt to response time, overload responses and owner policy. Host/origin limits may not protect shared IPs or one site with many names; add domain/IP guards when appropriate, considering shared hosting and DNS changes.

          6. Host ownership, failover and stale fetchers

          Hashing/partitioning hosts to owners colocates timers/queues and reduces hot-path coordination. It does not prove there is only one live worker after pauses, partitions or reassignment. Lease expiry does not terminate an old process, and fencing ledger writes does not automatically prevent external GETs because targets do not understand owner epochs.

          Handoffs need durable host state, ownership terms and in-flight request policy. Strict cross-failure host admission needs a controlled egress/scheduler boundary that rejects stale owners, or suspended fetching during uncertain ownership. An arbitrary failover delay is not proof without bounds on old workers/requests. At-least-once job recovery can repeat fetches while network-boundary politeness still needs enforcement.

          7. Robots policy and error states

          Robots applies to the relevant origin/authority and user-agent group with correct Allow/Disallow matching. RFC 9309 permits access after an unavailable 4xx but treats server/network unreachability as disallow by default; implementations can be more conservative. Normal caching should not exceed 24 hours except under protocol-defined unreachability. Robots is not authorization.

          Crawl-delay is not standardized by RFC 9309; support it only as an explicit extension policy. Operational throttling/backoff and opt-outs need their own behavior. Robots and page redirects both require network/security guards; another host must not bypass validation or rate budgets.

          8. URL identity must not change the resource

          Resolve relative URLs against the final response URL and appropriate HTML base semantics using a tested parser. Schemes/hostnames and default ports generally permit normalization, but paths and reserved escapes must not be casually lowercased/decoded. Fragments normally are not sent in HTTP requests, so an HTML-fetch baseline can exclude them from identity. Fragment routing can change rendered app state, so “fragments never change content” is too broad.

          Query ordering, duplicate parameters and session IDs can affect the target application. Do not globally sort queries or delete sid/sessionid/utm_* and declare equivalence. Use validated site-specific rules, version policies and retain original URLs/provenance for audit/rollback. rel=canonical is a page-provided hint, not authority to merge arbitrary URLs or bypass scope.

          // Baseline fetch identity only; NOT a complete SSRF or robots check.
function fetchIdentity(raw: string, base: string): string | null {
  try {
    const u = new URL(raw, base);
    if (!['http:', 'https:'].includes(u.protocol)) return null;
    if (u.username || u.password) return null;
    u.hash = ''; // This baseline fetches HTTP HTML, not rendered fragment routes.
    if (u.href.length > 4096) return null; // Product budget, not a protocol limit.
    return u.href; // Preserve query ordering, duplicate params and path case.
  } catch { return null; }
}

          The parser handles schemes/hosts/default ports under its own semantics. Connection-time DNS/IP/redirect validation, robots and scope checks remain necessary; a returned string is not permission to fetch.

          9. Bloom filters and exact admissions differ

          A standard Bloom filter returns definitely absent or possibly present at a configuration/load-dependent false-positive rate. Skipping every positive can omit new URLs: this is a coverage trade-off, not exact deduplication. For coverage-sensitive crawling, verify positives in an exact authoritative store. Negatives still need atomic reservation/enqueue to handle concurrent discovery.

          Marking seen before enqueue and then crashing can lose a URL without a durable job. Use a reservation state machine/outbox or atomic admission suited to storage. Discovery deduplication must not suppress due recrawls: separate URL identity, scheduled-job identity and completion. Bloom generations/resets/retention are operational choices, not complete history.

          10. Exact duplicates, near-duplicates and spider traps

          One normalized URL can change bytes over time, and many URLs can return the same bytes. Content hashes can share bodies while retaining per-URL/fetch provenance. Near-duplicate fingerprints such as SimHash or shingle similarity have false positives/negatives and need corpus-tested thresholds; a small distance does not universally mean the same document.

          Text/boilerplate normalization can aid deduplication while erasing meaningful changes such as prices, dates or numbers. Record fingerprint representation/version and decide whether raw snapshots are needed. Spider traps concern URL discovery/budgets; post-download deduplication cannot recover bandwidth spent on millions of trap URLs.

          11. Fetchers are network boundaries parsing hostile input

          Every outbound request crosses the same guards

          1. Scope and URL

            Validate parsing, schemes/authority, credentials and product limits.

          2. Policy and destination

            Check robots, readiness, DNS/IPs and egress permission.

          3. Bound and observe

            Bound time, bytes, redirects and CPU and record stage-specific reasons.

          Apply guards to robots, redirects and renderer subresources, not only seeds.

          Validate schemes and connection-time DNS/IPs on every redirect, restricting private/link-local/metadata/loopback and unauthorized egress under scope. Checking a hostname once and allowing a library to resolve another address does not stop rebinding/redirect escapes. Validate TLS certificates/hostnames. Renderer subresource requests belong to the same network policy.

          DNS caches reduce lookup cost while retaining TTL/negative-cache obligations; slow resolution can consume concurrency even for fast targets. Bound connection/read/total time, headers, compressed/decompressed bytes, redirects and parser CPU. Record compression-bomb, malformed-HTML and encoding failures rather than converting timeouts into long-cached missing pages.

          12. Trap defenses and JavaScript rendering

          URL length/depth caps are product budgets, not proof against traps. Facets, calendars and pagination can create unlimited shallow URLs. Combine origin/domain budgets, pattern detection, unique-content yield and sampling, retaining budget-denial reasons. Sitemaps are also untrusted and require size, recursion and scope limits.

          Headless rendering needs separate sandboxed pools with network and CPU/memory/time guards. Escalate pages only when purpose requires it; rendering does not guarantee access to login-gated or interaction-dependent content. Costs vary with execution/subresources rather than one universal multiplier. Distinguish raw-fetch and rendered snapshot identities/provenance.

          13. Recrawling is new scheduling, not just retrying

          Prioritize recrawls using observed change rates, user value, failure history and budgets. Rapidly changing low-value pages do not automatically deserve continuous crawling; important pages can have freshness SLOs. Observation intervals bias change-rate models: identical endpoints do not prove the page stayed unchanged between fetches.

          Use stored ETags/Last-Modified for conditional requests when available. A 304 saves body bytes but still costs a request, networking and host budget. Preserve validators/body references/versions appropriately as metadata changes. Without effective validators, content hashes save duplicate storage after downloading, not fetch bandwidth. Failure/robots backoff must retain future recrawl obligations.

          14. Body publication, metadata and recovery

          Use immutable blob keys/checksums and metadata keyed by URL ID plus fetch/job ID. A blob without committed metadata becomes an orphan requiring collection; published metadata without an available blob dangles. Use ordering and outbox/manifest/reconciliation so indexers read only eligible records. Version compression/formats/checksums and prevent untrusted stored HTML from executing in dashboards.

          Metadata includes original/final/canonical URLs and policy versions, provenance, fetch times, statuses/reasons, validators, body references, fingerprints, job/result identity and future eligibility. URL hashes aid routing/indexing; exact identity needs collision policy/full-URL comparisons. Restore frontier/seen/metadata consistently under a recovery contract rather than resetting one side and claiming no loss.

          15. Measure crawl quality and inject failures

          Track useful/unique-content yield, important-scope freshness lag, bytes per unique body, frontier age and origin budgets/throttling/backoff. Resource metrics include DNS latency, fetch tails, byte expansion, parser CPU/queues, storage publication lag and lease replays. High pages/second can hide duplicate/trap fetching.

          Crash after seen reservation before enqueue, after blob writes before metadata and after HTTP responses before acknowledgement; same-job replays must preserve the contract. Test stale owners, redirected disallowed destinations, unreachable robots, duplicate parameters/path case, malformed compression and infinite URL spaces. A normal-scheduler simulation does not prove distributed failover correctness.

          16. Interview questions and worked answers

          Explain an admission, fetch, result commit and recrawl, then break a crash boundary or slow down a host. More workers alone do not solve coverage or politeness.

          Will one host with millions of URLs become 100 times faster with 100 extra workers?

          Not if host rate/concurrency is the bound. More workers can help other hosts, parsing/storage or bounded long tails, not authorize more origin load. Prioritize valuable URLs, adapt scheduling and measure useful yield/freshness rather than raw QPS.

          Does consistent host hashing guarantee only one owner fetches at a time?

          Not through pauses, partitions or reassignment. Ownership and handoff/fencing are required, and external servers do not check epochs. Strict admission needs controlled egress/scheduling or suspension under uncertainty. Local timers simplify steady state without proving failover.

          Can every Bloom positive be skipped?

          Only if false-positive coverage loss is acceptable. Exact behavior verifies positives in an authoritative store; negatives still require atomic admission. No-false-negative behavior assumes correct state/hashing/insertion and does not prove queue/seen crash safety.

          Is it correct to sort query parameters and remove sessionid on every site?

          No. Ordering/duplicate parameters can matter, and sessionid can affect resources/authentication. Use tested site-specific rules with versions and original URLs. Lowercasing paths can also merge distinct resources.

          Why does disk grow faster than unique-page counts?

          Inspect unchanged recrawl snapshots, near duplicates, trap URLs, metadata/attempt overhead, replicas/backups and orphan blobs. Hashes/conditional GETs, evaluated near-duplicate policies, budgets and orphan reconciliation address different layers; Bloom alone cannot fix them all.

          Does robots.txt protect confidential content?

          No. It is public crawling policy; applications/servers enforce authorization. Crawlers still need network/security/scope guards, and Allow rules or a missing robots file do not authorize every destination/IP.

          Does a 304 make recrawling free of host budget?

          No. Requests, connections and server validation still cost resources; only body transfer/storage may be reduced. Preserve host intervals and correct validator/body versions. Post-download hashing saves storage, not already-transferred bytes.

          Seen is recorded but no job is queued before a crash. How do you recover?

          A boolean seen flag can lose the URL indefinitely. Pending reservations/outboxes with reconciliation or atomic seen/enqueue storage allow recovery. Retries preserve URL/job identity and keep discovery deduplication separate from recrawl scheduling.
