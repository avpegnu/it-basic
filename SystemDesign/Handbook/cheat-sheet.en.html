  3. Verify speculation

Optimizations preserve resource budgets, target semantics and user-visible deadlines.

  • Expected accepted tokens are not speedups; drafting, verification, memory and load all cost resources.
  • Disaggregation helps only when queueing, computation, transfers and capacity jointly fit SLOs.

Evaluation & Quality Gates: measure quality and understand uncertainty

From quality requirements to maintainable evidence

  1. Define acceptance

    Define outcomes, severity, slices and exclusions.

  2. Version cases

    Version representative samples, labels/rubrics and holdouts.

  3. Run / score

    Match candidate/baseline runs with code checks and calibrated judges.

  4. Qualify evidence

    Review intervals, slices and missing evidence.

  5. Expose / learn

    Bound exposure and learn from outcomes, rollback and incidents.

Each step addresses a different question: what to measure, whom it represents, how reliable the measurement is and when to stop rollout.

  • Evaluation suites are bounded operational acceptance contracts rather than complete product intent or proof of no unknown failures.
  • Version datasets, splits, rubrics and dependencies; never silently remove timeouts or errors from denominators.
  • Judge agreement, answer-order consistency and correctness are different quantities.
  • Paired bootstrap preserves matched cases, while clustering, sampling bias and degenerate samples require additional treatment.
  • Higher averages do not offset severe disclosures or critical-slice regressions.
  • Offline qualification permits controlled online trials, with product outcomes, guardrails and rollback still required.

  1. Measure gaps

    Measure tasks, baselines, latency, cost and evidence.

  2. Choose experiments

    Compare appropriate prompt, retrieval and weight changes.

  3. Train and evaluate

    Use reviewed data, pinned settings and independent holdouts.

  4. Operate artifacts

    Preserve compatibility, canaries, rollback and maintenance.

  • Choose interventions by measured gaps; prompts, retrieval and weight updates can cooperate rather than forming a mandatory ladder.
  • Weight adaptation can learn facts/behaviors without automatically providing freshness, evidence or access enforcement.

  • Preference learning needs sound data, references and evaluations; teachers/preferences are not oracles.
  • Adapted artifacts carry ongoing compatibility, regression and cost responsibilities across releases.

  3. Repeat decoding

  4. Stream and measure UX

  • Admission control and scheduling protect both memory and latency; one long request must not monopolize other users’ resources.

KV Cache, Memory & Quantization: budget bytes and reuse the right state

A budget across the request lifecycle

  1. Read the configuration

    Read layers, KV heads, dimensions, context policy and cache format.

  2. Budget each rank

    Budget weights, scales, KV, workspace and safe headroom.

  3. Manage pages

    Allocate, share, grow, copy on write and release safely.

  4. Measure and gate

    Evaluate quality, TTFT/TPOT, preemptions and realistic loaded capacity.

Separate logical tokens from physical bytes and state reuse from result reuse.

  • KV stores processed token/context state; it differs from weights and response caches.
  • Dense KV bytes depend on KV heads, dimensions, layers/context and dtype; the same formula does not fit every architecture.
  • Check each rank with head replication, workspace and future growth; aggregate HBM is not automatically a shared pool.
  • Paging reduces reservation waste without creating unlimited token capacity; shared mutable tails need copy-on-write.
  • Prefix hits require exact state identity and placement; they reduce reused prefill work without removing history reads during decode.
  • Quantization and offloading trade memory, quality, kernels and latency under measured workloads.

Parallelism & MoE: partition models, place GPUs and scale fleets

From workloads to operational layouts

  1. Define budgets

    Specify revisions, lengths, concurrency, quality and SLOs.

  2. Partition state and computation

    Partition tensors, layers, sequences or experts and identify communicating groups.

  3. Map onto topology

    Consider fast links, shared bottlenecks and replica fault domains.

  4. Measure and operate

    Profile tails, validate semantics and scale/drain whole groups.

Choose layouts using measured workloads and topology rather than the smallest weight-fitting GPU count.

  • A serving replica can be an entire GPU group; losing a required rank generally makes the group unavailable.
  • Memory fit, latency, throughput and failure isolation are distinct requirements that must work together.
  • TP trades tensor memory/computation for collectives; PP trades layer placement for handoffs and scheduling.
  • Total MoE parameters determine the weight inventory; selected experts explain only part of computation and communication costs.
  • Matching expert copies can preserve model selection; dropping contributions or choosing other experts changes computation.
  • Fleet capacity includes readiness delays, warm headroom, draining and correlated failures.

5. Add failures to every map

Commit before timeout

  • Unknown outcomes require lookup, deduplication or reconciliation rather than assuming rollback.

Duplicate delivery

  • Locate the effect and deduplication boundary; delivery guarantees alone are insufficient.

Stale owner

  • Caller-side lease checks are insufficient if resources accept stale authority.

  • Reuse and disclosure follow current access rules; cache hits do not grant permission.

Pair each happy path with an ambiguous outcome: a timeout after commit, a crash between effect and acknowledgement, an expired worker lease or revoked access after cache fill. These test understanding more deeply than adding retries.

8. Interview drill: move from pictures to reasoning

Answer without revealing a map, then check the linked lesson.

Why does a diagram with many components not establish a good design?

Component count says nothing about invariants, ownership, commit boundaries or recovery. A small coherent design is more informative than an ungrounded technology list.

Name a failure that makes a high-hit-rate cache incorrect.

Reusing private data after revocation can disclose it; delayed fills can also republish old versions. Enforce eligibility, freshness and versions at serving boundaries.

Does L=λ×p99 always give required concurrency?

No. Little's Law relates averages over a stable matching boundary. A percentile may inform other planning but is not a direct exact substitute.

When should you revisit the full lesson instead of more maps?

Revisit when you cannot explain ordering or consistency choices, confuse guarantees or cannot reason about failures. Maps cue structure while lessons repair the underlying model.
