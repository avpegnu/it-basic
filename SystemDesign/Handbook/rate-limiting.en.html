Rate Limiting: Contracts, Algorithms and Failure

Compare five algorithms on one traffic stream, expose counter races and design layered admission with explicit semantics.

From a rule to an admission decision

  1. Verify the subject

    Tenant, user, API key and endpoint.

  2. Determine policy and cost

    Window, burst, units and version.

  3. Check and spend

    Atomic boundary or bounded credits.

  4. Respond and observe

    Allow, throttle, failure and retry.

Each step needs a contract and failure behavior; admission does not promise every dependency succeeds.

  • Define subject, unit, window, burst and cost before selecting an algorithm.
  • A token bucket and a strict rolling limit are different contracts.
  • Atomic check/spend does not solve cross-shard coordination, failover or exact billing.
  • Failure modes, retry guidance and concurrency caps are part of the design.

1. Which behavior is limited, and why?

Protect a resource

  • Measure service time, concurrency and saturation alongside RPS.
  • Reject before expensive work has already happened.

Share capacity and enforce quotas

  • Choose users, tenants or API keys by contract; IP is only one signal.
  • Define resets, timezones, cost units and usage reporting.

A rule needs a subject, operation, unit, window, burst allowance and exhaustion behavior. “100 requests/minute” is ambiguous: fixed minutes, any rolling sixty seconds, or a bucket refilling at 100/minute with a burst of twenty? They can make different decisions on the same traffic.

Separate capacity protection, fairness, abuse defenses and commercial quotas. Protection may tolerate approximation for latency; charged quotas need durable semantics, audits and reconciliation. Rate limiting does not replace authentication, authorization or network-layer DDoS protection.

2. Five algorithms implement different contracts

A token bucket has capacity B and refill r tokens/s. Refill to min(B, tokens+r×elapsed), then spend the cost when available. It permits bursts with a long-term rate; over Δ it can admit roughly B+rΔ and does not enforce an arbitrary strict rolling-window maximum.

Leaky buckets have several variants. Here a bounded queue smooths output and adds delay; a queue-free meter differs. A sliding log counts admitted timestamps in a rolling window. Those admissions can still arrive together, so an exact rolling limit does not mean burst-free traffic.

In the lab, Arrival is request arrival and Release is departure from the service model. Non-queueing limiters release immediately; the leaky queue adds 1/r service time per unit and includes in-service work in capacity. This deterministic service model is not a real-server latency guarantee. Every lane uses one time scale, including queue drainage after arrivals end.

3. Layered protection uses different information

An edge/WAF may stop source-volume abuse before origin traffic. Gateways use verified identities for tenant/key/plan budgets. Services still protect concurrency, queues and resource cost. Whether an edge knows identity depends on TLS/auth termination and the actual architecture.

Rules need versions, owners, rollout and expiring overrides. Local rule caching avoids a mandatory configuration fetch per request; counters still need shared semantics. Define whether a mid-window policy change resets a budget or retains spending.

4. Trace an admitted or rejected request

Limit decisions precede side effects. A request within its quota may still fail resource admission; responses and telemetry should distinguish those reasons.

Layered admission

Component map; the complete ordered request paths are explained below.

Both request traces place decisions before side effects. A separate policy trace illustrates off-path refresh; counters must honor policy-version/usage semantics and backends retain resource admission.

Admit and execute

  1. The request reaches the edge with a deadline.
  2. Edge admission passes; the gateway checks rules/identity.
  3. Atomically check and spend the keyed budget.
  4. Return approval and budget information under the contract.
  5. Forward within the deadline; the service checks concurrency.
  6. Call the database only when resource admission permits.
  7. The database returns the operation result under its contract.
  8. The service returns the outcome and completes in-flight accounting.
  9. The gateway returns a response with metering under the defined policy.
  10. The client receives the final outcome; limiter allowance is not success of every mutation.

Budget exhausted

  1. The caller sends another request.
  2. The request reaches the gateway after a coarse check.
  3. Check finds insufficient budget for the request cost.
  4. Return denial without forwarding to the backend.
  5. The gateway creates a 429 with suitable retry guidance.
  6. The caller receives the policy outcome; retry requires waiting and its own budget.

Refresh policy off the request path

  1. A gateway polls/subscribes to versioned policies through a separate control path.
  2. Validate and install the policy snapshot; rollout defines retained usage versus budget resets. Reloading must not silently reset allowance.

5. Check and spend must be one atomic decision

Separate GET → compare → SET operations race across gateways. A counter may increase once while several requests pass. Atomic INCR alone does not make policy checks, TTL initialization and allowance decisions atomic. Choose scripts, transactions or conditional writes with the required boundary.

Redis scripts execute atomically on an instance but should stay short to avoid blocking other work. Cluster multi-key operations require compatible hash slots; one Lua call does not make tenant/global/endpoint decisions atomic across arbitrary shards. Replication/failover and counter durability can still affect quotas.

6. Clocks, TTLs and key cardinality

Use a shared time source for related state, handle negative elapsed time and define clock-jump behavior. Independent gateway wall clocks can disagree on refill. Redis TIME is still a server wall clock, not absolute-time certainty; define transitions and test jumps.

TTL cleans idle state rather than resetting budgets arbitrarily. Recreating a full bucket should require sufficient idle time under the contract. Normalize scoped keys and bound attacker-created cardinality so the limiter cannot exhaust memory. Never embed raw API secrets in keys/logs.

ATOMIC on one budget state:
  read policyVersion, tokens, lastRefill
  validate cost, capacity, refillRate and time assumptions
  available := min(capacity, tokens + safeElapsed * refillRate)
  if available >= cost: available -= cost; decision := allow
  else: decision := deny
  persist balance + logical refill position + safe idle expiry
  return decision + retry guidance

Boundary pseudocode, not a production script. The backend must implement validation, clock policy, expiry and suitable atomicity.

7. 429 and client retry behavior

429 communicates caller rate limiting; service-wide overload commonly uses 503 or another defined protocol. Explain the rule/unit and provide meaningful Retry-After guidance where possible. RFC 6585 permits the header rather than requiring it on every 429; including it is a useful cooperative design choice.

Retry-After is not a reservation: other traffic may consume the next allowance. Clients need capped attempts, deadlines and appropriate backoff/jitter without retrying earlier than the agreed guidance. RateLimit/RateLimit-Policy and X-RateLimit-* require an API contract and the adopted specification version, not interchangeable standard claims.

HTTP/1.1 429 Too Many Requests
Retry-After: 12
Content-Type: application/problem+json

{"type":"about:blank","status":429,"title":"Request budget exhausted"}

Illustrative response; derive the twelve-second guidance from the policy rather than hardcoding it for every caller.

8. When the counter store is slow or unavailable

Conditional fail open

  • Identify remaining resource self-protection.
  • Measure and bound degraded-mode duration.

Deliberate fail closed

  • Distinguish policy denial from unverifiable authority.
  • Set timeouts and recovery paths rather than hanging requests.

Budgeted local fallback

  • Allocate, account for and fence allowance under the failure contract.
  • A hot node can exhaust its allocation while global quota remains.

Fail open preserves request availability but may remove resource or abuse protection. Fail closed protects some contracts while making the limiter an outage dependency. Local fallback can bound damage with correctly allocated/fenced budgets; it is not universally better than the alternatives.

Dividing a limit by node count relies on traffic and membership assumptions: a hot node can reject despite spare global quota, while stale counts or duplicated allowances can overshoot. Token leasing needs accounting for outstanding credits, expiry, epochs and node loss. Exact charged quotas may need durable authority instead of approximate fallback.

9. Multiple rules, weighted cost and concurrency

One request passes several rules

  1. Burst

    Allow short spikes within defined capacity.

  2. Sustained rate

    Enforce explicit windows/refill rates.

  3. Period quota

    Account for costs and contractual resets.

  4. Resource admission

    Protect concurrency/deadlines near resources.

This is an evaluation sequence, not a cross-shard transaction. Later rejection requires explicit earlier-consumption/refund semantics; paid quotas also need durable metering.

A request may face per-user bursts, tenant sustained rates, daily quotas and global resource caps. Define whether attempts or successes are charged. If a later rule rejects after an earlier budget was spent, define refunds or intentional consumption. Different shards do not automatically share one atomic decision.

Weighted costs distinguish expensive searches from small GETs, but estimates need validation and caps. Concurrency limits complement rates when service time changes. Fair queues, tenant isolation and adaptive admission reduce noisy neighbors; controllers need stability and observability rather than reacting to every brief spike.

10. Hot keys and multiple regions

A hot tenant can overload its counter shard. Short-lived denial caches reduce lookups but may retain stale rejections after policy changes, requiring bounded TTL/version handling. Local leases reduce shared writes at an accuracy cost; key-based sharding does not split one hot logical counter.

Exact global budgets require coordination or safely partitioned authority across regions, creating latency/availability trade-offs. Uncoordinated regional budgets may grant the sum of all allowances. Derive overshoot bounds from outstanding credits instead of saying eventual sync is only slightly inaccurate.

For a 1,000-unit fixed-period quota, suppose the authority records 920 spent and three gateways retain 20, 10 and 15 unspent credits. Outstanding allowance is 45, leaving only 35 unallocated. If the authority looks only at 920 and grants another 80 while old credits remain spendable, total spending can reach 1,045: an overshoot of 45. This bound applies to this finite-grant example, not every local-sync design.

11. Rollouts, customers and observability

Shadow mode computes decisions/cost without blocking. Compare false positives, cardinality, store latency and downstream saturation, then canary tenant rules. Provide configuration rollback/kill switches, audited overrides and policy versions in traces. Avoid unbounded user/API-key metric labels.

Users need documented limits, useful usage visibility, reset semantics and a path to resolve incorrect throttling. Distinguish store failure, legitimate exhaustion and attacks in alerts. A quota change is a product contract, not merely a Redis number.

12. Interview: establish semantics before the algorithm

Where do you start with 100 requests/minute across 50 gateways?

Clarify fixed/rolling/burst-refill semantics, subject, cost and failure policy. Then choose atomic shared state or bounded credit allocation, verified identity, retry guidance and resource concurrency protection. Dividing 100 by 50 is not an exact global rule under arbitrary traffic distribution.

Assume a bucket refilling 100 units/minute, capacity 20 and unit-cost requests. Idle callers accumulate at most twenty, not one hundred immediately. Refill is 5/3 units/s; an empty bucket needs at least 0.6 seconds for one unit before contention. An integer Retry-After delay rounds up to one second and does not reserve admission. A strict 100-in-any-sixty-seconds contract instead needs a rolling log or equivalent semantics.

Route verified keys to an appropriate state authority with supported atomic check/refill/spend. Version policy caches and avoid resetting counter state on reload. Across fifty gateways, a static two-per-minute allocation can leave a caller on one gateway limited to two despite forty-nine idle nodes. Select failure modes by purpose; local credits must remain authoritative and restarts must not recreate full allowance.

Test boundary bursts, limiter-call retries after lost responses, counter failover, costs exceeding capacity, mid-window policy changes and cardinality attacks. Retried limit calls are not automatically refunded or idempotent; choose attempt versus logical-operation metering and decision receipts where needed. Measure decision p99, throttles by bounded policy class, store failures and downstream concurrency; use controlled logs/traces rather than unbounded tenant metric labels.

Does a sliding log prohibit bursts?

No. An empty budget may admit N requests together. It bounds admissions in the defined window; a leaky queue instead smooths execution and may add latency.

Does one Lua call solve tenant and global limits across Redis Cluster?

Only when required state lies within a supported atomic boundary, such as one slot. Across shards, choose coordination, credit allocation or explicitly staged consumption; Lua does not create cross-shard atomicity.

Why can a correct RPS limiter still overload the database?

Variable costs/service times, permitted bursts or many valid tenants can create excessive concurrency. Measure in-flight work, saturation and query cost, and add resource admission/bulkheads rather than relying on mean RPS.

Should every caller get 429 when the counter store is unreachable?

Not automatically: an unverifiable budget differs from proven policy exhaustion. Define failure mode and error semantics around abuse, commercial quotas and backend protection, with bounded and observable fallbacks.

When is a fixed window still reasonable?

For a fixed-window contract or coarse quota accepting boundary behavior in exchange for small state. Document resets/timezones and avoid synchronized retries. It is unsuitable for an unqualified strict rolling-window promise.
