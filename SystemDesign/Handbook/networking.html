Networking, API và protocol: theo dõi một request từ FE tới dữ liệu

Kết nối DNS, transport, TLS, HTTP, browser security và backend contracts thành một luồng dễ hiểu; chọn REST, RPC, GraphQL, polling hoặc streaming theo nhu cầu thật.

Một request đi qua nhiều hợp đồng

  1. Tìm địa chỉ đích

    DNS, routing và cache TTL.

  2. Thiết lập kết nối

    Transport, TLS và HTTP version.

  3. Đọc hợp đồng API

    Method, status, auth, retry.

  4. Theo dấu đến dữ liệu

    Deadline, ownership, response.

Các lớp liên quan nhưng không thay thế nhau: TLS không cấp quyền resource; CORS không xác thực user; timeout không chứng minh side effect đã thất bại.

  • Một request có nhiều giai đoạn độc lập: resolution, connection, bảo mật, routing, xử lý và đọc dữ liệu.
  • HTTP method, status và idempotency là hợp đồng; protocol không tự chống duplicate business action.
  • HTTP/2 multiplexing không loại bỏ TCP head-of-line blocking; HTTP/3 đổi transport, không tự sửa bottleneck của database.
  • CORS giới hạn browser đọc response; authorization và CSRF cần cơ chế riêng.

1. Phân biệt các lớp của request

Transport · Chuyển dữ liệu

  • Kết nối, stream, loss và congestion.
  • Bảo mật kênh truyền không thay thế authorization.

HTTP · Hợp đồng tương tác

  • Method, status, headers, cache và retry semantics.
  • Một HTTP response phải gắn với trạng thái ứng dụng đã hứa.

Ứng dụng · Quyền và invariant

  • Ai được làm gì với resource nào?
  • Khi timeout, xác minh outcome trước khi lặp side effect.

Khi frontend gọi API, nó không nhảy thẳng vào function backend. Browser cần biết địa chỉ đích, có connection phù hợp, thiết lập bảo mật, gửi HTTP message, qua proxy/load balancer rồi mới tới application. Application còn kiểm tra identity, quyền, input và query dữ liệu trước khi response quay về. Tách các bước giúp biết “chậm mạng” thực sự nằm ở DNS, TLS, queue hay database.

Connection reuse, DNS cache và TLS resumption có thể bỏ qua một số chi phí ở request sau. Một request cold và warm khác nhau; waterfall của browser phải được đọc cùng server trace. Frontend static deploy trên CDN vẫn cần backend riêng nếu muốn thực thi logic server, giữ secret hoặc truy cập database an toàn.

2. DNS và routing không phải service health

DNS ánh xạ tên tới record như A/AAAA hoặc CNAME theo resolver và TTL. Browser/OS/recursive resolver có thể giữ cache; đổi record không bảo đảm mọi client chuyển đích ngay. Khi dùng DNS failover, tính thời gian cache, connection đang sống và việc endpoint cũ vẫn nhận traffic.

Service discovery trong backend giải quyết việc tìm instance hiện có; load balancing và readiness quyết định instance nào nên nhận request. DNS resolve thành công không chứng minh application còn kết nối database được. Health check quá nông có thể route vào node đang lỗi, còn probe quá sâu có thể làm cả cụm bị rút khỏi routing vì một dependency chung chậm.

3. TCP, TLS và HTTP/2/3

TCP cung cấp byte stream có thứ tự và retransmission; nó không giữ ranh giới application message. TLS xác thực server theo certificate và bảo vệ confidentiality/integrity trên đoạn kết nối đó. Nếu TLS terminate tại proxy rồi proxy gọi backend plaintext, đoạn sau cần threat model và network policy riêng; biểu tượng HTTPS ở browser không mô tả toàn đường nội bộ.

HTTP/1.1 thường dùng connection reuse; HTTP/2 multiplex nhiều stream trên một TCP connection. Khi TCP thiếu byte do packet loss, các stream cùng connection vẫn có thể bị chặn chờ transport phục hồi. HTTP/3 dùng QUIC trên UDP với reliable streams và security tích hợp, giúp tránh kiểu blocking giữa stream do một ordered TCP byte stream; congestion và shared bottleneck vẫn tồn tại.

Không chọn version bằng một khẩu hiệu “UDP nhanh hơn TCP”. So trên packet loss, RTT, connection reuse, proxy support và workload. API mất 500 ms trong query không tự nhanh thành 50 ms khi đổi HTTP/2 sang HTTP/3. Tối ưu protocol phải được đặt trong latency budget toàn request.

4. Thiết kế hợp đồng HTTP rõ ràng

API contract gồm identity, resource, schema, validation, status, lỗi ổn định, pagination, quota và retry semantics. GET an toàn nghĩa là client không yêu cầu thay đổi business state; logging hoặc metric incidental vẫn có thể xảy ra. Idempotent nghĩa là lặp cùng request có cùng intended effect, không nhất thiết cùng response hoặc chỉ một dòng log.

PUT/DELETE có semantics idempotent theo HTTP, nhưng code phải thực thi đúng. POST tạo order cần application idempotency key nếu muốn retry an toàn: key gắn với actor, request fingerprint và kết quả đã lưu. Khi timeout, client không biết server chưa nhận, đang xử lý hay đã commit; query trạng thái hoặc replay cùng key tốt hơn tạo business action mới.

5. REST, gRPC và GraphQL

REST là architectural style, không đồng nghĩa mọi JSON qua HTTP đều đã RESTful. Resource-oriented HTTP API thường dễ debug, dùng browser/cache/proxy tốt và hợp với public boundary. gRPC dùng typed contracts và hỗ trợ streaming phù hợp internal RPC, nhưng cần tooling, compatibility discipline và browser adapter khi môi trường yêu cầu.

GraphQL cho client chọn field và ghép dữ liệu qua schema. Nó có thể giảm over/under-fetching nhưng không tự giải quyết N+1 query: resolver cần batching, query depth/cost limits và authorization theo field/resource. Một request HTTP duy nhất vẫn có thể tạo hàng nghìn query bên trong; rate limit theo request count đơn thuần sẽ bỏ lọt chi phí đó.

Ưu tiên evolution tương thích: thêm field optional thường dễ hơn đổi nghĩa hoặc xóa field đã dùng. Với RPC schema, tuân thủ quy tắc wire compatibility của encoding; với HTTP API, version không chỉ là /v2 mà còn semantics pagination, errors và idempotency. Contract test và staged rollout giúp client/server khác phiên bản vẫn giao tiếp.

6. Polling, long polling, SSE và WebSocket

Polling định kỳ dễ triển khai nhưng request count tăng theo số client và interval; 100.000 client poll mỗi 5 giây tạo trung bình 20.000 requests/s ngay cả khi không có update. Dùng jitter tránh mọi client poll cùng thời điểm. Long polling giữ request tới khi có event hoặc timeout, giảm response rỗng nhưng cần connection budget và reconnect policy.

SSE phù hợp stream event từ server sang browser bằng HTTP; submit/cancel có thể dùng request riêng. WebSocket hỗ trợ hai chiều liên tục cho chat realtime, collaboration hoặc audio, nhưng cần app-level identity, message schema, heartbeat, backpressure và reconnect/resume. Transport không tự lưu message hoặc chống duplicate sau reconnect.

Định nghĩa sequence/event ID, retention và replay window. Client mất kết nối sau event 40 chỉ resume được nếu server còn event 41 trở đi và đã kiểm tra quyền. Nếu log hết hạn, tải snapshot rồi tiếp tục theo protocol đã định nghĩa; không hứa “realtime exactly-once” chỉ vì dùng một socket lâu dài.

WebTransport cung cấp các kiểu stream và datagram cho ứng dụng cần hai chiều linh hoạt trên transport hiện đại, ví dụ realtime media hoặc game. Nó có mô hình API, deployment và khả năng hỗ trợ client khác WebSocket; kiểm tra browser/proxy và fallback của sản phẩm trước khi chọn. Unreliable datagram chỉ phù hợp dữ liệu được phép bỏ, không tự dùng cho confirm payment hoặc message cần bền vững.

7. Sơ đồ FE → BE và event quay về

Từ frontend tới backend, database và realtime

Sơ đồ các component; các luồng request được giải thích đầy đủ theo thứ tự bên dưới.

HTTP read

  1. Resolve tên nếu chưa có cache phù hợp.
  2. Dùng hoặc tạo secure connection, gửi HTTP request.
  3. Route cache miss/private request tới API cùng identity context phù hợp.
  4. Query có authorization và bounded deadline.
  5. Serialize response; browser áp same-origin/CORS và render an toàn.

Write + event

  1. Submit mutation có auth, CSRF protection khi phù hợp và idempotency key.
  2. Commit invariant và event intent theo transaction/outbox.
  3. Relay phát event sau commit; delivery có thể lặp.
  4. Gateway nhận event dành cho user đã được cấp quyền.
  5. Gửi event có sequence; client dedup và refresh state nếu cần.
Frontend / browser
Giữ UI state, gửi request theo auth/session policy và render output an toàn. Không giữ secret database hoặc service admin.
CDN / edge
Phục vụ static asset, TLS/routing và cache response phù hợp. Private response không được chia sẻ theo URL-only key.
Backend / API
Validate identity, authorization, schema và deadline; giữ transaction và business invariant.
Database
Nguồn sự thật của resource; index theo query, constraint giữ invariant và owner ghi rõ ràng.
DNS resolver
Trả địa chỉ theo cache/TTL; không kiểm tra correctness của application response.
Event log / broker
Phân phối event sau durable commit; replay, ordering và retention theo contract riêng.
Realtime gateway
Giữ connection, map session/user, giới hạn buffer và hỗ trợ resume nếu có retained events.

7a. Pagination và optimistic concurrency

Offset pagination dễ hiểu nhưng deep offset có thể phải bỏ qua nhiều row; insert/delete làm vị trí thay đổi khi user cuộn. Keyset cursor dùng một sort key ổn định và tie-breaker, ví dụ (created_at, id), cùng index tương ứng. Nó giảm chi phí đi sâu theo access pattern phù hợp, không tự bảo đảm snapshot nhất quán khi sort key thay đổi.

Cursor nên opaque với client và được validate, có thể ký để chống sửa, gắn filter/user/session khi cần. Base64 chỉ là encoding, không phải encryption hoặc chống giả mạo. Ranked feed cần ranking/session semantics riêng; mỗi trang vẫn kiểm tra quyền hiện tại, dù candidate thuộc snapshot cũ.

Với update cạnh tranh, trả version hoặc ETag rồi yêu cầu If-Match/expectedVersion. Server dùng conditional update atomic và trả conflict/precondition failure nếu resource đã đổi. Client phải đọc lại/reconcile; không chỉ retry payload cũ cho tới khi ghi đè được thay đổi của người khác.

      7b. API gateway, BFF và trust boundary

      Gateway có thể terminate TLS, xác minh token, áp quota, route và phát trace context chung. Các service bên trong vẫn cần resource-level authorization và chỉ tin identity metadata từ đường đã xác thực; không cho client tự đặt header “internal user” rồi vượt kiểm tra. Gateway là shared dependency nên cần capacity, HA, limits và rollout riêng.

      BFF (backend for frontend) tổng hợp dữ liệu phù hợp web/mobile/TV, giảm chatty client và giữ contract thân thiện với từng trải nghiệm. Nó khác việc nhồi mọi business workflow vào gateway: quyền và invariant nên ở domain owner, còn BFF quản lý aggregation/deadline. Hạn chế fan-out, batch các truy vấn và không để một endpoint gateway gọi cả hệ thống không giới hạn.

      Ở quy mô tổ chức, contract và error semantics tồn tại lâu hơn implementation. Có owner cho API, deprecation window, compatibility test và telemetry client version trước khi xóa field. Protocol quyết định cả vận hành: long-lived streams cần drain/reconnect budget khi deploy, không chỉ chọn thư viện gọi request.

      8. CORS, cookies, CSRF và authorization

      Origin gồm scheme, host và port; khác subdomain hoặc port có thể là cross-origin. CORS là chính sách browser cho script đọc response từ origin khác, không phải firewall bảo vệ backend khỏi curl hoặc request từ server. Một số request có thể đã được gửi trước khi browser chặn đọc response; side effect vẫn cần authentication/authorization và CSRF protection phù hợp.

      Cookie session được browser gửi theo cookie policy; cấu hình Secure, HttpOnly và SameSite theo nhu cầu sản phẩm. HttpOnly giảm script đọc cookie nhưng không thay authorization, và SameSite không nên bị hiểu là mọi origin/site đều tương đương. Với cookie-authenticated mutation, dùng CSRF token/origin checks và các biện pháp phù hợp với threat model.

      Credentialed CORS cần allowlist origin rõ ràng và response headers phù hợp; wildcard origin không dùng để cho script đọc credentialed response. Không phản chiếu mọi Origin không kiểm tra. Dù CORS đúng, API vẫn phải kiểm tra quyền trên conversation, order hoặc document theo actor thật; ID khó đoán không phải authorization.

      9. Timeout, retry và observability end-to-end

      Chia total deadline cho connect, TLS, upstream processing và response read; propagate remaining deadline xuống dependency. Retry chỉ trong tổng budget, ưu tiên một layer làm chủ để tránh retry multiplicative: 3 layer mỗi nơi 3 attempt có thể tạo 27 call tới dependency. Dùng exponential backoff, jitter, max attempts và idempotency cho side effect.

      Đo browser DNS/connect/TTFB/download, edge upstream wait và server trace gồm pool/query/service latency. Correlation/trace ID nối các hop; không log Authorization header, cookie hoặc secret trong URL. HTTP 200 với business error giấu trong body có thể làm success metric sai nếu SLI chỉ nhìn status.

      Contract tests cần duplicate submit, expired session, permission revoked giữa các trang, malformed cursor, slow stream và client disconnect. Load test có connection reuse và workload size thực; network error giả lập kiểm chứng cancellation không để backend tiếp tục công việc vô hạn.

      10. Câu hỏi và lời giải

      HTTP/2 có loại bỏ mọi head-of-line blocking không?

      Không. Nó multiplex HTTP streams nhưng vẫn dùng một ordered TCP byte stream; packet loss có thể ảnh hưởng nhiều stream cùng connection. HTTP/3 đổi transport sang QUIC stream semantics, nhưng shared congestion, server queue và application dependencies vẫn có thể gây chậm.

      DELETE trả 404 ở lần hai thì còn idempotent không?

      Có nếu intended effect vẫn là resource không tồn tại sau cả hai lần. Idempotency không yêu cầu response giống hệt. API có thể chọn 204 cho delete lặp để client đơn giản hơn, nhưng phải định nghĩa contract và tránh lộ resource ngoài quyền.

      CORS chặn rồi có chắc mutation chưa chạy không?

      Không. Có trường hợp browser gửi request nhưng không cho script đọc response; preflight có thể chặn trước một số request khác. Không suy luận business state từ thông báo CORS. Kiểm tra server state bằng actor được phép và giữ CSRF/authz đúng từ đầu.

      Một HTTP GraphQL request có phải chỉ tạo một DB query?

      Không. Resolver có thể tạo nhiều query, đặc biệt N+1 khi fetch mỗi child. Dùng batching/dataloader theo request scope, query cost/depth cap và authorization trên từng resource. Rate limit nên phản ánh work hoặc token/cost, không chỉ số HTTP request.

      Nên dùng WebSocket cho mọi API để nhanh hơn không?

      Không. HTTP request/response phù hợp phần lớn CRUD và tận dụng cache/tooling tốt. WebSocket có lợi khi hai chiều liên tục nhưng thêm connection state, reconnect, message routing và backpressure. Chọn theo interaction pattern và đo latency critical path.
