Batching & Speculative Decoding: protect latency and sampling correctness

Understand iteration scheduling, chunked prefill, fairness, split pools and speculative verification through four experiments covering latency, probability mass, draft costs and KV handoffs.

Optimizations preserve resource budgets, target semantics and user-visible deadlines.

  • Batch membership, token budgets and memory admission are related but distinct decisions.
  • Chunked prefill trades prompt-completion overhead for smaller decode gaps rather than guaranteeing hard latency bounds.
  • Average TPOT and individual inter-token gaps need separate measurement to reveal stuttering.
  • Exact speculative sampling preserves the target distribution through correct acceptance/correction, not identical sample paths at one seed.
  • Expected accepted tokens are not speedups; drafting, verification, memory and load all cost resources.
  • Disaggregation helps only when queueing, computation, transfers and capacity jointly fit SLOs.

1. Throughput, TTFT, TPOT and ITL

A replica serves sequences with varied lengths. TTFT runs from an agreed request boundary to the first visible token, including queues, routing, prefill and handoffs. TPOT commonly averages subsequent-token time for a request; ITL measures each gap. A good average TPOT can hide a long pause.

Token throughput, request throughput and goodput differ. If forty requests complete in ten seconds but only thirty meet both latency targets, observed goodput is three requests/second rather than four. State targets, traffic mix, arrivals, hardware/profile and measurement windows; benchmarks that omit queues may misrepresent the product.

2. Static, dynamic and continuous batching

Batch formation

  • Count/timeouts determine entry grouping.

Iteration membership

  • The engine changes selected work at safe iteration boundaries under budgets.

Output delivery

  • Streaming, buffering and bursts determine visible tokens separately from membership.

Static cohorts can retain membership until completion, leaving early-finished slots unavailable. Dynamic batching often forms entry cohorts by count/timeouts, while execution admission may remain cohort-based. Streaming need not wait for the cohort; delivery policy differs from batch membership.

Iteration scheduling revisits runnable membership after each model step, admitting new work within limits. It neither requires one allocator nor guarantees full utilization: arrivals, memory, shapes and overhead still matter. Paged KV supports flexibility but does not define iteration scheduling.

3. Chunked prefill and decode interference

A long colocated prefill can lengthen an iteration for existing streams. Chunking interleaves prompt work with decoding, often reducing long gaps at additional iteration/overhead cost and slower prompt completion. Token count is only a work proxy; context, shapes, kernels, precision and hardware affect timing.

Decode-first policies still need growth checks and admission caps, and strict decode-only scheduling can starve prefills. Unbounded prefill-first scheduling stalls existing streams. Reserve progress, use aging/deficits or separate traffic pools according to targets rather than absolute priority slogans.

4. Fairness, admission and deadlines

A guarded iteration

  1. Check runnable state

    Validate profiles, cancellation, deadlines and growth.

  2. Select bounded decodes

    Apply work budgets and tenant fairness rather than selecting everything.

  3. Allocate prefill progress

    Bound chunks and provide policy-defined progress.

  4. Run and commit

    Record timings/results and reconcile KV/lifetimes.

Make insufficient-budget policies explicit.

Before forming work, check lengths, quotas, priorities/deadlines and KV/growth capacity. If selected decodes exceed budgets, do not continue with negative remaining work; select bounded subsets, reschedule or apply overload policies. Account for preemption and its victim’s recomputation/transfer costs.

FCFS preserves arrival order but can block short jobs; short-first depends on estimates and can starve long work; strict priorities can starve lower tiers. Token budgets, deficits/aging and per-tenant/concurrent-length caps are tools rather than automatic fairness guarantees. Residency or token-seconds can matter beyond prompt counts.

5. Trace colocated, split and speculative paths

These are logical responsibilities that may share an engine. Split serving adds queues and state handoffs rather than only renaming services. Speculation commits verified output and rolls back rejected state before continuing. Draft and target KV cannot be interchanged arbitrarily because weights and architectures differ.

One scheduler, several kinds of work

Component map; the complete ordered request paths are explained below.

Trace colocated work, split pools, speculative verification and cancellation. Draft and target KV are not interchangeable state.

Chunked prefill on a shared replica

  1. Validate identity, bounds and deadlines.
  2. Admit under resource/fairness budgets.
  3. Allocate bounded prompt chunks alongside selected decode work.
  4. Update model/sequence state and lengths.
  5. Run selected decoding with measured kernel timing.
  6. Emit committed tokens and update request state.

Prefill/decode in separate pools

  1. Choose prefill workers using queue/locality evidence.
  2. Transfer compatible KV/context under limits.
  3. Validate destination state and ownership before activation.
  4. Decode after destination handoff and queueing.
  5. Stream output and measure TTFT separately from TPOT/ITL.

Draft and conditioned verification

  1. Choose draft length using measured acceptance/cost and memory.
  2. Score proposals at their conditioned prefixes with required proposal probabilities.
  3. Apply target sampling transforms and supported acceptance/correction.
  4. Commit accepted prefixes and discard invalid speculative state.
  5. Emit verified prefixes/corrections within stops and limits.

Reject and roll back the suffix

  1. The target evaluates proposals and may reject early.
  2. After the first rejection, discard tokens conditioned on that rejected prefix.
  3. Retain valid lengths/context and continue with correction-compatible state.
  4. Reschedule from committed context without draft-triggered external effects.

Cancel during an iteration

  1. Receive authenticated cancellations/deadline updates.
  2. Stop scheduling new work and account for completed work.
  3. Fence outstanding target/draft work at safe boundaries.
  4. Release or retain pages under references and kernel completion.

6. When should prefill and decode pools split?

Separate pools allow phase-specific tuning and reduce direct interference, at the cost of transfers, queues, buffering, placement and recovery. Prefill cache locality does not establish destination readiness. Route using end-to-end completion evidence rather than cache hits or compute time alone.

Transferred state needs compatible model/adapter, positions, formats/scales, partitions and ownership. Conversion/resharding may be needed, with completion confirmed before use. Pin buffers through cancellation/failures and define fallback; transfer queues do not automatically provide durable recovery.

7. Draft, verify, correct and commit

A speculative cycle

  1. Draft γ

    Generate proposals and required proposal probabilities.

  2. Conditioned verification

    The target evaluates each token’s preceding prefix.

  3. First rejection or bonus

    Correct the distribution or add a permitted bonus after full acceptance.

  4. Commit and reconcile

    Apply stops/limits, discard invalid KV suffixes and resume.

Commit only valid-prefix output.

A draft proposes tokens and a supported target run scores multiple conditioned positions. Verification uses the context before each token. After the first rejection, later proposals depend on a rejected prefix and cannot be retained merely because they appear plausible. Corrections/bonus tokens follow the selected algorithm and stop rules.

Accepted drafts still cost compute and memory: proposals, verification, temporary KV, logits and rollback consume resources. Loaded compute-bound batches may slow down. Maintain valid lengths/ownership in both models and stream only verified tokens without dispatching external effects from proposals.

8. Why does exact speculative sampling preserve a distribution?

Let P and Q be target/proposal distributions at the same conditioned prefix after relevant sampling transforms. Accept a Q-drawn token with min(1,P(x)/Q(x)), giving accepted mass min(P(x),Q(x)). On rejection sample from normalized positive P−Q, rather than arbitrarily resampling P. Accepted and correction masses then sum to P.

This is a distributional statement under the exact algorithm’s assumptions, not identical seeded token paths or a guarantee for every speculative heuristic. Greedy verification has its own contract. Sampling transforms, masks and penalties must match target semantics, and different tokenizers require supported alignment rather than concatenated identities.

The lab’s total variation distance is half the sum of absolute output/target probability differences. Zero means matching fixture distributions; eight percent does not mean eight percent of individual tokens are factually wrong. Probability distance differs from response-quality evaluation.

9. EOS, output limits and speculative KV rollback

An ideal cycle yields one to γ+1 tokens, but output limits and stops may terminate earlier. Do not emit bonuses after EOS, exceed limits to fill batches or count discarded proposals as delivered tokens. Stop strings can span token/chunk boundaries and need explicit buffering/usage semantics.

Scoring rejected suffixes does not commit their KV. Preserve accepted context, invalidate incorrect lengths and handle correction state correctly. Kernels, graphs, reference counts and cancellation need sound lifetimes. Name/version/evaluate relaxed acceptance separately instead of claiming exact target equivalence.

10. From acceptance to expected speedup

Under independent constant per-position acceptance and sufficiently long generations, E = 1 + α + … + α^γ tokens per target call, with E = γ+1 at α=1. Calls and workloads need not share this expectation. Acceptance varies with context, content, positions and policies, while stops truncate cycles.

Compare baseline token cost with cycle cost divided by E. Under constant verification T, drafting t_d and no overhead, S = T×E/(T+γ×t_d). Real verification can grow with draft length/load, while draft memory reduces active KV capacity. Single-stream optima need not maximize fleet goodput.

11. Choose proposal sources by contract

Separate models need memory, tokenization/sampling compatibility and lifecycle management. Prompt lookup can help repeated spans but may miss on other traffic. Feature/head methods require model-specific training, backends and verification; method names do not determine fixed acceptance or speedups.

Multiple-head/tree and feature-level proposals illustrate different draft mechanisms. Exactness depends on verification/acceptance modes and whether training changes the target backbone. Distinguish frozen targets, jointly trained targets and relaxed quality heuristics, evaluating against the promised baseline revision.

12. Adapt policies to workload and load

Scheduling latency

  • Track TTFT, ITL tails, queues and progress by traffic slice.

Scheduling efficiency

  • Track goodput per accelerator, wasted speculation and useful tokens.

Sampling correctness

  • Preserve target sampling, limits, tenant fairness and KV lifetimes.

Measure accepted lengths, proposal/discard counts, verification/draft time and memory by workload/profile. Global acceptance can hide differences. Include a no-speculation baseline, canaries and fallbacks. High load changes bottlenecks and requires measurement rather than universal on/off rules.

Use queues, TTFT, ITL, goodput and memory pressure alongside utilization. Split pools need balanced capacity and reserves on both sides; faster prefills cannot fix saturated decode queues or transfers. Cancellations/deadlines prevent stale requests from consuming future resources.

13. Failure review and validation

Load tests include length distributions, bursts, cancellation, slow clients, tenant mixes and profiles. User-facing boundaries include queues/transfers/streaming. Sampling tests cover finite distributions with zeros, identical/disjoint supports, conditioning and transforms; tolerances do not replace algorithmic correctness.

14. Questions with explanations and calculations

Does continuous batching keep every slot busy?

No. It permits membership changes per iteration, while arrivals, memory, shapes and overhead still determine occupancy. Output streaming is separate; static membership need not delay every visible token until the longest request ends. Inspect both admission and delivery contracts.

A long prompt stalls streams: what should be checked?

Correlate prefill admission with iteration durations and individual ITL spikes. Test bounded chunks with decode and prefill progress policies. The fixture’s 8K prompt, 1,024-token chunks and two streams give a 12 ms gap and 96 ms TTFT, versus a 68 ms monolithic gap/TTFT. Real workloads need measured trade-offs.

Why is resampling P after rejection not generally correct?

Accepted mass is already min(P,Q), so the remaining mass needs normalized positive P−Q. For P=(.6,.3,.1) and Q=(.1,.1,.8), acceptance is .3; resampling P on rejection produces (.52,.31,.17). Correct residual sampling restores P. Verification alone cannot fix incorrect correction rules.

Does unchanged output distribution mean identical seeded token strings?

No. Exact sampling preserves target conditional distributions under its assumptions, while random draw ordering and numerics can change individual paths. Greedy contracts differ. Correct conditioning, transforms, vocab alignment, stops and KV prefixes remain necessary; evaluate relaxed heuristics separately.

Does α = 0.8 and γ = 4 produce exactly 3.36 tokens per target call?

3.3616 is an expectation under independent constant acceptance and sufficient output budget. Calls emit integer counts and stops truncate them. Speed also includes cycle costs: the fixture’s 30 ms cycle and 20 ms baseline yield about 2.24×, before loaded goodput effects.

Why can larger drafts be slower than baseline?

Larger drafts add proposal/verification work, memory and discarded suffixes. Low acceptance or compute saturation can make cost per emitted token exceed baseline. Extra memory also reduces fitting sequences. Optimize measured goodput with a no-speculation fallback rather than one global acceptance rate.

Does splitting pools always improve both TTFT and TPOT?

No. Transfers and both queues can increase TTFT. With this fixture’s 4 GiB and 5 ms queues, split TTFT is about 198.2 ms at 32 GB/s and 97.6 ms at 128 GB/s. Only the faster split meets the stated pair of targets. Fleet goodput requires actual load/capacity measurements.

Is absolute decode priority fair?

It can protect current streams while starving new prompts. Use progress reservations, aging/deficits, tenant budgets and overload admission. Define preemption/recomputation for long or lower-priority work. Evaluate queue age and progress by workload/tenant rather than aggregate throughput alone.
