Thiết kế File Sync: chunks, revisions và offline conflicts

Đi từ bytes tới authoritative metadata và crash-safe device apply; thử delta upload, CAS parent revision và keep-both để hiểu cách đồng bộ đúng qua nhiều device.

Nhớ vòng đời của một thay đổi file

  1. Chuẩn bị bytes

    Chunk, verify, upload missing blocks và protect pending data.

  2. Commit revision

    CAS parent, atomic metadata/journal và retry result.

  3. Apply trên device

    Hint → replay → fetch → staged apply → cursor.

  4. Giữ dữ liệu qua lỗi

    Conflicts, offline retention, restore, GC và authorization.

Đọc theo thứ tự bytes → commit → replay → recovery, rồi mới tối ưu storage và fanout.

  • Uploaded bytes chưa phải committed file; protect blocks khỏi GC trước khi ACK metadata tham chiếu chúng.
  • File ID sống qua rename; revision, namespace cursor và local applied state có vai trò khác nhau.
  • CAS reject stale parent; preserve local edits và resolve idempotently thay vì silent overwrite.
  • Chunking tiết kiệm tùy edit/data; CDC có thể resynchronize nhưng không bảo đảm delta luôn nhỏ.
  • Notification chỉ hint; durable replay, client correctness, GC protocol và dedup privacy đều là phần cốt lõi.

1. File sync là ba bài toán gắn với cùng một invariant

Bytes

  • Chia chunk, resume và verify; chỉ truyền phần thực sự còn thiếu trong scope được phép.

Metadata

  • Stable file ID, parent revision, atomic head/version/journal và retry result.

Devices

  • Notification là hint; local DB, cursor và replay chịu trách nhiệm hội tụ sau crash/offline.

Đừng bắt đầu bằng “lưu file vào S3”. Bạn phải di chuyển bytes tiết kiệm, quyết định metadata/version nào được chấp nhận, và đánh thức nhiều device đang idle. Invariant trung tâm của baseline: một commit đã ACK không được trỏ tới bytes chưa durable hoặc bị GC thu hồi; một stale edit không được overwrite head mà không báo conflict. Durability luôn gắn với failure model, retention và recovery đã kiểm chứng, không phải lời hứa không bao giờ mất dữ liệu trong mọi thảm họa.

Baseline hỗ trợ upload/download, nhiều device, offline edits, revision history và shared folders; file có thể hàng chục GB và sync latency mục tiêu tính bằng giây khi network cho phép. Real-time co-editing kiểu Docs và full-text search nằm ngoài scope ban đầu. Không tự merge hai opaque binary files vì cả hai có cùng extension.

2. Logical bytes, delta bytes và idle devices là ba phép tính

Dùng ví dụ 50 triệu user, trung bình lưu 10 GB/user; 10 triệu DAU và 2 edit được sync/ngày. Giả sử file được sửa trung bình 1 MB và unique delta cần upload bằng 10% file, peak bằng 3 lần trung bình. Đây là giả định để tính, không phải mức tiết kiệm chunking luôn đạt. Dùng đơn vị thập phân: GB=10^9 B, PB=10^15 B.

Storage 500 PB là logical live data trước dedup, version history, compression, coding, metadata và backups. Nếu workload đo được dedup factor 1,25 thì unique live bytes là 400 PB, nhưng không được dùng factor đó cho mọi cohort. Bandwidth download còn nhân theo số device nhận thay đổi và sharing fanout; upload delta 2 TB/ngày không đồng nghĩa tổng egress chỉ 2 TB.

Dù write rate chỉ vài trăm/s trong ví dụ, 10 triệu device poll mỗi 30 giây tạo khoảng 333.333 request/s, phần lớn có thể rỗng. Long poll/WebSocket giảm empty polling nhưng tạo connection state và reconnect load. Tính metadata listing, journal page, block-check batches và hot shared namespace riêng; đừng kết luận metadata nhẹ chỉ từ file-edit RPS.

3. API phân biệt upload bytes với commit file

Mọi endpoint phải xác thực principal và namespace permission, có quota, batch/payload limit và capability hết hạn theo policy. Client-provided SHA-256 không chứng minh ownership hoặc quyền đọc; block-check chỉ trả existence trong dedup scope được phép. Upload service kiểm digest/length từ bytes thực, không tin filename hoặc hash do client khai.

Ví dụ dưới dùng JSON parentRev và trả application conflict 409. Nếu contract dùng HTTP If-Match thì failed precondition thường là 412; đừng trộn hai contract khi viết client. Retry commit dùng stable operation ID và payload fingerprint, trả đúng revision/result đã lưu; tái dùng ID với payload khác phải bị từ chối.

              4. Hai đường đi và một điểm quyết định sự thật

              Block path truyền immutable bytes qua block service/object storage. Metadata path quyết định tên, parent folder, head revision, tombstone và journal. Database giao dịch chia theo namespace là baseline thuận tiện vì có thể giữ file version, head, operation result, journal và outbox trong một transaction. Một shared folder có thể là namespace riêng được mount vào nhiều cây thư mục.

              Đường nét trong sơ đồ là logical calls, không bắt buộc mọi byte đi qua cùng API process. Upload/download có thể dùng scoped signed capability để đi trực tiếp object storage, miễn giữ authorization, verification và commit protection. Không route file GB qua metadata worker chỉ vì endpoint cùng domain.

              Bytes đi trước; revision và journal được commit cùng nhau

              Sơ đồ các component; các luồng request được giải thích đầy đủ theo thứ tự bên dưới.

              Bốn trace tách upload, commit, catch-up và stale edit. Metadata chỉ tham chiếu verified blocks còn được bảo vệ khỏi GC; notification chỉ là hint.

              Upload những block còn thiếu

              1. A gửi manifest candidate và hỏi missing blocks trong namespace được phép.
              2. Check không tiết lộ existence ngoài dedup scope đã chọn.
              3. Trả missing set và scoped upload capability; đây chưa là commit file.
              4. Upload unique missing blocks; server kiểm bytes, digest và length.
              5. Lưu bền immutable objects và bảo vệ bằng pending pins.
              6. Storage đạt durability boundary; receipt gắn với object version/scope.
              7. A nhận receipts để commit; upload xong không tự đổi file head.

              CAS head và append journal

              1. Commit op-42 cho file-main, parentRev=5 và ordered block list.
              2. Chuyển command với principal; kiểm permission hiện tại, không chỉ lúc upload.
              3. Transaction kiểm retry result, CAS revision và durable block protection; ghi version 6 + head + journal + outbox.
              4. Commit thành công theo durability contract; recovery protocol giữ block reachability.
              5. ACK cùng revision/cursor hint. Mất ACK thì retry trả cùng result, không tạo revision mới.

              Hint, journal và crash-safe apply

              1. Relay đọc outbox đã commit, có thể phát trùng.
              2. Namespace changed. B vẫn periodic reconcile nếu hint cuối bị mất.
              3. Đọc journal sau applied cursor, có pagination và ACL hiện tại.
              4. Đọc committed changes hoặc trả cursor expired/resnapshot theo retention.
              5. Trả ordered entries và opaque next cursor trong đúng scope.
              6. Tải những block local chưa có bằng authorization cho version tương ứng.
              7. Đọc đúng immutable block version; verify integrity khi nhận.
              8. Trả bytes; timeout không được advance applied cursor.
              9. Stage file, apply idempotently, recover filesystem/local DB rồi checkpoint cursor.

              Offline edit không được overwrite âm thầm

              1. B cũng sửa từ parentRev=5 và commit sau A.
              2. Commit có stable ID khác; không phải retry của A.
              3. Current head đã là 6; CAS parent 5 không còn hợp lệ.
              4. Trả conflict, không ACK thành công và không bỏ local bytes.
              5. Giữ pending edit, hỏi user hoặc thực hiện keep-both bằng operation mới idempotent.
              Device A
              Giữ local DB, pending operation và bytes chưa đồng bộ. Retry dùng cùng operation ID.
              Authenticated API
              Kiểm principal, namespace, quota và giới hạn batch/payload. Không dùng hash như access token.
              Block service
              Kiểm integrity và scoped existence; trả durable receipt/pin cho commit protocol.
              Private block store
              Immutable bytes theo dedup/encryption scope. GC phải phối hợp với pending pins và committed reachability.
              Metadata service
              Kiểm parent revision, namespace permission và commit identity; serialize thay đổi trong namespace boundary.
              Metadata + journal
              File head, version, operation result và journal entry trong cùng transaction. Outbox/hint được tạo bền cùng commit.
              Change notifier
              Coalesce namespace hints, long poll hoặc WebSocket. Không giữ file bytes hay thay journal.
              Device B
              Replay journal từ applied cursor, tải missing blocks, staged apply rồi mới checkpoint.
              Local staging + DB
              Giữ pending edits trước resnapshot; recover apply sau crash theo filesystem semantics.

              5. Manifest là ordered chunks; dedup không làm mất thứ tự

              Một version lưu danh sách chunk IDs theo thứ tự, mỗi phần có length và có thể offset, cộng tổng size/checksum theo contract. Cùng một chunk có thể xuất hiện hai lần trong file; storage có thể giữ một bản bytes nhưng manifest vẫn giữ cả hai vị trí. Missing set chỉ upload unique blocks chưa tồn tại/được phép reuse trong scope, không xóa repeated positions của file.

              Chunk nhỏ thường giảm byte phải truyền cho edit cục bộ nhưng tăng hash/index entries, manifest size, RPC/metadata và GC work. Chunk lớn giảm bookkeeping nhưng có thể retransmit nhiều hơn. Chọn bằng workload file size/edit patterns, CPU, memory, RTT và block-storage capabilities; không có kích thước tối ưu chung. Hash cache giúp tránh đọc lại khi có bằng chứng an toàn; mtime + size đơn lẻ không đủ vì timestamp có thể coarse hoặc được giữ nguyên.

              6. Fixed boundaries, CDC và file bị re-export

              Với fixed chunks 4 MiB, một byte được thay tại chỗ trong file không đổi size thường chỉ làm đổi chunk chứa byte đó; byte gần ranh giới vẫn thuộc đúng một chunk theo offset. Chèn một byte ở đầu làm dịch boundaries phía sau và có thể đổi gần như toàn bộ chunks. Không đồng nhất hai loại edit này. Demo dùng ASCII để thấy bytes và boundaries trực tiếp.

              CDC chọn cut points từ content với min/max chunk bounds; sau insertion có thể tìm lại boundaries cũ ở vùng phía sau. Không bảo đảm “chỉ chunk đầu đổi”: phụ thuộc data, rolling-window state, min/max rules và edit location. Rolling fingerprint để tìm boundary khác cryptographic digest để address/verify chunk. Đo dedup ratio cùng CPU throughput, tail chunk distribution và memory; không suy từ một ví dụ rằng CDC luôn thắng.

              Media editor re-export, compression stream hoặc randomized encryption có thể thay gần như mọi byte dù user chỉ sửa một chi tiết. Đừng hứa upload 4 MiB cho mọi lần sửa video 2 GB. Delta benefits còn đến từ copied files và shared versions; encrypted client-side designs phải xác định chunking trước/sau encryption và privacy policy.

              7. Từ uploaded block tới committed file: lấp khoảng hở với GC

              Thứ tự publish một file version

              1. Prepare bytes

                Verify digest/length và persist immutable blocks dưới pending protection.

              2. Commit truth

                CAS parent, version/head/result/journal/outbox trong metadata transaction.

              3. Recover protection

                Chuyển reachability theo protocol; collector không được xóa bytes còn được bảo vệ.

              4. Notify và reconcile

                Hint có thể trễ; journal và periodic catch-up giữ device hội tụ.

              Mỗi bước phải có retry identity, timeout và recovery; không giữ row lock trong suốt upload dài.

              Kiểm “block tồn tại” rồi commit sau đó không đủ: GC có thể xóa block trong khoảng giữa hai bước. Baseline dùng durable pending pins/receipts có expiry và protocol chuyển sang committed reachability có recovery. Pin phải còn hợp lệ tại commit, và collector phải đồng bộ với barrier/epoch hoặc metadata mà commit sử dụng. Một safety delay chỉ có tác dụng nếu bạn chứng minh giới hạn upload/commit/recovery tương ứng.

              Không có transaction SQL tự động bao trùm object store. Thiết kế một protocol: persist verified block + pin; validate protected receipts; commit metadata/head/journal và durable reachability intent; reconciler hoàn tất protection handoff, collector tôn trọng cả pending và committed intents. Nếu chưa triển khai protocol đó thì không được trình bày vài lệnh SQL như bằng chứng không thể có dangling head.

              8. Stable identity tách khỏi path và các loại cursor

              Dùng file_id ổn định thay vì lấy path làm identity duy nhất; rename đổi parent/name và journal entry, không upload lại bytes. Một namespace có file tree, version history và change order riêng. Shared mount trỏ tới namespace gốc; move qua hai namespace có thể cần workflow copy/delete với semantics rõ, không giả có transaction toàn cục miễn phí.

              File revision trả lời “nội dung/version nào của file”; journal cursor trả lời “device đã apply change feed tới đâu trong scope”; chúng không thay thế nhau. Opaque cursor có thể bao gồm epoch, pagination/filter state; không yêu cầu client đếm số nguyên liên tiếp khi ACL/filter/compaction làm visible entries không liên tục. Nếu dùng contiguous positions, server phải định nghĩa skip/abort semantics.

              9. Journal replay cần snapshot barrier và checkpoint đúng lúc

              Bootstrap phải nối initial tree snapshot với một journal position nhất quán. Chọn snapshot tại barrier/cursor, rồi replay changes sau barrier; nếu snapshot dài được phân trang, giữ consistency token hoặc thuật toán reconcile chống bỏ sót rename/delete giữa các page. “List hết rồi lấy cursor hiện tại” có thể bỏ qua một change xảy ra khi đang list.

              Device replay theo order cần thiết, fetch blocks, verify, staged apply và ghi durable local state trước khi advance applied cursor. File system và local DB thường không có cùng transaction: dùng recoverable operation log, temp file và atomic replacement khi platform hỗ trợ, cùng fsync/directory persistence theo durability target. Sau crash phải quyết định an toàn apply lại hoặc hoàn tất, không chỉ ghi cursor trước để nhìn có vẻ nhanh.

              Long poll/WebSocket chỉ nói namespace changed; coalesce được nhiều event. Nếu hint cuối bị mất trong khi connection vẫn sống, chỉ chờ reconnect sẽ làm device stale mãi: cần periodic journal poll, watermark check hoặc một recovery mechanism có bound rõ. Cursor hết retention trả explicit resnapshot; bảo vệ pending local edits trước khi reconcile lại remote snapshot.

              10. Hai offline edits: reject stale parent và giữ cả hai

              A và B cùng đọc revision 5. A commit thành 6; B đến sau với parent 5 phải nhận conflict thay vì overwrite. “First” ở đây là commit serialization order tại authority, không phải đồng hồ device. Upload blocks của B có thể đã xong nhưng chưa thay head; client giữ pending bytes và dùng explicit resolution policy.

              Keep-both tạo conflict copy với file ID mới và tên không đụng nhau theo filesystem policy. Resolution operation cũng idempotent để retry không tạo mười copies. User có thể so sánh/merge bằng ứng dụng hiểu format rồi commit một version mới. Silent overwrite làm mất update ở current head; có thể vẫn còn version history, nhưng đó không phải lý do bỏ conflict signal. OT/CRDT là lựa chọn ở application model phù hợp, không tự merge mọi binary.

              11. Client đúng phải xử lý rename, placeholder và partial write

              Bytes chưa sync

              • Không xóa khi resnapshot hoặc khi remote delete đụng local edit.

              Apply có recovery

              • Staged operations có durable identity và đường hoàn tất/replay sau crash.

              Rollout client

              • Canary, model-based tests và kill switch cho bug gây destructive reconciliation.

              Filesystem watcher là hint và có thể coalesce/drop events; cần local durable index và reconciliation scan. App có thể ghi temp rồi rename, mở file khi hash đang chạy, hoặc giữ mtime/size khi bytes đổi. Kiểm file identity và stability của snapshot được hash; nếu thay trong lúc đọc thì retry theo policy. Không suy “không có watcher event = server và disk giống nhau”.

              Case-insensitive volumes, Unicode name normalization, reserved names, symlink và path traversal cần rules rõ cho mỗi platform. Remote a.txt và A.txt có thể không cùng tồn tại trên một volume; tạo representable conflict name hoặc báo lỗi có thể phục hồi. Không follow symlink ra ngoài sync root một cách mù quáng. Rename dựa trên stable ID giúp tránh hiểu thành delete + upload toàn file.

              Selective sync và online-only placeholder không phải user delete. Tombstone từ remote khác file chưa tải; local state phải phân biệt hydrated, placeholder, excluded, pending edit và deleted. Khi nhận remote delete nhưng local có unsynced edit, bảo vệ local content rồi resolve thay vì xóa thẳng. Tombstone retention/cursor expiry phải được kiểm với device offline lâu.

              12. History, restore và GC phải cùng hiểu reachability

              Block còn được current head, retained versions, pending uploads/commits hoặc backup policy tham chiếu thì không thể thu gom chỉ vì file path đã delete. Reference counting cần idempotent increment/decrement và recovery cho lost/duplicate events; mark-and-sweep cần consistent reachability barrier/epoch. Chọn và chứng minh một protocol thay vì chỉ ghi “GC sau 24 giờ”.

              Restore tạo head revision mới và journal event trỏ tới manifest cũ còn giữ bytes, không giảm revision counter hoặc rewind cursor toàn namespace. Có thể rẻ về metadata nhưng cold-tier bytes phải hydrate, authorization vẫn phải kiểm và storage reads vẫn tốn thời gian. Nếu version đã hết retention/bytes bị xóa theo policy thì không hứa restore được.

              3× replication dùng ba bản bytes; coding 10 data + 4 parity có overhead nominal 1,4× trước metadata/repair/headroom. Với 500 PB unique bytes, arithmetic là 1.500 PB so với 700 PB. Không suy ra “durability tương đương” từ overhead: placement, correlated failures, repair time, corruption detection và degraded-read latency mới quyết định reliability. Tier old versions cần đo access distribution, restore SLO và cost, không gán một mốc ngày đúng cho mọi workload.

              13. Dedup privacy, shared folders và hot namespaces

              Global dedup/existence APIs có thể tạo oracle: attacker đo xem một content đã được người khác lưu chưa. Per-user/tenant scope, authorization/proof-of-possession protocols phù hợp và traffic policy có trade-off bandwidth/storage; chỉ biết hash không đủ để claim/download file. Convergent encryption còn có confirmation/dictionary risks với predictable content, không phải bản vá privacy chung. Randomized encryption, tenant keys, rotation và recovery phải được thiết kế cùng dedup policy; không tự invent crypto.

              Shared folders là authorization boundary sống: kiểm ACL khi commit, journal page và block download; revoke giữa upload và commit phải bị xử lý. Signed capability cần scope/expiry phù hợp, nhưng không thể thu hồi bytes recipient đã tải. Encryption-at-rest không đồng nghĩa E2EE; E2EE đổi sharing/key recovery, content scanning và dedup scope.

              Shard metadata theo namespace giúp giữ transaction local nhưng một team folder rất nóng vẫn có owner/order bottleneck. Batch/coalesce notifications, bounded journal pages, admission/quota và fair scheduling giúp trước khi tách namespace. Nếu cần partition một namespace thì phải định nghĩa lại order, rename/move atomicity và cursor; consistent hashing đơn thuần không tạo cross-shard transaction. Failover home region cần fencing và durability/RPO contract, không cho hai writer tự cấp cùng head revision.

              14. Kiểm thử từ bytes được ACK tới file xuất hiện trên disk

              Đo upload-to-commit, commit-to-device-applied, pending operation age, journal lag, stale-parent conflicts, integrity failures, orphan/pin age, GC backlog và restore success/time. Tách no-network, quota, disk full và denied permissions khỏi server errors; đừng coi request 200 là đã sync xong nếu filesystem apply còn thất bại. Theo dõi các metric theo client version/platform/namespace size để phát hiện rollout regression.

              15. Câu hỏi phỏng vấn và lời giải theo invariant

              Mỗi câu trả lời nên nói rõ bytes, identity, ordering boundary và recovery. Thử thay một assumption rồi kiểm lại guarantee thay vì liệt kê object store + Redis + queue như một đáp án hoàn chỉnh.

              Sửa một byte trong file 2 GB thì upload bao nhiêu?

              Nếu là overwrite tại chỗ và fixed 4 MiB chunks, thường một chunk đổi; cần upload chunk đó nếu server chưa có trong scope, rồi commit manifest. Nếu insertion ở đầu, boundaries dịch nên nhiều chunks có thể đổi. CDC có thể resynchronize nhưng không bảo đảm chỉ một chunk. Media re-export có thể rewrite toàn file.

              Hash cache dựa vào mtime và size có bỏ sót bytes đổi không?

              A và B cùng commit parentRev=5 thì ai thắng?

              Authority serialize CAS: commit đầu được nhận trở thành 6, commit stale còn lại nhận conflict. Clock device không quyết định. Giữ pending local bytes; keep-both tạo file ID mới bằng operation idempotent hoặc user merge bằng ứng dụng hiểu format.

              Có thể check block rồi transaction metadata là đủ tránh missing bytes chưa?

              Chưa. GC có thể xóa ở giữa. Cần protocol pending pins/protected receipts và durable reachability handoff với collector/reconciler; transaction SQL không tự bao object store. Test crash và expiry đúng điểm giữa các bước.

              Notification bị mất thì journal có tự làm device bắt kịp không?

              Journal giữ authority nhưng device vẫn phải đọc nó. Nếu hint cuối mất khi socket sống, cần periodic poll/watermark hoặc recovery trigger có bound. Khi đọc, fetch/verify/apply rồi checkpoint; cursor hết retention thì resnapshot và giữ local pending edits.

              Rename file lớn có cần upload lại toàn bộ không?

              Không nếu identity ổn định và bytes không đổi: update parent/name và journal với concurrency rules. Path không nên là identity duy nhất. Cross-namespace move, filename collisions và filesystem case/Unicode rules có semantics riêng cần giải thích.

              Global dedup giúp tiết kiệm thì cứ bật cho mọi tenant được không?

              Không tự động. Existence/timing có thể lộ content presence; digest không chứng minh quyền đọc. Chọn scope, encryption và authorization theo privacy model. Convergent encryption không xóa confirmation/dictionary risk; cân bandwidth/storage với isolation.

              10+4 coding có durability giống 3 replicas không?

              Không kết luận được từ số shard. 1,4× và 3× là storage arithmetic; reliability phụ thuộc placement, fault correlation, repair, scrubbing và operational errors. Test degraded reads/restore SLO cùng cost trước khi chọn.

              Restore revision cũ có nên giảm head revision về số cũ không?

              Không. Tạo revision mới tham chiếu manifest cũ còn retained và append journal event. Điều này giữ monotonic history/cursor semantics; check authorization và bytes availability, tính cả cold-tier restore latency.
