Prompting & Structured Output: contracts, schemas and tool boundaries

Manage prompts as versioned interfaces; understand few-shot examples, token masks, response envelopes, validation, bounded repairs and code-authorized tool execution.

A request crosses several contract boundaries

  1. Assemble

    Pin revisions and input provenance.

  2. Generate

    Use supported constraints and explicit budgets.

  3. Validate

    Check envelopes, parsing, schemas and task rules.

  4. Consume or authorize

    Use typed data, scoped tools, effects/receipts and audits.

Successful JSON parsing does not transfer authority from model text to applications.

  • Prompts participate in contracts with inputs, owners, revisions, consumers and evaluation gates.
  • Roles/delimiters clarify instructions/data without replacing authorization or eliminating injection.
  • Syntax, supported schemas, source truth and permissions are distinct checks.
  • Grammar masks filter pieces using parser state; envelopes still handle truncation/refusal.
  • Tool calls propose actions; effects need scoped authorization, validation and durable idempotency.
  • Greedy decoding, voting and retries do not automatically establish correctness or determinism.

1. Prompts are versioned interfaces

Prompt-contract lifecycle

  1. Registry

    Define ownership, immutable revisions and interfaces.

  2. Evaluation gate

    Test common, edge and untrusted-data cases.

  3. Canary

    Bound traffic and observe quality/cost with rollback.

  4. Observe

    Trace revisions, attempts and outcomes.

Version behavior rather than string literals alone.

Prompt packages contain instructions, templates, examples, tools, output contracts and failure policies. Model revisions, tokenizers/templates, schema backends and sampling also affect behavior. Versioning instructions alone is insufficient for reproducibility or auditing. Store immutable revisions, ownership, rationale and evaluation suites.

Record contract identifiers/configuration by request and attempt without automatically logging sensitive inputs. Small edits can alter many task slices. Use offline evaluations, bounded canaries, thresholds and rollback; multi-client migrations need compatibility and explicit deprecation.

2. Roles and trust boundaries

Privileged rules

  • Version instructions/tool scope in server-controlled templates.
  • Exclude secrets unnecessary for the task.

Task data

  • Bound user/retrieved/tool data and retain provenance.
  • Quote/delimit for clarity while retaining untrusted status.

Execution authority

  • Backends verify principals, resources and actions.
  • Models propose tools/arguments without granting authority.

Chat APIs can expose system/developer, user, assistant and tool channels with contract-specific naming/priority. Place durable instructions in supported privileged channels; treat user text, retrieved documents and tool results as untrusted data. Escaping delimiters does not make them privileged instructions.

Delimiters, typed templates and provenance help distinguish tasks/data and support debugging. They are neither sandboxes nor guarantees against document-borne instructions. Escaping avoids delimiter collisions but injection is a broader semantic-trust problem. Applications control secrets and privileged tools rather than trusting a model’s permission claims.

3. Zero-shot, few-shot and dynamic examples

Zero-shot uses instructions without demonstrations; few-shot adds contextual labeled examples without weight updates; dynamic few-shot retrieves from approved pools. Examples can clarify labels, formats and abstention but consume context and can encourage irrelevant copying. No example count is universally optimal.

Cover ambiguous, negative and edge cases without leaking test answers. Retrieved examples need tenant access, freshness and separation from evaluations. Compare zero/fixed/dynamic approaches on matched suites and budgets rather than assuming retrieval wins. Define units, unknown/null policies and field meanings instead of forcing guesses.

4. Explanations and reasoning need measurable goals

Some multistep tasks benefit from intermediate demonstrations/planning, but not every model/call needs a step-by-step instruction. Explicit explanations cost tokens/time and can rationalize wrong answers. Request concise justifications or externally verifiable evidence when useful, keeping machine-readable final contracts distinct.

Measure task success, evidence validity and latency rather than explanation length. Generated rationales are neither proofs nor execution authority. Prefer accurate lookups/parsers/rules when they solve the task without probabilistic generation.

5. Structural guarantees are separate from truth

Asking for JSON is an instruction; JSON-constrained modes target syntax; schema-constrained decoding enforces supported grammar/schema subsets. Names and guarantees vary by backend/version. Test keywords, enums, extra fields, nullability and envelopes. Refusals, limits, cancellation and transport failures still need handling outside the domain schema.

A closed status can match syntax/schema while contradicting an open source ticket. Schemas can express some rules but do not automatically possess external state or authority. Types clarify downstream code, while correctness needs evidence, domain checks, evaluations and explicit unknown/abstention behavior.

6. Token masks follow generated prefixes

Matchers track generated prefixes and permit pieces compatible with completion. Disallowed logits can become −∞ before sampling/renormalization. Pieces can span quotes, commas and following keys rather than matching individual grammar terminals. Tokenizer bytes, escaping, padded vocabularies and EOS must match the engine; compilers/caches also consume time and memory.

The lab uses six exact strings instead of a full schema compiler. Observe pieces spanning boundaries, compare free/masked generation and shorten budgets to distinguish valid prefixes from complete output. Scripted greedy logits are not benchmarks; local masks demonstrate structure rather than truth or universal global conditional-sampling guarantees.

7. Specify schemas and parsing precisely

Properties describe fields without requiring them; required makes presence mandatory. additionalProperties:false rejects unknown fields within its schema scope. Null differs from missing. allOf does not simply merge object declarations; oneOf requires exactly one matching branch, anyOf at least one. Pin dialects and supported subsets before using recursive/complex combinations.

Strict JSON excludes preambles/fences, NaN/Infinity and trailing commas. Duplicate keys have inconsistent parser behavior; rejecting them requires detection before object conversion loses duplicates. Bound bytes, depth and arrays before expensive validation. Do not silently change contracts through arbitrary brace-based salvage.

9. Trace prompt-platform boundaries

Assemblers combine approved instructions with bounded data; consumers receive validated typed results. Tool dispatch has a separate authority boundary and repairs have separate budgets. Rollout belongs to evaluation/control planes rather than models rewriting production prompts after each error.

From prompt revisions to outputs and authorized effects

Component map; the complete ordered request paths are explained below.

Trace extraction, tools, bounded repair, incomplete/refused outputs or rollouts. Application code enforces trust boundaries; prompt delimiters do not.

Structured extraction

  1. Validate typed inputs/principals and pin task contracts.
  2. Resolve exact prompt/schema/model/template revisions.
  3. Attach provenance and bounded untrusted data to appropriate channels.
  4. Generate within budgets using supported constraints.
  5. Inspect outcomes before treating text as domain JSON.
  6. Parse intended complete payloads and validate types/rules.
  7. Deliver typed results or explicit fallbacks/errors.

From tool proposals to effects

  1. Models propose tool names/arguments without execution authority.
  2. Validate completion/call identity, schemas and business constraints.
  3. Authorize the principal/resource/action in server code.
  4. Check operation identity/versions and atomically commit effects/receipts under the transaction contract.
  5. Return scoped results with call identity; replay does not create a new effect.

Validation failures and bounded repair

  1. Classify errors, redact unnecessary data and check remaining budgets.
  2. Supply allowed repair context without expanding tools or privileges.
  3. Run a bounded new attempt under the same logical task contract.
  4. Recheck outcomes rather than assuming repairs are valid.

Truncation or refusal

  1. Classify limits, refusals and cancellations separately.
  2. Choose bounded retry/context reduction/fallback without arbitrary salvage.
  3. Return explicit errors/fallbacks when no validated result exists.

Version and roll out prompts

  1. Evaluate candidate revisions on pinned representative/adversarial cases.
  2. Approve canary/rollback gates using quality, cost and error evidence.
  3. Resolve immutable approved revisions and record schema/tool contracts.

10. Function calling exposes proposal interfaces

Tool definitions describe names, purposes and schemas for proposals. Dispatchers allowlist names/versions, validate complete arguments, bind verified principals and enforce resource permissions, limits and state preconditions. An owner-only description is guidance rather than backend enforcement. Tool results remain untrusted model context.

Effects need stable operation identity and backend-enforced idempotency. Arbitrary model-invented keys do not deduplicate retries: define scope, fingerprints, durable results, expiry and effect atomicity. External effects need cooperating idempotency/reconciliation for ambiguous outcomes. Do not execute partial streamed arguments or unverified drafts.

11. Bound repairs using failure categories

A loop with a stopping boundary

  1. Classify

    Distinguish envelope, syntax, schema, business and authorization failures.

  2. Budget

    Check remaining time, tokens, attempts and cost.

  3. Permitted repair

    Repair eligible errors using scoped context.

  4. Revalidate or stop

    Reapply boundaries or return explicit fallbacks/errors.

Repairs cannot expand authority or bypass checks.

Structural error

  • Parsing/schema failures can enter permitted repairs with bounded errors and required schema revisions.
  • Revalidate envelopes and domain rules after repairs rather than trusting a claim that the issue was fixed.

Incomplete / refusal

  • Inspect finish reasons and remaining time/token budgets, then choose retries, smaller scopes or typed fallbacks under policy.
  • Refusals are not domain objects missing braces; do not convert them into empty successes.

Business / authorization denial

  • State conflicts may require fresh evidence; permission denials preserve authority boundaries.
  • Do not retry by changing callers, bypassing blockers or inventing keys to force repeated effects.

Policies can permit bounded repairs for structural failures using sanitized errors/context without new privileges. Blind retries must not bypass business/authorization denials. Limits may need smaller scopes or permitted budgets, while refusals need distinct handling. Bound total deadlines/tokens/costs and measure repair success rather than promising one repair suffices.

After exhaustion, return typed errors, deterministic fallbacks, quarantine/review or abstention as appropriate. Avoid batch crashes, silent success defaults and unauthorized repair/shadow tool effects. Preserve reasons/attempts to distinguish quality failures from unavailable engines or incompatible schemas.

12. Temperatures, seeds and caching do not establish truth

Greedy decoding depends on engine contracts; numerical differences, near ties, batching or revision changes can alter outputs. Seed semantics are backend-specific rather than universally reproducible. Pin configurations and measure variation, controlling execution environments when stronger reproducibility is required.

Caches can improve repeatability but need tenant/access scope, meaning-preserving input identities, relevant revisions and data freshness. Unsafe normalization or cross-tenant reuse can corrupt meanings or leak outputs. Voting costs resources and can repeat correlated errors rather than replacing evidence or permissions.

13. Evaluate and canary prompt changes

Evaluate normal, ambiguous, negative, missing/null, long, multilingual and injected inputs, unsupported schemas, refusals, limits and retries/cancellation. Separate structural rates from field/source accuracy, abstention, unauthorized proposals/executions, tool correctness, cost and tails. Perfect schema rates cannot hide semantic regressions.

Call sites need typed adapters and exact revisions, with migrations that preserve label meanings. Bound canary traffic/costs, use slice-level gates and retain approved rollbacks. Trace revisions and attempts under privacy limits without exposing secrets/credentials. A prompt platform is a software lifecycle around a probabilistic component.

14. Questions with worked answers

Where should invalid JSON crashes be addressed?

Use supported constraints where appropriate while keeping consumer envelope, syntax, schema and domain checks. Bound repairs and use typed fallback/quarantine, measuring field accuracy separately from structure. Visible syntax failures do not describe all quality problems.

Why can a valid prefix fail JSON parsing?

A viable prefix can still end early due to budgets/cancellation. Check completion envelopes rather than consuming partial objects, and allow EOS only under compatible matcher states.

Does escaping ticket text prevent prompt injection?

Escaping/delimiters help presentation rather than guaranteeing instruction adherence. Preserve provenance, restrict tools and enforce permissions so effects remain bounded even when model behavior is manipulated.

Do properties declarations require fields?

No. required checks presence, additionalProperties controls unknown fields within scope, and null requires allowed typing. Pin dialect/backend support and test combinations rather than treating allOf like object spread.

Is a schema-valid tool call ready to execute?

Not yet. Bind verified principals, allowlist tools/versions and check permissions, state, limits and operation identity. Proposals do not grant authority; partial/discarded attempts cannot trigger effects.

How should a lost commit response be retried?

Use the same scoped logical key/fingerprint to obtain durable results. Effects/receipts need atomicity or cooperating external reconciliation. New keys bypass deduplication, while reused keys with changed arguments must be rejected.

Are greedy decoding and a seed enough for exact-output tests?

Not universally. Pin configurations and verify backend/environment guarantees. Test semantic/domain properties when token identity is not contracted; caches do not repair wrong answers or stale data.

How would fifty call sites migrate to a prompt registry?

Inventory consumers, define typed versioned contracts and baseline evaluations, then add adapters/capability checks. Migrate cohorts through canaries with tracing/rollback and slice-level measurements rather than merely moving strings into a database.
