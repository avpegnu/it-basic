Questions about publication, durability and lifecycle

1. Define object semantics before disk layouts

Metadata plane

  • Keys, versions, heads, indexes, permissions and publication state.

Data plane

  • Immutable fragments, verified writes, reads and repair.

Lifecycle

  • Reader/upload pins, retention, migration and fenced GC.

The baseline includes buckets/keys, PUT/GET/HEAD/DELETE, ranges, prefix listing and multipart uploads. Immutable generations make overwrites new bytes followed by head changes. This is not a POSIX filesystem with implicit append/rename/locking or arbitrary cross-key transactions. Define object/part sizes, metadata limits, throughput, consistency, retention and restore latency for the chosen backend. This is an educational platform rather than a private cloud implementation.

Durability, availability and consistency are distinct. Recoverable bytes do not imply reachable APIs, and strong metadata cannot restore lost data. Replica counts, AFRs or coding formulas do not prove durability targets. Models need correlated failures, repair windows, software/deletion risks and operational evidence; the calculations below are conditional sizing/availability arithmetic.

2. Object counts and bytes create separate capacity problems

Assume decimal 100 PB logical data, one-MB average objects and one-KB metadata. This gives a hundred billion objects and roughly a hundred TB of metadata before indexes, replicas and history. Triple replication needs 300 PB payload; MDS 8+4 needs 150 PB. Ignoring reserves/overhead, twenty-TB disks imply fifteen thousand versus 7,500 disks. At an assumed two-percent AFR, 7,500 disks average about 0.41 failures/day, not an object-loss probability or independence guarantee.

Add free-space reserves for repairs/compaction, skew, placement, rebuild backlogs, uploads and temporary tier copies. Tiny objects stress requests/indexes/metadata differently from large bandwidth-heavy objects. Averages miss tails: measure sizes, accesses, operation mixes, ranges and hot keys. EC saves capacity while adding encoding, decoding and repair work.

3. APIs expose checksums, preconditions and outcomes

The teaching API uses its own namespace; actual S3-compatible implementations must follow protocol-specific wire/auth/encoding/limits. Signed requests or presigned grants are scoped, expiring capabilities whose URLs need protected logs. Conditional writes prevent silent lost updates. ETags are contract-specific validators rather than universal whole-object MD5s or identities across upload modes.

            4. Publication and recovery span both planes

            Metadata determines existence; data nodes provide verified immutable fragments. Placement maps carry epochs and failure domains rather than merely reachable hosts. Uploads, readers and migrations participate in lifecycle. Stateless API instances can scale, but underlying state needs authority and recovery. The traces describe a logical protocol rather than hiding atomicity inside a metadata-write arrow.

            Prepare bytes before publishing metadata

            Component map; the complete ordered request paths are explained below.

            PUT and metadata commit

            1. Send bytes, checksums and expected ETags/generations under the chosen API.
            2. Authorize tenant/bucket/key and encryption use.
            3. Allocate an immutable object ID and reservation epoch.
            4. Stream/encode, complete checksum validation and reach durable placement thresholds.
            5. Conditionally publish a sealed manifest while its reservation remains valid.
            6. Commit head/version and authoritative key indexes under the contract.
            7. Return final success after commit; lost responses require reconciliation.

            GET pins an immutable generation

            1. Send GET/range requests with authorization context.
            2. Resolve immutable versions without violating consistency through stale caches.
            3. Reader pins/leases or epochs protect the resolved version.
            4. Read sufficient verified fragments with scheme-dependent range optimizations.
            5. Return one generation and validate range/full-object checksum semantics.

            Complete multipart publication

            1. Upload independently identified parts without restarting whole objects on retries.
            2. Track tags/checksums and sessions while retaining pins.
            3. Prepare part fragments under durability contracts.
            4. Validate ordered manifests/tags/checksums/head preconditions before publication.
            5. Commit the object and retained completion result in this platform model.

            Repair without changing the logical object

            1. Scrubbing detects known missing/corrupt fragments and selects enough valid survivors.
            2. Allocate replacement targets under the current placement epoch.
            3. Reconstruct, verify and durably write replacements.
            4. CAS placement generations without overwriting newer repairs.
            5. Reclaim old fragments only after reachability/reader/migration checks.

            Migrate and clean up

            1. Copy or re-encode under tier rules, retaining verified sources.
            2. Publish verified targets/status with visible replication/restore lag.
            3. Fence reference changes before sweeping under retention/version locks.

            5. Pointer commits need byte durability and GC contracts

            A write with explicit boundaries

            1. Prepare

              Immutable IDs, allocation epochs and durable fragments.

            2. Validate

              Final integrity, manifest completeness and placement.

            3. Commit

              Conditional head/index publication with reservation fencing.

            4. Reclaim

              Reclaim orphans/old generations with reader protection.

            Integrity failures may leave staged bytes; only validated metadata publication exposes objects.

            The baseline allocates immutable IDs/reservations, streams/encodes and durably prepares all n fragments under its placement layout. Validate whole-object integrity after body completion, then publish sealed manifests using metadata CAS. All n is this example’s contract rather than a universal rule: k fragments allow reconstruction but lack the desired spare redundancy. Missing targets require replacement placement or write failure under the availability policy.

            Crashes before commit may leave invisible orphan bytes rather than partial objects. Reservations/pins must protect bytes while commits remain possible; GC fences expired reservations before deletion, and commits reject fenced allocations. Lost post-commit responses have unknown outcomes requiring retained records or contract-specific reconciliation. Atomic head CAS does not create transactions across arbitrary keys or external systems.

            6. Erasure tolerance depends on placement

            For a systematic MDS code with k data and m parity fragments, any k valid fragments reconstruct data. Tolerance of m failures means unavailable or identified-bad fragments, not arbitrary m zones or unknown silent errors. Shared racks/zones correlate losses. An 8+4 layout with four fragments in each of three zones survives one zone loss, but another unavailable fragment before repair exceeds tolerance.

            The compared schemes have overheads 12/8 = 1.5 and three respectively. This does not make all EC half as costly as every replica scheme or require one availability zone per fragment. Codes depend on placements, reads, repair bandwidth, CPU and reserves. The lab models MDS availability arithmetic without encoding parity; changing placement exposes different correlated-failure behavior under the same code.

            7. Repair closes vulnerability windows under resource limits

            Missing or checksum-invalid fragments become repair candidates requiring enough valid survivors from the correct object/stripe generation. Basic repair may read k full fragments and write one replacement; systematic ranges, batching and specialized codes change costs. Targets respect placement/epochs, output is verified and replacement manifests CAS-published so stale workers cannot overwrite newer placements.

            Throttle repairs without making exposure arbitrarily long. Prioritize low-redundancy objects and account for queues, inter-zone bandwidth and spare capacity. Scrubbing discovers latent cold-data errors before additional failures. Limit firmware/deployment/deletion blast radii: parity cannot repair software deleting every fragment or encryption key.

            8. Packing, streaming integrity and physical layout

            Packing tiny objects into large sealed files can reduce filesystem metadata and seeks. Indexes map object/fragment IDs to files, offsets, lengths and checksums. Logical deletions do not immediately free packed interiors; compaction copies live records, verifies and publishes new mappings before reclaiming old files. Old-reader mappings need protection. Packing trades read/compaction amplification rather than universally optimizing every size.

            Whole-object validation completes only after consuming the body unless it was fully buffered. Stream into staging while calculating integrity, reject publication on mismatch and clean temporary bytes. Fragment checksums support reads/scrubbing; ranges and whole objects have distinct validation semantics. CRCs detect corruption rather than replace authentication or cryptographic tamper protection. Handle ETags and explicit checksum algorithms/types according to API contracts.

            9. Multipart manifests must preserve intent

            Multipart transfers independent parts and completes an explicit ordered manifest. Part numbers/tags/checksums must match accepted data; replacing a part can invalidate old manifests. Refreshing tags alone does not prove assembled content matches the client’s intent. Preserve expected checksums/sizes and validate supported types. Missing intermediate part numbers are not universally rejected: protocols may assemble exactly the supplied list, so intended completeness needs separate validation.

            Concurrent public-key overwrites need conditional completion rather than upload IDs alone. Re-read and reconsider intent after conflicts instead of dropping preconditions. Lost responses may follow successful commits. Actual S3 completion can emit initial HTTP 200 followed by an embedded error, requiring suitable SDK handling or final-body parsing. The lab simplifies this into retained completion records and exact-payload checks rather than a full S3 simulator.

            Aborts and lifecycle rules reclaim unfinished parts, but in-flight requests can race cleanup. Use session fencing, bounded retries and backend-specific rechecks. Completed objects and unfinished uploads have different lifecycles: aborting is not deletion of published objects. Ownership, quotas and lifecycle controls must also govern staged bytes.

            10. Strong GET does not automatically create snapshot listings

            Baseline GETs resolve heads through linearizable metadata authorities for read-after-write behavior. Stale gateway/CDN heads can violate this despite immutable bytes, requiring compatible validation/leases or authority reads. Heads and authoritative key indexes need coordinated publication; lagging secondary indexes can omit successfully written keys. Metadata scales with objects, versions, key lengths, indexes and hotspots rather than only payload bytes.

            Full-key hashing distributes point operations but makes prefix listing scatter/merge or use directories. Ranges over bucket/key favor scans while requiring hotspot splitting and relocation. Hashing fixed prefixes does not solve arbitrary prefixes for free. Versioned directories/cursors handle splits under explicit duplicate/skip rules, and tenant quotas bound broad listing work.

            The baseline reads authoritative committed indexes with read-after-write freshness for completed prior writes, without promising one snapshot across pages under concurrent mutation. Cursors bind query scopes, required directory state and last keys. Full-list snapshots need retained MVCC timestamps or coordinated snapshots across cursor lifetimes; per-key Raft alone is insufficient. Backend bucket types can also have different ordering semantics.

            11. Reader pins and GC fencing protect generations

            A reader resolving v1 must read v1 throughout even if the head becomes v2. Re-resolving heads per chunk can mix generations, while deleting any non-head version can break readers. Use pins/leases, epoch protection or proven lifetime/grace bounds. Leases need pause/crash, renewal and fencing behavior; arbitrary waits do not protect longer readers/uploads.

            Reachability also includes retained versions/locks, uploads, snapshots, repairs and migrations. Mark/sweep needs consistent cuts or allocation-age/fencing protocols to avoid deleting concurrently published objects. Idempotent cleanup and suitable audits/canaries/dry runs matter because GC bugs can delete all copies together. The lab models one tracked reader and overwrite rather than distributed reference counting.

            12. Delete markers differ from physical erasure

            With versioning, deletion can create a marker hiding latest lookups while older versions remain accessible under permissions. Specific-version deletion, expiration and overwriting differ. Policies, retention locks and holds are separate controls; encryption-key deletion has its own blast radius and cannot substitute for unclear deletion semantics.

            A logical 404 does not establish removal from replicas, packs, backups or logs. Define retention/deletion timelines and inspect live references before reclamation. Authorization covers versions and cached/private assets rather than only latest keys. Deletion/retries need idempotent behavior when notifications duplicate or arrive late.

            13. Verify-before-switch migrations and restore contracts

            Tier transitions can copy, re-encode or change media depending on design. Retain sources while preparing targets, verify integrity/durability and publish compatible placement generations before cleanup. Background quotas/priorities prevent migrations from harming reads or repairs. Rollback also needs retained source generations until safe cleanup.

            Cold/archive designs can have distinct restore delays, retrieval costs or retention behavior; lower storage prices do not make every workload cheaper. Distinguish objects needing restoration from absence. Restored copies need expiry/authorization and idempotent job tracking. Cost includes requests, staged/storage bytes, repairs, egress and restoration rather than disk prices alone.

            14. Security, cells and cross-region recovery

            Separate tenant/bucket/object authorization, signature validation, quotas and key permissions. Encryption does not replace access controls; key loss/revocation can make intact bytes unreadable. Presigned grants constrain methods/keys/expiry and protected logs. Data-node access must not bypass object policies. Metadata/billing audits should serve their purposes without leaking sensitive names.

            Cells limit some operational blast radii only when data/metadata/control dependencies are actually isolated. Asynchronous regional replication has contract-specific lag/RPO; promotion needs generations/fencing, deletion order and conflict policies. Synchronous commits have different latency/availability trade-offs. Healthy replica regions do not prove recoverable metadata, bytes and keys without restoration drills.

            15. Failure matrices matter more than engine names

            Track size/count tails, metadata p99, fragment/integrity failures, repair backlog/age, under-redundant bytes, GC lag, staged uploads and listing fan-out. Capacity alerts include reserves and cross-zone throughput: free disks do not prove adequate repair speed. Drill publication-boundary crashes and verify client behavior rather than process liveness.

            16. Questions about publication, durability and lifecycle

            Draw an overwrite with an active v1 reader, a replaced upload part and a lost commit response. Identify visible objects, protected bytes and client knowledge after each timeout.

            Does metadata publication automatically solve distributed atomicity?

            No. Prepare durable bytes, validate manifests/integrity, protect reservations and fence commit/reclamation races. CAS is a visibility point within that protocol rather than a universal distributed transaction.

            Does 8+4 tolerate four zone failures?

            The MDS assumption tolerates four unavailable fragments, not arbitrary zones. Placement determines fragments lost per zone, while unknown corruption needs separate integrity/error models.

            Do matching ETags prove intended object bytes?

            Not universally. Tags may be validators and multipart tags are not always whole-object MD5s. Matching references still require separate intended-length/checksum/content validation.

            Does HTTP 200 always prove multipart completion?

            Not when final errors can be embedded as in S3 completion. Parse final results and treat lost replies as unknown outcomes requiring reconciliation rather than blind duplicate actions.

            Do linearizable point reads create snapshot pagination?

            No. Listing needs authoritative indexes, split-aware routing and retained common snapshots/MVCC when promising frozen sets. Per-key consensus does not freeze concurrent pagination.

            Can non-head versions be reclaimed immediately?

            Not while readers, retained versions, uploads, snapshots or migrations reference them. Use fenced pins/epochs/leases or proven lifetime bounds; correct initial metadata reads do not prevent premature deletion failures.

            Can AFRs and parity counts establish extreme durability targets?

            No. Include correlated failures, repair exposure, latent corruption, software/deletion/key risks and validation. Disk failure rates and storage ratios are not object-loss probabilities.

            Does aborting an upload delete published objects?

            No. Unfinished cleanup differs from object deletion/version lifecycle. Fence/recheck in-flight parts and respect completed-generation references/retention rather than bypass object policies with aborts.
