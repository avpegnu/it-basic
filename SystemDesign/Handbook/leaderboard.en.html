1. Define ranks, freshness and seasons

Ordering

  • Ordinal, competition and dense ranks differ under ties.

Freshness

  • Accepted scores, visible projections and finalized seasons are different boundaries.

Trust

  • Authoritative servers reduce score forgery rather than making anti-cheat absolute.

The baseline covers global top-K, own ranks, neighborhoods and monthly seasons, with authoritative game outcomes. An example visibility target is below one second after durable results under healthy conditions, with explicit stale/partial policies under overload. Matchmaking and complex social feeds are outside scope. Exact ordinal positions differ from competition/dense ranks where ties can share rank two.

Ties can use member IDs, earliest achievement or domain rules. Seasons need timezones/cutoffs, trusted event times and late-result/freeze/correction policies. Award-bearing exact ranks must not silently become percentiles because implementation is cheaper; approximation is an explicit product decision.

2. Count player outcomes, queries and peak memory

Assume twenty-five million monthly players, five million DAU and ten scored player outcomes per DAU/day. This counts participation/outcomes, not unique multiplayer matches. Fifty million daily updates average 578.7/second, with an assumed fivefold peak of 2,894/second. Rank reads depend separately on sessions/UI refreshes rather than write rates.

Twenty-five million times one hundred B gives 2.5 GB under an illustrative per-entry assumption. Measure actual encodings/member bytes/allocators, version maps, deduplication state, replicas, AOF rewrite/copy-on-write and overlapping rebuild generations. One primary per board is a simple baseline when benchmarks support the workload/failures, not a universal memory or throughput claim.

        4. Durable sources precede projections instead of independent dual writes

        A baseline transaction records unique outcomes, per-player/season aggregate totals/versions and outboxes. Relays publish absolute aggregate events; workers apply monotonic versions. Independent history/Redis consumers on ephemeral events can expose scores absent from durable history, requiring authoritative durable logs or transactional sources/outboxes.

        Reads retrieve ranks/scores then batch-hydrate profiles. Redis is a serving projection under durability/failover policies, not the sole source when rebuilds are promised. Retained history, rules, corrections and moderation must reconstruct populations/scores correctly rather than sum every observed positive event.

        1. Query authorized seasons/boards and K or player neighborhoods.
        2. Read top-K or coherent rank/range results under ranking/generation contracts.
        3. Return members, scores, positions and projection watermarks/freshness.
        4. Batch-hydrate authorized names/avatars rather than sequential per-player calls.
        5. Missing profiles have fallbacks rather than silently reranking populations.

        1. Snapshot consistent score totals at watermarks, using partition vectors when required.

        5. Sorted sets return positions efficiently, but product ranks can differ

        Redis sorted sets support logarithmic updates/ranks, while ranges returning M members typically cost O(log N+M), not logarithmic regardless of output. Skiplist spans support large-set order statistics, with compact encodings for small sets. SQL score indexes handle top-K well, but generic B-trees do not inherently store arbitrary ordinal-rank subtree counts; counting preceding entries can scan many entries depending on plans/selectivity. SQL remains valid for small workloads or offline/snapshot ranks.

        Ascending Redis order uses score then member byte lexicographic order; REV reverses both scores and ties. ZREVRANK returns zero-based ordinal positions, commonly displayed plus one. Competition ranks count higher-scoring players, while dense ranks count distinct higher scores, so ZREVRANK does not implement every product rank. The demo uses ASCII IDs for transparent byte ordering.

        6. Tie-breaking must not destroy score precision

        Redis scores are doubles: supported integers are exact, but arbitrary decimals/composites can collide through rounding. Packing points×2^32+tieBits needs proven bounds and safe integer totals; arbitrary Unix milliseconds do not fit thirty-two bits. Use conservative JavaScript safe-integer checks or suitable integer representations/validation before submission.

        Earliest-achievement ties need timestamp sources, precision, season epochs and penalty/correction rules. Composite packing invalidates raw-point ZINCRBY updates; use atomic compute/set with dedup/version guards or indexes supporting actual tuple comparators. Equal packed ties still need deterministic final ordering. Redis member comparisons are not arbitrary configurable comparators.

        7. Handle duplicate/reordered events at the projection boundary

        Apply an absolute score event

        1. Validate

          Validate trusted sources, rules/seasons/epochs and numeric bounds.

        2. Compare versions

          Old/duplicate versions leave scores unchanged.

        3. Apply atomically

          Set absolute scores and source versions within one boundary.

        4. Checkpoint

          Acknowledge after application; retries remain idempotent.

        Scope identities/versions by board/season/player; lower scores can still be valid newer corrections.

        ZINCRBY double-counts when workers update Redis then crash before offset commits. Source deduplication protects the source, not Redis side effects. Options include atomic marker-plus-delta updates with replay-compatible retention or atomic absolute totals plus monotonic player/season versions. The demo uses absolute totals, relying on correct source aggregation and newer versions even for downward corrections.

        Version maps and score keys need shared atomicity/Cluster slots for scripts. Lua execution is atomic relative to other commands, but runtime errors do not roll back prior writes: validate types/limits/key states first and provide rebuild/reconciliation. Stale workers must not mix generations, and projection safety also depends on persistence/failover and source-watermark recovery.

        8. One ZSET key does not automatically span Redis Cluster

        Distribute boards/seasons across keys and add freshness-aware read replicas/caches before splitting one board. Redis Cluster places one key in one slot; adding nodes does not split giant sorted sets. User-hash sharding can merge local top-K from all shards under common orders/filters/snapshots: global top-K members cannot follow K members within their own shard.

        Exact ordinal ranks count tuples preceding targets on every shard: greater scores plus preceding equal-score members under the tie rule. Summing only greater-score counts gives competition rather than ordinal rank. Independent shard reads at different times do not establish a global snapshot; missing shards require partial/failure behavior. The demo freezes data to isolate arithmetic.

        9. Range sharding and histograms change query costs

        Score-range sharding combines higher-range counts with local ranks but migrates players across score/correction boundaries. Ownership/count updates must remain consistent, with hot-range splitting; sparse highest ranges can make top-K span several ranges. Hashing balances key counts rather than necessarily QPS. Candidate merging costs network/CPU proportional to shards times K and waits for slow shards.

        Exact top-K plus approximate percentiles/histograms is valid when product/awards permit. Histograms must decrement old buckets and increment new ones while handling duplicates, corrections and population changes; incoherent counts invalidate intervals. Specify percentile/tie definitions, resolution/error bounds and as-of times. Frozen-demo intervals do not prove live histogram pipelines exact.

        10. Ranks and neighborhoods need a coherent view

        Separate ZREVRANK/ZRANGE calls can race updates and yield neighborhoods no longer surrounding users. Use atomic reads on the same key or suitable snapshot/generation views. Profile hydration need not alter score views, while eligibility/bans need explicit semantics. Clearly label acceptable live best-effort responses instead of claiming fixed snapshots.

        Offset paging over live ranks can duplicate/skip moving players. Cursors bind seasons/rank policies/generations and last tuples, but tuple cursors alone do not freeze changing data. Snapshot/finalized boards provide stable pages with compatible retention/expiry. Missing profiles should not silently remove players and reassign ranks while the population still includes them.

        11. Rollovers, late results and rebuilds need watermarks

        New seasons use new keys/generations rather than mass resets. Trusted season assignment follows chosen finalized-match or ingestion times, timezones and grace policies; post-freeze events are rejected, archived or corrected explicitly. Awards need finalization watermarks/replays/audits rather than expiry clocks alone. Old-board history/appeal retention differs from cache TTL.

        Rebuild consistent source snapshots at watermarks into fresh generations with totals/rules/eligibility, then replay subsequent tails. Validate counts, score sums and sampled ranks, retain streams long enough and use partition-offset vectors when no global cursor exists. Taking newest offsets after snapshots can skip tails. AOF/replicas have specific RPO/RTO; measure recovery rather than promising instant rebuilds.

        12. Friends, moderation and profile privacy

        Small friends boards can batch-read F scores and sort in O(F log F) for top-K/neighborhoods; linear fetching does not make sorting free. Check friendships, visibility, blocks and regional policies before hydration; global ranks are not friends ranks. Large social audiences can need materialized projections with fanout and policy lifecycles.

        Authenticate game services, verify replay/rule bounds and retain outcome evidence for anti-cheat review. Persist bans/removals/corrections at sources and propagate under policy: temporary ZREM plus unfiltered rebuilds can resurrect excluded players. Scoring-rule changes need versioned recomputation rather than repeatedly adding retried penalties.

        13. Measure score visibility and rebuilds during failure drills

        Measure durable-outcome-to-visible latency by season/region, stale-version rejections, source/projection mismatches, membership, hot-key CPU, replication/AOF lag, partial queries, hydration latency and rebuild ETAs. Track corrections/bans and award-finalization errors separately. Failovers must preserve score/version consistency, not merely restore Redis pings.

        14. Interview questions on ranks, replay and distributed views

        Explain sorted tuples, event identities, projection boundaries and snapshot semantics. Validate sharded merges against brute-force fixtures before using complexity to justify architecture.

        Does ZREVRANK always give the desired player rank?

        It is a zero-based ordinal position under score/member ordering. Competition/dense ranks differ on ties. REV reverses lexical ties; earliest-achievement rules need explicit ordering/encoding bounds.

        Does source match-ID deduplication prevent repeated ZINCRBY effects?

        No. Redis updates followed by pre-ACK crashes can replay. Use atomic deduplication/deltas or absolute aggregates/versions at the projection boundary, with player/correction-aware identities.

        Does hash-sharded global rank only sum higher scores?

        That gives competition rank. Ordinal ranks also count preceding equal-score members, using correct target versions and coherent shard views when claiming exact snapshots.

        Can available-shard top-K be returned as complete after one timeout?

        Missing shards may contain leading players. Mark partial or fail under the contract; the union proof requires all shards and common orders/filters/views.

        Why not add a small timestamp fraction to scores for ties?

        Floating precision/magnitudes can erase fractions or reorder ties. Prove bounded safe packing or use appropriate tuple indexes; packed updates are not raw-point increments.

        Does adding Redis Cluster nodes split a giant ZSET?

        No: one key occupies one slot. Splitting boards changes models, fanout/count consistency or explicitly accepted approximation policies.

        Does rebuilding with SUM(points) always restore the board?

        Only with sufficient sources/rules/retention covering deduplication, corrections, eligibility and seasons. Use snapshot watermarks, tail replay and generation publication; missing policies/incorrect offsets restore wrong scores.

        Can all lower ranks be replaced with percentiles for scale?

        That is a product trade-off, not an automatic replacement for requested exact ranks/awards. Accepted approximations need explicit definitions, resolutions/errors/as-of times and coherent histogram updates.
