1. Which work does the cache remove?

Caches retain computed/fetched results to avoid repeated work. They help when reuse within a freshness window outweighs storage, lookup and invalidation costs. An endpoint reading unique data or requiring authoritative current state may gain little from response caching, even if the database page cache helps.

Start with access patterns and the goal: lower database QPS, latency, egress or expensive computation? Measure request/byte hit rates, origin load and latency together. A 99% hit rate can still fail to protect the database if the 1% misses are costly or bursts exceed origin capacity.

2. Choose cache location and trust boundaries

Browser caches are closest to users, CDNs to user groups, local caches to code and shared caches to multiple instances. Each layer saves some latency while adding a copy requiring freshness policy. Local caches avoid network calls but can disagree across app replicas; shared caches improve reuse while adding a network dependency.

Distinguish HTTP no-store from no-cache: no-store disallows storage under cache semantics; no-cache permits storage but requires revalidation before reuse. Private limits shared-cache use rather than replacing authorization. Content-hashed assets fit long immutable caching; private APIs need suitable keys/headers and permission boundaries.

3. Read/write patterns and acknowledgement points

Cache-aside looks up the cache, reads the source on miss, fills and returns. Writes commonly commit then invalidate, but concurrency can still reinsert stale values. Read-through moves loading into the caching abstraction without inherently changing correctness. Identify the durable authority and cache-write failure handling.

Write-through synchronously updates the source through a caching layer; two stores are not automatically atomic. Define behavior when the source commits but cache updating fails. Write-behind acknowledges before source updates and can fit delay-tolerant work, but loses writes if buffers are not durable enough; queue persistence/replication and recovery are required.

Refresh-ahead updates popular keys before expiry within a budget. Stale-while-revalidate can return an allowed stale copy while refreshing, but must not be blindly applied to authorization, balances or inventory decisions. Serving stale is a product contract, not merely an optimization switch.

Write-around writes directly to the source without populating the cache, usually invalidating an older copy. It avoids pollution for rarely read data but may cause a first-read miss. It is a write policy, not forgetting invalidation; stale-refill races still depend on the freshness contract.

4. Eviction differs from expiration and invalidation

Eviction reclaims memory, expiration stops reuse after TTL and invalidation removes copies after source/policy changes. LRU uses recency, LFU frequency and FIFO insertion age. No policy wins every trace: scans can evict hot LRU working sets, while LFU without decay may preserve obsolete popularity.

Real capacity depends on bytes/object overhead, not just key counts. A 20 MB object differs from a 20-byte object; admission can reject oversized or low-reuse objects. Byte/cost-aware policies differ from the three-key toy below. Measure fragmentation/eviction to distinguish churn from a slow source.

Production often approximates recency/frequency to reduce bookkeeping instead of updating a global list on every read. TinyLFU-style admission estimates frequency to decide whether a newcomer should replace a resident; a recency window can help resist scans. Understand implementation and memory/CPU costs rather than generalizing exact toy LRU to every cache.

5. Keys, versions and missing data

Keys must include response-affecting dimensions: tenant/user scope, resource ID, filters/sort, locale and relevant schema/model versions. Canonicalize equivalent queries, limit cardinality and avoid secrets/PII in logged keys. Omitting a tenant is a more dangerous logical collision than a rare hash collision.

Negative caching briefly retains true not-found results to reduce repeated misses, but distinguishes them from timeouts or denied permissions. Do not turn transient failures into long-lived absence or reuse one user’s 403 as another user’s resource state. Creation must invalidate negative entries or use appropriate versions/namespaces.

6. Invalidation races: why delete-after-write is insufficient

An invalidation can still end with stale data

  1. T1 · Cache miss

    The reader finds no cached value.

  2. T2 · Read v1

    The reader obtains v1 but has not refilled.

  3. T3 · Write v2 + delete

    The writer commits v2 and invalidates.

  4. T4 · Refill v1

    The earlier reader caches v1 again.

This is a failing interleaving: the writer commits v2 and deletes the cache, but an older reader later refills v1. Coordinate refill/version handling; TTL only bounds lifetime under its assumptions.

A typical interleaving is: reader A misses and reads database version one; writer B commits version two and deletes the cache; A then fills version one. The cache is stale again despite post-commit invalidation. TTL may bound the window but does not satisfy a current-version contract.

Options include versioned entries with conditional publication, invalidation watermarks/tombstones, ordered per-key CDC or bypassing caches for strongly consistent reads. CAS on an existing entry alone is insufficient if invalidation removed all version evidence; retain a watermark/version or coordinate with the owner. One delete command does not create a database/cache atomic transaction.

Delayed double deletion can reduce race probability under an assumed delay but does not prove correctness against longer loader pauses, network delay or replica lag. Choose by the freshness contract/failure model rather than treating an arbitrary delay as a guaranteed barrier.

7. Trace reads, writes and races

Component map; the complete ordered request paths are explained below.

Read miss

  1. Receive a read and its freshness/permission context.
  2. Look up a correctly scoped tenant/resource/version key.
  3. On miss, read the source within deadline/concurrency budgets.
  4. The loader receives the value and source version.
  5. Publish the entry under the TTL/version policy.
  6. Return loaded data after policy checks.
  7. Return the response and record hit/miss/origin latency.

Commit + invalidate

  1. Receive an authorized, suitably idempotent mutation.
  2. Commit new authoritative state under its invariant.
  3. Trigger invalidation through the write path or durable event.
  4. Invalidate/update the entry using versions and retry policy.

Race: reader A / writer B

  1. A reads version one after a miss.
  2. A’s delayed loader holds the old value.
  3. B commits version two before A fills.
  4. B requests invalidation after committing.
  5. The cache is deleted; without a watermark, no version barrier remains.
  6. A fills version one after invalidation, restoring a stale value.
  7. A later read can hit version one without stale-publication protection.

8. Stampedes, penetration, avalanches and hot keys

Many readers, one key

  • Single-flight/coalescing combines origin work for one key.
  • Bound concurrency, set deadlines and handle loader failure.

Many keys expire together

  • TTL jitter spreads expiration across many keys.
  • Jitter does not coalesce duplicate misses for one key or remove all long-term work.

A stampede occurs when many readers miss one key and all call the origin. Single-flight/coalescing permits one loader while waiters use bounded deadlines; cross-process leases need expiry, owner identity and dead-loader handling. Never hold indefinite locks or use cache locks as universal business-invariant protection.

An avalanche expires many keys or loses a whole cache at once. Jitter, prioritized warming, admission and origin bulkheads spread load. Penetration repeatedly requests absent keys; use validation, short negative caching and rate limits. Bloom filters offer probabilistic membership and require correct updates; they replace neither authorization nor authority.

A hot key dominates traffic while other shards sit idle. Local read caches/replicas or coalescing may help; splitting is useful only where data/aggregation semantics permit it. More shards do not split that key’s requests, and shorter TTL can increase origin load instead of solving the problem.

Probabilistic early refresh lets some readers regenerate before hard expiry, often using remaining lifetime and recomputation cost. It can spread regeneration but does not replace coalescing, deadlines or permission to serve stale. Overeager refresh adds origin work; measure usefulness and bound concurrent regeneration.

9. Cache sizing and observability

Estimate working sets from distinct reusable keys × entry bytes plus indexing/allocation/replication overhead. Choose TTLs from freshness/update/read patterns rather than attractive hit rates. Ten million 200-byte payloads equal 2 GB payload, not cluster RAM; representations and replicas can change totals substantially.

Dashboards need hits/misses by cache class, origin loads/latency, rejected loads, coalesced waiters, evictions, memory/fragmentation, stale serves and invalidation age. A miss is not inherently an incident; origin overload or freshness violations are the user-impact signals. Avoid raw-key metric labels for cardinality and privacy.

10. Failover, rollout and race testing

Cache failover may lose recent entries or create cold working sets depending on replication/persistence. Rebuild copies within bounds. A cache retaining unrebuildable pending jobs/state has taken on durable-store responsibilities and needs matching RPO/RTO. Not every deployment called a Redis cache can safely lose its state.

New key/schema versions can cause sudden misses; warm cohorts or use deliberate dual reads with an overlap memory budget. Test delayed old loaders after invalidation, partial database/cache writes, cache timeouts, slow origins and permission revocation. Controlled interleavings are more reliable than adding threads and hoping to expose a race.

10a. A budgeted single-flight loader

This illustration requires cache, source, semaphore and deadline adapters. The scopedKey already includes required identity/policy dimensions and authorization runs before entry. originSlots is a per-process budget; multiple instances need an aggregate source-capacity budget rather than unbounded multiplication of a local cap.

One waiter’s deadline should not cancel work shared by others; loaders have internal deadlines. Fill failure need not discard a valid source result where the freshness contract permits it, but must be measured. publishIfNotOlderThanWatermark requires version/invalidation coordination; it is not a universal built-in atomic cache operation.

type Value = { version: number; payload: unknown };
const pending = new Map<string, Promise<Value>>();

async function read(scopedKey: string, requestDeadline: number): Promise<Value> {
  const hit = await cache.lookupWithinBudget(scopedKey, requestDeadline);
  if (hit && hit.isFresh) return hit.value;

  const shared = pending.get(scopedKey);
  if (shared) return waitWithinRequestBudget(shared, requestDeadline);

  const permit = originSlots.tryAcquire();
  if (!permit) throw new OverloadedError();

  // Internal work has its own deadline; one waiter cannot cancel every waiter.
  const work = Promise.resolve()
    .then(() => origin.loadWithDeadline(scopedKey, 150))
    .then(async (value: Value) => {
      try {
        await cache.publishIfNotOlderThanWatermark(scopedKey, value);
      } catch (error) {
        metrics.recordCacheFillFailure(error);
      }
      return value;
    })
    .finally(() => {
      pending.delete(scopedKey);
      permit.release();
    });
  pending.set(scopedKey, work);
  return waitWithinRequestBudget(work, requestDeadline);
}

Illustrative adapter contracts, not a drop-in module. The 150 ms deadline is an exercise assumption to be replaced by measured SLO budgets.

10b. Lists, multiple regions and read-your-writes

A cached list/feed projects many records. One post update can affect query keys, filters and pages; deleting a postId entry does not invalidate every list. Choose dependency tags/indexes, namespace versions or ID-only lists with current hydration. Each trades invalidation cost, memory and read complexity; one row need not map to one key.

Regional caches add invalidation delay and broader failure domains. Measure per-region invalidation age, version events and reject stale overwrites. Read-your-writes can use session versions, owner routing or deliberate cache bypass. Fast revocation cannot be proven merely by shortening TTL; validate policy/versions under the contract.

11. Questions and conditional worked answers

Why does a 60-second TTL not necessarily bound staleness to 60 seconds after an update?

A loader reading a lagging replica or completing after an update can refill stale data with a new TTL. Update-relative staleness includes lag, loader delay and refill. A real bound needs versions/watermarks and propagation semantics or cache bypass for current-state reads.

Can single-flight and TTL jitter replace each other?

No. Single-flight coalesces concurrent misses for one key; jitter spreads expiration across keys. One hot expired key can stampede despite jitter elsewhere. Both still need origin deadlines and failure policies.

Should permission checks be cached for a long time to speed up APIs?

Only when the promised revocation window is satisfied. Scope by actor/resource/policy version and invalidate/version correctly; fail closed for unverifiable private access under the contract. A content/timeline hit does not prove current permission.

Exercise: 100 keys expire, each with ten concurrent misses. What does single-flight change?

Without coalescing the toy creates 1,000 origin loads; perfect per-key coalescing creates 100. It does not reduce distinct loaded keys. Uncoordinated processes may still create several loaders per key; 100 is the declared ideal model, not an automatic deployment property.

Is unrestricted database fallback safe when the cache fails?

No. The database may be sized for normal cache hits; all traffic can exhaust pools/IO. Bound fallback concurrency, prioritize critical requests, coalesce loads, serve stale only where permitted and shed load before losing the origin.

When can LFU perform worse than LRU?

Rapid popularity changes can leave historically frequent keys resident without current reuse, especially without decay/aging. LRU reacts to recency but is vulnerable to scans. Choose using representative traces, byte costs and admission rather than a universal ranking.
