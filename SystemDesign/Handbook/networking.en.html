Networking, APIs and protocols: trace a request from frontend to data

Connect DNS, transport, TLS, HTTP, browser security and backend contracts into one understandable flow; choose REST, RPC, GraphQL, polling or streaming for actual needs.

One request crosses several contracts

  1. Find the destination

    DNS, routing and cache TTL.

  2. Establish a connection

    Transport, TLS and the HTTP version.

  3. Read the API contract

    Methods, statuses, auth and retries.

  4. Trace through to data

    Deadlines, ownership and responses.

These layers are related, not interchangeable: TLS does not authorize a resource, CORS does not authenticate a user, and a timeout does not prove a side effect failed.

  • A request has separate stages: resolution, connection, security, routing, processing and data access.
  • HTTP methods, statuses and idempotency form a contract; a protocol does not automatically deduplicate business actions.
  • HTTP/2 multiplexing does not remove TCP head-of-line blocking; HTTP/3 changes transport, not database bottlenecks.
  • CORS constrains browser response access; authorization and CSRF need separate controls.

1. Separate the layers of a request

Transport · Move data

  • Connections, streams, loss and congestion.
  • Securing the channel does not replace authorization.

HTTP · Interaction contract

  • Methods, statuses, headers, caching and retry semantics.
  • An HTTP response must match the promised application state.

Application · Rights and invariants

  • Who can do what to which resource?
  • After a timeout, establish the outcome before repeating a side effect.

A frontend API call does not jump directly into a backend function. The browser resolves the destination, obtains a suitable connection, establishes security, sends an HTTP message and traverses proxies/load balancers before reaching the application. The application still checks identity, authorization and input and queries data. Separating stages reveals whether “network slowness” is DNS, TLS, queuing or database work.

Connection reuse, DNS caching and TLS resumption can avoid some costs on later requests. Cold and warm requests differ; read browser waterfalls alongside server traces. A static frontend on a CDN still needs a backend for server logic, secrets or safe database access.

2. DNS and routing are not service health

DNS maps names to records such as A/AAAA or CNAME through resolvers and TTLs. Browsers, operating systems and recursive resolvers may cache answers; changing a record does not immediately move every client. DNS failover must account for caches, existing connections and old endpoints still receiving traffic.

Backend service discovery finds current instances; balancing and readiness determine which should receive work. Successful DNS resolution does not prove the application can reach its database. Shallow health checks can route into broken instances, while overly deep probes can remove every instance during a shared dependency slowdown.

3. TCP, TLS and HTTP/2/3

TCP provides an ordered retransmitted byte stream without preserving application-message boundaries. TLS authenticates the server certificate and protects confidentiality/integrity on that connection segment. If TLS terminates at a proxy that calls a plaintext backend, the latter segment needs its own threat model and network policy; the browser’s HTTPS indicator does not describe every internal hop.

HTTP/1.1 commonly reuses connections; HTTP/2 multiplexes streams over one TCP connection. Missing bytes from packet loss can still stall streams until TCP recovers. HTTP/3 uses QUIC over UDP with reliable streams and integrated security, avoiding cross-stream blocking from one ordered TCP byte stream; congestion and shared bottlenecks still exist.

Do not choose versions using “UDP is faster than TCP.” Compare packet loss, RTT, connection reuse, proxy support and workload. A 500 ms database query does not become 50 ms by switching from HTTP/2 to HTTP/3. Protocol optimization belongs in the full request budget.

4. Design explicit HTTP contracts

An API contract includes identity, resources, schemas, validation, statuses, stable errors, pagination, quotas and retry semantics. A safe GET means the client does not request business-state changes; incidental logs/metrics may still occur. Idempotent means repeated identical requests have the same intended effect, not necessarily identical responses or one log entry.

PUT/DELETE have idempotent HTTP semantics, which implementations must honor. Retriable order-creation POSTs need application idempotency keys bound to actors, request fingerprints and stored outcomes. A timeout does not reveal whether a server received, is processing or committed the request; status lookup or same-key replay is safer than a new business action.

5. REST, gRPC and GraphQL

REST is an architectural style, not a label automatically earned by JSON over HTTP. Resource-oriented HTTP APIs are often easy to debug and integrate with browsers/caches/proxies. gRPC offers typed contracts and streaming for internal RPC but needs tooling, compatibility discipline and browser adaptation where required.

GraphQL lets clients select fields and compose data through a schema. It can reduce over/under-fetching but does not automatically eliminate N+1 queries: resolvers need batching, depth/cost limits and field/resource authorization. One HTTP request can trigger thousands of internal queries, so request-count-only rate limits can miss the cost.

Favor compatible evolution: adding optional fields is usually easier than changing meanings or removing used fields. Follow encoding-specific wire rules for RPC; HTTP API versioning includes pagination, errors and idempotency beyond a /v2 path. Contract tests and staged rollouts support mixed client/server versions.

6. Polling, long polling, SSE and WebSockets

Periodic polling is simple but request counts grow with clients and interval: 100,000 clients polling every five seconds create 20,000 requests/s on average even with no updates. Jitter prevents synchronized polls. Long polling waits for an event or timeout, reducing empty replies while requiring connection budgets and reconnection policies.

SSE suits server-to-browser HTTP event streams, with separate submission/cancellation requests. WebSockets support continuous bidirectional chat, collaboration or audio but require application identity, message schemas, heartbeats, backpressure and reconnection/resumption. Transports do not automatically persist messages or deduplicate reconnects.

Define event sequences, retention and replay windows. A client disconnected after event 40 can resume only if authorized replay of event 41 onward remains available. When retention expires, load a snapshot and resume under a declared protocol; a long-lived socket alone does not provide realtime exactly-once behavior.

WebTransport offers streams and datagrams for flexible bidirectional use cases such as realtime media or games. Its API, deployment and client support differ from WebSockets; validate the product’s browsers, proxies and fallback. Unreliable datagrams fit discardable data, not automatically payment confirmations or durable messages.

7a. Pagination and optimistic concurrency

Offset pagination is simple, but deep offsets may skip many rows and inserts/deletions shift positions while scrolling. Keyset cursors use stable sort keys with tie-breakers, such as (created_at, id), and corresponding indexes. They improve deep pagination for suitable access patterns without automatically preserving snapshots when sort keys change.

Cursors should be opaque to clients and validated, potentially signed against tampering and bound to filters/users/sessions where needed. Base64 is encoding, not encryption or integrity protection. Ranked feeds need separate ranking/session semantics; each page still enforces current permissions even for old snapshots.

For concurrent updates, return a version/ETag and require If-Match or expectedVersion. The server performs an atomic conditional update and returns a conflict/precondition failure when state changed. Clients reread/reconcile instead of retrying stale payloads until another user’s update is overwritten.

      7b. API gateways, BFFs and trust boundaries

      Gateways can terminate TLS, validate tokens, enforce quotas, route and propagate trace context. Internal services still need resource authorization and may trust identity metadata only from authenticated paths; client-supplied “internal user” headers must not bypass checks. Gateways are shared dependencies needing capacity, availability, limits and safe rollout.

      A backend for frontend aggregates data for web/mobile/TV, reducing client chatter and shaping suitable contracts. It differs from putting every business workflow in the gateway: domain owners retain authorization/invariants while BFFs manage aggregation/deadlines. Bound fan-out, batch queries and prevent one gateway endpoint from calling the entire system without limits.

      At organizational scale, contracts/error semantics outlive implementations. Assign API ownership, deprecation windows, compatibility tests and client-version telemetry before removing fields. Protocol choices also determine operations: long-lived streams require deployment draining/reconnection budgets, not merely a request library.

      8. CORS, cookies, CSRF and authorization

      An origin consists of scheme, host and port; changing a subdomain or port can be cross-origin. CORS is a browser policy for script access to cross-origin responses, not a firewall against curl or server requests. Some requests can be sent before response access is blocked, so side effects still require authentication/authorization and appropriate CSRF controls.

      Session cookies are sent under browser cookie policy; configure Secure, HttpOnly and SameSite for the product. HttpOnly limits script access to cookies but does not replace authorization, and site and origin are not interchangeable. Cookie-authenticated mutations need suitable CSRF tokens/origin checks and threat-model controls.

      Credentialed CORS needs an explicit allowed origin and matching headers; a wildcard origin does not grant script access to credentialed responses. Do not blindly reflect every Origin. Correct CORS still leaves resource authorization necessary for the actual actor; unguessable IDs are not authorization.

      9. End-to-end timeouts, retries and observability

      Allocate total deadlines across connection, TLS, upstream processing and response reads; propagate remaining time to dependencies. Retries stay within the total budget and should have one owner to avoid multiplicative amplification: three layers with three attempts each can create 27 downstream calls. Use exponential backoff, jitter, attempt caps and side-effect idempotency.

      Measure browser DNS/connect/TTFB/download, edge upstream waits and server pool/query/service traces. Correlation/trace IDs connect hops; never log authorization headers, cookies or URL secrets. An HTTP 200 hiding business errors can distort success metrics that look only at status.

      Contract tests cover duplicate submission, expired sessions, revoked access during pagination, malformed cursors, slow streams and disconnections. Load tests need realistic connection reuse and payload sizes; network-failure injection verifies cancellation does not leave unbounded backend work.

      10. Questions and worked answers

      Does HTTP/2 remove all head-of-line blocking?

      No. It multiplexes HTTP streams over an ordered TCP byte stream, so packet loss can affect multiple streams. HTTP/3 uses QUIC stream semantics, but shared congestion, server queues and application dependencies can still delay work.

      Can a DELETE returning 404 on the second attempt still be idempotent?

      Yes, if the intended effect is resource absence after both attempts. Idempotency does not require identical responses. An API may return 204 for repeated deletion to simplify clients, but must define that contract and avoid leaking unauthorized resources.

      If CORS blocked access, can we be sure the mutation did not run?

      No. Browsers can send some requests while withholding response access; preflight can block other requests earlier. Do not infer business state from a CORS error. Inspect state with an authorized actor and enforce CSRF/authorization independently.

      Does one GraphQL request imply one database query?

      No. Resolvers may generate many queries, especially N+1 child fetching. Use request-scoped batching/loaders, query-cost/depth caps and resource authorization. Rate limits should reflect work or cost rather than HTTP counts alone.

      Should every API use WebSockets for speed?

      No. HTTP request/response fits much CRUD work and benefits from caching/tooling. WebSockets help continuous two-way interaction but add connection state, reconnection, routing and backpressure. Choose by interaction patterns and measure the critical path.

      Open questions: explain the underlying mechanisms

      Attempt an answer before reading, then change an assumption and reconsider the conclusion. Answers retain units and failure boundaries; the preceding sections provide diagrams and models.

      When should an API use REST, gRPC or GraphQL?

      Choose by consumers and interaction contracts. Resource-oriented HTTP APIs fit broad clients and HTTP semantics, including eligible caching. gRPC supplies typed schemas, generated clients and supported streaming, often useful between services with compatible infrastructure. GraphQL lets clients express fields over a typed graph, but a single request can still produce many backend calls.

      Compare serialization, round trips, fan-out, complexity and tooling rather than claiming universal speed. All choices need authorization, deadlines, pagination, compatibility and abuse controls. Bound GraphQL complexity and batch resolvers, propagate cancellation and backpressure in gRPC streams, and recognize that HTTP APIs can also stream when contracts and clients support it.

      How do polling, long polling, SSE and WebSocket fit different update needs?

      Polling is simple for infrequent updates or relaxed latency. Long polling holds a request until an event or timeout and reconnects. SSE provides a server-to-client HTTP event stream, useful for notifications or generated tokens with supported clients. WebSocket supports bidirectional messages after its handshake. Choose using direction, frequency, latency, intermediaries and client capabilities.

      None inherently supplies durable history or exactly-once business effects. Define identities, cursors, replay horizons, gap detection, ordering and slow-client behavior. Last-Event-ID only helps with an implemented replay contract, and one connection’s byte order does not order reconnects or multiple producers. Mobile background and battery constraints may favor additional push services.

      What state makes a payment-creation API idempotent?

      Retain one logical intent identity across retries. Scope the key appropriately, bind it to a canonical request fingerprint, and coordinate reservation and business state within a controlled authority boundary. Reusing a key with a different payload needs an explicit conflict contract. Concurrent attempts require one winner and defined in-progress or completed results.

      Retain a stable result or reconstruction path with an explicit replay horizon. A timeout after commit is ambiguous, so callers query or retry the same identity. External processors need their own supported idempotency, status and reconciliation boundaries; local deduplication alone is insufficient. Retry-safe APIs and durable business intents do not imply a single network call or unconditional exactly-once effects.
