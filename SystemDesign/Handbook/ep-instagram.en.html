1. From a photo app to multiple product surfaces

Post authority

  • Authors, current generations, visibility, readiness and tombstones are durable state.

Media plane

  • Immutable storage/CDN bytes with scoped authorization and lifecycle.

Projections

  • Feeds, search, trays and caches have lag/rebuild semantics and never replace current permissions.

This lesson builds an Instagram-style photo/video platform around media volume, metadata placement, feed latency, ephemeral surfaces and geography. Stages are teaching designs with explicit assumptions rather than a current production inventory. Familiar tools can scale when access patterns, durability and ownership are sound.

Scope includes photo/video publishing, following/private audiences, feeds, Stories, deletion and retries. Advertising, messaging and copyright enforcement need separate contracts; naming them does not fully design them. Sizing below is illustrative reasoning.

2. State machines and ACK boundaries before service lists

Publish lifecycle

  1. Upload

    Scoped staging objects remain private.

  2. Commit

    PROCESSING, keyed results and durable intent.

  3. Ready

    Conditional generation transitions after processing.

  4. Serve / delete

    Current permissions/expiry; tombstones precede cleanup.

Serving requires both state and audience authorization.

Uploads and posts have distinct lifecycles. Slots permit staging writes; PROCESSING acknowledgements promise durable metadata/intent, not playability. READY requires validated authorized renditions, and failures have explicit pending/error behavior. Finalization retries preserve post/results and reject payload conflicts.

Workers and projections retain generation/mutation versions. Tombstones block stale work; the last job to finish does not override the latest business mutation. Captions, audiences and media may need distinct version domains with explicit ownership and merges.

3. Twelve evolutionary stages with exit criteria

Read each stage as problem, decision, cost and next pressure. Additional boxes alone do not justify services. State baseline tails, errors, costs and required failure behavior, then drill new boundaries.

MVP: one app and transactional metadata

Costs and trade-offs: One deployment/database has a broad blast radius; upload/body limits and quotas are still required.

5. Trace uploads, feeds, Stories and deletion

Select and step through traces to inspect authority. Asynchronous arrows do not imply exactly-once behavior: retain intent, identities, versions and recovery. Metadata transitions are conditional, not permission for workers to publish arbitrary outputs.

Trace a post through upload, readiness and serving

Component map; the complete ordered request paths are explained below.

Metadata authorizes visibility; objects hold bytes and feeds/search are projections. Deletion must block serving before asynchronous physical cleanup finishes.

Upload and finalize

  1. Authenticated slot requests retain upload identity, quotas and expiry.
  2. Upload scoped staging objects; checksums establish integrity, not moderation.
  3. Finalize with the same identity; lost-reply retries do not create new posts.
  4. Validate owned complete objects, types, limits and generations.
  5. Commit PROCESSING metadata, keyed responses and processing intent.

Ready, then fan out

  1. Outbox/CDC places committed intent in a replayable log.
  2. Retry jobs with stable post/generation identities.
  3. Validate, decode, scan and write immutable renditions.
  4. Condition readiness on current undeleted generations.
  5. Durable readiness intent materializes eligible IDs idempotently.

Open feed

  1. Cursors retain stable page/ranking context rather than only offsets.
  2. Gather materialized IDs and bounded pull candidates.
  3. Deduplicate IDs, filter eligibility and score bounded candidates.
  4. Hydrate and recheck visibility/deletion for top items.
  5. Fetch scoped renditions under permission-aware origin policies.
  6. Misses fetch exact published generations.

Trays and viewed state

  1. Request active trays under current principals/server time.
  2. Read candidate authors/items and hole-aware viewed state.
  3. Enforce expiry, current audience and deletion versions before URLs.
  4. Fetch only within the selected serving-capability window.

Deletion and stale work

  1. Delete with authenticated ownership and stable request identity.
  2. Commit v2 tombstones and durable invalidation intent.
  3. Invalidate projections/caches and revoke serving under contract.
  4. Track original/derivative purges under retention policy.
  5. Reject late v1 workers rather than resurrecting READY.

7. ID layout: time, shard and sequence

In the illustrative 41/13/10 layout, shift elapsed milliseconds by23, the logical shard by10, then OR the sequence. Thirteen bits permit8192 labels without requiring that bucket count. Forty-one milliseconds bits span about69.7 years. Positive signed PostgreSQL bigint values permit only40 time bits here, about34.8 years; plan sign, epoch and format transitions.

Modulo1024 alone does not prevent duplicates: equal timestamp/shard/sequence fields collide. Capacity waiting/rejection, clock handling and exclusive ownership are separate guards. Independent table sequences may define per-table rather than global cross-entity uniqueness.

Wall-time IDs do not establish trusted creation time, causality or commit order. Skew, transactions and delays break that inference. UUIDv4 can paginate through composite indexes; UUIDv7/ULID offer time locality. Evaluate width, locality, routing and threat models rather than declaring UUIDs universally wrong.

8. Logical-to-physical mapping and shard moves

A safe shard move

  1. Copy

    Versioned snapshots and retained change capture.

  2. Verify

    Rows, deletions, lag and actual invariants.

  3. Fence

    Activate ownership epochs at write authority.

  4. Route

    Publish maps; stale callers retry with stable identities.

Stable IDs do not make migration atomic.

A fixed-bucket user modulo is one policy. Directories separate bucket identity from physical hosts/epochs, so host count changes do not change the modulo denominator. Buckets still cost schemas, pools, backups and cross-shard queries. Hot authors may need dataset-specific subdivision without silently changing public routing identities.

Move by validating target capacity, backfilling versioned snapshots, replaying changes including deletions, catching up to a barrier, activating target ownership while fencing the source, then publishing the directory epoch. Stale requests retain identities. Mapping changes alone risk split writes or lost changes.

9. Media DAGs and visibility boundaries

Integrity checks do not establish safe decoding, permitted content or correct audiences. Isolate decoders and bound pixels, duration and expansion. Retain policy checks and generation-bound job inputs/outputs; partial outputs never enter published manifests.

Readiness and feed intent need a coherent boundary. Workers may finish and lose replies; retries use conditional updates and immutable keys. Deletion changes serving eligibility before cleanup and rejects stale readiness. Failed work needs bounded retries, repair queues and visible stuck-processing detection.

10. Feeds: push, pull, ranking and pagination

Push IDs for ordinary authors and use bounded pull/merge for high-fan-out authors. Choose thresholds using posting, active readership and amplification rather than a permanent follower count. Deduplicate posts across push, pull and retries, then enforce following, audience, blocks and deletion during serving.

Ranking optimizes multiple outcomes within latency, diversity and safety constraints. Distinguish recall, calibration and policy filtering. Retained ordering/snapshots stabilize pages; otherwise declare refresh/reordering semantics. Feature failures may use an authorized chronological fallback, never unfiltered object IDs.

11. Stories: eligibility, archives and viewed-state holes

Server-time expiry is a product predicate even when cache cleanup lags. Before issuing capabilities, validate expiry, audience and tombstones; URL/cache lifetimes must honor serving windows. Archives/highlights are separate authorized views, and disappearing from trays is not proof of erasure.

Exact cross-device viewed state cannot generally use only a maximum sequence: viewing102 before101 leaves a hole. Use sparse sets, bitmaps or contiguous watermarks with holes and bounded retention. Union observed identities across devices without assuming lower sequences were viewed; preserve identities across edits, deletion and arrivals.

12. Runtime, geography and recovery have distinct scopes

Pre-fork sharing can reduce memory while GC/reference metadata writes trigger copy-on-write. Profile memory, allocations and cycles before tuning. Disabling cycle collection neither disables reference counts nor makes all objects immutable. Immortal objects offer another mechanism, not a reason to copy a flag into every Python app.

Home-region writes reduce coordination only when authority and replication are local. Global relationships/privacy still need appropriate reads or versions, and eventual projections never grant permission. Define separate recovery contracts for metadata, media and events with capacity, replay and fencing. Travel differs from data migration; proximity is not residency policy.

13. Reels: media pipelines and feedback loops

Video costs depend on duration and viewing distribution. Produce basic playable ladders after validation, then schedule advanced encodes when expected delivery savings justify compute/storage. Account for codecs, devices, quality and forecast uncertainty. Viral priorities need protections against starving new uploads.

ABR controls playback using throughput/buffers; recommendation selects content using user/model features. They interact through QoE and viewing observations but are distinct controllers. Measure startup, stalls, skipping, completion and device costs while avoiding leakage and harmful single-metric feedback.
