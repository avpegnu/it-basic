1. Object semantics trước disk layout

Metadata plane

  • Key/version/head/index, permissions và publication state.

Data plane

  • Immutable fragments, verified writes, reads và repair.

Lifecycle

  • Reader/upload pins, retention, migration và fenced GC.

Baseline có bucket/key, PUT/GET/HEAD/DELETE, range reads, prefix LIST và multipart. Object data là immutable generation; overwrite tạo bytes mới rồi đổi head. Đây không phải POSIX filesystem có append/rename/locking tự động hay transaction across arbitrary keys. Chốt max object/part size, metadata limit, request throughput, consistency, retention và restore latency theo backend đã chọn. Bài này là platform minh họa, không tuyên bố triển khai private của một cloud service.

Durability, availability và consistency là ba mục tiêu khác nhau. Một object còn recoverable trên disk chưa có nghĩa API đang reachable; strong metadata cũng không cứu bytes đã mất. Không suy “11 nines” từ số replicas, AFR hoặc một coding formula. Product cần mô hình failure correlation, repair windows, software bugs/deletion và evidence vận hành; các phép tính dưới chỉ là sizing/availability theo giả định.

2. Object count và bytes tạo hai bài toán capacity

Giả định 100 PB logical data, average object 1 MB và metadata 1 KB theo đơn vị thập phân. Object count là 100 tỷ; metadata payload khoảng 100 TB trước indexes, replicas và history. Triple replication cần 300 PB raw payload; MDS 8+4 cần 150 PB. Nếu disk 20 TB và bỏ mọi reserve/overhead, tương ứng 15.000 và 7.500 disks. Với 7.500 disks và AFR giả định 2%, kỳ vọng trung bình khoảng 0,41 disk failure/ngày; đó không phải xác suất mất object hoặc guarantee failure độc lập.

Cần thêm free-space headroom cho repair/compaction, skew, placement constraints, rebuild backlog, staging uploads và temporary tier copies. Nhiều tiny objects gây request/index/metadata pressure khác với một vài huge objects gây bandwidth pressure. Average size không đủ mô tả tail; đo size distribution, access distribution, GET/PUT/LIST mix, range sizes và hot keys. EC tiết kiệm capacity nhưng thêm encode/decode/repair cost.

3. APIs có checksum, preconditions và outcome rõ

API minh họa dưới đây dùng namespace riêng; real S3-compatible implementation phải theo wire/auth/encoding/limits của protocol cụ thể. Signed request hoặc presigned grant có expiry và scope chặt nhưng vẫn là một authorization capability; không để URL logs lộ grant. Conditional writes ngăn silent lost update khi key đã đổi. ETag là validator theo contract, không mặc định full-object MD5 hoặc content identity dùng chung mọi upload mode.

            4. Publish và recover đi xuyên cả hai planes

            Metadata trả lời object nào tồn tại; data nodes trả verified immutable fragments. Placement map có epochs và failure domains, không chỉ một danh sách hosts đang ping được. Upload sessions, reader pins và migration state cũng tham gia lifecycle. Stateless API instances scale được, nhưng state cần authority và recovery ở các services phía sau. Trace dưới đây chọn một logical protocol, không giấu atomicity vào một mũi tên “write metadata”.

            PUT và metadata commit

            1. Gửi bytes, checksum và expected ETag/generation theo chosen API.
            2. Authorize tenant/bucket/key và encryption use.
            3. Cấp immutable object ID và allocation/reservation epoch.

            6. Commit head/version và authoritative key index trong contract.
            7. Trả parsed final success sau commit; mất response cần reconcile.

            GET pin immutable generation

            1. GET/Range và auth context tới gateway.
            2. Resolve current immutable object version; không dùng stale cache phá consistency.
            3. Reader lease/pin hoặc epoch protection giữ đúng version trong thời gian đọc.
            4. Đọc sufficient verified fragments; systematic range reads có thể tối ưu theo scheme.
            5. Trả đúng một generation và validate checksum theo range/full-object semantics.

            Multipart completion

            1. Upload parts bằng session/part identity; retry một part không restart toàn object.
            2. Track accepted tags/checksums và session state, giữ upload pin.
            3. Chuẩn bị part fragments theo durability contract.
            4. Validate ordered manifest/current tags/expected checksum và head precondition trước publish.
            5. Commit object generation và retained completion result trong platform model.

            Repair không đổi logical object

            1. Scrub phát hiện missing/corrupt fragment đã biết; chọn đủ valid survivors.
            2. Allocate replacement target dưới placement epoch hiện tại.
            3. Reconstruct, verify và ghi bền replacement fragment.
            4. CAS placement manifest/generation; loser không ghi đè repair mới hơn.
            5. Old fragments chỉ reclaim sau reachability/reader/migration checks.

            Migration và cleanup

            1. Copy hoặc re-encode theo tier, giữ nguồn trong lúc verify.
            2. Publish verified target manifest/status; expose replication/restore lag.
            3. Fence reference changes trước sweep và tuân retention/version locks.

            5. Commit pointer chỉ an toàn khi bytes và GC cùng contract

            Một write có boundary rõ

            1. Prepare

              Immutable ID, allocation epoch và durable fragments.

            2. Validate

              Final checksum và manifest completeness/placement.

            3. Commit

              Conditional head/index publication với reservation fencing.

            4. Reclaim

              Orphans/old generations qua reachability và reader protection.

            Integrity failure có thể để lại staged bytes; chỉ final validated metadata publication làm object visible.

            Baseline tạo immutable object ID, reserve placement, stream/encode và chờ tất cả n fragments được chuẩn bị bền trên failure-domain layout đã chọn. Kiểm whole-object checksum sau khi body hoàn tất rồi publish sealed manifest bằng metadata CAS. Chọn all n là contract của ví dụ, không yêu cầu mọi storage system giống nhau: ACK khi chỉ đủ k fragments có thể đọc được ngay nhưng chưa có đủ redundancy mong muốn. Khi thiếu node, có thể chọn replacement target hoặc fail write theo availability policy.

            Nếu API crash trước commit, prepared bytes có thể thành orphan nhưng không xuất hiện như object nửa chừng. Tuy nhiên, reservation/pin phải giữ chúng khỏi GC trong khi commit còn có thể thành công; GC cần fence expired reservations trước khi delete và metadata commit phải reject reservation đã fenced. Sau commit, lost response là unknown outcome: lookup retained request/completion record hoặc reconcile theo API contract. Atomic head CAS không tự tạo transaction across mọi keys hay mọi external system.

            6. Erasure tolerance phụ thuộc placement

            Với systematic MDS (k data, m parity), bất kỳ k valid fragments có thể reconstruct. “Chịu m failures” ở đây là m fragments unavailable hoặc known-bad đã được loại, không phải tùy ý m zones hoặc m silent unknown errors. Nếu nhiều fragments cùng một rack/zone, một correlated fault làm mất nhiều fragments. Ví dụ 8+4 phân bố bốn fragments mỗi zone qua ba zones chịu mất một zone; mất thêm một fragment khi chưa repair sẽ vượt tolerance.

            Overhead 12/8 = 1,5 so với replication ba bản là 3,0 trong hai schemes cụ thể. Không suy mọi EC đều “nửa chi phí” mọi replication scheme, hoặc k+m fragments cần k+m availability zones. Chọn code theo placement, read pattern, repair bandwidth, encode CPU và capacity reserve. Lab mô phỏng MDS availability arithmetic, không tạo parity thật; có thể đổi layout để thấy same code nhưng khác correlated-failure behavior.

            7. Repair nhanh vừa đủ để khép vulnerability window

            Missing fragment và checksum-detected corruption trở thành repair candidates; trước reconstruct phải có đủ valid survivors đúng object/stripe generation. Basic full-stripe repair của một fragment có thể đọc k fragments rồi ghi một replacement. Systematic range reads, batching, regenerating/LRC designs có cost khác. Repair target phải respect placement và epoch, verify output rồi CAS replacement manifest; một repair worker cũ không được ghi đè placement mới.

            Throttle repair để không làm foreground traffic sụp, nhưng không kéo dài exposure tùy ý. Ưu tiên objects gần hết redundancy, account cho rebuild queues, cross-zone bandwidth và spare disk capacity. Scrubbing phát hiện latent errors ở cold data trước khi một disk failure khác xảy ra. Đặt guardrails cho firmware/deploy/deletion blast radius; mathematical parity không cứu correlated software xóa tất cả fragments hoặc encryption keys.

            8. Packing, streaming checksum và physical layout

            Tiny objects có thể được pack vào large sealed files để giảm filesystem metadata và seeks; index giữ object/fragment ID → file, offset, length và checksum. Delete logical reference không lập tức giải phóng giữa packed file; compaction copy live records, verify và publish mapping generation mới trước reclaim file cũ. Không overwrite offsets ngay khi reader cũ còn dùng mapping cũ. Packing cũng tạo read amplification/compaction trade-offs, không tối ưu miễn phí mọi size.

            Whole-object checksum chỉ được validate đầy đủ sau khi đọc hết request body, trừ khi buffer toàn body trước. Có thể stream vào staging và tính checksum đồng thời; mismatch ngăn publication rồi cleanup bytes tạm. Per-fragment checksums phát hiện lỗi đọc/scrub; full-object/range validation có semantics riêng. CRC phục vụ integrity detection, không thay authentication/cryptographic tamper protection. ETag và explicit checksum algorithm/type phải được xử lý theo API contract.

            9. Multipart manifest phải giữ đúng intent

            Multipart tách transfer thành independent parts và complete bằng explicit ordered manifest. Part number và tag/checksum phải khớp data đã accept; một writer hoặc retry khác thay cùng part number có thể làm manifest cũ invalid. Nhưng chỉ đọc lại tags rồi complete chưa chứng minh assembled bytes đúng nội dung client định gửi. Giữ expected application checksum/size và verify theo checksum type mà protocol hỗ trợ. Không giả thiếu một part number ở giữa luôn bị backend reject: một số protocols complete chính danh sách parts caller cung cấp, nên completeness của intent cần kiểm riêng.

            Concurrent overwrite của public key cần conditional completion, không chỉ uploadId. Sau conflict, re-read state và quyết định intent; không tự bỏ precondition để retry thành công. Nếu completion response mất, object có thể đã commit. Với real S3 CompleteMultipartUpload, initial HTTP 200 còn có thể chứa final error trong body, nên dùng SDK phù hợp hoặc parse final result; status header không đủ chứng minh success. Lab là platform contract đơn giản với retained completion record và exact-payload checksum model, không mô phỏng hết S3.

            Abort/lifecycle giúp reclaim unfinished parts, nhưng requests đang in-flight có thể race cleanup. Cần session fencing, bounded retry và recheck theo backend contract. Completed object có lifecycle khác với unfinished upload: abort không được dùng như DELETE của object đã publish. Retention/locks/quota và upload owner cần áp dụng cho cả staged bytes để tránh uploads bỏ dở chiếm disk mãi.

            10. Strong GET không tự thành snapshot LIST

            GET resolve key head qua linearizable metadata authority để đáp ứng read-after-write trong baseline. Gateway/CDN cache head cũ có thể phá contract dù bytes immutable, nên cần validation/lease/freshness rule tương thích hoặc đọc authority. Head và authoritative key index phải commit trong protocol đã chọn; asynchronous secondary index có thể làm PUT thành công nhưng LIST chưa thấy key. Scale metadata theo object count, versions, key length, indexes và hot namespaces, không chỉ byte payload của data plane.

            Hash full key phân bố point operations tốt nhưng prefix LIST cần scatter/merge hoặc directory index. Range partition theo (bucket,key) thuận tiện prefix scans nhưng dễ hot range và cần split/relocation protocol. Hash một prefix cố định không giải mọi arbitrary-prefix query miễn phí. Shard directory/version phải giúp cursor đi qua split đúng, tránh skip/duplicate ngoài contract; tenant quota cũng phải giới hạn broad LIST work.

            Baseline chọn LIST đọc authoritative committed indexes, có read-after-write freshness cho writes hoàn tất trước request; không hứa mọi pages cùng một point-in-time snapshot khi concurrent writes xảy ra. Cursor giữ query scope, shard-directory state cần thiết và last key theo contract. Nếu cần snapshot toàn listing, thêm MVCC/read timestamp hoặc coordinated snapshot được giữ qua cursor TTL; per-key Raft một mình chưa đủ. Real backend có loại bucket và ordering rules riêng, không áp mọi semantics của general-purpose listing lên directory bucket.

            11. Reader pin và GC fencing bảo vệ immutable generations

            Một reader đã resolve v1 phải đọc đúng v1 tới hết dù head đang là v2. Chỉ dùng head lookup lại cho từng chunk có thể trộn generations; chỉ kiểm v1 không còn head rồi delete có thể làm reader fail. Có thể giữ reader pins/leases, epoch-based protection hoặc bound lifetime/grace được chứng minh. Lease expiry cần xử lý network pause/crash, renewal và fencing; “chờ vài phút” không đủ khi reader/upload có thể kéo dài hơn.

            Reachability còn gồm retained versions, legal/retention locks, multipart sessions, snapshots, repairs và tier migrations. Mark/sweep cần consistent cut hoặc allocation-age/fencing protocol để object được publish đúng lúc sweep không bị xóa. Cleanup phải idempotent và có audit/canary/dry-run safeguards phù hợp vì GC bug có thể phá tất cả copies cùng lúc. Lab chỉ minh họa một tracked reader và một overwrite; không triển khai distributed reference counting.

            12. Delete marker khác physical erasure

            Với versioning, DELETE có thể tạo delete marker để latest lookup không thấy object, trong khi previous versions vẫn retained và có thể đọc nếu có quyền. Xóa specific version, lifecycle expiration và overwrite không mặc định giống nhau. Bucket policy, retention locks và legal holds là controls riêng; crypto-key deletion cũng có blast radius và không được dùng thay thế một deletion policy chưa rõ.

            Không suy logical 404 có nghĩa physical bytes đã biến mất khỏi replicas, packs, backups hoặc logs. Công bố retention/deletion timelines và trạng thái lifecycle phù hợp, kiểm các version/reference còn sống trước reclaim. Read authorization phải áp dụng cho versioned URLs và cached/private assets, không chỉ latest key. Repeated delete/retry cần idempotent semantics, nhất là khi event notifications có thể duplicate hoặc đến trễ.

            13. Migration verify-before-switch và restore contracts

            Tier transition có thể copy, re-encode hoặc chuyển media, tùy thiết kế; không phải mọi tiering luôn re-encode. Giữ nguồn trong khi chuẩn bị target, verify checksums/durability và publish compatible placement generation trước reclaim. Background IO cần quota và priority để migration không làm tăng read timeout hoặc kéo dài repair window. Rollback cũng cần giữ generation nguồn tới khi đủ điều kiện cleanup.

            Cold/archive classes có thể có restore delay, retrieval fees hoặc minimum-retention behavior riêng; không coi “cheaper per GB” là rẻ hơn mọi workload. API cần phân biệt object tồn tại nhưng cần restore với not found. Cache restored copies theo TTL/authorization và theo dõi restore jobs idempotently. Cost model gồm requests, stored/staged bytes, cross-zone repair, egress và restore—not chỉ disk price.

            14. Security, cells và cross-region recovery

            Tách tenant/bucket/object authorization, signed-request validation, quotas và encryption-key permissions. At-rest encryption không thay access control; mất hoặc revoke KMS key cũng có thể làm bytes còn nguyên mà không đọc được. Presigned grants phải hạn chế method/key/expiry và tránh log secrets; data-node URLs không được bỏ qua checks của object API. Audit metadata và billing cần nhất quán đủ mục đích nhưng không nên biến thành leakage của sensitive object names.

            Cell-based deployment giới hạn một số operational blast radii nếu data/metadata/control dependencies thật sự tách đúng. Async cross-region replication có lag và RPO lớn hơn zero theo contract; promote replica cần generation/fencing, delete ordering và conflict policy. Synchronous cross-region commit có latency/availability trade-off khác. Một healthy replica region không tự chứng minh metadata, object bytes và encryption keys đều đủ để restore; phải drill restore bằng evidence.

Capacity alert cần include reserve và cross-zone throughput; disk còn trống không có nghĩa repair đủ nhanh.             16. Câu hỏi về publication, durability và lifecycle

            Vẽ một overwrite có reader đang đọc v1, một part bị replace và một metadata commit mất response. Mỗi thao tác phải chỉ rõ object nào visible, bytes nào còn được bảo vệ và client biết gì sau timeout.

            Metadata commit có tự giải distributed atomicity không?

            Không. Chuẩn bị bytes đủ bền, validate manifest/checksum, giữ reservation khỏi GC và fence commit/reclaim races trước. Metadata CAS là visibility point trong protocol đó; nó không tạo transaction across mọi hệ thống.

            8+4 có chịu bốn zone failures không?

            Chỉ bảo đảm theo MDS assumption với tối đa bốn unavailable fragments. Một zone có thể chứa nhiều fragments. Tính loss theo placement/correlation, không đếm zone như một shard đơn lẻ; silent unknown corruption cũng cần integrity/error model riêng.

            ETag match có chứng minh uploaded object đúng expected bytes?

            Không chung cho mọi protocol. Tags có thể chỉ là validators; multipart tags không luôn full MD5. Manifest tag match xác nhận accepted parts phù hợp references, còn intended length/checksum/content cần validation riêng theo algorithm/type.

            Complete multipart HTTP 200 là chắc chắn success?

            Không với protocol có final embedded error như S3 completion. Parse final body/SDK result và xử lý lost reply như unknown outcome. Reconcile theo contract, không blind retry tạo version khác rồi tưởng đó là cùng action.

            Linearizable GET từng key có đủ cho LIST nhiều pages snapshot?

            Không. Cần authoritative index freshness, shard routing/split contract và nếu hứa frozen set thì retained common snapshot/MVCC cursor. Concurrent inserts/deletes giữa pages không tự được “đóng băng” bởi per-key consensus.

            Old version không là head thì có GC được ngay?

            Không khi reader, retained version, upload, snapshot hoặc migration còn reference. Dùng pins/epochs/leases với fencing; grace period chỉ đúng nếu có lifetime bounds chứng minh. Lab cho thấy GET metadata đúng vẫn fail nếu bytes bị xóa sớm.

            AFR và parity có đủ tính 11 nines?

            Không. Cần correlated failures, repair exposure, latent integrity errors, software/deletion/key-loss risks và validation evidence. Disk failure rate không bằng object loss rate, storage overhead cũng không là xác suất.

            Abort upload có xóa object đã publish không?

            Không trong contract này: unfinished upload cleanup khác object DELETE/version lifecycle. In-flight parts cần fencing/recheck; completed generation có references/retention riêng. Không dùng abort như shortcut bypass policy của public object.
