1. What do engines, servers and gateways do?

Data plane

  • Requests, model execution, KV and delivery share latency budgets.
  • Cancellation/timeouts must stop or fence outstanding work correctly.

Control plane

  • Manage artifacts/revisions, capabilities, deployments and health.
  • Administrative load/unload APIs are not automatically public tenant endpoints.

Evaluation plane

  • Track task labels, policy versions, calibration and drift.
  • Shadow work costs resources, respects privacy and avoids repeated side effects.

A serving engine handles scheduling, KV, kernels, distributed execution and sampling. Server/API layers accept requests, stream output and expose metrics. Gateways add identity, budgets, routing and application policies, while control planes manage artifacts, placement and rollouts. These are responsibilities rather than exclusive product categories; one project can provide several layers.

Existing engines are usually a sensible starting point unless requirements justify specialized execution work. No engine wins universally: architecture, hardware, precision, adapters, output constraints and traffic shape matter. Benchmark token rates under other conditions cannot replace profiling matched revisions and quality on representative traffic.

2. Compare capabilities rather than product names

This is a capability orientation checked in October 2026 rather than a benchmark or release recommendation. Pin releases/containers, model commits and runtime/hardware profiles. Backends within one engine can have different support matrices; supported features are not universal across models, quantization and parallel layouts.

3. Engine evaluation preserves quality and traffic mix

Replay lengths, arrival bursts, concurrency, reuse, applicable multimodal payloads and adapter churn. Measure queue-inclusive TTFT, token gaps/TPOT, target-qualified goodput, memory peaks, cold starts and cancellation/errors. Open-loop arrivals reveal overload that self-throttling closed-loop clients can hide. Bound workloads rather than reporting only requests that survive OOM.

Match revisions, templates/tokenizers, sampling, quality/precision and hardware allocation. Evaluate output, structured and tool semantics; numerical kernels need not yield identical tokens despite acceptable quality. Report unsupported features instead of silently dropping fields. Choose among quality, latency, cost and operational trade-offs with rollback prepared before rollout.

4. Compatible HTTP APIs still need semantic contracts

Familiar JSON shapes ease integration but compatibility needs feature-level tests. Templates/special tokens change prompts; tools require parsers/delivery rules; JSON support can be syntactic only. Seeds, stops, reasoning fields and usage can differ. Reject unsupported fields or document handling rather than silently suggesting parity.

The following teaching API is internal to this architecture rather than an engine/provider API. Requests pin logical model/adapter revisions, contract versions and overall deadlines. Gateways translate to engine calls and normalize only tested semantics, preserving authorization, capabilities, limits, attempts and cancellation.

        5. Multi-LoRA shares bases without mixing adapters

        LoRA represents an update using low-rank factors: ΔW = scale×B×A for W of shape d_out×d_in, with A shaped r×d_in and B shaped d_out×r. The delta has r(d_in+d_out) parameters. A hypothetical 4096× 4096 BF16 matrix uses 32 MiB, while a rank 16 delta has 131072 parameters or 256 KiB before metadata. This is one matrix rather than a full adapter or universal size.

        Multi-LoRA retains a compatible base and applies the correct request-specific adapter. Specialized batching/kernels can serve multiple adapters without globally merging all deltas. Arbitrary full fine-tunes do not automatically become small adapters; representation changes need supported retraining/conversion and quality validation. Check base commits, tokenizer/templates, target modules, rank, precision and backend support.

        Shared bases save weights but still require adapter memory/loading, rank-sensitive kernels, KV and tenant scheduling. Prefix/KV reuse must include relevant model/adapter/context identity rather than matching token prefixes alone. Strong isolation can require separate pools or reservations; shared computation does not meet every isolation requirement.

        6. Adapter admission and active references

        Registries issue approved immutable revisions with checksums, owners and compatibility metadata. Public requests resolve authorized identities instead of arbitrary paths/code loads. Residency follows validation. Unloading/updating waits for active references and safe kernel boundaries; reusing a slot for a new revision while old kernels run can corrupt requests.

        This is an admission snapshot rather than a running cache server. Change caller/target to see tenant/base mismatches rejected even when memory is available. Pinned candidates force WAIT without partial destructive eviction. Illustrative loading time separates payload transfer from full cold starts.

        7. Routing, cascades and shadowing follow different paths

        Routers choose eligible models before generation; cascades evaluate candidates before escalation; shadow work gathers evidence without changing user output or triggering side effects. Gateways preserve policy versions, overall deadlines and request generations across retries. The traces distinguish user-critical paths from background evidence.

        Routing selects models; serving also manages state, quality and delivery

        Component map; the complete ordered request paths are explained below.

        Upfront routing

        1. Validate tenants, capabilities, bounds and deadlines.
        2. Apply pinned routing policies with privacy-safe features.
        3. Choose one eligible pool using task/capacity evidence rather than always running both.
        4. Return output under streaming/finish contracts and current request generations.
        5. Deliver committed output with stable sequencing.

        Buffered cascade

        1. Try the small model within overall deadlines/budgets.
        2. Buffer candidates and run task-appropriate checks.
        3. Escalate only within policy/budget, paying additional cost/latency.
        4. Commit the selected answer without assuming large-model infallibility.
        5. Emit selected output rather than exposing every attempted stream.

        Admit a LoRA request

        1. Resolve approved adapter identities/revisions and caller access.
        2. Verify base/layout/tokenizer compatibility and artifact integrity.
        3. Load within residency budgets and pin revisions through outstanding kernels.
        4. Preserve request/adapter/KV identity and release references safely.

        Engine failure and fallback

        1. Classify failures/timeouts and preserve attempt/output boundaries.
        2. Fallback only to eligible capabilities/revisions within remaining budgets.
        3. Record attempts, usage, cancellation and selected results.
        4. Visible output requires explicit restart/resume rather than arbitrary answer concatenation.

        Shadow evaluation

        1. Record sampled features/routes under retention and tenant scopes.
        2. Replay eligible samples without executing tools or side effects.
        3. Review task quality, calibration and costs before rolling out a policy revision.
        Client / stream
        Request identity, deadlines, output contracts and cancellation.
        Gateway / policy
        Authentication, tenant limits, allowed models/adapters and capability checks.
        Model router
        Versioned rules/classifiers, task features, quality budgets and capacity.
        Large-model pool
        Compatible model/engine groups, admission and cancellation.
        Model / adapter registry
        Pinned bases/adapters, checksums, ownership, approved formats and capabilities.
        Adapter admission
        Authorization, base compatibility, residency and active references.
        Small-model pool
        Base weights, request-scoped adapters, batching and KV.
        Verifier / gate
        Schema/task checks or calibrated classifiers with false accepts/rejections.
        Decision / usage log
        Policy/model revisions, routes, attempts, usage and privacy-aware telemetry.
        Offline / shadow eval
        Representative labeled tasks, route slices, drift and rollout gates.
        Output commit boundary
        Buffered selection or explicit provisional protocols; separate side effects.

        8. Routers and verifiers need different evaluations

        Upfront routing can use rules, features or classifiers to choose eligible models. Prompt length describes cost rather than reliably measuring semantic difficulty. Tenant tier is a product rule rather than quality evidence. Easy/hard classification accuracy alone does not establish answer quality; evaluate model outcomes and routing errors by task slice.

        Cascades apply post-generation checks. JSON/schema validation establishes structure rather than factual or business correctness. Self-confidence needs calibration, and verifier models have cost, errors and correlated blind spots. Large fallbacks are not oracles: small models can be correct when larger ones fail. Tune gates on held-out tasks under explicit quality/latency constraints.

        Large-only correctWrongRecovered when the verifier escalates

        9. Explore policies using joint outcomes and latency budgets

        This toy evaluation declares joint outcomes instead of assuming every small-model success is also a large-model success. Default 70% easy traffic yields 76.5% small and 89.1% large accuracy. Recall 80% with 10% false escalations yields 91.13% cascade accuracy by retaining some small-only successes and recovering large-only failures. These are synthetic results; degraded verification can perform worse than small-only.

        Latency measures buffered full-answer completion rather than TTFT/token gaps. Serial small+check+large execution can miss p 95 budgets despite good means. Real runtimes do not know the ground truth used for exact expected accuracy here. Drift can change joint outcomes and gate errors together; sliders are not calibrated production models.

        The fixture applies identical gate rates to joint outcomes sharing small-model correctness. Aggregate recall alone cannot determine recovery when the gate treats large-only failures differently from both-wrong cases. Production evaluation needs joint evidence by slice; these labels are not runtime routing inputs.

        10. Where does streaming commit an answer?

        Visible small-model tokens cannot silently be recalled by a final verifier. Buffering allows output selection at higher TTFT; upfront routing can stream one selected path. Provisional/replacement events require an explicit client protocol, consistent accessibility/history and honest usage/latency measurement. Do not concatenate small and fallback outputs as one generation.

        Tools and side effects need separate commit/idempotency policies. Shadow/discarded attempts must not execute actions merely because output resembles tool calls. Overall deadlines include attempts, retries, queues and checks; cancellation propagates safely. Record attempted work separately from delivered output so cost/error analysis includes spent computation.

        11. Token costs need matching spend and output windows

        Generally, costPerMillion = windowSpend/windowTokens× 1,000,000. Hourly spend with busy-throughput T and duty fraction u gives T× 3600×u counted output tokens/hour. Whole-window throughput already includes duty, so applying u again double counts it. Duty is not GPU utilization; bandwidth-bound decoding still costs money at low utilization readings.

        Eight GPUs at an assumed $3/GPU-hour cost $24/hour. Busy output of 10,000 tokens/s at 40% duty yields 14.4M output tokens/hour, or≈$1.67/million. If 80% of output belongs to SLO-qualified requests, the denominator is 11.52M and cost≈$2.08/million qualified output tokens. Include other infrastructure/idle/retry costs and report input/prefill separately rather than padding the output denominator.

        Different tokenizers make token counts non-equivalent across models for the same task. Shorter outputs can reduce tokens while task success and per-request cost remain product concerns. Report cost per successful task and quality distributions, distinguishing provider prices, internal infrastructure costs and billable usage.

        windowOutputTPS = busyTPS * busyDuty  // only for a busy-period rate
hourlySpend = gpuCount * gpuHourlyPrice + otherHourlyCost
costPer1MOutput = hourlySpend / (windowOutputTPS * 3600) * 1_000_000
sloOutputTPS = windowOutputTPS * shareOfOutputFromQualifiedRequests
// If windowOutputTPS was measured directly, do not multiply busyDuty again.

        Define counting boundaries first; a zero denominator has no finite unit cost.

        12. Explore busy/window rates and SLO-qualified denominators

        Switch bases to see that duty applies only to busy-period inputs. The same observed 4,000 tokens/s comes from 10,000 busy TPS at 40% duty or 4,000 window TPS, producing equal cost. Basis changes redefine inputs rather than increasing capacity. Zero duty/qualification yields NONE instead of division by zero or a free-service claim.

        13. Capacity planning still separates prefill and decoding

        Four capacity-planning steps

        1. Demand mix

          Track lengths, arrivals, tasks and tenant scope.

        2. Measured pools

          Measure models/adapters, queues, verifiers and hardware.

        3. Ready capacity

          Budget peaks, failures, startup and draining.

        4. Price and evaluate

          Compare unit costs and task success, not token rates alone.

        Keep quality, traffic mixes and SLOs consistent between measurements and forecasts.

        Start with request mixes and peak arrivals. Requests/s times mean input/output lengths gives separate prefill/decode demands. Their costs differ, with nonlinear effects from context, reuse, adapters and batching. Dividing combined input+output tokens by a peak rate can mislead. Use realistic joint-load benchmarks or validated capacity models.

        Then size replicas for peaks, headroom, failures, readiness delays and warm capacity. Routing changes shift demand and adapter locality across pools; verifiers have queues and capacity too. Background batches can use idle periods only with priorities/preemption/budgets that protect interactive targets, without assuming instantaneous state/graph changes.

        14. Observe drift and bound rollouts

        Trace policy/model/adapter versions, capabilities, routing reasons, attempts, queue/compute/check times, cancellations and output boundaries. Privacy-aware sampling does not imply logging raw prompts by default. Control metadata access and prevent cross-tenant leaks through caches/adapters. Restrict artifact administration and validate formats/revisions before publication.

        Monitor task/tenant/model slices, labeled gate errors, disagreement/drift, escalations and request costs. Bound fallback storms and verifier saturation with deadlines, retries and eligible circuit policies. Engine/adapter/router upgrades need offline regression, bounded canaries/shadows and rollback. Average quality must not hide regressions in important slices.

        15. Questions with worked reasoning

        Can compatible APIs make engine replacement automatic?

        No. Test templates/tokenizers, tools/constraints, sampling/stops, stream chunks, cancellation, usage and errors under pinned versions. Replay quality/load suites and canary with rollback. Familiar JSON only reduces part of integration work.

        Does multi-LoRA immediately consolidate two hundred full fine-tunes?

        Only with compatible adapters on a shared base, or supported retraining/conversion that passes quality checks. Different bases/tokenizers/modules are not automatically compatible. Group eligible adapters, reserve/isolate capacity where needed and measure churn, KV and costs with tenant ownership enforced.

        Does schema-valid JSON justify accepting an answer?

        It establishes structural constraints rather than factual/business correctness. Use task checks and calibrated gates with measured errors. Some tasks lack cheap reliable verifiers, changing cascade economics and quality assumptions.

        Can escalation make results worse?

        Yes: falsely escalating small-only-correct cases can replace them with wrong outputs. Under fixture assumptions, quality = bothCorrect + smallOnly×(1−falseEscalation) + largeOnly×recall. Larger models and self-confidence are not oracles.

        How would a fifty-percent cost reduction preserve quality?

        Measure spend, task success, slices and SLOs, then identify tasks cheaper models solve. Validate routers/gates on held-out data with check costs and escalation tails. Bound shadows/canaries and roll back regressions; do not promise fifty percent before evidence.

        What is output cost for eight $3/hour GPUs at 10,000 busy TPS and 40% duty?

        Spend is $24/hour;4,000 window TPS yields 14.4M/hour and≈$1.67/million output tokens before other costs. A directly measured 4,000 window TPS needs no additional duty factor. At 80% qualifying output,11.52M/hour gives≈$2.08/million.

        May an active adapter be evicted when memory fills?

        Do not remove weights still referenced by kernels. Pin exact revisions, plan residency/admission and wait or queue/reject under budgets. Authorization/base validation precede hits; slot reuse waits for old references to become safe.

        How should fallback behave after small-model output has streamed?

        Use explicit restart, supported resumption or provisional/replacement semantics understood by clients. Do not silently concatenate generations. Final-answer selection can buffer candidates at added TTFT, with tool effects committed under separate policies.
