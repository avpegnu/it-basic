LLM inference: understanding prefill, decode and serving budgets

Follow tokens onto the GPU, distinguish TTFT from TPOT, calculate KV memory and protect latency when many requests share an inference engine.

1. What does the model receive and return?

An LLM consumes token IDs rather than the character strings seen by an application API. A tokenizer maps text to vocabulary-dependent units; a Vietnamese word or emoji may span several tokens. Word or character counts are not exact token counts for context validation or cost accounting.

A chat template serializes message roles, content, tool results and special tokens into a prompt. Count system instructions, history, retrieval context, schemas and template overhead. Different model templates may count and interpret role boundaries differently; arbitrary string concatenation does not preserve the same behavior.

A causal autoregressive model predicts the next-token distribution from the prefix. Sampling chooses a token using temperature/top-p or another rule. Fluent output does not mean the model queried a reliable internal database: grounding, tools and authorization belong to the application system.

2. How do prefill and decode differ?

Prefill processes the prompt and builds the input-token KV cache. Prompt positions can be processed in parallel with the appropriate causal mask; future output tokens remain unknown. Long prompts increase attention work and can delay other requests if the scheduler handles the entire prompt in one large turn.

Decode repeats: use the newest token and existing KV to compute the next token, append its key/value and continue until a stop condition. Within a sequence, the next step depends on the selected token, so the full answer cannot be generated in parallel like prefill. Independent sequences can share a batched forward pass.

Prefill often has high arithmetic intensity; small-batch decode is often limited by memory bandwidth while reading weights and KV. These are profiling hypotheses, not universal rules for all models, GPUs and batches. Long contexts, quantization, tensor-parallel communication, kernels and batch size can change the bottleneck.

3. Measure latency as the user experiences it

TTFT · Wait for the first token

  • From a defined request boundary to the first token.
  • May include queueing, network time and prefill, depending on the measurement boundary.

ITL / TPOT · Subsequent generation pace

  • ITL measures the gap between consecutive tokens.
  • Mean TPOT commonly excludes TTFT; state the calculation and token count.

Goodput · Work meeting the SLO

  • Count completed work meeting the selected thresholds.
  • Higher throughput may not improve goodput if latency exceeds the SLO.

TTFT measures from a declared start, such as request acceptance or client send, to the first token. Depending on the observation point it includes network, authentication, queuing, tokenization, prefill and stream flushing. GPU prefill time alone is not end-to-end TTFT.

TPOT is average time per output token under a declared definition; inter-token latency reveals stalls that an average can hide. For N output tokens, a simple approximation is E2E ≈ TTFT + (N−1) × TPOT when tool rounds and other overhead are negligible. Multi-token chunks require engine timestamps or another measurement convention; an SSE event is not necessarily one token.

For an assumed 0.8 s TTFT, 0.04 s TPOT and 200 output tokens, completion takes about 8.76 s. A larger batch may increase aggregate tokens/s while pushing TPOT to 0.08 s, making the same response about 16.72 s. Choose task-specific SLOs: short autocomplete needs very low TTFT, while batch summarization may prioritize throughput and cost.

Goodput counts requests/tasks completed within declared SLOs. A high aggregate tokens/s configuration can have low goodput if most requests are late. Report throughput with workload, admission/queue policy and TTFT/TPOT compliance rather than comparing peaks without latency.

4. KV cache: budget memory before increasing concurrency

Each attention layer stores keys and values for processed tokens. For a conventional attention architecture, KV payload per token is 2 × layers × KV heads × head dimension × bytes per element. The factor two represents K and V, not batch size or replicas. GQA/MQA use fewer KV heads than query heads, so substituting query heads can overestimate memory. Architectures such as latent attention require their own formula.

With 32 layers, eight KV heads, head dimension 128 and two-byte BF16, each token needs 131,072 bytes, or 128 KiB. An 8,192-token sequence needs 1 GiB of payload; 16 sequences need 16 GiB, about 17.18 decimal GB. Keep GB/GiB consistent and count both input and generated tokens still retained.

GPU memory also holds weights, activations/workspace, runtime buffers and allocator reserve. An eight-billion-parameter model at two bytes per parameter has about 16 GB of weights before overhead; dividing the full device capacity by KV size does not give realistic concurrency. Tensor/pipeline parallelism may distribute memory, but implementation-specific KV replication, head divisibility and communication matter.

5. Why does paged KV improve memory utilization?

Reserving a contiguous maximum-context buffer per request wastes space for short prompts and early finishes. Dynamically growing contiguous buffers also fragments memory. Paged KV allocates blocks and maps logical token blocks to physical blocks through a block table, so a sequence can grow without one large contiguous physical region.

Paging does not inherently shrink the KV payload for the same tokens. It reduces reservation and fragmentation waste; the final block can still have internal fragmentation. Prefix caching can share immutable prefix blocks and copy on write when sequences branch. Reuse depends on token prefixes, model/tokenizer/adapters and other KV-affecting state; identical text does not always imply identical tensors.

Prefix caches have isolation and privacy implications. Keys should separate tenants where data must not be shared; hit/miss timing can reveal prior prefix use. TTL, eviction and memory budgeting must balance cached prefixes against active KV; retaining old prefixes can starve running requests.

5a. Roofline: understanding memory-limited decoding

Consider a simplified dense autoregressive model. A decode step reads weights and active sequences’ KV and performs matrix operations. Linear layers require roughly 2 × parameter count × batch FLOPs; minimal memory traffic is weight bytes + batch × context length × KV bytes/token. This is a reasoning bound, not a description of every kernel or attention architecture.

Arithmetic intensity is FLOPs per byte moved. Roofline bounds attainable FLOPs/s by min(peak compute, bandwidth × intensity). Small batches reuse weights across few sequences and have low intensity; larger batches improve reuse while increasing KV traffic and step time. Long contexts reduce intensity through more KV reads.

These assumptions omit attention FLOPs, communication, launch overhead, cache effects and kernel efficiency. Therefore max(memory time, compute time) is a model latency lower bound, not a real-latency prediction. Attractive throughput ceilings do not constitute serving capacity when memory does not fit or TTFT/TPOT targets fail.

6. Static batches, continuous batching and fairness

Static batching groups requests and waits for the whole group to finish before replacing it. One long sequence leaves finished slots idle. Continuous batching updates active sequences between steps: finished requests leave and new ones enter within budget. Utilization can improve, but a policy is still needed to prevent long prompts from stalling active decodes.

Chunked prefill splits long prompts into pieces interleaved with decoding. It adds scheduling overhead and may affect long-prompt throughput/TTFT. A per-step token budget differs from a sequence-count cap: 64 short requests and 64 long prompts do not create equal work or KV demand.

Fairness can use per-tenant concurrency caps, token-weighted admission and separate interactive/batch priorities. Expired deadlines should cancel requests and reclaim KV rather than spending GPU time after a client leaves. A client timeout without engine cancellation creates ghost work and worsens queuing.

A request’s loop inside an inference engine

Component map; the complete ordered request paths are explained below.

This is a logical teaching architecture, not a guarantee about a particular implementation. Decode revisits the scheduler until stopping.

Prefill

  1. Validate the token budget and enqueue with a deadline.
  2. Admit only within available budget and priority policy.
  3. Run the prompt or one prompt chunk.
  4. Store prompt keys/values in the block pool.
  5. Select the first output token from logits.
  6. Send the first token to the client and record TTFT.

Decode / release

  1. Batch active sequences and advance each by a decode step.
  2. Read prefix KV and append new KV; free blocks must remain.
  3. Select the next token and check stopping conditions.
  4. Flush the token/chunk under the streaming policy.
  5. If not stopped, schedule the next turn; cancellation removes the active request.
  6. On completion, release blocks with no remaining references.

7. Capacity planning requires more than requests/s

Two workloads at ten requests/s can differ by orders of magnitude in token demand. Specify input/output-length distributions, prefix reuse, bursts, model mix, concurrency and SLOs. Benchmarks with very short prompts/outputs mispredict production with long documents and tool histories.

Assume 20 requests/s averaging 1,000 input and 200 output tokens: input demand is 20,000 tokens/s and output demand is 4,000 tokens/s. Do not add them and divide by throughput measured on an unrelated workload; prefill and decode compete through batches and scheduling. Benchmark a representative workload and find the region satisfying both TTFT and TPOT SLOs.

Little’s Law for a stable system gives average requests in the system L = arrival rate λ × mean time in system W. At 20 requests/s and ten seconds, about 200 requests are in the system, including queued and running requests. This is not the number of sequences that must fit on one GPU; separate queue waiting from active residency and budget KV by live lengths.

8. Optimization levers and when they apply

Weight quantization reduces weight memory and may reduce bandwidth, but speed depends on kernels/hardware and quality must be evaluated on real tasks. KV quantization is a separate choice affecting context memory and potentially long-context quality. Four-bit weights do not imply four-bit KV.

Speculative decoding proposes a group of tokens using a draft model or another mechanism, then verifies them with the target. Benefit depends on acceptance and draft/verification overhead; there is no fixed speedup. Exact-sampling algorithms are designed to preserve the target distribution when implemented correctly, but not every speculative mode in every engine has identical semantics.

Disaggregating prefill and decode separates their resources and scheduling, but requires transferring KV over the network and handling ownership/failover. It helps only when transfer and operational costs are outweighed by isolation/utilization benefits. A simpler engine on a few GPUs is often easier to operate and may be preferable initially.

9. Failure modes and safe limits

Do not wait for CUDA OOM to control load. Admission needs input-plus-output reserve or an explicit preemption policy for KV growth. Output caps, context limits, queue caps and tenant quotas are distinct limits. Early overload rejection with retry hints is often preferable to accepting requests that all time out.

10. Make benchmarks reproducible

Record model revision, tokenizer/chat template, engine version, quantization, GPU topology, driver/runtime and scheduler parameters. Workloads should capture realistic prompt/output lengths and arrivals, including bursts, cancellation and long-context tails. Declare warm-up and prefix-cache state so cold and warm runs are not compared as equivalents.

Report p50/p95/p99 TTFT, TPOT/ITL, end-to-end latency, accepted/rejected requests, input/output tokens/s, active/queued sequences, KV utilization and cost per successful task. Increase load until SLOs begin failing to find the operating envelope; peak tokens/s after latency collapses is not interactive serving capacity.

11. Check your understanding

Does a KV cache store old answers?

KV holds prefix-token key/value tensors for attention reuse. It differs from a response cache returning a saved answer. Prefix reuse can reduce prefill for a new request that still needs decoding; response caching has separate freshness, identity and policy semantics.

How does growing context from 8K to 32K affect KV?

With the same layers, KV heads, dtype and sequence count, KV payload grows fourfold. Time need not scale by exactly four: attention work, kernels, cache locality and scheduling can change. At 128 KiB/token, 32,768 tokens need 4 GiB of KV per sequence.

Why can users see slow responses at 100% GPU utilization?

Utilization says nothing about individual deadlines. Large batches, long prompts and queues can maximize GPU work while worsening TTFT/TPOT. Inspect latency by input length/tenant and adjust admission, scheduling or resources.

Exercise: 131,072 bytes/token, 16K tokens and 24 sequences need how much KV?

If 16K means 16,384 tokens, each sequence needs 2 GiB; 24 need 48 GiB, about 51.54 decimal GB. This is only KV payload, excluding weights/workspace/padding. The worksheet’s 40 GB KV budget is insufficient.

Can we automatically retry a broken stream?

Before the first byte, retry under an appropriate policy and idempotency contract. After text has streamed, a retry may generate different or repeated content; use generation IDs, incomplete state and explicit UI behavior. Cancel the old generation to avoid disconnected work continuing to consume GPU resources.

Explain and compare the mechanisms

These open questions connect terminology to state, assumptions and failure boundaries. Try an example from your own work before comparing the explanation.

How do prefill and decode differ within an LLM request?

Prefill processes prompt tokens and builds generation state, often exploiting parallelism across prompt positions. Autoregressive decode produces successive tokens while reusing and extending context KV. Long-prompt prefill is often compute-intensive, while small-batch decode can be bandwidth-sensitive. These are workload-dependent tendencies, not universal classifications.

Distinguish time to first token, per-token intervals and end-to-end latency. Large prefills can interrupt existing decode streams, motivating chunking and admission policies. Continuous batching admits or removes requests between iterations, improving reuse of freed capacity without eliminating KV limits, unfairness or delivery buffering. Benchmark actual prompt/output distributions and report tails by workload slice.
