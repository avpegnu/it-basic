Prompting & Structured Output: contract, schema và tool boundary

Quản lý prompt như một versioned interface; hiểu few-shot, token masks, response envelopes, schema/business validation, bounded repairs và tool execution được authorize bằng code.

Một request có nhiều contract boundaries

  1. Assemble

    Pin prompt/model/schema và provenance của input.

  2. Generate

    Supported constraints, context/output/deadline budgets.

  3. Validate

    Envelope → parse → schema → task rules.

  4. Consume / authorize

    Typed data, scoped tools, effect/receipt và audit.

Không chuyển quyền từ model text sang application chỉ vì JSON parse thành công.

  • Prompt là một phần của contract có input, owner, revisions, consumers và eval gates.
  • Roles/delimiters giúp biểu đạt instructions/data nhưng không thay authorization hoặc loại bỏ prompt injection.
  • Syntax, supported schema, source truth và permission là các lớp kiểm tra khác nhau.
  • Grammar mask lọc token pieces theo parser state; truncation/refusal vẫn cần xử lý ở envelope.
  • Tool calls là proposals; side effects cần scoped authorization, validation và durable idempotency contract.
  • Temperature 0, majority votes hoặc retry không tự tạo correctness/determinism; cần evidence và bounded budgets.

1. Prompt là versioned interface

Lifecycle của prompt contract

  1. Registry

    Owner, immutable revision và inputs/outputs.

  2. Eval gate

    Cases thường gặp, edge cases và untrusted data.

  3. Canary

    Bounded traffic, quality/cost và rollback.

  4. Observe

    Trace revisions, attempts và outcomes.

Version behavior, không chỉ version string literal.

Một prompt package gồm task instructions, input template, examples, tool definitions, output contract và failure policy. Model revision, tokenizer/chat template, schema dialect/backend và sampling settings cũng ảnh hưởng behavior. Version một câu instruction nhưng không biết model/template đang dùng thì chưa đủ reproduce hoặc audit. Lưu immutable revisions, owner, rationale và eval suite cho mỗi contract.

Log contract identifiers và relevant configuration trên mỗi logical request/attempt, không mặc định log toàn bộ sensitive input. Một one-word change có thể đổi outputs ở nhiều task slices. Rollout qua offline eval, canary với quality/error/cost thresholds và rollback; migration nhiều call sites cần compatible inputs/outputs và explicit deprecation.

2. Roles và trust boundaries

Privileged rules

  • Version instructions và tool scope ở server-controlled template.
  • Không đưa secret không cần cho task vào context.

Task data

  • User/retrieved/tool text có provenance và bounded size.
  • Quote/delimit để rõ ngữ cảnh; vẫn giữ untrusted status.

Execution authority

  • Principal, resource và action do backend xác minh.
  • Model chỉ đề xuất tool/arguments, không cấp quyền.

Chat APIs có thể cung cấp system/developer, user, assistant và tool channels với naming/priority khác nhau theo contract. Durable instructions nên đặt ở privileged channel được engine/provider hỗ trợ; user text, retrieved documents và tool output được coi là untrusted data. Không chèn chúng vào privileged instruction template chỉ vì đã escape dấu ngoặc.

Clear delimiters, typed templates và provenance giúp model phân biệt task/data và giúp người đọc debug. Chúng không là sandbox, không guarantee model bỏ instructions nằm trong document và không thay permission checks. XML escaping chống delimiter collision ở presentation layer, còn prompt injection là vấn đề semantic trust rộng hơn. Secrets và privileged tools chỉ được cấp theo application policy, không dựa vào model tự nói “được phép”.

3. Zero-shot, few-shot và dynamic examples

Zero-shot dùng instructions không có task demonstrations; few-shot thêm labeled examples trong context mà không cập nhật weights; dynamic few-shot chọn examples từ một approved pool. Examples có thể làm rõ label boundaries, output formatting và abstention, nhưng cũng tốn context/latency và có thể làm model copy irrelevant surface patterns. Không có số examples luôn tối ưu cho mọi model/task.

Chọn examples cover ambiguous/negative/edge cases, cân label mix và không leak test answers. Dynamic retrieval cần tenant access, freshness/version và separation giữa training examples và evaluation cases. Đánh giá zero/fixed/dynamic trên cùng task suite và total token budget, thay assume retrieval luôn tốt hơn. Input schema cần units, null/unknown policy và task-specific meaning để tránh model phải đoán.

4. Giải thích và reasoning cần mục tiêu đo được

Một số tasks multi-step hưởng lợi từ intermediate demonstrations hoặc planning, nhưng không suy ra mọi model cần yêu cầu “think step by step” ở mọi call. Explicit reasoning có thể tăng cost/latency và tạo rationale nghe hợp lý cho answer sai. Với code consumers, yêu cầu concise justification hoặc externally verifiable evidence khi có ích; giữ machine-readable final output contract riêng.

Đo answer accuracy/task success, evidence validity và latency thay chấm độ dài giải thích. Model-generated rationale không là proof và không cấp quyền thực thi. Nếu lookup, parser hoặc deterministic rule giải chính xác task, dùng nó thay thêm probabilistic generation chỉ vì có LLM trong hệ thống.

5. Ba lớp structure và một lớp truth

Asking for JSON chỉ là instruction; JSON-constrained mode nhắm JSON syntax; schema-constrained decoding áp supported schema/grammar subset. Mode names và guarantees phụ thuộc backend/version. Cần test unsupported keywords, enum, additional fields, optional/null và envelope outcomes. Không hứa every response parses: refusals, cancellation, output limits và transport errors cần handling ngoài domain schema.

Một output {"status":"closed"} có thể đúng syntax và schema mà sai source facts vì ticket còn open. Schema có thể express một số rules nhưng không tự có external world state hoặc business authorization. Typed output giúp downstream code rõ hơn; correctness vẫn cần source evidence, domain rules, quality evals và explicit unknown/abstain behavior.

6. Token mask hoạt động theo generated prefix

Grammar matcher theo dõi output prefix và xác định token pieces nào vẫn có thể dẫn tới permitted completion. Disallowed logits có thể bị set −∞ trước sampling/renormalization. Một model token không nhất thiết trùng JSON terminal: piece có thể chứa closing quote, comma và phần key tiếp theo. Tokenizer byte representation, escaping, vocabulary padding và EOS handling phải match engine; grammar compiler/cache cũng có compile cost và memory limits.

Lab dùng finite language gồm sáu exact strings, không compile full JSON Schema. Nhìn một piece đi qua nhiều boundaries, compare free generation với masked generation và giảm step budget để thấy valid prefix chưa đủ complete output. Đây là scripted logits/greedy choice, không model benchmark; local masking chỉ mô tả allowed structure, không proof về truth hoặc exact global conditional distribution của mọi constrained sampler.

7. Viết schema và parser contract rõ

Trong JSON Schema, properties mô tả known fields nhưng không làm chúng required. required khai báo fields bắt buộc; additionalProperties:false chặn unknown fields trong scope của schema đó. null khác missing và cần allowed type nếu hợp lệ. allOf không đơn giản merge object declarations; oneOf yêu cầu đúng một branch, anyOf ít nhất một branch. Pin dialect và supported backend subset trước dùng recursion hoặc complex combinations.

Strict JSON không có preamble/Markdown fences, NaN/Infinity hoặc trailing commas. Duplicate keys có interoperability risks và parser behavior khác nhau; nếu application cần reject thì dùng parser/check có khả năng đó trước khi duplicate bị mất trong object mapping. Đặt byte/depth/array limits trước expensive parsing/validation. Không salvage tùy ý bằng “lấy từ dấu{đầu đến}cuối” để âm thầm đổi contract.

8. Envelope → parse → schema → trusted evidence

Thử các outputs có extra field, string thay integer, missing field, semantic mismatch và refusal/truncation. Pipeline phân loại envelope trước parse, structural validation trước source comparison. Mismatch với trusted fixture là evidence cụ thể; nếu không có trustworthy source, validator không tự biết answer đúng và không nên báo semantic pass chỉ vì JSON hợp lệ.

9. Theo dõi từng boundary của một prompt platform

Prompt assembler ghép approved instructions với bounded data; output consumer chỉ nhận typed result sau validation. Tool dispatcher có authority boundary riêng và repair loop có resource budget riêng. Traces bên dưới cũng cho thấy version rollout thuộc evaluation/control plane, không phải model tự sửa prompt production mỗi lần lỗi.

Từ prompt revision tới output và authorized effect

Sơ đồ các component; các luồng request được giải thích đầy đủ theo thứ tự bên dưới.

Chọn trace cho structured extraction, tool proposal, bounded repair, incomplete/refusal hoặc rollout. Trust boundaries do application code giữ, không do dấu phân cách trong prompt.

Structured extraction

  1. Validate typed input và principal; pin task contract.
  2. Resolve exact prompt/schema/model/template revisions.
  3. Gắn provenance và đưa bounded untrusted data vào đúng input channel.
  4. Generate trong token/deadline budget với supported constraints.
  5. Inspect outcome trước khi coi text là domain JSON.
  6. Chỉ parse intended complete payload; validate types/rules.
  7. Deliver typed result hoặc explicit fallback/error.

Tool proposal tới effect

  1. Model proposes tool name/arguments; chưa là execution permission.
  2. Validate completion/call identity, schema và business constraints.
  3. Authorize current principal đối với resource/action trong server code.
  4. Check operation identity/version, commit effect và durable receipt theo transaction contract.
  5. Return sanitized result có call identity; repeated delivery không tạo effect mới.

Validation failure và bounded repair

  1. Classify structural/business error, redact unnecessary data và check remaining budget.
  2. Only allowed repair context; không mở rộng tools hoặc principal permissions.
  3. One bounded new attempt dưới same logical task contract.
  4. Re-check completion/refusal thay assume repaired output hợp lệ.

Truncation hoặc refusal

  1. Generation limit/refusal/cancel được phân loại riêng.
  2. Policy chọn retry/reduce context/fallback trong bounded budget; không salvage tùy ý.
  3. Trả explicit error/fallback khi không có complete validated result.

Version và rollout prompt

  1. Evaluate candidate revision trên pinned representative/adversarial cases.
  2. Approve canary/rollback gate bằng quality/cost/error evidence.
  3. Resolve immutable approved revision; log version và schema/tool contract.

10. Function calling là proposal interface

Tool definitions khai báo name, description và argument schema giúp model đề xuất operation. Dispatcher phải allowlist tool name/version, validate complete arguments, bind verified principal, authorize resource/action và áp dụng limits/state preconditions. Tool description “chỉ dùng cho owner” giúp model hiểu, không ngăn unauthorized backend call. Tool results cũng là untrusted context khi đưa lại vào model.

Side effects cần stable logical operation identity và idempotency semantics do backend enforce. Một arbitrary key do model bịa không tự deduplicate retries; scope/fingerprint, durable result, key reuse/expiry và atomicity với effect phải rõ. Nếu effect ở external system, local receipt một mình không giải ambiguous outcome; cần cooperating idempotency/reconcile protocol. Không execute partial streamed arguments hoặc unverified drafts.

11. Bounded repair và failure taxonomy

Một loop có điểm dừng

  1. Classify

    Envelope, parse, schema, business hay auth failure.

  2. Budget

    Remaining deadline/tokens/attempts/cost.

  3. Allowed repair

    Only eligible errors với scoped context.

  4. Revalidate / stop

    Same boundaries hoặc explicit fallback/error.

Repair không được mở rộng authority hoặc bỏ qua validation.

Structural error

  • Parse/schema failure có thể vào allowed repair; gửi exact bounded error và schema revision cần thiết.
  • Revalidate cả envelope và domain rules sau repair; không tự cấp PASS vì model nói đã sửa.

Incomplete / refusal

  • Xem finish reason và remaining deadline/token budget; chọn retry, scope nhỏ hơn hoặc typed fallback theo policy.
  • Refusal không phải JSON domain object bị thiếu dấu ngoặc; không đổi nó thành success rỗng.

Business / authorization denial

  • State conflict có thể cần reload evidence; permission denial giữ nguyên authority boundary.
  • Không retry để đổi caller, bypass blocker hoặc tạo key mới nhằm ép effect lặp lại.

Parse/schema errors có thể repair khi policy cho phép; gửi bounded sanitized error/context, không thêm privileges. Business/auth denial không nên retry mù để model tìm cách bypass. Output limit có thể cần smaller scope hoặc larger allowed budget; refusal có handling riêng. Mỗi attempt dùng overall deadline/token/cost cap và logs cùng logical request; repair success rate phải đo chứ không hứa một lần sửa là đủ.

Sau budget exhaustion, chọn explicit typed error, deterministic fallback, quarantine/review hoặc abstention theo application. Không crash cả batch vì một malformed item, không default “ok” để che lỗi và không execute tools trong repair/shadow attempts chưa được authorize. Preserve error reason và attempt count để distinguish model-quality issue với unavailable engine hoặc incompatible schema.

12. Temperature, seeds và caching không tạo truth

Temperature 0 thường chọn greedy token theo engine contract, nhưng tiny numerical differences/near ties, batch-dependent kernels hoặc changed revisions có thể đổi output. Seed có semantics riêng theo backend và không universal bitwise reproducibility. Pin revisions/settings và đo variation; reproducibility yêu cầu kiểm cả execution environment nếu task cần mức đó.

Response cache có thể giúp repeatability nhưng key cần tenant/access scope, normalized input có semantics an toàn, prompt/model/adapter/template/schema/tool versions và relevant data freshness. Không normalize làm mất meaning hoặc dùng cache cross-tenant để lộ outputs. Majority voting tăng cost và có thể lặp correlated errors; không thay correctness evidence hoặc permission checks.

13. Đưa prompt changes qua eval và canary

Eval matrix nên có normal/ambiguous/negative cases, null/missing, long inputs, multilingual data, injected instructions, unsupported schema, refusals, truncation và retry/cancel. Đo parse/schema rates riêng field-level/source accuracy, abstention, unauthorized proposal/execution rates, tool correctness, cost và latency tails. Một schema-valid rate 100% không che semantic regressions.

Mỗi call site cần typed adapter và exact contract revision; consumer migration tránh silently treating new labels như old semantics. Canary có bounded traffic/cost, per-slice gates và rollback về approved version. Telemetry phải privacy-aware, đủ trace model/prompt/schema/tool revisions và logical attempt nhưng không expose secrets/tool credentials. Prompt platform là software lifecycle với probabilistic component, không tập string literals rời rạc.

14. Câu hỏi và lời giải

Invalid JSON làm downstream crash thì sửa ở đâu?

Dùng supported structured generation nếu phù hợp, nhưng consumer vẫn kiểm envelope/parse/schema và domain rules. Bound repair rồi typed fallback/quarantine; đo field accuracy riêng structural rate. Không assume invalid 2% là toàn bộ lỗi quality.

Vì sao valid prefix có thể không parse được?

Grammar cho prefix còn có đường tới completion, nhưng max tokens/cancel có thể dừng trước closing structure. Check finish envelope và không consume partial streamed object như complete result. EOS cần matcher state phù hợp.

Escaping ticket text có chặn prompt injection không?

Escaping/delimiters giúp presentation và tránh delimiter collision, không guarantee instruction hierarchy được tuân thủ. Giữ untrusted provenance, limited tools và server authorization. Permissions phải chặn effect ngay cả khi model bị tác động.

Có properties thì fields đã bắt buộc chưa?

Chưa. required kiểm presence; additionalProperties quản unknown fields trong schema scope. null khác missing và phải hợp allowed type. Pin dialect/backend subset, test combinations thay giả định allOf merge fields như object spread.

Tool call có schema đúng thì execute được chưa?

Chưa. Bind principal đã verify, allowlist tool/version, authorize resource/action, kiểm state/version/limits và operation identity. Proposal không cấp quyền; partial arguments hoặc discarded attempts không được tạo side effects.

Commit thành công nhưng response mất thì retry ra sao?

Retry same logical key/fingerprint trong proper scope để đọc durable result. Effect+receipt cần atomic hoặc cooperating external idempotency/reconcile contract. New arbitrary key có thể bỏ dedup; reused key khác arguments phải reject.

Temperature 0 và seed có đủ để test exact output không?

Không universal. Pin model/template/settings, kiểm backend/environment guarantees và numerical variation. Test semantic/domain properties khi exact token equality không là contract; cache không tự sửa answer sai hoặc stale data.

Muốn migrate 50call sites sang prompt registry thì làm gì?

Inventory inputs/consumers, tạo typed versioned contracts và baseline evals. Thêm adapters/capability checks, migrate từng cohort sau canary, trace revisions và giữ rollback. Đo quality/cost/error theo slice; không chỉ move string vào database rồi gọi là versioning.
