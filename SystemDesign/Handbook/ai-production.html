1. Application boundary và model gateway

Một model call là dependency có latency, quota, cost, data handling và behavior contract. Có thể dùng shared gateway để gom routing, request normalization, attempt limits, cache policy và usage attribution. Không phải mọi project đều cần một gateway service riêng ngay từ đầu: một internal module với explicit contracts có thể đủ; tách service khi ownership/scale/isolation yêu cầu. Gateway cũng là dependency cần capacity, availability và rollout riêng.

Application vẫn quyết định task, user intent, business rules và allowed evidence/actions; resource server vẫn enforce object-level auth. Không chuyển mọi policy sang một prompt hoặc để caller tự chọn tenant/model endpoint không hạn chế. Gateway cần trusted principal/feature context và chỉ route tới endpoints đáp ứng data/capability policy. Nếu gateway lỗi, degraded mode phải là quyết định product có chủ đích, không trả arbitrary cached output cho mọi user.

Từ product request đến stream, usage và quality evidence

Sơ đồ các component; các luồng request được giải thích đầy đủ theo thứ tự bên dưới.

Theo trace cache hit, model miss, fallback, cancellation hoặc rollout. Gateway chuẩn hóa cross-cutting controls nhưng app/resource servers vẫn giữ business semantics và authorization.

Trả cached response đúng scope

  1. Bind request/principal và intended task/context.
  2. Render pinned prompt/profile và exact cache identity.
  3. Lookup theo scope/dependencies và revalidate permission.
  4. Return eligible answer/provenance; hit không bypass task constraints.
  5. Serve declared completed response/generation.

Model miss và usage

  1. Pin supported route/model/template capabilities và data policy.
  2. Atomically admit request/token/concurrency/spend reservations.
  3. Start bounded attempt và first-content/overall deadlines.
  4. Deliver framed output qua app/gateway với generation identity.
  5. Reconcile authoritative usage; preserve unknown exposure khi thiếu evidence.
  6. Record attempt/config/finish/cache metadata theo data policy.

Fallback có commit boundary

  1. Retryable error hoặc first-content deadline trước visible/effect commit.
  2. Check remaining deadline, retry budget và fallback capacity.
  3. Use qualified capabilities/data endpoint, không blind provider swap.
  4. Return fresh answer; after partial content cần explicit generation restart.

Client rời đi

  1. Signal abort; client disconnect không tự chứng minh upstream stop.
  2. Stop queued work và request provider cancellation.
  3. Propagate abort theo supported contract.
  4. Settle actual usage hoặc preserve unknown until reconcile.

Deploy prompt/model có evidence

  1. Evaluate candidate prompt/model/retriever/safety configuration.
  2. Qualify task slices, latency/cost và fallback scenarios.
  3. Expose bounded candidate mapping, preserve rollback profile.
  4. Review drift/incidents và cost/quality per feature.

2. Streaming UX: first content không phải response headers

Output có trạng thái rõ

  1. Waiting

    Headers/heartbeat khác first answer content.

  2. Provisional output

    Stream framed chunks, giữ generation ID.

  3. Complete / validate

    Finish reason, parse/schema và task constraints.

  4. Partial failure

    Giữ partial/error hoặc explicit restart, không splice.

Client không chỉ có boolean loading=false cho cả success lẫn partial failure.

Phân biệt time to response headers, first transport event/heartbeat, first meaningful model content, inter-chunk gaps và total completion latency. Một HTTP 200 hoặc SSE heartbeat không chứng minh model đang trả answer. Định rõ TTFT đang đo provider token, server chunk hay first visible content; tokenizer/chunking/buffering làm các thời điểm khác nhau. Đo p50/p95/p99 theo route/task/length và include failures/timeouts theo SLO contract, không chỉ successful fast calls.

SSE dùng text/event-stream, UTF-8 và event framing; network chunk không luôn là một SSE event hoặc một token. Parser cần incremental decoding, multiline data fields và event boundaries. Native EventSource thường phục vụ GET event streams; authenticated POST generation thường dùng fetch streaming hoặc một request-then-subscribe design phù hợp. WebSocket có hai chiều nhưng thêm connection/session complexity; chọn theo interaction contract, không vì tên protocol.

Partial JSON thường chưa parse được và cũng chưa qua schema/business checks. Có thể render provisional text nhưng không execute tools hoặc commit business action dựa trên half payload. Define completion/error/abort events, finish reasons và request/generation IDs; app-level sentinel như [DONE] không là yêu cầu chung của SSE. Reconnect chỉ resume đúng nếu server có retained event cursor/replay contract, không tự regenerate một answer khác rồi nối vào đoạn cũ.

3. Deadline, fallback và visible commit boundary

Dùng connection/setup, first-content, idle và overall deadlines phù hợp với workload; không reset model first-content deadline chỉ vì transport heartbeat. Retry/fallback phải còn đủ end-to-end time và budget, không nhân mỗi attempt timeout vô hạn. Slow first content là một tín hiệu quan trọng nhưng không phải lúc nào tốt nhất: queueing, network, context length và provider state cần diagnosis.

Trước visible content, một fresh qualified attempt có thể thay thế failed generation nếu không có unsafe external effect. Sau content đã hiển thị, silent retry tạo duplicate/spliced answers; dừng với partial-error state hoặc explicit restart bằng generation mới và UI giải thích. Với tool-enabled requests, effect commit có thể xảy ra trước first visible text, nên “chưa stream token” không tự làm retry safe.

COMPLETE chỉ là stream fixture state; còn parse/schema/task checks ở application. Generation đổi khi explicit restart sau visible content; cancellation chưa xác nhận remote stop hoặc final bill.

4. Ba kiểu cache: response reuse và prefix reuse

Exact response cache tránh model call bằng trả output đã có cho cùng effective request identity. Semantic response cache mở rộng matching theo similarity nhưng có false-hit risk: gần vector không chứng minh cùng intent, tenant, time hoặc answer conditions. Provider prompt/prefix caching tái dùng phần input/prefill work được support; output vẫn được generate và billed theo actual contract. Đây là ba lớp khác nhau, có thể phối hợp nhưng không cộng hit rates tùy tiện.

CacheWork được reuseCần kiểm
Exact responseEligible full outputEffective identity, freshness, permissions và task semantics
Semantic responseOutput cho query tương tựLabeled false hits, intent/scope và fallback on miss
Provider prefixSupported prompt-prefix/prefill stateExact prefix rules, eligibility/TTL, writes/reads và output charges

5. Cache identity, invalidation và current authorization

Một response-cache identity có thể gồm principal/tenant permission scope, task/locale, canonical effective input, model/revision, generation parameters, prompt/template, tools/schema, evidence/source/policy versions và freshness window. Không nhất thiết đưa raw secrets vào key: dùng canonical IDs/hashes theo privacy policy. Hash đầy đủ text không giải quyết mutable dependency không có trong text, clock-based questions hoặc resource auth đã bị revoke.

TTL giới hạn age nhưng không tự là invalidation correctness. Source update/delete, ACL changes hoặc policy revision có thể cần namespace/version change, targeted invalidation và current permission check trước trả sensitive data. Không cache một external side effect như một answer rồi replay tool writes; effect receipts có semantics/idempotency contract riêng. Exact caching không tự “an toàn tuyệt đối” chỉ vì string match.

6. Đánh giá semantic cache bằng labeled mistakes

Tạo task/locale/tenant/time slices và negative pairs gần nhau nhưng khác meaning: refund versus exchange, “không được” versus “được”, product edition khác hoặc policy vừa đổi. Đo false accept, false reject, stale/unauthorized hits và quality sau fallback. Threshold cần dựa trên actual embedding/metric/index và workload, không dùng một universal 0.9. Candidate retrieval, relevance validation và permission là các bước khác nhau.

Nếu dùng model validator sau similarity, tính thêm latency/cost và grader errors; validator không thay deterministic access rules. Low-risk FAQ public có thể khác financial/account-specific answers; policy có thể disable semantic reuse cho task nhạy cảm. Rollout cache policy qua eval/canary, giữ cache provenance/age/hit type trong trace để diagnosis.

Exact string equality không thay current tenant/access/dependency checks. Permission revocation cần current access guard ngay cả khi cached request identity không đổi.

7. Provider prefix cache: eligibility và accounting

Đặt stable instructions/tools/reference prefix trước changing query khi provider supports matching như vậy. Exact segment matching, minimum cacheable tokens, supported models, TTL, workspace/organization isolation và cache write/read accounting tùy endpoint/version; kiểm docs/config hiện tại thay đoán. Không đổi prompt order chỉ để cache nếu làm hỏng task semantics hoặc model behavior.

Cache hit input discount không xóa output generation cost hoặc guarantee total latency tốt hơn cho mọi request. Cache creation/storage/refresh có thể thêm phí; cold traffic và prefix churn thay economics. Prefix cache isolation của provider không tự thay per-user authorization trong app dùng shared organization credentials. Không ghi provider-specific TTL/discount thành constant universal trong product code.

8. Conditional hit rates và unit economics

Nếu exact hit rate e tính trên mọi requests, semantic hit rate s tính trên exact misses, semantic share toàn traffic là (1−e)s và model share là (1−e)(1−s). Với 100000 requests, e=20% và s=10%, có 20000 exact, 8000 semantic và 72000 model calls. Nếu 2% semantic hits sai thì expected wrong cached answers là 160 trong fixture assumptions, không 2% toàn traffic.

Worksheet dùng fixed hypothetical token inventory và prices để tách response avoidance với prefix discounts. Lookup embeddings dùng query tokens, không mặc định embed toàn rendered prompt/system context. Full production economics còn có retrieval/rerank, cache infrastructure/write fees, retries/fallbacks, tools, human review và failed tasks. Không suy saving cao là quality tốt; track cost per successful task cùng quality/severity và overall spend.

Bật semantic lookup là một quyết định riêng với observed hit rate. Một window không có hit vẫn có thể thực hiện mọi embedding lookup và trả phí; chỉ khi bypass/disable lookup mới loại khoản đó. Lab giữ riêng toggle và hit-rate input để không đánh đồng hai trường hợp.

9. RPM, TPM, concurrency và spend không cùng một quota

Reserve trước, reconcile sau

  1. Admit

    Check tenant/feature và provider capacity budgets.

  2. Reserve

    Atomic request/token/concurrency/spend allowance.

  3. Attempt

    Bound outputs/deadlines, tag attempt identity.

  4. Settle

    Actual usage evidence hoặc unresolved exposure.

Unknown usage không được tự biến thành zero.

Một request dài có thể tiêu nhiều input/output/reasoning budget, trong khi nhiều short requests có thể hit RPM hoặc concurrency trước TPM. Provider definitions về estimated/admitted/actual token usage và windows khác nhau; app cần request, token, concurrency và spend dimensions theo tenant/feature/tier. Invoice cũng có thể gồm image/audio/tools/cache/batch charges, không chỉ một token rate.

Reserve trước admission bằng known input estimate và bounded output/external-spend allowance theo contract; settle actual authoritative usage sau completion. Estimator không exact tokenizer/reasoning usage thì cần headroom/limits phù hợp. Concurrent admission phải atomic hoặc quota partitioned đúng; timeout/cancel không tự release toàn reservation nếu upstream work vẫn có thể bill. Giữ explicit unknown/reconcile state và receipts để không double charge/release.

10. Retry budgets, backoff và failure amplification

Classify retryable network/temporary capacity failures so với invalid request, policy rejection, unsupported schema và auth failure. Không retry y hệt payload invalid vô hạn. Exponential backoff với jitter giảm synchronized bursts nhưng không tạo thêm provider capacity. Chọn bounded retry ở một tầng hoặc coordinate retry budgets; nếu ba tầng đều tối đa 3 attempts, một logical request có thể thành tối đa 27 downstream attempts trong worst-case nested retry.

Shared overall deadline, admission budget, queue bounds và Retry-After handling phải đi cùng retries. Circuit breaker open giảm load vào unhealthy dependency; half-open probes cần bounded concurrency và tránh false recovery. Một provider slow không có nghĩa tất cả regions/models/routes cùng hỏng; phân scope health theo observed failure domains. Không record mọi user error thành provider outage.

11. Routing và fallback cần qualification theo task

Fallback có thể khác model capabilities, context length, tool/schema behavior, languages, safety profile, data region và price. Evaluate actual task slices và expected degraded behavior; không tự nói provider B “parity” trên mọi task vì endpoint trả HTTP 200. Prearrange capacity/quota hoặc fallback outage chỉ chuyển từ A sang B. Có thể pause batch, queue bounded work, serve eligible cached/public FAQ hoặc báo limited mode theo product policy.

Upfront routing khác student-first cascade. Ví dụ 100 requests, giả định small call cost 1 unit và large cost 4, route trực tiếp 80 small/20 large tốn 160 units; chạy small cho tất cả rồi fallback 20 sang large tốn 180 units trước classifier/validation costs. Quality phụ thuộc routing mistakes và joint outcomes, không chỉ share; latency tails và initial paid work cũng khác. Giá này chỉ là illustrative units.

12. Cancellation, backpressure và disconnected clients

Client abort nên propagate qua app/gateway tới upstream khi supported, bỏ queued work chưa dispatch và stop unnecessary downstream consumers. Nhưng request abort không chứng minh provider đã dừng compute/billing hoặc tool đã abort. Reconcile usage/effects theo actual receipts và giữ limitations trong run state. Một intentional background job có owner/retention riêng không nhất thiết bị cancel vì UI tab đóng; phân biệt job lifecycle với stream connection.

Slow client cần bounded buffers/backpressure và idle policies để không giữ vô hạn memory/connection. SSE reconnect với event IDs chỉ replay an toàn khi backend retained events và dedup/generation rules phù hợp. Không dùng reconnect để silently invoke model mới có tool effects; nếu retention không đủ, báo snapshot/restart contract rõ.

13. Metrics và traces: attribution, denominators và privacy

Record request/attempt IDs, tenant/feature tier, route/model revision, prompt/retriever/config revisions, cache layer/hit reason/age, input/output/cache token categories, finish reason, content/total latency, retries, failure class và usage evidence status. Logical request và provider attempts khác denominators; cost một successful user task có thể gồm failed attempts và fallbacks. Không cộng p95 của các stages thành p95 end-to-end.

Dùng consistent schemas và version conventions khi adopt OpenTelemetry/instrumentation; attribute names/stability có thể đổi, cần pin compatible SDK/schema thay coi một blog code sample là fixed standard. Trace sampling không tự cho phép lưu raw prompts/secrets. Store minimal authorized payloads/redacted samples khi thực sự cần diagnosis/evals, với access, retention/deletion và audit; high-cardinality user IDs không nên thành metric labels tùy tiện.

14. Prompt/model/cache policies là deployable configuration

Version đến rollback evidence

  1. Pin manifest

    Task/data/capability dependencies và rollback profile.

  2. Qualify

    Task slices, cache/fallback failures và operations.

  3. Expose

    Canary bounded với clear stop criteria.

  4. Monitor / revert

    Quality, usage, drift và cache artifact compatibility.

Đổi prompt hoặc cache threshold cũng là behavior change.

Manifest nên bind template/model route, retriever/embedding/index versions, tool schemas, safety settings, cache policy và gateway normalization. Pin available immutable revisions khi provider supports; nếu alias có thể đổi thì monitor task evidence/drift, không giả version string đủ reproduce. Rollback phải giữ compatible dependencies và prior config, không chỉ đổi model name.

Offline evals gồm streaming truncation, partial failure, fallback capability, cache false hits/staleness/ACL và billing reconciliation. Sau đó bounded shadow/canary theo data policy và online guardrails. Shadow vẫn có costs/data exposure; canary không tự causal proof. Cache rollout cũng cần version/invalidation plan, nếu không old response artifacts có thể sống qua config rollback.

15. Data policy theo từng boundary và artifact

Prompt/RAG context, tool outputs, embeddings, cached answers, provider state và traces đều có thể chứa dữ liệu nhạy cảm. Minimize/redact/tokenize khi task không cần raw data, route tới approved endpoints/regions theo applicable policy và verify provider retention/training controls thực tế. Không khẳng định mọi prompt luôn rời organization hoặc mọi endpoint có cùng retention: self-hosted/private routes và configurations khác nhau.

Source deletion cần propagation plan cho derived caches/indexes/logs và provider artifacts theo available contracts, với retention/backups/legal scope được định nghĩa. Không hứa mọi copy biến mất tức thì chỉ vì xóa một database row. Quản access và deletion evidence; semantic caches dễ bị quên nhưng có thể chứa personal answer dù query text chung chung.

16. Completion, stream và usage contracts minh họa

Các internal APIs sau không gọi provider thật. Tách logical request, attempt, output generation và usage settlement; server lấy principal/scope từ trusted authentication. Retry request ID không tự đảm bảo effect idempotency; tool actions giữ contract riêng.

POST /internal/llm-requests

Tạo bounded generation theo profile đã approve.

    GET /internal/llm-requests/{requestId}/events?after={cursor}

    Stream/replay theo retained event contract.

    200 text/event-stream: { eventId, generationId, type: "delta | complete | error | restarted", payload }

    17. Luyện giải thích production LLM decisions

    Bill tăng nhanh hơn traffic: bắt đầu từ đâu?

    Break down theo feature/tenant/route, attempts per task, input/output/cache usage, context lengths, tools và price/config changes. So sánh cùng window/task mix và usage evidence. Sau đó test context trimming, eligible response/prefix reuse hoặc routing bằng quality gates; không giảm cost bằng giấu failed/unsafe tasks.

    Provider headers nhanh nhưng answer chờ 20 giây thì sao?

    Headers/heartbeat không là first model content. Kiểm content deadline, queue/context/provider slices và bounded failover capacity. Retry chỉ khi visible/effect boundaries cho phép, giữ overall deadline và usage exposure. Đừng xem HTTP 200 là healthy answer completion.

    Stream được nửa câu rồi lỗi: nối fallback vào được không?

    Không silent splice từ independent generation. Dừng partial/error hoặc explicit restart với generation mới và clear UI. Reconnect cursor chỉ resume retained original events theo contract; tool effects có idempotency/reconciliation boundary riêng.

    Exact cache có luôn safe không?

    Không nếu thiếu principal/ACL/source/policy/time dependencies hoặc cached result có personal data. Kiểm effective identity, invalidation/current permissions và task semantics. Match cùng text không tự chứng minh context hoặc quyền hiện tại giống nhau.

    Semantic threshold tăng có chắc giảm false hits không?

    Trên fixed scores nó thường giảm số accepts, nhưng không đảm bảo remaining hits đúng hoặc quality tốt hơn theo mọi metric. Fixture wrong-intent0.96 vượt valid paraphrase0.94: threshold 0.95 giữ wrong hit và bỏ valid one. Cần labeled workload/calibration cùng deterministic scope checks.

    Prefix cache hit có tránh cả model bill không?

    Không: output vẫn generate và billed theo contract; input cache reads/writes, TTL/minimums và other usage còn phải tính. Response cache avoidance và prefix reuse có denominators khác nhau. Dùng authoritative usage để settle, không suy mọi cache hit là free.

    Client cancel thì trả hết reserved budget ngay không?

    Không nếu upstream usage/effects còn unknown. Stop new work, propagate supported cancel và reconcile actual evidence; release phần chắc không dùng theo contract, giữ uncertain exposure. Cancellation request không chứng minh remote compute hay billing dừng ngay.

    Fallback có uptime tốt hơn nhưng quality thấp thì sao?

    Định qualified task scope/degraded mode trước, kiểm tools/schema/data policy và capacity. Có thể hạn chế features hoặc báo limited mode, không silently giữ promise của primary. Evaluate quality/cost/latency theo slices và keep rollback/stop criteria.

    Giải thích và so sánh các cơ chế

    Các câu hỏi mở kết nối thuật ngữ với state, assumptions và failure boundaries. Thử đưa một ví dụ từ dự án của bạn trước khi đối chiếu lời giải.

    Khi nào semantic response cache có thể đáng dùng?

    Chỉ reuse khi câu hỏi tương tự thực sự có cùng answer contract: quyền, tenant, locale, freshness, tool/data snapshot, model/prompt revision và policy phải tương thích. Similarity cao không chứng minh semantic equivalence: “hủy” và “đừng hủy” hoặc hai mã hóa đơn gần nhau có thể gây wrong hit nghiêm trọng. Semantic cache không là prefix KV cache; hai loại cache reuse objects khác nhau.

    Chọn eligible tasks ít biến động và risk phù hợp, có namespace/access checks, TTL/version invalidation, evaluation false-hit cost và safe miss fallback. Đo quality theo slices, không chỉ hit ratio/cost saved. Exact cache cũng không mặc định an toàn nếu key thiếu authority/freshness scope. Với personal/private hoặc side-effectful tasks, bỏ response reuse hoặc dùng contract chặt hơn có thể hợp lý hơn tăng threshold.
