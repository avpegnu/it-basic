Building a Design Canvas: rendering, multiplayer and metadata

Follow a vector editor from a local canvas to ordered edits, durable recovery, isolated plugins and sharded live metadata, with property-conflict, journal-gap and cache-race experiments.

From input to safe shared state

  1. Local feedback

    The model and renderer respond immediately while marking edits pending.

  2. Order edits

    The file owner validates edits and decides property values.

  3. Persist and recover

    Journals and checkpoints have explicit boundaries and verified replay.

  4. Scale each plane

    Metadata shards and subscriptions do not share every canvas mechanism.

Ask what users see, who decides, where state persists and how it recovers.

  • Separate local feedback, authoritative ordering and durable acknowledgement; visible does not necessarily mean saved.
  • Property-level conflicts preserve unrelated edits, but convergence does not imply preservation of every user’s intent.
  • Snapshots must match their sequence and journals must retain contiguous suffixes; maximum sequence numbers do not prove correct recovery.
  • Canvas state, ephemeral presence and relational metadata have different load, freshness and security contracts.
  • Sandbox capabilities, cache generations and shard ownership are correctness boundaries that need testing.

Three kinds of state, three contracts

Canvas document

  • Shapes, layers and property edits require ordering, validation, undo and recovery.
  • Large documents and busy documents impose different limits.

Presence

  • Cursors, selections and viewports are often ephemeral and can use TTLs/coalescing.
  • Do not journal every mouse movement just to display cursors.

Metadata

  • Names, memberships, comments and permissions have relational invariants.
  • Live views need correct authorization and freshness, not merely sockets.

Assume a collaborative vector editor with shapes, text labels, layers, comments, team permissions and plugins. Stages follow engineering pressures rather than a private company timeline. We choose file-scoped authority to explain ordering; decentralized or CRDT designs may fit different offline and merge requirements.

The user’s drawing canvas contains document objects; architecture diagrams explain where those objects are processed and stored. Before scaling, agree on editors per file, maximum file size, offline behavior, save semantics, revocations, supported devices and acceptable data loss.

The document model determines synchronization

Separate object identity from array position. A property set carries file/object identities, property/value, schema version, client/session identity and operation identity. Server sequences represent accepted order; client clocks do not override authority. Validate property schemas and bounds rather than exposing arbitrary prototype paths.

A drag produces many intermediate positions but undo often treats it as one action. Coalesce unsent positions only when final positions are sufficient; do not discard structural or relative operations that carry meaning. Coalescing must preserve operation identities so acknowledgements cannot retire newer edits.

Twelve stages: change architecture under pressure

Select stages to inspect paths, responsibilities, decisions and exit criteria. A small modular design may remain sufficient; reaching the last stage is not a correctness requirement. Every service/storage split must preserve existing protocol and durable-state contracts.

A canvas inside the browser

Start with a small file that opens, selects and moves shapes, zooms and saves. A DOM shell can coexist with a custom canvas renderer when measurements justify it. This is an educational vector-editor design, not a claim about current private production systems.

Problem pressure: A daily-use tool needs responsive input, correct text/layout and intact files.

Architectural decision: Separate document models from rendering; version file formats and verify save/load round trips.

Costs and trade-offs: Custom GPU rendering adds font, hit-testing, accessibility and export work.

When is the next step needed?: Link sharing introduces simultaneous editors.

Opening and saving preserves IDs, geometry and schema, with frame timings measured on target devices.

An authority per file

Choose one active owner per file. Gateways route updates to it for validation and ordering. Ownership is a logical role, not necessarily an OS process in every implementation. Directory caches locate owners; activation and sink fencing exclude stale owners.

Problem pressure: Concurrent sockets send edits and may reconnect to different machines.

Architectural decision: Use file-scoped ordering, ownership epochs and stable operation identities.

Costs and trade-offs: Hot files remain owner-bound; failover needs recovery and admission control.

When is the next step needed?: Coarse conflict boundaries lose unrelated edits.

Two gateways cannot create two active writers for one file epoch.

Synchronize properties

Objects have stable identities and independent properties. Setting x must not resend stale fill/name values. Server order still chooses one value for concurrent writes to the same property; this does not merge both users’ intent or text. Clients track the latest pending identity per property.

Problem pressure: A drags a shape while B changes its color; whole-object writes erase B’s change.

Architectural decision: Use property patches, ordered echoes and matching-operation acknowledgement guards.

Costs and trade-offs: String replacement does not preserve concurrent character edits; undo needs context.

When is the next step needed?: Startup and file size begin to constrain usability.

An A1 echo cannot clear pending A2; clients converge while retaining unrelated fill.

Measure startup before changing runtimes

If parsing or initialization is limiting, evaluate a binary engine such as WebAssembly with suitable compilation and caching. Measure downloading, compiling, instantiating, deserialization, fonts and first interaction separately. Wasm does not automatically accelerate every workload or eliminate allocations and GPU stalls.

Problem pressure: The screen stays blank despite apparently adequate networking.

Architectural decision: Profile cold and warm starts and optimize their critical paths while preserving compatibility.

Costs and trade-offs: Toolchains, debugging, binary delivery and browser variation add cost.

When is the next step needed?: Server-side document work develops tail latency and noisy neighbors.

Compare the same files, devices and networks; parsing gains are not end-to-end gains.

Isolate document work

Separate networking from CPU-heavy model work when profiles justify it. Worker or process boundaries allow supervision, memory caps and smaller failure domains; IPC and queues still need backpressure. A native worker is one option, not proof of universal speed or memory safety at every boundary.

Problem pressure: A large file blocks shared work and raises other files’ latency.

Architectural decision: Use bounded queues, resource quotas and per-file restart paths.

Costs and trade-offs: Additional processes consume baseline memory and add IPC/deployment contracts.

When is the next step needed?: Third-party extensions need controlled document access.

Worker death respects acknowledged-state guarantees and gateways remain bounded under backlog.

Plugins are capability boundaries

Do not evaluate untrusted code in the application origin. Isolate or interpret plugin logic and expose narrow, validated document capabilities with quotas. Isolate UI frames and validate messages. Historical Realms-style shims were replaced after security issues; old designs are not current sandbox recommendations.

Problem pressure: Plugins need bulk edits without inheriting ambient application authority.

Architectural decision: Require user activation, scoped host APIs, bounded batches and independent server authorization.

Costs and trade-offs: A sandbox does not prevent exfiltration when policy permits both document reads and network access.

When is the next step needed?: Teams, files and comments create separate metadata load.

Forbidden-capability tests, budget termination and version/revocation controls work.

Buy metadata capacity deliberately

Measure plans, indexes, connection churn, locks and read/write mix first. Tuning, pooling, caching, larger instances and replicas may suffice. Route only stale-tolerant reads to replicas and define freshness for permissions and read-your-write flows.

Problem pressure: One relational database serves multiple domains near saturation.

Architectural decision: Optimize measured bottlenecks, bound pools and shed work before overload.

Costs and trade-offs: Replicas do not multiply write capacity and can lag; larger nodes still have limits.

When is the next step needed?: Independent table groups need separate ownership.

Load tests preserve latency/headroom and every read path has a freshness contract.

Partition table groups deliberately

Move a metadata domain with consistent backfill/CDC, parity checks and a cutover barrier. Cross-domain joins and transactions stop being automatically local. Routing switches must handle old clients, in-flight writes and rollback after destination writes, not merely flip configuration and delete the source.

Problem pressure: Different table groups compete for resources and ownership.

Architectural decision: Partition by domain/locality while colocating atomic invariants.

Costs and trade-offs: New network and recovery boundaries do not yet scale out one huge table.

When is the next step needed?: Non-canvas views need real-time updates.

Cutovers have fencing, known catch-up positions and count/content/constraint checks.

Subscribe to metadata views

CDC observes commits and a service identifies affected subscriptions for versioned patches or invalidations. This differs from the canvas plane. Consistent initial snapshots and stream handoffs avoid lost updates; reconnects need replay or resnapshot. CDC may replay after crashes and is not exactly-once transport.

Problem pressure: Polling file lists and comments repeats work across clients.

Architectural decision: Use query-scoped subscription state, authorization and bounded delivery.

Costs and trade-offs: Slow subscribers, revocations and CDC lag become operational state.

When is the next step needed?: Volatile canvas acknowledgements need clearer durability contracts.

Mutations during subscription setup remain visible and revocations stop unauthorized data.

Small journal entries and coherent checkpoints

Append sequenced validated changes and track durable prefixes separately from accepted/applied prefixes. Broadcasting before persistence can reduce latency but requires distinct syncing/saved states. Snapshots pin state at sequence s; recovery replays the contiguous suffix and publishes pointers only after durable objects/manifests.

Problem pressure: Periodic snapshots leave unsaved work windows and deployment spikes.

Architectural decision: Use batched journals, explicit durable acknowledgements, coherent checkpoints and tested replay.

Costs and trade-offs: Balance batching delay, storage cost, retention and replay time; p95 is not a worst-case bound.

When is the next step needed?: A metadata table outgrows one machine.

Crashes at each boundary cannot label edits saved without durable evidence.

Shard metadata by locality

Separate logical partitions from physical placement and route by shard key/ownership version. Colocate tables to keep common transactions local. Bound scatter-gather with deadlines, failure semantics and pool budgets. A proxy does not turn arbitrary SQL into free distributed transactions.

Problem pressure: Vertical partitioning no longer fits the largest table or tenant.

Architectural decision: Use key-aware routing, colocated invariants and staged logical/physical migration.

Costs and trade-offs: Hot tenants, cross-shard joins, sequences and schema rollouts need explicit support.

When is the next step needed?: Subscriptions and caches must follow topology and invalidation scale.

Stale routing cannot create dual writers and global queries have admitted, observable costs.

Separate session edges, shared query caches and per-database change readers when justified. Cache hashing and database routing partition different work. Estimate concrete activity

Assume 2,000 active files with six connected editors each; 10% are dragging at 20 accepted property updates/second. These are teaching assumptions, not product traffic or benchmarks. Averages hide the difference between one file with 500 viewers and 500 files with one viewer.

The assumed 160-byte update excludes transport, encoding, authorization, journal metadata and replicas. Egress depends on actual audiences and subscriptions rather than all online users. Measure layout work and checkpoint sizes separately; CPU can saturate before network links.

              Trace edits, opening, recovery and plugins

              Use Edit to distinguish local actions from durable journal acknowledgements. Rename follows a separate metadata/CDC/subscription path. Open and Recovery expose snapshot/stream handoffs and ownership fencing, which happy-path demos often omit.

              One edit, two data planes

              Component map; the complete ordered request paths are explained below.

              Canvas ordering/durability differ from relational metadata and subscription freshness. Select a trace to inspect each boundary.

              Edit and durable acknowledgement

              1. Send file/ownerEpoch/opId/property patches with authorization context.
              2. Route to the current owner and validate schema, permissions and limits.
              3. Append the batch and await the chosen durable boundary.
              4. Broadcast ordered changes with cursors and backpressure.
              5. Acknowledge operation identities/prefixes with precise save state.

              Open a file and hand off to its stream

              1. Authorize access to the file generation.
              2. Read an immutable snapshot pinned to sequence/schema/checksum.
              3. Subscribe from the snapshot sequence without a snapshot/live gap.
              4. Replay the suffix then stream updates in the same file context.

              Recover a file after a crash

              1. A fenced replacement owner loads a coherent snapshot at s.
              2. Replay the contiguous suffix, detecting gaps, duplicates and schema mismatches.
              3. Advertise readiness after recovery and accept contextual reconnects.
              4. Rebase or retry pending edits against authoritative state and current permissions.

              Rename a file outside the canvas

              1. Rename with the contract’s version/idempotency context.
              2. Commit the row and constraints in the relational authority.
              3. CDC carries commit cursors and may replay to consumers.
              4. Push scoped invalidations/results with access and generation checks.

              Plugin edits through the host API

              1. Validated capability calls do not inherit ambient origin authority.
              2. Edits use the normal protocol and quotas.
              3. The server independently checks permissions, schema and resource bounds.

              Property merging and pending guards

              Changing x and fill need not cause mutual overwrites. Concurrent x writes follow server order; replacing a whole string does not merge both users’ typing. Evaluate sequence semantics, OT or CRDTs for genuine collaborative text rather than generalizing coordinate behavior to every data type.

              The guard must identify the acknowledged operation. An A1 acknowledgement does not retire a later A2 on the same property. Ordered delivery and reconnect protocols matter; reordered broadcasts also need version checks. Once updates settle, clients reconcile with authority rather than retaining pending state forever.

              Trees, ordering and undo need more than property sets

              A safe structural mutation

              1. Validate context

                Check principal, file/epoch, object existence and schema.

              2. Check invariants

                Check parent type, cycles, order keys and versions.

              3. Commit the result

                Assign a sequence, retain retry results and update the model.

              4. Broadcast/reconcile

                Clients receive canonical results and actionable rejections.

              One decision boundary protects tree invariants.

              Reparenting A under B and then B under A must be rejected or resolved by a tree-preserving algorithm. A central authority can validate existence, types and ancestry in one serialized decision rather than allowing two stale checks to commit. This is a design option, not a claim about every product.

              Fractional ordering reduces sibling renumbering, but repeated float midpoints eventually exhaust precision. Equal concurrent keys and key growth need tie-break and reindex protocols. Creation/deletion are explicit, and stale property writes must not resurrect nodes. Undo records action/context and considers others’ changes rather than restoring an entire old document.

              A journal does not make accepted mean saved

              Define durability explicitly. Journal-before-ACK adds latency but protects acknowledged suffixes under stated storage/failover assumptions. Broadcasting first improves feedback but save indicators advance only with durable evidence. Save-latency percentiles do not bound worst-case loss; client buffers supplement rather than replace server guarantees and backups.

              A snapshot at s must encode the logical state after edit s, not a mutable mixture labeled with a recent sequence. Use a verified stable view or boundary. Manifest publication and collection respect readers and retained suffixes; upload initiation is not durability. Recovery validates identities, schemas, checksums, gaps and duplicate replay.

              Rendering has more budgets than FPS

              Startup

              • Measure delivery/compilation, decoding, fonts and first interaction separately.
              • Version cached binaries/assets and reject incompatible schemas.

              Canvas quality

              • Hit testing, shaping, color, clipping and scaling affect correctness.
              • Cull invisible work without compromising exported fidelity.

              Inclusive UX

              • Design keyboard navigation, focus, semantic inspectors and accessible alternatives.
              • WebGL/Wasm do not automatically provide accessible shape semantics.

              Separate input processing, mutation, dirty-region/layout work, command generation and presentation. Local drag frames should not await network round trips, but still expose pending/save state. Profile tails and long tasks on large files, mobile, missing fonts and low-memory devices; average FPS can hide input lag.

              Plugin isolation needs narrow, maintained authority

              Isolation does not replace policy. A plugin allowed to read a file and contact the network can transmit permitted data. Make data/network scope understandable to users and administrators; allowlists, signed versions, revocation and audit reduce exposure without proving every plugin safe. Servers still treat generated edits as untrusted.

              Do not reuse an old sandbox shim and assume review is finished. Test escapes, host objects/prototypes, messages, cancellation and quotas continuously. WebAssembly is an execution format; security depends on imports, runtime and host boundaries rather than the format alone.

              Live metadata needs coherent handoffs and repair

              Subscribing is not simply selecting rows and then opening a socket: a mutation can occur between them. Use a snapshot at cursor c plus a retained suffix, or register/buffer before snapshotting and reconcile versions. CDC/consumer checkpoints detect replay and gaps; separate database streams do not automatically share a global total order.

              Query results depend on principals, organizations, filters, schema and permission policy; a query hash alone cannot safely share private results. Revocations affect initial reads and ongoing pushes. Bound slow-subscriber buffers and use coalesced invalidations or resnapshot signals rather than retaining all events in memory.

              Shard keys preserve invariants and expose query costs

              A verifiable cutover

              1. Copy plus changes

                Backfill consistently and stream changes to a known barrier.

              2. Verify

                Check counts, sampled content, constraints and load behavior.

              3. Fence and switch

                Fence old writers, drain writes and publish new ownership.

              4. Observe and retain

                Observe while retaining recovery evidence and tested rollback paths.

              Post-write rollback needs a data path, not merely old configuration.

              Choose keys from access patterns and atomic invariants. File-scoped comments may colocate by file identity while organizational policies have separate authority. A large tenant can remain hot despite balanced hashing. Logical buckets aid placement changes but still need fenced ownership and cutovers. A proxy cannot preserve every query’s semantics automatically.

              Keep atomic joins/transactions local when needed; cross-shard mutations need genuine protocols or redesign. Bound scatter-gather and label partial results rather than presenting approximate counts as exact. Change readers follow database topology while shared caches may hash query contexts; those mappings differ.

              Review failures before adding features

              Measure input-to-frame, edit-to-accepted and edit-to-durable separately. Track journal gaps/lag, recovery duration, ownership conflicts, per-file resources, subscription staleness and rejected fills. Correlate file/session/operation/epoch identities without unnecessary document-content logging.

              Questions with reasoning and examples

              Should a canvas use per-property LWW or a CRDT?

              Start with the model, offline semantics and expected conflicts. Server-authoritative property patches can preserve independent x/fill edits, while same-property writes follow the chosen order. Evaluate sequence/CRDT/OT approaches for collaborative text or decentralized offline merging. Convergence alone proves neither intent preservation, tree validity, undo correctness nor durability.

              Why must an A1 acknowledgement not clear pending A2?

              A displays A2 at x=160 while the server echoes A1 at x=80. Retiring pending state by property name rolls the display back prematurely. Track operation identities and retire only the matching latest operation. Ordered echoes then reconcile authority; lost acknowledgements/reconnects still need retained results and deduplication.

              Does adding a journal guarantee no edit loss?

              A component name is insufficient. Check acknowledgement boundaries, storage/failover assumptions, suffix retention, checkpoint coherence and recovery logic. Asynchronous journaling leaves accepted-but-not-durable windows, and a measured percentile is not a worst-case promise. Backups address corruption/deletion under separate recovery points.

              What if recovery sees sequence 5 but cannot find 4?

              Do not advance to 5 and call recovery complete. In the fixture, edit 4 changes fill while edit 5 changes x; skipping 4 preserves the wrong color. Stop contiguous replay and obtain trusted recovery evidence or report failure. Gaps are skippable only when the protocol proves no required state is missing.

              Is a custom Wasm canvas sufficient for performance?

              No. Profile delivery, compilation, initialization, decoding, input tasks, layout, shaping, GPU stalls and memory. A DOM shell with a custom canvas can work, but accessibility and keyboard behavior need design. Compare matched workloads; faster parsing does not imply faster every interaction, and worker isolation adds IPC and memory costs.

              Does sandboxing a plugin protect document confidentiality?

              A sandbox limits exposed authority, while policy decides readable data and permitted destinations. File access plus arbitrary networking can allow content export. Use understandable consent/admin policy, scoped APIs, maintained isolation, quotas and server validation; UI review is not the security boundary.

              Why can a cache stay stale after invalidation?

              An earlier fetch can finish after invalidation and reinstall stale data. Capture the generation and validate it before installation. If invalidation is lost entirely, the generation does not change; replay/gap detection, verified barriers or bounded resnapshotting are needed. Both mechanisms require correct tenant/principal scope.

              Should the MVP be sharded immediately?

              Decide from requirements and measured runway. Tuning, pooling, larger nodes and replicas may buy time. Vertical partitioning separates domains; horizontal partitioning splits a table. Choose keys by locality/invariants, separate logical and physical placement and budget cross-shard work. Migrations need coherent copying, barriers, fencing and post-write rollback; proxies do not make distributed SQL free.
